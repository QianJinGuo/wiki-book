# AIOps MCP Agent

## 概述

AIOps MCP Agent 是结合 AIOps（智能运维）与 MCP（Model Context Protocol）的智能体架构，用于自动化 IT 运维场景。通过 MCP 协议，Agent 可以接入监控告警、日志分析、故障诊断等运维工具链，实现从告警感知到根因分析再到自动修复的全链路自动化。核心能力包括：多源告警聚合、基于 LLM 的根因推理、自动化故障处置剧本执行、以及运维知识库的持续学习。

## 主要内容

- MCP 工具链集成
- 告警聚合与降噪
- LLM 根因分析
- 自动修复剧本
- 运维知识沉淀

## 深度分析

### MCP 是 AIOps 从"观测"走向"行动"的协议桥梁

传统 AIOps 的价值止步于告警聚合与相关性分析——它擅长"看见"问题，却不擅长"处理"问题。MCP 的出现补齐了最后一段闭环：Agent 通过标准化的工具调用协议直接操作告警系统、日志平台和变更管理工具，把根因分析结论转化为可执行的修复动作。这使得 AIOps 从被动监控平台演进为主动运维执行体，告警到修复的平均时间（MTTR）成为可以直接优化的指标。

### 工具生态的广度决定根因推理的深度

LLM 根因分析的质量上限取决于 Agent 能触达多少运维数据源：Prometheus 指标、日志检索、链路追踪、配置管理、发布历史。MCP 工具越多，模型可交叉验证的证据链越完整——例如把"延迟突增"的时序指标与"最近一次发布"的变更记录关联，才能区分性能退化与配置回退两类根因。反之，工具匮乏会让推理退化为基于单一信号的猜测。

### 剧本执行需要"人机边界"设计

自动化故障处置剧本（runbook）执行是高风险动作：误操作可能扩大故障面。成熟的 AIOps Agent 需要为每个剧本定义权限分级——只读诊断默认放行、变更类操作需审批、破坏性操作强制人工确认。这一边界设计直接决定了 Agent 能否在生产环境长期运行，也呼应了 Harness Engineering 中"可控的自主性"原则。

### 运维知识库是持续学习的沉淀层

每一次告警处置、每一个根因结论、每一条修复记录，都应回写运维知识库，成为后续推理的参考案例。知识库的积累质量（而非模型参数）是 AIOps Agent 长期价值的分水岭——检索增强（RAG）让 Agent 在新故障中复用历史处置经验，避免重复踩坑。

## 实践启示

1. 从只读诊断场景起步（告警聚合 + 根因分析），验证 MCP 工具链稳定后再开放自动修复能力
2. 优先接入变更记录与发布历史等"上下文型"数据源，它们对根因推理的增益通常大于单纯增加指标源
3. 为每个 runbook 剧本建立权限分级，高风险动作保留人工审批环节
4. 将每次处置记录结构化回写知识库，形成"处置越多、推理越准"的正循环
5. 监控 Agent 自身的告警误报率与修复成功率，用运维指标反向评估 AIOps Agent 的成熟度
