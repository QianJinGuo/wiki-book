# Skill 路由优化：用 description 自进化修「能力越界」

> 📊 Level ⭐⭐⭐⭐ | 21.3KB

## 一句话结论

Agent 选错 Skill 时的默认做法是"抛个错误请求给模型改 description、再重跑整批"，问题是三件事都答不上来：**为什么改这里、改的是不是真正的冲突、下一轮能学到什么**——而且完整业务执行把查询/操作/通知耗时一起带进优化，改一句简介要等很久。千问 AI 平台这次的实践把问题拆成两半：**用本地首路由回放把反馈周期压到分钟级**，用「**归因与优化方向 → description 改写 → 回归验证 → 经验沉淀**」四段式把迭代变成可解释的。结果：34 条开发请求命中 **31 条（91.18%）**，候选核心阶段 **3 分 23 秒 / 3 分 25 秒**（并发 8）。作者明确标注：**这是开发集选优结果，不能代表未见请求或线上完整任务成功率**。

## 一、先定义"首路由"这个被优化的目标

**首路由 = Agent 第一次把请求交给哪个 Skill 或子 Agent。** 它决定接下来由谁承接，但**不代表后续执行成功**。这个区分是整套方法论的地基——否则"路由对了"会被误当成"任务成功了"。

作者用一组"相邻但不同入口"的场景把边界讲清楚：

| 当前任务状态 / 交付目的 | 通用首入口 | 需要保护的边界 |
|---|---|---|
| 对象未确定，要先发现、筛选再交接 | 发现与编排 | **不能承诺自己完成由其他能力执行的操作** |
| 对象已明确，直接操作 | 直接执行 | 不应接管尚缺必要筛选的请求 |
| 新建或修改周期安排 | 计划创建 | **在已有计划中执行 ≠ 新建计划** |
| 联合信息做趋势、风险或原因分析 | 综合分析 | 与单项数据查询区分 |
| 向外部渠道发送通知 | 通知投递 | **内部查询步骤不自动构成独立查询入口** |

最后一行的规则，正是全篇案例的来源。

## 二、机制一：本地首路由回放——把反馈周期从"分钟到小时"压到分钟

回放保留完整的「消息历史 → 模型 → 前置工具 → 追加调用与返回 → 模型」循环：**模型仍被真实调用**，受支持的检索、目录列举、简介读取由**冻结材料**提供，**观察到首次 Skill/子 Agent 调用就停止**，省掉后续业务执行。

比"单次分类"更接近真实选择过程，但**工具返回仍是受控模拟**。比较新旧简介时的冻结清单（少一项就不算可比实验）：**题目、人工预期、身份、模型参数、系统指令、工具及能力目录**——只修改授权范围内的 description。

**判分协议写得比多数评测文都严**：首次路由错误、参数非法、直接回复而没有路由、达到轮次上限，一律按既定协议计为**未命中**；接口异常、不支持的前置工具动作等**基础设施问题单列**，受影响的配对结果**不能用于候选晋级**；准确率之外必须报告**异常数与覆盖率**。还有一条防自欺的规则：**如果模型用了模拟器尚不支持的合理检索写法，应先修模拟器、完成预检、再重新冻结环境建立基线——不能为绕开模拟缺口去改 description 压制正常检索；环境变了也不能拼接旧成绩**。

## 三、机制二：先写归因假设，再动一个字

**流程是"从可观察错误开始"，不是从"我觉得应该这么写"开始。** 案例：一类请求要在会话内交付"汇总数据 + 记录明细"两张表，实际首路由却选了通知投递能力。可确认的现象只有两条——**预期承接方与实际选择不一致**、**用户没有要求向外部渠道发送通知**；至于模型为什么选错，**只能先提假设**。

| 归因假设 | 当前可检查的证据 | 区分假设的验证方式 |
|---|---|---|
| 通知描述把内部查询步骤写成了宽泛适用范围 | 简介同时列出查询汇总、读取明细与发送通知，未限定交付目的 | **只收窄通知描述**，看会话查询是否恢复、真实通知是否仍正确 |
| 数据交付能力没有表达组合查询场景 | 简介未说明汇总与明细可联合交付 | **只补充该场景**，看相关查询及相邻分析任务 |
| 两侧缺少交付目的的分工 | 双方都强调数据步骤，未区分会话展示与外部投递 | **分别改与联合改**，比较相邻边界 |

这张表的方法论价值在于**每条假设都配了一个"只改这一处"的验证设计**——否则改完之后无法归因。作者同时划了认识的边界：**这些证据能支持假设，却不能读取模型内部的真实决策原因；错例分簇只帮助发现共同冲突，不能证明某个根因已成立**。

**归因与修改方向必须分开记录**：同一个边界问题可以有多种修法（补正向适用条件 / 加排除条件 / 明确复合请求承接规则）。而且"简单提高某 Skill 优先级"也许能修复目标错例，**却可能把更多相邻请求错误吸进来**。所以生成 description 前先写清本轮方向，例如：

> 围绕最终交付目的区分入口。会话内交付汇总与明细的请求，由具备该能力的查询入口承接；向外部渠道发送通知的请求，由通知入口承接。保留两者已有能力，不因共享查询步骤而相互接管。

这个中间产物的作用是**让审校和评测有明确对象**：本轮是在澄清交付边界，还是在提高优先级？实际编辑有没有改变同一个分界？

方法来源标注得很老实：ProTeGi（用错误样本生成自然语言批评再编辑、BeamSearch + Bandit 搜候选）提供"先形成反馈再指导修改"的思路，但**这里的自然语言梯度是待验证的语义反馈，不是数学导数，也不保证归因正确**。

## 四、机制三：description 能改什么、不能改什么

**description 是模型选择能力时看到的职责简介**，需要表达四样东西：**适用条件、必要输入、交付物、相邻分工**。**它只能澄清已有能力，不能增加工具能力或扩大权限**——这条边界决定了"改描述"永远不是"加功能"的偷懒替代。

| 对象 | 修改前的表达问题 | 修改后的表达重点 |
|---|---|---|
| 数据交付入口 | 未说明汇总与明细的组合交付 | 支持联合查询并在会话内交付汇总表与记录清单；**用户无需先提出后续操作** |
| 通知入口 | 查询、生成内容、发送通知**并列**，混淆步骤与适用范围 | **先限定通知投递目的**，再说明查询只是内部步骤，**排除单纯会话查询** |

作者提炼的关键洞见：**这是把"会话数据交付"写成正向职责、把"通知投递"写成适用条件，并解释内部查询与外部服务范围的区别**——改变的是模型理解分工的方式，而不是关键词覆盖。

### 三类证据不能互相替代

这是全文最可迁移的一条纪律：

- **业务正文、工具定义、实现**回答「**能否做到**」（能力依据）——能力证据摘录不全应补原文；承诺超出实现应**收窄**（"返回分页列表不等于支持总体统计，输出某字段不等于支持任意组合筛选"；反过来，排除项也不能否定真实存在的独立查询或清单交付能力）。
- **人工确认的职责规则**回答「**应该由谁先承接**」。
- **回放轨迹**回答「**模型实际上选了谁**」。

## 五、机制四：回归验证——保护例、机械校验、语义审校、互补候选

**三道工序**：候选生成后先做**机械校验**（程序负责：恢复证据引用、应用替换、生成完整描述、核对实际差异和长度），再做**语义审校**（模型负责判断能力承诺、适用范围与消歧作用），最后进入回放。作者补了一句很关键的话：**当前生成与审校用同一模型的独立调用——职责分开不等于消除同源偏差**。

**一个真实的三方脱节案例**：某次候选在诊断里讨论 A 与 B 的竞争，实际修改主要澄清"计划创建"，审校又按"通知入口"检查——**每句话都可能合理，却没有改中同一个问题**。所以：**诊断、实际差异、审校必须围绕同一组竞争入口。**

**先测目标与保护例**：小批验证同时包含需要修复的错例与原本正确的保护例（会话查询、真实通知、以及用相似词但交付目的不同的请求）；**至少修复目标且保护不退化**才进入整体回归。整体回归再查**误吸、漏接与关键边界**，并且——**高分不能抵消重要保护失败**；复用观测必须同候选、同环境、同请求及对应重复轮次（**改过一句话，旧成绩就不能当新候选成绩**）。

**保留互补候选但不许直接合并**：总分较低的安全候选可能修复另一组错例，值得留在研究池（作者引 GEPA 的轨迹反思、逐实例表现与互补候选搜索为参考）；但**两个版本正确请求的并集只是搜索线索，合并后的 description 必须重新回放**。

**这轮结果能支持什么、不能支持什么**（作者写得非常克制）：

- 34 条开发请求命中 31 条；每题回放 **3 次按多数首路由计分**，三次各不相同计未命中（**不挑正确的那一次**）；
- **没有独立留出集**，已用于诊断和选优的历史题只能继续当开发/回归数据；
- 选定版本两道真实通知保护题均正确承接、查询与通知分界改善，但**这次同时改了两份简介，尚不能分离两侧描述及各句编辑的独立贡献**——单侧与联合修改的对照是下一步方向，不是已完成的实验；
- 剩余三题分别涉及：综合分析与单项查询、组合编排与前置查询、计划创建与业务执行。

## 六、机制五：把验证过程变成"下一轮能用的经验"

保存候选历史只能保证可追溯；要让下一轮少走弯路，得把反馈变成**可检索、可限定范围的经验**。而**归因经验与修改经验要分开存**：前者描述"什么错误模式可能对应什么原因"，后者描述"什么修法在什么条件下有效"。一次候选失败**不能直接推翻所有归因**——也可能是方向过宽、具体改写偏离方向、或模型波动。

经验条目应包含六项（这是可直接抄的 schema）：**错误模式 / 归因假设与证据 / 优化方向 / 实际编辑 / 验证结果 / 适用范围与反例**。其中"实际编辑"强调**记录两侧修改及最终差异，不能只存修改意图**；"验证结果"要含逐题修复、退化、保护表现、重复回放与**环境版本**。

**失败反馈也要足够具体**：格式错误要指出字段与允许值，能力误拒要给原句与证据，回放无收益要给逐题差异和反例——"上次被拒绝"无法指导下一轮。作者还自曝一处缺口：**曾出现新冻结版本未向首次生成传递旧反馈**，说明记录与消费之间仍有缝；下一步要核对"检索到哪些经验、哪些进了归因与方向生成、哪些因环境变化不再适用"。判据一句话：**旧经验可以成为线索，旧分数不能迁移。**

推荐迭代流程：**当前错例与冻结环境 → 提出归因假设 → 检索适用经验并复核 → 明确优化方向 → 生成并审校 description → 小批与整体回归 → 记录成功、失败及适用范围**。经验复用仍需在当前请求上验证；新记录进入时要**合并重复、区分冲突条件、保留被反例否定的方向**，否则经验库会变成"另一份错题补丁集"。

## 七、机制六：控制描述膨胀与反馈成本

**每遇一题就加一句例外，description 会越来越长、适用条件反而越来越窄。** 当前实现设了 **600 字符上限**，并要求**先替换错误边界、合并重复、删除冗余，再考虑新增**；作者同时点明局限：**硬限制只防止无限增长，不能证明规则已经泛化**（引 TextReg 关于提示词容量成本与规则适用范围收窄的联系，但声明其推理任务结果不能直接当本项目路由收益）。后续策略可试：**逐题覆盖、准确率与退化表现相同时优先短版**；从有效父版本生成压缩候选后**重新完整回归**，且**不能删除权限、真实能力或交接约束来腾位置**。

**成本要分清阶段**：本地首路由即停（省后续执行）、小批淘汰（省无效回放）、并发（缩等待）三者成本性质不同。34 题实验中两次自动候选的**生成、审校、小批与整体评测合计约 3 分 23 秒与 3 分 25 秒**，回放并发 8；**计时不含初始基线、收口复测、历史种子重测、报告和人工验收——不能写成"完整优化三分钟完成"**；早期不同题量/模型条件下的完整业务耗时也**不能直接换算成提速倍数**。当前计时只能说明候选反馈周期，不能估算从搜索到上线的总周期。

## 深度分析

### 它修的不是"描述写得好不好"，而是"能力越界"

案例的本质不是关键词没覆盖，而是**通知入口的描述把"内部查询步骤"写成了适用范围的组成部分**——于是"要两张表"的请求被当成"要发通知"。修法也相应不是加词，而是**把内部步骤明确降级为流程细节、把交付目的提为适用条件**。这篇因此给了一个比"prompt 优化"更准的名字：**这是在澄清职责边界**。推广一步：**凡是"相邻能力共享步骤"的系统（查询 vs 投递、草稿 vs 发布、只读 vs 写），路由错误基本都是这个形状。**

### "先写归因与方向"是把不可归因的迭代变成可归因的

默认流程"改完看总分"有两个致命弱项：**改好了不知道是哪句起效，改坏了不知道是不是方向错了**。加入"归因假设表 + 方向声明"之后，每一步都有可被反驳的对象：假设错了会暴露在"只改这一处"的验证里，方向错了会暴露在"实际编辑是否改变同一分界"的核对里。**这一层中间产物，比任何自动搜索算法都更决定迭代效率。**

### 三类证据的分离，是所有"AI 改配置"场景的通用纪律

「业务正文/工具定义回答能否做到；人工职责规则回答应该由谁先承接；回放轨迹回答模型实际选了谁」——三者**不可互替**。这条纪律直接排除两类常见错误：**用实现细节去论证职责**（"它能查数据所以该它接"）、**用一次成功轨迹去修改职责规则**（"模型这次选对了所以规则没问题"）。它也解释了为什么"承诺超出实现就收窄、能力证据不全就补原文"必须成对执行。

### 保护例机制是防"修一个坏两个"的唯一低成本手段

把"原本正确的请求"放进小批验证，并规定**高分不能抵消重要保护失败**，等于给优化装了负向约束。比这更细的一条是：**改过一句话，旧成绩就不能当新候选成绩**——它堵住了"复用历史通过记录"这条最常见的自欺路径。**在只有 34 条题的规模上，这两条比增加题量更能保证结论可信。**

### 最难的部分被作者留在了"下一步"

三处未完成说得很清楚：**没有独立留出集**（选优与诊断共用一个集合）、**同时改两份简介无法分离贡献**（单侧对照未做）、**经验检索是否降低迭代成本未验证**。这三条恰好是"能不能上线"的门槛——尤其第一条：**91.18% 是开发集最优，不是泛化证据**。这种自我限定的写法，比数字本身更值得作为模板。

## 实践启示

1. **先定义被优化的对象**：首路由 ≠ 任务成功；把"第一次交给谁"单独作为指标，否则评测口径会漂。

2. **用"冻结 + 早停"压缩反馈周期**：冻结题目/预期/身份/参数/系统指令/工具与能力目录，模型真调用、工具返回受控模拟，观察到首次调用即停。

3. **基础设施异常必须单列并禁止晋级**：接口异常、模拟器不支持的合理写法——先修模拟器再重建基线，别用改 description 绕过。

4. **归因假设要配"只改这一处"的验证设计**，并承认读不到模型内部原因；错例分簇只是线索。

5. **归因与修改方向分开记录**：先写"本轮是澄清边界还是提优先级"，再审校实际编辑有没有改中同一分界。

6. **description 只能澄清能力，不能扩权限**；四要素写全：适用条件、必要输入、交付物、相邻分工。

7. **三类证据不可互替**：能力依据（能否做到）/ 职责规则（该谁接）/ 回放轨迹（实际选了谁）。

8. **保护例与小批先跑**，且**高分不能抵消保护失败**；改一句话即作废旧成绩。

9. **互补候选可留池、合并必须重跑**：两个版本正确集合的并集只是搜索线索。

10. **经验库分"归因经验"与"修改经验"**，六字段存全（含实际编辑与环境版本）；旧经验可当线索，旧分数不可迁移。

11. **描述容量要有硬上限 + 替换优先**（600 字符），并联想到"容量膨胀=过拟合信号"。

12. **报告必须交代阶段边界**：3 分 23 秒只含候选核心阶段，不含基线/复测/报告/人工验收；不可换算成提速倍数。
