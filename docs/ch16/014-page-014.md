# 手机应用原生大模型：先定预算，再定架构

> 📊 Level ⭐⭐⭐⭐⭐ | 22.1KB

## 一句话结论

淘宝 MNN 团队开源的 **MNN-Pocket-0.3B**，价值不在"0.3B 能跑多快"，而在它示范了一套**倒着做**的模型设计法：**先写死应用的资源预算（<300MB 峰值内存、>200 tok/s、100 次推理 <1% 电量、能力对标 8B），再让架构、词表、数据、量化、推理引擎全部朝这个预算收敛**。他们把这套方向叫 **"手机应用原生大模型"**，并对起点做了一句很清醒的纠正：**"成功加载模型、完成一次对话，只是起点。"**

## 一、为什么"能跑"不等于"能用"

> "对于淘宝、闲鱼这类日常高频使用的应用，大模型必须**与其自带业务共享算力、内存和带宽**。同时，还得在**持续调用与多任务并发**下，兼顾响应时延、功耗和温升。"

这句话把端侧模型的评价标准整体挪了一格：**不是单次 benchmark，而是"融入日常使用"**。所以四个目标必须**同时在持续调用中被检验**——"在满足任务要求的同时，控制功耗与温升，保持整机流畅"。

## 二、四个设计目标（预算即需求文档）

| 维度 | 目标 | 定目标的理由（原文） |
|---|---|---|
| **速度** | 解码 **>200 token/s** | "参考高速云端模型服务的生成吞吐，力求在本地提供流畅的生成体验" |
| **内存** | 峰值 **<300MB** | "即使手机有 8~16GB，也需由系统与多个应用共享。以约 **500MB 的模型模块预算**为例，把推理峰值控制在 300MB 以下，可以为**上下文增长和集成开销保留余量**" |
| **功耗** | 单次增量 **<电池能量的万分之一**（100 次 <1%） | "控制**高频调用**的续航开销" |
| **能力** | 指定场景对标 **8B 级模型** | "兼顾中英文理解、世界知识与数学、代码推理，**重点强化指令遵循**，并为长上下文与多步骤任务保留扩展空间" |

内存那条最见功力：**预算 500MB、峰值只许 300MB**，剩下的 200MB 不是浪费，是**留给上下文增长和集成的余量**——**给未来的自己留空间，而不是把预算用满**。

## 三、关键数字：体积、内存、速度

**部署体积与运行内存（INT4）**：

| | MNN-Pocket-0.3B | Qwen3-0.6B | 差异 |
|---|---|---|---|
| 部署文件 | **173MB** | 340MB | **−49%** |
| 峰值 Metal 驻留增量 | **228MB** | 427MB | **−47%** |

测试条件写得很明确：iPad Pro M5 / Metal 后端 / 512 token，"模型加载与推理期间的峰值 Metal 驻留内存**相对加载前基线增加**"。业务含义也点透了：**体积小降低下载与更新成本，内存小给"页面、图片、视频等业务模块"留空间**。

**跨平台吞吐**（MNN 3.6.2、INT4、预热 1 次测 5 次取中位数、Prefill/Decode 分测）：

| 设备 / 后端 | Prefill | Decode | 对比 |
|---|---|---|---|
| iPad Pro M5 / Metal / 512token | **8,721 tok/s** | **466 tok/s** | Qwen3-0.6B 286 → **1.63×** |
| 骁龙 8 Gen 5 / CPU | — | **251 tok/s** | — |
| **iPhone 18 Pro（真机离线）** | — | **~350 tok/s** | MNN 引擎完全离线 |

**与 llama.cpp 对比**（4bit、骁龙 8 Gen 5）：**Prefill 1.51~2.90 倍，Decode 1.43~1.82 倍**。

**能耗**（一加 13 / 骁龙 8 至尊版 / CPU 4 线程 / 输入 1024 输出 128 / 三轮）：**约 2.7 J/轮**→"以 6000mAh 电池计算，执行 100 次同等负载累计增量能耗约占电池总电量的 **0.3%**"。

## 四、架构选型：用约束筛，而不是用直觉猜

这一步是全篇方法论最硬的地方。他们**先扫参数规模**："构建覆盖约 **50M 至 1.3B** 参数的稠密模型配置，在 iPad Pro M5、统一推理设置下测试"，结论是——

> **"约 300M 是该组实验中同时满足两项约束（<300MB 峰值内存、>200 tok/s）的最大候选规模。"**

**先找可行域的上界，再在这个上界里做能力最大化**——顺序与"先追能力再压缩"完全相反。

规模定了，再调深度/宽度/FFN/注意力，这里有一个很有说服力的**非单调性发现**：

| 层数 | 能力 | Decode |
|---|---|---|
| 16 | 较低 | — |
| **28** | **提升** | **355 tok/s**（选型对比口径） |
| 36 | **均分不再提高** | **323 tok/s（下降）** |

最终选 **28 层 + GQA**。注意作者特意标注了"这里的吞吐用于架构选型对比，与前述最终部署版本的测试配置不同"——**口径分离做得很干净**，这种自觉在厂商文章里不多见。

## 五、词表：0.3B 模型里被低估的成本中心

> "对于 0.3B 模型，**词嵌入与输出层会占用相当一部分参数**。更大的词表通常有助于压缩文本长度，也会增加存储、访存和输出投影开销。"

做法：基于 Qwen3 分词器，**151K → 64K，词条缩减约 57%**，减少词嵌入与输出层参数，"并降低逐 Token 生成时的**输出投影开销**"。

裁剪不是简单砍频次，三条纪律值得记：

1. **用覆盖中英文、代码、数学和指令格式的语料筛选**词条——按目标任务分布裁；
2. **保留特殊 Token、字节回退 Token 与必要的 BPE 合并依赖**——否则会出现无法编码的输入；
3. **避免过度裁剪造成序列变长**——"否则会抵消部署收益"。

第 3 条是最容易踩的坑：**词表小 → 同样文本 token 数变多 → Prefill 变慢、上下文变短**，净收益可能为负。所以词表裁剪必须**同时看"存储节省"和"序列膨胀"两个方向**。

## 六、模型与引擎协同：三层各管一段

作者把效率来源归成三条：**"参数规模与结构控制整体开销，词表设计减少存储与输出计算，推理引擎提高硬件执行效率。"**

引擎侧的具体动作：

- **CPU**："针对 Arm 点积与矩阵指令定制**低比特内核**"；
- **GPU**："根据不同架构优化**缓存访问、计算分块和线程配置**"，并提供"面向**高通 Hexagon 的专用后端**"；
- **执行路径**："为 Prefill、Decode 选择合适的执行路径，通过 **QKV、FFN 算子融合与 GPU 命令复用**减少访存和调度开销"；
- **投机解码**："针对 **8-draft 配置实现专用 GPU 内核**，优化多 Token 的并行计算"。

工程基础也给了：**MNN 16K GitHub Star、MNN-LLM 支持 200+ 款大模型、累计下载超百万次**——这解释了为什么它能把"模型设计"和"内核实现"放在同一张桌子上谈。

## 七、能力：不追总分，追"受约束输出"

他们选的评测重心很有针对性："评论抽取要求**忠实复现原文**，标签判断需要**限定在候选集合内**，结构化输出则必须**遵守字段与格式**。内容遗漏、无依据补充或类别越界，都可能影响后续处理。"——所以"重点强化**指令遵循与受约束输出**"。

| 指标 | MNN-Pocket-0.3B |
|---|---|
| IFEval（英） | **73.20**（比较模型最高） |
| IFEval-zh（自建） | **74.59**（最高） |
| 11 项平均 | **50.00**（高于同规模及 MiniCPM4-0.5B、Qwen3-0.6B） |
| MGSM-zh | **51.20** |
| HumanEval | **53.66** |

限定也写清了："具体业务仍需通过任务数据和验收标准验证。**知识密集型任务与复杂推理，也仍是模型需要继续提升的方向。**"

## 八、训练四段：每段解决一个具体失效模式

### 8.1 多阶段预训练：把"数据值不值得学"拆成两问

数据按**五个维度**标注分级：领域、文本形式、知识密度、难度、质量。其中两组分级最有意思：

| 维度 | 分级 | 区分什么 |
|---|---|---|
| **质量** | Q1–Q3 | 准确性、连贯性、完整性 |
| **知识密度** | D1–D3 | 有效信息含量、冗余程度 |

> **"区分'内容干净'和'信息充实'，提高筛选与配比的精度。"**

这两者经常被混为一谈：**干净但空洞的文本（低信息密度）和充实但粗糙的文本（低质量）需要不同处理**。难度则用 **H1–H3** 控制分布，并对"问答、表格和列表进行结构化整理"，"在部分数学与代码样本中**补充概念、推理步骤或解释**，增强可学习性"。

配比方法是**数据分桶 + 候选配方试验 + 实际混合训练**，"联合调整各阶段的采样比例"；关键一句：**"提高数学数据占比时，也同步考虑其中的质量、知识密度和难度构成"**——**调一个维度必须连带考虑另外两个**，否则配比失真。

规模：**约 4.1T token、四阶段**——语言与知识基础 → 强化中文/数学/代码 → 高质量数据**退火** → 上下文扩到 **32K**。

### 8.2 SFT Loop Engine：让"补短板"自动化

**316 万条** SFT 样本，闭环为：

```
训练 → 评测 → 失败归因 → 分配数据配额 → 合成与筛查 → 再训练
```

三个细节决定这套闭环是否可信：

1. "将失败回答**映射到细粒度任务类别**，结合历史训练数据分布，确定需要补充的**类别、语言与样本数量**"——配额是算出来的，不是拍的；
2. "合成环节**不直接读取原始评测题**"——防泄题；
3. "执行**去重和泄漏检查**"——防污染。

再加一条：**"通过回归评测检查新增数据带来的收益与其他能力的变化"**——补 A 不能塌 B。

### 8.3 MOPD：多教师 on-policy 蒸馏，把四个方向塞进一个学生

问题陈述很准："数学、代码、知识和指令遵循各有优化目标，混合训练需要处理目标之间的相互影响，**顺序训练也可能造成已有能力退步**。"

做法：**四条经过领域强化学习优化的教师路线**，"按样本所属领域选择教师，共同监督一个学生模型"。

> **"On-Policy 的关键是由学生先生成。教师读取学生实际产生的上下文，并在这些位置提供 Token 分布监督，使训练覆盖学生自身容易遇到的生成状态。"**

采用**分布匹配目标**，"为小模型提供更密集的学习信号"。效果：11 项平均 **35.79 → 50.00（10 项提升、1 项持平）**。

最后一句是工程上的点睛：**"多教师承担训练阶段的能力指导，部署时只保留一个 0.3B 学生模型，使能力提升无需增加端侧教师模型的存储与推理开销。"**——**蒸馏的收益留在权重里，成本留在训练时。**

### 8.4 QAT：让"训练出来的能力"活到部署版本

"将量化纳入后训练流程，通过 **Self-OPD 与量化感知训练（QAT）**，让 **W4A16** 学生在**自身生成的上下文**上，对齐**冻结的 BF16** 模型，缓解量化带来的能力损失。"

结果：**INT4 平均 49.59 vs BF16 50.00，仅降 0.41 分**——"这使前一章展示的部署效率与本章的任务能力，最终能够在**同一个 INT4 版本**上交付"。

注意这里的**对齐目标设计**：学生不是去拟合教师的输出，而是**在自身分布上对齐冻结的 BF16 自身**——避免"教师-学生分布差"在量化时被放大。

## 九、六个开源版本：按"你要做什么"切，而不是按"我们发了什么"切

| 版本 | 主要用途 |
|---|---|
| **Base** | 继续预训练、领域适配、基础能力研究 |
| **SFT** | 后训练研究、RL、蒸馏与消融实验 |
| **指令版** | 通用指令调用与业务任务适配 |
| **MNN** | W4A16 QAT 端侧部署（特定设备解码可达 466 tok/s） |
| **DFlash2** | 投机解码草稿模型（"一次提出 **8 个候选 Token**，由目标模型统一验证"；特定任务可达常规自回归的 **2.06 倍**） |
| **Dec** | "通过**决策头**完成候选选择类任务，在一次前向计算中完成候选打分" |

这份切分很务实：学生要 Base/SFT（"0.3B 的参数规模有助于**降低单次微调与评测开销**，支持更高效的多轮实验"）；开发者要指令版 + MNN；**分类/排序任务用 Dec（决策头），生成加速用 DFlash2**——**把"生成"和"判别"分开交付**，是很懂业务的做法。

## 十、两条实战链路

### 10.1 电商评论观点挖掘（天池）

输出四字段：**属性词、观点词、类别、情感极性**。约束很硬："属性词与观点词**必须来自原文**，类别与情感**必须限定在预定义集合内**，未明确表达的字段**按规则置空**"；一条评论多个观点需完整抽取。例子："'很好，遮瑕功能差一些'——同时包含整体正向评价和对具体功效的负向评价。"

**3,229 条评论**同配方 LoRA 微调 → 提交隐藏测试，判分要求**四元组四个字段全部匹配**：

| 模型 | F1 |
|---|---|
| **MNN-Pocket-0.3B** | **80.15** |
| Qwen3-0.6B | 77.47 |
| Qwen3-1.7B | 78.59 |

"以不到后者**五分之一**的参数规模，取得高出 **1.56 个百分点**的任务成绩。"这个对比有说服力，因为**判分是四字段全匹配**——同时考察抽取、分类与格式遵循，正是小模型最容易失分的地方。

### 10.2 全端侧流式语音对话

链路：ASR + MNN-Pocket + TTS，"集成**语音活动检测、语义断句和打断控制**，所有神经网络模块均通过 MNN 在设备本地运行"。流式设计："语音转文本后，MNN-Pocket 开始生成回答，文本**增量分段送入 TTS**，随后逐段播放，**无需等待完整回答生成**"；"用户再次开口时，系统**停止当前生成、合成与播放**，进入新一轮交互"。

**首音频时延 P50**：iPad Pro M5 **600ms** · 骁龙 8 Gen 5 设备 **935ms** · iPhone 13 Pro **1,055ms**。
**VoiceBench 九项总分 45.44**，"为报告所比较语言底座中的最高分"。

限定也给了："完整系统包含额外的 ASR、TTS 等模块，其**整体存储与内存需求需结合具体应用单独评估**"——没有拿语言模型的 173MB 冒充整机占用。

## 深度分析

### "应用原生"这四个字，是一次评价标准的转移

端侧模型的主流叙事是"把更大的模型塞进更小的设备"（压缩视角）。这篇的视角是反的：**从应用的资源账本出发，反推模型该多大**——500MB 模块预算、300MB 峰值上限、200 tok/s 下限、100 次调用 1% 电量。**一旦把预算写成约束，架构选择就变成了可行性筛选，而不是审美偏好。** 这个转向的实际后果是：**模型不再是"能力上限"的竞赛，而是"在预算内能力最大化"的工程**。

### 300M 这个数字是"算"出来的，这是最有价值的方法论

他们没有先定 0.3B 再解释为什么，而是**扫了 50M–1.3B**，发现"约 300M 是同时满足两项约束的最大候选规模"。**先找可行域上界，再在上界内最大化能力**——顺序很关键。多数团队的顺序是"先追能力，再想办法压"，结果往往在最后一步被迫砍功能或超预算。**把约束前置，等于把返工后置为零。**

### 36 层的反例，说明"规模定律"在端侧要重写

16→28 层能力提升，28→36 层**均分不再提高、吞吐还掉了 32 tok/s**。这说明在**固定内存预算**下，深度的边际收益会被**访存与调度开销**吃掉——**端侧的 scaling law 里有一项是延迟，而延迟不是线性的**。这条经验对做端侧模型的人比任何 benchmark 都有用：**加层之前先问，预算还够不够喂饱它。**

### 词表裁剪是"两头记账"的活

151K→64K 省了 57% 词条、显著压缩嵌入与输出投影，但代价是**同样文本的 token 数上升**。他们明确写了这条风险："避免过度裁剪造成序列变长，抵消部署收益"。**这是端侧特有的权衡**：云端词表大一点无所谓（一次 prefill 而已），端侧每一次多出的 token 都要付**解码时间 + 上下文占用**两份成本。所以端侧词表优化的目标函数不是"压缩率"，而是**"压缩率 − 序列膨胀率"的净值**。

### MOPD + QAT 的组合，解决的是"训练-部署落差"

两个动作各治一半：**MOPD** 治"多目标互相踩"（顺序训练导致能力退步，混合训练导致目标冲突）；**QAT** 治"训练精度≠部署精度"（BF16 学到的东西在 INT4 上打折）。合起来的效果是：**11 项平均从 35.79 到 50.00，再只掉 0.41 分落到 INT4**。这套"先合能力、再保精度"的顺序值得抄——很多团队反过来，先量化再微调，结果 QAT 的收益被后续训练破坏。

### SFT Loop Engine 与今天的"自进化"叙事是同一族

"训练→评测→失败归因→分配配额→合成→再训练"，加上"不读原始评测题""去重与泄漏检查""回归评测防塌方"——这跟 SkillHone 的"优化/评估双权限"、AWS Skill Eval 的"确定性断言"、支付宝的"7 项运行时指标"是同一套**闭环工程学**：**失败要能归因到可操作的类别，改进要有防作弊与防回归两道闸。** 区别只在对象：他们优化的是**数据配方**，别人优化的是 Skill、Prompt 或知识库。

### 它的诚实之处，也是它最可信的地方

三处主动限定：能力上"知识密集型与复杂推理仍是短板"；语音上"整机存储内存需单独评估"；吞吐上"架构选型口径与部署口径不同"。**厂商文章愿意区分口径、承认短板，通常意味着数字经得起复现**——这比任何"全面超越"的表述都更有信息量。

## 实践启示

1. **先写预算，再选架构**：内存/时延/功耗/能力四条约束定死，再让模型规模去适配，而不是反过来。

2. **预算不要用满**：500MB 模块里只允许 300MB 峰值，余量留给上下文增长与集成开销。

3. **扫参数规模找可行域上界**，在上界内做能力最大化——"最大可行规模"比"最优规模"更好用。

4. **加层要看边际收益**：端侧深度收益会被访存/调度吃掉，28 层可能优于 36 层。

5. **词表按目标语言与任务裁**，同时记账"存储节省 vs 序列膨胀"，保留特殊/字节回退/BPE 依赖。

6. **模型与引擎同设计**：算子融合、低比特内核、专用后端、投机解码——端侧效率一半在引擎。

7. **数据分级要拆两问**："值不值得学"（质量 Q1–Q3、知识密度 D1–D3）与"适不适合学"（难度 H1–H3）。

8. **调一个配比维度时连带看另外两个**（提数学占比时同步看其质量/密度/难度构成）。

9. **SFT 闭环要防作弊**：不读原始评测题、去重与泄漏检查、回归评测防能力塌方。

10. **多教师 on-policy 蒸馏**：让学生先生成、教师在学生分布上给监督；部署只留学生。

11. **量化放进后训练**（Self-OPD + QAT），在自身分布上对齐冻结的 BF16，别先量化再微调。

12. **按使用场景切版本**：Base/SFT 给研究者，指令版 + 部署版给开发者，决策头给判别任务，草稿模型给加速。

13. **评测重心放在"受约束输出"**：原文抽取、候选集合内分类、字段格式遵循——这才是业务真正会崩的地方。

14. **区分测试口径**：选型吞吐 ≠ 部署吞吐，语言模型内存 ≠ 整机内存。
