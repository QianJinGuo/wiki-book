# 淘小蜜分流模型：把四分类做成候选 logits 选择（Jev 与 System One 的生产对照）

> 📊 Level ⭐⭐⭐ | 23.8KB

## 淘小蜜分流模型：把四分类做成候选 logits 选择

> 淘天集团阿里技术（吴双）把客服 Agent 的分流做成了一个「只预测一个字母」的 7B 分类模型：不生成标签文本、只取首 token 候选 logits 的 argmax。线上旧链路 92.02%/84.73% → 新模型推全 96.17%/94.24%，两次双十一压测稳定支撑千级 QPS、平均 55ms、P99 约 150ms。文章后半用这套实践对照 Jev 与 System One，并逐条标注哪些是官方事实、哪些是社区推测。

## 业务：分流不是语义分类，是能力边界分类

淘小蜜客服 Agent 在回答前要先判断由哪个 Agent 承接：售前、售后、其他问题、意图不清四类。表面上是个普通四分类，难点在于**类别标准不是按通用语义划分，而是按不同 Agent 的能力边界划分**——订单评价、取消订单、价保、退款后的优惠券和红包都归售前；「退差价」不能见词就判：因质量不符、重量不足、少件、描述不符等**商家责任**要求退差价属售后，没有商家责任原因的退差价属售前；猫超、国际、百补、小时达、闪购等自营场景超出当前 Agent 承接范围时又可能归其他问题。这些规则带强业务属性，与预训练常识并不一致。

## 三阶段演进：从 ICL 到 7B SFT，再到选择题

**第一阶段：通用 LLM + ICL few-shot**。prompt 里写规则加示例、直接输出标签。开发快，但有三个硬伤：大模型调用成本高、响应慢、大促高峰期系统稳定性；业务规则与常识冲突时仅调 prompt 纠不回来；退款权益、红包、退差价等边界 case 继续加 few-shot 的收益递减。

**第二阶段：7B SFT（约 2.1 万条）**。解决了「模型不懂业务规则」，但标签直接写成「售前/售后」，输入格式、输出词与标签比例长期固定——对只有几种分类的任务，模型很容易把训练集里的词和标签记成捷径（见「红包」就倾向售前，可体验赔付红包可能属售后；见「退差价」就倾向售后，又错过无商家责任的售前）。训练数据也天然不均衡：早期二分类售前/售后约 3:7，扩成四分类后仍不等量，标签直出会把分布直接反映到输出词上，形成「更常回答售后」的先验。团队后来把业务标签**随机映射到字母**，让同一标签在不同样本对应不同字母，使答案字母分布接近均衡——注意这里平衡的是**输出 token 分布**，业务样本本身仍不均衡，随机映射的有限样本也不保证每个字母数量完全相同。

**第三阶段：改成选择题**。给每个标签分配选项字母，模型只学预测正确字母；线上一次前向、读候选字母 token 的 logits、取最大者映射回业务标签，实际生成的文本不参与判定。输出由候选表控制，因此不会返回候选表之外的标签或解释——**这与 Jev 所说「不产生幻觉」相似：解决的是输出越界，模型仍然可能选错候选项**。此时模型更像一个带语义理解能力的决策函数：输入对话与分类标准，输出有限候选之一及其分数。

## V1→V2 最大的一次跃迁：不是字母变多，是映射被打乱

V1 已改成四选一，但**标签与字母映射、选项顺序都没 shuffle**：售前永远对应同一个字母、同一位置，标签比例原样变成答案字母比例——除答案缩短成一个 token 外，与标签直出基本一致。V2 做了两件事：可用选项 token 从 4 个大写字母扩到 **26 个**，同时 **shuffle 标签→字母映射与选项在 prompt 中的顺序**。效果（884 条 benchmark：685 goodcase + 199 badcase）：V1 整体 **72.06%** → V2 **90.95%（+18.89pp）**，badcase 从 69.85% 到 69.35%（几乎没动）——提升几乎全在 goodcase，作者强调**不能只归因于字母从 4 个变 26 个，关键是固定标签的输出先验与位置捷径被削弱**。

## hardcase 回流：用 std_sigmoid 而不是 softmax 筛难例

V3/V6 引入 **std_sigmoid** 辅助筛选 hardcase：先对单个样本内的候选 logits 做标准化 `z_i = (logit_i − mean) / std`，再 `sigmoid(z_i)`。理由是 softmax 在 logit 差距大时轻易得到接近 0/1 的值，筛选边界样本不方便——四个 logits `[10,0,0,0]` 的 softmax 首名约 0.9999，std_sigmoid 约 0.85。标准化后再 sigmoid 只看**候选在本次选项组内的相对高低**，对整体平移与正比例缩放不敏感；它**不改变候选排序**，分数也不合计为 1，因此只用作挖掘难例的相对分数。线上记录第一名与第二名分差，从低分差样本中筛 hardcase、标注后回流训练，收益集中在 badcase：V3 → 92.76%（badcase 74.87%），V6 → **93.67%**（badcase 80.40%）。

**多 pattern 投票试过但没采用**：同一 case 构造多组选项映射再投票，两组整体准确率 92.42% 与 91.97%，都没超过单 pattern 的 92.76%。调试中观察到「退运费」换几组字母仍能正确判售后，但另一些边界 case 会随映射变化——说明模型已能处理部分未见映射，稳定性仍有空间。

## 线上效果与「为什么继续用生成模型」

去年 7 月 19 日旧链路准确率/召回为 **92.02% / 84.73%**；新模型逐步放量，到 9 月 3 日推全时两项为 **96.17% / 94.24%**（期间修过推理 bug、调过流量与分流标准，所以反映的是整套方案迭代效果）。

没有换成 BERT 分类器，理由是任务需要**读对话历史、判断最新消息是否覆盖旧意图、理解不断补充的业务边界**；固定分类 head 的输出维度与训练标签绑定，只改 prompt 加一条规则，边界未必跟着变。团队更想复用指令模型读规则与候选描述的能力，方便 zero-shot/few-shot 验证新标准。典型调试：同一句「这物流为啥往回返了？」，按原四分类（物流归售后）返回 `B`；把发货物流拆成新类别 `H` 后返回 `H`——两次都没有对话历史，说明模型跟的是**当前分类标准与候选集合**，而不是把「物流」固定对应某标签（但单个 case 不代表整体泛化）。他们也明确：**没有做同数据、同训练预算的 BERT 对照实验**，这里只是方案选择考虑。

## 最新一轮：动态映射 + 两阶段训练 + 部署精度

**数据重查**：20000+ 条训练样本中修正 **24 条高置信度错误标签**，另整理 **7000+ 条 hardcase** 用于 Stage 2；评测用 600+ goodcase、近 200 条历史 badcase 加 20 条最新专项 badcase。**动态映射**：同一 case 在不同 epoch 换一组选项映射并作为新训练数据（区别于 V1 所有样本共用同一张字母表）。组合数：四个标签映射到 26 字母有 `26×25×24×23 = 358,800` 种，再算四行选项排列，完整 prompt pattern 为 `358,800 × 4! = 8,611,200` 种——实际训练不必覆盖全部，目的是避免业务标签绑定固定字母。

**两阶段训练**：Stage 1 用通用分流数据学整体业务标准，Stage 2 用历史 badcase 与新业务边界 case（退款权益、红包、物流赔付、上下文继承、意图不清）继续训练。结果（四分类准确率 / 线上实际分流准确率）：V4 Stage 1 **79.41% / 93.55%** → V4 Stage 2 **80.20% / 94.57%**；V5 固定映射 Stage 1 **79.07% / 93.89%** → Stage 2 **79.19% / 95.48%**；**V5 动态映射 Stage 1 79.86% / 93.78% → Stage 2 82.35% / 95.81%**。Stage 1→Stage 2 的增益：V4 +0.79pp/+1.02pp、V5 固定 +0.12pp/+1.59pp、**V5 动态 +2.49pp/+2.03pp**；同阶段比较，Stage 2 动态相对固定四分类 **+3.16pp**、实际分流 +0.33pp。作者注明**只跑了一轮训练，收益是否稳定还需重复实验**。

**为什么有两套指标**：线上最终只有售前、售后两个承接方（售前 → 售前 Agent；售后、其他、意图不清 → 售后 Agent），后三类之间错分会影响四分类准确率但不改变实际路由。所以四分类看「模型是否理解业务标准」，实际分流看「最终有没有交给正确的 Agent」。

**部署精度坑（本节最值钱）**：同一 checkpoint 在 **RTX PRO 5000** 上的评测结果与单测、**H20** 不一致，V4/V5 多个 checkpoint 都受影响，切回 H20 才稳定复现。对单 token 分类这尤其致命：生成文本时某一步 token 排序变了，后面还有继续生成的空间，有时能把意思「圆」回来；而分流取的就是**第一个输出位置的候选 logits**，最大值对应哪个选项就走哪个业务分支，**候选排序一旦翻转，分类结果就变，没有后续 token 可以补救**。排查结论：不能只确认 checkpoint 相同，还要对齐卡型、推理引擎、量化配置、prompt 模板、候选 token 与并发方式。**压测**：两次双十一、稳定支撑千级 QPS、平均响应约 55ms、P99 约 150ms。

## 对照 Jev：共同点、差异与三种输出

**共同点**：都把自然语言理解转成**有限候选上的打分问题**，不依赖长文本生成，结果可直接进代码逻辑。**差异**：分流模型针对固定四类业务标签训练、领域窄；Jev 支持运行时定义的问题与候选，并提供 Choice/Score/Noul 三种统一接口；分流返回业务标签与候选相对分数，Jev 还强调**经过校准的 probabilities 与 confidence**。

**三种输出及从 logits 还原**：Choice（`choice` / `probabilities` / `confidence`，最多 255 选项，超出建议分层分类）；Score（`score` / `legend` / `probabilities` / `confidence`，对有等级编号与概率加权求和，如 `0×0.0 + 1×0.57 + 2×0.43 = 1.43`）；Noul（判断命题为真的概率，0–1，可写成两 logits 的 softmax 或对差值做 sigmoid）。`confidence` 由概率分布集中程度计算但**官方未公开公式**；`legend` 是调用方传入的元数据。因此三种输出的核心数值都能从 logits 推出，但不能逐字段复现 Jev 的返回——这也不能说明 Jev 底层用的是普通字母 token、special token 还是独立分类 head。

**「不产生幻觉」的准确含义**：TypeSafe 强调 Jev 不生成字符串，因此不会类型错误、不会返回定义外的值。这指的是**输出结构与取值范围**，不是语义判断一定正确——候选只有售前/售后时它一定返回其一，但仍可能把售前判成售后；open-bonsai-jev 的实验里出现过**以 0.998 置信度给出错误答案**。类型安全解决「结果能不能直接被代码用」，准确率与概率可信度要单独评测。

**社区三条复现路线**（都实现了类似接口，不等于复现了 Jev 内部结构）：①**冻结生成模型读候选 token logits**——SemIf 用冻结 Qwen3.5-4B，同一 state 下 21 个二元问题直接读 logits 中位 **1.023s**、生成精简 JSON **5.332s**；37 个 state × 21 criterion 共 777 个判断，逐条 333.1s → shared prefix + parallel suffix **38.8s**；open-bonsai-jev 同机制应用到低比特 Bonsai 27B（5.95GB 本地运行）。②**NLI 分类 head**——AlexWortega/openjev 对 Qwen3.5 做 NLI 后训练，取最后 token hidden state 接分类头输出 entailment/contradiction/neutral 概率，多选时把每个候选改写成 hypothesis 按 entailment 排序。③**编码器 + 选项打分 head**——Laya 用 ModernBERT-large / mmBERT + decision head，不做自回归，T4 上单问题约 33–40ms；其 typed-decisions 零样本 **0.362**、训练后 **0.766**，10 类客服工单分流只有约 **0.50**，作者自己建议在具体领域继续训练。

**校准数据（社区实测里最该看的一段）**：open-bonsai-jev 在 WANLI-256 上，Bonsai 2 27B 准确率 **74.6%**、平均置信度 **89.9%**、原始校准误差 **0.176**；温度缩放把 ECE 降到 **0.088**，但**准确率不变**。这说明直接对候选 logits 做 softmax 能得到总和为 1 的分布，却不等于真实正确率——温度缩放能让 0.8 更接近「同类样本约 80% 正确」，但不能把错误答案改对。

**作者对 Jev 结构的判断（明确标注为猜测）**：他更倾向于 Jev 沿用**语言模型的候选 token logits**（现有 lm head 的 vocab token 分数）而非另接分类 head，依据是三种输出都能从候选分数算出、SemIf/open-bonsai 已验证这条路可行、自己的分流训练也跑通；若把单一业务分类数据换成大量跨领域、不同候选与问题类型的通用任务，再用 RLCD 约束决策概率，是可能的方案。但 TypeSafe 只公开了新架构、并行 sampler 与 RLCD，**未公布输出层与训练配方**；多问题并行还需要推理侧专门设计，不能只靠「取一次 logits」解释。

## System One 分工：快模型在哪里、代价是什么

现在不少 Agent 把所有判断都交给负责回答的大模型：读对话、生成分类结果、决定查不查工具/转不转人工、再继续生成。复杂问题确实需要这种能力，但「这句话是不是在催退款」「现在要不要中断输出」这类判断在高并发链路里反复消耗推理时间与输出 token。**更具体的分工**：慢模型负责理解复杂诉求、规划步骤、生成最终答复；快模型在每轮对话与执行中处理分流、守卫、工具路由、打断与结果校验，输出只需有限选项与可用分数。

客服场景几乎可以逐项映射到 Jev 的三种接口：Agent 分流 → Choice（售前/售后/其他/意图不清）；双工判断 → Choice（`ignore`/`continue`/`interrupt`/`discard`/`force`）；意图或工具选择 → Choice；是否需要转人工 → Noul；用户情绪、风险与复杂度 → Score。**双工判断**是典型例子：响应未完成时收到新消息，要快速判断忽略、继续、中断、丢弃还是强制执行——每次调通用 LLM 生成 JSON 太贵太慢，写成规则又覆盖不了口语、省略与上下文相关表达。

**多问题共享一次 state**：请求里只传一次对话、订单与 Agent 状态，再并行提出多个问题（路由到哪个 Agent、是否打断、当前意图、是否需要转人工）；TypeSafe 接口本身支持对同一 state 提多个独立问题，并把减少重复上下文计算作为主要能力之一。但作者提醒：**具体能省多少延迟，要在客服真实输入长度、并发量与部署环境重测**；共享模型也意味着一次更新可能同时影响分流、双工与意图判断，因此每个模块仍要保留独立评测集、阈值、监控与回退。

**接入时真正要看的指标**：准确率、概率校准、覆盖率、回退比例，以及整条 Agent 链路的 P99——如果新业务没学好，快模型先跑一遍、慢模型再重做一遍，RT 与成本反而增加。

## 深度分析

### 输出长度只是表象，捷径先验才是泛化失败的主因

V1 把标签直出改成四选一后几乎原地踏步（goodcase 72.70%、badcase 69.85%），这个结果常被误读为「选择题没用」。真实原因藏在训练目标的结构里：售前永远对应同一个字母、出现在同一个 prompt 位置，样本比例原样变成答案字母比例——对模型而言，除答案缩成一个 token 外，任务与标签直出并无区别，仍可依靠「见红包就答固定字母」这类浅层捷径拟合训练集。V2 同时扩字母池并 shuffle 映射与顺序才换来 +18.89pp，说明起作用的是削弱固定输出先验与位置捷径这一机制本身，字母池从 4 扩到 26 只是给 shuffle 提供了空间。这与 [SFT 与预训练的关系](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/llm-pretraining-vs-sft.md) 中「SFT 容易拟合表层模式而非学会判断条件」的一般观察一致：标签不均衡不是靠重采样解决，而是让输出 token 分布在统计上均衡，业务样本本身保持不均衡。

### 三种输出都能从 logits 还原，校准却是独立工程

Jev 的 Choice/Score/Noul 三个接口字段各异，但核心数值都能从候选 logits 出发推出：Choice 取 softmax 后的 argmax，Score 对等级编号按概率加权求和，Noul 等价于对两个 logits 的差做 sigmoid；无法逐字段复现的只是 confidence 的未公开公式与 legend 这类调用方元数据。社区实测揭示了更关键的事实：softmax 得到总和为 1 的分布不等于真实正确率——Bonsai 27B 准确率 74.6% 而平均置信度 89.9%，温度缩放把校准误差从 0.176 降到 0.088，准确率却纹丝不动。淘小蜜团队在自己的实践里撞到同一堵墙：std_sigmoid 只保留候选在本次选项组内的相对高低，不改变排序、分数不合计为 1，因此被刻意限制在难例挖掘这一用途上；而一旦想按分数决定是否转人工或是否升级到慢模型，就必须对每个分数区间单独做校准。「打分」与「让分数可信」是两件事，前者一个 softmax 就够，后者是独立的训练与评测工程（分数怎么信，见 [决策模型的三个可调旋钮](https://github.com/QianJinGuo/wiki-public/blob/main/entities/decision-model-jev-threshold-calibration-logit-tuning-alibaba-2026-11-06.md)）。

### 单 token 分类把部署精度问题变成单点故障

生成式模型对推理精度扰动有天然缓冲：中间某个 token 的排序变了，后续生成还有空间靠上下文把意思「圆」回来。候选 logits 分类没有这个余地——取的就是第一个输出位置的候选 logits，argmax 对应哪个选项就走哪个业务分支，候选排序一旦翻转，路由立刻翻转，没有任何后续 token 可以补救。这解释了同一 checkpoint 在 RTX PRO 5000 与 H20 上评测不一致为何如此致命：对生成任务这种偏差可能只是措辞变化，对分流模型则直接改变业务分支。它暴露的对齐面也不止 checkpoint 一项，还包括卡型、推理引擎、量化配置、prompt 模板、候选 token 集合与并发方式——任何一项漂移都会让线上 logits 与离线评测失去可比性。

### 从业务内 shuffle 到跨任务泛化的距离

动态映射与两阶段 hardcase 训练的组合拿到了本轮最好成绩（四分类 +3.16pp），但它解决的仍是单一业务内部的捷径问题。要走到 Jev 式的跨任务泛化——运行时候选、运行时问题类型——中间还差一层多任务混合训练：让候选数量、标签描述、问题类型与 state 在训练中都发生变化，模型才有机会把「根据当前标准判断」的能力迁移出去。Laya 的成绩单是这条路的现实校验：typed-decisions 训练后 0.766，10 类客服工单分流只有约 0.50，第三方用仇恨言论数据集测试原始模型仅 22.10%——响应快与输出格式稳定并不自动带来新业务上的准确率。此外字母 token 自带预训练先验，对得分接近的边界 case，换一组字母仍可能翻转结果；团队为此准备了三组验证映射观察一致率，而不是只看平均准确率。

## 实践启示

1. **先 shuffle 再扩容**：把分类改成候选 logits 选择题时，第一步 shuffle 标签→字母映射与选项顺序，其次才是扩字母池。V1 只把答案缩成一个 token 而不动先验，效果与标签直出无异；4 标签 × 26 字母有 358,800 种映射，训练不必覆盖全部，只需避免业务标签绑定固定字母。
2. **难例挖掘用相对分数，置信度决策前单独校准**：筛边界样本用组内标准化（std_sigmoid），不要拿 softmax 概率当难例信号——logit 差距大时 softmax 轻易给出 0.9999。反过来，一旦要把分数用于「是否转人工/是否升级慢模型」，必须先对每个分数区间验证真实准确率；温度缩放能修正 ECE，却不能把错误答案改对。
3. **单 token 分类按单点故障对待部署精度**：评测与上线前固定 checkpoint、卡型、推理引擎、量化配置、prompt 模板、候选 token 与并发方式的组合；换卡复现不了离线指标时，先怀疑推理栈漂移而不是模型本身。
4. **分类指标与路由指标分开报**：售后/其他/意图不清三类之间的错分不影响实际路由；本轮动态映射的收益主要落在四分类指标（+3.16pp）而实际分流只有 +0.33pp——优化投入应跟随真实业务损失，两套指标都要保留。
5. **分类边界调整先改 prompt 后训练**：生成式底座读规则与运行时候选的能力，允许新业务标准通过改 prompt 加评测集快速验证（如把物流拆成新类后模型返回 H）；验证不过再补数据训练，不要一上来就重训或改输出层。
6. **快模型接入要防「成本反转」**：共享一个 System One 模型承接分流、双工、意图等高频判断时，每个模块保留独立评测集、阈值、监控与回退方案；若新业务没学好，快模型先跑一遍、慢模型重做一遍，延迟与成本反而更高。准入要看准确率、校准、覆盖率、回退比例与整条链路的 P99。
