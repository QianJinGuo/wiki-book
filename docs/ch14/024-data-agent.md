# 高德 Data Agent：分析是两段翻译，可靠性却沿链路连乘

> 📊 Level ⭐⭐⭐⭐ | 16.8KB

## 一句话结论

高德商业智能中心把"数据分析"重新定义成一件事：**坐在真实世界与数字世界之间的翻译**。一次分析是**两段往返翻译**——**降维**（业务语言层层译成可执行的查询语言）与**升维**（数字层层回译成带结论、带判断的业务语言）。而这件事真正的拦路虎，不是 SQL 写得对不对，是**可靠性会沿链路连乘**：每步 99%，**10 步只剩 90.44%，50 步约 60%，100 步仅三成多**。

## 一、为什么数据分析比 AIGC 难：容错曲线完全不同

作者的对照极为锋利：**生文、生图、生视频这些 AIGC 场景里，用户 10 次里 1 次超预期，就像中彩票一样满意；但数据分析你连续对 10 次，第 11 次错了，用户对 Agent 的信心就会瞬间崩塌。**

所以"每一步的准确率"在这里不是平均分，而是**乘法因子**。这也解释了行业现状的尴尬：**"能跑通 SQL 取数的很多，能跑准的也不少（L2 阶段），但能真正回答业务问题、给出靠谱判断的很少。"**

## 二、两段翻译：降维与升维

- **降维**：业务语言 → 机器能执行的查询语言。难处在"目标、口径、时间、跟谁比，全靠默认共识省略着"。
- **升维**：跑出来的数字 → 带结论、带判断的业务语言。难处在"把一堆数字重新装配成一句能拍板的话"。

组织里长出数据运营、数据分析师、数据产品经理、数据开发这些角色，本质是**在弥补"人类无法直接理解原始数据"这个限制——每一层都在翻译，成为下一个环节人脑能处理的形态**。作者称之为典型的工业时代设计逻辑：**把每个环节高度专业化，以换取规模化**。

对变革节奏的判断也值得记：**AI 会变革这个范式，但不会太快——"2～3 年吧，也可能更久，或许是一代人"**，因为"**技术只是器物层面最早期的变化，也是最简单的一层**"。

## 三、CFHL：给 Agent 补四样东西

| 补什么 | 通俗说法 | 决定什么 |
|---|---|---|
| **Context**（补知识） | 脑子里有货——知道业务在说什么、口径该怎么算 | **能不能做** |
| **Function**（补能力） | 手上有活——会取数、会算、会验 | **能不能做** |
| **Harness**（卡校验） | 心里有尺——做完先自查，**过不去不许出门** | **敢不敢信** |
| **Loop**（留兜底） | 事后有账——人在关键处接手，做过的事有记录、有回收 | **敢不敢信** |

判据一句话：**"前两样决定能不能做，后两样决定敢不敢信。"** 这也正是熟练分析师靠谱的四件事。

## 四、第一步：业务需求 → 分析需求（厘清）

> **"需求理解错了，口径再准、SQL 再对，也只是一个错问题的正确答案。"**

人类靠四样先验秒懂，Agent 要逐样补齐：

| 人脑机制 | 具体表现 | Agent 对应 |
|---|---|---|
| **动态画像感知**（情景记忆） | 知道你是谁（老板还是同事）→ 决定你要看进度、风险还是增量 | 提问人画像 / 记忆系统 |
| **时空对齐与标记**（时间戳） | 知道"最近"对你意味着什么（季度 review → 本季度 + 环比 + 同比） | 意图识别与澄清 |
| **领域本体认知**（颞叶新皮层） | 懂美食这门生意靠什么赚钱、处在什么阶段、和谁竞争 | 知识库 / 知识图谱 / 业务本体 |
| **程序性记忆与模式提取**（基底神经节） | 有用了三年的分析框架与手感，能快速初判 | 从经验中学习与自我反思，把跑过的分析沉淀成可复用框架 |

产出目标写得很务实：**一份写清目标、边界、方法的《详细分析需求》，给后面五步画一张能照着施工的图纸**——"有了清晰的交付目标，Agent 的执行就不会过于发散与偏离"。

## 五、第二步：分析需求 → 数据需求（口径与 SQL）

**一个"收入"躺着三个口径**：应付 GMV、实付 GMV、核销 GMV，退单算不算？"这是一个没有 AI 时就存在的难题，只是在 AI 时代被放大了数倍。"更麻烦的是：**"AI 是很难承认错误的。为了满足主人的愿望，它会开始说一些善意的谎言，更离谱的是，它还能把编出来的数解释一通。"**

**双主线**：

- **主线 NL2Metric2SQL**：列查数目标 → **官方指标词典召回候选（实在没有就诚实说没有）** → 对应具体表与字段 → SQL 构建 → 门禁校验；
- **支线 NL2SQL**：无指标定义 → 寻找可解数据表 → 命中 → 理解元数据 → SQL 构建 → 门禁校验。

**知识侧要建两样东西**（都不轻）：

- **指标字典**（指标定义、可用状态、口径、应用场景）——"要维护统一、高质量、常态化更新的指标字典，其实很难"，现实是"口径根本形不成稳定共识，要么散落在各处的数据集和代码里，要么只存在少数几个人的脑子里"；高德**花了一年做指标统一与治理，共 2000+ 指标，仍在进行中**；
- **数据说明书**（表、字段、数据血缘）——AI 时代冒出"**AI Friendly**"这个新词：**从面向人类可读，转向面向机器推理**；高德借这波清理了 **1000+ 待下线表**，把重复加工与孤儿表理出来，"对数仓整体做了一次体检"。

**校验侧两道门**：

1. **SQL 逻辑错误门禁**——数据模型与查询场景越复杂，LLM 写的 SQL 越不能信。高风险清单可直接当检查表：**Cube 多维模型、不可聚合字段、比率、半可加/不可加指标、N 天留存计算、多层级维度上卷下钻级联、维度枚举与筛选、去重口径、收入双算、多表 Join**。
2. **可得性核对（防幻觉的关键）**——查询前先过"有没有"：**这张表在不在、这个字段有没有、这个粒度支不支持、目标值/对比基准/去年同期在不在库里**；凡是要用却拿不到的，**一律不许编，只能老实报错**："这项缺失 / 这个维度拆不了 / 没有去年同期"。

理由被写得很直白：**"大模型有个致命的讨好型天性：你要什么，它就给你什么，哪怕这东西根本不存在。你问这个月目标多少——没有目标，它会一本正经编数，并且看起来很合理；你说按门店拆一下——表里没门店字段，它会凭空虚构一列。"** 而且这不是历史问题：**"到目前为止，我们线上运营时还是有 1%～3% 的任务里，LLM 会幻想出不存在的表和字段。"**

本节收束那句几乎可以当数据 Agent 的墓志铭：**"很多人以为 Agent 取数的难点是会不会写 SQL。其实真正的坑是口径和幻觉。写得出来不难，写得对、以及拿不到时肯承认没有，才难。"**

## 六、第三步：数据需求 → 数字结果（体检）

分析师拿到数第一反应不是用，是**扫一眼对不对**，靠四种"老师傅经验"：

| 直觉 | 具体判据 |
|---|---|
| **量级感** | 美食一天的 GMV 不可能只有几千，也不可能一夜翻十倍 |
| **逻辑关系** | 实付不可能大于应付、转化数不可能大于点击数、各项拆分加起来得等于总数 |
| **常识边界** | 比率落在 0～100%、点击率不可能 40%、分母不能为零 |
| **记忆对照** | 跟昨天/上周/去年同期比，突然多出一个数量级那准有鬼 |

心理学上这叫**知晓感（Feeling of Knowing）**那杆秤给出的读数——它触发"要不要再验证一遍"的开关。Agent 要做的，就是**把这直觉翻译成机器能自动跑的检查规则**，把"扫一眼"做成**强制门禁**。

**工程权衡这一段是全文最值钱的实操经验**：校验越多越慢越贵，所以要按重要性与风险决定跑到哪一档。**"最早我们把校验全打开，跑完数都要过一遍。数确实稳了，但一次问数从 30 秒变成 600 秒。用户的问题从'这数对吗'变成了'怎么这么慢'。后来按风险分档，日常问取数只留正性校验，例行汇报的才全量。"**

## 七、现状与自我定位

- **WAU 450 人左右**，**L2 智能问数准确率稳定 85%+**；
- 自评克制："**离好用还有距离，正在努力往 L3、L4 迈进**"；
- 本篇只讲**降维三步**，升维三步（结论、归因、行动建议）在**下篇**。

## 深度分析

### "两段翻译"这个定义，把 Data Agent 的失败点从"技术"挪到了"语义"

大多数 Data Agent 项目按技术环节拆（意图识别、检索、SQL 生成、执行、总结），于是优化目标也变成各环节指标。而"翻译"这个定义逼你问一个更难的问题：**这次翻译丢失了什么？** 降维丢了业务默认共识（"最近"是多久、"表现"看哪几件事），升维丢了判断（数字对但结论错）。**一旦承认是翻译问题，"补知识/补能力"和"卡校验/留兜底"就有了明确的挂载点（CFHL），而不是一堆散装模块。**

### 可靠性连乘，是数据分析必须"慢下来"的数学理由

0.99^10 = 90.44%，0.99^50 ≈ 60%，0.99^100 ≈ 36%。这组数字一摆出来，"端到端一次到位"的幻想就结束了——**任何六步以上的分析链路，都必须假设"中间会有错"，于是必须在链路上放可验证的检查点，而不是在末端放一个更会说话的模型**。这也解释了为什么高德宁可把"体检"做成强制门禁：**门禁的价值不在提升单步准确率，而在阻断错误的向后传播。**

### "可得性核对"是对 LLM 讨好型天性的结构性对冲

提示词里写"不知道就说不知道"基本无效，因为**幻觉的诱因是用户的期待，而不是模型的无知**。高德的做法是把"存在性"变成查询前必须通过的独立检查：表在不在、字段有没有、粒度支不支持、对比基准在不在库里。**这本质上是把"能不能答"从模型判断改成系统查询**——与淘宝智能建场的"确定性优先"、速卖通的"状态码不让模型猜"完全同源。而 1%~3% 的残留率说明：**这道闸必须常开，不能当一次性修复。**

### 30 秒 → 600 秒 → 分档，是"质量-成本"曲线的一次真实测量

这条经验值得所有做校验的人抄下来：**全量校验把正确率拉满的代价是 20 倍延迟，而用户的痛点会立刻从"准不准"切换到"快不快"**。解法不是折中，而是**按风险分档**（日常问数只留正性校验、例行汇报全量）。这与 HarnessPro 的"lite/medium/heavy 三档"是同一结论的两次独立发现——**校验强度应该是可配置的产品维度，不是全局常量。**

### 2000+ 指标治理一年、清理 1000+ 表：Data Agent 的真正成本在数据侧

文章最诚实的地方是它没把功劳给模型：**指标字典是花一年统一治理出来的**，口径共识"根本形不成稳定共识"是常态；数仓还借着 AI 的由头做了次体检（下线表、重复加工、孤儿表）。**"AI Friendly"这个词的要害不是格式，而是"面向机器推理"这一取向**——它要求元数据、血缘、口径都以机器可判定的方式存在。**这意味着 Data Agent 项目的工期，大概率由数据治理进度决定，而不是由模型选型决定。**

### 85% 与 95% 的差距：不同团队、不同口径下的"准确率"不可直接比较

库里另有一篇高德信息业务中心的实践称盲测 40%→95%（线上灰度 90%），本篇商业智能中心是 L2 稳定 85%+。**两个数字不该被拿来比高低**——团队不同、指标定义不同（盲测 vs 线上稳定、L1/L2 分级口径不同）。**跨文章引用准确率时，必须带上"谁测的、怎么测的、测的是哪一级"。**

## 实践启示

1. **先定义"翻译"再拆模块**：降维（问题→查询）与升维（数字→结论）分开设计，各自的失败模式不同。

2. **算一遍可靠性连乘**：链路有几步、每步准确率多少，先算出端到端上限，再决定要不要加检查点。

3. **CFHL 四件套当清单**：Context/Function 决定能不能做，Harness/Loop 决定敢不敢信——任缺一项就别上线。

4. **需求厘清阶段要补四类先验**：提问人画像、"最近"的时间对齐、领域本体、可复用分析框架。

5. **指标字典是地基**：没有官方口径就诚实说没有（走 NL2SQL 支线），别让模型自由发挥口径。

6. **SQL 门禁按高风险清单查**：Cube、不可聚合字段、比率、半可加指标、N 天留存、上卷下钻、去重、收入双算、多表 Join。

7. **可得性核对必须前置且常开**：表/字段/粒度/对比基准四项存在性检查，拿不到就报错——这是防幻觉最有效的一道闸。

8. **把"扫一眼"变成规则**：量级感、勾稽关系、常识边界、同比环比突变，四条可自动化。

9. **校验强度按风险分档**：全量校验的代价可能是 20 倍延迟；日常档与汇报档分开配置。

10. **数据治理进度决定项目工期**：指标统一、AI Friendly 元数据、下线表清理，先算清这笔账。

11. **引用准确率必须带口径**：谁测、怎么测、测哪一级，否则数字之间不可比。
