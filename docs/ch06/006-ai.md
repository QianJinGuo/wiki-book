# 企业级AI记忆基质三层架构：事实/交互/行动记忆

> 📊 Level ⭐⭐⭐ | 13.0KB

## 企业级AI记忆基质三层架构
> 来源：原文存档 — AI 小老六，2026-05-14

## 核心问题：检索 ≠ 记忆
打通 Slack/Jira/CRM API 套上搜索框，只解决了"检索"问题。检索系统回答"哪份文档提到了这件事"，企业记忆系统回答"这件事在当下业务语境里意味着什么"。
没有记忆基质的 Agent = 在没有上下文的冰面上狂奔。

## 三层记忆基质
### 事实记忆（Factual Memory）— 追溯信息本源
**核心挑战**：高可信度的溯源体系（Provenance）。
合格的事实记忆不能是孤立断言，必须包含明确元数据：

- 这条结论出自哪场会议？
- 谁是当前的 Owner？
- 信息的保鲜期（Freshness）过了吗？
- 置信度有多高？
- 权限边界在哪里？
**技术方案**：Semantic File System + Context Graph。
Embedding 擅长文本相似度，但无法处理：

- 负责人变更
- 事实被新决议覆盖
图网络将业务 Artifact 的关系固化，使之可遍历、可更新。

### 交互记忆（Interaction Memory）— 还原决策现场
记录"为什么这么决定"。
通过 Ontology 将非结构化对话识别为业务实体：

- **Commitment**（承诺）
- **Risk**（风险）
- **Assumption**（假设）
- **Objection**（反对意见）
**工程边界严苛**：

- 不是保存所有会议转录（Transcript）
- 系统必须在"提供上下文"与"避免监控感"之间找到平衡
- 有些异议（Dissenting view）应当被完整保留而非被摘要抹平
能让组织安全地"重读过去"，才是交互记忆的真正价值。

### 行动记忆（Action Memory）— 上下文驱动的协同
把 Agent 从"莽撞的 API 调用器"变成"懂得组织分寸的数字成员"。
为 Agent 提供清晰的执行边界：

- 哪些动作可以直接执行
- 哪些需要人工审批
- 哪些判断已经过期需要重新对齐
**关键场景**：同一客户的抱怨在三次电话中被提及，但未被汇总为产品需求。Action Memory 能将散落的上下文拼凑起来，带回工作现场。

## MVP 五原则
1. **先建 Event Log**：Append-only 事件流，保留回放能力，Schema 迭代后可重新解析
2. **Extractor 输出 Claim 而非 Truth**：带置信度、"待验证（Unverified）"状态的声明，在图网络中交叉验证后才确认为事实
3. **双擎检索**：Embedding 召回候选切片 + Graph 补全关系链
4. **Policy Layer 必须是一等公民**：权限细化到"用户是否有权知道某条记忆的存在"
5. **克制的 Action Router**：从低风险动作切入，逐步向自动化演进

## 与常见 RAG 的区别
| 维度 | 传统 RAG | 企业记忆基质 |
|------|---------|------------|
| 底层逻辑 | 文本相似度检索 | 图关系 + 语义 + 权限 |
| 动态性 | 无法处理动态逻辑变化 | Semantic File System + Context Graph |
| 决策支持 | 仅召回相关文档 | 理解"这件事意味着什么" |

## 深度分析

### 三层分工的本质：把"信息存放"升级为"记忆生命周期治理"
三层基质并非三套并行的存储桶，而是同一条记忆生命周期的三个治理阶段。事实记忆回答"这条信息从哪来、现在还作数吗"——其元数据五问（出自哪场会议、谁是 Owner、保鲜期、置信度、权限边界）把检索系统当作噪音丢弃的上下文全部回收为可治理的字段。传统 RAG 的盲区在此暴露：Embedding 相似度是静态快照，"负责人变更""决议被覆盖"这类动态逻辑变化不会反映在向量空间里——结果越相似，越可能是过期事实。Semantic File System + Context Graph 的必要性正在于此：图网络把业务 Artifact 的关系固化为可遍历、可更新的一等结构，元数据变更能沿关系边触发更新传播，记忆由此获得"过期"与"被替代"的生命周期语义。

### Claim 与 Truth 的分离：企业记忆的认识论设计
MVP 第二原则"Extractor 输出 Claim 而非 Truth"是整套架构中最反直觉、也最承重的一条：系统不承诺存储真理，只存储带置信度和"待验证"状态的声明，再靠图网络交叉验证把声明逐步升格为事实。它与交互记忆抽取出的 Assumption 呼应——假设是天然可证伪的声明，"这个结论依赖了哪些假设、后来被什么事件证伪"的追踪，只有 Claim 形态才能承载；若 Extractor 一开始就输出 Truth，证伪通道即被关闭，记忆退化为不可纠错的断言堆栈。工程推论是：置信度必须随证据流动持续重算，[Claim Half Life](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/claim-half-life.md) 的时间衰减与 [Memory Source Provenance](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/memory-source-provenance.md) 的溯源要求，不是附加特性，而是架构自洽的前提。

### 交互记忆的组织学价值：还原决策现场，而非压缩会议
交互记忆的工程边界——不保存全量转录、在"提供上下文"与"避免监控感"之间找平衡——并非合规妥协，而是记忆观层面的取舍：组织需要重读的不是"谁说了什么"，而是 Commitment / Risk / Assumption / Objection 四类业务实体构成的意义结构。其中 Objection（反对意见）地位特殊：自动摘要天然趋向把少数派声音平滑掉，而组织学习最昂贵的时刻，恰恰是"多数人否决后证明少数人是对的"。把异议作为一等实体完整保留，等于给组织装上对抗集体叙事漂移的回放装置——"能让组织安全地重读过去"的深意正在于此："安全"同时指向权限边界与心理边界（无监控感）。

### 行动记忆：从"查得到"到"做得有分寸"
行动记忆把记忆系统从被动存储推入主动编排：划定哪些动作可直接执行、哪些需人工审批、哪些判断已过期需重新对齐，本质是把组织规程编码为运行时约束，让 Agent 成为"懂得组织分寸的数字成员"。"同一客户的抱怨在三次电话中被提及却未被汇总为产品需求"说明：散落的信号必须被拼回工作现场才有行动价值；这也是 Action Router 保持克制的原因——初期只做生成简报、标记冲突、建议复核这类低风险动作，让"建议"先于"执行"建立组织信任。三层在此闭合：事实记忆回答"是什么"，交互记忆回答"为什么"，行动记忆回答"接下来谁被允许做什么"；三者共享同一条 Append-only Event Log 底座，因此是同一数据底座上的三种视图而非三套系统，这也是 Schema 可事后迭代重解析的结构性保证。

### 与 RAG 对照的结构性根源
"与常见 RAG 的区别"表格里的三行差异可归约为一个根源：RAG 把文档当作检索的终点，记忆基质把关系当作治理的对象。"底层逻辑"一行的"图关系 + 语义 + 权限"，意味着每次召回都要同时通过相关性、关系链与权限三重判定——对照 [Retrieval Augmented Generation Rag](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/retrieval-augmented-generation-rag.md) 的纯相似度范式，这是从"找文档"到"治理记忆"的范畴跃迁。双擎检索（Embedding 召回候选切片 + Graph 补全关系链）因此不是性能优化，而是正确性设计：向量负责"找到文本上像的"，图负责"补全业务上相关的"，二者缺一，要么漏召、要么错联。评测口径因此也要重定：不能只测召回率，还须检验溯源完整性、Claim 升格速度与权限泄露面——这些维度在传统 RAG 评测中并不存在，却是回答"这件事在当下业务语境里意味着什么"的必要条件。

## 实践启示
构建企业级记忆基质，建议遵循以下优先级：
**阶段一（0→1）**：先建立 Event Log 作为底层基础设施。Append-only 事件流是所有上层能力的地基——它保证了记忆的可回放性和可审计性。Schema 的演进设计（比如预留版本字段）比初期设计一个完美 Schema 更重要。
**阶段二（1→N）**：从 Interaction Memory 切入而非 Fact Memory。原因：Fact Memory 的源头数据往往分散在多个系统中，接入成本高；而 Interaction Memory 只需要定义好 Ontology（Commitment/Risk/Assumption/Objection），就能从现有会议记录、Slack 对话中抽取。
**关键权衡**：在"提供上下文"和"避免监控感"之间，**优先保护反对意见的完整性**。系统应该默认保留 Dissenting view，而不是让自动摘要将其平滑掉——因为组织学习最重要的时刻，往往是"多数人否决后证明少数人是对的"这类case。
**Action Router 的克制原则**：初期只做"建议"而非"执行"。当 Agent 标记"此客户在三次通话中均提及同一问题，建议转为产品需求"时，这个信号比自动创建 Jira Ticket 更安全、更符合企业文化的接受度。
