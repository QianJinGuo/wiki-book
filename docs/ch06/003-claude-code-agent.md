## 从 Claude Code 记忆系统看四层 Agent 记忆方案，一个比一个夯

我先给 Claude Code 一条明确约束：

> 这个项目只使用 PostgreSQL。后续涉及数据库选型、建表、部署或架构设计时，不要推荐 MySQL。

如果这条规则写进项目根目录的 `CLAUDE.md`，Claude Code 会在每次会话启动时加载它；即使长会话发生上下文压缩，这类项目级规则也会从磁盘重新注入。Claude Code 还有 Auto Memory，会自动沉淀一些它从项目、命令和用户纠正中学到的经验。

看起来，它已经解决了“Agent 不记得上一轮说过什么”的问题。

但实际使用中，问题并没有消失，只是换了一种形式。

例如，用户可能只是在一次普通对话里说过：

> 我只用 PostgreSQL，别给我推 MySQL。

第 1 轮，Claude Code 会回答：“好的，记住了。”

第 3 轮，让它基于 PostgreSQL 设计数据表，它通常也能正确执行。

但任务继续推进、文件内容和命令输出不断进入上下文、会话经历自动压缩，或者用户换到一个新会话后，这条只存在于聊天记录里的约束，未必还会出现在模型当前能看到的有效上下文中。

于是到了第 5 轮，用户换了一个看似无关的问题：

> 推荐一个云数据库。

Agent 可能又回到默认知识，给出：

> MySQL 配合 Redis 是一套成熟、稳定的方案。

这不一定是模型笨，也不代表 Claude Code 没有记忆。

更准确地说，Claude Code 的记忆体系主要由四部分组成：

1. 当前会话的上下文历史；
  2. 长会话接近容量上限后的自动摘要压缩；
  3. 用户显式维护的 `CLAUDE.md`、规则文件与个人配置；
  4. Claude 自动沉淀的项目级 Auto Memory。

它们已经比简单的：
    
    
    chat_history.append(message)

    

成熟得多。

但它们的核心仍然是：**在合适的时机，把规则、摘要和历史重新放回模型上下文。**

这与真正面向 Agent 的记忆系统，仍有一个关键差异：

> Claude Code 更擅长管理“项目上下文”；而复杂 Agent 系统还需要管理“可检索的事实、长期偏好、任务状态、经验沉淀、跨会话边界，以及什么时候应该遗忘”。

也就是说，Agent 记忆的难点从来不是“保存更多聊天记录”，而是四个更具体的问题：

  * 哪些信息应当永久保存，哪些只在当前任务有效；
  * 新任务到来时，应该检索哪些历史，而不是把全部历史塞回 Prompt；
  * 用户偏好、项目规范、工具经验与任务状态，是否应该放在同一个记忆层；
  * 当记忆彼此冲突、过期或不再适用时，系统如何更新、降权和遗忘。

本文将以 Claude Code 的 `CLAUDE.md`、Auto Memory 与上下文压缩机制为起点，结合 LangGraph、Mem0、Letta 的公开文档与架构设计，拆解 4 种 Agent 记忆方案：

  * 它们分别把什么当作“记忆”；
  * 各自解决了什么，又遗漏了什么；
  * Claude Code 的文件化记忆适合哪些工程场景；
  * 什么时候应从上下文与规则文件，升级到检索式、结构化、可治理的 Agent 记忆系统。

## 01从"检索"到"自治"的演化

这 4 种方案不是 4 个并列选项——它们是**演化关系** ，每一层解决上一层解决不了的新问题。

    
    
    L0 RAG          →  "帮 Agent 找到相关的外部知识"

         ↓ 但 Agent 还需要记住对话过程本身

    L1 Summary      →  "把长对话压缩成摘要，节省上下文"

         ↓ 但压缩会丢细节，特别是限定词  
    L2 Reflection   →  "不存原文，存对原文的判断"

         ↓ 但谁来管理记忆？外部系统总有判断盲区

    L3 Cognitive    →  "Agent 自己管自己的记忆"

核心变量只有一个：**谁来管理记忆？**

  * L0：检索算法
  * L1：LLM（只做"概括"这一种操作）
  * L2：外部记忆系统（LLM 提取 + 多通路检索）
  * L3：Agent 自己（通过 tool calling 主动读写记忆）

下面逐层拆解。

## 02L0 RAG：上下文塞的越多效果越差

多数人以为给 Agent 加记忆就是接一个向量数据库——把对话历史 embed 进去，下次对话时检索相关片段注入 Prompt。

这个方案的问题不新鲜：**语义相似 ≠ 因果相关** 。两个事实可能在向量空间中距离很近，但之间没有逻辑关系。

更深层的问题是：RAG 只能检索"外部知识"（文档、代码、FAQ），但 Agent 记忆至少需要三种完全不同的信息类型：

信息类型| 例子| RAG 能处理吗？  
---|---|---  
外部知识| "PostgreSQL 支持 JSONB"| ✅

对话状态| "用户说了只用 PostgreSQL"| ❌

自我认知| "上次推荐 MySQL 翻车了，因为没问清楚需求"| ❌

  
RAG 查到的永远是被动的"相关文档"，不是"关于这个用户的动态事实"。

**代码示例** （基于 LangChain 官方 Quickstart 文档）：

    
    
    # 标准 RAG pipeline — 只能检索文档，不是 Agent 记忆  
    from langchain.embeddings import OpenAIEmbeddings

    from langchain.vectorstores import Chroma

      
    vectorstore = Chroma(embedding_function=OpenAIEmbeddings())

    retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

      
    # 用户问 → 向量检索 → 注入 Prompt  
    query = "推荐一个数据库"  
    docs = retriever.get_relevant_documents(query)
    # → 返回 PostgreSQL 和 MySQL 的文档片段，但不知道用户偏好

**RAG 能做到的上限** ：检索外部知识片段，注入当前 Prompt。

**RAG 解决不了的** ：跨对话维护用户偏好、理解因果链、从错误中学习。

如果 Agent 只需要"查文档"，RAG 够了。但如果需要"记住用户是谁"，就得往上一层。

## 深度分析

原文在 L1 处收束，把四层讲成"每层解决上一层问题"的演化史。并排来看，它更像一条用保真度换自治的曲线，而每一层的付费凭证都被悄悄丢掉了。

### 一条用保真度换自治的曲线

L0 保留原文，丢的是相关性——语义相近 ≠ 因果相关，检索不到就等于没有，但这种丢失可重试；L1 丢限定词（CogCanvas 实测 exact match 93.0% → 19.0%），"everywhere" 退成 "prefers"，实现要求降级为风格偏好，递归压缩还会放大失真；L2 丢证据链，判断留下了、依据的句子没了；L3 丢确定性，记忆状态成了 agent 的隐变量，行为难以复现。关键差别是可逆性：L1 之后每次丢失都是写入时刻的一次性切除，事后没有任何入口能把原文找回。所以工程重心该压在写入路径，而不是检索路径。另一个常见误读是把 L3 当终点——它换来的自治，恰恰建立在 L0-L2 仍在位的前提下；四层丢的东西互不重叠，生产系统并行跑两三层才是常态（[来源可溯](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/memory-source-provenance.md) 沿这条曲线单调下降）。

### "越多越差"成立在哪一段

原文用这句话描述 L0，但证据撑不起它：语义相似 ≠ 因果相关是概念论证，"三种信息类型"是分类学，两者都不是测量；唯一的量化数据（19.0%）其实属于 L1。这个错位会直接导出误诊。"越多越差"至少是三个机制：注意力稀释，top-k 变大后无关片段摊薄信号，改 k 或加 rerank 即可，且可测；指令冲突，两条权威不同的规则同时在场而模型没有"谁优先"的元信息——这才是 `CLAUDE.md` 每轮重新注入的真正用途，不是让它被看见，是让它在冲突中靠位置占优；事实过期，新旧事实并存且无时间权重，Mem0 v2 把 0.5 的权重给时间衰减，等于承认这个判断不该交给模型。只有后两个是结构性的、能靠写策略修；三者混称"上下文污染"的后果，是去加压缩层，而压缩会顺手把刚注入的规则一起压掉。

### Claude Code 四件套映射到哪里、断在哪里

会话历史是工作集，不在四层之列；自动摘要对应 L1，自动、不可选、损失同构且递归放大；Auto Memory 是 L2 雏形，缺多通路检索、时间衰减与遗忘；sub-agent 隔离常被误当 L3，但它管的是任务边界不是记忆，产出仍以返回值回流主上下文，回流即压缩，写入权还在主 agent 的 prompt 里。`CLAUDE.md` 根本映射不进去：无检索（全量注入）、无压缩、无写入判断，只能算退化的 L0 加一层强权威——而它的短板恰是 RAG 的长处，长处恰是 RAG 的短板：确定性注入、可 diff、来源即文件名。断裂有三处：知识与约束混在一个文件，导致规则无法降权，只能整条留或整条删；没有跨会话的用户事实层，偏好仍只活在聊天里，这正是开头 MySQL 复现的机制；没有写入裁决，token 成本随文件线性上涨，靠人手工删，等于把遗忘外包给用户。

### 没解的三件事：写策略、遗忘、评测

四层共用一个未答问题——谁决定什么进记忆。Mem0 交给 LLM 提取，错了无声；Letta 交给 agent 自己，错了变成不可复现的行为。两者都缺"被拒候选的可观测性"：只记录记了什么，就无法归因为什么没记住，而召回失败才是记忆系统的主要故障模式。遗忘则被集体回避，至少要拆成三种：过期（TTL，可全自动）、降权（需反证信号）、删除（合规纠错，必须有人）。只做 TTL 的系统会留下"这个项目用 PG"这类曾为真、后来失效的判断——它没过期，是失效了。评测同样错位：recall 奖励"存得多"，而真实失败是存错、漏存、取错。该测的是长程行为——跨 N 轮后早期约束是否仍生效、长程任务成功率、一条错误记忆写入后多久被纠正。19.0% 只是保真度代理指标，不是效果（[记忆评测](https://github.com/QianJinGuo/wiki-public/blob/main/entities/agent-memory-evaluation-landscape-taobao-survey.md) 目前尚无公认基准）。

## 实践启示

1. **规范与事实分层存放。** `CLAUDE.md` 这类每轮注入的常量层放约束，可检索层放偏好与任务状态；两者混在一起，约束的权威性会被相似度稀释。
2. **不可逆压缩必须留原文指针。** 摘要或判断旁边存 source span，否则丢掉的限定词事后无从追回——74pp 的损失不是压缩算法差，是没有回溯路径。
3. **把限定词结构化。** only / must / everywhere 抽成"作用域 + 强度"字段，靠 prompt 叮嘱防不住 "only PG → prefers PG" 的漂移。
4. **让冲突显式化。** 两条相反事实并存时输出"存在冲突 + 各自时间 + 谁更新"，而不是让模型猜；时间衰减只该当默认权重，不该当唯一裁决。
5. **采样被拒的候选。** 记录没写进去的东西，否则召回失败永远无法归因，记忆系统会退化成不可调试的黑箱。
6. **用长程约束保持率评测，不用 recall。** 构造"第 1 轮给约束、第 12 轮问相关问题"的回归集，再加一个记忆投毒用例；起步仍从 L0+L1 开始，等你在写越来越多记忆规则时，才说明该上 L3。
