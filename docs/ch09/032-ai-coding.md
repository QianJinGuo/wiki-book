# AI Coding 的底层框架：一切优化都是在对抗熵增——信息论视角

> 📊 Level ⭐⭐⭐ | 10.2KB

## 核心概述

用信息论三个概念（熵、条件熵、互信息）统一解释 AI Coding 的所有优化手段：**一切优化都是在对抗熵增**——让模型少猜一点，让真实约束多暴露一点。Context Engineering、RAG、记忆、SDD、Harness Engineering 都可以放到同一个坐标系里看。

## 信息论三概念 → AI Coding 映射

| 概念 | 公式 | AI Coding 含义 |
|------|------|----------------|
| **熵 H(X)** | 不确定性度量 | 目标越模糊，可能性空间越大（"写一个登录函数"熵很高） |
| **条件熵 H(Y\|X)** | 已知 X 后 Y 的剩余不确定性 | 模型看完上下文后还需自己猜的部分 |
| **互信息 I(X;Y)** | 观测 X 获得的关于 Y 的信息 | 上下文排除错误方向、减少模型自由发挥空间的能力 |

核心公式：**AI Coding 质量 ∝ I(X;Y)/|Context|（信息密度） + H(Q,P)（模型-业务差距）的最小化**

上下文不神奇——有用是因为它能排除错误方向。RAG 的逻辑：不是把知识库塞给模型，而是找到与当前任务互信息最高的片段。

## 两个现实修正

### 修正一：低熵 ≠ 正确（模型自信度 vs 正确性）

模型在自己的分布 P 下对某输出概率很高时会显得很笃定（低熵），但你的仓库里的真实规则不一定在训练分布里。模型自信地调用 `userClient.getProfile()`，但你的项目里真实存在的是 `profileService.fetchByUid()` 还必须带灰度参数。

**低熵更像模型的自信度，不等于正确性。**

### 修正二：交叉熵 H(Q,P) 才是更关键的问题

模型分布 P（训练先验）和真实业务分布 Q（私有仓库 + 业务约定 + 运行环境 + 团队经验 + 历史包袱）的差距用交叉熵衡量。很多 AI Coding 失败不是模型输出发散，而是**太自信地遵循了另一个世界的规则**。

复杂历史业务难做的根本原因：真实约束藏在私有代码和团队经验里，模型先验来自公开语料。P 和 Q 差距越大，越不能指望模型靠猜补齐。

## 覆盖层 vs 填补层

- **覆盖层**：上下文能覆盖的部分——可通过工程手段（RAG、记忆、SDD）提高信息密度
- **填补层**：上下文覆盖不到、模型必须靠猜的部分——需要缩小 P 和 Q 差距，或让人介入

AI 最容易出问题的地方，通常就在填补层。

## 四个经典问题的回答

### Q1. Context Engineering vs RAG vs 记忆

都在做同一件事的不同切面：**提高覆盖层的信息密度**。RAG 找互信息最高的片段；记忆存犯错记录和业务约定；Context Engineering 组织输入结构。记忆系统竞争力不在于存了多少，在于每次能否召回少量高密度信息。

### Q2. 历史业务为什么总翻车

双重困境：隐性规则无法进入上下文（I(X;Y) 对最关键约束几乎为零）+ 模型先验 P 和业务真实分布 Q 差距大（H(Q,P) 很高）。真正困难的不是让模型写代码，而是**让模型知道哪些地方不能按通用经验写**。

### Q3. Agent 能不能只给需求文档完成交付

**数据处理不等式**：信息经过多步处理只会损耗不会增加。需求文档里没表达的意图，Agent 在后续步骤中无法恢复。填补层的缺口——那些从未被表达出来的业务意图——是自动化真正的边界。

### Q4. 记忆越多越准还是越走神

召回太多低相关记忆会稀释有用信号；召回过期记忆会把模型推到旧规则上。**过期记忆属于填补层的污染，比低密度信息危害更大。**

## Harness Engineering 的信息论解释

Harness = 计划分解 + 状态管理 + 工具编排 + 验证门控 + 反馈回路 + 回退机制 + 人机交接点

用信息论看：Harness 不是简单给模型更多上下文，而是**在每一轮生成后把真实世界的约束不断显性化**。Prompt 只在一次调用前，Harness 关心多轮行动里的信息流、验证流和状态流。

边界：业务直觉、架构审美、跨系统潜在耦合——没法完全写成自动测试。Harness 能把一部分隐性 Q 转成可执行约束，但不能替人恢复从未被表达出来的意图。

## 核心金句

> 衡量 Agent 系统的关键不是模型会不会写代码，而是：它有没有办法识别哪些缺口是可以自动弥补的，哪些必须升级给人。
> 记忆系统的竞争力不在于存了多少，而在于每次能不能召回少量高密度信息。

## 深度分析

这个框架的真正价值不在于三个公式本身，而在于它把散落的工程手段收进一个可判定的坐标系：任何新工具、新方法，都可以问一句"它是提高了 I(X;Y)，还是缩小了 H(Q,P)"。 以下从四个切面展开。

### 从"对抗熵增"到工程决策坐标

Context Engineering、RAG、记忆、SDD、Harness 各自的营销叙事差异很大，但在这个坐标系里它们的身份一目了然：RAG 是互信息最大化器，记忆是业务约定的增量显性化，SDD 把意图写成可验证约束，Harness 是多轮循环里的约束再显性化。反过来，判断一个看起来热闹的新方法是否值得引入，也只需要问：它往上下文里塞的是高互信息片段，还是仅仅把 |Context| 变厚、稀释了信息密度。这一问把"工具之争"转换成了可度量的问题。

### 低熵陷阱：笃定恰恰是危险信号

修正一的深层含义是：模型的自信度衡量的是它在自身先验分布 P 内部的一致性，与真实业务分布 Q 的对齐无关。推论是，代码审查的注意力分配应该倒过来——最该盯的不是模型写得磕绊的地方（那说明它在探索、在求助），而是写得异常顺滑、又恰好触及私有业务约定的地方：顺滑意味着它正在调用通用先验，正是填补层失守的高危区。覆盖层/填补层由此从概念区分升级为一张审查优先级地图。

### 交叉熵 H(Q,P)：私有知识问题的真正刻度

复杂历史业务难做的根因，不是上下文不够长，而是 Q 从未被显性化——真实约束藏在私有代码、团队经验和历史包袱里，公开语料训练出的 P 天然与之错位。 又因为数据处理不等式（信息经多步处理只损耗不增加），需求文档里没表达的意图在后续任何步骤都补不回来。两者合起来给出工程排序：先做 Q 的显性化（spec、约束清单、测试），再谈自动化程度；顺序颠倒就是大多数翻车案例的剧本。

### 与 Harness Engineering 的闭环

用这套语言重读 Harness 的六个组件，可以看到一条完整的降熵链路：计划分解压缩每轮的条件熵，验证门控把"模型自信"交给真实世界裁决，反馈回路维持记忆系统的信息密度，回退机制为误判兜底。而人机交接点不是自动化失败的耻辱柱，而是设计本身——业务直觉、架构审美、跨系统潜在耦合无法写成自动测试，识别"哪些缺口可以自动弥补、哪些必须升级给人"才是 Harness 的核心能力。

## 实践启示

1. 评价新工具或新方法时只问一个问题：它提高 I(X;Y) 还是缩小 H(Q,P)？两者都不沾的，多半是噪音。
2. 上下文不是越多越好：以信息密度 I(X;Y)/|Context| 为准，定期清理低互信息片段；过期记忆属于填补层污染，比信息缺失危害更大。
3. 代码审查把注意力集中在"模型写得很顺"且涉及私有业务约定的代码上——低熵不等于正确，顺滑恰是先验驱动的信号。
4. 接手复杂历史业务时，先做 Q 显性化（写 spec、列约束、补测试）再谈自动化；文档没表达的意图，Agent 在后续步骤中无法恢复。
5. 记忆系统按召回质量而非存量考核：竞争力在于每次能否召回少量高密度信息，而不是存了多少。
6. Harness 设计必须有显式的人机交接点：把"哪些缺口可自动弥补"当作一等设计对象，而不是等失败后再补救。
