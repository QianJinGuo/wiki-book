# Automate progressive rollouts with Vercel Flags - Vercel

> 📊 Level ⭐⭐ | 7.9KB

## 深度分析
Vercel Flags 是 Vercel 平台推出的 Feature Flag 解决方案，本次更新新增 **渐进式发布（Progressive Rollouts）** 功能，属于 Feature Flag 策略中的「时间基权重」类型。

### 核心概念：渐进式发布 vs 加权拆分
传统加权拆分（如 A/B 测试）将流量固定分配，如始终保持 50/50 的分流比例。而渐进式发布则按照**预定义时间表**动态调整流量权重，每个阶段有目标百分比和持续时间。
这意味着：

- 初期：小比例流量（如 5%）进入新版本
- 中期：逐步提升至 50%
- 后期：接近 100%

### 为什么渐进式发布有价值
核心价值在于**降低回归风险**。当新版本有缺陷时，只影响当前阶段的小部分用户，而非全量用户。
典型场景：
1. **新功能灰度发布**：先覆盖内部用户，再逐步扩大
2. **配置变更验证**：数据库 schema 变更后，通过 flag 控制流量
3. **性能回归检测**：逐步增加流量便于观察监控指标

### 技术实现路径
文章提到两种使用方式：
1. **Dashboard 可视化配置**：通过 Vercel Flags 界面管理
2. **CLI 命令**：`vercel flags rollout` 命令，支持自动化管道集成
这意味着 CI/CD pipeline 中可以方便地编排渐进式发布，结合监控告警实现自动化回滚。

### 渐进式发布中的 flag 生命周期：从「开关」到「调度对象」

把这次更新放进 Feature Flag 的演进脉络里看，flag 的角色发生了实质变化。传统 flag 生命周期是「创建 → 人工拨动开关 → 删除」，开与关是两个瞬时动作，flag 只是一个布尔门闩；而渐进式发布把 flag 变成了一个**带时间表的调度对象**——每个阶段有目标百分比和持续时间，状态在「排期中、当前阶段、已完成」之间自动流转，不再依赖人工逐步拨动。

这个变化对工程组织的含义是：发布策略从「操作员的知识」变成「可版本化、可审计的配置」。当权重推进由平台按时间表自动执行时，团队讨论的焦点从「今天推到多少」变成「时间表本身设计是否合理」——阶段划分粒度、每阶段观察窗口时长、目标百分比曲线，这些成为 code review 的新对象。Dashboard 配置与 CLI 命令两条路径并存，恰好对应了这两种工作方式：前者服务手动观察与干预，后者服务把时间表作为代码管理。

### 回滚策略：时间表是「承诺」还是「可撤销的提议」

原文强调渐进式发布能在小流量阶段「catch a regression on a small slice of users before it hits everyone」，但没有说明阶段推进过程中能否暂停或回退。这留下一个关键的工程判断：时间表究竟是平台自动履行的承诺，还是随时可撤销的提议？

两种语义对应两种运维姿态。若时间表不可中断，渐进式发布只是把「爆炸半径」从全量缩小到单阶段增量，团队仍需人工盯监控、在窗口期内手动干预；若支持暂停/回退，它才能与告警系统串成真正的自动化闭环——错误率超阈值即回退到上一稳定阶段，人在环外。从原文「每个阶段有目标百分比和持续时间」的表述看，Vercel 目前把中断语义留给了使用者自行处理，这意味着**自动回滚目前是集成问题而非平台内置能力**：需要团队自己用 CLI 命令 + 监控告警组装，或者等待平台补齐。采购这类功能时，「能否编程式暂停」应该作为验收标准之一。

### 与 CI/CD 的集成取舍：发布节奏该不该交给时间表

渐进式发布天然存在一个张力：它的时间表是**日历驱动**的，而 CI/CD 的交付节奏是**事件驱动**的（build 完成、测试通过即触发部署）。把两者接起来时需要做取舍。

一是「什么该走 flag、什么该走部署」的边界：渐进式发布适合的是已经部署完成、只控制曝光比例的变更；代码本身的发布仍走常规 CI/CD。flag 时间表管的是「用户看到什么」，deploy 管的是「服务器跑什么」，混淆两者会导致回滚语义混乱——回退 flag 是瞬时操作，回退部署要重新构建。二是调度与流水线的所有权问题：如果发布节奏完全交给平台时间表，deploy pipeline 里的进度感知就变弱了；用 `vercel flags rollout` 把推进动作编入 pipeline，则保持了「一切变更皆由 CI 触发」的单一事实来源。原文把 CLI 与 Dashboard 并列给出，本质上就是把这个取舍交给团队：小团队用 Dashboard 手动控制观察窗口更务实，有严格变更管理要求的团队则应把时间表编排进 pipeline 以获得审计轨迹。

## 实践启示
1. **在 CI/CD 流程中集成渐进式发布**：结合监控指标（错误率、延迟）设置自动回滚阈值，当新版本指标恶化时自动降低流量比例。
2. **优先在高风险变更时使用**：数据库迁移、大幅重构、依赖升级等场景，建议通过渐进式发布逐步验证，而非全量上线。
3. **结合 Flags SDK 实现客户端感知**：Vercel 提供 Flags SDK，客户端代码可以据此条件渲染 UI，结合渐进式发布的百分比控制实现细粒度灰度。
4. **CLI 集成支持 GitOps 流程**：`vercel flags rollout` 适合在 GitOps 场景中使用，通过 Infrastructure as Code 管理发布策略，实现审计追溯。
> [!note] 与传统 A/B 测试的权衡
> 渐进式发布侧重「时间维度」的风险控制，而加权拆分侧重「空间维度」的实验精确度。两者并非替代关系——渐进式发布适用于生产级变更，A/B 测试适用于产品决策验证。
