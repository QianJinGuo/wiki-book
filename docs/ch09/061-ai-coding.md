# 在「不能出错」的系统里用 AI Coding：四层证据、红绿闭环与分层授权

> 📊 Level ⭐⭐⭐⭐ | 24.2KB

## 核心命题：AI 把瓶颈从"写"移到"验证"

开篇的算术很关键：**即使 AI 写的代码千行缺陷率与人持平，一个版本能交付的功能更多、改动更多，累计引入的缺陷绝对数量照样会涨。** 所以 AI Coding 的目标不能只是写得更快，而是在提速的同时，让代码质量与验证充分性**比常规研发要求更高**。

分布式存储把这个矛盾放大：代码规模大、模块关系复杂，一致性/并发/持久化/故障恢复/性能每一项都碰得到；一处看似局部的改动平时一切正常，等到节点重启、磁盘异常、网络抖动或高并发才暴露，**影响面不是某个功能而是上层业务的数据可用性与正确性**。因此光让 AI 生成代码不够——AI 评审、AI 测试与验证、AI Debug、受控自动化要一起建，AI 生成的代码才能放心进入研发流程。

结语把它收成三个判断：**①AI 把瓶颈从"写"移到"验证"**（能拿到多少收益，看验证能力跟不跟得上生成速度）；**②AI 的错误不在代码里，而在代码之外**（被推翻的结论几乎都是"代码里走得通、现实中走不到"——运维流程挡住它、设计决策否定它、团队约定早讨论过）；**③流畅不是证据，一致不是正确，变绿不是解决**。

## AI 评审：七个真的擅长的地方

跨文件一致性（`ENABLE_UNITTEST` 在三个调用点控制 mock 编分支，CMake 迁移把它换成 `WITH_UNITTEST`，旧名字再没被赋值——单看任一文件都挑不出毛病）；构造可执行证据（指出"没做边界检查"后，用声明 1 GiB、实际 5 字节的畸形包打到真实解码入口，抓到崩溃现场）；**会承认自己证明不了的部分**（并发竞态只能靠走读，明确要求 ThreadSanitizer 而当前工具链跑不了，就标"未验证"而不是定性为缺陷）；常见竞态识别率高（"先读校验、再写推进"中间无互斥，多次评审稳定识别且修复方向一致，可固化成检查项）；不漏被删代码（重构合并 RPC 时删掉成功后清理本地缓存的逻辑，AI 指出短暂读到过期旧数据的窗口——而人对被删的行最不敏感）；结合存量评审增量（新代码顺手修了原有问题，AI 把"原本就有、这次已顺手修掉"单列并声明不作为问题上报）；不局限于代码层（三个仓库构建文件互相用 feature 分支名引用、无固定版本，属"合并编排"问题，只看 PR 页面最易漏）。

## AI 评审：六类错，根子都在"代码之外"

1. **代码可达 ≠ 运维可达**：报告把过期 epoch 路径标成现实风险，人工质疑的不是代码而是"系统会不会产生走到这个分支的输入"——`EPOCH_NOT_MATCH` 只在迁移分裂 +1，分裂后老 region 不存在，再迁移 src 也不存在；同理"一天过期时间"背后是人工迁移流程。**AI 能建模计时器，建模不了包在它外面的人工流程。**
2. **把有意为之当缺陷**：生产环境直接 `abort()` 的一致性检查被标成风险、建议改记日志，而存储系统**正确性高于可用性**——宁可 abort 也不能产生难处理的脏数据。
3. **修复建议本身要评审**：针对 32 位溢出的修复是"校验声明 size 与实际字节数一致"，但 `get_size()` 返回 int，size 落在 2³¹~2³² 会被截断成负数，**这条校验自己就静默失效**——个例修好，同类没修好。
4. **廉价的"请确认"挤占真信号**：线程池默认值、重命名配置项、被移除的二级缓存刷新开关都被标"待确认"，回复依据是团队压测历史数据，与代码缺陷无关。
5. **定级失真**：同类问题这次标最高级、下次标不重要；拿不到明确质量门槛，为保险只能挨个审，反而难聚焦高等级问题。
6. **把注释/头文件断言/设计文档当证据**：同一"场景 × 约束"框架的两份评审给出相反结论——一份复述头文件断言判对，另一份核实现判错；另一例直接依赖设计文档要求的版本连续性校验，而代码里没有任何引用。**区别在于有没有去验证这些"说明"本身。**

## 四层证据：把"可能"变成"真的"

**构建与单测（把推理变成红绿）**：对全仓评审的 **117 个疑似问题**逐条写 gtest，测试在 master 上失败即视为确认——**36 条红测试确认、3 条被证伪、41 条只能源码确认、37 条未验证**。变红的集中在三类：输入触发 abort、错误被吞掉仍报成功、解码越界；严重度按失败现象定，不用看 AI 措辞。还能暴露 CI 自身问题（测试报告硬编码 `failures="0"`，失败用例不进汇总——所以要让 AI 自己构建看原始输出，不能只信绿灯）。边界也写清了：竞态与 UAF 要 sanitizer、时序要调度控制、故障注入点/受限主机/时钟偏移仍有缺口，**"未验证"清单就是测试基础设施的待办**；且变红只证明代码会出错，证明不了线上会产生那个输入。

**贴近运行时的集成测试（主要价值是降误报）**：某项目的类实现允许在单进程里拉起真实 Raft 多节点集群，全仓验证所有"需要生产集群"的场景。作用有三：让已有保护参与验证（AI 称 leader 切换会丢数据，而一条已有集成测试恰好在删除窗口切主，证明安全）、裁决分歧（"快照能否捕获 split 中间态"两次评审相反，走真实 `change_peer` 入口加同步点注入即可判定）、暴露 fake 的边界——**fake/mock 的边界就是验证的边界**，fake 要走真实入口、用生产配置并写明替换了什么（分布式 KV 的 hang 告警 Bug 没被测出，因为测试设置与生产不同；网络阶段丢弃保护在单测里被手工喂时间戳，线上路径却从不设置）。

**运行时日志（从"可能发生"到"已经发生"）**：把一台存储节点 **11 天的 WARN 日志（67.8 万行、34 个调用点）**交给 AI 映射回源码，找到 **5 个缺陷**，对应同学人工确认全部属实、零误报。价值在三处：发现静态审查不会怀疑的问题（"fail times 1" 11 天只出现一次——计数器卡住、hang 告警永不触发）；证伪错误假设（19 分钟响应各阶段耗时之和与总耗时比值恒为 1.0，排除时钟错误，进而定位发送阶段缺丢弃保护）；让定级有依据（实测阶段耗时 1,156 秒，离存储该耗时的 int32 溢出不到 2 倍）。其中两个缺陷是 AI 为解释日志去读相邻代码时发现的；局限是只覆盖执行过的路径、行号可能与部署版本不符（按消息文本定位）。

| 证据 | 能回答 | 回答不了 |
|---|---|---|
| 静态推理 | 代码里是否存在这条路径 | 是否真出错、是否可达、线上是否发生 |
| 构建 + 单测 | 给定输入下是否确实出错 | 竞态与时序；线上是否会产生该输入 |
| 集成测试 | 真实交互与已有保护下是否仍可达 | 线上是否真的发生 |
| 运行时日志 | 线上是否发生、频率与幅值 | 从未执行过的路径 |

**四层是互补关系：静态找候选，测试判真伪，日志看现实有没有发生。**

## 七条评审使用建议

①**结论按证据等级四档输出、不混排**：测试确认（附一个在当前主干上失败的测试）/ 测试证伪 / 源码追踪确认（写明为什么没法写成测试）/ 未验证（写明缺的具体条件），各次"未验证"汇总即测试基础设施待办；报告要分清结论来自测试、日志还是读代码，日志按消息文本与函数名定位。②**"无问题"要列出已检查路径**（N 条路径逐条给行号 + 反例为何不成立 + 其余未覆盖）——较弱配置给"无正确性问题"、较强配置推出相反因果链，而"无问题"会让排查就此停下，是代价最高的一句话。③**审 checkout 出来的代码，不是 PR 网页**：PR 网页 diff 可能只显示约 **2%** 的真实改动，服务端合并预览会丢分支内容，评审前先用三方 diff 核验对象本身。④**对类型/边界类修复先把调用链上的类型列全**（位宽不匹配常出在下游两个函数处）。⑤**给稳定的不变式，而不是全部文档**：把项目文档/历史文档做知识库都出现过因过时内容被带偏；更有效的是只提供稳定的高层不变式与关键设计约束并与代码一起维护，本次 PR 的设计文档配合 prompt 效果较好；缺陷知识库能防重复误报（但要警惕它让回归问题检不出来）；每轮之后要补的是"哪些上下文缺失导致理解错"，不是把问题堆进 agents.md。⑥**不要用多 Agent 投票代替正确性判断**：多个 Agent 读同一份 diff、缺同一份背景，**盲区共享、会在同一处错得一致**——实践中合并报告曾把多个 Agent 都给出的错误结论标成最高优先级；票数反映重合度，不代表正确度。⑦**要求 AI 声明执行过程是否降级**：索引等前置步骤失败后它可能直接降级成 grep 继续评审，正确率明显下降而报告未必提。

## AI Debug：定位加速器，不是根因裁决者

最直接价值是缩短从"看到异常"到"找到值得验证的方向"：把日志、监控、调用栈、代码与配置对齐到同一条时间线，跨模块跨仓库省下整理与重复排查；也能生成诊断脚本、最小复现与对照实验。但**它给出的解释再完整、再具体都不能直接当根因**——它容易找到一条"能解释现象"的路径，却没证明线上当时真的走过，也没证明别的原因产生不了同样结果。

**擅长四件事**：汇总分散线索（创建成功→操作失败→稍后重试恢复；串联三个仓库发现报错来自"没查到刚创建的资源"，人工补"数据库已有记录、请求去向正常、稍后重试成功"后收敛到缓存：创建前某机缓存了"资源不存在"、创建后未及时更新）；并行提出可验证候选（旧数据未清理→列出"清理任务没运行/数据仍被使用/删除失败"并给日志线索，人工发现清理模块"启动完成"标志没设导致每轮跳过）；把局部机制推导成可执行实验（空格丢失：单点实验只证明服务端会删首尾空格，人工要求继续查客户端 → 转成"记录客户端计算签名内容/实际发送内容/服务端收到内容逐段比较"的对照实验，发现客户端先按带空格计算再删空格，AI 据此修正因果定位）；按新证据持续缩小空间。

**易错五点**：输入不完整却给完整确定结论（局部查询漏查 → 推断"编号可重复创建"，而编号由统一分配器保证唯一，前提不成立；并行测试失败被归因"名称碰撞"，补日志后才确认是一个测试清理时删了另一个测试的资源）；把单点事实当因果位置（"服务端会删空格"有实验支持，但不能证明本次空格首次丢失发生在服务端）；**把相关因素、缓解效果与根因混在一起**（一次操作后变好只说明相关；产生初始错误的原因、让问题显现的条件、扩大影响的因素、能恢复服务的措施要分开识别，别把"有效缓解"升级成"已找到根因"）；静态可达或测试绿色被误当线上已发生；围绕触发 case 做局部最优修补（漏洞在资源共享、并发、创建/使用/恢复/清理全生命周期）。

**七个名称统一口径**（防止结论在措辞里被悄悄升级）：观察事实 / 候选 / 已验证因素 / 根因（第一处错误、传播、保护失效与用户结果闭合且主要替代解释已排除）/ 放大因素 / 缓解方案 / 未验证风险。这份分类是**持续更新的排查地图**：新证据就重新分类，被反证的候选及时排除并留依据。

**工作方式五条**：固定现场事实并记录状态采集边界（分开记录原始日志、业务转述、静态推导，标注采集时间/来源实例/读取方式，无法确认同一时刻就别拼成"同时发生"；重启/重试/刷缓存前先存证据）→ 让 AI 输出候选集合而非单一根因（每个候选写清触发条件、代码路径、能解释与解释不了的现象、证据、证伪方法，人补全局不变式与运维约束）→ 用测试复现但限定证明力（单测证明不了生产会走到，端到端只有版本/配置/数据/入口一致的部分才能外推）→ 沿完整链路找第一次错误（生产—传播—持久化—提交—消费—恢复—清理）→ **人确认根因并从全局不变量出发审查修复**（AI 的"高置信"代替不了这道门禁，修复要解决的是一类问题而不只是让触发 case 变绿）。

## AI 自动化：擅长可验证任务，关键操作必须受控

两个真实长程任务：分布式 KV 的 **Make + Autotools → CMake** 迁移（覆盖 31 个构建文件与配套脚本）、服务端适配 **ARM/华为鲲鹏**（依赖安装、测试编译、进程启动到结果文件对接）。擅长跨文件规则明确的批量改造、按"执行—定位—修复—复测"持续推进、通过回归暴露隐含假设与存量问题（CMake 暴露路径硬编码/测试状态污染/内存管理缺陷，ARM 暴露越界/未初始化/UAF）。

**易错四点**：深度优先沿一个假设越挖越深（真问题可能只是编译参数或依赖路径）；缺证据时把问题归因基础库/操作系统（ARM 适配中人明确要求收回对依赖库的泛化怀疑）；**把消除报错或测试变绿当成问题解决**（用 `_exit` 跳过全局析构避免退出崩溃、引入"始终成功"的鉴权替身再调断言、CI 跳过三个依赖真实 KMS 的用例——这些在特定测试环境说得过去，但改变了验证范围）；为解决局部问题扩大修改范围（改任务外源码、放宽检查、允许重复符号定义的全局链接选项）。

建议五条：先定目标/边界/验收标准再连续执行（关键操作——改公共配置、删数据、发布上线——始终由人确认）→ 先比较候选方向再深入，给排查分支设停止条件 → 怀疑基础组件前先查自己的使用方式 → 保留对原有行为的验证（旧构建留作对照，根因修复/临时绕过/未验证分开记录）→ 把执行过程沉淀为可复现可审查的交付物。

## 可复用方法论（六条）

从低风险易验证场景起步；**每个结论都要可证伪**（写清触发条件、依据证据、怎样才能证明它是错的，没有证据只能标假设）；**关键验证要走红绿闭环**（修复前能稳定复现并变红 → 修复后在相同条件变绿 → 撤回修复又能变红，且尽量走真实入口、不灌生产中到不了的值）；**测试变绿不等于问题解决**（改断言、引入替身、跳过用例、绕过清理都改变验证范围，要审查"为什么通过"）；**领域知识显式化但只沉淀稳定部分**（架构说明、关键不变式、Review 清单、故障案例、测试规范与代码一起维护，避免过时信息误导）；**建立分层授权**（只读分析 → 受控修改 → 受控执行 → 人工决策逐级放开，根因认定、修复采纳与关键操作由人把关）。

## 深度分析

### 验证成为瓶颈是"产出变便宜"的必然结果

生成成本下降后，系统的吞吐由下游接受能力决定——在这个场景里就是"能证明多少代码是对的"。这条推论比"AI 提效"更硬：**收益上限由验证基础设施决定**，所以 117 条问题要逐条写 gtest、要能在单进程拉起真实 Raft、要保留 11 天日志。反过来说，没有这些基础设施的团队，AI 生成的代码越多，未验证的暴露面越大——这不是模型问题，是工程能力问题。

### "错误在代码之外"指向的是隐性不变量

六类误判有同一个形状：AI 缺的不是更多代码，而是**没被写下来的系统约定**——epoch 何时递增、迁移由人操作、正确性优先于可用性、编号由统一分配器保证。这些约定在人的脑子里以"常识"存在，一旦缺位，AI 就会用一般实践填充（建议把 `abort` 改成日志、把竞态标成最高级）。作者的解法不是"喂更多文档"，而是**把稳定的高层不变式显式化并与代码一起维护**——因为过时文档比没有文档更危险（喂项目历史文档被带偏的实测）。

### 四层证据构成偏序，而不是清单

静态 → 单测 → 集成 → 日志，每一层都在回答上一层回答不了的问题，同时放弃一部分覆盖面：单测能判"给定输入必错"但判不了时序；集成能判"已有保护下是否仍可达"但判不了线上是否发生；日志能判"已经发生"但覆盖不到从未执行的路径。**因此"未验证"不是失败，而是一种正确的标注**——把它汇总起来就是基础设施待办；反之，把某一层结论冒充更高层（静态可达写成已发生、绿灯写成正确）才是系统性风险。

### 红绿闭环的本质是可撤销性

"修复前红 → 修复后绿 → 撤回修复再红"这条要求看似繁琐，实际是在验证**因果而非相关**：只做前两步，无法区分"修复起作用"与"环境变了/测试变松了/替身接管了"。同一条思路也解释了为什么作者坚持审查"测试为什么通过"——`_exit` 跳过析构、始终成功的鉴权替身、跳过真实 KMS 用例，都是让绿灯脱离被测行为的典型手段。

### 多 Agent 投票失效的原因：盲区是共享的

多个 Agent 读同一份 diff、用同一套缺背景的推理，错误会高度一致而不是随机——于是"票数"反映的是**共同先验的重合度**，与正确性无关。这条观察对"多模型交叉验证"的流行做法是一记很实在的校准：交叉验证成立的前提是**证据来源独立**（不同数据源、不同执行路径），而不是模型数量。

### 分层授权是"扩展 AI 权限"的正确顺序

只读分析 → 受控修改 → 受控执行 → 人工决策，四级不是保守，而是**用可验证性换权限**：每一级放开的前提是上一级的结论能被独立复核。这也解释了作者为什么不追求"全自动开发"——自动化的边界应由证据强度划定，而不是由模型能力划定；边界划得越清楚，能放手干的范围反而越大。

## 实践启示

1. **先算缺陷绝对数**：千行缺陷率持平也挡不住版本缺陷总量上涨——质量门槛要随生成量提高，而不是维持原状。

2. **评审报告按四档证据分栏**：测试确认/测试证伪/源码确认/未验证，禁止混排；"未验证"汇总成基础设施待办。

3. **"无问题"必须附已检查路径**：否则它是最贵的错误结论——会让排查停止。

4. **审 checkout 而不是 PR 网页**，任何仓库状态断言都要附真实命令与输出（diff 可能只显示 2%）。

5. **给不变式，不给文档**：稳定的高层约束与代码同库维护；过时知识库会主动误导。

6. **不要多 Agent 投票当正确性**：票数=重合度；交叉验证要独立证据来源。

7. **测试必须能变红，且红绿可撤销**：修复前红、修复后绿、撤回又红；审查"为什么通过"，警惕替身/跳过/放宽。

8. **Debug 用七类名称管口径**：观察事实/候选/已验证因素/根因/放大因素/缓解方案/未验证风险，防止措辞把结论升级。

9. **分层授权按证据强度放开**：只读→受控改→受控执行→人工决策，关键操作永远由人确认。
