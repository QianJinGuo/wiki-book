# 不只是 Memory：Ontology 如何让 Coding Agent 越用越懂项目

> 📊 Level ⭐⭐⭐⭐ | 36.9KB

## 摘要

腾讯技术工程的第一方研发实录，回答一个具体问题：Agent 怎样才能越用越懂一个项目？答案分三件套——**本体（Ontology）给项目知识一个可核对的含义，Memory 保存经验与来源，RSI（递归自我改进）让"改进的方法本身"也能被检验和优化**。落点很具体：让 Agent 少花重新理解项目的时间，少犯团队已经弄明白的错误。实践是在设计完成到上线前测试的研发 Loop 里，用四类记忆资产 + 工程事实 / 项目语义 / bug_fixed 三层互索引图谱组织项目知识；初步结果是内部 Bug 定位成功率 **58%→65%（+7pt）**，附完整的归因边界声明——不能换算成整条 Loop 的效率提升，也不能单独证明本体语义层贡献了全部增益。

## 核心要点

- **本体 ≠ 知识图谱 ≠ RAG**：Schema 管字段结构、CodeGraph 管调用位置、知识图谱管实体关系实例、RAG 管找相关材料，本体管"这些材料在说哪个对象、在什么条件下成立、能支持哪一步推断"——检索到一份政策，还要判断它是否适用于当前车型、年款、地区和时间。
- **Loop 能完成任务，不等于系统学会了**：新会话会重新搜索同一条链路、再误解一次相同的业务约定；Memory 是跨轮次保存的燃料，但"保存不等于学会"，一条错误经验被更稳定地召回，反而让错误重复得更稳定。
- **RSI 按改动对象分三层**：执行内迭代（改当前任务的计划或产物）、跨任务自改进（改持久知识 / 工具 / 方法）、改进过程的自改进（改生成、选择与验证改进的方法本身）；Darwin Gödel Machine 与 Skill∞ 是后两层的参照，Skill∞ 明确把评分放在自改进范围之外，候选须经独立审查。
- **三层图谱不是七类资产**：四类记忆资产（Chat Memory / Wiki / CodeGraph / Skill）是材料的形态与用途，三层（工程事实 / 项目语义 / bug_fixed）是知识之间怎样关联和访问；本体不需要再成为第四层，它体现在第二层的概念与约束表达中。
- **经验必须可撤回**：父实例已删除、逻辑拓扑表仍保留记录的复盘，撤回了原先"已证实删除缺陷"的定性；旧结论被替代后，引用它的摘要、Skill 与测试假设应进入待复核状态——系统要能收紧适用范围、拆开误合并的概念、撤回不成立的结论，而不只是继续增加内容。

## 1. 本体：把领域的共同模型写下来

本体是知识工程的概念：把一个领域里有哪些概念、概念之间是什么关系、有哪些成立条件，明确表达成一套可以共享的模型。"共享"是关键词——一个人心里知道什么叫"订单完成"，不代表仓储、财务和客服用同一种含义；模型知道中文"完成"是什么意思，不等于知道某家公司以支付、出库还是签收作为完成标准。

订单例子把这点讲透了："订单"和"发货单"是概念，"某一笔订单"是对象，"订单对应发货单"是关系，金额、币种、创建时间是属性；业务允许拆单时，一个订单对应多张发货单；"所有有效发货单签收后订单才完成"这个条件也要明确写下来——于是"一张发货单已签收"和"整个订单已完成"不能随意互换，区别来自对象和关系，不来自两句话看起来有多相似；条件还要带上适用范围，因为拆单规则会随业务版本变化。

表达与验证是两件事，要分开：本体可以表达订单与发货单的关系，但当前订单是否满足完成条件，还需要查询数据并检查——SHACL 处理图数据的约束验证，业务系统也可以用普通程序和测试完成检查；**本体不会因为写下了一条规则，就保证现实已经遵守它**。W3C 的 OWL 2 提供类、属性、个体及逻辑公理的表达方式，说明本体不是大模型出现后才发明的东西；工程实践也可以从有版本的概念定义、关系类型、数据映射和规则文件起步，关键是含义能被核对，模型不必每次从散落的材料里临时猜测。

分工上，五者各管一摊：数据库或接口 Schema 提供字段、类型、数据结构和部分约束，但不回答字段在业务中代表什么；CodeGraph 提供符号、调用、依赖和代码位置，但不回答调用链承担什么业务职责、哪些约定不能破坏；知识图谱提供实体及其关系实例，但不回答关系是否有明确含义、适用范围和依据；文档与 RAG 提供与当前问题相关的材料，但不回答多段材料是否在谈同一对象、是否适用当前场景；**本体提供共享概念、关系语义和相关公理或约束**，但不直接回答当前事实是否符合这些定义、动作是否产生预期结果。增加检索能力与补齐领域含义是两项不同的工作；一张图所有边都叫"相关"，模型仍然不知道两端究竟是实现、依赖，还是一方违反了另一方的约束。

Palantir 的 Ontology 系统把 data、logic、action 和 security 联系起来，不只组织可查询的数据，还将业务对象与逻辑、操作和权限结合；FDE（Forward Deployed Engineer）关注本体，也是因为深入业务现场后必须把用户目标、既有系统和交付标准连接起来——用户说"这个流程成功了"，工程师得继续确认哪个对象成功、哪个阶段成功，是受理成功还是业务结果已经生效。Agent 越接近实际操作，这类工作越难省略：含义不一致，会继续传到工具参数、代码实现和验收断言里。

## 2. Loop、Memory 与 RSI：完成任务 ≠ 学会

Agent 利用模型作判断、调用工具执行动作、再根据环境反馈继续推进，Loop 就是这段"行动、观察、调整"的循环。写代码、执行测试、读取失败、修改后重测，已经构成一个执行 Loop；但这个循环能把当前任务做得更好，不代表下一轮有所不同——新会话可能重新搜索同一条链路，再误解一次相同的业务约定。**当前任务的完成与跨任务学习，需要分别设计。**

Memory 保存可以跨轮次使用的信息：发生过的事件、已确认的知识、处理任务的方法。Reflexion 给出了利用语言反馈的例子——Agent 根据任务反馈形成反思，保存在情节记忆中，指导后续尝试；Agent Workflow Memory 进一步关注可复用工作流，从历史经历中归纳操作方法，再选择性提供给后续任务。但反馈不能只留下"成功"或"失败"：相同的失败可能来自代码缺陷、环境异常、观察器错误或业务概念混淆，用同一种反思模板很容易形成宽泛但不能指导行动的建议；**有价值的反馈应保留发生条件、判断依据和被排除的解释**。

RSI（Recursive Self-Improvement，递归自我改进）按改动对象分三个层次：**执行内迭代**改当前任务的计划或产物（测试失败，修改这次需求的代码）；**跨任务自改进**改持久知识、工具或工作方法（保存已验证的兼容经验，供下一轮使用）；**改进过程的自改进**改生成、选择和验证改进的方法（根据后续表现，修改经验抽取或 Skill 优化策略）。Darwin Gödel Machine 研究了迭代修改 Agent 自身代码的路线——维护候选 Agent，通过编码评测筛选改动，改变的是解题系统的工具和工作机制，不只是某道题的代码；Skill∞ 则把递归关系表达得更直接，用 task skill 保存解决方法、用 meta-skill 描述如何优化这些 skill，meta agent 根据执行轨迹诊断问题、提出候选、请求独立审查并分配搜索预算，同一种优化过程还可以作用于 meta-skill 自身。一个版本改进"如何定位 Bug"，另一个版本改进"如何分析定位失败、并生成更好的定位方法"；后者是否有效，要看它能否在给定预算下产出更好的 task skill。**Skill∞ 将评分放在自改进范围之外**，候选还需要经过独立审查——允许改进方法，与允许改低评分标准，是两件事。

对企业研发而言，可以从外部记忆、工具和流程开始探索，无需先改基础模型权重；同时，**一次正向实验也不足以说明系统能够持续、无限地变强**。本体与 RSI 不是互相成立的前提，但当主要卡点来自概念理解时，本体就成为一个值得改进的对象。

## 3. EvoOntology：让本体根据使用反馈演进

预印本 EvoOntology（A Self-Evolving Ontology Layer for Data Agents）讨论的场景是数据分析和 text-to-SQL：Agent 面对数据库或文件时，经常反复确认字段含义、表间关系和过滤条件，即使某次已经查明白，后续任务仍可能重新发现一遍。它把可演进的本体系统拆成 Content、Schema 和 Tool 三部分——Content 保存领域概念、到数据字段的映射、使用约束和支撑证据；Schema 规定这些对象及关系怎样表达；Tool 决定 Agent 怎样找到和展开这些信息；并提供两类访问：browse 找到语义上相关的对象，resolve 取得所需对象及关联记录。会话开始时只提供简要说明，具体知识由 Agent 按需查询——本体既是可维护的知识，也是 Agent 实际会使用的接口。

卡牌查询案例很直观：要找在某种游戏赛制下被禁用的卡牌，初始本体知道卡牌与合法性记录的关联，也知道状态存放在 legalities.status，但没有明确状态相对于赛制成立；Agent 能找到字段，却还要自己重新确认如何使用。演进把问题定位为**语义内容缺失**，增加状态值的含义、对应字段、观测证据及约束——要找目标赛制的禁用卡牌，需要同时满足 legalities.status = 'Banned' 与 legalities.format = target_format；只检查"禁用"会丢掉适用范围。这次改动补充的是内容，不需要修改查询工具或整个 Schema。

更重要的是方法：它先分析执行轨迹，判断限制来自内容缺失、工具暴露不合适，还是当前 Schema 无法表达所需知识；每个候选针对其中一个层面作局部修改，然后让候选与原版本在相同模型、验证集和交互预算下比较，**改善达到设定幅度才保留，未通过的修改记录下来，不直接部署**；同时区分用于构建和选择候选的材料、与最终测试任务——本体在最终测试前冻结，不能一边看到测试答案、一边补充语义后再报告同一批成绩；完整查询仍由工具执行并验证，本体只提供有依据的解释与使用条件。

把 Reflexion、Agent Workflow Memory、EvoOntology、Skill∞ 放在一起，路线逐渐具体：不要把所有失败统一归为"模型还不够聪明"或"Memory 还不够多"。同样表现为定位失败，背后可能完全不同：代码关系没找到、业务含义理解错、旧经验的条件不匹配、或者已经知道约束却没有执行相应检查。**本体可以让这些反馈有更明确的归属**：一次失败不只关联一个会话，还可以关联到某个业务概念、某条跨仓映射、某个状态条件、或者某项错误推断；下一次优化就有了具体对象，不必把整份记忆重写一遍。比如，把"请求受理"和"业务完成"混为一谈，需要补充或拆分概念；概念已经准确、但搜索只返回相似旧案例，需要调整索引或适用性过滤；检索和解释都没有问题、却仍省略数据面检查，则要检查工作流程和验证工具。这几种问题不能只靠增加同一句提醒来解决。

老工程师看代码时的判断，是提取什么知识的标尺：他可能不知道某个函数的精确行号，但知道这段逻辑处在什么业务流程、谁负责推进状态、哪个消费者还依赖旧协议；看见特殊分支会想起保留它的原因；看见异常知道先查哪项观察，才能区分环境问题和真实缺陷；也知道哪些条件在流程变化时仍然必须成立。"知道自己还不知道什么"同样重要——老工程师会区分当前实现、已确认需求和个人猜测，发现冲突时回到设计或找业务负责人确认；提取的项目经验同样要保留这种区别，不把每句自信的解释都当作事实。

## 4. 实践：研发 Loop 里的三层项目知识

实践范围是需求与设计完成之后、从代码实现到上线前测试的一段：人确定目标、设计和必要的业务取舍；Agent 理解需求、实现改动、执行验证，遇到失败就定位和修复，直到得到约定范围内的验收结果。设计完成不代表所有细节都无歧义——一轮开始时，Agent 需要把设计转成可以观察的验收条件，说明对象、范围、输入、预期状态和排除项；发现业务冲突时仍需澄清，不能靠猜测补齐；当前范围也不自动包括生产发布或其他未授权动作。分工上，Agent 负责语义理解、规划、实现和异常判断，确定性工具负责推进已经确定的常规步骤（构建、部署、等待和回执归集，不必每一步都重新交给模型决定）；**工具成功也不能替代业务验收**，Loop 要交付的是对应实际版本的验收证据，而不只是模型的一句"完成了"。

团队 Memory 已有四类资产：Chat Memory 保存对话中的背景、澄清与决定；Wiki 组织业务与架构知识；CodeGraph 提供代码结构和依赖；Skill 保存可复用的处理方法；四类资产分别有自己的用途，原始来源也应保留。在这些资产之外，是单仓和跨仓可用的三层关联图谱：**第一层工程事实**主要依靠工程手段建立函数、类型、字段、接口及其使用者之间的关系，类似 CodeGraph，但还包含跨仓关联，整体偏静态——帮助 Agent 知道定义在哪里、谁使用它、一个功能可能跨越哪些仓库；跨仓关联需要通过 API、消息或 Schema 等契约核对生产者与消费者，不能仅凭同名符号连边；对反射、配置路由等动态行为，静态图也可能无法确定实际路径，需要用运行信息补充；"代码中可能连接"与"这次实际执行经过"仍有区别。**第二层项目语义**结合工程分析与 LLM，提取功能职责、业务概念、定义之间的关系、字段含义、跨仓映射及相关约束，同样支持仓内和跨仓；相比第一层更偏动态，会随着新材料和理解修正而更新——第一层告诉 Agent 一个字段从仓库 A 传到仓库 B，第二层进一步解释两端分别是什么意思、是否发生单位转换、默认值是否相同、哪些版本需要兼容；LLM 生成的候选关系，不能仅凭语言流畅就升级为项目事实。**第三层 bug_fixed**将历史 Bug 整理成经验，挂到前两层的相关节点和关系上，以渐进式披露的方式供 Agent 使用；代码能找到相关经验，经验也能反查涉及的代码和业务约定。这里要区分"发生过的一次事件"与"可以复用的经验"：事件记录版本、现象、条件、原因判断和修复；经验提炼其揭示的风险及适用范围；一次事件可能支持多条经验，多个事件也可能共同支持一项约束；故障表现位置、根因位置和补丁位置也可能不同，不宜压成一条没有说明的"关联代码"。

三层互索引意味着模型可以从任何一层进入：有明确符号时从工程层开始，只有业务需求时先找概念，面对故障现象时先检索经验；进入之后再依据当前问题选择下一条关系，不必固定执行"先读代码，再读语义，最后读历史"。渐进式披露用来控制这段过程的信息量：首先提供关联理由、风险摘要和适用范围，然后展开触发条件与检查方法，最后读取完整差异、对话和运行证据；**关键前提必须跟摘要一起出现**——一条经验只适用于旧协议，就不能把版本条件藏到最后一层；权限和项目范围也应在检索入口受到约束，跨仓可导航不意味着可以读取所有仓库；图遍历还需要预算和停止条件，找到足以支持或排除当前假设的材料后，就应回到任务。

语义的提取与维护上，不想让同一个抽取 Prompt 把所有材料都压成几条类似的总结：先用工程分析定位符号与契约，再让 LLM 围绕高频误判生成语义候选，每条候选都带来源、对象、版本和适用条件，再用设计、实现、测试或领域确认相互核对。概念卡除了定义，还应包含易混淆对象、状态作用域、工程映射、关键约束和验证入口；一条经验则至少保留现象、触发条件、原因依据、处理方式和不适用条件。内部复盘的父实例删除案例是关键证据：父实例已经完成删除，逻辑拓扑表中仍保留记录，早期判断将其视为脏数据；后续核对发现父实例与子拓扑状态属于不同作用域，逻辑记录也不能等同于物理进程，因此**撤回了原先"已证实删除缺陷"的定性**——字段和数据都找到了，但对象或适用范围没有完整表达；清理 helper 的安全检查即使通过，也不能证明业务上应该清理；反过来，当前实现保留记录，同样不足以证明所有版本都应该保留；需要先核对删除契约，再分别观察业务状态、逻辑数据和物理资源。对这样的经验，下一步是沿关联追踪更正影响：旧结论被替代后，引用它的摘要、Skill 和测试假设应进入待复核状态；原事件不必删除，但不能继续以已确认规则指导新任务。另一次复盘记录了"读过但没有落实"的问题：共享管理端口的经验已经被读取，后续观察器仍然按错误的一一对应关系作判断——**仅靠召回日志不能确定经验是否生效**，一条稳定约束最好能对应本轮的对象映射、测试断言或动作前检查。

## 5. 初步结果，以及怎样检验后续改进

在一项内部代码 Bug 定位试验中，加入上述图谱能力后，Agent 的问题定位成功率从 **58% 提升到 65%，增加了 7 个百分点**。这是目前得到的一个初步正向结果，说明三层关联知识在这批定位任务上值得继续验证。定位是完整 Loop 中的一项子任务：找到问题之后，补丁是否正确、回归是否充分、环境是否稳定，都会继续影响最终交付；**这个结果尚不能换算成完整研发效率的提升，也不能单独证明本体语义层贡献了全部增益**。

要分开几种能力：工程图是否让跨仓代码更容易找到？语义解释是否减少了对象和条件误判？历史经验是否提供了更好的诊断起点？三层配合是否比任何单层都更有效？这些问题需要在相同模型、信息来源和预算下做分层对照。比较图谱与普通 Memory 时，信息来源尤其重要——如果图谱组额外获得了历史工单，而普通检索组只能读取代码，结果可能反映的是信息增多，不能完全归因于组织方式；更合适的比较是给两组同样的材料，观察关系与适用性表达是否带来额外收益。bug_fixed 还对应两种不同的业务价值：已知故障再次出现时找回旧解法，可以减少重复劳动；目标 Bug 从未进入图谱时，用其他事件的经验完成定位，则更能体现迁移能力；两种结果应该分别报告。评估未见问题时，需要排除目标补丁、后续回归测试、重复工单和从这些材料抽出的间接关系；只删除目标 Bug 标题不够，语义层也可能保留答案线索；时间切分和来源追踪既是实验要求，也能帮助发现生产图谱中的过期知识。

对于持续学习，一个可行实验是按时间推进任务：一组使用冻结版本的图谱，另一组只吸收已经结束任务中形成并通过检查的经验；两组在下一批未见任务上比较，同时保留旧任务的回归检查；如果新知识提高了一部分任务表现，却让原先能完成的任务退化，这同样必须计入结果。更接近 RSI 的尝试，则是把知识更新过程也纳入比较：固定抽取策略与新抽取策略处理同一批历史材料，分别生成候选图谱，再在独立任务上检验；改进对象可以是概念拆分规则、跨仓映射核对方法、经验适用性筛选或 Skill 生成流程；**不能只因为新策略生成了更多关系，就认定它更好**。借鉴 Skill∞，若修改的是学习策略，就要检验它能否在多个任务中产生更有用的知识或方法，而不仅是修好某一条经验。

企业场景还需要外部边界：知识可以修订，业务目标与权限不能由学习过程自行放宽；Agent 可以指出测试工具不可靠、提议修正，但不能通过删除失败用例获得更好的成绩；高影响约束的发布、版本切换和回退也应保留审查机制。成本同样要计入：语义抽取、图谱维护和额外检查会消耗时间，检索噪声还可能引入新的错误；最终要比较用户等待的端到端时间、模型与工具开销及维护投入，而不能只看累计执行耗时或知识条目数。当前三层图谱的定位收益，与系统持续改善学习方法，是两项需要分别取得证据的目标。

## 6. 结论：让项目理解成为下一轮的起点

本体帮助明确业务对象、关系和约束，让经验有可核对的含义与适用范围；Memory 保存这些知识以及它们的来源；Loop 提供行动与反馈；自改进机制则利用后续结果判断什么应该保留、修正或放弃；当改进过程本身也能被检验和优化时，才进一步体现出递归性。当前的实践，是在设计完成到上线前测试的研发 Loop 中引入团队 Memory，并用工程事实、项目语义和 bug_fixed 三层图谱关联仓内与跨仓知识——让 Agent 可以从代码找到经验，从经验反查实现，再通过概念和约束判断是否适用。58% 到 65% 的定位结果给出了初步信号，完整 Loop 的收益和持续学习效果还需要继续验证。

值得模拟的，是老工程师对项目的那些有效联想：知道一段代码负责什么、为什么这样设计、哪里曾经出错、怎样检查自己的判断。这些理解不必一次提取完整，但应该能够逐步积累，也能够在新证据出现时更正。一个 Loop 结束后，除了交付需求和测试结果，还希望留下这轮新弄明白的项目知识——下一轮能够可靠地从这里开始，就少一次重复理解，少一次相同误判；本体与 RSI 在内部研发中的结合，可以先从这件具体的事情做起。

## 深度分析

### 本体的真正卖点不是"多一层存储"，而是让反馈有了落点

全文最值得提炼的一条主线是**归因**：同样表现为定位失败，背后可能是代码关系没找到、业务含义理解错、旧经验的条件不匹配、或者已经知道约束却没有执行相应检查——四种病因对应四种完全不同的修法（补图谱、拆概念、收紧适用范围、改工作流）。没有本体时，一次失败只能关联到一个会话；有了本体，它可以关联到某个业务概念、某条跨仓映射、某个状态条件或某项错误推断，下一次优化就有了具体对象，不必把整份记忆重写一遍。 EvoOntology 的方法论与这条主线同构：先分析执行轨迹，判断限制来自内容缺失、工具暴露不合适还是 Schema 无法表达，每个候选只针对其中一个层面作局部修改。 这本质上是一个"先诊断、再动刀"的闸门——与 [评估-优化防火墙](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/eval-optimizer-firewall.md) 的思路一致：归因必须先于优化，否则改进只是随机扰动。

文章还点出一个容易被忽略的代价：本体与 RSI 的结合需要同时具备"能关联"和"能纠正"两种能力——收紧适用范围、拆开误合并的概念、撤回不成立的结论，而不只是继续增加内容。 一个只会增量的知识系统，错误经验被更稳定地召回，反而让错误重复得更稳定。

### 三层是访问结构，四类是材料形态——别把"几层"画成存储架构图

四类记忆资产（Chat Memory / Wiki / CodeGraph / Skill）与三层图谱（工程事实 / 项目语义 / bug_fixed）描述的是两个维度：前者是材料的形态与用途，后者是知识之间怎样关联和访问，两者不是七类平行资产。 这与 [Agent 记忆三层基底](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/agent-memory-substrate-three-layer.md) 的分层视角可对照，但本文多了一层工程约束的细节：第一层跨仓关联必须经 API、消息或 Schema 等契约核对生产者与消费者，不能仅凭同名符号连边；静态图也分不清"代码中可能连接"与"这次实际执行经过"。 第二层由 LLM 生成候选关系，但不能仅凭语言流畅就升级为项目事实——语义层要围绕工程位置给出可核对的解释。 第三层严格区分"发生过的一次事件"与"可复用的经验"：一次事件可能支持多条经验，多个事件也可能共同支持一项约束，故障表现位置、根因位置和补丁位置还可能不同，不宜压成一条没有说明的"关联代码"。 这组区分恰好对应 [情节记忆与语义记忆之分](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/episodic-vs-semantic-memory-agent.md) 在工程侧的落法。最关键的一句是"本体不需要再成为第四层"——它体现在第二层的概念与约束表达中，第一层提供工程锚点、第三层提供历史反例，两者都能帮助修订项目语义。

### "保存不等于学会"的两道闸门：可撤回与可观察

父实例删除案例是全文最有信息量的证据：父实例已删除、逻辑拓扑表仍保留记录，早期判断视为脏数据；后续核对发现两者属于不同作用域、逻辑记录不等同于物理进程，于是**撤回**了"已证实删除缺陷"的原定性——字段和数据都找到了，但对象或适用范围没有完整表达。 由此引出的机制要求是：旧结论被替代后，引用它的摘要、Skill 和测试假设应进入待复核状态；原事件不必删除，但不能继续以已确认规则指导新任务——这需要版本化的陈述和依赖关系。 这正是 [记忆固化与衰减](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/memory-consolidation-decay.md) 的工程化表达：撤回路径不是删除，而是让依赖链降级。第二道闸门是可观察性：共享管理端口的经验已被读取，观察器仍按错误的一一对应关系作判断——**仅靠召回日志不能确定经验是否生效**，一条稳定约束最好能对应本轮的对象映射、测试断言或动作前检查。[记忆派生可观察性](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/memory-derivation-observability.md) 讲的正是这层：召回 ≠ 生效，生效必须有行为证据。

### RSI 的保守主义：把评分、冻结和独立审查放在改进范围之外

把 Darwin Gödel Machine、EvoOntology、Skill∞ 三条线并排看，共享的不是"系统会改自己"这个口号，而是三条防御性设计：Skill∞ 将评分放在自改进范围之外，候选须经独立审查——允许改进方法，与允许改低评分标准，是两件事； EvoOntology 让候选与原版本在相同模型、验证集和交互预算下比较，改善达到设定幅度才保留，未通过的修改记录下来不直接部署，且本体在最终测试前冻结，构建候选的材料与最终测试任务严格分开； 企业侧则先从外部记忆、工具和流程入手，不改基础模型权重，并明确"一次正向实验不足以说明系统能够持续、无限地变强"。 这套纪律把 [Agent 自改进回路](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/agent-self-improvement-loops.md) 与空想区分开：被改进的对象可以变，裁判标准不能由被裁判者自己改。[RSI 到持续学习](https://github.com/QianJinGuo/wiki-public/blob/main/entities/rsi-to-continual-learning-compounding-intelligence-overseas-unicorn-2026-10-20.md) 讨论的退化风险（新知识提升一部分任务、却让原先能完成的任务退化）在这里被明确要求计入结果。

### 58%→65% 的归因纪律比数字本身更值得复制

+7pt 是初步信号，但文章真正严谨的是它**拒绝把这个数字兑换成更大的结论**：不能换算成完整 Loop 的效率提升，也不能单独证明本体语义层贡献了全部增益；下一步要分层对照——工程图是否让跨仓代码更容易找到、语义解释是否减少对象和条件误判、历史经验是否提供更好的诊断起点、三层配合是否优于任何单层，且必须在相同模型、信息来源和预算下比较。 两组对照时信息来源尤其要对齐：如果图谱组额外拿到了历史工单，测到的就只是信息增多而非组织方式的收益。 bug_fixed 的两种业务价值（已知故障找回旧解法 vs 从未入库的 Bug 靠迁移定位）应分别报告；评估未见问题时要排除目标补丁、后续回归、重复工单和间接关系，只删目标 Bug 标题不够——语义层也可能保留答案线索。 成本也要计入端到端账：语义抽取、图谱维护和额外检查消耗时间，检索噪声可能引入新错误，最终比较用户等待时间、模型与工具开销及维护投入，而不是知识条目数。 这套"边界声明先行"的评估姿态，比成功率数字本身更接近可复制的工程方法——[hindsight 记忆本体固化](https://github.com/QianJinGuo/wiki-public/blob/main/entities/hindsight-agent-memory-ontology-consolidation-datafun-2026-10-27.md) 与 [MemCurrent 生产级持久记忆](https://github.com/QianJinGuo/wiki-public/blob/main/entities/memcurrent-persistent-memory-production-agents-databricks-2026.md) 处理的是同一族问题：经验进图之后，如何验证它真的改变了行为。

## 实践启示

1. **把失败归因做成显式分类，再决定优化对象。** 同一症状至少有四种病因（代码关系 / 概念含义 / 旧经验条件 / 未执行约束），先诊断后动刀，每个候选修改只针对一个层面；避免把所有失败统一归为"模型不够聪明"或"记忆不够多"。
2. **关键前提必须跟摘要一起出现。** 渐进式披露的顺序应是：先给关联理由、风险摘要和适用范围，再展开触发条件与检查方法，最后才读完整证据；一条只适用于旧协议的经验，版本条件不能藏到最后一层。同时权限和项目范围在检索入口受约束，图遍历要有预算和停止条件。
3. **概念卡与经验必须带"不适用条件"字段。** 概念卡 = 定义 + 易混淆对象 + 状态作用域 + 工程映射 + 关键约束 + 验证入口；经验 = 现象 + 触发条件 + 原因依据 + 处理方式 + 不适用条件。字段不全的经验宁可标记为待复核，也不要以已确认规则的身份进入下一轮。
4. **为每条稳定约束找一个可执行落点。** 对象映射、测试断言或动作前检查，三者必有其一；只有召回日志不算生效证据。自然语言经验升级为强制检查时，要确认契约来源、审查断言，不能让同一套错误假设同时生成实现和唯一验收标准。
5. **对照实验先对齐信息来源，分层报告收益。** 图谱组与基线组给同样的材料，否则测到的是信息量不是组织方式；已知故障召回与未见问题迁移分别报告；排除目标补丁、重复工单、语义层答案线索等泄漏渠道。
6. **学习系统的边界要先于学习设计。** 知识可以修订，业务目标与权限不能由学习过程自行放宽；Agent 可以提议修正测试工具，但不能靠删除失败用例提分；高影响约束的发布、版本切换和回退保留审查机制；成本按用户端到端等待时间计算，不按知识条目数。
