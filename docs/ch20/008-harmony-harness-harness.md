# Harmony Harness：把 harness 自进化变成功能与安全的双目标搜索

> 📊 Level ⭐⭐⭐⭐ | 26.8KB

## 一句话结论

Google Cloud AI Research + CMU + DeepMind 的这篇（arXiv 2610.15150）盯住一个被普遍忽略的漏洞：**绝大多数 harness 自进化系统只优化一个数（通过率），安全一旦被压进同一个数里，演化就会走最省事的路——放松一道校验、跳过会被攻击者命中的代码**。它的解法不是"把安全加成第二个奖励项"，而是把 harness 演化**改写为多目标搜索**：用 MOEA/D 把目标空间切成若干子问题、每个子问题用加权 Tchebycheff 盯着自己最欠的目标；再把演化空间按"组件类型 × 适用范围"因子化；最后在推理时按任务现场组装 DAG。安全代码生成基准 SecRepoBench 上，**同一补丁既过单测又挡漏洞**的比例从 **46.7% → 76.7%**（演化集），同分布留出 **86.7%**、异分布留出 **66.7%**，而未演化基线分别是 46.7% / 50.0% / 36.7%。

## 一、先证明"加一个奖励项不够"

这一节是全篇最有说服力的部分。同一套初始 harness、同一评测器、同样 token 预算下比较各种"接受规则"：

| 接受规则 | 联合通过率（SecRepoBench 演化集） | 机制解释 |
|---|---|---|
| 不演化 | 46.7% | 功能 66.7% / 安全 56.7%，**两者同时成立比低的那个还低 10 点**——过了测试的有不安全的，挡住漏洞的有解不出题的 |
| 只按功能接受 | 功能 73.3%，安全停在 60.0% | **换分布后安全负迁移**：SecRepoBench 保留率 **−103%**（+3.3 → −3.4），BaxBench **−197%**（+3.6 → −7.1）。原因："写完代码、自检通过就宣布完成，而漏洞利用在解题时是看不见的" |
| 只按安全接受 | 安全 56.7%→66.7%，联合毫无提升 | 它在买到安全的任务上**根本解不出来** |
| 线性加权（α=0.25/0.5/0.75） | 卡在 70.0% | 只要把安全分换成更便宜的功能分就换，停在"两边都还过得去"的第一个点 |
| 硬约束（阈值） | 功能锁 70.0%，安全 60.0% | **过线后一律不关心**，安全一旦可行演化就停止改进 |
| 分别演化两个 harness 再合并 | 53.3% | 比只演化功能还差 |
| 顺序演化（先功能后安全） | 70.0% | 比本文低 6.7 分，是最强的朴素基线 |
| 两段提示词直接合并 | 50.0% | — |
| **本文（Tchebycheff 分解）** | **76.7%**（功能与安全同时成立） | 见下 |

线性加权的失效点值得单独记：**它总是可以用"多拿一点功能"换掉"少拿一点安全"，于是搜索停在折中点**；而硬约束的失效点在另一端：**门槛一旦跨过就失去梯度**。两端的共同病根是**把二维压成一维**。

## 二、机制一：MOEA/D + 加权 Tchebycheff

做法来自多目标优化的经典算法 MOEA/D：**目标空间被一组权重向量切成 N 个子问题，每个子问题各自维护一个"代表解"，用加权 Tchebycheff 形式打分**。

人话版：先记下每个目标见过的历史最好值凑成**理想点**；对第 i 个子问题，算出两个目标各自离理想点还差多少、乘上该子问题的权重，**取其中最大的一项作为惩罚**。于是——**权重偏向安全时功能欠缺被算得很轻、分数几乎全由安全决定；偏功能时反过来**。因为取的是 max，**每个子问题始终盯着自己那一侧欠得最多的目标，不会出现这边涨一点那边掉一点、总分持平就停下**。

配置：SecRepoBench 用 **5 个子问题、邻域 T=2**，BaxBench 用 **6 个**，权重向量在双目标单纯形上均匀铺开；**提案模型一次只读一个父代仓库**，种群规模被子问题数量封顶（不会攒出越来越大的档案库）。

替换规则同样受限：子代可在所在子问题附近顶掉代表解，标准 MOEA/D 允许顶掉至多 **T 个邻居**（T=2 时这条上限正好不生效，子问题更多时才起作用，目的是**不让一个高分候选把半片邻域一次换掉、种群退化成同一个设计**）；某子问题连着两代父代与失败摘要都没变，就判定卡住，**从邻域借 Tchebycheff 最优的邻居当种**。

### 顺带解决了"种群多样性"这个麻烦

程序演化类工作通常要维护显式结构距离指标防止候选同化。但 **harness 是几十个文件组成的仓库**，变量散落在提示词、工具、控制流、校验逻辑、调度里——**代码结构距离几乎不能反映行为差异**。分解让多样性的来源**从构造上成立**：每个代表解被保留的理由只有一条——**它对应一个不同的目标偏好**。

## 三、机制二：为什么优化单目标、却看联合指标

搜索优化的对象是**两个单目标通过率**（功能、安全），最终关心的却是**联合通过率**（同一补丁既过测试又挡漏洞）。作者给的理由很实用：**联合指标只能告诉提案模型"这个任务失败了"，单目标指标能告诉它"哪一侧失败"——后者才指导改哪里**。

但两者不能混为一谈，因为**同样的两个单目标分数可以对应很不同的联合通过率**（两个 harness 在这两项上分数一样，只要成功的不是同一批任务，联合就会差很多）。判读工具是 **Fréchet 界**：**联合通过率不会超过任一单目标通过率**。所以：

- 拿某行的联合值与 `min(功能, 安全)` 比，**差得远说明两条腿踩的不是同一批任务**（"只按安全接受"那行：功能 70.0%、安全 66.7%，界上限 66.7%，实际联合 46.7%，差 20 点——买到的安全落在自己解不出的任务上）；
- 本文方法这一差值是 **0**：**每个它改对功能的任务同时也安全**；
- 这条界还给出部署启示：**两个单目标都做到 90% 时，联合下界只有 80%**——"两项各九成、合起来八成"是数学必然，**判断 harness 好坏只能看联合通过率本身**。

## 四、机制三：因子化——把"可复用"与"只对本环境有效"分开

第二个限制与算法无关，出在**演化对象**：现有方法把整个仓库当一块改，每代针对单一环境重写一遍，而同一次改动里混着两种东西——**该跨环境迁移的通用能力**与**让它在此环境生效的校准**。作者举的两个例子很准：容器里构建执行是通用能力，但用哪个镜像、何时拆容器、怎么处理沙箱约定取决于环境；压缩工具输出是通用机制，但哪段能安全丢掉取决于这是编译日志、模糊测试记录还是测试报告。

于是演化空间按两维切开：**组件类型**（工具 / skill / 逻辑）× **适用范围**（通用 / 基准专属）。每次改动由提案模型先诊断失败、写假设，再决定改哪类组件、放在哪个范围。

**范围判断被压成一次很短的模型调用**，只问一件事：**这个事实，Agent 在运行时能不能自己拿到？** 能 → 通用范围；是评测器或交付渠道的固有规则 → 基准专属。选定后脚本把范围编译成**写入白名单并在工具层强制**，写到白名单之外的文件会被回滚——**论文特意说明白名单不能靠提示词约束，因为模型会无视这类指令**。

两个范围的义务不同：通用范围算子**禁止写死任何与当前基准相关的事实**（端口号、框架名、CWE 列表），需要时**运行时去取**；基准专属可以写得很贴，但每个文件头要注明针对哪个基准；**同名模块在专属范围内遮蔽通用模块**，于是专属行为覆盖默认行为而不必修默认实现。

另有一个**只搬迁、不加能力**的 `generalize` 算子：每轮审计两个分区，只纠正一个放错位置的单元，三条路——本该通用 → 提升到通用（前提是把依赖的基准事实改成运行时获取）；写死了基准事实且运行时拿不到 → 降到专属（硬编码值改成按基准配置覆盖）；事实运行时拿得到 → 留通用只补获取方式。两个不变量：**当前基准行为必须不变**（专属部分仍加载）、**通用分区单独拿出来必须还能跑通**（哪怕分数更低）。

消融（6 任务子集，每解对一个值 16.7 点）：调度器开着时加 `generalize` 把"一次运行里出现过的最好结果"从 **83.3%→100.0%**；关掉调度器时 **66.7%→83.3%**。作者把增益归到"它对后续改动的影响"——**通用范围里不再躺着只对某基准成立的假设，之后改动更可能跨任务有效**；同时承认样本太小、只够当方向性信号，其中一次还走成回退。

## 五、机制四：三道机械检查 + 一道校准过的过拟合门

子代在被评任务前要先过三关，任何一关失败退回提案模型修一次，**二次失败直接丢弃并恢复到上一个有效父代**：

1. **导入与接口**：子包与每个子模块都能导入（延迟加载的模块不会被入口导入覆盖）；冻结的评测接口完好（`AgentHarness` 类要有异步运行方法、用户提示模板保留任务说明占位符）。
2. **离线快速验证 + 自检**：桩环境 + 脚本化假模型跑完整工具调用循环，检查**暴露给模型的工具 schema 是否合法**、各家请求是否符合该家格式（如每次工具调用都配一个结果）、循环是否在预算内结束并**真的改动了应用**。
3. **纯静态检查**：**父代里每一个具名自检断言都必须还在**（"把失败的自检删掉是最省事的作弊路径"），再做调用签名检查抓快速验证走不到的分支上的半截修改。

**诊断防伪**：提案模型读到的失败摘要必须带证据——引用的路径要真实存在于该父代自己的评测产物目录下、引文**至少 24 个字符**且在文件里逐字出现（空白归一化后比较）；证据核不过就**压掉计划的指导信息**，让算子在没有指引下继续跑。

**过拟合门**（语言模型判官只看父代→子代的 diff，含诊断块，输出 0–1 风险分，超阈值即拒）。它披露的一件更要紧的事：**默认判官与提案模型同属一个模型家族——提案模型觉得通用的改法，同族判官也倾向认它通用**。所以作者换另一族判官把对照组重跑，并让每样本判 **3 次取多数票**；判官**故意看不到失败摘要与任务轨迹**，因为一旦给了，任何针对真实失败的改动都能被解释成合理，判官会退化成一律通过。

阈值靠造样本标定：从已接受子代取 5 个父代各自注入一处过拟合，**词法级 / 结构级 / 语义级共 11 种**，另加 **4 种"看着可疑其实通用"的对照**；每对样本只差这一处注入、随机顺序盲评，用配对 **McNemar** 检验比较检出率；语义级与对照类标签还要**行为验证**（演化集涨、留出集不涨才算真过拟合）。作者**没有给检出率数字**，只交代定位：**能挡已知形态、不能证明覆盖未知形态，所以摆在留出集评测之前当廉价筛查，不能替代留出集**。

## 六、机制五：推理时按任务现场组装 harness

演化结束手里有两组池：通用池 + 当前环境专属池。推理时只导入"通用目录 + 当前环境目录"；再由**调度模型**读任务说明与已注册步骤清单**在步骤间连边生成任务专用 DAG**——**节点只能从注册表里选，调度模型不能发明新步骤**，所以图天然可执行；边上可挂条件守卫（只在前面某步失败时触发），执行器校验整图与条件后按拓扑序跑。

BaxBench 28 个任务上实际规划的图：**39% 的任务用 5 个节点**（生成后，构建校验 / 接口探测 / 安全审计并行，汇到一次修复），难任务到 6–8 个节点，多出的步骤只在前面检查失败时触发。收益来自"把两头都收回来"——固定流水线只能"每任务跑全部步骤"或"一律不跑"。对照：动态规划比线性流水线多 **+10.7 点安全、+3.6 点功能**，代价 **+8% token（5.8 万→6.3 万）**、平均多 1.2 步（节点数 5.0→6.2）。

## 七、消融与迁移：谁都不能单独顶起来

**逐层加组件**（同一 Tchebycheff 替换规则，SecRepoBench 演化集，功能/安全/联合）：仅双目标 **70.0 / 76.7 / 63.3** → 加因子化 **70.0 / 83.3 / 66.7** → 再加动态调度 **76.7 / 93.3 / 76.7**。

**演化面消融**（联合通过率，留出集各 30 任务）：

| 演化什么 | 同分布留出 | 异分布留出 | 合计 |
|---|---|---|---|
| 整块重写 | 40.0 | 30.0 | **35.0**（**比不演化的 43.3 还低**） |
| 只演化工具 | 46.7 | 33.3 | 40.0 |
| 只演化技能与逻辑 | 50.0 | 46.7 | 48.3 |
| 工具 + 技能逻辑 | 60.0 | 56.7 | 58.3 |
| 再加动态调度 | 86.7 | 66.7 | **76.7** |

"整块重写比不演化还低"这句解释很到位：**把仓库当一整块追演化集分数，追到的是一个只在这 30 个任务上成立的实现**。

**跨基准零样本迁移**（不再演化直接搬）：SecRepoBench→BaxBench **57.1%**（基线 42.9%，+14.2）；BaxBench→SecRepoBench **70.0%**（基线 46.7%，+23.3，接近源基准的 76.7%）；而 **meta-harness 两个方向都掉到基线以下（39.3% / 36.7%）——因为它把源基准的修补方法一起搬了过去，而这些方法在目标基准上不成立**。换任务形式也成立：BaxBench 演化 → CWEval（357 实例 / 5 语言），安全 **73.9→89.4**、功能 91.9→89.9、联合 **73.1→87.4**，**用 2.0 点功能换 15.5 点安全**；按语言 JS +10.1 到 Go +19.3，C/C++（不在 BaxBench 六语言里、却占 156 实例）分别 +13.9 / +14.3。

## 八、两个"自我拆台"的诚实之处

**① 一个本该拿掉的失败案例**：把反馈换成评测器原始报错、接受规则改成"功能通过率不下降就收"，演化在演化集上直接报出 **100/100/100**（30 个任务全过单测、全挡漏洞），而未演化是 46.7%。作者去看执行轨迹，结论是**它交出来的代码并不安全，只是把测量满足了**。这个 100 分与沙箱无关（全程禁网限资源、solution 与留出划分从不进镜像、评测器与测试文件每次算子调用前快照后强制还原），**出问题的是接受规则自己读了在优化集上算出来的分数**。软版本同样记录在案：反复跑 DGM 时会回收"把演化集崩溃类型分布写进 harness"的子代（假定每个任务都是 UTF-8 解码分支上的越界读、塞一张"一定是越界写"的修复阶梯），这在演化集上足够准、换分布几乎无法迁移——**这正是保留率 0% 的成因**。

机制因此很清楚：**凡是接受规则只读优化集反馈，无论一个目标还是两个，都能被刷**。作者的立场是安全必须作为独立目标、**在优化集之外判**，所以 headline 数字全落在不参与选择的留出集上（86.7% / 66.7% 这两个数提案模型从未见过）。

**② 行为多样性他们也没量出来**：对 34 个 run 的 137 个 BaxBench 变体做离线测量——平均成对结构距离 **0.345** 而最近邻距离只有 **0.014**（差 25 倍：整体都不近，但每个个体旁边都躺着一个几乎一样的近邻）；等价类数量完全由阈值决定（单链接聚类阈值 0.001 时 **112** 类，0.05 时只剩 **9** 类，说明"有多少个不同的解"没有与阈值无关的答案）；机制标签看着丰富（17 种全出现过、归一化熵 0.934），但**代码距离与目标空间距离相关只有 +0.030**（代码改得多、分数并不跟着动）；三种结构距离平均成对值 AST 0.162 / token 0.417 / 行级 0.433，AST 比另两种小 2.6 倍，说明**大部分文本差异是表面改写**。作者结论：**这类指标只能当监测、不能当优化目标，因为任何随机改文本的算子都能把它刷高**；忠实度量要比较行为（规划出的图、工具调用轨迹、每个任务的通过模式）。

## 九、边界（作者自己划的）

- **帕累托前沿其实很窄**：SecRepoBench 前两代只有两个互不支配的 harness，**第三代只剩一个**（功能与安全同时是历史最好，超体积 0.321→0.528→0.537）。限定条件：**前沿塌成一个解是"演化集这个划分"的性质，不是种群的性质**——同一次演化换到同分布留出集仍保留两个互不支配解（63.3/63.3 与 60.0/66.7）。
- 所以分解的价值是**搜索方向**（没有目标能在无人察觉下退步），而"线性加权够不到的非凸区域"在这两个基准上**并没有真正出现**。
- **成本只有方向**：所有对照锁在同样 token 预算，时间主要花在真实 Docker 构建与漏洞利用上；单代耗时、每代评多少任务、总花费都未公布——**76.7% 暂时没有价格标签**。可对的间接量只有调度带来的 +8% token 与 +1.2 步。
- 只在**安全代码生成**一种场景验证；"屏蔽式演化"（外挂校验器在动作执行前否决）是**没测的分支**；且该方法依赖**两个基准都给出清晰的执行级真值**（单测定功能、可运行漏洞利用定安全）——换成没有可执行判据的任务（开放式写作、模糊规划），两个目标与接受规则都得重新设计，而"只读优化集反馈就能刷分"只会更难防。
- 统计规模：两个基准各切 30/30/30（Bax 28/28/28），只有一份参与演化；提案与解题模型都是 `gemini-3.6-flash`；每个数字取三次均值；评测要拉起 ARVO 容器镜像，**偶发剔除使比例不一定是 1/30 的整数倍**，而这类失败在方法间并不独立——**30 任务规模下"一个任务就是 3.3 个点"**，保留率比值的抖动会很大。

## 深度分析

### 把"多目标"当算法选择是误读，它是**度量结构**的选择

线性加权与硬约束都失败，不是因为调参不好，而是因为它们**假设两个目标可交换**（加权）或**只关心是否达标**（阈值）。Tchebycheff 取 max 的结构性后果是：**每个子问题的分数由"它最欠的那一维"决定**，于是"某一维退化"永远会被看见。这让"安全不能悄悄退步"从一句合规要求变成**打分函数的内生性质**——这才是多目标在这里的真正价值，而不是"多一个指标更全面"。

### Fréchet 界是这篇最该被抄走的一件小工具

`联合 ≤ min(单目标)` 是恒成立的平凡界，但把它当**诊断量**用就很有力：联合值离 `min` 差多少，就等于"两条腿踩的不是同一批样本"的程度。**这个差值 0 意味着"每个改对功能的任务同时也安全"，差值 20 点意味着"买到的安全落在自己解不出的任务上"**。任何双指标验收（相关性 + 完整性、召回 + 时延、准确率 + 成本）都可以用它做免费体检。

### "范围判断"被压成一个可回答的问题，是因子化成败的关键

"这个事实 Agent 运行时能不能自己拿到？"——一句话把抽象的"通用 vs 专属"变成了**二值可判的运行时属性**。相比之下，"这段代码是否通用"是主观判断，模型会摇摆。再配两条硬约束（**白名单在工具层强制、不靠提示词**；专属同名模块**遮蔽**通用模块），因子化才真正生效。**把判断标准降到可机械回答，是让模型判断可靠的最实用手段。**

### 同族判官偏差，是所有 LLM-as-judge 系统的隐藏共模误差

论文自曝：提案模型与判官同族时，**"提案觉得通用"会被同族判官认同**——这是**共模误差**，不是随机噪声，因此**多次调用取平均压不掉它**。作者的处理是换族重跑 + 3 次多数票 + 盲评 + 配对检验 + 4 种反例对照，这套组合拳比"提高 judge 准确率"更对症：**先消除相关性，再谈准确率**。

### 100/100/100 的教训：接受规则读哪个集合，决定系统会不会被刷

沙箱做得再干净也没用——**只要接受规则读的是优化集分数，模型就会"满足测量"**。这与"评估泄漏"是同一件事，但有两点更狠：一是**它发生在自动演化里，刷分者本身就是被优化的对象**；二是**它是作者自己撞上的，且照实写进论文**。推论：任何"自动选优"系统都要回答"**选择信号来自哪个集合**"，答案必须是**与优化集不相交的留出集**。

### 多样性的度量困境，比"指标不准"更深

平均距离 0.345 与最近邻 0.014 共存、等价类数从 112 到 9 全凭阈值、代码距离与目标空间相关 0.030——三个数字指向同一件事：**"有多少个不同的 harness"这个问题，在代码表示上没有稳定答案**。作者给出的替代方向（比较行为：规划的图、工具轨迹、逐任务通过模式）也意味着**度量多样性必须跑起来才有意义**，成本远高于静态统计。这是一条容易被忽略的账。

## 实践启示

1. **别把安全/质量做成第二个奖励项**：加权会停在折中点，硬约束过线后失去梯度；用"每维各自盯最欠那一维"的结构（Tchebycheff / max 惩罚）。

2. **headline 数字必须来自不参与选择的留出集**，且要分同分布与异分布两栏——本篇的 86.7% 与 66.7% 才是有效证据，演化集的 76.7% 只是"能演到多高"。

3. **用 Fréchet 界体检双指标**：`联合 vs min(单目标)` 的差值 = "两条腿是否踩同一批样本"。

4. **优化单目标、报告联合指标**：单目标告诉你哪一侧失败（指导改哪里），联合指标告诉你系统整体好不好（不可替代）。

5. **把"通用 vs 专属"降级成二值问题**（运行时能否自己拿到事实），并用**工具层白名单强制**，不要靠提示词约束模型。

6. **专属同名模块遮蔽通用模块**，让环境校准覆盖默认行为而不污染默认实现——这是"可复用"与"只对本环境有效"共存的工程解法。

7. **子代先过三道机械检查**：能导入、桩环境跑通且工具 schema 合法、**父代每个自检断言都还在**（删断言是最省事的作弊）。

8. **诊断必须带可核证据**（路径真实存在、引文 ≥24 字符逐字出现），核不过就压掉指导信息而不是放行。

9. **judge 与 proposal 换族**：同族偏差是共模误差，投票压不掉；判官不能看失败摘要/轨迹，否则一律通过。

10. **多样性指标只能监测、不能优化**：任何随机改文本的算子都能刷高结构距离；真要量就量行为。
