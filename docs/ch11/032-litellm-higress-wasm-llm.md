# LiteLLM 两度被投毒与 Higress 的 Wasm 沙箱防线：LLM 代理的爆炸半径设计

> 📊 Level ⭐⭐⭐ | 15.1KB

## 核心判断：问题不是"会不会被投毒"，而是"投毒之后能拿走什么"

2026 年 LiteLLM（周下载量约 2,300 万的开源 LLM 代理）**半年内两次被投毒**：3 月 24 日的 1.82.7/1.82.8，10 月 21 日的 1.107.0。阿里云云原生（Higress 团队）的复盘给出的框架比"如何防投毒"更有用——**沙箱决定"毒进来之后能做什么"，发布链路决定"毒能不能进来"**；而在"装上就执行"的生态里安全靠运气，在"默认无权限"的沙箱里安全靠架构。

## 事件复盘：一次走完正规流程的投毒

**时间线（北京时间 2026-10-21）**：19:39，1.107.0 出现在 PyPI；**7 分钟后** Docker Hub 与 GHCR 的 `latest`、`main-stable` 等标签被指向投毒镜像；PyPI 约 **1.7 小时**后隔离、Docker Hub 标签约 **2.5 小时**后撤下；Wiz 观察到恶意版本发布后**不到 5 小时**，攻击者就开始用偷来的 AWS 凭证调用 `bedrock:ListFoundationModels`。

**四步攻击链（关键在"每一步都合规"）**：

1. **拿到钥匙**：三名开发者的 **GitHub CLI OAuth Token**（官方推测来自一个对公网开放的内部 LiteLLM 部署日志）。
2. **改写发布流程**：18:08 修改发布工作流被分支保护拦下，**5 秒后**用组织 Owner 权限 Token 覆盖保护强推；工作流改为从**只差一个连字符的仿冒仓库 `Berri-AI/litellm`** 构建；第二个账号"正常"通过生产发布审批；第三个账号删除工作流运行记录。
3. **只毒制品、不毒源码**：`pyproject.toml` 的 maturin 配置多一行 `data = "cook"`，让三个文件落到 `site-packages` 根目录——**`cook.pth`（只有一行 `import cook`，Python 解释器每次启动都执行；pip、IDE 后台、任何脚本启动即触发，不需要 import litellm）**、`cook.py`（解压运行约 **61 KB** 窃密程序）、`sitecustomize.py`（fork 脱离终端的守护进程，**每小时**从 GitHub"死信箱"取地址下载执行未签名代码）。官方 tag 源码干净，但恶意构建源码与它**相差 309 个文件**；这些文件**不在 litellm 包目录里，卸载 litellm 也删不掉**。
4. **能拿的全拿走**：**16 个模块**覆盖 SSH/GPG/TLS 私钥与 Shell 历史、AWS/Azure/GCP 凭证与实例元数据（并调 `GetCallerIdentity` 验证可用）、K8s 配置与 ServiceAccount Token、Docker/GitLab Runner/Jenkins/Vault/Terraform 机密、浏览器密码与 Cookie、**Claude/Codex/Gemini/Cursor/Copilot 等 15+ 种 AI 工具凭证**、Linux 上所有可读进程环境变量。另有**专为 LiteLLM 写的模块**：有 `DATABASE_URL` 就直连代理库查 `LiteLLM_CredentialsTable` 与 `LiteLLM_ProxyModelTable`——**那里存着代理替所有下游团队转发时用的上游厂商 API Key**。外传用 AES-256-CBC + RSA-4096 封装，伪装成健康检查 POST 到 `www.litellm[.]dev/healthcheck`。

**浮动标签是放大器**：`latest`/`main-latest`/`main-stable` 全被改指——**没主动升级、只要在那 2.5 小时里拉过这些标签（比如用 `latest` 的 Pod 恰好重启）也会中招**；Endor Labs 总结："浮动标签和不锁版本，让一个坏版本波及了那些从没选择过它的部署。"官方的处置口径也很直接：**包可以下架，已外传的凭证收不回来**——只要 1.107.0 在能上外网的主机跑过，就按"已外传"处理、轮换一切。

## 为什么 LLM 代理是最高价值目标

两次事件入口不同（3 月是 CI 里的安全扫描器 Trivy 被投毒 → 拿走 PyPI 发布 Token；10 月是 OAuth Token + 篡改发布工作流），但**进门后做的三件事一样**：装上就执行（都用 `.pth` 启动钩子）、**与代理进程同权限**、**直奔"钥匙串"**。Chainguard 的判断是本实体的核心论点：**一台被攻破的代理主机可以一次性暴露许多上游 AI 厂商的 Key**。自建 LLM 代理同时具备三个高危特征——**钥匙集中**（统一接入/计量要求所有厂商 Key 汇总）、**位置敏感**（生产集群 + 云实例角色 + SA + 必须出公网访问模型 API）、**扩展即进程**（Python 代理里第三方依赖与回调都是进程内代码）。

**Key 集中管理本身是好事**（统一接入/审计/轮换的前提），问题只在第三条：**扩展代码拿着进程的全部权限**。因此"爆炸半径"的唯一决定因素是**扩展代码的权限面**，而不是依赖数量或供应链环节数。

## 防线一：Wasm 沙箱——默认无权限

Higress 数据面基于 Envoy（C++）：网关核心能力原生实现，AI 代理/鉴权/限流/内容安全/MCP 等扩展以 **Wasm 插件**运行在 Envoy 内嵌 Wasm VM。**根本区别**：Python 依赖默认拥有进程全部权限，**Wasm 插件默认只有宿主明确开放的能力**，一切经 Proxy-Wasm 接口。可直接对 `proxy-wasm-cpp-host` 源码核对六条边界：

| 能力 | 沙箱行为 |
|---|---|
| 自启动 | 无 `.pth`/`sitecustomize` 类钩子；只在 WasmPlugin 显式引用时加载，代码只在请求处理与配置下发回调里跑 |
| 文件系统 | `path_open` 恒返 NOENT；`fd_read`/`fd_readdir` 注释明示"没有真正的文件系统"——`~/.aws/credentials`、`~/.ssh/id_rsa`、SA token 一字节读不到 |
| 环境变量 | `environ_get` 只返回该 VM 被显式配置的变量（Higress 即 `vmConfig.env`）；宿主与其他进程环境变量"不存在" |
| 网络 | 无 socket（`sock_send`/`sock_recv` → ENOTSUP）；外发只能由 Envoy 代发且目标 cluster 必须已注册——`169.254.169.254`、仿冒外传域名无路可走 |
| 进程 | 无 fork/exec，起不了守护进程、写不了 systemd、部署不了特权 Pod |
| 内存 | 仅自己的线性内存，读不到 Envoy TLS 私钥与他插件内存；崩溃不拖垮 Envoy，可选 FAIL_CLOSE/FAIL_OPEN |

**边界必须说清：沙箱只能限制"越界"，不能限制"职责内作恶"**——插件仍能读写经手的请求响应（可借响应外带）、读自己的配置与插件间 KV；`ai-proxy` 要转发就必须拿到上游 Key。所以沙箱只是四件事之一：只装可信插件、**最小授权**（鉴权插件只拿消费者凭证、模型代理只拿模型 Key）、**版本锁定**（`sha256` 校验不对就拒绝加载）、**凭证托管**（KMS 加密、配置只留引用）。

## 防线二：不可变发布——让"已经在跑的版本"无法被悄悄换掉

自 **v2.2.4（2026-08）** 起，Higress 官方 Go/Rust Wasm 插件采用"**构建一次、评审快照、按 digest 晋升**"，逐环补上 LiteLLM 的失守点：构建来源必须**恰好是 main 分支当前 commit**且候选制品记录源码 commit 与输入哈希、过 PR 评审；镜像用 OCI 注解（`org.opencontainers.image.revision`、`io.higress.plugin.input-hash`）**绑定源码与输入**，正式发布**只按 digest 复制已评审制品、从不重建**；写公共标签的凭证只放在受保护环境 + release manager 人工审批 + 专用发布 App；**公共版本标签不可变**（同名标签 digest 不一致直接失败，`latest` 只在整批校验通过且版本号只增不减时前移，默认配置锁具体版本）；**证据文件（含 SHA-256）提交在代码仓库**（v2.2.4 快照锁 43 个插件，每个含版本/digest/inputHash/sourceCommit）。原文的诚实边界值得记住：**没有流程能挡住所有盗号**，不可变标签的意义是"就算出事，运行中的版本不会被悄悄换掉，换没换一查便知"。

## 处置清单（可直接照做）

**LiteLLM 受影响环境**：①**先别在该环境启动 Python/pip**（每启动一次解释器就再执行一次载荷）；②用 `find`/`sha256sum` 等**非 Python 工具**查 `site-packages` 下 `cook.pth`/`cook.py`/`sitecustomize.py` 与 `/tmp/.pc_once_*`、`/tmp/remote_code_loader.lock`，并杀掉持锁守护进程；③**从干净机器轮换全部凭证**（厂商 Key、master/virtual key、库密码、云凭证与实例角色、K8s Token、Git/npm/PyPI Token、SSH 密钥、AI 工具会话）；④固定 `litellm==1.106.2`、镜像按 digest 引用。**Higress 侧**：插件固定版本号 + sha256、`vmConfig.env` 最小注入、**鉴权插件保持 FAIL_CLOSE**、**只注册业务需要的上游服务（这份列表本身就是出网白名单）**、自研插件与官方插件同等待遇。

## 深度分析

### 爆炸半径的单位不是"包"，而是"身份"

此案最易被低估的细节，是窃密程序专门写了查 `LiteLLM_CredentialsTable` 与 `LiteLLM_ProxyModelTable` 的模块——攻击者拿到的不是几个 Key，而是一张**组织级身份清单**。代理为统一接入与计量，必然把 N 个下游团队 × M 个上游厂商的凭证收敛到一处；收敛是治理成果，却把攻击者的工作降级为"读一张表"，把防守方的负担放大成"轮换 N×M 把"。攻防成本在这一步量级错位。

由此得到比"依赖数量"更可靠的度量：这段代码被投毒后，攻击者继承的是哪些身份的什么权限。若答案是"全部"，加扫描器、缩窗口、加快通报都只在压缩时间窗——**半径由信任边界的位置决定，不由检测能力决定**。

### 启动钩子：为什么"卸载"是最危险的误判

`.pth` 在解释器初始化阶段执行，早于任何用户代码，也不需要被 import。两个连锁后果：**处置动作本身会再触发一次载荷**（`pip uninstall` 就是一次解释器启动，所以要先冻结 Python、改用非 Python 工具取证）；**"包"不再是删除的单位**——三个文件落在 `site-packages` 根目录，卸载 litellm 碰不到它们。

性质更值得记住：这不是漏洞，是打包格式的合法能力（构建配置里声明 data 目录）被用于持久化。所以别寄望"这类手法被修掉"，只能把 `site-packages` 根目录的 `.pth`、`sitecustomize.py`、顶层 `.py` 纳入基线哈希巡检——粒度是"目录里的可执行入口"，不是"已安装包列表"。

### 沙箱的三个决定，各自的代价

**默认无权限**买到的是结构性不可执行：无启动钩子、无文件系统、无 socket、无 fork。代价实打实——Wasm 处理大报文要把请求体复制进线性内存，而线性内存可增不可缩，于是团队会把核心重链路挪出沙箱换吞吐：边界往往就是从这种"合理妥协"开始被侵蚀的。**env 最小注入**的失效模式很具体：一旦用 HOST 方式透传宿主变量，这条边界等于整体删除。**FAIL_CLOSE** 的代价是可用性：插件 trap 或超时即拒绝，于是总有人提议改 FAIL_OPEN——对鉴权类插件，这等于把安全组件改成可用性组件，"出错即放行"是最坏的默认值。

还有一处易漏的耦合：注册的上游服务列表本身就是出网白名单。好处是策略不漂移；坏处是"为新模型随手加个 upstream"事实上就是一次白名单扩张，该按安全变更评审。

### 不可变发布买到的是"可判定性"，不是"不可能"

快照加 digest 真正回答两个事后问题：线上跑的是不是当初评审过的那一份；它对应哪个 commit 与哪组输入哈希。原文承认没有流程能挡住所有盗号，这应读作范围声明而非免责——digest 挡不住评审时已含恶意的制品、挡不住运行时替换（热更新、挂载卷、sidecar），也挡不住被盗凭证在别处使用。

它比"签名"多一层：签名只说"谁签的"，快照还说明"用什么输入构建、能否复现"，事故后能把影响面收敛到"哪些制品用了这份被污染的输入"。摩擦成本也要接受——人工审批加快照 PR 是真慢，而这层摩擦就是作用机制；指望"零成本的不可变发布"等于指望它不生效。

### 迁移到 Agent 基础设施的等价设计

平移到 Agent 栈，同一模式正在重演，只是入口换了：第三方 MCP server 的常见装法是 `npx`/`uvx` 拉最新版并继承整个进程环境变量，一次集齐浮动版本、启动即执行、凭证全可见。等价设计是独立进程运行、env 显式白名单、出网只允许声明域名、工具清单本身当权限清单评审。

agent runtime 更棘手：它同时持有模型 Key、代码执行能力与内网凭证，还读取不可信内容——提示词注入把"代码执行"直接变成"攻击者代码执行"。所以不只是加沙箱，而是**把持凭证的组件与读不可信内容的组件分到不同信任域**，凭证以短时按次注入而非常驻 env；工具执行侧照搬 Wasm 语义：默认无文件系统、默认无网络、**按次授权而非按进程授权**。

一条判据收束：任何"扩展与主程序同进程"的架构都会被同一类手法打穿；换语言、换运行时、加扫描器都不改变这一点，只有把信任边界画在进程或 VM 之间才改变。

## 可迁移的工程判断

1. **"扩展即进程"是 Python 生态的结构性风险**：只要扩展与代理同权限，任何依赖投毒都等于整套凭证泄露；换语言不解决，**换信任边界才解决**。
2. **启动钩子比 import 更危险**：`.pth` + `sitecustomize` 让载荷在"什么都没 import"时执行，也让"卸载包"失效——排查必须扫 `site-packages` 根目录而非包目录。
3. **浮动标签把被动升级变成被动中招**：`latest` 的风险不在你选错版本，而在你**从未选择过它**。
4. **不可变发布的价值是事后可判定性**：不能阻止盗号，但能让"运行中版本是否被替换"成为一条可查的事实。
5. **凭证集中管理必须与权限最小化同做**：只做前者是放大器，只做后者是运维负担。
