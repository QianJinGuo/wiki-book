# PolarDB-X 缺陷修复 Agent：把「稳定复现」做成交付门禁

> 📊 Level ⭐⭐⭐ | 17.8KB

> 阿里云 PolarDB-X 团队（盛涛涛/无沐）把「报警/工单 → 排查 → 复现 → 修复 → 验证」整条链路交给 Agent 自主执行，研发只做审核。半年内从上万次报警中识别并记录 200+ 缺陷，**超过 70% 能稳定复现**并由 Agent 修复后进入评审；首轮分析覆盖率 100%。文章摘录自 Alibaba Cloud AI Agent Handbook 实践篇章。

## 起点：时间不在改代码上

作者年初修过一个 Bug：最后真正要改的代码只有**两行**，但前面查日志、看监控、分析问题就花了一整天，为了复现又在会议间隙反复调试，前后接近一周，之后还要补测试用例、跟进评审。由此提出本文的核心问题：AI 已经能帮我们写代码了，但**如果只帮写那两行代码，其实没省下什么时间**——那些真正费时的工作能不能也交给它。

PolarDB-X 是分布式数据库，正确性与可靠性要求极高：多组件多模块、线上多个版本并存，一处修改可能影响其他功能。让 Agent 参与研发，同样要面对这些约束。

## 任务二分：新功能 vs 缺陷修复

团队把研发任务分成两类，采用不同协作方式。**第一类是新功能开发或已有功能优化**（优化分布式事务、实现新的数据压缩能力），涉及组件多、实现细节要在开发中不断调整——研发仍主导方案设计与关键决策，Agent 主要协助编码与测试。**第二类是工单、报警与缺陷修复**：问题相对明确、代码修改通常较小、结果可通过测试验证，且是团队长期痛点——因此**让 Agent 自主完成，研发负责审核交付结果**。这个二分是本实践成立的前提：不是「Agent 能不能写代码」，而是「哪类任务的结果可被验证」。

## 端到端流程与三个门槛

流程是：Agent 接到报警或工单 → 获取现场信息 → 分析可能原因 → 准备环境尝试复现、验证自己的判断 → **问题能稳定复现之后才修改代码** → 把复现过程固化成测试用例 → 通过回归测试 → 将代码与验证结果交给研发审查。

要让 Agent 自主跑完这套流程，首先要保证产出可靠。业界的可靠性讨论多集中在编码阶段（用 Skills 或约束保证代码正确），但作者认为**缺陷修复中最重要的一步是稳定复现**：没有复现，就无法确认分析结论是否正确；分析错了，代码写得再规范也可能没解决真正的问题。据此设了三个关键门槛：**现场信息完整、问题能稳定复现、修复结果必须经过测试验证**，后续的工具与环境建设都围绕这三条展开。

## 现场还原：先让研发系统可被 Agent 调用

报警和工单通常只记录现象，要形成完整修复需求还得补现场：看监控、查日志、结合源码判断是否属于缺陷。早期这些由研发完成，确认后才整理成需求交给 Agent；后来团队把现场信息直接交给 Agent 分析，发现它**往往做得比人更好**——能把问题前后的时间线梳理得更清楚，擅长从海量日志中检索分析，还能注意到人工排查遗漏的线索。于是进一步让它直接接收报警与工单：查询实例管控平台的拓扑、配置、任务流，查看监控指标与日志，再结合代码仓库的实现与变更继续分析。

典型链路：一条 SQL 执行报错，Agent 从报警里拿到实例 ID 与报错信息，到日志系统找到对应错误堆栈，再结合源码分析原因，最后整理出问题现象、现场证据与原因假设。

**关键基础设施是 CLI。** 以前是把监控截图发给 AI 让它看曲线，但曲线便于人观察，Agent 需要的是按需查询、解析、比较**原始数据**——阿里云官方 CLI 可让 Agent 拿到指定时间范围、指定节点的结构化监控数据。日志则应先汇入 SLS 这类日志平台，再通过查询接口或 CLI 提供给 Agent，这样分析中缺什么信息它就能自己查，不必等研发补材料。

存量平台没人维护、也没人提供 Agent 可用工具怎么办？团队的做法是**自己封装 CLI**。灵感来自阿里内部一个很受欢迎的「抢会议室」CLI——作者只是普通研发同学、并没有会议室平台源码，却能用一条命令订会议室。于是让 Agent 参考已有 CLI 的实现与认证方式，操作网页分析背后的接口请求，再把需要的功能封装出来；**大约一周**就把监控指标、日志、实例拓扑等常用功能集成成一套 CLI。

## 静态分析的失败：为什么必须有运行时验证

团队遇到过一个低概率并发问题，线上存在很久、因难复现一直没查清。Agent 拿到现场信息后**几分钟**就给出一份分析报告，代码位置、执行过程、可疑点都写得很完整、很有说服力；但团队花约**两个小时**验证，发现解释不成立。反馈后再给一版，再验证，还是不对，来回几次留下一堆报告，问题依旧没查清。

原因是 Agent 当时只能做静态代码分析，缺少动手手段——而人排查时都需要准备环境、尝试复现，必要时打打断点、控制线程执行时序、检查内存数据。于是团队补了**调试**与**内存分析**两类工具，让 Agent 能自己动手验证。

**调试工具**：核心组件用 Java 编写，最初尝试 JDK 自带的 JDB，但它面向人设计、需要终端持续交互，Agent 要维护交互进程再通过进程通信收发命令，很麻烦。团队基于 Java 调试接口**重新实现了 JDB CLI**：会话管理在后台保留调试进程与现场，前台每条命令执行完即可退出、下次调用仍接同一会话；结果以结构化形式返回，Agent 可解析检查，也可等待断点命中后获取线程、栈帧与变量信息。最关键的是**指定线程断点**——只让目标线程触发断点、命中后只暂停该线程，其他线程继续运行；配合恢复操作就能控制相关线程按特定时序交替执行。

**内存分析**：检查锁泄漏时的内存现场要看 Java 堆快照（Heap Dump），可查看对象字段值、引用关系与内存占用。Heap Dump 文件通常很大，团队把文件放到大内存云服务器集中加载处理，**专门给 Agent 提供查询接口**——Agent 按需查询所需内存数据、根据结果继续分析，不必本地处理整个大文件；分析完还可把记录与报告上传平台，供研发查阅。这样**内存现场成为 Agent 可直接检查与引用的证据**。

## 复现环境两档：秒级临时实例 vs 完整集群

只有工具没有环境，Agent 仍然无法真正复现。团队提供两档：**PolarDB-X Zero**——Agent 可在**几秒内**创建临时实例，快速尝试复现简单问题（SQL 报错、功能异常），用完立即释放，版本固定，适合先做快速验证；**K8s 完整复现环境**——问题需要特定历史版本、特定拓扑或复杂并发场景时，按问题实例的版本与拓扑搭建集群，再配合调试工具复现。代码改完后，Agent 还能把修复版本部署到该环境，用同样方法检验原问题是否已解决。

## 稳定复现：用线程时序构造偶发问题

回到那个并发问题：有了工具与环境，Agent 能自己尝试复现，并依据实际运行结果继续分析与调试；经过几轮迭代找到关键触发条件，**复现出与原问题相同的 MDL 锁泄漏现场**。关键在于它通过调试工具让两个线程按特定时序交替执行，把原来很难碰到的偶发问题**主动构造**出来；调试结果还能与内存现场相互印证，确认复现的就是同一个问题。此时团队既有根因分析、又有可重复执行的操作步骤，还观察到这些步骤确实触发了原问题——**分析结果有了实际运行的证据支撑**。稳定复现的另一重价值是让修复有了明确验证依据：这些步骤可固化成测试用例，检查代码修改后的效果。

## 门禁：修复前必须复现，修复后必须消失

实际交付中，**稳定复现用例被设为进入代码评审的关键门禁**：Agent 补了测试、测试通过，还不足以说明原问题已解决，**首先要确认用例确实触发过那个问题**。同一个用例，在修复前版本上必须稳定复现原问题，在修复后版本上必须验证问题不再出现；完成这组对照并通过完整回归测试，代码才能进入评审。Agent 提交 MR 时一并交付代码、用例与验证结果；研发先检查有没有对应复现用例、对照最初问题描述确认复现的确实是原问题，才继续审查代码改动，通过后按流程合并。前面那个低概率并发问题最终也由 Agent 完成修复并通过验证。

## 持续运行：从笔记本到云端沙箱

要让这套流程承担日常工作，还需要一个持续运行的环境。早期跑在笔记本上，**屏幕一合上流程就断了**；要让 Agent 持续处理报警、分析问题、修复缺陷，运行环境必须独立于研发的本地电脑。团队基于**云端沙箱**构建了 PolarDB-X Agent，使其 7×24 小时持续运行；云端沙箱还能与本地开发环境隔离、避免影响研发电脑，并可限制沙箱内工具的访问与操作权限，让执行过程更安全可控。

## 结果

所有报警都会先由 Agent 完成首轮分析与处理，**首轮覆盖率 100%**；半年内从上万次报警处理中识别并记录 **200 多个缺陷**，其中**超过 70% 能稳定复现**，并由 Agent 完成修复后进入代码评审。研发从「排查、复现、修复」中抽身，改为审核问题描述、代码修改与验证结果。

## 三条可借鉴的工程启发

①**让研发系统可以被 Agent 调用**：从团队常用系统入手，给它们配 CLI 工具或开放 API，让 Agent 能自主获取信息、操作这些系统，分析缺材料时自己补齐；②**让研发过程可以验证**：提供调试工具与运行环境，让 Agent 自己复现问题、检验分析结果——实际运行的反馈才能帮它发现错误、调整分析、完成修复；③**让任务流能够持续运行**：把流程放到云端，不依赖研发本地电脑。作者建议其他团队先选一个目标明确、结果可验证的任务，备好工具与环境把流程跑起来，再按实际问题逐步完善。

## 为什么这篇值得单独立实体

库内 SRE/AIOps 实体讲的多是**告警分诊与根因定位**（`agentic-incident-triage`、`aws-devops-agent-autonomous-incident-resolution`），编码类实体讲的是**写代码与评审**（Kitta 领域化 CR Agent、淘宝 AI-SRE 代码质量治理）。本篇补的是中间那一段没人做的：**把「稳定复现」变成可执行、可验证、可门禁的工程对象**——为此重写了 JDB CLI（会话化 + 指定线程断点）、把 Heap Dump 变成查询接口、用秒级实例与 K8s 集群两档环境承接复现，最后用「修复前必现、修复后必消」的对照把修复质量钉死在评审之前。这条链路也是「验证驱动」在缺陷修复场景最完整的一个实例。

## 深度分析

### 稳定复现为什么必须是交付门禁

缺陷修复的本质风险不在「代码写得对不对」，而在「改的是不是真问题」。静态意义上再规范的补丁，如果根因分析错了，就什么都没有解决。把门禁设在复现而非评审，等于把「分析是否成立」的裁决权交给可重复执行的环境：同一个用例在修复前版本上必须稳定触发原问题，在修复后版本上必须验证问题消失，这组对照把修复质量钉死在人工审查之前。它与「测试通过」是两种不同的证据——测试通过只说明新代码没有引入回归，复现对照才说明原问题确实被消除。这也是本篇与 [AWS DevOps Agent](https://github.com/QianJinGuo/wiki-public/blob/main/entities/aws-devops-agent-autonomous-incident-resolution-datadog.md) 只做到事件分诊与处置建议的本质分野。

### 运行时验证对静态分析的不可替代性

那轮失败迭代给出了一个精确反例：Agent 只花几分钟就产出一份结构完整、论证自洽的分析报告，人花约两小时验证却发现解释不成立；反馈后再来一版，仍然不对，来回几轮留下一堆报告而问题依旧。失败原因不是模型能力不足，而是它当时只有静态代码分析一种手段——代码文本里没有真实的运行时序、没有锁的实际持有状态，任何解释都无法自证其正确。人排查同类问题要做的事（准备环境、打断点、控制线程时序、检查内存数据）恰恰是它缺的。可推广的教训是：对并发与状态类缺陷，「解释的说服力」与「解释的正确性」完全解耦，必须靠实际运行的反馈来闭合验证回路。

### 用线程时序把偶发问题变成必现问题

指定线程断点是这套工具链里最关键的设计：只让目标线程触发断点，命中后只暂停该线程，其他线程照常运行，再配合恢复操作，就能让相关线程按特定时序交替执行。这把偶发缺陷从「等待运气」变成「主动构造」——Agent 靠它复现出与原问题一致的 MDL 锁泄漏现场，再经 Heap Dump 查询接口核对内存现场，调试结果与内存证据相互印证，确认复现的就是同一个问题。这个思路与 [STAROps 故障注入](https://github.com/QianJinGuo/wiki-public/blob/main/entities/starops-aiops-eval-set-fault-injection-aliyun-2026-10-28.md)同源：确定性地注入触发条件，换取可重复执行的验证信号，分析结论由此获得实际运行证据的支撑。

### 环境分档：复现成本与场景真实性的折中

两档环境对应两类复现需求：PolarDB-X Zero 秒级临时实例承接 SQL 报错、功能异常这类简单问题，用完立即释放且版本固定，把快速验证的边际成本压到接近零；K8s 完整集群按问题实例的版本与拓扑搭建，承接需要特定历史版本、特定拓扑或复杂并发的场景。关键在于闭环：修复完成后把修复版本部署回同一环境，用同样的方法检验原问题是否消失——验证信号与复现信号出自同一环境，排除了环境差异掩盖问题的可能。这套「约束动作空间 + 环境验证」的搭建方式是 [Harness Engineering 框架](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/harness-engineering-framework.md)在缺陷修复场景的生产实例，也与 [环境验证驱动](https://github.com/QianJinGuo/wiki-public/blob/main/entities/from-spec-driven-to-environment-verification-driven-ai-coding-wu-zuoyan-2026.md)的概念主张相互印证。
