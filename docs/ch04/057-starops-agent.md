# STAROps 评测集：把运维 Agent 的「过程可信」做成可重跑的数据

> 📊 Level ⭐⭐⭐ | 24.5KB

## 核心命题：结论正确不等于过程可信

阿里云 STAROps 是生产运维 Agent，通过连接多域数据、运维工具与专家经验做根因分析与处置。这篇讲的不是它的能力，而是**怎么评它**：一次根因分析可以抽象成"输入 → 多轮（Agent 判断、工具取证）循环 → 诊断结论"，评测的难点在于**每一轮的判断与取证站不站得住**，因为结论正确也可能是碰巧正确。

具体要评三件事：①**思路能否通用**——同一类故障表现好，换场景、换异常类型可能就不行，评测集必须覆盖足够多的场景；②**结果错在哪一步**——是工具没查到，还是查到了没用对，数据要能逐步对照"调了什么工具、返回了什么、据此做了什么判断"；③**执行效率**——结果对了也要看有没有无效工具调用、上下文有没有越堆越乱。

**最隐蔽的失效模式是"时间窗查错"**：工具调用成功、返回真实数据、推理前后自洽、结论甚至可能碰巧正确，只是数据对应的不是这次故障发生的时间段——从外面看一切正常。要发现它，数据里必须记下故障的真实时间窗，再与 Agent 实际使用的时间窗对照；这正是后文"时间绑定"与"告警锚点"两项要求的来源。

## 评测数据的三条基本要求

**覆盖要广、能重复执行、每一条要能证明自己有效**（文中三栏数字来自外部公开研究，不是本评测集统计）。覆盖：一版公开运维根因数据集在三个系统上覆盖 27 类注入机制、500 个可评测实例，仍不足以代表真实环境。重复：同一 Agent 对同一场景跑 10 次只有 6 次诊断成功，原因包括模型不确定性与环境变化，所以"只跑一次、只留成功那次"不够。有效：有些数据集有故障输入输出却缺乏清晰因果——注入了 CPU 故障就把 CPU 当标准答案，而同样的异常在真实运行时完全可能由别的原因导致；另一项研究从九千多次初始注入里只保留 1,430 条，其余按标准没有造成可感知异常——**执行了注入不等于产生了可用数据**。

## 一条评测数据长什么样

核心要求是**能还原一次完整的分析轨迹**。轨迹分五步：**目标**（要考核什么，例：从下单错误/商品查询错误/前端异常三条告警定位根因）、**观测**（指标/日志/调用链/事件/拓扑/变更记录）、**工具**、**动作**（定范围→提假设→排除→定下一步，以及每次取证调用）、**结果**（根因实体、传播链、影响面、处置建议）。只看答案只能比结论，保存轨迹才能看出在哪一步查错数据、在哪一步判断失误；但轨迹不要求固定路径，**关键判断、关键证据、关键动作必须明确**。

轨迹之外必须同时保存两样：**配套条件**（环境、工具、观测手段）与**核验依据**（评价标准）。理由是评测集要反复评不同版本——配套条件没一起存，下个版本跑同一道题时环境工具已变、轨迹不可比；评价标准没固定，同一条轨迹这次判对下次判错，分数变化就说不清是 Agent 变了还是判分的人变了。

运维场景还特有四项约束：**环境绑定**（故障离开真实服务、流量与观测就不存在，数据与产生它的环境一起存）、**时间绑定**（调用链与日志有保留期，要及时把时间窗与当时证据保全，否则无法回头核验）、**完整因果链**（原因、传播、影响每一步都要有证据）、**低频高风险**（线上不能反复试，用故障注入在同一机制上造，可重复执行）。

## 12 步 4 阶段的构建流程

图上一共十二步、四个阶段，**注入只是其中一步**，注入前后的准备、取证与核验才是大头（等告警、核信号、取证、写答案、过两道检查，任何一步不过都要退回重来）。

- **设计（Agent）**：选场景（能力地图空格 + 线上回流）、设计故障（注入什么、注入在哪、沿哪条链传播、影响哪里）。
- **注入、验证与恢复（工具）**：注入准备要确认处在未注入的**干净基线**（流量在跑、观测可查）；**注入成功只说明命令跑完，故障是否生效要看信号**（后文"信号捕获"六项）；等告警真正出现（告警既是诊断起点，也是标准答案的锚点）；最后恢复环境，让下一次注入从干净状态开始。
- **取证与写答案（Agent）**：故障期间与恢复之后两个阶段都要取证——故障期间的信号、告警与调用链反映"正在发生时"的状态，要当场保存；恢复后再取一次，才能把注入点、根因、传播链、影响面完整还原，并按七字段写标准答案。
- **检查与入库（程序 + 人）**：**程序门禁**查能写成规则的事（字段齐全、每个数字附可执行查询且重跑同值）；**准入复核**查需要判断的事（因果链说不说得通、相似候选有没有排除干净）——先由 Agent 审一遍，**审核时不沿用构建时的上下文，重新取证据核对**，最后由人决定是否入库。

终点是"STAROps 拿着同样输入做一次诊断"，输出与标准答案逐字段对照——所以前面每一步都影响评分：故障没真发生，答案就是错的；证据没取全，评分缺依据；检查没把住，错答案会把正确诊断判成错。

## 四个核心问题与四 Agent 分工

持续构建要解决四个互相依赖的问题：**如何选题**（能力域 × 难度规划 + 线上回流）、**如何建环境**（按需扩展）、**如何保证有效性**（故障注入构建循环）、**如何高质量迭代**（质量检查）。"环境不稳，有效性无从验证；题目来源不受控，效率再高也只是批量生产熟悉的那几类。"

分工是四个 Agent 各管一段、各四项工作：**ScenarioAgent**（缺口识别、变更分析、架构还原、现场回流）、**EnvironmentAgent**（拓扑构建、业务仿真、流量注入、观测接入）、**BuildAgent**（故障注入、信号捕获、证据提取、准入复核）、**SupervisorAgent**（质量体检、失效识别、回归复测、难度进阶）。人只做三件事：**定目标**（哪些能力域/难度优先补、先做哪一格）、**定验收**（标准答案要哪些字段、证据到什么程度）、**终审**。

作者把这个过程本身当成**对 Agent 能力与基础设施成熟度的压力测试**，考验四方面：Agent 自身能力（理解业务架构、正确调工具、基于证据推理、发现自己的问题）、Agent 间协同（角色间输入输出与状态传递，前一角色产出必须是后一角色可靠输入）、**基础设施**（工具是否标准化、环境能否重建、上下文与状态怎么存、长任务怎么恢复、失败怎么重试、角色间怎么交接、证据怎么追踪——"这一层往往最关键"）、治理与质量机制（程序检查、证据校验、独立复核、人工终审）。

## 能力地图：8 个能力域 × 4 档难度

横轴是能力域：代码与变更、应用运行时、数据库、容器、中间件、云产品、主机、网络；纵轴是难度：单点故障、有传播链、多故障并发、告警风暴。**纵轴不是互斥分类，而是"要排除多少干扰才能定位"**：单点故障一个异常一条线；告警风暴同时十几个信号在响，真正的根因藏在里面。地图上每一格放具体场景——单点行从配置改错、接口内部错误、慢查询、容器反复重启、队列积压、CPU 打满、磁盘写满到丢包；传播链行有发布引发报错、依赖超时堆积、锁等待致超时、节点驱逐降级、缓存击穿压库、主备切换断连；多故障并发已有发布叠加限流、限流叠加超时；**告警风暴整行还是空的，标为下一批构建任务**。空着的格子就是还没覆盖的，由人确认优先级再交给 Agent 构建。

## 线上回流：先保全，再还原

第二个出题来源是线上真实问题——它可能落在已有格子里成为真实样本，也可能是地图上原来没记录的机制，**那就要补一格**再规划后续构建。顺序很硬：**先保全，再还原**——线上出问题时先用工具把轨迹、调用链与当时时间窗保全，否则证据过期就取不回来。之后三步：**机制还原**（Agent 弄清因果与必要条件，同样报错可能来自不同原因）、**等价重放**（工具用同一机制重新执行，只复现报错不算）、**重建验证**（程序对齐线上与重放信号，信号先后反映传播顺序，时序对不上就退回重建）。验证通过后交 BuildAgent 用**同一套七字段与检查**做答案核验，线上数据与注入数据才能放在一起比较。

## 按需扩展环境：覆盖需求触发，观测优先

环境扩展**由覆盖需求触发**，单纯规模变大不构成理由：能力地图出现空白、线上出现新机制、或故障需要隔离时才扩。起点是一个开源微服务样板加脚本驱动的下单链路（只能做应用层单点故障）；每新增一类故障域就扩一次——加主机域要有主机层注入手段与主机指标，加云产品域要接入云产品自己的观测与告警。做跨集群与多故障并发时克隆第二套集群，流量从脚本扩成**常态 + 场景化两层**（常态让环境像真实系统一直有请求在跑，场景化让要验证的传播路径真有请求经过），告警阈值用历史数据回放校准。

一次扩展五步：Agent 读依赖与已有环境定要补什么 → Agent 编排、工具按模板生成部署或克隆集群 → 接通观测与两层流量、建告警、回放校准 → **程序检查未注入时的基线**（常态流量必须干净、观测必须可查，不过就停止构建）→ 产出可复刻的**环境配置代码**（拓扑/业务/流量/观测 + 固化注入与恢复）。三项长期要求里**优先保证观测**：缺少它，连数据中的故障是否真实都无法确认。

## 构建循环：注入三路、信号六查、答案七字段

**注入三路**：复用已固化的注入方式、改配置（配置类故障）、改代码（程序内部错误）。无论哪条路，**注入完成后都要逐项证明故障真的发生**，不能因为命令执行成功就认为故障发生。

**信号捕获六项必查**：告警源头（是否由本次注入对象触发）、环境变更（同时间有无别的变更混入）、指标异常（根因相关指标是否真的异常）、调用链路（异常是否沿链传播）、影响范围（哪些上下游受影响）、**噪音干扰**（同一时间窗有别人的故障在跑，信号就说不清是谁的，这条数据直接作废）。

**答案七字段**（标准答案的格式决定评估能查到什么；只记"时间+根因组件+原因"的格式没有因果链，无法回查依据、难区分相似候选，数字没有固定时间窗可重查）：**根因实体**（写到具体资源或服务）、**故障类型**（可验证的机制，不是表面现象）、**因果链**（原因/传播/影响分开写）、**鉴别点**（为什么排除了相似候选）、**告警锚点**（实际触发的事件与时间窗，用于对照"时间窗查错"）、**关键数字**（必须附原查询）、**评分规则**（按字段独立打分，允许根因对而传播链错）。四个取证维度与字段一一对应：注入点与根因→根因实体与故障类型；传播链→因果链的原因到传播段；影响面→因果链的影响段。

**数字必须单独核验**：一条答案写着错误率约 25%，人工阅读没发现异常，工具重查连续五个时间窗错误数均为零；还有两类数单看都像对——查询接口有返回上限时返回条数不能当总数、基线窗与故障窗长度不同时比值不能直接用。结论是一句硬规则：**写不出查询的数字，不能进入标准答案**。

## 质量五项：按短板检查，失效下架、修复后复测

入库通过不代表长期有效：**质量**（证据完整、七字段齐、数字有可执行查询）、**覆盖**（类型与难度分布对照能力地图）、**区分度**（强弱分差能否拉开）、**规模**（最低样本与总量是否够）、**新鲜度**（抽样原样重跑能否跑通）。五项**按短板检查，不能用平均分抵消局部问题**。新鲜度的判据不是数据年龄，而是"当初的信号今天还能不能复现"——基础镜像、告警规则或观测配置一变，昨天建好的数据也可能跑不出来。

两种处理：**失效的下架**（否则被评 Agent 在这些题上答不对会被记成能力问题，研发去修一个不存在的缺陷）；**Agent 修复后在仍有效的数据上复测**（混着失效题，分数变化就说不清是修复还是数据带来的）。所以先判断是数据问题还是 Agent 问题，再决定下架还是复测。

**区分度最不直观**：评测集用久了强弱都接近满分，两条曲线在顶部重合，"Agent 能力提升"与"数据难度不足"呈现相同结果，单看分数决定不了该发版还是补数据。做法是**主动加难**（把单点换成有传播链、多故障并发，告警风暴建好再叠），曲线重新分开说明原数据已难区分能力；**加难后分数下降是题目变难，不能读成能力退步**。作者还给出外部研究对照：2026-08 PAIChecker 复查 SWE-bench Verified 500 条发现一成多任务描述与参考修复不对齐（质量）、2026-06 CORE-Bench 在几十条修订任务上最强配置已近满分（区分度）、2026-07 一项研究按置信区间决定评多少数据（规模）、ICML 2026 MMBench-Live 只取一年内上传图像（新鲜度）。

## 规模、成本与开源

截至 9 月，评测数据 **1,400 多条**（含已复核与在建）；其中**根因分析 838 条**已复核有效、覆盖 **100 多类故障类型**，**3 月还只有 58 条、半年增长 10 倍以上**；另有**取数 500 多条**（Agent 取数取得对不对同样要评）。公开数据集不少仍要自建，三个原因：服务拓扑与告警规则是自己的、线上新机制公开集合里没有、环境一变已有数据要能立刻重跑。

**成本结构**分三段（示意而非实测）：起步以人工为主 → 补齐环境与判据阶段环境投入快速追上人工、人工在此见顶 → 复用已有构建路径阶段重复人工回落、构建侧模型调用超过人工。最终**环境**成为三项里最高的一块（集群、流量、观测常年运行，覆盖越广越大）。结论很克制：**用了 Agent 总成本不一定下降**，减少的只是重复人工操作。公开研究也有类似做法（2026-06 一条被接受的任务约 40 美元、1-2 小时；2026-08 Agent 流水线筛选材料并保留专家校准判据）。

开放共建三方向：**开源**（RCA100、RCA200 已开放，后续逐步开放更多数据与评测方式）、**共建**（更多团队提供真实环境与领域经验）、**重建**（把公开场景描述搬进真实环境重建；共建与重建尚无对外时间承诺）。下一步是让评估侧 Agent 根据**地图空白、分数长期接近上限、线上新问题**主动发现缺口并发起下一批构建，能力更新后自动复测、稳定后再提难度。

## 深度分析

### 为什么"过程可信"在这类任务上是硬要求

运维根因分析的输出本身包含推理链（根因实体、传播链、影响面），一旦只比最终结论，两种错误会被系统性地漏掉：**碰巧对的答案**（时间窗用错但结论撞对）与**过程无效但结果正确的答案**（乱调工具、上下文越堆越乱）。轨迹化评测把"证据—动作—判断"三者钉在一起，代价是数据构建成本从"写一道题"变成"造一次故障 + 取一轮证据 + 过两道检查"——这也是它必须自动化的原因：人工逐条做，规模上不去。

### 时间绑定是运维评测的特有难题

通用 Agent 评测可以用静态快照，运维不行：调用链与日志有保留期，**证据会自然消失**。所以"数据"不是一条记录，而是"某个时间窗、某套环境下的一次完整快照"；线上回流必须先保全（否则不可回溯），标准答案必须带告警锚点（否则无法核对 Agent 用的是不是这段时间的数据）。这条约束把评测集的时间语义从"版本"推进到了"窗口"。

### 程序门禁与准入复核分开：规则与判断不能混在一个关卡里

字段齐全、数字可重跑是**规则可判定**的；因果链说不说得通、相似候选排没排干净是**需要判断**的。混在一起的后果是：要么用规则去判语义（把合理答案判错），要么用模型去判格式（放过缺失字段）。更关键的是独立性设计——准入复核**不沿用构建时的上下文、重新取证**，因为一旦顺着构建者的叙述走，复核就退化成确认偏误。这条与"复核的独立性来自证据的独立"是同一条原则的两次表述。

### 区分度衰减是评测集的必然命运，只能靠主动加难对冲

任何评测集都会被"刷满"：题目固定、Agent 变强，分数逼近上限后失去分辨力。STAROps 的处理不是等分数下滑，而是**在分数接近上限时主动升难度档**（单点→传播链→多故障并发→告警风暴），并用"加难后曲线是否重新分开"判断原数据是否还有效。这背后是一条经常被忽略的判据：**分数下降有两种含义**——能力退步或题目变难，必须靠难度档位而非分数本身来区分。

### 成本不降是诚实的结论

多数"用 Agent 做 X"的文章会暗示成本下降。这里给出的是三段式结构：人工在中期见顶后回落，模型调用随构建量上升，而**环境成本最终成为最大项且持续增长**（集群、流量、观测常年运行）。这解释了一个容易被忽视的组织事实：**评测能力的天花板由基础设施预算决定，而不是由 Agent 数量决定**。也正因为环境最贵，"覆盖需求触发扩展"这条纪律才重要——按需扩，而不是按规模扩。

### 评测集构建是一次 AI Native 压力测试

作者把"能否自动构建可信评测集"当成组织能力的探针：它同时要求 Agent 理解业务架构、正确调工具、基于证据推理、发现自己结果的问题，要求角色间有清晰的输入输出与状态传递，要求基础设施提供可重建环境、可追踪证据、可恢复长任务，还要求治理层有程序检查、独立复核与人工终审。换句话说，**评测集是这套系统交出的成品，而不是它的准备工作**——这也解释了为什么"用一个 Agent 还是多个 Agent"不是重点，重点在能力、工具与环境是否被建设到可自主调用与协同的程度。

## 实践启示

1. **先定义"过程可信"的判据**：轨迹五步（目标/观测/工具/动作/结果）+ 配套条件 + 核验依据，比一堆分数更能定位问题。

2. **把时间窗当第一等公民**：线上先保全再还原，标准答案带告警锚点，否则"查错时间窗"这类错误永远发现不了。

3. **注入成功 ≠ 故障发生**：六项信号必查，尤其噪音干扰——同一时间窗有别人的故障在跑，数据直接作废。

4. **标准答案只写可重算的事实**：每个数字附查询与时间窗，写不出查询的数字删掉；按字段独立评分，允许"根因对、传播链错"。

5. **规则与判断分两道门**：程序门禁查字段与可重跑，准入复核查因果与排除，且复核必须重新取证、不沿用构建上下文。

6. **按短板检查评测集**：质量/覆盖/区分度/规模/新鲜度，失效下架、修复后只在有效数据上复测。

7. **主动加难而不是等天花板**：分数接近上限时升难度档，用曲线是否重新分开判断原数据是否仍有效。

8. **预算要算环境**：集群、流量、观测是长期成本，评测能力上限由基础设施而非 Agent 数量决定。
