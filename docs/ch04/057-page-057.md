# 天猫数字员工：以一个数字同事接管需求全链路（实践篇）

> 📊 Level ⭐⭐⭐ | 21.2KB

## 核心命题：不是"每人一套 Agent"，而是团队共享"一个"数字员工

天猫技术统一建设的 AI 端到端交付架构，以**钉钉群为统一入口**驻进需求群承接交付：与产品、前端、后端、测试共享同一份需求上下文，接需求、写方案、调度 Agent、跟进交付。已在天猫技术所有业务线推广，**月均活跃需求交付 100+**。区别于一般 AI 编码工具的两个视角——**协作**（所有角色共享同一份上下文，让协作重新连起来而不是被 AI 切碎）与**资产**（把散在人脑与聊天记录里的业务认知，从组织维度沉淀成可复用资产）。

**关键产品论证（为何不是按岗位拆一组 Agent）**：按岗位拆出数字 PM/前端/后端/测试再加编排器，能提升单任务专业化与并行度，但**需求上下文仍会在角色交接时被切断**——产品侧澄清得到的信息不会自然进入技术侧执行上下文，需求收口、跨角色对齐、组织知识沉淀仍需额外解决。因此选择让团队在协作现场共享同一个数字员工身份和同一份需求上下文；"一个"不限制背后调用多少子 Agent（需求分析/编码/测试），而是强调**面对团队只有一个稳定入口**，收口、术语对齐、执行进展与最终产物都回到同一现场。

**执行方式的取舍**：稳定可枚举的环节（阶段、输入输出、门禁明确）适合工作流编排，便于控制与审计；研发需求又有强差异性（只做评估/改配置/跨仓编码），难以全部固化成同一条流程。因此**不是工作流与 Agent 二选一，而是确定性流程与动态规划并用**：主 Agent 判断意图与任务形态、按需调子 Agent/Skill/工具；进入评审、测试、发布等稳定环节后由明确流程与门禁约束执行。

## 自主交付率：一个把"人在环内"算清楚的定义

需求能在既定流程与门禁内连续推进，**没有因为流程中断、执行错误或结果不符合预期而需要人工纠正、驳回或重新启动**，才算一次自主交付。**方案判断、权限授权、评审确认和最终验收属于计划内的人类节点，不视为流程中断**。这一定义把"人类该在的时刻"与"人类被迫返工的时刻"分开，是后续效能度量的口径基础。

## 交付能力：三个尺度

**一条需求之内（跨角色接力）**：产品进出结构化 PRD 与待澄清清单（被指"只写接口没写业务逻辑"就按业务逻辑分域重写，接受批评按反馈返工）；前端出页面改动、构建部署与 Diff 预览；后端出技术方案、服务改动与预发部署；测试出测试用例与自测结果——**质量门禁（静态检查→构建→自动测试）+ Harness 浏览器验证贯穿全程，"写完自己验"**，用例带着需求澄清的全部上下文。**编码执行不重造轮子**：沙箱里 Claude Code、Codex CLI、通义灵码按需选，数字员工管"把上下文喂进去、把进度收回来"。真实案例：手猫「问底价」一次迭代从需求描述、元信息录入、代码级澄清到方案评审、测试用例、预发部署，由同一个数字员工**两天内连续处理**，人主要出现在确认与验收节点。

**一组场景之内（开箱即用、按域定制）**：主 Agent 接非流程化协作面（找人/答疑/读文档/查数据/拉群建单），流程化交付交子 Agent；默认路径已预置需求单对接、钉钉文档与多维表读写、数据库操作、数据表理解、迭代创建、发布单创建，默认编码子 Agent 覆盖需求分析/方案设计/编码/测试/发布。**定制定义权归业务**：交付流程以 Skill 装载（分几阶段、每段产出、评审门禁），手猫团队装载**九阶段交付流程**后把需求到方案压到**十几分钟**；能力按业务域配 Skills/Hooks/System Prompt 并关联本域知识库，主/子 Agent 独立定制、分钟级加载。

**一个业务之上（看板与主动推进）**：需求进群后自动维护看板（成员/里程碑/卡点/产物，随讨论与进展更新），群内吊顶卡看当前需求、跨需求用 Web 大盘（四列状态流转、每条一卡、与研发工单系统状态同步）；确认/验收 @ 负责人、超时按规则催办、**每日需求摘要**（状态/下一步/待处理），群成员可回"第 2 条展开说说"追问。

## 系统四层：一条消息的旅程

**① 消息路由（钉钉 Stream → 沙箱）**：官方 Stream 模式建长连接、事件沿连接推送，不暴露公网回调；**除连接状态外还监控"最后一次收到事件的时间"**，识别"连接在、事件不再到达"。三类事件（私聊/卡片回调/群消息），@ 到的进应答、没 @ 的进旁听。**@ 判定踩坑**：平台在不同接收关系下回传的身份标识不适合静态配置 → 网关维护**机器人标识集合**（已确认直接匹配 / 未覆盖用文本规则兜底 / 运行中补全）。**路由规则：一个路由身份一个沙箱**——私聊按发送人、场景群按群会话 ID 派生群身份（一群一箱，群/个人隔离）；多实例收到同一事件先**原子认领**。**网关刻意做"薄"**：不调 LLM、不做业务判断，只做三件确定性工作——接得住（立即回执+原子认领去重）、留得下（图片文件凭证有效期内先行转存）、送得准（识别路由身份、选沙箱、组装统一格式）。**为什么业务调度必须过数字员工**：绕开则"分析完成却没有统一状态与反馈主体"、点"开始编码"时网关不知道分析结果、编码中无关消息无法判断转发还是忽略——管道层若兼做业务判断，状态会分散两侧。返回用"**先建卡再覆盖**"（占位卡取轨道号后续更新同一张）。**运行数据（截至 7 月底）**：热路径首响约 1 秒、P90 三秒内；冷启动首响 P90 约六秒；首响成功率 >99%。

**② 沙箱（一需求一箱）**：一条需求 ↔ 一个场景群 ↔ 一个独立沙箱，代码/依赖/调试状态互不影响。**镜像只含基础环境、运行时代码启动时从发布服务拉取**——发版不重建镜像，在线沙箱可分批升级（守护脚本拉新版、切软链、空闲重启）。创建时网关注入身份/凭证/业务域配置，多仓并行克隆并按特征识别技术栈；冷启动两侧优化：**预热池**（首条消息到达一次性认领，绑定完成前不接业务消息）+ **需保留状态放容器外**。**状态取舍只有一道**：必须保留（会话/记忆/任务状态 → 独立持久卷，重建后重挂）与可重建（仓库代码/临时上下文 → 不留）；`/reset` 只重置运行状态不删持久数据。Session 支持跨端：Web 工作台不另建会话，拉快照回放 + 订阅事件流接续，钉钉与 Web 合流同一沙箱。

**③ Agent 层（调度可控、执行可插拔）**：一主多子，主 Agent 是常驻 Thread；**通用性归执行端、可控性归调度端**。没把通用编码 Agent 当常驻中枢，是因为 AI Card 发送、编码 Agent 调度、卡片时机、多会话状态、确定性直转五项都需要外部适配层（对照表逐项列出）。主 Agent 不退化成规则引擎（"改完了吗""先帮我看看线上报错"仍需上下文判断）；子 Agent 清单按域动态生成、**轮次边界**加载配置、不重建 Thread。**三条工程约束**：同会话中途不换引擎 / 不同后端流式事件统一映射 / **所有模型请求必须过统一网关，未配置网关拒绝启动**。**能力投影三动作**：派发装载（Skills/MCP/Hooks → 执行器原生格式）、执行追问（桥接通道回群提问）、完成收口（事件回主 Thread 统一更新状态）。**确定性路由短路**（源自试点抱怨"部署时轮询占用会话"）：消息先过一道**不调 LLM** 的路由——子 Agent 等待回复时直接转发，其余才进推理；"识别哪些环节不需要调用 LLM，与提升模型调用效果同样重要"。复杂度三档：简单（轻量执行后验证）/中等（单 Agent 执行自检）/复杂（单编码 Agent 分阶段 + 方案确认 + 自检 + 发布门禁 + 异常纠偏）。

**④ 身份与权限（谁干活算谁的，谁消费算谁的）**：四类动作四种身份——读写钉钉文档/多维表用**当轮发送人**（只能访问本人有权数据）；构建/部署/平台登录用**服务身份**（不借个人账号、可独立审计）；提交代码用**当轮发送人署名**（产出归属实际指挥者、个人凭据不落盘）；查中间件/监控/数据平台用**群负责人经身份委托服务授权的身份**（资源端仍按负责人原权限判断、不额外扩权）。**最关键的不是身份有几类，而是模型不能指定任意一个人**：只接受受控角色，角色到真实身份的映射由可信环境注入——模型生成"以某某身份查询"也不被接受。受控资源再加一步**显式授权**：指定技术负责人后只有本人登录确认才生效，请求记录委托用户/执行 Agent/来源沙箱，授权只证明"谁委托了谁"不扩大原权限。**硬约束**：一个沙箱生命周期内"用户+Agent"绑定不变——换负责人不修改现有沙箱，而是**销毁旧沙箱冷启动新沙箱并禁止从旧快照恢复**；整套绑定实现为一台状态机（提案→激活→分离→重授权→吊销，三者一致才就绪，可撤可续可追溯）。

## 效能度量：两把尺子 + 一个参考信号

传统指标（代码采纳率、使用覆盖率）已处高位，继续涨也难说明 AI 在真实需求中承接到了哪一步——它们回答"有没有使用"，不能区分一次提示词生成、一次研发闭环、一条需求的完整交付；单按耗时统计也失真（任务并行、等待与阻塞可能在链路之外）。因此用两把尺子：**需求分层 C1–C4**（复杂度，按核心中台影响/产品形态/跨团队范围等**七个维度**综合、**就高原则**）× **AI 交付深度 L1–L4**（提示词驱动→研发闭环→测试闭环→全流程交付），交叉为主视图（每格"需求数+平均介入次数"）；并列 **人工介入次数**（首轮发起后人补充/澄清/追问/纠偏的轮次），按**协作层**（主 Agent 群内讨论澄清评审）与**交付层**（编码子 Agent 会话内的补充纠偏）分账。**该数据只用于观测归因、不追求越低越好**——必要追问本就是交付的一部分，把轮次当目标只会诱导延后反馈或合并消息；它与自主交付率不同口径：计划内判断记为参与轮次但不判"非自主"，只有异常纠正/驳回/流程重启才影响自主交付。

**落地数据（截至 7 月底）**：所有业务线接入，需求池百余条、覆盖 **20+ 业务域**，近 30 天新建需求群与活跃会话均超 100。**首批十余个试点需求逐条复核**（样本不足以证明整体提效）：多数记录集中在协作层（单条十到几十轮，含计划内协作）；交付层多数几轮到二十轮，**已完成编码的需求平均约七轮**，较早稳定运行的域已降到**约一轮**；该批**全链路约三十轮、纠错返工约占两成**。优化重点已从"能否生成代码"转向"能否减少协作中的反复确认与信息补充"。**介入归因**：每轮介入标六类（催进度/解决卡点/拍板确认/提出需求/纠错返工/补充上下文）+ 两类风险信号（上下文缺失、理解偏差）→ 生成**预授权/Prompt/Skill 三类改进建议**，人工确认后沉淀为域资产——介入次数因此成为下一轮系统优化的输入。

## 边界与判断

更容易端到端跑通的仍是**接口与基础能力已具备、以组装为主的需求**；复杂领域改造仍需人在需求判断、方案选择、风险确认处介入。作者的反直觉判断：**数字员工不会自动修复不清晰的 PRD、依赖默契的分工和缺少沉淀的业务知识，反而会把这些更早暴露**（输入不足无法继续、责任不清无法路由、门禁缺失无法判断能否前进）——建设过程本身就是在把研发体系里依赖人兜底的部分逐项显式化。真正可能带来数量级变化的，不是某次编码更快，而是**同样的人类注意力可以支撑更多并行交付**。

## 深度分析

### 四层拆分的动机：每层只收敛一种不确定性

消息路由、沙箱、Agent、身份四层不是技术堆叠，而是把不确定性分层收口：网关只做回执去重、附件转存、路由组装三件确定性的事，把"这条消息该干什么"整体让给持有状态的主 Agent，避免进度同时存在于管道与业务两侧。沙箱层用一需求一箱隔开环境漂移；Agent 层用"通用性归执行端、可控性归调度端"拆开模型能力与调度控制；身份层再把权限判断移出模型。共同原则是越靠近入口越薄，判断集中在唯一持有上下文的那层。同会话不换引擎、事件映射统一、模型请求必须过网关否则拒绝启动，就是这条原则的硬约束形态。

### 自主交付率：为什么要把"人在环内"单独算清

采纳率类指标到达高位后便失去分辨力，分不清一次提示词生成与一条需求的完整交付，可参照 [天猫 AI Coding 的采纳率实践](https://github.com/QianJinGuo/wiki-public/blob/main/entities/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md)。自主交付率把方案判断、权限授权、评审确认、最终验收划为计划内人类节点，只有异常纠正、驳回与流程重启才计入中断；它与人工介入次数是两套口径，后者按协作层与交付层分账、只作归因输入不追求越低越好。两者并用，才能避开"少问几句"的伪优化并定位真实返工来源——试点全链路约三十轮、纠错返工约两成，正需要这种口径才看得见。

### 共享一个 Agent 与每人一套：组织含义在责任而非工具

按岗位拆出数字 PM／前端／后端／测试再加编排器，能提高单任务专业化与并行度，但需求上下文会在交接处被切断，澄清得到的信息不会自然流入下游执行，最终没有一方对全链路负责。共享同一身份与同一份需求上下文，是把收口、术语对齐、执行进展与产物重新放回同一现场，代价是单入口的并发与上下文压力，需靠一需求一沙箱与按域子 Agent 消化。组织上的真实变化是责任从个人技能迁移到流程与门禁，团队共同维护一个执行单元——这正是 [协作成为新瓶颈](https://github.com/QianJinGuo/wiki-public/blob/main/entities/agent-productivity-paradox-collaboration-bottleneck.md) 所描述瓶颈的正面处理。

### 身份委托与跨群隔离：边界由工程而非提示词保证

身份按动作拆成发送人、服务身份、署名、群负责人委托四类；要害不是分几类，而是模型不能指定任意一个人：身份化调用只接受受控角色，角色到真实身份的映射由可信环境注入，模型即便生成"以某某身份查询"也不被接受；受控资源还需本人登录确认，授权只证明委托关系、不扩权。沙箱生命周期内"用户＋Agent"绑定不可变、换负责人只能销毁旧箱冷启动并禁止快照恢复，是把边界写进状态机而非文档。跨群隔离同理：一个路由身份一个沙箱、群会话 ID 派生群身份，隔离性由路由映射保证，与 [沙箱基础架构](https://github.com/QianJinGuo/wiki-public/blob/main/entities/我们如何构建安全可扩展的智能体沙箱基础架构.md) 的多租户思路同源，也呼应 [把对象、状态与权限接进执行流程](https://github.com/QianJinGuo/wiki-public/blob/main/entities/一文讲清-agent-如何理解业务把对象状态和权限接进执行流程.md) 的授权注入主张。

### 与既有路线的差异：组合才成立，代价是每块都显得过重

岗位级数字员工把 Agent 做成某个职能的证据化替身，平台级多智能体编排解决如何组织一批 Agent，本篇则把它做成团队共享的执行单元，在自建团队内以主子 Agent、沙箱与身份落地。作者也承认，单看消息路由、长期状态、独立沙箱、身份权限，每项都像过度设计，只有组合才定义出新的组织执行单元。代价因此可预期：门槛高、组件耦合紧，更易跑通的是接口齐备、以组装为主的需求；对照 [快手电商的 AI 流水线 Harness](https://github.com/QianJinGuo/wiki-public/blob/main/entities/kuaishou-harness-engineering-ecommerce-delivery-pipeline-2026.md) 这类以流水线固化为主的方案，本路线把柔性放在调度端、把确定性放在门禁端，适应性要用更高的工程质量来支付。

## 实践启示

1. **先定口径，再上系统**：计划内的人类判断与异常返工分开统计，自主交付率只对后者扣分，否则团队只会学会少提问。

2. **网关做薄**：只做立即回执、原子认领去重、附件转存与路由组装；让管道层顺手判断业务，状态就分裂到两侧。

3. **沙箱是隔离与审计的最小单位**：一需求一箱、一身份一箱；镜像只装基础环境、运行时代码启动时拉取，才能不重建镜像地升级。

4. **身份化调用只允许受控角色**：映射由可信环境注入，模型无权提名身份；高权限资源需本人确认且不扩权，换负责人即销毁旧箱并禁止快照恢复。

5. **稳定环节设门禁，差异环节靠动态规划**：编码执行端可插拔、不重造引擎；模型请求必须统一过网关，未配置则拒绝启动。

6. **介入次数是优化输入，不是考核目标**：标注介入类型与风险信号，产出预授权、Prompt、Skill 三类改进并按域沉淀。
