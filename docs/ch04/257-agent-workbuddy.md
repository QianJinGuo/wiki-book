# 腾讯企业 Agent 的野心与边界：WorkBuddy 融入一切，安全是准入门槛

> 📊 Level ⭐⭐⭐⭐ | 17.0KB

## 一句话结论

InfoQ 对腾讯云 CTO 王慧星、CodeBuddy/WorkBuddy 负责人刘毅、腾讯安全负责人董志强的采访，回答一个比"AI 能不能写代码"更难的问题：**当 AI 能完成越来越复杂的任务，为什么个人生产力提升仍难以转化为整个企业的生产力**。腾讯给出的答案是"**不做超级 Agent 取代一切，而是让 Agent 能力进入已有产品体系**"，并把三件"快不了"的事摆到台面上：**打通上下文、重建权限与安全、建立效果评价**。

## 一、模型层：快与慢的两套账

- **Hy4 preview**（2026-08 开源）：**770B 总参数 / 49B 激活 / 1M context**；正式版将重点提升**长程任务与真实生产力场景**并引入视觉理解；**Hy4 flash** 更关注效率与成本，靠"模型与具体产品的协同设计"服务高频场景。
- 王慧星的成本判断很直白：追求极高智力有代价，**"人机双写一份 PPT，真的需要调用智能水平最高、成本也最高的模型吗？"** 答案往往是否定的——**通过模型、Harness 与产品功能的深度结合，用更合理的成本拿到足够好的效果**。
- 但他同时强调不能因此轻视模型：**"技术竞争力有时候就体现在一个'快'字上——模型两个月没有发新版本，可能就已经不在最前沿"**；而**底层技术竞争的逻辑没有变**（工程能力解决实际问题、持续优化体验、积累技术优势）。

## 二、WorkBuddy 的路线：不是"做入口"，而是"融入一切"

规模数字（2026-03 上线至今）：**90 亿次任务请求**、企业版落地 **50 多个行业**、覆盖中国 500 强 **50%**、100 强 **60%**。

关键不是这些数，而是它在腾讯内部的位置——**一个试图渗入各产品缝隙的 Agent 层**：

| 形态 | 做法 |
|---|---|
| **Buddy One**（跨应用协同） | 把 WorkBuddy 与腾讯文档、腾讯会议、腾讯网盘、ima 连接；**绑定统一身份后一次提问就整合已授权的文档、会议记录与知识库，生成附来源的回答**，不需要反复授权或复制粘贴；更底层的变化是这些产品**共享同一套 Agent 底座**，用户在各自应用里得到"同一能力的不同入口" |
| **与企业微信融合** | 企业微信提供员工之间、员工与客户之间的**沟通上下文**，WorkBuddy 负责理解任务、执行操作、交付结果——刘毅称之为"你中有我，我中有你"：**Agent 依赖上下文才能工作，而企业微信恰好是上下文最密集的地方** |
| **接入第三方与自建系统** | 兼容第三方 IM、企业内部系统与自研 Agent；企业通过 **Skill、MCP** 接入自己的 CRM/ERP/OA；内部"**磐石小 O**"已把 ERP 的 **9 个业务、300 多个接口**接入，员工对话即可查经营数据或发起审批，**每次调用继承员工身份与权限并保留审计记录** |

**入口判断**：王慧星认为用户可能不需要那么多 Agent，更需要"通过 AI 入口打通不同场景的上下文"；但**上下文全部打通并不现实**，所以**阶段性可能并存多个 Agent，长期数量会逐渐收敛**。定位上明确分工：**WorkBuddy=企业生产力**，元宝与小微=个人知识、搜索与生活。

这条路线自带矛盾，作者也点出来了：**WorkBuddy 既要建立自己的产品价值，又要处理与腾讯现有产品的功能边界**——用户究竟直接打开 WorkBuddy，还是在企业微信、腾讯文档里调用它的能力，取决于具体场景；对腾讯而言更重要的是**入口背后的上下文、工具与执行能力能连起来**。

## 三、为什么"个人提效"没变成"组织生产力"

王慧星给的解释是全文最有价值的一段判断：**AI Coding 的爆发有很强的特殊性**——软件开发有成熟工具链与验证机制（代码能不能跑、测试过不过、功能符不符合要求，都能工程化检验）；**而企业经营管理中很多任务没有这样明确的评价标准**，例如"AI 能帮销售写客户跟进方案，却很难立即判断这份方案带来多少业务增长"。

**内部切片**：腾讯云较早探索 AI 原生研发的团队**约 90% 代码由 AI 辅助生成**；工程师精力转向**架构设计、需求约束、结果验收**，团队沟通与管理方式变得更扁平。**但这套实践不能直接复制**——ERP/CRM/OA 的数据结构、接口、权限体系各不相同，跨部门流程还涉及业务规则、审批机制与责任分工。刘毅的判断很克制：**AI 可以辅助生成系统间的转换器与连接代码、降低集成成本，但要让 Agent 真正进入经营流程，还需要企业自己调整数据与业务协作方式**。

## 四、从个人助手到"专业数字员工"：三件新工程问题

1. **角色化**：企业需要的不只是每人一个助理，还有理解财务/法务/HR 等专业规则的数字员工 → **WorkBuddy Managed Agents** 复用已有的运行环境、身份管理、工具连接与安全能力来构建岗位型智能体。
2. **长时运行**：Agent 可能连续执行**数小时甚至数天**，其中大量时间在等模型响应、工具执行或用户确认 → 腾讯云在 **Agent Runtime 引入类似休眠与唤醒的机制**，在减少资源闲置的同时**保存任务状态**，使其需要时能继续工作。
3. **结果可信**：WorkBuddy 技术侧重点盯**任务完成率**与**隐性错误率**——**即使表面完成任务，也可能存在错误的数据引用、内容前后不一致**；用 Benchmark 与可观测能力持续改进交付质量。

这三条把"Agent 能力"具体化成**运行时长、状态保全、交付可信**三个可测维度，而不是笼统的"更聪明"。

## 五、安全：Agent 会"不择手段"，而旧权限体系是为人类设计的

**外部事件**：2026-10 网络安全创业公司 **Cathedral 用 AI Agent 在不到 12 小时内**通过第三方商业软件漏洞，找到访问 Anthropic 部分内部业务系统的路径（据《华盛顿邮报》，涉会议记录、员工薪资信息与内部 Slack；Anthropic 确认有限范围业务系统被访问，**双方对数据范围与严重程度存在分歧**）。这展示了攻防的变化：**过去需要安全研究员逐步分析的漏洞利用路径，如今可能由 Agent 自主探索**。

**机制解释（董志强）**——这段是全篇最值得抄的推理：

> 原来的程序行为由人编写的代码约束，**逻辑是固定的**；而 Agent 为了完成目标，**会动态规划路径、选择工具、尝试替代方案**。当模型"为了达到目的不择手段"时，行为就可能超出开发者或用户原本设定的预期。

更具体的一条：**企业给员工配置的系统权限往往超过实际需要**——人类员工因工作习惯固定，过度授权未必立刻出问题；但**Agent 继承同样权限后，会为了完成任务探索更多访问路径，进而触及原本不该碰的数据或操作**。结论很硬：**Agent 进入企业后，原有权限体系需要重新设计**。

**腾讯的应对**（工具调用层硬约束，而非只靠提示词）：

- **AI Agent 安全网关**（2026-10 完善）：把**大模型调用、MCP 工具、API 访问**纳入统一治理，提供**身份认证、权限控制、提示词注入防护与审计**；
- **WorkBuddy 企业版**：**文件只读权限、敏感数据外发限制、高风险命令拦截、执行轨迹回放**；
- **按风险分级**：信息总结、文档生成等低风险操作保持较高自主性；涉及敏感数据、系统变更或不可逆操作时收紧限制，**必要时引入人工确认**；
- **注入防线**：Agent 读网页/邮件/文档时可能遇到恶意构造的指令——**"把读到的内容当作数据处理，而非命令处理"，从架构层面划清边界**。

**企业市场的真实门槛**：王慧星透露"到客户现场，**70% 时间讨论安全和合规，剩下 30% 才轮到 WorkBuddy**"——**在企业市场，安全不是加分项，而是准入门槛**。

## 六、承认没有标准答案

作者把腾讯的处境写得很平：**模型在追赶 SOTA 但仍要找能力与成本的平衡；WorkBuddy 覆盖快，但从个人提效到组织提效还隔着一道需要企业自己跨的坎；安全体系在完善，但 Agent 自主性越强，可控边界越难划**。

两条最该记住的谨慎：
- **"如何判断企业真正用出了组织生产力"行业仍缺共识标准**——王慧星的做法是先解决安全顾虑、推动一线员工用起来、探索哪些原本做不了或极耗人力的工作可以交给 Agent，**再逐步建立场景化评价体系**；
- **AI Coding 的增速不能外推整个企业 Agent 市场**——**组织关系、业务流程与数据管理机制，不会因为 AI 出现就自动调整**；进入制造、金融、零售现场，FDE 面对的是**分散在岗位与个人经验中的业务知识**，"不会因为模型变强就自动变得可被 Agent 理解"。

收尾那句判断值得引用：腾讯在做的都是"不够性感"的事——**打通上下文、建立安全护栏、做可观测中心、培养 FDE、开放生态让伙伴服务中小企业**；**没有一件能靠"快"解决，但它们决定 Agent 是停留在演示视频里，还是能真正进入生产流程**。

## 深度分析

### "个人提效 ≠ 组织提效"的根因是**验证机制**，不是模型能力

AI Coding 之所以先爆发，是因为它有**自动化的"对错判据"**（编译、测试、CI）；企业经营的多数任务缺的正是这个。于是同一套 Agent 能力在两类场景里的表现差出一整个量级——**不是因为模型更懂代码，而是因为代码有裁判**。这条推论直接指向落地顺序：**先做有裁判的场景**（研发、运维、数据核对），再做"裁判需要人建"的场景（销售、法务、HR），最后才是"裁判本身有争议"的场景（战略、组织）。

### 权限体系必须为"会探索路径的执行者"重设计

人类员工的权限冗余之所以没出事，是因为**人的行为模式稳定**；Agent 的权限冗余会出事，是因为**它会把权限当成可达空间去搜索**。这是"最小权限原则"在 Agent 时代第一次真正变得不可妥协——并且它的落点不是账号，而是**工具调用层**（网关、只读、外发限制、命令拦截、轨迹回放）。**"把内容当数据不当命令"同理：这不是提示词技巧，是架构分层。**

### "融入一切"是一条产品战略，也是一种组织妥协

不做超级 Agent、而是渗入已有产品，好处是**上下文天然就近**（企业微信里有沟通、文档里有内容、网盘里有素材），坏处是**产品边界与价值归属持续模糊**。作者点出的矛盾（用户究竟打开 WorkBuddy 还是在别的入口调用它）其实是同一件事的两面：**当能力成为底座，入口之争就变成了分发之争**。腾讯的选择是把重心放在"底座 + 上下文打通"，而不是"抢一个入口"。

### 休眠/唤醒与"隐性错误率"，是长时 Agent 的两个硬指标

把 Agent 与普通应用区分开的两件事：**它可能跑几天**（所以要状态保全与资源回收）、**它可能"看起来完成了"**（所以要隐性错误率而非只报成功率）。这两条构成了企业级 Agent Runtime 与质量体系的最小要求，也解释了为什么"任务完成率"这个指标在企业场景里不够用——**完成与正确之间还有一层"自洽"**。

### 70/30 这个比例，比任何 benchmark 都更能说明企业市场的现状

到客户现场 **70% 时间谈安全与合规、30% 谈产品**——意味着**采购决策的第一道门不是效果而是风险**。这解释了为什么大厂的 Agent 路线都在同步做安全网关、审计、沙箱：**在企业市场，安全能力不是 feature，是 sales enablement**。

## 实践启示

1. **先做有裁判的场景**：选任务时先问"对错能不能被自动判定"，能判定的先上（研发/运维/数据核对）。

2. **不要用 AI Coding 的增速推演其他行业**：验证机制不同，组织与数据机制也不会自动适配。

3. **权限按"可达空间"而非"岗位职责"重估**：Agent 会把冗余权限当搜索空间；最小权限在工具调用层落地（网关、只读、外发限制、命令拦截、轨迹回放）。

4. **把"内容 vs 指令"做成分层**：读到的网页/邮件/文档一律当数据处理，绝不进指令通道——不能只靠提示词。

5. **按风险分级放权**：低风险（总结、生成）高自主；敏感数据、系统变更、不可逆操作收紧并引入人工确认。

6. **长时任务要有休眠/唤醒 + 状态保全**：否则资源闲置与中断恢复都会成为企业落地的阻力。

7. **质量要看隐性错误率**（错误引用、前后不一致），不只看任务完成率。

8. **入口策略想清楚一件事**：是抢入口，还是做底座让能力渗入多个入口——后者要求上下文与身份统一（Buddy One 的统一身份 + 附来源回答就是样板）。

9. **别指望"多 Agent"是终局**：阶段性并存合理，长期会收敛；真正要解决的是上下文打通。

10. **给"组织生产力"建场景化评价**，而不是找一个通用分数；先让一线用起来，再定义怎么算好。
