# AI Native 团队协同：知识底座＋Agent＋人三层闭环

> 📊 Level ⭐⭐⭐⭐ | 27.1KB

## 摘要

天猫技术团队（书牧）从"单点提效遍地、全局增量不见"的困境出发，提出 AI 提效的真正瓶颈是**协同**而非单点产能，核心论断是：AI 时代生产侧的**串联者从人换成 Agent**——这是"AI Native"与"AI 辅助"的分水岭。在此基础上给出 AI Native 团队的理想形态：以完整业务单元为边界的"知识底座＋Agent＋人"三层闭环，并论证**软件是被固化的知识**（TBox/ABox 本体论视角），实现该形态的关键瓶颈不是协同工具（方向已清楚）而是**存量业务的知识底座**（构建方法难、知识在人脑、底座自治存活三坎）。

## 核心框架

### 消费侧 vs 生产侧二分

一切生产活动最终满足人的需求，而原始需求本质稳定（马斯洛需求不变），变的是满足方式。据此把业务切成两类：

- **消费侧**（直面人的需求）：演进本质是交互方式升级（报纸→门户→信息流→AR/脑机接口），未来朝"个人助理"（贾维斯式）方向走，接管"最后一公里"需求，高度个性化；终端永远是人，"以人为本"不被技术动摇。
- **生产侧**（B 端，组织与串联生产）：没有"终端是人"的锚，完全是当下技术水平的产物——有什么技术就长出什么流程分工系统，技术每升级一轮就被重写一次（手工作坊→流水线→ERP/OA→互联网化/移动化）。

### 串联者转换：AI Native 的分水岭

过去几十年生产侧软件的隐含设计前提是**"人是串联者"**：表单让人填、看板让人看、审批流让人点，流程本质是一连串由人完成的传递、判断和衔接（人靠"泛化性+容错性"天生适合串联）。AI 时代最大的变化是**串联者从人换成 Agent**：

- **AI 辅助**：流程骨架不动，串联者还是人，只是某个环节加挂 AI 功能（在旧流程上加挂能力）。
- **AI Native**：把串联者整个换掉，由 Agent 承担传递、判断和衔接，并围绕"Agent 是串联者"这个新前提重建流程本身。

推论：会消亡的不是"软件"这个笼统概念，而是那些把"人是串联者"当设计前提的软件——表单、报表、审批流，以及大量"等人来操作下一步"的内部系统环节。生产侧形态注定被重构（不是在旧骨架修补，而是围绕新串联者重新长一遍）。

### 三层闭环：知识底座＋Agent＋人

以完整业务单元为边界的理想形态：

- **底层：统一知识底座**——沉淀业务规则、业务流程、领域知识和规范约束（"这个业务究竟怎么运转"本身）。
- **中层：各司其职的 Agent 群**——运营/产品/研发 coding/测试/运维/客服等，都从知识底座取知识，承接并串联自己环节的工作；还需依赖工具和技能（查数据/调系统/跑流程/触发变更）。知识底座决定"知道什么、该怎么做"，工具技能决定"能做到什么"。**拆分为多 Agent 而非大而全**：不同 Agent 感知知识范围、服务范围、权限和安全要求不同，拆分后上下文相互隔离，评测和优化可独立迭代（运维 Agent 感知代码层知识+调用 normandy/sunfire/arthas；内部答疑 Agent 可回复代码级错误定位；外部客服 Agent 要专业话术）。
- **顶层：人**——不再是流程里逐个传递信息的"接力棒选手"，而是与 Agent 群围绕同一业务目标协同：定方向、做判断、处理例外、把新知识沉淀回底座。角色边界会变模糊（全栈融合目前主要发生在执行层如写代码），但专业深度决定面对 AI 产出时能做哪一层的专业决策——判断 AI 给的复杂工程/架构方案靠不靠谱的能力将更稀缺，非"全栈"可覆盖。

闭环运转示例：业务需求由业务/PD 借助业务/产品 Agent 基于知识底座产出 MRD/PRD → 研发 Agent 定位领域/应用/规则拆解技术方案 → 人在协作空间（项目群）与 AI 协同、关键节点确认判断 → 编码/测试/发布由 Agent 串联执行 → 新决策与知识回流底座；监控报警触发运维 Agent 自动排查定位、止血操作由人决策；答疑 Agent 基于知识底座自动回答、不确定时群里 at 成员确认（Qteam 的 Q仔实践）；用户 bug 自动记录 Aone 缺陷并触发研发 Agent 自主修复；运营 Agent 产出业务状况报告供老板决策。

### 软件是被固化的知识（TBox/ABox 视角）

知识底座包含两类内容，对应本体论的经典区分：

- **TBox（类型层定义）**：业务规则（"是什么、要遵守什么"的陈述性知识）+ 业务流程（"按什么次序做"的程序性知识）——都是知识。
- **ABox（事实层）**：运转中产生的一笔笔订单、商家、用户等具体事实。完整知识底座须同时含 TBox 和 ABox。

软件在此模型里不是必需品——抽象地看，业务完全可以由 Agent 直接在知识底座上运转。软件之所以需要，是因为 Agent 动态运转在某些地方不够用（交互体验/确定性/性能/成本/安全/合规审计），于是把一部分业务规则和流程"固化"成产品规则和产品流程，落到软件研发流程（含 AI Coding）。**软件是被固化的知识**；"把知识固化成软件"本身又是条业务流程（研发流程），同样可由 Code Agent 在知识底座上完成——**AI Coding 本质就是这个固化动作**。生产侧被重构但不会被清空：确定性逻辑以产品规则/流程形态固化在软件层，源头始终是知识底座。未来"沉淀"动作本身也变：过去交付一套软件，往后交付更多是"知识"（含 Skill）；过去集成交付端到端软件系统，往后更多是给 Agent 交付一件件工具。

### 两件事：知识底座是瓶颈，协同工具是基建

- **协同工具**（长期看不是瓶颈但很重要）：通用基础能力，理论上跨团队协同需无缝，不适合各业务重复造，但当下基础团队无完整方案。已有探索：Aone 团队的 Devix、Qteam 团队的 Qoder 系列、企业智能的数字员工账号、ideawork 等，均不完善属探索阶段。已见关键概念雏形：**业务空间**（划定业务闭环边界的核心容器，Devix 产品空间类似）/ **参与者**（人类成员+各类 Agent，关联技能和知识）/ **任务**（项目/需求/话题）/ **频道**（人与 Agent 协同入口，IM/Web/通用助手；传统入口在钉钉，未来也许在通用助手）/ **产物**（协同沉淀结果）/ **知识底座**（每个业务空间管理的知识+数据，是业务护城河）。**批评**：企业级业务的复杂度和瓶颈往往不在写代码一段（拿半托管超链跨团队项目为例，商业逻辑/方案取舍在多个角色间讨论清楚极其耗时）；别被"Coding 变快了"的幻觉带偏（简单需求全自动交付对全局提升有限；研发为"完美写代码"反过来要求 PD 更完整 PRD 反而把产品设计与研发割裂，协同成本一点没省）；协同工具不该只停在研发流程（AI Coding），应往更左侧的需求侧、业务侧走。
- **知识底座**（真正长期卡住全局的瓶颈）：不通用、不可复制，每块业务都得自己长出一套，做得越久的传统业务越难。

### 存量业务知识底座三坎

新业务/新团队（白纸）可从第一天按"知识底座＋Agent＋人"组织，不用还历史债；真正的硬骨头是存量业务：

1. **构建过程和方法难**：系统架构是历史一块块长出来的（边界/耦合/字段含义留痕迹）；在划定范围里把知识底座扎扎实实构建出来——抛开历史包袱重新讲清"业务到底怎么运转"——是最难也最有价值的部分，结果理论上应反过来指导组织和架构长成什么样。
2. **大量知识在系统之外、在人脑里**：最关键的规则、"为什么当年这么定"的来龙去脉、只有老人才清楚的例外大多是隐性的。原则：尽量把每条知识锚定到权威事实来源，能从代码/配置/数据自动生成和校验的绝不靠人肉维护；越靠人脑那端的越要专门设计沉淀机制外化；能不能自治取决于知识离权威来源有多近。
3. **底座必须能"自己活下去"**：业务天天变，靠人肉更新维护很快烂掉/过期/没人信；须靠自动化+人工确认保鲜（自治能力），而非架构师责任心硬扛。本体论提供了描述"规则/流程/数据及其关系"的语言，但落地难点仍是在具体存量业务里建起来并持续转下去。

**边界问题**：知识底座以多大范围为单位建/闭环？划太大规则流程千头万绪难收敛，建到一半陷在复杂度；划太小凑不成完整闭环，Agent 一串联频繁跨边界又退回"靠人对接"。边界还关乎组织结构（需求依赖商品详情/交易等平台团队就没法只从"我这个业务"视角闭环）。作者认为两年前架构组讨论的业务大图/产品树等概念与知识底座本质是一回事，AI 背景下更有必要性和可行性。

### 为什么现在绕不开

"把一个业务彻底讲清楚、让它可被复用"一直很难，过去因串联者是人而被"扛"过去（知识不全/流程不清/文档过期靠人补位、对接、救火，问题被掩盖）。AI 时代串联者换成 Agent，遮羞布被揭开——Agent 没法像人那样靠经验和默契补位，只能在知识底座上运转，底座有多清楚它就能跑多远。"建知识底座"从可一直拖着的事变成绕不开的必选项；迈不过这道坎的大公司迟早被没有历史包袱的创业公司（白纸优势，存量之难不用还）用"知识底座＋Agent"跑出数倍效能甩在身后。

## 下篇：那个「协同工具」长什么样——数字员工（2026-11-09 补充）

上篇讲完「为什么」就停在这里：串联者从人换成 Agent 之后，把「人、Agent、知识底座三者协同」的工具具体长什么样，没有回答。下篇给的答案是**数字员工**——而且它用「协同层 / 执行层」的二分把这个角色钉死了。

**两层解的不是同一件事**：协同层解决「人与人、人与 AI 之间如何对齐目标与上下文」——把隐式的、线上线下的上下文搬上来，确定目标，再串联任务；**「目标」是执行层 Harness 的前提条件**。执行层解决「AI 如何自主把一件事干完」，其目标是通过 Harness 不断降低人工介入率。这个区分解释了一个现象：现有数字员工方案大多只做执行层——按开发/测试/产品/TeamLeader 拆角色，让员工继续和各角色打交道，甚至开始讨论对这些角色做绩效考核；那些其实只是「流水线上的执行工位」，缺的是把工位串起来的那条流水线。执行层已相对成熟、当下的命题是**收敛与统一**（让 Harness 工作流、技能、知识库在组织内复用产生复利）；真正稀缺的是协同层。

**命名上的较真（本篇最锋利的一刀）**：只有「协同者」角色才配叫数字员工——背后干活的执行角色叫 Agent 就行，它们**不必各自拥有记忆，按需动态创建、任务完成即可销毁**；把执行角色贴传统职能标签并非关键。另一组必须分开的是**数字分身 ≠ 数字员工**：分身面向个人、是个人助理，代替个人一部分工作、仍活在现有流水线里，沉淀的是**个人效率，人走了东西也跟着走**；数字员工面向业务单元、是 toB 的，沉淀的是**组织资产，越用越厚，不随个人流动流失**。这一条直接决定了「沉淀归谁」，也决定了它是让个人更快，还是让组织重构。

**它的原型是一个业务单元维度、随时在线的 PM**：拉群、把对的人拉进来、追问澄清、盯着目标往前推、到点催办、把风险和卡点主动亮出来，再把诉求、决策和经验一路记录沉淀；最核心的两件事是**拉齐上下文**和**派活**。与执行层的关键差别在「关注点落在感知侧而不是执行侧」——工具是被动的，你不用它就待在那儿；PM 是主动的，会追着目标、追着人、追着卡点往前走。执行层追求「把交代的活干好」，协同层追求「没人交代也知道该往哪儿推」。

**感知的三个入口，构成一条同步→异步的轴**：①**IM 群**（钉钉群）是当下最合适的入口——群本来就是人协作的入口，数字员工驻在群里，讨论和文档都能「听」到「收」到（类似 Claude 基于 Slack 的思路）；②**围绕工作项的协作板**（Aone 的 CoCo，可参考开源的 Multica），靠评论与 @ 对齐；③**会议**——应对复杂场景最绕不开，却最难搬进共享空间：现在只能靠钉钉 AI 听记事后补纪要，而听记缺上下文，纪要常不尽如人意；理想形态是数字员工像在场员工一样参会、可被 cue、也能主动发问、全双工实时沟通（类似 AI 访谈的虚拟主持人），这也是钉钉 AI 听记可演进的方向。三者的协同强度与留痕特性不同：会议最即时、适合高频对齐的复杂场景，群居中，协作板最异步、最能留痕慢推。还有一条边界：**协同层与执行层的入口不必也不该相同**（Coding 的细粒度进展与代码变更塞进群聊是别扭的），但两者背后要共享同一个上下文空间。

**承载平台五条标准**：轻量（基于一个业务单元就能快速创建一个）、拎包入住（自带「串联角色」的内置能力，开箱即用而非从零搭）、可自定义（在开箱基础上做差异化）、与执行层无缝衔接（数字员工费劲感知并拉齐的上下文，不能在交接给执行 Agent 时摩擦掉）、跑在云端（随时在线、面向业务单元，而不是依附某人的电脑、人一关机就没了）。作者对现状的批评很具体：一些平台自定义足够灵活，但申请与使用有门槛、不同数字员工之间缺少可复用模板——**既不容易拎包入住，也不好沉淀复用**。

**组织形态：业务单元 → 协同层 → 执行层**。数字员工不该做成大而全的全能实例——要真正懂一块业务、把上下文维持在能驾驭的范围内，就必须框定在一个相对聚焦的边界里（业务单元）；上下文铺太宽既抓不住重点，也沉淀不出可复用的东西。层次之下是「主题 → 多个协作入口（群/私聊/会议）→ 多个工作项 → 多条工作流」的嵌套：以「天猫国补」为例，业务单元绑定一批成员、一套业务知识、一组常用技能；主题是「国补交易表达」这类要持续推进的事；一个主题拉起多个群与私聊；主题下的具体需求走对应工作流（研发交付 / 工单处理 / 取数）。**两层沉淀的东西不同**：协同层沉的是这块业务的上下文、知识和对齐后的目标，执行层沉的是把活干完的 SOP——所以研发、数据、运营的 AI Native 差异全在执行层，对协同层的诉求是一致的。

**两个明确留白**：①**身份与权限**——数字员工要替人调工具、改代码、跑部署、提 CR，它该拥有独立身份与权限，还是继承委托人权限？群协同场景下如何切分？这牵涉安全、审计与责任边界；②**业务单元的边界怎么划**，上篇提过是另一个重要而困难的话题。作者还给了冷启动的现实判断：短期内在多数组织里感受不到价值，因为「厂房还没有改造好」；而且个人把数字分身打磨得很好时会有很强的「爽感」，但**个人效率 ≠ 组织效率**，组织的瓶颈往往在人和人、段和段之间的协同上——那恰恰是分身够不到、数字员工要补的地方。收口一句：**短期的红利在执行层，长期的胜负手在协同层**。

**与实践篇的关系**：2026-10-23 的 [天猫数字员工实践篇](https://github.com/QianJinGuo/wiki-public/blob/main/entities/tmall-digital-employee-agent-harness-2026-10-23.md) 给的是这套概念落地后的工程形态（钉钉群为统一入口、四层系统、自主交付率定义、月均 100+ 需求交付）；本篇给的是**为什么必须是「一个」协同者而不是一组执行角色**的概念论证。两篇合起来才是完整的「为什么 + 长什么样 + 怎么建」。

## 深度分析

### 三层闭环与协同层/执行层：同一张蓝图的两半

上篇的三层闭环讲组织形态，下篇的协同层/执行层二分讲工具形态，两者是同一次重构的两个投影：协同层正是「串联者」干活的那层——对齐目标与上下文再串联任务，且目标是执行层 Harness 的前提；执行层对应中层的 Agent 群。关键是知识底座在两层的**分仓沉淀**：协同层沉上下文、知识与对齐后的目标，执行层沉把活干完的 SOP——按 TBox/ABox 视角，陈述性知识留在协同层，程序性知识固化为工作流落在执行层。研发/数据/运营的差异全在执行层，对协同层的诉求一致。

### 感知层是知识底座缺失的上游传动轴

上篇默认「新知识回流底座」自然发生，但 Agent 没法靠经验默契补位，底座多清楚就能跑多远；下篇补上这个前提的机制——「感知」：把散在群聊、协作板、会议里的线下隐性上下文搬进共享空间。三入口构成同步→异步的轴：会议最即时却最难搬进共享空间（听记补纪要缺上下文），IM 群居中，协作板最异步留痕。对读可推出：**感知入口本质是知识底座的采集管道**——三入口正是上篇「越靠人脑越要专门设计外化机制」的具体形态，会议是至今未打通的一段。

### 持久性成为 Agent 拆分的第三维度，「沉淀归谁」是组织级判据

上篇拆多 Agent 依据知识范围与权限；下篇补出第三维度——**记忆是否持久**：执行 Agent 不必有记忆，动态创建、完事即销毁，只有「协同者」才配叫数字员工。与数字分身的区分给出「沉淀归谁」的判据：分身面向个人、沉的是个人效率，人走了东西跟着走；数字员工面向业务单元、沉的是组织资产，越用越厚、不随人流失。个人效率 ≠ 组织效率，组织瓶颈在人和人、段和段的协同上，恰是分身够不到的地方。

### 冷启动悖论与「Coding 变快了」的幻觉互为表里

上篇批评别被「Coding 变快了」带偏：企业级业务瓶颈往往不在写代码一段，研发反过来要求更完整的 PRD 反而割裂产品与研发；知识底座的边界（太大难收敛、太小不成闭环）也指向组织结构。下篇解释体感为何集中在执行层：执行层已相对成熟、红利可见，协同层价值要等「厂房改造好」才显现。合起来是冷启动悖论：**最该补的那层，恰恰短期最难被感知、最难立项**——迈不过这道坎的大公司，迟早被白纸创业公司的「知识底座＋Agent」飞轮甩开。

## 实践启示

1. **评估「数字员工」方案先问：它是协同者，还是一组执行工位？** 按开发/测试/产品拆角色、让人继续和各角色打交道的只是流水线工位（工程形态可对照 [天猫数字员工实践篇](https://github.com/QianJinGuo/wiki-public/blob/main/entities/tmall-digital-employee-agent-harness-2026-10-23.md)）；真正缺的是把工位串起来的那条流水线。执行层当下的命题是收敛统一，让工作流、技能、知识库在组织内复用产生复利；度量协同层要用组织级指标（上下文拉齐耗时、跨段返工率），别把个人分身的爽感当组织提效。

2. **知识沉淀分两仓治理，锚定权威事实来源。** 能从代码、配置、数据自动生成和校验的绝不靠人肉维护；越靠人脑的隐性知识越要专门设计外化机制——感知入口即外化管道。选协同工具时把「能把线下上下文搬上来」当一等能力验收。

3. **协同平台按五条标准打分，重点盯两条。** 轻量、拎包入住、可自定义、与执行层无缝衔接、跑在云端；其中「拎包入住」与「上下文交接零摩擦」（拉齐的上下文不能在派活交接时摩擦掉）最易被现状欠账：有申请门槛、缺可复用模板。

4. **承认会议是协同层最大缺口，先做低成本补偿。** 复杂需求几乎绕不开会议对齐，但会议最难搬进共享空间，听记纪要缺上下文；理想形态落地前，先把留痕纪律当过渡机制：关键结论必须落到协作板。
