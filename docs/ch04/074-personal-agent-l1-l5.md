# Personal Agent 的主动性分层：目标−现状驱动，横轴 L1–L5 × 纵轴执行深度

> 📊 Level ⭐⭐⭐ | 15.0KB

## 核心命题：主动性不是功能，是三件事的组合效果

这一轮 Personal Agent（PA）产品讨论里出现最多的词是"更主动了"。作者的第一刀是把它拆开：**主动不是一项功能，而是「身份 + 数据源 + 记忆」三要素组合出来的外显效果**，缺一件就有一处失效——只有身份没有数据源，Agent 在场却无事可做；只有数据源没有记忆，推送什么都像群发通知；只有记忆没有身份，Agent 想到了也只能等你下次打开对话框。

**身份一旦独立，数据源的变化本身就是事件源。** 定时轮询是一种获取变化的方式，而 push、merge 这类事件在 DevOps 里本来就是 pipeline 的触发时机；Agent 有了自己的账号与权限，就能像流水线一样被它们唤醒。所以"什么时候该动"有两种时机来源（主动轮询 / 被动事件），而"该在什么事上主动"才是真正没被回答的问题。

## 本质：主动性来自「目标 − 现状」

回到最朴素的问题——人为什么会主动做一件事：心里有个目标，眼前状态与目标之间有差距，差距让人意识到"这里有个问题"，问题再被拆成任务。Agent 同理：**没有目标就没有差距，没有差距的主动只是在刷存在感。**

这个机制在任务级 Agent 上早已发生（给 goal、跑 loop、执行后对照 outcome 判断完成、缺什么补什么）。PA 并没有发明新机制，它做的是把任务级的 goal/outcome 在**时间维度**和**责任维度**上同时放大，于是有三件事随之改变：

1. **主动性从加分项变成刚需**：任务级 Agent 不主动也能交付，因为用户就在旁边随手推一下；长期目标下用户大部分时间不在场，Agent 不自己跟踪、不自己发现问题，目标就停在原地。主动性是被长期目标逼出来的。
2. **授权跟着子任务走，不跟着目标走**："把这个里程碑推到上线"不等于授权它替我给所有人发消息、也不等于授权它改线上配置——目标只说明方向，每个子任务风险不同，授权只能一个个给。
3. **周期越长越需要持续对齐目标**：一次任务里目标开头说清基本不变；几周的周期里优先级会变、上游决策会变、用户自己的想法也会变。Agent 拿着三周前的理解一路推进，就是"目标已经错位却还在用力推进"——作者称之为长期主动最危险的失败方式。

## 两根独立的轴：谁定义问题 × 做到哪一步

分层的标准不是"多聪明"，而是**这个问题是谁定义的**。横轴 L1–L5 按问题定义权划分：L1–L3 无论看起来多智能，问题都是用户定义的（L2 的时间规则、L3 的触发条件都是用户定的，Agent 只是挑时机执行）；**L3→L4 是质变**——用户只给目标，"现在缺什么、该补什么"由 Agent 自己算出来；L4 的前提是**差距必须可计算**（目标清晰、能量化或有可检查状态）；L5 则是 Agent 自己推断目标，而"L4 的目标如果说不清，就会实际上变成 L5"。

横轴只回答"问题从哪来"，不回答"Agent 能做到哪一步"。同样是 L4，"提醒你某个依赖没人认领"和"直接替你在群里认领"完全是两件事，所以需要第二根轴（做到哪一步：告知 / 建议 / 代执行 / 对外不可逆动作）。**两轴独立**：L5 的 Agent 可以只停在"告知"，L3 的 Agent 也可以直接对外执行——讨论 PA 能力时必须同时说清它在两根轴上的位置。

## 一个真实的 PA：Daisy 的 276 条 todo

作者自建了一个叫 Daisy 的 PA，有两个常驻 loop：每日收敛 loop（每晚 20:00 扫当天会话、钉钉群、关键私聊与文档，产出 todo 与"可能值得沉淀的话题"discover）和自动回复 loop（白名单群有人 @ 我时按规则先替我回复）。放到两根轴上：横向已到 L4/L5（todo 是对照工作目标算出的差距，discover 是它推断"我可能关心什么"），**纵向几乎都停在最底下两格**。

数据很诚实：**07-01 起每日 loop 共产出 276 条 todo，其中 138 条被标完成；这 138 条里有 126 条是 08-13 一次会话里集中手动核销的，loop 自己执行关闭的 0 条。** 它每天都在"发现问题"，从未"解决问题"，所有执行与收口最后都回到人身上。

**这不是谨慎，而是责任归属。** 同一个 PA 的自动回复 loop 直接在钉钉群里替作者回复同事——对外、不可逆、回出去收不回来，风险比关掉一条 todo 大得多，但作者放心交给它，因为**规则全是自己定的：问题是我定义的、边界是我画的、出了事责任在我**。而 todo 是 Agent 自己算出来的问题：它判断"这件事该做"，算错了、替我做错了，后果谁担？在没有答案之前，只让它停在"建议"。

## 升仓：同一件事从 L5 走到 L4

discover 一共扫出 80 多个话题，作者没有照清单直接入库，而是"觉得值得就接着聊，聊透了再让它整理进知识库"；剩下没处理的一部分是没时间，另一部分是担心自动生成内容质量不够。**换一个设定，结论就不同**：如果明确说"我要成为某个领域的专家"，同时给出清楚的入库规则——知识架构能挂到已有概念体系、来源扎实优先官方与一手资料、与库内已有结论冲突就标出来——那么在风险可控前提下，一部分入库可以交给 Agent 自己完成。

这一步里**Agent 的能力没有变，变的是人交给它的东西：一个可计算的目标，和一套可检查的验收规则**。作者把这称为"升仓"：从"猜我关心什么"，到"对照专家目标算差距"，再到"符合规则的直接入库"。

## 五档判定：问题谁定义 × 失败代价

一件事能不能交给 Agent 执行，与它在第几层关系不大，与个人谨不谨慎也关系不大，真正起作用的是两个问题：**问题是谁定义的**（决定出错时的责任归属）、**失败代价有多大**（拆成能否撤回、影响到谁、结果能否验证）。按这两个维度把待办分成五档：左下角（问题是我定的、做错代价小）最适合直接执行，越往右上越需要人在关键节点把关。

## 主动性的上限：L4 的责任不对称，L5 的目标猜错

L1–L3 的执行今天已能比较放心交出去（问题用户定义、边界用户画、Agent 按规则执行）。真正卡住的是 **L4 的执行和 L5 的一切**：L4 的问题是 Agent 算的，算对省事、算错后果仍由人担——**只要这个不对称存在，人就会本能地把 L4 留在"建议"**；长周期会让情况更糟，目标在几周里会漂，Agent 在用户不在场时拿着旧目标往前推，差距算得越认真偏得越远，所以 L4 想往上走还需要"在关键节点重新确认目标还是这个吗"的持续对齐机制。L5 则在 L4 风险上再叠一层误差：L4 是"目标对、差距算错"，L5 是"目标本身就猜错，后面的差距、问题、任务全跟着错"。作者援引媒体报道的 Meta Muse 系统指令要求推断用户"没有说出口"的目标（读取聊天、消息、邮件与已连接应用，引发隐私争议）说明：**推断未说出口的目标能力上做得到，但用户愿不愿意被这样理解是另一回事**，所以今天 L5 更适合停在"告知"。

## 杠杆只有一个：把目标和验收规则说清楚

回看所有例子，能让一件事往上走的只有一件事：**说清目标，Agent 就不用猜，L5 变成 L4；说清验收规则，"做没做对"就能被检查，L4 的一部分变成"按规则执行"，问题定义权与责任也重新回到用户手里。** 于是落点是一句相当克制的话：PA 的主动性能放大到什么程度，不只取决于 Agent 多聪明，也取决于人愿意把目标和规则说到多清楚；**主动性的上限，是人与 Agent 之间能显式对齐的那部分目标**。

## 深度分析

### 为什么"主动性"必须先拆成身份 + 事件源 + 记忆

这三件事对应三种不同的失败：没有身份就没有**触发资格**（不能像流水线一样被 push/merge 唤醒，只能靠人打开对话框）；没有事件源就没有**触发时机**（有身份但无事可做，退化成聊天机器人）；没有记忆就没有**跨会话的连续性**（推送无法与历史对齐，等价于群发通知）。把它们当功能清单会做出"更聪明的对话框"，当组合条件才会做出"在场的东西"。

### 为什么授权必须跟着子任务走

目标级授权在人类组织里也不成立：给你一个"把项目做完"的目标，不包含"替我给全员发消息"和"替我改生产配置"的授权。Agent 的风险面由**动作**决定而不是由**意图**决定，因此授权的最小粒度天然是子任务；这也是为什么本文的第二根轴（做到哪一步）必须与横轴独立——L5 的目标推断能力再强，也不能推导出对外动作的许可。

### 责任不对称是 L4 的天花板，而不是能力不足

Daisy 的数据把这件事量化了：276 条里 138 条"完成"，其中 126 条是人一次集中核销，自执行 0 条。**这不是 Agent 笨，而是"问题由它定义、后果由我承担"的结构使然**——同一个系统在自动回复上敢直接对外，是因为问题与边界都是人定的。换句话说，PA 的执行深度不是被模型能力卡住的，是被**责任分配**卡住的；要让 L4 往上走，工程上要补的不是更强的规划，而是"关键节点重新确认目标"的对齐机制与可检查的验收规则。

### 为什么"可计算的目标"是 L4 的入场券

L4 要求 Agent 自己算出差距，而差距要能被算，目标就必须可量化或有可检查状态。这条前提解释了升仓案例的全部差异：同样是"沉淀知识"，"猜我关心什么"不可计算，"对照专家目标 + 三条入库规则"可计算——后者让 Agent 的自主判断变成**规则内的执行**，问题定义权与责任一起回到人手里。反过来说，任何"让 Agent 更有主动性"的产品承诺，如果不能落成可计算目标 + 可检查验收，都只是在提高 L5 的猜测频率。

### 分层反过来定义产品基础设施

作者在最后把讨论从"Agent 多聪明"转到"PA 产品需要什么底座"：稳定的身份与记忆让目标跨会话持续，Channel 与 Schedule 提供事件与时机，云端执行环境让行动在用户离线时继续；**权限、确认与运行记录用来承接不同执行档位的风险**。这条推导值得单独记——分层不是评测标签，而是**功能需求表**：每往上一档，缺的都不是模型分数，而是身份、时机、执行环境与审计中的某一块。

## 实践启示

1. **先补三缺一**：身份（能否被事件唤醒）、数据源（有无可做的事）、记忆（能否跨会话对齐）——按缺失项定位"不主动"的真实原因。

2. **用两轴描述能力，别用一轴**：任何 PA 能力声明都写成"问题谁定义（L1–L5）+ 做到哪一步"，避免把"能推断目标"误当成"能替你执行"。

3. **授权按子任务发，不按目标发**：对外、不可逆、影响他人的动作单独要权，目标级授权只覆盖方向。

4. **把"失败代价"当分档依据**：能否撤回、影响到谁、结果能否验证——三项都过关才谈自动执行。

5. **要升仓，先写验收规则**：可计算的目标 + 可检查的规则，是把 L5 降到 L4、把 L4 降到"按规则执行"的唯一杠杆。

6. **长周期必须设目标复核点**：不设的话，越认真的执行越会把过时的目标推得更远。
