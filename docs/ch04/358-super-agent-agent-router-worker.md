# Super-agent：把 Agent 从单会话里放出来——Router/Worker 双层、事件驱动与存算分离

> 📊 Level ⭐⭐⭐⭐⭐ | 50.0KB

## 问题：单任务的上限取决于模型，多任务的上限取决于人的注意力

Coding Agent 已证明模型能用工具解决复杂问题、越来越少需要人持续监控；人的角色正从底层执行上移到决策与验收。但现有 Agent 仍以**单一 Session 为基本单位**，Session 之间彼此独立：用户并行推进多项工作时要手动切换并记住各自上下文，而**一个人通常只能同时跟进 3–5 个活跃 Session**。在单会话上叠 CLI/MCP/连接器做扩展也不够——仍受制于**单会话同步阻塞、多任务上下文混乱、本地设备离线即停**。

Super-agent 的目标是打破"Agent = 一次手动会话"的绑定，让它成为**跨会话保持上下文、并行推进多任务且互不干扰的连续实体**。四个基础特征：**连续**（在 IM 群聊、GitHub 评论等熟悉界面交互，感觉始终只有一个 Agent，不必想"Session X 里有没有 Y"）、**高效**（不必等上一条命令结束就能接新指令，并行高质量完成多任务）、**主动**（持续观察环境事件主动推进，不需要介入时保持安静）、**持久**（始终在线、接入真实工作环境、长期运行异常能自愈）。

## 模块一：双层架构（连续 × 高效）

核心权衡是**连续性与吞吐量**：所有事件交给同一 Session，上下文最连续但受单 ReAct Loop 串行速度上限约束、多任务细节互相污染；每条事件新开 Session，吞吐最高但任务不独立时缺全局上下文、多个 Session 各自回复造成混乱。解法是把"维护全局连续性"与"高并发执行"拆到两层：**常驻 Router 层**统一承接人类交互与全局协调，**上下文隔离的 Worker 层**并发执行具体任务。**Session 因此成为实现细节，而不是用户的认知负担**——让用户手动管 Session 很大程度上是从底层 LLM API 延续下来的设计惯性。

### Router 层：只做交互与分派，不干具体活

Router 是全局的**序点、协调点与记忆**：所有跨任务信息与决策在这里汇总。为避免它成为瓶颈，设计上**不直接执行具体任务、甚至可以不配 Bash**，只做人类交互与任务分派。它与常见 Agent Team 的区别在于侧重点：Team Lead 要在单任务内部拆解并高频协调、推理负载重；Router 只处理**任务之间**的高层关联。实践反馈是**Router 的任务常没那么复杂，用较轻量的模型就能兼顾速度与效果**。

单会话 Router 为何不立刻成为吞吐瓶颈？因为**上一轮推理期间到达的 Trigger 会积压，在下一轮一并注入**——形成天然批处理。每步是"长输入、短输出"，积压多条合并进一次调用后在 Prefill 阶段并行计算，**单次请求耗时增长远慢于 batch 大小**，于是"积压越多，单个决定分摊的推理时间越低"；上限取决于上下文长度与模型一轮能准确处理多少条 Trigger。规模再大时可做多层过滤或**水平切分**——但切得越细吞吐越高、**分片间记忆与上下文连续性越低**，在全局记忆问题解决前这个权衡一直在。

### Worker 层：上下文隔离、满配工具、只对 Router 汇报

Worker 挂载完整执行工具、在独立上下文里专注单一任务，**通常要配最强模型**（它直接决定任务结果与代码质量）；它**不直接与人交互**，推理与工具调用不外发，只向 Router 汇报、由 Router 统一回复——既保并发又避免多会话各自回复的混乱。同层 Worker 一般不直接通信：冲突多发生在共享工作环境（同一 PR），**只要都订阅了对应 Thread 就会收到相同事件**，从而有机会自行发现并解决冲突，少数跨任务协同由 Router 中转。

每个 Worker 内部也不限于单会话：可再开 Subagent、本身就可以是一个 Agent Team，**对上层 Router 透明**。这套结构既适用代码协作（并行复现问题、评审 PR、开发特性互不阻塞），也适用个人助手——**前端一个聊天页维持交互连续性，底层按话题分派 Worker 并行推进**。

## 模块二：事件驱动（主动）

驱动 Agent 的主要输入从"人逐条键入的提示词"变成"环境中的半结构化事件"，即 **Trigger**：群聊消息、邮件与日程提醒、代码评审评论、CI 结果。围绕一条事件的生命周期有四个递进问题：

### 3.1 两级过滤：Fast Path / Slow Path

真实群聊与代码平台的事件流是**高噪音、低触发率**，对每条都调大模型判断成本不可承受。借鉴 Fast/Slow Path：**程序层策略**（来源、群组、白名单等确定性条件）先做快速准入，把大部分无关消息在调用模型前滤掉；通过准入的候选交给**语义层策略**（LLM 按提示词判断是否需要行动）。语义层同时是**面向人类的自然语言扩展点**——加策略就是改提示词。

### 3.2 订阅与直通：让 Router 只处理"新任务"

若每条后续事件都经 Router 转发，全局节点仍会承压。于是 Fast/Slow 也用于路由：同一 PR / IM 话题 / 邮件串下的连续事件构成一条 **Thread**；Worker 创建后直接**订阅**该 Thread——**已订阅（Fast Path）**后续事件由程序直通该 Worker，超出任务范围时 Worker 可退订或交回 Router 重新分派；**未订阅（Slow Path）**Router 仍可观测所有事件以掌握全局，但只负责判断与分派尚未被订阅的新事件。**Thread 与 Worker 是多对多**：一个 Worker 可订阅多个 Thread，一个 Thread 也可被多个 Worker 订阅——这让它们在共享环境里"不点对点通信也能获知彼此操作"。

### 3.3 Inline & Spill 与链式召回：把上下文窗口当 Cache 管

"**浪费上下文窗口，就是浪费模型的智能**"。把有限窗口当 Cache：**Inline** = 把近期很可能用到的信息直接内联（省掉工具往返）；**Spill** = 超出预算或低频的信息留在窗口外，只保留引用或摘要供按需读取。结合**局部性**的渐进优化：从最少信息开始（对象 ID + 摘要）→ 利用局部性逐步 Inline（先紧邻对象 ID，再时空相邻内容：正文前 50 字、IM 前后消息与所回复消息、评审讨论中的相邻评论）→ 超上限则 Spill（截断+保留续读入口）。

把 Inline & Spill 一致应用到各类对象后，就得到**链式召回（Chain of Recall）**：给 Trigger、Thread、Worker Session 唯一 ID，注入时内联紧邻对象的 ID，使对象在底层构成一张**引用图**；每次工具召回的结果自身也遵循 Inline & Spill，于是模型可从当前事件出发**沿引用关系逐跳展开**（当前消息 → 所在 Thread → 关联 Worker → 该 Worker 关联的另一个评审 Thread）。这缓解了 Router 在长程中丢失先前信息的问题。

### 3.4 投机执行：用后台算力换人的等待

借鉴**投机执行**：在还不确定结果是否被采用时，按环境信号在后台提前尝试，**有价值就交付、没价值就丢弃**。个人助手场景：收到会议邀约/待办时先核对日程冲突、搜集背景、备好草稿，用户过目即可发出。研发场景：团队在内部用户群配置"静默复现并修复"策略——有人反馈问题或讨论方案时，Agent 先在后台尝试复现与修复，**只在确认问题且找到简单修复后才交付，否则全程安静**。

## 模块三：面向人的交互（连续 × 高效）

**异步 ReAct Loop**：经典 Loop 中模型发起同步 `run()` 后阻塞到工具返回，期间无法响应新输入。改成异步 `start()` / `stop()`——调用 `start()` 立即收到 "Started"，循环不再等待；后台完成后把结果作为**新的事件消息**投递进会话；模型可用 `stop()` 终止过长任务。**前台对话与后台执行就此解耦**，新输入在当前推理步结束后即被处理。（作者注明：这一机制已在 DeepSeek Harness 实现，但**尚未默认开启**。）

**多信道交互**：不同信道信息密度与习惯不同，把终端式输出直接搬进群聊会造成信息过载。双层架构已隔离掉冗长推理与密集工具调用，再按信道定制规范：**IM 等即时信道**低打扰、像同事一样只在需要决策或验收时通知、只问直接问题给简短结论——他们验证过的一条硬性规定是**单次回复不超过 100 词**；**GitHub/邮件/文档等异步信道**侧重结构化高密度交付（完整问题背景、改动说明、验证结果）。

## 模块四：计算、状态与环境的分离（持久）

本地 Agent 默认把**计算**（推进 Loop）、**状态**（会话）、**环境**（代码库与工具链）绑在同一台设备：设备休眠即停，也访问不了别处的环境。分两步解耦：**①计算与状态分离**——Loop 放云端无状态弹性容器，Session 等持久状态入数据库，容器可水平扩展/重启/替换，连续性由存储保障；**②计算与执行环境分离**——真实环境常有未提交修改、私有凭据、内网依赖与特定硬件，云端重建成本高且易漏，要求用户迁云又不现实；于是**让环境留在原地**，端侧只装**不保存会话状态的轻量 daemon**，只负责执行命令与返回结果，由云端 Agent 按需读取其中上下文。

作者明确这与 Anthropic 的"脑手分离"一致（harness 无状态、会话日志在 harness 之外、统一接口按需接环境），差别在场景：那篇讲托管服务与按需沙箱/客户 VPC，这里首先要接的是**用户日常使用、可能间歇在线的个人机器**。因此既支持 **BYOM（Bring Your Own Machine）**，也支持云端托管机器——一个 Agent 可在不同设备间切换，甚至**等间歇在线的设备重新上线后再触发完成需要在该设备执行的任务**。

## 模块五：Watchdog（自愈）

长期在线的分布式系统很难仅靠主系统内部逻辑保证可靠，需在主系统之外引入独立**控制回路**。Agent 系统还需第二类监控：**许多异常不是进程崩溃，而是模型陷入无效循环或偏离目标**——所以既要监控基础设施存活，也要监控**任务本身的进展**。做法是在主系统外配一个独立 **Watchdog Session**，用定时消息驱动构成外部 Control Loop：处理接口报错、状态恢复失败等故障，并由模型判断各 Worker 是否**有实质进展、方向是否偏离整体目标**，发现异常及时介入，偶发故障持续复查至恢复。它本身也是具备完整工具能力的 Agent Session，维护者可用自然语言问故障原因，也可让它**在线修正主系统行为**（增删提示词、调整触发规则）。

## 实验：调度层的收益与代价都被量出来了

**消融（7.1）**：群聊 + GitHub CI 消息流驱动四种方案，单次约 300 条消息（约 20 条工作请求，其余闲聊/跟进/叫停/CI），工作用只耗时的工具代替，每方案跑 5 次。

- **Super-agent：p50 12.4 分钟、p95 15.7 分钟**，显著优于带 Subagent 工具的单 Session。
- 单 Session 受提示词影响极大：**中性提示下 5 次运行一次都没调 Subagent**（全在主会话执行、不断被新消息打断），**p95 达 29.5 分钟**；改为"优先委派"后 5 次里 4 次委派、时间缩短但仍慢于 Super-agent，剩下 1 次判断"工作很小"自己干，形成长尾。**结论：分工靠提示词工程与模型临场判断不稳定，双层架构在系统层面消掉了这个问题。**
- 代价：Super-agent 维护多个会话，**读缓存 token 高于单 Session**——用更多 token 换更短更稳的完成时间。
- **去掉直通**：完成时间基本不变，但 Router 决策数 **+约 30%**、总读缓存 token **2323 万→3177 万（+37%）**——**直通不提升质量与速度，但为 Router 省下可观 token 与推理开销**。

**Router 批处理压测（7.2）**：Router 用真实模型、Worker 用 Mock，Trigger 到达速率从约 1 条/分钟升到约 40 条/分钟——**平均 batch 1.0→2.8，单次请求耗时仅 2.5s→3.9s，单决定分摊推理时间 6.4s→1.6s**。这解释了为何去掉直通后峰值负载上升仍未触及单 Router 瓶颈，也支持"当前团队规模下不必过早水平切分、牺牲全局上下文连续性"。作者声明：**实验基于合成负载与简化环境，仅为初步参考。**

## 开放问题（四条，都指向"简化失效处"）

1. **双层架构如何扩展**：单 Router + 订阅直通 + Worker 不直接通信是"以较小工程代价覆盖大多数日常任务"的简化组合；规模与耦合度上去后，Router 何时切分、粒度如何划、Worker 何时需要直接通信与何种拓扑，均无定论。系统与模型 **co-design**（针对 Router 的事件判别、批量分派、上下文召回做专项训练）值得探索。**长程记忆**（跨月甚至更长）是主要扩展瓶颈。
2. **脱离 Session 后如何协作**：底层会话不再对应界面会话，如何呈现任务与项目管理成了新问题；"以聊天窗口为中心"部分上是**路径依赖**，交互可以更多发生在领域特化界面（如直接在 Issue/PR 里工作）；界面上的一个会话底层未必只对应一个 Session。过渡期内还需设计"用户随时介入/接管/实时协同"。
3. **上下文边界与 A2A**：给组织配 Super-agent 本质是在**划分上下文共享与隔离的边界**——该共享的共用一个实例，该隔离的各配一个；一旦存在多个隔离实例（个人助手 vs 团队实例），跨边界协同就是 A2A（不特指某协议），在互不共享上下文、各自代表不同权限边界的前提下如何安全可靠通信仍需探索。
4. **安全与隐私**：事件驱动扩大了接触不可信输入的面。云端 Loop + 端侧 daemon 的设计**默认云与端互信**，一旦云端被入侵或提示词注入攻破，**其连接的全部端侧设备都面临被控制风险**；即使云端未被攻破，**凭据进入模型上下文就存在泄露风险**——需要设计"Agent 完全不接触凭据本身也能使用凭据"的机制。

## 深度分析

### 这篇的真正主张：Session 是系统实现细节，不该是用户概念

多数 Agent 产品把"会话"同时当作上下文容器与项目管理单元，用户被迫记住"哪件事在哪个会话里"。Super-agent 把这两件事拆开：**上下文连续性由 Router 保障，任务粒度由 Thread 与 Worker 表达**。副产品是一系列产品问题的解放——项目管理形式、界面形态、交互重心都可以重新设计。这是**架构决策反推产品形态**的典型例子。

### 五个模块几乎一一对应操作系统经典问题

双层架构≈内核态/用户态的分工与"中断不打断调度器"；两级过滤≈Fast/Slow Path；订阅直通≈路由表与已建连直通；Inline & Spill + 链式召回≈**Cache 与缺页按需加载**；投机执行≈CPU 推测执行；存算分离 + daemon≈**无状态计算 + 远端执行代理**；Watchdog≈外部看门狗定时器。作者自己说"没有提出全新理论，只是把计算机系统的经典思想用到 Agent 系统"——**这个类比的价值在于：每个模块的失效模式与权衡都能被预先知道**。

### "Router 用轻模型"是一个反直觉但重要的工程结论

多数人多 Agent 系统的直觉是"协调者最难、要用最强模型"。这里恰恰相反：Router 只做任务间关联与分派、每步长输入短输出，**轻量模型就够**，而且**批处理让积压反而降低单决定成本**（6.4s→1.6s）。这条经验的可迁移性很强——**协调层的成本模型与执行层完全不同**：执行层要质量，协调层要吞吐与稳定。

### 把"提示词分工"换成"结构分工"，是消融实验最硬的结论

中性提示下模型 5 次运行**一次都没调 Subagent**；改成强提示后仍有 1 次"觉得工作很小"自己干。这说明**靠提示词让主 Agent 主动委派是不可靠的**，因为它在每个决策点都要重新判断"要不要分"。双层架构把这件事变成结构性约束：**Router 没有 Bash、Worker 只收订阅 Thread 的消息**——不需要模型每次都想清楚。**能用结构解决的，不要留给提示词。**

### 直通机制是"纯成本优化"，这类改动最该先做

去掉直通后完成时间不变，但 Router 决策 +30%、token +37%。这意味着直通**不改善结果、只降低系统开销**——从工程优先级看，这类"不改语义只省资源"的机制应该尽早落地，因为它不引入正确性风险，却直接决定系统在同样预算下能撑多大。

### 诚实度：实验声明与安全自陈

作者主动标注"合成负载、简化环境、仅作初步参考"、"异步 Loop 已实现但未默认开启"、"原型并非正式产品"，并在开放问题里直接点出**云端被攻破即控制全部端侧设备**、**凭据进入上下文即泄露**这两个结构性风险。**这种自陈让架构描述可信：读者知道哪些是已验证的，哪些是设计意图。**

## 实践启示

1. **先问"瓶颈是模型还是人的注意力"**：多任务场景下限制往往在人的并发上限（3–5 个活跃会话），而不是模型能力。

2. **把 Session 拆成"上下文容器"与"任务单元"**：连续性交给常驻协调层，任务粒度交给可并行的执行单元。

3. **协调层别配最重的模型**：长输入短输出 + 天然批处理，轻模型往往更划算；积压越多单决定越便宜。

4. **确定性判断先走代码**：来源/白名单/群组用程序层过滤，语义判断才交给模型，并把语义层当"策略扩展点"。

5. **已归属的事件直通，不要都过协调层**：纯成本优化、无正确性风险，收益是 token 与决策数。

6. **上下文当 Cache 管**：先给 ID+摘要，按局部性内联，超限就 Spill 留续读入口；对象间内联 ID 形成引用图，按需逐跳召回。

7. **用结构强制分工**：别指望提示词让主 Agent 每次都愿意委派——把它做成"没有执行工具"的角色约束。

8. **计算无状态、状态入库、环境留原地**：BYOM 比"把环境搬上云"现实得多；端侧 daemon 只执行不保存状态。

9. **Watchdog 要监控"进展"而不只是"存活"**：Agent 的典型故障是空转与偏航，不是进程崩溃。

10. **安全边界先画清**：云端被攻破=全部端侧设备被控；凭据不应进入模型上下文。

## 附三：模块↔经典软件的类比，与四处语义澄清（阿里云 AgentCore 解读，2026-11-02）

阿里云 AgentCore 用一个贯穿全篇的办公场景（IM 群布置季度汇报 → 下午邮件改 10 分钟并聚焦未来规划 → 财务群更新最终数据 → 团建闲聊不打断 → 投机执行先备提纲 → 18:30 关机后云端继续 → 次日开机写回本地 PPT）把五个模块重讲了一遍，价值在**类比框架**与**四处澄清**：

| 模块 | 熟悉的软件设计概念 | 在 Agent 中解决的问题 |
|---|---|---|
| 双层架构 | 调度与执行分离 | 协调者保持响应，执行者并行工作 |
| 事件驱动 | 消息队列、异步通信、发布—订阅、缓存 | 程序的多样化驱动 |
| 计算、状态与环境分离 | 无状态服务、共享存储、远程执行 | 更换计算实例不丢必要状态，工作环境不用整体迁移 |
| Watchdog | 健康检查、外部控制循环 | 不仅检查服务存活，还检查任务是否在推进 |

以及它对 Multi-Agent 三拓扑的定位：**主管—执行**（关键是别让所有决定都等主管）、**对等协作**（路径短，但要明确共同决策与交付责任）、**分层编排**（减少顶层细节，增加层间协调成本）。DeepSeek 的双层最接近"主管—执行"，但**把主管的职能收缩了**——只承接人类交互与任务间分派，不介入单任务内部拆解，避免主管变成新的上下文与执行瓶颈；Worker 内部再套 Subagent/Team 对应分层编排的小组，多 Worker 订阅同一 Thread 互相可见对应"对等协作里共享讨论空间"。

**四处澄清（原文没明说、但很容易被误读的地方）**：

1. **"连续"≠ 全局记忆**：记忆是**知识层面的连续**，而**运行层面的连续依赖更多工程手段**。把两者混为一谈，会以为"上了长期记忆就等于会话连续"。
2. **批处理提高有效吞吐，但不保证每条消息等待更短**：它摊薄的是每次调用的开销（类比数据库批量写入），不是单条时延。
3. **状态保存是恢复的基础，不是恢复的全部**：共享 Session 解决了"换台服务器还能找到状态"，但 Agent 还得知道**接着执行哪一步**、**上一条工具命令是否已经生效**。
4. **投机执行改变的是准备的时机，不改变谁有权做决定**：后台准备的内容在确认前只是草稿，**不能当作正式要求去改动交付物**。

另有两处类比值得记住：端侧 daemon 像 **CI 的 Runner**（调度在中心、活在各台机器上跑、Runner 不记得流水线走到哪一步）；Watchdog 像 **Kubernetes 的控制循环**（对比期望态与实际态），区别是 K8s 看的是副本数、健康检查这类程序可判断的指标，而"有没有实质进展、方向偏没偏"**必须由模型判断**。

## 附四：从设计到可运行的部署链路（架构师 JiaGouX 实操版，2026-11-02）

前四份来源都在讲**这套架构是什么**；这一份讲**怎么把它跑起来**——把一条 GitHub Issue 交给 Agent，让它读讨论与代码、修复、在原讨论里回复并提 PR，人在澄清、确认与合并处参与。作者明确标注 **"操作依据官方文档和源码，尚未独立部署跑通"**，案例（`acme/widgets`、Issue `#42`、`@csv-fix-agent`、CSV 字段转义）为教学示例。

### 环境与身份的四个硬约束

| 项 | 要求 | 为什么 |
|---|---|---|
| Node / 包管理 | `^22.19.0 || >=24.0.0`，`pnpm@11.7.0` | 该提交的 `packageManager` 指定 |
| 依赖 | git 2.32+、Python 3.8+、tmux、GitHub CLI 2.48+ | prepare 与执行链路需要 |
| GitHub 身份 | **专用用户账号**（接受仓库邀请 + 写权限），**不能用 GitHub App** | 原型要**读这个账号的通知**，App 没有通知流 |
| 范围 | 公开原型围绕**一个 github.com 仓库**，可选接飞书，**不支持 GHES** | 当前实现边界 |

**凭据隔离只做到 wrapper 层**：用 `GH_CONFIG_DIR` 单独装一套 `gh` 凭据（`~/.local/bin/gh-agent`），面板里填这个 wrapper 的**绝对路径**；但**运行命令的 OS 用户仍是部署者**，权限预设 `danger-full-access`，独立 worktree 也只隔离代码目录。要真正隔离文件与系统权限，得按官方建议用独立 OS 账号——**这是最容易高估安全边界的地方**。

### 安装与配置：两处"只能跑一次"的坑

```bash
npm install -g @deepseek-ai/dsh@0.2.1-rc.3
git clone https://github.com/deepseek-ai/dsh-superagent-prototype.git dsh-superagent
cd dsh-superagent && git checkout 6337fc823ce20251c8de8085948165c81aaa701e
pnpm install && pnpm build
dsh superagent --from-default-profile web --dump-config > /dev/null   # ⚠ 仅新装
dsh plugin --profile superagent add "link:$PWD"
cp examples/profile.cordis.patch.yml "$HOME/.dsh/profiles/superagent/cordis.patch.yml"  # ⚠ 仅新装
```

两个⚠：**已有 profile 时不要重跑 `--from-default-profile`**（会替换已有配置并删掉 `cordis.patch.yml`），**已有配置文件不要覆盖**（升级走部署文档流程）。`cordis.patch.yml` 里 `stateDir` 必须换成真实绝对路径（数据库、执行用 Git 配置等持久状态都在这里，默认任务目录是它的 `work` 子目录），端口示例 `127.0.0.1:3082`。Super-agent 使用**独立 profile**，可独立启停。

### Settings 三层：谁能让它做事、在哪个目录改、按什么规矩交付

1. **Sources → GitHub**：填 `owner/name` 与实际 wrapper 绝对路径；**receive-all 先关**，只靠明确 `@` 触发。
2. **Eval → On each Source → GitHub**：allowed list 填**发请求的人**的登录名——注意这里有两个账号，**wrapper 登录的是 Agent，允许名单填的是请它做事的人**，名单为空则请求不被接下。mode 先留默认 `observe`。
3. **Execution**：`directory root` 填 `.../superagent/work`，`prepare` 用官方示例命令从本地 clone 建独立分支与 worktree（`DSH_SUPERAGENT_*` 变量由原型注入，**必须填进面板、不要在终端试跑未展开的命令**）；并发先设 1。不配 prepare 的话，Agent 启动时只有空目录，找不到要改的项目。
4. **Prompts**：要求用 Agent 自己的提交身份、说明实际运行过的检查；按 `SETUP.md` 移除 auto-merge 段落、不配另一账号的 merge CLI —— **合并权留在人手里**。

另有一条省事路径：让编码 Agent 读原型目录的 `SETUP.md`，按仓库/账号/允许名单/本地 clone/提交身份收集配置后操作，但**账号登录与密钥输入仍在人自己的终端完成**。

### off / observe / auto：区分的是"没被明确委派时能否自己接单"

| mode | 对**推断接单**的影响 |
|---|---|
| `off` | 不产生推断候选 |
| `observe`（默认） | 评估候选；即使认为可接，**只记录 `would_accept`，不据此执行** |
| `auto` | 评估通过**且**匹配至少一条启用规则，才可接单 |

关键点：**允许名单里的用户明确 `@`，在三种 mode 下都能让它做事**——mode 只约束"没有明确委派时的自主发现"。要让它在无 `@` 的新 Issue 里主动找活，还得打开 receive-all 并按规则过滤；且该版本默认主动规则只有 `copy` 和 `visual`，**并不覆盖所有代码缺陷**。

### Ticket 四状态与范围边界

**Queued**（排队等执行名额）/ **Working** / **Awaiting answer**（详情里列问题，回答仍写在原 Issue）/ **Awaiting review**（Agent 报 `ready` 且有跟踪中的 PR，等人评审——`ready` 只表示"可评审"，不等于合并）。成功接单的判据是 Overview 里出现 Ticket，默认轮询间隔 **60 秒**。

**范围内的追加**（如"再覆盖空字段、检查编码兼容"）会沿原任务继续：评论直接送给负责修复的 Agent，Trigger 显示 **Delivered to Ticket 但不产生新 Eval**。**超出范围**（"顺便重做整个导出页面"）应被交回系统重新判断是否作为新工作。只有背景订阅的 Issue/PR，其评论**只提供上下文**，不扩大范围、也不唤醒已结束的任务。

### 故障恢复：先分清"消息没进来"还是"进来没开工"

| 症状 | 排查顺序 |
|---|---|
| 发了 `@` 无 Ticket | 确认是**新评论**（仅编辑旧正文补 `@` 不产生新通知）→ 作者在 allowed list → Sources 已启用 → 未 Pause → 看 Source 凭据 → Trigger 搜评论 → Eval 看为何未接。**不要先把 `observe` 改 `auto`** |
| prepare 失败 | 看 Ticket 命令输出，检查本地 clone 绝对路径、Agent 仓库权限；修好后 **Retry**，或补一条说明让它重试。**prepare 失败不会像模型网络错误那样自动退避重试** |
| Blocked / Failed / Input undelivered | Retry 只用于未结束且处于投递失败/blocked/failed 的 Ticket；它沿用原会话、目录、分支与 PR。人在 blocked 任务里补的消息若已送达，会继续或重新排队，此时面板不再提供 Retry |
| 服务重启 | 会话与目录保留，运行中的 Agent 重新启动并收到恢复提示——**它要先查工作目录、Git 历史与 GitHub，尤其确认远端是否已有提交或 PR，避免重复创建** |
| `status` 退出码 | 1=查服务与启动日志；2=看部件错误；3=补待配置项（后两者反复重启无益）。日志在 `.artifacts/dsh-superagent-superagent-*.log` |
| 不想继续 | 面板 **Stop** 直接撤回授权；与 Retry 不同，**Stop 后评论不会自动恢复原任务**，需重新接单。"在评论里写停止"仍只是一条待判断的消息 |

### 评审清单：四条可迁移的判据

1. **PR 必须写明**哪里转义错、怎么改、补了哪些用例、**实际运行过哪些检查**，以及失败或未运行的检查。
2. **新测试要能抓住原错误**：临时换回修复前实现，它应当失败；恢复修复后通过。**"编译通过"不算复现，"测试被跳过"更不算。**
3. **字段转义与编码分别查**：先确认原实现/文档的编码与是否带 BOM，再用含中文的固定样本核对导出字节——**不能只看读回后文字相同**。
4. **检查要对应当前 PR 的提交 SHA**：Agent 根据评审又推了提交，就重新核对受影响的检查，**不能沿用旧提交的通过结论**；diff 若带来大面积 UI 改动或无关依赖升级，要问清原因。

另外两点收尾习惯：补出的空字段用例要留在回归测试里；确认稳定的约定可补进项目规则（作者以 Magpie 的 `LESSONS.md` 为例），让下一次修改先读这些约束。

### 这套用法的边界（作者自己划的）

- **只接一个 GitHub 仓库**（+可选飞书），不支持 GHES；其他事件入口需按 `008 Cookbook` 自己开发 Source。
- **生产发布、重启、回滚由人决定**，不是原型默认会做的事。
- 延展场景（CI 失败跟进、接口延迟排查、版本与勘误跟踪、家庭维修报价比较）都是**人工先把材料追加到同一话题**；要自动采集日志/监控、接日历与交易工具，需另接工具并单独授权；现场诊断仍靠人。
- 一句提醒：**"某次变更与异常同时出现，只能作为排查线索，不能据此认定根因。"**

## 附五：四处追问与三个边界外的补充（陈焕新拆解版，2026-11-05）

腾讯云开发者刊载的这篇拆解（作者陈焕新）自陈"多数分享停在复读概念"，因此只写与原文不同的判断——**它最有价值的是四个追问，和三个"系统边界之外"的补充**。

### 追问一：把"3–5 个 Session"从产品问题翻译成系统问题

官方那句"一个人通常只能同时跟进 3 到 5 个活跃 Session"，多数人读成产品体验（界面不好用）。作者往下翻一层：**"用户管理 Session 这件事，很大程度上是从底层 LLM API 延续下来的设计范式——记忆、调度、审批、恢复，全都困在一个会话里。"**

- **并行上**：多个任务同时跑，你得逐个查进度、逐个回结果、逐个补信息——"任务并行了，协调却退回给人"；
- **单会话上**：长程任务里聊天记录回答不了全部问题，"记忆会被压缩，摘要有取舍"，等真要背景时又得回去问人；
- **外部连接上**：IM、会议、文档、App 里的信息"要么人手动告知，要么人手动触发，调度权还在人手里"。

于是"3 到 5 个"有了另一种解释：**不是人的注意力只有这么多，而是本该由系统承担的记忆、调度、审批、恢复被交给了人。** 官方那句被他一字点出：**"Session 应当是系统的实现细节，而不应是用户的认知负担。"** 目标因此拆两条：产品上"**最大化 Agent 产出，最小化人的注意力**"，技术上"**Human out of the loop**"。

### 追问二：Router 的可行性前提是"上下文有边界"（全篇最硬的一击）

官方说 Router 可以很轻量、甚至用小模型。作者追问：**"Router 凭什么知道你这句话该派给谁？"** 两条论据：

- **模型能力**：小模型能担这个责任吗？"我们在单个会话里用旗舰模型聊久了都会出幻觉，何况 Router 要理解、调度、裁决全局的复杂上下文"；
- **安全边界**：Router 理解错的代价不是"答得不好"——"比如一句'帮我把某个临时文件删掉'，恰好历史里有同名文件，或者模型幻觉一下，**删掉的就可能是重要工作**"。

结论：**"根源往往不是模型能力不够，而是上下文本身没有边界：所有历史、所有项目、所有渠道糊在一起，怎么判断都是猜。"** 解法是**工作区级 Context 边界**——群聊、GitHub、项目文档这些事件源**天然自带边界**（"A 专项群大概率和 B 专项群讨论的内容不同，一个群本身就是一个自带边界的工作区 Context"），开源产品 Buzz、Raft、Cumora 也都把人与 Agent 的协作限定在逻辑工作区/群/频道里。边界一旦可控，**"谁能访问、在哪个项目里访问"就能用代码规则写死，不必交给模型猜**——这正是 Fast Path（代码规则）/ Slow Path（LLM 决策）两级判断能成立的前提。

### 追问三：链式召回为什么必要

长程任务必然沉淀远超窗口的上下文，作者把三种失败模式摊开：**只压缩不维护 → 早期信息必然丢失；全塞进去 → 挤占窗口、稀释注意力；塞太少 → 模型反复调工具读，执行步数上去了。** 官方那句判据被引用为纲：**"浪费上下文窗口，就是浪费模型的智能。"** 机制描述也很清楚：**把上下文窗口当 Cache，系统给所有对象分配 ID 构成引用关系图，每次只内联摘要与 ID，需要细节时再顺 ID 逐跳取。**

### 追问四：七个概念为什么不能合并

以"`@agent` 这个 retry 逻辑超时之后会重复扣款，改成幂等的"为例，他给出"一件事"的七段切分：**Source（把外部世界翻译成事件）→ Thread（按线索归拢）→ Eval（接单判断，Policy 给尺子）→ Ticket（让工作有身份，Mandate 给边界）→ Subscription（让上下文自动流动）→ Assignment + Executor（真正执行）→ Channel（把结果送回人群）**。为何不能简化：**"让工作持续关注且不越界需要同时保存两样东西——事件关系（让系统找到相关 Ticket）和工作约定（限定这项工作可以做什么）"**；否则你说一句"顺便把日志降噪也做一下"，"系统可能就多出一张重复工单，或者改错一个地方"。

### 架构层的四点澄清

1. **Router=控制面，Worker=数据面**（沿用分布式系统的角色划分，"它不执行，只决策"）；
2. **"Worker 这个词不足以描述它的性质，更准确的说法是 Agent as a Service"**——"不是常驻的 Agent 实例，而是一个可调度、可替换的执行服务"；对比 **Agent in the Sandbox**（WorkBuddy / Codex / Claude Code）的死结是"**实例不可替代**：它挂了，任务跟着挂；它慢了，任务跟着慢；它用的 Harness 过时了，任务只能跟着过时"；
3. **Sandbox as the Agent Tool**：真实环境复制不了（未提交的本地修改、私有凭据、本地配置文件、只在特定网络可达的服务），所以**反过来做**——云端 Agent 通过端侧一个**不保存会话状态、只执行命令返回结果的轻量 daemon** 按需接入真实环境；"Sandbox 从'Agent 的容器'变成了'Agent 的工具'"，天然支持 **BYOM**。与 Anthropic"脑手分离"同源，差别在场景：**这里首先要接的是用户日常使用、可能间歇在线的个人机器**；
4. **订阅直通解决"Router 自己成瓶颈"**：同一 IM 话题/工作区/PR 下的消息构成 Thread，Router 与已订阅 Thread 建直连，**程序直接送 Worker，只有尚未被订阅的新消息才需 Router 判断**；订阅多对多，前提仍是 Thread 这个边界。

### 两处被忽略的交互硬约束

- **全双工**：经典 ReAct Loop 里同步 `run()` 会阻塞会话；DSH 改成异步 `start()` / `stop()`——调用后立即返回，**后台完成后作为一条新事件投递进会话**，"前台响应与后台执行就此解耦"，新输入在当前推理步结束时就处理；
- **多信道**：IM 场景**单次回复不超过 100 词**。"这类规则看似琐碎，但它决定了 Agent 在群里的存在感是'同事'还是'噪音'。"

### 消息系统在这里为什么值得用（四条价值）

**时间解耦**（发起方不必等，结果以消息回来）、**位置解耦**（模型池与工具端可在不同机器/网络，中间是一条通道而不是一个调用栈）、**可靠投递**（进程崩了消息还在，重启能续上——"内存回调和 RPC 都做不到"）、**可控消费**（消费方可以"暂时不接"，消息留着等下次）。并指出 Agent 时代的改造难点：传统异步假设"队列消息同质可互换"，而 **Agent 任务不同质——"一条可能要跑二十分钟的消息，就能拖住整个队列"**（原文未答；业界如 RocketMQ LiteTopic 在试）。

### 三个"系统边界之外"的补充（原创价值最高）

作者判断：**"Agent 缺三样东西——身份、感知、界面。身份决定它能进哪些系统，感知决定它什么时候该动，界面决定人怎么看到和改动它的结果。"**

**① 身份**：现在 Agent 都是借你的身份干活（用你的 cookie 提 PR、用你的 token 发消息），"**但身份不是自己给的，是平台发的**"——GitHub 得愿意开 machine account、企业微信得愿意发机器人身份，OA/日历/支付/审批每一个系统都得在权限体系里给它留位置。他的切身体验："Coding 工具从 Claude Code、Codex 换到 CodeBuddy 再到 WorkBuddy，**就 Harness 而言交付质量差不多**；但 WorkBuddy 的 Agent 身份带来极致便捷。" 由此给出两句可引用的判断：**"生态不是功能有多少，是有多少系统愿意认这个身份。"** 以及 **"模型会趋同、算力会变便宜、Harness 会开源——这些都会贬值；但'它能进哪些系统、以什么身份进、被谁信任'，不会让自己变便宜。"** 收束为：**"一个 Agent 的能力上限，是它能拿到多少身份；它的价值，是这些身份连起来的那张网。"**

**② 感知**：官方事件源仍是 GitHub / IM / 问答，都能用 Webhook 实现——但现在的 Trigger 主要是**定时器**和**消息**，共同点是"发生了什么"、需要有人主动发出来。而"**真实业务里，大量关键变化不是消息，是状态**"：早上打开电脑没人通知 Agent、步数心率睡眠不会主动推送、**司机接单/换路线/快到了是订单状态迁移而不是聊天消息**、会议结束日程变化亦是如此。所以 **"Trigger 的本质不是事件接入，是感知力"**；连接器"不只是工具，还得是传感器——它要能订阅：订阅状态、订阅变化、订阅边界条件"。反面判据也很利落：**"感知力上去了，主动服务才成立；否则所谓'主动'，不过是定时轮询一遍所有接口。"**

**③ 界面**：过去是"人打开界面、操作功能"，Agent 要么浮在旁边要么藏在对话框；如果 Agent 成为主体，界面就得翻过来——**"不是人操作软件，而是 Agent 编排能力，界面是人看它编排结果的窗口"**。Agent 需要三样东西：**工具调用（一次性把事做完）/ 工作台（能持续存状态、能被反复进出）/ 界面（人能看到、能改、能确认）**，而"现在的 Agent 大多只有第一样"。"生成一个 HTML 页面，看起来像有界面，但它是死的：数据停在生成那一刻，要更新还得回聊天里重新交代，改完也留不下来。" 真正应用至少要补：**持续运行**（有后端在跑、能持续取数、重启数据还在）、**双向调用**（Agent 能调它的工具，它也能请 Agent 在后台干活）、**边界明确**（能调什么写在声明里，**权限由宿主把关，而不是靠提示词约束**）。判据：**"一个只能在你现成软件里点来点去的 Agent，能力上限就是你那些软件；一个能给自己造工作台的 Agent，上限才是它自己的判断力。"**

### 收尾：贾维斯为什么强

"很多人记得它聪明、有性格、会调侃。但我不这么看。贾维斯真正厉害的地方，是它能调动斯塔克工业的所有系统——实验室的门、装甲库的权限、卫星的视野、财务的账。它不只是个聪明的助手，**它是那个世界的一个身份**。" 由此"**真正的 Super，不在于它有多聪明，而在于它能连上多少东西**"；而"3 到 5 个 Session"的解法分两半：**一半在架构**（把记忆/调度/审批/恢复搬进系统，解放注意力——DSH 给了很好的答案），**一半在生态**（让这个系统拿到足够多的身份，替你走进足够多的现场——"也许才刚刚开始"）。

### 这一版补充为什么值得单独留档

前面几条来源（阿里云 AgentCore、架构师部署手册）回答的是"**它怎么运转**"，这一篇回答的是"**它凭什么成立**"：Router 的决策能力不是模型能力问题，而是**上下文边界问题**；而 Super-agent 的天花板最终不在系统内部，而在**它能不能拿到身份**。这两条判断都可以直接拿去审自己的架构——**凡是"让模型理解全局再决策"的设计，先问它的上下文有没有物理/逻辑边界；凡是"我们的 Agent 更强"的论证，先问它比别人多认了几个身份。**
