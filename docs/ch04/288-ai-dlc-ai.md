# AI-DLC：紫讯落地 AI 原生研发新范式的实践

> 📊 Level ⭐⭐⭐⭐ | 12.8KB

> **Background**：本文基于 AWS China Blog 2026-06-29 发布的案例，由紫讯科技架构师胡淮波与亚马逊云科技团队撰写。案例展示紫讯围绕 AI-DLC（AI-Driven Development Life Cycle）方法，建立从知识沉淀到经验回流的端到端研发闭环。

## 三个独有贡献（不应合并到现有 entity）

1. **四件套架构** — 知识底座 + 流程契约 + 系统约束 + 协作平台，自下而上层层支撑 AI 原生研发
2. **三个实战踩坑** — 文档≠上下文、过早并发放大混乱、人工审核变瓶颈（含具体解法）
3. **组织级量化数据** — 版本量提升22%，重点AI项目版本量提升5倍，版本占比从6%→30%

## 四件套架构

### 知识底座：让 AI 看到正确上下文

紫讯将项目知识分为五类，面向 AI 和 Agent 可消费的工程事实：

| 类别 | 内容 |
|------|------|
| 业务知识 | 核心目标、用户角色、关键流程、验收口径、不可破坏的业务规则 |
| 系统知识 | 模块边界、接口契约、数据模型、部署方式、故障处理经验 |
| 决策知识 | 技术取舍、历史方案背景、未采用方案的原因 |
| 协作知识 | 各阶段输入输出标准、谁负责确认、何时必须等待人工判断 |
| Agent 规范 | 上下文读取顺序、禁止猜测场景、任务拆解粒度、提交记录格式 |

**关键实践**：每次需求完成后，判断哪些信息是临时材料、哪些已变成长期规则；只有后者回流到知识底座，避免把偶然处理固化成永久约束。

### 流程契约：让 AI 按标准动作工作

需求→方案→设计→实现→测试→复盘，每个阶段有清晰输入输出。前序问题未收敛时后续不启动。AI 从"被动响应问题"变成"按流程参与研发"。

### 系统约束：让 AI 可控、可验证、可纠偏

**核心判断：模型不是瓶颈，围绕模型的系统才是。**

AI-DLC 不依赖单次提问的"聪明"，而是通过流程规则、质量检查、人工确认和结果回写，把 AI 约束在可验证路径中。

### 协作平台：让多人多 Agent 不退化为 IM 流

- 每条需求变成可追踪工作项（阶段、负责人、阻塞原因、待确认人、产物链接）
- **角色记录边界**：队长 Agent 只路由不写代码，Worker Agent 只负责某阶段交付，人工 Reviewer 只在决策性阶段介入
- 平台成为 AI-DLC 的运行账本，不只是任务看板

## 实践路径：一条需求的 AI-DLC 流转

1. **项目准备（Context）** — 梳理背景、边界、模块、规则、历史决策
2. **需求塑形（Shape）** — AI 辅助澄清目标、约束、验收标准，拆解任务单元
3. **方案收敛（Plan）** — 统一执行计划（负责人、时序、依赖、验收标准）
4. **分批实现（Execute）** — AI 辅助编码、检查、验证；小需求串行，边界清晰的并行
5. **测试验证（Verify）** — 基于验收标准设计验证方式
6. **资产回流（Merge-back）** — 沉淀长期资产，避免一次性处理误固化为长期规则

## 三个踩坑与解法

### 坑1：文档足够多 ≠ AI 上下文足够好

早期大量文档不适合 AI 直接消费：过期未标记、缺少适用范围、只记结论没记原因。

**解法**：区分权威事实、阶段材料、历史记录、待确认信息；为关键文档补充适用范围、更新时间、责任人。

### 坑2：过早追求多 Agent 并发

需求边界未冻结、接口契约未明确、状态记录未统一时，并发放大不确定性。

**解法**：只有任务边界、依赖关系、验收标准和冲突处理方式都清楚后，才扩大并发。

### 坑3：人工审核变成新的等待瓶颈

每个小动作都等待人工确认，流程退化成排队审批。

**解法**：区分"必须确认的决策点"（范围变化、架构影响、验收口径）和"可自动推进的执行点"（格式修复、局部实现、常规测试）。

## 深度分析

### 断点不在编码，而在两个隐含假设
AI 辅助编程默认两件事由人兜底：上下文现场粘贴、产物事后验收。AI-DLC 把这两条抽走，规格因此从"沟通材料"升为一等产物——验收标准必须在 Shape 阶段冻结，否则 AI 会"缺信息时倾向于补全空白，而不是显式承认缺口"。审核经济学随之反转：从抽检代码变成前置审口径，单次更贵但返工更少；坑 3 说明决策点不分级时，审核总量反而成为新瓶颈。

### 四件套是 harness，不是工具链
四条分别回答"看到什么/怎么做/如何可控/多 Agent 如何协同"，没有一条是提示词或某个模型的能力。判据很硬：四件套可以在没有 AI 的情况下写完，却无法靠升级模型获得。故它属于 [Harness Engineering](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/harness-engineering-framework.md) 而非采购清单。缺项会精确退化：缺知识底座→上下文漂移，缺流程契约→阶段跳跃，缺系统约束→不可验证，缺协作平台→并发重新退化为 IM 流。

### 三个坑是结构性的，不是选型问题
三坑同构：都是把人的隐式协调机制显式化失败——文档多但缺时效与权威元数据、依赖图未冻结就并行、决策点与执行点未分级。所以换更强的模型或更好的 IDE 都不解决。命中画像：已有大量历史文档、正从个人提效转向组织提效、交付节奏紧的中型团队；小团队通常不撞坑 2，但几乎必撞坑 1。

### 数据工程变体：骨架同、验证器异
同构部分在骨架：Spec 先行、Unit of Work 粒度、Human Gate 三类决策点（口径/阈值/架构），与紫讯"必须确认的决策点"是同一机制的两个命名。差异在验证对象：要证的不是代码正确，而是口径正确且可加——月度 mart 不能由日表相加，因为去重指标不可加；质量规则由血缘反推（Redshift MCP），而非由需求推导。可迁移的是 spec→unit→gate→回写，领域特定的是验证器（dbt tests / Glue Data Quality / Property-based Testing）。参见 [数据质量框架](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/data-quality-framework.md)。

### 成熟度跃迁的记账：哪些数字算因果
22% 版本量、5 倍重点 AI 项目、6%→30% 占比，原文自我限定为"多团队持续覆盖 + 重点项目高频迭代"共同拉动，即存在挑选效应。版本数还是产出代理而非价值代理，缺交付周期、返工率与缺陷逃逸率。可当因果的只有机制的直接产物：Spec 文档化 100%、需求到 Spec 从 3-5 天压缩到数小时、测试从样例扩到性质推导；组织级百分比只能算相关性。

## 实践启示

1. **先修上下文，再上 Agent。** 给关键文档补适用范围、更新时间、责任人，并区分权威事实与阶段材料；文档数量不构成上下文质量。
2. **把验收标准前移到 Shape 阶段冻结。** 它是 spec 的一部分；留到测试阶段补写，对齐的就是 AI 的实现而非需求。
3. **并发设门禁。** 任务边界、接口契约、状态记录三者齐备才扩并发；否则并发放大的是不确定性，不是产能。
4. **人工介入分两级。** 范围/架构/验收口径走确认，格式修复/局部实现/常规测试自动推进，并把"豁免审核"显式记录，防止口头同意固化为长期规则。
5. **平台当运行账本，不当看板。** 阶段、负责人、阻塞原因、待确认人、产物链接须为结构化字段，Agent 才能据此续推。
6. **度量分层汇报。** 过程指标（spec 覆盖、阶段覆盖、回流资产数）可归因于机制，版本量只作相关性证据使用。
