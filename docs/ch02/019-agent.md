# Agent 系统的三个可设计变量：流程、接口、信息供给

> 📊 Level ⭐⭐⭐⭐ | 24.1KB

## 一句话结论

这篇精读把 Anthropic 前三篇工程博客压成一句话的骨架：**agent 系统只有三个可设计的工程变量——流程的复杂度（workflow 还是 agent）、接口（工具定义与描述）、信息供给（哪些 token 在什么时机进入上下文）**；而这"三个变量没有一次性的最优解"，唯一贯穿始终的元原则是：**从最简单方案起步，任何复杂度都要用可证实的收益来换，而收益的度量依赖评测。**

## 一、流程：先问"能不能不用 agent"

**定义先行**：**workflow** 是 LLM 与工具通过**预定义代码路径**编排；**agent** 是 LLM **动态主导自身流程与工具使用**、对如何完成任务保持控制。

**元原则**：寻找尽可能简单的方案，只在需要时增加复杂度——**"这可能意味着完全不构建 agentic 系统。"** 代价是**用延迟和成本换任务表现**，要判断交换是否划算。选择依据：任务定义明确、需要可预测性与一致性 → workflow；需要大规模灵活性与模型驱动决策 → agent。**对许多应用而言，用检索与上下文内示例优化单次 LLM 调用通常就足够了。**

**框架的弊端**（这段很实用）：框架简化了调用 LLM、定义解析工具、串联调用等标准任务，但**"额外的抽象层往往容易遮蔽底层提示与响应，使调试更困难，也容易诱导在更简单的方案已够用时添加复杂度"**；建议从直接使用 LLM API 开始，"若使用框架，务必理解底层代码，**对框架内部机制的错误假设是客户错误的常见来源**"。

**五种工作流模式**：

| 模式 | 机制 | 适用/要点 |
|---|---|---|
| **提示链** | 任务拆成固定子任务，前一步输出喂下一步；中间可加 **gate 检查门**，未过提前退出 | 能以**延迟换准确率**时；让每次调用变成更简单的任务 |
| **路由** | 输入分类 → 导向专门的下游流程/提示/工具 | 存在明显不同的类别，且分类可靠；简单问题走便宜模型、困难走强模型 |
| **并行化** | **分段 sectioning**（拆独立子任务）/ **投票 voting**（同任务多跑几次） | "把每个考量交给单独的 LLM 调用、使每次专注单一方面，通常表现更好"——护栏与核心响应分开是典型 |
| **编排者-工作者** | 中央 LLM 动态分解、委派、汇总 | 与并行化**拓扑相似但子任务不预定义**，由编排者按输入决定 |
| **评估者-优化器** | 一次生成、一次评审，循环迭代 | 有明确评价标准、且迭代能带来**可度量**价值时 |

**agent 模式**的定义被压成一句极简的话：**"agent 通常就是'基于环境反馈在循环中使用工具的 LLM'"**。关键在**每一步都从环境获得真实反馈（工具调用结果、代码执行结果）来评估进展**；可在检查点或遇到阻塞时暂停求人类反馈；通常跑到完成为止，但**常设停止条件（如最大迭代次数）以保持控制**。代价是**更高的成本与错误累积（compounding errors）**——"建议在沙箱环境中做大量测试，并配上适当的护栏"。

**两个高价值场景的共同点**被提炼为四条：**任务同时需要对话与行动 · 有明确的成功标准 · 能形成反馈回路 · 接入有意义的人类监督**（客服支持、编码 agent）。编码之所以先跑通，是因为"代码方案可通过自动化测试验证，并以测试结果为反馈迭代；问题空间定义良好、结构化，输出质量可客观度量"——但"**自动化测试只能帮助验证功能，人类评审对确保方案符合更广泛的系统要求仍然关键**"。

## 二、接口：从 HCI 到 ACI

**格式的隐性成本**：同一动作常有多种指定方式（写 diff vs 重写整个文件；代码放 markdown vs JSON），"这些差异**在软件工程意义上是表面性的、可无损互换，但对 LLM 的生成难度差别很大**"——写 diff 要求在写出新代码之前先确定 chunk header 中变动的行数；JSON 里写代码要对换行与引号做额外转义。

**三条格式建议**：**给模型留出足够 token 先行"思考"**（避免输出进行到中途已难以回退）· **让格式贴近模型在互联网文本中自然见过的形式** · **确保没有格式"负担"**（如需要精确数清数千行代码的行数、或对所写代码做字符串转义）。

**经验法则**：**"想想在人机交互界面（HCI）上投入了多少精力，就计划在 agent 与计算机的接口（ACI）上投入同等精力。"** 具体做法：站在模型角度审视（仅凭描述与参数，用法是否一目了然）· 好的定义含用法示例、边界情况、输入格式要求、与其他工具的明确界限 · **"像给团队里的初级开发者写 docstring 那样打磨参数名与描述"** · 在工作台跑大量示例观察错误并迭代 · **做防呆设计（poka-yoke）**，修改参数使出错误更难。

**最硬的一个实证**：构建 SWE-bench agent 时，**"团队花在优化工具上的时间实际多于整体提示"**；典型 bug 是模型在移出根目录后会在使用相对路径的工具上出错——**把工具改为始终要求绝对路径后，模型对该方法的使用再无错误**。

## 三、工具是一种"确定性↔非确定性"的契约

**定义很准**：**"工具是一种新型软件，反映确定性系统与非确定性 agent 之间的契约。"** 确定性函数在相同完整输入与状态下产生相同输出；而 agent "在表面相同的起始条件下也可能生成不同响应"，甚至幻觉或没理解工具用法（同一句"今天要带伞吗"，它可能调天气工具、直接凭常识回答、先反问城市，或者干脆调错）。

两条推论：工具仍需遵循**可靠 API 设计原则**，同时要**针对 agent 选择、调用、理解工具的方式进行设计**；设计目标是**"扩大 agent 能有效解决问题的策略空间，让它能用工具追求多种成功路径"**。一个反直觉经验：**"对 agent 最顺手（ergonomic）的工具，人类理解起来也惊人地直观。"**

### 五步开发流程（评测驱动）

1. **构建并试用原型**：先选要支持的工作流，快速实现并**亲自试用**，收集潜在用户的真实任务与表达方式；
2. **设计评测任务与验证方式**：基于真实工作流与代表性数据构造任务，并为每项定义**可验证的结果**。**强任务示例**——"客户报告一次购买被扣款三次，要求找出相关日志并判断其他客户是否受影响"；对比之下"只要求搜索指定事件和客户 ID 的任务更难检验 agent 独立解决问题的能力"。两点提醒：**"复杂任务可能需要数十次工具调用，但调用次数本身不是质量标准"**；**涉及外部操作时，应验证实际状态，而非只检查回答**。**路径验证**可以记录预期工具调用，但**"同一任务可能有多条正确路径，不应将一种调用序列误当作唯一答案"**；**数据必须划分**：分析用的评测集与保留测试集分开；
3. **运行评测并收集轨迹**：除准确率外记录**时长、调用次数、token 消耗、工具错误**，保留完整调用与响应轨迹。agent 的推理与反馈"只是线索，**不能替代对实际调用和结果的检查**"；
4. **分析失败并改进工具**：判断问题来自**工具选择、描述、参数、返回结果还是实现**——"大量无效参数调用可能提示描述或示例不清楚；重复查询可能提示分页、筛选或返回内容需要调整"；原文例子是改进网页搜索工具的描述后，纠正了模型不必要地向查询追加年份的问题；
5. **重新评测并验证**：用**未参与迭代的保留测试集**检验；"持续开发时应维护新的独立测试数据，避免反复观察同一测试集造成过拟合"。

原文报告：在内部 Slack 与 Asana 工具上，**agent 辅助优化在已有"专家"实现基础上进一步提升**——但**图表未标数值**，不能推算幅度，也不能推广到所有工具与任务。

### 五条工具设计原则

| 原则 | 关键细节 |
|---|---|
| **①选择工具** | **"工具越多，结果不一定越好"**；从少量高价值工作流起步、按评测扩展，而不是把每个 API 端点直接暴露；粒度要顾及上下文限制（`search_contacts` 优于"返回完整通讯录"）；**可在工具内部组合多个操作**——`schedule_event` 替代 `list_users`+`list_events`+`create_event`、`search_logs` 替代 `read_logs`、`get_customer_context` 替代三个查询 |
| **②命名空间区分** | `asana_search` / `jira_search`，或进一步按资源 `asana_projects_search`；"**前缀式与后缀式命名方案对工具使用的影响因模型而异，因此应在自己的评测中选择**" |
| **③返回有意义的信息** | `name`/`image_url`/`file_type` 常比 `uuid`/`mime_type` 更好用；"将难以识别的 UUID 转换为语义更清晰的表示或简单编号，在检索任务中改善了准确率"；但标识有时是后续调用必需——**Slack 案例：详细响应含 `thread_ts` 用 206 token，简洁响应只返回线程内容用 72 token**，"二者适用于不同任务，**不能仅以长度决定是否保留字段**" |
| **④控制响应 token** | 分页/范围/筛选/截断 + 合理默认值；**截断要告知输出不完整并给出可执行后续**（缩小范围、请求下一页、多次小范围搜索）；出错要给**可操作的修正建议**而不是只有错误码或堆栈 |
| **⑤写清描述与参数** | 用途、专用查询语法、领域术语、底层资源关系、预期输入输出；`user_id` 优于 `user`；"**描述、参数规范与实际行为应保持一致**"；"精修工具描述后，Claude Sonnet 3.5 在当时的 SWE-bench Verified 取得当时最好成绩"（特定模型与评测条件）；**"MCP 工具注解可声明开放世界访问、破坏性操作等属性，但这些声明不能替代权限控制和实现验证。"** |

## 四、上下文：把它当有限资源来策划

**范围区分**：**提示工程**=编写与组织模型指令（尤其系统提示）；**上下文工程**=**在每次模型调用时，选择和维护模型能够看到的全部信息**——指令、工具定义、工具结果、外部数据、消息历史。一次性任务主要准备输入；agent 则"会在多轮模型和工具调用中不断产生新信息，**每一轮都要决定保留哪些历史、加入哪些新结果**"。

**context rot**：信息能放进窗口，**不代表模型一定能可靠使用**；衰退程度取决于模型、任务、信息位置与上下文内容，**"不能据此断言每增加一个 token，效果都会下降"**。原作者用**"注意力预算"**类比，候选因素包括注意力关系（全注意力计算随序列长度近似二次增长）、训练分布、位置编码——但这篇精读特意补了两条限定：**"这些是理解问题的线索，不足以单独证明所有模型退化的原因"**、**"'注意力预算'也不是可直接测量、逐 token 消耗的固定数值"**，且"长上下文表现通常是**渐进变化**，而非必然在某一点突然失效"。

**总原则**：提供足以完成任务的高相关信息，同时控制无关内容——**"'最小'不等于尽量短；省略必要的约束、背景或证据同样会损害结果。"** 系统提示要"清楚说明目标、约束和判断依据，同时为需要灵活处理的情况留出空间"，避免"用大量脆弱的 if-else 指令规定每一步"（那会增加维护成本）；示例要**多样而典型**，"不建议在提示中堆砌大量边界情况，试图穷举每一条规则"。

### 预检索 vs 按需探索

**按需检索（just-in-time）**：**保留文件路径、查询或链接等轻量引用，运行时按需读取**——重点是"不必一开始就把所有可能相关的数据装入上下文"，**"并不要求完全避免预处理或索引"**。Claude Code 的做法是"编写针对性查询、保存结果，再用 `head`、`tail` 等命令检查大量数据，而不必把完整数据对象传给模型"。**元数据也是线索**：`tests/test_utils.py` 与 `src/core_logic/test_utils.py` 的路径暗示不同用途——"但最终仍需读取内容确认"。

**渐进式披露的代价**：先看目录/搜索结果再逐步读取，每次获得的信息帮助决定下一步；但"运行时探索可能比使用预计算结果更慢；**如果工具或引导不足，agent 也可能误用工具、陷入无效路径或漏掉关键信息**"。**混合方式**（预载 `CLAUDE.md` + `glob`/`grep` 按需查找）往往最实用。作者提醒"实际应根据任务、数据变化频率、延迟和效果选择，**而不是按行业一概而论**"。

### 长任务三法：压缩、笔记、子智能体

| 方法 | 做法 | 代价/边界 |
|---|---|---|
| **压缩对话（compaction）** | 接近窗口上限时总结历史，保留**架构决策、未解决的 bug、实现细节**，丢弃冗余消息与工具输出，再结合最近访问的五个文件继续 | "**过度压缩可能丢失后来才显现价值的细节**"；轻量做法是清理较早工具结果，但"**应先确认结果可重取或不再需要**" |
| **结构化笔记** | 目标·进度·关键事实·待办写入上下文窗口外的持久存储（`NOTES.md`），按需读取；Claude 玩 Pokémon 时自行组织训练进度·地图·战斗策略，**上下文重置后读笔记继续** | 需要维护、检索与更新，否则**可能过时或遗漏** |
| **子智能体** | 主智能体委派聚焦任务，子智能体在各自上下文探索后只回结果 | 案例数字：**子智能体用数万 token 探索，只返回约 1,000–2,000 token 摘要**（"这些数字是案例，不是固定配置"）；委派与综合**增加成本**，摘要**可能遗漏证据** |

三者**可以组合**，典型是"用笔记保存项目状态，同时压缩当前对话"。选择依据不是任务长度，而是"先看需要保留什么、在哪里处理信息"。

## 五、证据边界（这篇精读最值得学的地方）

## 深度分析

### 把"三个变量"当框架，比记五种模式更有用

列模式容易被当成菜单，但真正可迁移的是那句判据：**流程决定何时需要决策与调用工具，工具决定 agent 能采取哪些行动、获得什么结果，上下文决定模型在每一步能依据哪些信息判断**。三者互相牵制——工具设计粗，上下文就会被塞满；上下文太紧，工具就得做得更"组合"；流程太自主，错误累积就被放大。**所以任何一个变量的改动，都必须用评测同时看三者。**

### ACI 这个概念值得单独立起来

"想想在 HCI 上投入了多少精力，就计划在 ACI 上投入同等精力"——这句话解释了为什么很多 agent 项目卡在"能跑但不好用"。**人机界面设计有几十年的方法论（可用性、可发现性、防呆），而 agent 的接口长期被当成"函数签名"**。三个可直接落地的动作：给每个工具写用法示例与边界情况；把相对路径改成绝对路径这类"防呆"；在工作台用大量示例输入观察模型怎么犯错。尤其是那条 SWE-bench 实证——**优化工具的时间多于优化提示**——它把"提示工程"的重心从措辞挪到了接口。

### 工具的"响应设计"比"能力设计"更容易被忽略

五条原则里有三条（③④⑤）都在讲**返回什么**：字段是否语义化、长度是否可控、截断与错误是否给出下一步。这和大多数人做工具时的注意力（"能查什么"）正好相反。而 Slack 那个 206 vs 72 token 的例子说明：**同一份数据要提供两档，因为下游任务不同**——这不是优化，是接口设计。

### "最小上下文"是个被误读的口号

文中最有价值的一处纠偏：**"'最小'不等于尽量短；省略必要的约束、背景或证据同样会损害结果。"** 配套的是 context rot 的正确理解——**衰退是渐进的，不是断崖**，所以"塞到刚好放得下"既不安全也没必要；真正要控制的是**无关内容**，而不是 token 总量。这条对人写系统提示、对自动装配上下文的框架，都是同一约束。

### 长任务三法的本质是三种"信息位置"

压缩 = 把历史留在**当前上下文里但变短**；笔记 = 把状态移到**上下文之外**；子智能体 = 把探索过程放进**另一个上下文**。三种做法对应三种信息损失：摘要丢细节、笔记会过时、子智能体摘要丢证据。**所以选型的正确问法不是"任务多长"，而是"这段信息以后还会被谁、以什么精度需要"。**

### 评测循环的真正难点是"任务设计"，不是"跑评测"

原文那条强任务示例（扣款三次、找出日志、判断其他客户是否受影响）与它的反面（"搜索指定事件和客户 ID"）划出了分界：**前者检验独立解决问题的能力，后者只检验会不会用工具**。再配上"调用次数不是质量标准""路径验证不能当唯一答案""评测集与保留集必须分开"，这四句合起来才是一个能防止自欺的评测方案。

## 实践启示

1. **先证明简单方案不够**：单次调用 / 固定工作流能解决就别上 agent；复杂度必须用可证实的收益来换。

2. **把延迟与成本当显式代价**：agent 是在用这两样换任务表现，交换不划算就该退回去。

3. **警惕框架遮蔽**：抽象层会隐藏底层提示与响应；"对框架内部机制的错误假设"是最常见的错误来源。

4. **用 ACI 的标准做工具**：用法示例、边界情况、输入格式、与其他工具的界限；像写 docstring 一样打磨参数名；做防呆设计。

5. **格式成本要算进去**：给模型留思考空间、贴近它见过的形式、避免"要数行数/做转义"这类负担。

6. **工具不是越多越好**：从少量高价值工作流起步，按评测扩展；宁可组合工具（`schedule_event`）也不暴露一堆原子端点。

7. **返回三件事**：语义化字段（不要裸 UUID）、可控长度（分页/截断）、可执行的下一步（截断提示与错误信息）。

8. **保留标识 vs 控制 token 不是二选一**：提供 `concise`/`detailed` 两档，按下游任务选。

9. **命名空间按服务或资源分组**，并且**在自己的评测里**决定前缀式还是后缀式（模型间有差异）。

10. **评测任务要"强"**：检验独立解决问题（多步、需判断影响面），而不是只检验能不能调对工具。

11. **验证要看状态不只看出回答**：涉及外部操作时检查实际状态；路径验证可以记录但不当唯一答案。

12. **必须留保留集**：开发评测集与保留测试集分开，且持续开发要换新数据，防过拟合。

13. **上下文按"相关性"而非"长度"管理**："最小"不等于尽量短，缺约束同样有害。

14. **默认按需检索**：保留路径/查询/链接等轻量引用，用元数据（目录名、时间戳）做线索，读内容确认。

15. **长任务按"信息将来还会被谁需要"选方法**：压缩（留在窗内变短）／笔记（移出上下文）／子智能体（换个上下文）。

16. **别把博客当结论**：图表无数值、无系统性消融的地方，只能当设计起点。
