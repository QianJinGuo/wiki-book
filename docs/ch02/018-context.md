# Context 不能藏：群聊是容器，数据库是骨

> 📊 Level ⭐⭐⭐⭐ | 24.4KB

## 一句话结论

冯若航（Pigsty / Silo 作者）对 DeepSeek Harness 的第二篇反驳，结论只有一句但很重：**Session 可以藏，Context 不能藏**。因为 **"Session 只是一次临时的执行过程"**，而 **"Context 是工作现场和权限边界，必须端到端，绝不能对用户隐藏"**。他给出的替代表达是：**群聊是天然的 Context 容器（皮），共享数据库才是骨（骨），中间需要一位"书记"把讨论沉淀成结构化记录**。

## 一、为什么"小秘书遇上大工程就拉胯"

他先承认 DSH 在"点对点对话框里替用户自动切分 Session、异步派活"这件事上做得扎实——"不少细节一看就是真干过活、踩过坑的人写出来的"。然后追问：**Session 藏到底下之后，Router 凭什么知道你这句话该派给谁？**

**最锋利的一段自我认知**：

> **"今天的多任务并行里，真正充当 Super-Agent 的，其实是我们自己。"** 在几个 Codex 窗口、几个 Claude 对话、几个飞书群之间来回切换，脑子里记着每摊事推到哪一步、该按什么规矩办的人，是你。

推论也很利落：**"如果真有一个全知全能的 Super-Agent，光靠跟你在一个聊天窗口里一问一答，就能听懂你每一句半截话背后的项目归属、代码边界和轻重缓急，在后台摆平所有冲突还从不闯祸，那它早就不是你的助理了，它直接把'你'给替代了。"** 所以 **"Super-Agent 这个名字也起得太大了，实际做的事情要窄得多，不如改叫 Secretary-Agent（秘书代理）更贴切。"**

**一层很现实的原因**：微信"至少到今天，只给个人机器人开了点对点单聊的口子"，没法把机器人拉进工作群——"大家被迫在单聊的螺蛳壳里做道场，做着做着，就把这种受限于环境的权宜之计，当成了 Super-Agent 本该有的样子"。

## 二、两层 Context 必须分开

| 层 | 是什么 | 能否隐藏 |
|---|---|---|
| **上下文窗口 Context Window** | 往模型眼前塞多少 Token（DSH 的 Inline/Spill、链式召回都在这一层腾挪） | 可以（是工程细节） |
| **工作上下文 Working Context** | **"一组边界：你在哪个现场，能碰什么东西，守什么规矩，跟谁一起干活"** | **绝对不能** |

落到写代码：**代码仓库 · 散在不同机器的工作目录 · 写明环境依赖与行为准则的 AGENTS.md · 内部文档站链接 · 绑在这套环境上的工具权限与历史决策**。"你在 Codex / Claude 里给每个仓库单独配的那套环境，本质上就是一个显式的 Context。"

## 三、两条风险：猜测路由与投机执行

**风险一（路由靠猜）**：**"在一个真能对外动手的系统里，靠猜来路由，迟早要出事故。"** 他举的例子极具体：你在聊天框里随口一句"帮我把临时垃圾清一下"，本意是清理本地测试目录，"Router 但凡猜偏一步、派错了地方，搞不好就是一场线上删库事故"。

**风险二（投机执行）**——这段是全文最有分量的批评：

> **"CPU 的投机执行猜错了还能回滚，就这样还捅出了 Spectre 漏洞；而 Agent 跑命令、跑 CI、提 PR，全是收不回来的外部副作用，连一个'可回滚的架构状态'都没有。"**

他的场景是：Agent 持续监听公共群聊，哪怕没人 @ 它，看到大家在讨论缺陷，就在后台悄悄拉代码复现、提修复 PR——"**没有显式的边界拦着，群里随便谁扔一句不可信的话，都可能触发后台静默跑代码**"。

## 四、群聊是天然的 Context 容器

**为什么是群**：人说话能省字，"是因为开口前就知道自己在什么场合——会议室有会议室的规矩，机房有机房的红线"。**"每一个群，天生就是一个显式的 Context 容器"**：财务群、法务群、运维群、研发群，同一个人在不同群里扮演不同角色、守不同群规。

**历史锚点**：**ChatOps**——GitHub 十多年前就在聊天室 @Hubot 跑部署，撑起 Slack 过去十年的机器人生态。今天三件事变了：**机器人不再是跑死脚本的工具，而是有独立执行环境、能跨机器干活的 Agent；群里不止一个机器人，而是一支舰队；底下得有一份共享的状态。**

**关键对比**："与其费劲在单聊框里搞一个全局 Router 猜谜，不如直接按工作上下文建群，把对应的 GitHub 仓库、文档站绑进群里。你点进 Silo 研发群，@ 里面的编码 Agent 派活，它自然就带着 Silo 的代码目录、AGENTS.md 规范和专属权限去动手——**原本最容易出错的路由问题，在你进群开口的那一刻就零成本解掉了**。"

**最好的类比**（数据库人的直觉）：

> **"没人会写个数据库代理，靠语义去猜一条 SQL 该发给哪个库；连上 PostgreSQL 的第一件事，永远是显式声明 database 和 role。"**

他也承认群聊自身的毛病（信息过载、重要决定被刷走、群多看不完）："群只是把 Context 摆到了明面上，至于群聊自己的老毛病，得靠后面说的'书记'和数据库来治。"

## 五、与 DSH 的差别：管道 vs 容器

> **"在它那里，群聊只是一根外接的'消息输入管道'；而在我说的这套模式里，群本身就是硬隔离的 Context 容器。"**

把关系倒过来，顺手解开两个死结：

**① 安全与主动性可以分级**："公开的用户反馈群碰不到生产环境，大可放手让 Agent '无人 @ 也自动复现 Bug'；但握着线上密钥的运维群，就得立下铁律——**必须同时满足显式的群 × 有权限的真人 × 明确的指令，三样齐了才准动手。转发的聊天记录、贴进来的邮件、别的 Agent 的转述，统统不算数。**"全局 Router 则退居二线当"**版主**"：发现有人在私聊或别的群跑题派活，就提醒把话题挪回对应的项目群，"进对了房间再开工"。

**② 重活靠异构舰队而非单体**："复杂的重活，从来指望不上单个 Agent 包打天下。"到了指挥舰队的阶段，**"人的核心工作其实是做管理：划定群组、分配角色、立规矩、给授权、玩制衡，靠管理拿结果"**。他自己的日常是**"三方制衡"**：Claude 做顶层设计与规划、Codex 埋头写码、**Gemini 与 Claude 一起审 Codex 的活**、Gemini 补文档记账；写文章同理（Claude 头脑风暴、Codex 事实核查、Gemini 润色收口）。理由："**不同厂商的模型盲区不一样，交叉审查能揪出单一模型自己怎么也看不出来的问题。**"

## 六、为什么"盯十个群"比"盯十个 Session"省力

> **"差在群是可以做出层次结构的。Session 是一条平铺直叙的流水账，什么过程细节都往脸上刷；群里却可以分层：Agent 之间的交接和争论默认折叠，群里的'书记'定期出摘要，敲定的结论沉淀进 Wiki，人只在三种时刻露面：被 @、要拍板、出事故。"**

由此得出全篇最重要的一句排序判断：**"更聪明的路由是 nice to have，而真正能省下大量注意力的，是良好设计的信息结构。"**

## 七、群聊是皮，数据库是骨

**现状的糟糕**："舰队要打配合，总得有地方共享上下文；可现阶段大多数人的做法，是在各个工具之间手动复制粘贴，拿自己当人肉总线。"——想让 Claude 接手 Codex 干了一半的活，要么把整段会话贴过去，要么指路让它去翻 Codex 的本地会话，"然后它还真就钻进人家的私有目录，硬啃那一堆 JSONL 日志。这种协作方式，实在太糙了"。

**核心主张**：**"群聊其实只是套在外面给人看的一层皮，底下真正的骨头，是一个跨 Agent 共享的数据库。"** 推理："假如系统里只有 Agent，压根不需要渲染聊天气泡，直接在数据库里读写结构化记录、传指针、发信号，效率最高。"而 **"IM 软件本身也是数据库套了层壳"**——保留群聊这层皮（或给老派极客配个邮件列表网关），"**纯粹是为了迁就人类的习惯：人要看进展，要查审计，要随时插话接管。底下存的是同一份状态：普通用户看群聊，老黑客看邮件，Agent 直接读写库。**"

**两个直接推论**：①"人往群里说的是大白话，**得配一个'书记'**，负责把日常讨论提炼成库里的结构化记录：建了什么任务、做了什么决定、推到了哪一步"；②"Agent 之间私下怎么高频沟通都行，但**每一条都得对人透明**，平时折叠收起，需要时随时展开——否则群聊'看得见、插得上话'的最大价值就丢了"。

**别忘了群只是 Context 的一面**："一个项目的 Context 底下，往往同时挂着聊天群、代码仓库和文档站。"所以"你在 IM 里定了用方案 A，后来在 PR 评论里改成了方案 B，Agent 得跟得上变化"——在这套模型里很自然，"**群和仓库本来就挂在同一个 Context 底下，两边改的本就是同一份状态**"。

## 八、记忆：WAL → 表 → 索引

这是全篇最漂亮的类比：

| 数据库概念 | 对应 | 特性 |
|---|---|---|
| **WAL（预写日志）** | **聊天记录** | 只追加不修改，**是一切事实的源头** |
| **表** | **Wiki / 文档** | 从记录整理出来、人能读能改的知识 |
| **索引** | 向量 / 全文 / 图索引 | **随时都能重建** |

所以"备份只需盯紧前两样，索引丢了重算一遍就行"。**真正难的不是存，是怎么持续整理**——"这就像数据库得定期跑 VACUUM，光往里堆不收拾，记录越积越多，Wiki 很快就会臃肿到没法看"，**这就是"书记"的第二份工作**。

**整理时最值得留两类**：**决定**（当时为什么这么定——"这是群聊刷屏最容易冲走的东西"）与**规矩**（如 AGENTS.md，"往往是真金白银踩坑换来的，含金量最高"）；"Wiki 里的每条结论，最好都能链回群里的原话，方便日后追溯"。

**三个落地坑**：①向量这种模糊检索**对报错码、函数名这类精确字符串很不灵**，必须配全文检索；②**记忆写入要设门槛**——"不能群里谁随口一句话就往长期记忆里塞，最好像提 PR 一样，由书记提议、人或负责审查的 Agent 批准合入，**免得一句话污染所有 Agent 的记忆**"；③**要学会遗忘**——"被推翻的决定、过时的结论要能标记作废、定期清理，就像清理 MVCC 里的死元组一样，不然一个早被否掉的旧方案还会在记忆里阴魂不散"。

## 九、部署与归属：状态和身份才值钱

**两个实际部署问题**：①**Agent 得常驻**（笔记本合盖、断电就失联，"除非你接受手底下的 Agent 到点跟你一块下班"）；②**工作环境又不在那台机器上**（未提交代码、本地凭据、挑环境的工具链）。他对 DSH 这一点的判断表示认同：**"既然这些环境很难搬上云，那就让它们留在原地，每台机器驻一个轻量 Daemon（甚至可以是 sshd），Agent 需要时远程过去执行命令"**；"中心只要记好一本总账：**有哪些 Context，各自在哪台机器的哪个目录，按什么规矩办**"；"代码同步直接走 git，犯不着再造一个网盘"。

**三层收敛 + 一条补充**：他此前写过 Agent 技术栈会收敛成**模型 / Harness / 数据库**三层，"现在看还得再补一样：**身份**，也就是 Agent 的账号由谁发、手里的钥匙归谁管"。判断：**"运行环境和模型只会越来越便宜、越来越容易替换，最后真正值钱的是状态和身份"**——所以"厂商一定会想尽办法把这两样攥在自己手里"。举证是 2025 年年中 Salesforce 改 Slack API 条款（第三方不许批量导出消息、建持久索引、长期保存、喂大模型）——"**数据名义上是你的，能带走多少却得看房东脸色**"。检验标准一句：**"数据的控制权应该留在自己手里，检验标准只有一条：能不能随时带走。"**（"状态放在 PG 里，哪怕用的是别人托管的 PG，哪天不爽了随时一行 pg_dump 拎包走人。"）

## 十、现状盘点：零件到处是，整机还没有

| 方案 | 到了哪一步 | 缺什么 |
|---|---|---|
| **腾讯 WorkBuddy** | 3 月公测，**日活报到 1300 万**（花旗 7 月研报），10 月与企业微信打通 | "**骨子里还是个人桌面 Agent，IM 只是个遥控器，算不上协作现场**" |
| **飞书** | Agent 进群、领工号、与别的 Agent 分工 | 更接近"有工号的数字同事" |
| **Slack** | **把 DSH 那套 Router 直接做成了产品**（Slackbot 统一调度） | 仍是围墙花园 |
| **OpenClaw** | 一 group 一 session | **数据仍散在各 Agent 本地 JSONL** |
| **MCP Agent Mail** | 给每个 Agent 身份与收件箱（"活像一个给 AI 用的邮件列表"） | 默认只跑单机 |
| **Mattermost** | 可自部署、底层正是 PG、群里可放多个接不同模型的机器人 | "主要还是对话助手，缺独立执行环境" |
| **AI Village**（实验） | 四家 Agent 放同一个群 | **"群体协作有时提效、有时反而拖后腿"**；某 Agent 心得："**在社区里当 Agent，最要紧的是拿捏好什么时候闭嘴**" |
| **cumora / magpie**（yetone） | 人与 Agent 混编团队聊天，Agent 进群/发私信、有自己的记忆与状态，后端 Postgres；magpie 管模型切换 | 最接近，但仍是零件 |

结论：**"大厂有群、有数据、有身份，但全锁在自家的围墙花园里；开源的零件越造越齐，但把'自己部署、以 Context 为中心、各家 Agent 混编进群、共享数据库底座、跨机远程调度'这几块拼图一口气咬合到一起的东西，目前还没有。"**

## 十一、底座：PG + S3，几乎是现成的

**"不管走哪条路，共享状态的底座扒到底都落在两样东西上：数据库和对象存储。"** 单机玩具=本地文件系统+SQLite；跨设备=**PG + S3** + 文档框架跑 Wiki + Git 管代码。

他细数了一遍，这些"几乎全是 PG 的看家本领"：**结构化记录→落表 · Agent 之间发信号→LISTEN/NOTIFY · 时断时连的机器排异步任务→SKIP LOCKED 队列 · 两个 Agent 抢着改同一页 Wiki→advisory lock · 按 Context 隔离权限→行级安全（RLS）· 混合检索→pgvector + 全文索引 · 合规审计→pgaudit**；大文件与构建产物扔 S3。

结论是分工很清楚：**"Agent 跑在哪无所谓，模型走 API 调用随时能换，唯独状态（记录、记忆和规矩）必须有个固定的家。"** 而 **"真正需要新造的，其实就是显式的 Context 管理层，以及群里那位'书记'"**。

## 深度分析

### 他和陈焕新得出同一个前提，却走向相反的解法

陈焕新（另一篇拆解）也追问"Router 凭什么知道该派给谁"，解法是**给上下文划边界**（工作区级隔离）。冯若航接得更彻底：**边界不该由 Router 暗中持有，而应显式外化成人类本来就懂的结构——群**。差别在于**谁承担认知成本**：前者靠系统内部约束让 Router 可预测，后者靠人进哪个房间来消灭问题。而那句"**没人会写个数据库代理，靠语义去猜一条 SQL 该发给哪个库**"把这件事讲透了——**路由不是智能问题，是标识问题**。

### "投机执行"这段批评，值得所有做主动 Agent 的人抄下来

CPU 的投机执行有硬件回滚，尚且捅出 Spectre；Agent 的"主动"没有回滚——跑命令、跑 CI、提 PR 都是不可撤销的外部副作用。**所以"主动"的前提不是更聪明的判断，而是更硬的边界**（哪个群、谁授权、指令是否明确）。这也解释了为什么他对"无人 @ 也自动复现 Bug"的态度是**分群分级**，而不是一刀切禁止：**主动性应当是 Context 的属性，不是 Agent 的属性。**

### "信息结构 > 路由智能"是一个反直觉但可验证的排序

大部分团队把精力投在"更准的意图识别 + 更好的任务分派"上，这篇文章说那是 nice to have，真正省注意力的是**折叠、摘要、沉淀**这三件事。逻辑也成立：**路由错了可以纠正一次，信息结构乱了则每一次都要重新理解**。这条判断可以直接用来审产品——如果你的 Agent 界面里每轮都在刷过程细节，那再准的路由也救不了注意力。

### WAL / 表 / 索引 这个类比，把"记忆治理"变成了运维问题

多数 Agent 记忆讨论停在"存什么、怎么检索"，他的三层划分直接给出运维语义：**日志只追加（事实源头）、Wiki 可编辑（人的知识面）、索引可重建（丢了重算）**。于是"整理"这件事有了名字（VACUUM）、有了责任人（书记）、有了质量门槛（像提 PR 一样合入）、有了删除策略（标记作废、清理死元组）。**"记忆污染"这个抽象担忧，被翻译成了"没有写入审批 + 没有 GC"。**

### "最后值钱的是状态和身份"，是一个可检验的产业判断

模型会趋同、算力会变便宜、Harness 会开源（陈焕新说过几乎一样的话），真正不可替代的是**状态（记录/记忆/规矩）与身份（账号/钥匙）**。检验标准他给得很硬：**能不能一行 pg_dump 带走**。这条标准同时是选型准则——**任何把状态锁进私有黑盒的方案，无论体验多好，都带着迁移风险**。

### 但也要看清它的立场

作者是 PG 发行版与对象存储的作者，结论落在"PG+S3 就是答案"上——这不减损论证质量，但读者要自觉：**"群聊+共享库+书记"这套方案对"团队规模、消息量级、权限模型"的假设，比 DSH 那套更重**。他自己也承认"这套完整体我自己也还没攒出来"，且明确只打算在底座层下注（"应用层的仗我大概率不会亲自下场"）。**这是一篇高信息密度的架构主张，不是一份已验证的工程报告。**

## 实践启示

1. **区分两层 Context**：窗口大小是工程细节，可以调；工作现场与权限边界必须显式可见。

2. **别让路由靠猜**：能用标识（进哪个群、哪个仓库、哪个 database/role）解决的，不要交给语义推断。

3. **主动性按 Context 分级**：低风险群可无人 @ 自动干活；握密钥的群必须"显式群 × 有权限真人 × 明确指令"三样齐。

4. **警惕不可回滚的"投机执行"**：Agent 跑命令/CI/提 PR 没有回滚，别用 CPU 的类比自我安慰。

5. **把群当 Context 容器**：按工作上下文建群并绑定仓库、文档站、权限——路由问题在"进对房间"那一刻就消失了。

6. **给群配一位"书记"**：把大白话提炼成结构化记录（任务、决定、进度），并定期出摘要。

7. **共享状态放数据库，群聊只是皮**：Agent 之间传指针别传整段会话；人看群、Agent 读库，同一份状态两种视图。

8. **记忆按 WAL/表/索引分层**：聊天记录只追加、Wiki 是人可编辑的表、索引随时重建；备份只盯前两样。

9. **记忆写入要审批**：像提 PR 一样合入，避免一句话污染所有 Agent 的记忆。

10. **记忆要能作废**：被推翻的决定、过时的结论定期清理，否则旧方案阴魂不散。

11. **整理比存储难**：定期 VACUUM，留下"决定"与"规矩"两类，并让结论链回原话。

12. **Agent 常驻 + 环境留在原地**：中心记总账（有哪些 Context、在哪台机器的哪个目录、守什么规矩），环境用轻量 daemon 远程接入，代码走 git。

13. **用"能不能带走"检验状态归属**：能 pg_dump 走人，才算自己的。

14. **把路由预算挪到信息结构上**：折叠、摘要、沉淀的收益远大于意图识别再提几个点。
