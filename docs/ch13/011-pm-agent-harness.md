# PM 视角的 Agent Harness：把需求写成任务卡、工具契约与验收反例

> 📊 Level ⭐⭐⭐⭐⭐ | 21.9KB

## 一句话结论

vivo 互联网产品团队的这篇指南，把"Agent 需求"从"一个聊天页面 + 一段 Prompt"推到**系统契约**层面。开篇判据极硬：**"如果一份 Agent 需求只能描述输入和输出，它通常还没有进入工程设计阶段。"** 它对 Harness 的定义也适合当统一口径：**承接任务定义、步骤调度、工具调用、权限执行、结果校验与运行观测的控制层**——"业务工作流决定要完成什么，工具实现决定如何访问外部能力，Harness 把两者组织成一段可约束、可追溯的运行"。

## 一、工作流要有执行语义，不能只有顺序

每个步骤九个字段：**步骤名 / 输入 / 输出 / 使用工具 / 是否可并行 / 是否需要审批 / 失败处理 / 产出类型 / 验收标准**。四类步骤语义：

| 类型 | 典型场景 | 技术要求 |
|---|---|---|
| **serial** | 先清洗再聚类 | 前序输出**校验通过**才可启动 |
| **parallel** | 同时查历史与统计影响 | 独立输入、并发上限、聚合策略 |
| **fan-out/fan-in** | 按类别分别分析再汇总 | 分片键、子任务失败容忍度、聚合条件 |
| **human-gate** | 提交前等待确认 | 暂停条件、审批 payload、过期处理 |

**最关键的一条纪律**：某个上游是"硬依赖"还是"增强信息"，**必须由任务定义决定，不能让执行器在运行时猜**。历史匹配若是硬依赖就阻塞后续生成；若是增强信息，就记录"历史匹配缺失"并降级继续。语义应写进 **Workflow DSL / JSON**（`dependsOn` 依赖图 + `input` 数据绑定 + `onFailure` 失败传播 + `timeoutSeconds`），**不要散落在 Prompt 里**。

## 二、四类对象必须分开：Conversation / Task / Run / Artifact

| 对象 | 定义 | 作用 |
|---|---|---|
| **Conversation** | 按时间组织的消息与上下文记录 | 交互入口与沟通历史 |
| **Task** | 围绕明确业务目标的任务定义（输入、工作流、完成标准） | **承载需要被完成和验收的业务工作** |
| **Run** | 任务在特定配置/输入版本/时间点下的**一次执行实例** | 支持重试、运行对比、过程追踪 |
| **Artifact** | 执行后生成的、可访问/下载/继续消费的结果对象 | 承载报告、结构化结果或外部系统记录 |

**"一个任务可以包含多轮对话、多次运行和多个产物。对话是交互载体，任务是业务目标，运行是一次执行实例，产物是可继续使用的交付结果。如果把这些对象混成一个聊天线程，后续很难支持重试、对比、恢复和结果归属。"**

**版本与引用语义**是这里最容易被漏掉的工程细节：Task 要支持**输入可复现**（保存输入的稳定引用，而不是提示词里的长文本）与**结构可演进**（字段可逐步增加而历史任务仍可读）。三个版本字段各管一件事：`schemaVersion` 管对象结构演进、`workflowVersion` 管同一任务在不同编排版本下的行为差异、`inputRefs.version` 避免"数据源更新后无法解释历史结论"。另有两个语义澄清：**`Task.owner` 是业务归属/责任主体，不等于发起会话的用户**；**`Run.approvals` 存审批记录引用，不把审批内容复制进每条消息**。

## 三、工具是业务动作协议，不是接口列表

契约九个字段：`name · description · inputSchema · outputSchema · permission · sideEffect · timeout · retryPolicy`。PM 要确认的八件事：**何时可调用、参数是否够、返回是否够支撑下一步、是否改外部系统、是否需审批、失败能否重试、是否允许重复调用、是否需要幂等键**。

> "工具不是'给模型调用的接口列表'，工具是 Agent 工作流中的**业务动作协议**。一个工具的输入、输出、权限和副作用如果没有明确约定，**模型的自由度越高，系统的不确定性也越高**。"

**三层校验**（层层递进，缺一不可）：

1. **调用前**：JSON Schema + 字段枚举 + 权限策略，拒非法参数（优先级越界、项目不在授权范围）；
2. **执行后**：对返回值做 Schema 校验——**"避免模型把错误响应误当成成功结果继续推理"**；
3. **业务结果**：验证业务不变量，如"提交成功后必须获得可查询的 `recordId`"。

**错误不许拼成自然语言**，要返回稳定结构：`{ok:false, requestId, error:{code, retryable, message, details}}`——`retryable` 决定执行器是否自动重试、`requestId` 用于日志关联、`details` 让后续步骤能跳转已有记录。并且**必须区分四态**：**未执行 / 执行失败 / 已执行但结果不满足业务条件 / 幂等重放返回已有结果**（同幂等键应返回首次成功的资源，并标 `idempotentReplay: true`）。

**四层分离**是这一节的方法论核心：**description 告诉模型何时用/不用 → JSON Schema 约束类型枚举必填 → Policy 约束主体·资源范围·风险等级 → Executor 负责超时·重试·幂等·审计**。目的很明确：**"避免把'禁止修改其他项目''标题最长 80 字'之类的硬约束仅写在 Prompt 中。Prompt 可以被误解，Schema 和 Policy 必须能够在执行前强制生效。"**

## 四、风险五级 + 授权绑定三元组

| 等级 | 类型 | 示例 | 默认策略 |
|---|---|---|---|
| **L0** | 只读计算 | 文本分类、格式转换 | 自动执行 |
| **L1** | 读取业务数据 | 查历史记录、查知识库 | 权限校验 |
| **L2** | 生成内部产物 | 方案草稿、报告、测试用例 | 自动执行**并记录来源** |
| **L3** | 修改业务数据 | 提交记录、更新任务字段 | **明确授权，必要时审批** |
| **L4** | 高风险外部动作 | 删除数据、发消息、对外发布 | **强制审批和审计** |

**审批不是布尔值**。有效授权至少绑定三类上下文并加约束：

```json
{"subject":"user_12345","action":"recommendation.submit",
 "resource":{"scopeId":"workspace_1001"},
 "constraints":{"priorityIn":["P1","P2"],"expiresAt":"2026-08-22T12:00:00Z"},
 "approvalId":"approval_01"}
```

判据一句：**"允许提交建议"并不等于"允许向所有目标空间写入记录"。** 当参数越过资源范围、修改了受约束字段、或审批过期时，**执行器必须重新请求授权**——**避免一次确认被错误扩展为无限范围的通行证**。

## 五、结果协议：四类结果 + 可定位证据

| 结果类型 | 说明 | 适用 |
|---|---|---|
| **自然语言说明** | 结论、解释、过程摘要 | 会话中说明依据与下一步 |
| **结构化业务结果** | 固定字段、可被程序读取与校验 | 传给后续 Agent/页面组件/规则引擎 |
| **可下载产物** | 有格式、版本、访问地址 | 报告、表格、文档、图片 |
| **外部系统记录** | 目标系统中创建/更新的稳定资源 | 可继续跟进的事项或数据记录 |

结果对象字段：`summary · evidence · decisions · risks · pendingQuestions · artifactRefs · nextActions`。**`evidenceRefs` 不能只是 URL 列表**，要能表达"哪条结论依据哪些来源"：`sourceId + locator + role`（如 `feedback_328 / row:328 / user_feedback`），并带 `confidence` 与 **`assumptions`（把模型推理依赖的前提显式化）**。进入外部系统的结果还要带 `resultVersion / generatedAt / generatorVersion`，便于比较不同版本的分析差异。

**发布前加确定性校验器**（用普通代码或规则引擎，**不要再交给模型判断**）：每条建议至少绑定一条 evidence、priority 只能 P0-P3、`sourceRef` 必须在本次 Task 可访问输入内、`externalRecordId` 只能在写工具成功后出现、高风险必须有 nextAction。一句话：**"模型负责生成候选结论，校验器负责守住协议边界。"**

## 六、失败处理：七分类 + 读写分离的重试

七类错误各有策略：**InputError**（引导补信息）、**PermissionError**（求授权或换数据源）、**ToolError**（重试或换工具）、**TimeoutError**（后台继续或拆分任务）、**ModelError**（降级模型或重新规划）、**ValidationError**（返回 Agent 修正）、**ExternalSystemError**（保留任务并支持恢复）。

**"最多重试三次"不是通用策略**：

| 操作类型 | 典型失败 | 推荐策略 |
|---|---|---|
| 只读查询 | 网络抖动、限流 | 指数退避 + 抖动（`delay = base * 2^attempt + jitter`，抖动防二次拥塞） |
| **写外部系统** | 响应丢失、网关超时 | **先按幂等键查询，再决定是否重试** |
| 模型生成 | 格式不合法、内容不完整 | 修提示词，或基于校验错误再生成 |
| 长任务 | 执行超时 | 拆分、异步化或延长租约，**不盲目重复执行** |

**幂等键要表达业务动作**：`idempotencyKey = hash(taskId + stepId + targetProjectId + normalizedPayload)`，其中 `normalizedPayload` **排除时间戳、展示文案等不影响业务语义的字段**。纪律一句：**"同一个 taskId + stepId 不应重复创建相同业务数据。"** 这样即使执行器重启、响应丢失或用户重复点击，也能把同一业务动作折叠成一次结果。

## 七、可观测与验收：监控不能替代验证

两种典型误判：**"跑完了"就当成功**（掩盖结论无依据、写操作重复执行）、**"平均耗时下降"就当体验变好**（可能以牺牲结果质量为代价）。诊断的正确顺序是先分辨失败发生在**任务设计 / 模型决策 / 工具接口 / 用户确认**哪一环——"**工具超时率只有和具体的步骤、数据源及重试次数放在一起，才有诊断意义。单独统计'工具成功率'通常解决不了问题。**"

**一条可关联的执行记录**就够：`traceId, taskId, runId, stepId, toolName, workflowVersion, promptVersion, inputRef, outputRef, latencyMs, retryCount, errorCode, approvalId`。分工很清楚：`taskId` 服务业务检索、`traceId` 跨服务追踪、`workflowVersion`/`promptVersion` 解释"为什么同一类输入这周开始产生不同结果"。

**验收保留少量高价值反例样本**（空反馈、历史服务不可用、重复提交、目标空间越权、用户拒绝审批），每个写清不可触碰的边界，并写成**契约测试**：`requiredTools` / `forbiddenTools` / `resultSchema` / `assertions` / `sideEffects.maxSubmittedRecords`。

> 这类用例"更接近契约测试：它不承诺模型必须写出哪一句话，却明确要求**不能绕过证据、不能调用无关工具、不能因为重试创建两条需求**。把它放进 CI 或灰度回归，比让测试同学反复手工体验更能发现工程回归。"

## 八、PM 的交付物：一张围绕关键业务动作的"任务卡"

Agent 需求常失败在一个朴素的地方：**"文档里写了用户要什么，却没有写清系统在不确定条件下该怎么做。研发只能把判断塞进 Prompt，测试也只能凭感觉点几轮。"** 更有效的交付不是六张独立清单，而是**一张任务卡**，七项审查：

| 审查项 | 要回答的问题 |
|---|---|
| **业务完成条件** | 产生什么可验证结果？什么状态下算真正完成？ |
| **输入和来源** | 来自哪里？有无版本号、权限限制、失效处理？ |
| **工作流边界** | 哪些硬依赖、哪些可降级、哪里必须等人？ |
| **工具和副作用** | 能读写哪些资源？超时与重复调用会发生什么？ |
| **结果与证据** | 哪些字段必须结构化？结论如何回指来源？ |
| **异常和恢复** | 缺输入、无权限、超时、写入不确定分别怎么办？ |
| **验收反例** | 哪些越权、重复写入、无证据结论必须被拦住？ |

## 九、总结句

> **"Agent 产品的技术设计，不能停留在 Prompt、模型和聊天界面。真正需要被设计的是—条业务动作链：任务的输入和完成条件先被固定下来，再拆成带依赖关系的步骤；每个步骤只能通过有 Schema、权限和副作用约束的工具执行；结果以可追溯的结构化协议交付；异常、重试和验证则保证这条链在不确定环境下仍然可控。"**

以及收尾那句：**"好的 Agent 需求，是先把不能出错的业务边界写进任务、工具和验证规则。"**

## 深度分析

### 这篇补的是"工程化之前的那一层"：契约由谁定

技术团队写的 harness 文章（天猫国际、速卖通、腾讯）都在讲**系统怎么实现**；这篇问的是**这些约束由谁在什么时候定下来**。答案是 PM，且必须在需求阶段——因为"哪些步骤是硬依赖""什么范围允许写入""超时后怎么办"这些判断，**一旦推迟到实现期就会以补丁形式出现**。它给出的度量也很锋利：**一份只能描述输入输出的需求，说明它还没进入工程设计阶段**。

### "四类对象分开"是整篇的地基，也是最多团队栽跟头的地方

把 Conversation/Task/Run/Artifact 混成一个聊天线程，代价不是"代码难看"，而是**四件能力同时消失**：重试（没有 Run 就没有"再跑一次"）、对比（没有版本就没有"哪次更好"）、恢复（没有 Task 就没有"接着做"）、归属（没有 Artifact 就没有"结果是谁的"）。这与天猫国际"对话是入口，Task 才是业务事实"、速卖通"主 Agent 不生产业务实体"是同一根支柱的三种表述——**先把事实对象从对话里拆出来，其他工程能力才谈得上**。

### 授权三元组（Subject/Resource/Action）+ 约束，是"一次确认别变成通行证"

多数审批系统只记"谁批了、批没批"，于是出现典型事故：用户批了"A 项目的 P1 建议提交"，执行器却拿这张票去写 B 项目、写 P3、甚至写一百条。这里的解法是把授权写成**可判定的记录**：主体 + 资源（scopeId）+ 动作 + 约束（`priorityIn`、`expiresAt`），且**参数越界、改受约束字段、审批过期都必须重新请求**。这条设计可以直接用在任何"人在回路"的系统里，与腾讯"账号/外发/付费仍要人确认"、速卖通"ODD 按风险裁剪工具"属于同一族的权限工程。

### 错误四态（未执行/失败/已执行但业务不达标/幂等重放）是异步系统的分水岭

把"失败"当一个布尔值，是所有重复写入事故的起点。这里的四态直接对应四种完全不同的处理：未执行 → 可以重试；执行失败 → 看 retryable；**已执行但业务不满足 → 不能重试，要修正**；幂等重放 → 直接用返回的既有资源。配上"写操作先按幂等键查询再决定是否重试"，才算真正解决"响应丢了但记录已经写进去"这个经典难题。这与速卖通"故障语义三分（未受理/已受理未回传/远端异常）、宁可挂起也不激进重试"几乎逐条对应——**两家不同公司、不同业务，收敛到同一套错误语义**。

### 契约测试是"验收"这一环的正确答案

"看几条回答顺不顺眼"无法回归，因为 LLM 输出不确定；而契约测试绕开了措辞，只断言**不可违反的边界**：必须调用哪些工具、禁止调用哪些、结果必须满足哪个 schema、副作用上限是多少（`maxSubmittedRecords: 1`）。这条思路把 Agent 验收从"人工体验"变成"可进 CI 的断言"——**它不测模型聪不聪明，只测系统守不守规矩**。而"守规矩"恰恰是可以工程化保障的那一半。

### 任务卡七问，本质是一张"把补丁前移"的清单

七个审查项彼此咬合：完成条件定标准、输入来源定可复现、工作流边界定调度、工具副作用定权限、结果证据定可信、异常恢复定鲁棒、验收反例定回归。**它们共同的作用是：让"上线前才发现要补的规则"提前到需求评审**。这也解释了作者那句"目标不是让 PM 承担实现细节，而是避免关键业务判断在实现后期才以补丁形式出现"。

## 实践启示

1. **需求评审先问一句**：这份需求除了输入输出，说清了步骤依赖、工具副作用、确认点、失败策略、交付形态吗？说不清就是还没进工程设计。

2. **工作流写成 DSL 而非 Prompt**：`dependsOn` + `input` 绑定 + `onFailure` + 超时；硬依赖与增强信息由任务定义决定，**不让执行器猜**。

3. **四对象分开建模**：Conversation / Task / Run / Artifact，分别承担交互、目标、实例、产物；否则重试、对比、恢复、归属全丢。

4. **三个版本字段都要有**：`schemaVersion`（结构演进）、`workflowVersion`（编排差异）、`inputRefs.version`（解释历史结论）。

5. **工具契约九字段 + 三层校验**：调用前 Schema/枚举/权限、执行后返回值 Schema、业务层不变量（如必须有 recordId）。

6. **错误返回结构体，不返回散文**：`code / retryable / requestId / details`，并区分四态（未执行·失败·已执行业务不达标·幂等重放）。

7. **风险分级放权**：L0-L4 五档，L2 也要记来源，L3 需明确授权、L4 强制审批+审计。

8. **授权绑 Subject/Resource/Action + 约束**：越界、改受约束字段、过期一律重新请求，防"一次确认变通行证"。

9. **写操作先查后重试**，幂等键 = `hash(taskId+stepId+targetProjectId+normalizedPayload)`；读操作才用指数退避+抖动。

10. **结果分四类交付**：说明、结构化结果、可下载产物、外部系统记录——存储与消费方式完全不同。

11. **证据要可定位**（sourceId+locator+role），并显式写 `assumptions`；confidence 不能替代证据。

12. **发布前跑确定性校验器**（不是再问一次模型），把"必须有证据""优先级枚举""记录 ID 只能来自成功写"变成代码。

13. **验收写契约测试**：requiredTools / forbiddenTools / resultSchema / assertions / sideEffects 上限，进 CI。

14. **用任务卡七问自查**：完成条件·输入来源·工作流边界·工具副作用·结果证据·异常恢复·验收反例。
