# OntSQL Agent：从生产代码抽本体的 AI SQL 生成（淘宝行业经营分析）

> 📊 Level ⭐⭐⭐⭐ | 19.1KB

## OntSQL Agent：本体驱动的 AI SQL 生成

> 大淘宝技术的核心判断：**通用模型写 SQL 的瓶颈不在模型能力，而在业务知识获取**——「模型不缺代码生成能力，缺的是用哪张表、取哪个字段、指标口径怎么算」。他们的解法是把本体当成数据研发的业务说明书，**从生产 SQL 自动抽三元组**（不是让人写文档），再靠三道关校验、七路召回与三条反馈链路维持新鲜度。业务侧结果：需求整体耗时从数个人日缩到约一个人日，AI 代码行占比从个位数升到八成以上。

## 三类错误与一个共同特征

一个看似简单的需求「查上月各品类 top 品牌成交额及同比」，通用模型几秒就能生成语法完整的 SQL，但四个判断它都答不出：品类下的品牌数据从哪张表取、成交额对应哪个字段、是否含退款、同比口径是什么。归纳成三类高频错误：**选错表**（同域下明细表/汇总表/快照表十余张，粒度不同）、**用错字段**（同名不同义、同义不同名，按关键词匹配必错）、**口径对不上**（分子分母取什么、是否剔除特殊数据、时间窗口怎么定义——这些「约定俗成」不在需求文档里，在历史代码与个人经验里）。

**共同特征最致命：SQL 能跑、能返回、不报错，但数据就是不对**。所以常规测试拦不住——没有异常、没有报错，只有错误的数据流进看板。这也决定了修法不是加测试，而是补知识。

一个重要的反证：**换更强的模型，选表与语法稳定性确有提升，但指标口径仍然偏**。因为无论模型多强，都无法获取从未出现在上下文里的业务约定——这把问题从「模型选型」钉死成「知识供给」。

## 本体是什么，以及它不是什么

本体要做的是把资深研发脑子里的东西变成团队共享、AI 可读的资产，三个价值：**消除歧义**（把「店铺类型」这种多义词绑定到具体业务域、字段、枚举——同一个「店铺类型」在决策域、服饰行业、国际行业各有一套判定逻辑）、**补全规则**（把散落在历史代码里的 CASE WHEN、映射表、兜底逻辑显式化）、**可迭代**（人工修正与 bad case 回流）。

边界划得很清：**数据库管「数据在哪」，语义层管「口径统一」，知识图谱管「关系推理」，本体管「让 AI 具备写对这类 SQL 所需的完整业务理解」**。后面这一点很重要——它不追求通用知识表达，只追求「够用来写对 SQL」。

架构参考 Palantir 的三层本体框架，但重新界定了每层在数据研发中的边界；承载五类知识，全部结构化存储，**每条规则可追溯到线上代码的具体位置**。整套工具是 **OntSQL Agent = 本体资产 + 按需召回 + 飞轮迭代**。

## 本体从哪来：四种方案，选最脏的那条

- **只给 DDL**：解决不了语义。DDL 只说「表长什么样」，缺的是「这张表该怎么用」——不知道某个品牌 ID 字段何时该用、和另一个字段什么关系、映射不上怎么兜底。
- **人工整理知识库**：方向对、效果好，但**维护不动**——线上表逻辑与口径一直在变，写的时候慢、写完很快过期。
- **AI 把文档编译成知识库**（LLM-Wiki 思路）：作者认可「先编译再查询」，但落到数据研发有两个不同——**知识来源**上，真实生产中大量需求是语音会议形成共识、协作平台一句描述就直接开发，**很多口径根本没有文档**，补文档本身成本最高；**产物**上，编译出的是自然语言知识页（如「按层级逐级匹配」），机器无法判断它与线上代码是否还一致。
- **读取生产代码**（他们的选择）：直接从运行中的 SQL 与元数据抽，产出机器可查的结构化资产。作者也承认文档编译方案可整合多格式资料、覆盖更广、周期更短，两者取舍在于**专注点不同**（他们要的输入是业务知识包、产出是 SQL）。

**入口是核心表 + 血缘，不是逐份 SQL**：先从业务交付表、看板表识别场景真正在用的核心表，人工核实补充；再顺着上下游把该带的表与知识带出来——**最终本体里四成的表是靠血缘分析找出、确认有价值后才建的**。核心表决定从哪儿进去，上下游决定能捞回多少。

## 抽取形态：三元组，而不是一句话

不让模型写自然语言，要求它把每条 SQL 里的业务 CASE WHEN 抽成结构化三元组，并带上取证信息：

```yaml
case_group:        shop_type            # CASE 组
branch_order:      1                    # 分支序号
condition_sql:     shop_name IN (...)   # 判断条件
action_sql:        结论A                 # 结果动作
source_sql_hash:   bbbd38537a7ba41e     # 源码指纹
evidence_sql_node: 308513553            # 生产节点 ID
```

理由不是「模型看不懂自然语言」，而是**一句话没法校验**——说不出它对应 SQL 哪一段，也说不出有没有过期。写成条件 + 动作，规则就能与分支逐条对齐，脚本自动抹平写法差异、算指纹、逐条落库并绑定生产节点。**要的不是给人看的文档，是机器自己能查的资产**。

## 三道关：专防抽取幻觉

1. **对指纹**：算指纹前先抹平空格、大小写等无语义差异，同一段 SQL 的人写版与模型抽版指纹必然一致——品牌案例中人工写的规则模型全抽到，条条对得上。
2. **回溯 SQL**：把每条规则拿回生产 SQL 找落脚分支；找不到落脚点的就是模型编的，直接删。
3. **查格式**：字段是否填全、格式是否合规。

三道关只解决一件事：**抽出的规则与生产代码逐条对得上**。

**人工只在两处介入**：核心表首次进本体时人工过一遍（验证、复核、补充）；线上发现生成不对时（校验未通过、逻辑冲突）人工判断是否本体的问题。其余——拉元数据、抽规则、对指纹、回溯 SQL、表刷新后重查——全自动。首次接入一张再难的表只需一个权限账号加一次人工校验；口径变化时机器能自己发现并提示刷新。

## 召回：给材料，不给硬规则

本体里上千条规则，每次写 SQL 不能全给——这是**注意力稀释**：上下文窗口的物理容量与有效容量是两回事，塞满无关信息的长上下文，有效容量可能不如精心裁剪的短上下文。召回机制对应**渐进式披露**：Agent 判断是 SQL 生成任务后按约定自动调起召回，拿到上下文包才开始写。

召回包包含：需求相关的表本体与字段语义、指标口径定义、触发条件匹配的业务规则、历史相似 SQL 写法、值域/枚举/异常处理等生产证据。一个真实需求是**七路并行召回**（相似实现、时间切换、血缘、值域画像、表族信息等），相关度最高的表本体只挑与本需求最相关的规则，**召回的规则恰好就是这个需求最容易踩坑的地方**。

**刻意设计：召回给材料，不是硬规则**。不改写 AI 输出，也不强制它必须用某条规则。早期把规则写成必须遵守的指令，结果模型从「聪明的 AI 工具」退化成「蠢笨的规则执行器」——遇到规则没覆盖的情况就不会推理了，生成质量不升反降。这与 Agent 设计里「从防御到赋能」同构：**与其用更多约束堵错误出口，不如把该看的资料找全、打开正确入口**。另外召回内部是确定性程序逻辑，召回什么不由模型临场决定，同一需求跑多少次结果一样。

## 飞轮：三条反馈链路

静态知识库一定会老化。三条链路把真实使用中的修正回注：**研发真实 diff**（对比 AI 初稿与最终上线 SQL，回流补的字段、过滤、join、CASE WHEN 与口径修正）、**评测集驱动**（扣分 case 拆成「本体缺口 / 召回不足 / 模型误用 / 需求隐含条件」四类，分别补规则、补证据、调召回）、**线上使用日志**（Qoder、千问办公等平台的提问、结果、失败日志与人工修正，补场景规则与使用约束）。三者汇入反馈池，**经人工确认后**写回本体。

**跨场景与跨平台**：生成本体的技术不与业务场景绑定；资产标准化为 Turtle / JSON / Markdown + 索引文件，SQL 生成日志、采纳统计、反馈、回归测试都是独立 Python 模块，其他平台只保留薄入口读同一套资产——**换工具不换知识**。

## 评测：五维加权 + 两条防作弊硬规则

评测 case 全部来自真实业务工单，每条含需求信息、依赖表、Agent 输入，并绑定已上线生产 SQL 作 Ground Truth；评测集靠定时抓取 + LLM 自动分类持续扩充，不是静态集合。

**两条硬规则**：① 禁读 GT SQL，也禁止通过节点 ID 反查代码，防模型直接复用标准答案；② 只读当前版本本体，禁读其他版本、共享生产版本或个人工作区版本，保证版本间可比。

**五维赋权 100 分**：语法 10、选表 20、字段 20、**业务规则 40**、数据结果 10——业务规则权重最高，因为它是 AI 当前最薄弱、也是本体价值最集中的地方。每条 case 按总分判「通过/不通过」，打分用于量化版本差异，最终结论用 0/1 二分呈现。五层递进检测从语法到数据结果逐层校验，不通过时自动归因到层级与原因，结果回流飞轮形成「生成 → 评测 → 归因 → 修正」闭环。

## 效果与证据边界

**技术侧**：语法与选表已稳定通过，**字段维度提升最明显**，当前瓶颈集中在复杂业务规则的完整还原。业务规则维度「表面仅提升 1 分」，但评分按「全部命中」算，拆开看——**无本体时 AI 生成的映射规则基本错误、代码不可用**；引入本体后，原依赖模型猜的规则分支已由历史代码与值域分布补齐。

**业务侧**：月均需求处理量提升数倍、单需求交付周期大幅缩短；**一个需求整体耗时从数个人日缩到约一个人日**；**AI 代码行占比从个位数升到八成以上**。

**证据边界要说清**：无本体 vs 有本体的逐维分数**以图呈现，正文只给了定性描述**（「字段提升最明显」「业务规则表面 +1 分」），没有绝对准确率、没有 case 数、没有置信区间；「提升数倍」「八成以上」也是区间性表述。所以这篇的价值在**方法与工程细节**，不在可复现的实验数字。

## 角色重新定义

结论很直接：**模型承接确定性，人专注不确定性**。模型负责可复现、依赖信息检索而非业务判断的环节（逐行编码与语法实现、查历史逻辑与血缘、对齐字段口径、套用既有范式）；人负责需要业务知识输入与价值判断、无法从既有信息推导的环节（定义业务规则、做方案取舍、把关结果质量）。**AI 越强，系统越能把人定义清楚的东西执行好，而定义的精确程度决定产出质量的上限**——省下的时间不是消失的工作量，是从「执行」转移到「定义与判断」。

## 深度分析

### 为什么本体是知识供给侧的修复，而不是又一次模型升级

三类高频错误（选错表、用错字段、口径对不上）共享一个致命特征：SQL 能跑、能返回、不报错，只有错误的数据流进看板——常规测试对这类「静默错误」完全失明。更强的模型也修不了它：换旗舰模型后选表与语法确有提升，但指标口径仍然偏，因为口径是「从未出现在上下文里的业务约定」，模型无法凭空推理从未见过的知识。这把问题从「模型选型」钉死成「知识供给」：瓶颈不在生成能力，而在资深研发脑内的隐性经验无法被 AI 读取。本体的定位因此很克制——不追求通用知识表达，只追求「够用来写对这类 SQL」，与数据库、语义层、知识图谱各管一段、互不越界。

### 三元组设计与三道反幻觉关卡

选择结构化三元组而非自然语言描述，表面是格式偏好，实质是**可校验性**的取舍：一句话规则说不出对应 SQL 哪一段、也说不出有没有过期，无法进入任何自动验证流程；写成 `condition_sql + action_sql` 并绑定 `source_sql_hash` 与 `evidence_sql_node` 后，每条规则都能与生产代码的分支逐条对齐，校验才有了锚点。三道关（对指纹、回溯 SQL、查格式）正是建立在这个锚点上的反幻觉闭环：抹平无语义差异后算指纹，保证「同一人写版与模型抽版指纹必然一致」；回溯找不到落脚分支的规则判定为模型编造、直接删除。这套设计的深层含义是：**LLM 抽取的产物默认不可信，可信必须由确定性的程序逻辑事后构造**——指纹比对与分支回溯都不依赖模型自评，幻觉被挡在落库之前。

### 召回哲学：给材料，不给硬规则

上千条规则不能全塞进上下文——物理容量与有效容量是两回事，塞满无关信息的长上下文可能不如精心裁剪的短上下文，这是注意力稀释问题；七路并行召回对应渐进式披露，且召回的规则「恰好是本需求最容易踩坑的地方」。更值得记住的是那个踩坑换来的反转：早期把规则写成必须遵守的指令，模型从「聪明的 AI 工具」退化成「蠢笨的规则执行器」，遇到规则没覆盖的情况就不会推理了，质量不升反降。解法是把定位从「约束」改成「供给」：本体只负责把该看的证据找全，用不用交给模型判断——与其堵错误出口，不如打开正确入口。同时召回内部是确定性程序逻辑，同一需求跑多少次结果一致，保证可复现性。

### 反馈飞轮与五维加权评测：让知识资产对抗老化

静态知识库一定老化——代码重构了知识没跟上、口径变了规则还是旧的。三条反馈链路（研发真实 diff、评测集扣分归因、线上使用日志）把使用中的修正持续回注，全部经人工确认后写回，自动化与人工把关的边界划在「知识写入」这一处。评测与之咬合：业务规则独占 40 分，因为它既是 AI 最薄弱环节、也是本体价值最集中处；两条防作弊硬规则（禁读 GT SQL、只读指定版本本体）保证版本间可比；五层递进检测不通过时自动归因层级，结果回流飞轮形成「生成 → 评测 → 归因 → 修正」闭环。评测集本身靠定时抓取 + LLM 自动分类持续扩充；跨平台资产标准化（Turtle / JSON / Markdown + 薄入口）则保证换工具不换知识——知识沉淀为团队资产而非某个工具的附属品。

## 实践启示

1. **先判断错误类型再选修法**：「能跑但不对」的静默错误，加测试、换模型都无效，唯一解法是把缺失的业务知识变成 AI 可读的资产——先问模型需要的知识是否根本不在上下文里。
2. **知识抽取的产物必须自带取证锚点**：让 LLM 抽知识时要求结构化输出并绑定来源指纹与生产位置——不能回溯到原始出处的规则无法校验也无法维护，应视为编造删除。
3. **知识库定位为材料供给而非硬约束**：强制模型遵守规则会让它丧失规则之外的推理能力；正确姿势是把相关证据召回找全，判断权留给模型，且召回逻辑要确定性、可复现。
4. **知识资产要设计回注链路，否则建完即老化**：从真实 diff、评测扣分归因、线上日志持续收集修正，经人工确认写回；人工只把守「写入」关口，其余全自动。
5. **评测权重压在价值最集中的维度上**：把评测火力对准 Agent 最薄弱、知识资产贡献最大的环节，并配防作弊硬规则保证版本可比。
6. **知识资产与工具解耦**：资产用开放格式标准化存储，平台只留薄入口读取，才能「换工具不换知识」，避免知识被锁死在某个工具的私有格式里。
