# 个人分身的日常运转：共享仓库 + live 状态 + 四层记忆，与「洗澡时刻」

> 📊 Level ⭐⭐⭐ | 17.5KB

## 核心命题：分身不是更强的模型，是一套能接续的工作环境

腾讯游戏数据团队负责人 spike 的自述起点很朴素：想到什么，就找当时顺手的分身聊一下——在电脑前可以深入讨论、查材料、改文件、跑实验；离开电脑就从手机上的企微/Htalk 继续。**很多随手聊出来的内容，是正式文档里不会留下的背景和取舍**（刚开完会为什么改主意、哪句话让人起疑问），等回到某台电脑重新讲一遍，往往只剩一个很简略的结论。

所以这套系统的设计目标不是"让 AI 更聪明"，而是**让它随时能用、能接着之前的事情往下做**：共享资料与近期记录帮助接续工作，而各个分身仍保有自己的会话与运行状态。后半句是全文的难点——共享与隔离必须同时成立。

## 两个案例：分身如何把"没连起来的想法"接上

**案例一（跨角色 context）。** 9 月中旬作者口述当天几个讨论（没开会也没录音），其中一个问题是"怎么让用 AI 更深入的同学带动其他人"，类比游戏里升级快的人带动团队。同一天经分团队同步了他们的实践：把数据服务 Agent 挂载在内部 HTalk，做出 WorkBuddy 专家并接进用户自己的 WorkBuddy——业务同学在工作流里提需求，需求进入一个有经分同学和数据 Agent 的企微群，中间补背景、确认口径，完成后把结果拿回去继续用。作者当时关注的是"把散在几处的 context 连起来了"，**分身读完后提醒：这个案例本身就是他在思考的"传染机制"的一种具体实现**——熟练者把知识、工具与处理方法建设进 Agent，其他人不必先学会整套建设方法、不必学新工具，就能在自己的工作里先用上。于是问题往前推了一步：带动别人除了"把方法教给他"，还可以"让他无痛先用上已经建设好的能力"；产品要支持的事也更具体——熟练者能否方便地交出能力、使用者能否在自己的工作里用起来、出问题能否找到人、反馈能否回到维护者。

**案例二（想法直接进实验）。** 作者关注 Jev 模型能否帮他判断工作群消息（哪些需要关注、哪些可让 Agent 准备、哪些应等已有负责人）。他把 Jev 小模型在本机跑起来，让 cb-a 分身结合背景经 HTalk 读消息、整理样本、写调用脚本、跑几轮测试，再把有分歧的地方拿出来看：**小模型给候选判断，分身组织实验与检查结果，人校准与实际工作有关的取舍**。第一轮拉到三条消息，反馈各不相同——问方案落地情况时对方说"已经在用"，而作者想了解的是具体怎么用、效果如何（只归为"知道了"没接住意图）；有人报问题且已明确负责人，此时应让负责人处理，Agent 不必再替作者接一遍；请同事比较两份材料、对方回"好的"，值得记住的是**他已承接但还没反馈结果，不能把这句"好的"当成事情完成**。调整判断选项与示例后有些改善、有些仍不稳定，**甚至只调整候选项排列顺序也会影响部分结果**——还没到可放心自动处理的程度，但这轮工作让"理解我的 bias"落到可操作的定义上：它要知道这件事当前到哪一步、我是什么角色、谁已负责、我希望它补的那一步是什么。"主动一点"太宽，真实工作里既有该主动了解的，也有该记住等待的。

## 工作环境：仓库承载资料，权限决定取数

分身工作的地方本身就放着持续积累的资料，现在主要是一个仓库：背景、当前关注、过去的讨论、会议记录、外部材料，以及做过的实验与产物。工作群信息通过 HTalk **按权限**去取；环境里还有文件、代码执行与其他工具能力，具体能做什么取决于那个环境接了什么。因此"看看这个"有时是回去找原文，有时是对照几次讨论看判断怎么变了，有时是继续动手验证——**人不必每次先把材料整理好再一段段复制**。

## 四层记忆：稳定背景 / 当前推进 / 完整历史 / 按需索引

资料放进去不等于能用好。作者踩过的坑是"把所有重要的东西都让它读一遍"——内容变多后默认带进去的东西互相干扰，**旧重点压住新问题**。现在的处理是分层：相对稳定的背景与取舍、当前正在推进的事、完整的历史材料各有位置；近期进度及时留下，旧材料通过索引按需找，需要核对再回原文；**每次默认读的内容要控制，历史细节仍然保留**。

同一条原则也适用于"结论"：只留下"最后决定做 A"，下一次它很容易理解成"我一直偏好 A"，而当时可能只是资源不够、或另一个方案的前提还没验证。所以作者要求**把为什么这样选、讨论过什么别的办法、后来哪里改了也尽量留下**——条件变了才有机会重新判断。

分身的调参同样分层：早期"回答不满意就加一条要求"（不要过度赞同、不要给空泛建议、不要回避矛盾），结果它越来越小心、遇到新问题仍不会取舍；后来拆成——**背景与当前重点放 USER、冲突时更在意什么放 SOUL、文件和动作规则放操作规则、某类任务怎么做单独整理成 SOP/Skill**。出问题时先让它说清"刚才怎么理解我的目标、差异在哪"，再决定补背景还是改长期规则。作者的判据是一句工程口径：**当场改对一句话，和下次遇到类似问题能做对，是两件事**——所以要回到后续真实工作里看，这也是他愿意花时间解释"为什么"的原因。

## 多设备多分身：路径、版本、会话三层坑

- **路径不统一**：两台电脑用同一仓库，后来接进带企微/微信入口的 Claw——两边都说"记下来了"，结果一个写在工具自己的目录、另一个写在仓库的 memory 目录，双方根本没在读同一份东西，最后才把路径统一并写进操作约定。
- **版本不一致**：增加 AnyDev 云端分身减少对某台电脑在线的依赖，同步时出现过"新文件传过去了、已有记录没及时更新"——看起来两边都有资料，实际读到的版本不一样。
- **会话隔离**：即使读同一份仓库，两个分身各有自己的 Session——"刚才为什么否定一个方案、哪个问题还在犹豫"如果只留在当前会话，另一个分身未必知道。

对策是给"近期状态"单开一层：仓库里的 **live** 文件记录刚处理了什么、有哪些变化、哪里还没结束，需要时再回到完整笔记与原始材料；另一个分身接手时就有地方找线索；需要定向交接的留在各自收件箱。并发写的约定随之出现：**谁写自己的近期记录、谁维护共同文件、追加前先看最新内容、保留写入来源**；尤其"还在讨论的推断，不能因为被写进记忆就变成我已确认的结论"。

## 「洗澡时刻」：一句 prompt 触发的关系发现

人有洗澡、散步时把没连起来的事想通的时刻，作者把这个模式交给分身：先放下明确任务，看最近这些事情之间有没有自己没注意到的联系。前提是"得有东西可看"——日常积累（工作讨论、会议记录、随手想到的问题、一起做事时的补充与纠正，尤其**没想完的事要留下当时为什么卡住、有哪些不同考虑**）+ 接入的 RSS 信息源（AI 工程、产品、商业、组织管理，**也有与作者观点不太一样的作者**；自动抓取后分身先筛一轮，留来源、摘要与"为什么可能值得关注"）。两类材料处理方式不同：外部文章提炼观点、保留出处与适用背景；自己的思考更在意保留**推导过程**，只记结论后面就不知道当时为什么那么想。

说一句"洗澡时刻"，它就沿最近的工作、当前关注与未完成的问题回看更早记录，也可把外部材料并置：两件看起来无关的事是否遇到同一种问题、最近的决定与之前坚持的判断是否矛盾、新案例会不会改变某个没验证的前提。输出是先给几个观察并说明**为什么想到这个联系**，人再挑有意思的继续追；有些是硬凑的，有些追问几轮才发现值得认真想。一次典型的产出是自我诊断：回看几周讨论后它怀疑——**"我们是不是太习惯用同一套框架解释新材料了"**，每看到新产品/文章/管理案例最后都归到原来那几个判断，看起来理解越来越通，但有没有不同的东西被忽略？这条提醒同样适用于 RSS：如果每篇都被解释成"又验证了原来的想法"，就还是绕回熟悉的框架。讨论完有价值的内容整理下来，保留从哪些材料想到这里、中间怎么推、人补充或否定了什么；**没想清楚的明确留作待讨论，不急着变成长期结论**。作者称它是"分身理解我的 bias 的最好实现，因为 prompt 就是一句'洗澡时刻'"。

## 多分身的价值与成本

几个分身参与过的讨论、模型与运行环境不完全一样，会给出不同解释；作者把一个分身意见拿给另一个看，比较分歧在哪。有一次把"不了解我"拆开：有的是不知道这件事刚推进到哪、有的是旧资料没更新、还有的才是对自己的取舍理解不够——分清楚才知道该补状态、更新记录，还是拿具体问题继续校准。但同时要防"共识假象"：**几个 Agent 都赞同，也可能是读了同一份有问题的摘要**；他们就遇到过还在讨论的推断被提前写成结论，另一个分身再读到就当成确定前提往下推，前面那些来源与确认状态的约定正是防这个。结论也克制：多个分身有额外同步与维护成本，**先有一个能持续参与真实工作、接受纠正、接着上次往下做的 Agent，就已经可以探索很多事情**。

## 深度分析

### 为什么"live"是必要的一层，而不是记忆的冗余

长期记忆解决"我是谁、我怎么想"，会话解决"这次在干什么"，两者之间缺一层"**这件事目前到哪了**"。session 是私有的、随设备与入口分裂；把近期状态写进共享仓库，等于把"接续点"从会话里提取成可被任何分身读取的事实。没有这一层，换设备/换工具的成本不是"少一点背景"，而是**重新建立整条推理链**——这也解释了作者的判断：入口方便与积累充分会相互强化，越方便继续聊，人越愿意把刚发生的事交出去，背景越厚，下一次越容易被理解。

### 写入来源与"推断不得升格为结论"：并发写的最小协议

多个 Agent 改同一份文件，与多人协作的冲突模式同构，但多了一种更隐蔽的失败：**推断被写进记忆后获得事实的地位**。作者的约定其实是三条最小协议——谁写自己的区域、追加前读最新、保留写入来源；再加一条语义约束：讨论中的推断必须带"待讨论"状态。这不是流程洁癖，而是防止错误沿分身网络指数扩散：一个分身把未确认前提当事实，另一个再据此推理，第三轮就没人能追溯它从哪来。

### 为什么"洗澡时刻"能成立：bias 的可执行化

多数"更懂我"的实现停留在让模型读更多资料，结果是旧重点压住新问题。这里的关键设计有三条：①**输入是"未完成的问题"而不是结论**（保留当时为什么卡住、有哪些替代考虑）；②**任务定义是"找联系"而不是"给建议"**（所以它能提出"我们在用同一套框架解释一切"这种元层观察）；③**输出必须带理由**（为什么想到这个联系），人才有得挑。三者合起来把"理解 bias"从形容词变成一句可执行的指令——这正是作者说"prompt 就是一句洗澡时刻"的含义。

### 判断带宽：人参与的是取舍，不是过程

从 Jev 实验可以看出分工的边界：读群聊、选样本、写脚本、保存返回、检查错例都由分身完成，人只参与"想验证什么、哪些判断不符合意图、结果是否足以支持下一步"。作者自己的说法是把精力放在有分歧、需要取舍、或出现新东西的地方。这与"每步都要人确认"的路线相反，但它成立的前提很硬：**分身必须真的懂背景**（仓库 + 权限取数 + live 状态），否则人无法只靠取舍就校正方向。

### 单分身优先：多 Agent 的边际收益被同步成本吃掉

多分身能提供交叉验证（不同模型/环境给出不同解释），但同步成本是三项叠加：路径、版本、会话。作者的实测结论是**先把单分身做到能持续参与真实工作、接受纠正、接着上次往下做**，遇到限制再建设。这条经验对"多 Agent 协作"热潮是个反向校准：更多 Agent 不自动带来更多判断带宽，只有在共享事实层（仓库 + live + 来源约定）稳定之后，第二个分身才开始产生净收益。

## 实践启示

1. **先建接续层，再谈智能**：仓库承载长期资料，`live` 承载"这件事到哪了"，收件箱承载定向交接；三者缺一，换设备就要重建推理链。

2. **记忆按"稳定/当前/历史"分三层**：默认读入量受控、旧材料靠索引按需、核对回原文；只留结论会让下一次误读成"我一直偏好 X"。

3. **保留"为什么"与"替代方案"**：决策理由和当时被否掉的选项，是条件变化后能重新判断的唯一依据。

4. **配置分层**：USER（背景与重点）/ SOUL（冲突时的取舍）/ 操作规则（路径与确认）/ SOP·Skill（某类任务），避免单点要求污染全局。

5. **并发写要留来源与状态**：谁写哪块、追加前读最新、推断标注"待讨论"，防止未确认前提被下游当成事实。

6. **给"没想完的问题"留入口**：一句"洗澡时刻"就能让 Agent 去找联系，输出带理由，人只挑值得追的。

7. **先单分身后多分身**：多 Agent 的交叉验证收益，必须建立在共享事实层稳定之后。
