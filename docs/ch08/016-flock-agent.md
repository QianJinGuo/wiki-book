# 阿里云 Flock 协同空间：一群人、一群 Agent 对一件事负责到底

> 📊 Level ⭐⭐⭐⭐ | 30.4KB

## 阿里云 Flock 协同空间：从 SuperAgent 到「一群人对一件事负责」

> 阿里云云原生郑天先逐行拆了 DeepSeek SuperAgent 的 1.6 万行开源原型（五个代码级设计判断），再讲他们自己的协同空间 Flock。两个系统回答的问题不同：**DSH 回答「一个 Agent 怎样同时做很多事」，Flock 回答「一群人和一群 Agent 怎样对一件事负责到底」**。两边不约而同收敛到同一组结构——任务对象比会话长寿、控制面与执行面分离、模型提议而程序裁决。

## 一、问题的定义：注意力才是上限

一个人同时只能跟进 **3 到 5 个活跃会话**，这是 DSH 团队观察到的经验值。所以那句总结被反复引用：**单任务的上限取决于模型，多任务的上限取决于人的注意力**。Super Agent 的目标一句话：**让人感觉始终只有一个 Agent，而它能同时做很多事**——四个要求：连续（群里说方案 A、代码评论里改成 B，它能接上）、高效（不等上一件做完就接下一件）、主动（自己看环境，该推进就推进，没必要就闭嘴）、持久（一直在线，自己恢复，不会因为你合上电脑就停）。

`[行业对照]` 之前各家各拆一块：Cursor Background Agents 拆掉「要人盯着」（任务变任务列表，但发起与调度还是人）、LangChain Ambient Agents 拆掉「要人发起」（事件驱动，但多任务协调要自搭）、Muse/dots/Grok Bot 这类 Personal Agent 拆掉「要人在线」（偏个人，团队责任不是重点）。DSH 用 **Router + Worker** 把这些一起解，留下长程记忆、组织边界、安全三个开放问题。

## 二、DSH 的原理层：五组取舍

**双层架构解决「连续 vs 吞吐」**：全塞一个 Session 最连续，但单个 ReAct 循环只能串行、互相打断；每件事开新 Session 能并发，但彼此不知道、还各自跟你说话。拆开——**Router 负责连续性**（所有对外沟通与任务间协调都过它，是全局序点与记忆；甚至不给它 Bash，用轻模型就够），**Worker 负责并发**（每任务一个隔离 Session，配最强模型）。**这和 Agent Team 的 Team Lead 不同**：Team Lead 要钻进任务内部拆解，Router 只管任务之间的关系；Worker 内部再套 Subagent 对 Router 是透明的。

**事件驱动用 Fast/Slow 双路径**：真实环境的事件流是「高噪音、低触发率」——DSH 实验负载里约 **300 条消息只有约 20 条是工作请求**。所以先规则过滤（哪些群、哪些人重点监听），模型放在漏斗最后。**Thread + 订阅直通**是这里的巧劲：同一 PR 或同一群话题下的一串事件是一条 Thread，Worker 接单后订阅它，后续事件由程序直送、不再经过 Router；Worker 与 Thread 多对多，两个 Worker 订阅同一 PR 就能看到彼此动作（这也回答了「Worker 之间不沟通不会打架吗」）。消融显示：去掉直通，任务完成时间几乎不变，但 **Router 多做约 30% 的决定、读缓存 Token 多约 37%**——**它省的是 Router 负载，不是任务时间**。

**上下文当 Cache 管**：借编译优化两个词——**Inline**（近期很可能用到的直接放窗口，省一次工具调用）、**Spill**（超预算或低频的留在窗口外，只留摘要或引用），放什么由局部性决定（一条 IM 消息的前后相邻、一条评论所在的讨论串）。规则一致地套到 Trigger / Thread / Worker Session 上，它们就构成引用图：每个对象内联下一跳对象的 ID，模型顺引用逐跳展开，就是**链式召回**。原文承认边界：**主要解决近期任务，跨月之后长程记忆仍是瓶颈**。

**全双工 ≠ 能插话**：插话解决「消息能不能进来」，全双工还要解决「消息要等多久才被处理」。模型循环是「推理—调工具—等结果—再推理」，如果正等一个同步工具，你说「先停」也可能要等 20 分钟测试跑完。DSH 把耗时命令改成异步 start/stop：调用立即返回「已启动」，结果作为新事件投递回来，推理步因此一直很短。**原型里 Worker 前台命令超过 5 秒自动转后台**，理由正是让下一步能收到新消息。

**计算 / 状态 / 环境三层分离**：Agent Loop 进无状态容器、Session 进数据库（容器重启不影响进度）；而**环境留在原地**——本机有未提交修改、私有凭据、内网依赖，云端重建成本高且易漏，于是只装一个不保存会话状态的轻量 daemon 负责执行与回传，这就是通用 **BYOM（Bring Your Own Machine）**。代价是依赖设备在线（离线时那一步停下，但状态在云端不丢）。Cursor/Codex 走的是另一条路：云上重建环境，好处是不依赖你的电脑、可并行隔离，代价是复刻成本——**两种做法换的东西不同，没有绝对好坏**。

还有一个常被忽略的点：**Agent 的故障常常不是进程挂了，而是进程好好的、模型在原地打转**，存活探测发现不了。所以 DSH 在系统外放了一个**独立的 Watchdog 会话**，定时判断每个 Worker 有没有实质进展、方向有没有偏。

`[实验结果要这样读]` 原文「快了近一倍」容易被误读：

| 方案 | P50（分钟） | P95（分钟） | 读缓存 Token |
|---|---|---|---|
| Super Agent | 12.4 | 15.7 | 2323 万（3.8×） |
| 单会话，提示词要求优先委派 | 13.8 | 29.0 | 1082 万（1.8×） |
| 单会话，提示词保持中性 | 20.4 | 29.5 | 605 万（基准） |

只改一句提示词，一半任务只比 Super Agent 慢 11%，Token 还不到一半。**那架构买到的是什么？是稳定**——模型总有一次判断「这活很小我自己干」，这一次就把最慢任务拖到 29 分钟，这种随机性靠提示词消不掉；代价是 Token 翻倍多。而且**这是合成负载**（编码工作用一个只耗时间的工具代替），测的是调度能力，不能直接推出真实团队会快这么多。

## 三、代码层：五个设计判断

原型约 1.6 万行，围绕四个概念组织：**Trigger/Thread**（世界上发生了什么、哪些属于同一回事）、**Ticket**（一份获准开工的工作，最稳定的东西——会话可断、执行者可换，Ticket 不变）、**Policy**（团队规矩，有版本）、**Mandate**（这份 Ticket 凭什么可以做：谁要求、范围多大、依据哪版规则）。

**为什么 Ticket 与 Mandate 要分开**：一个修复已合并、Ticket 结束；一周后有人在该 PR 下说「这里还有个问题」。重走评估太慢，直接开工可能越权。有了独立 Mandate，就可以沿用当时的授权恢复工作，但先对照最新规则检查它是否仍有效。**一件工作能不能继续，和它现在是什么状态，是两个问题**。

**一条消息怎么变成工作**（整条链路只有一步调用模型）：① 进门登记——不管有没有用先落库、重复只算一次（Append Only，重启不重放，事后可查）；② 查 owner——人的后续消息若落在某 Ticket 的 Thread 上，直接交给对应 Worker，Router 不介入；③ 门禁——用代码判断发消息的人有没有资格；④ 才用模型；⑤ 开单时 Ticket、Mandate、订阅、确认回复**一次性生成**，不出现「单开了但没人知道」的中间态。

1. **模型提议，程序裁决**。系统有一个确定性核心，是 Ticket 状态的唯一写入者；Router 模型「接单」本质只是提交申请，核心校验权限、规则、参数与当前状态，不合格就拒。**模型错了或被注入，最坏只是提交了一个被拒绝的申请**。所以「Router 不许干活」不只是提示词，长时间等待这类操作在代码层就被拒。
2. **先记账，再动手**。把要做的外部动作也当数据，与状态改动记在同一笔账里，提交后由后台逐条执行（**Outbox 模式**）；启动 Worker、投递消息、发 IM 全走这条路。模型工作无法完全重放，所以重启后 Worker 会收到提示：先看代码目录与 PR 实际状态，再决定要不要重做。
3. **外部文本永远只是数据**。整天读群聊和评论，都可能带恶意指令，所以有明确优先级，**外部文本在最底层**。细节：Router 转交任务时备注**最多 30 个词**，且不许添加实现计划与验收标准，Worker 必须自己读原始消息——**这是在防「传话失真」**，和人类团队一样，转述越多走样越严重。
4. **主动能力要能灰度**。把「判断」与「执行」分开：新规则默认试运行，模型照常判断但只记下「如果放开我会接这个单」，不真开工；团队看记录觉得准了再放开。而且判断必须针对每条规则逐一给结论，接单要引用消息原文作证据。
5. **人的优先级最高**。三个落点：状态按「在等谁」算，等人的排最前；并发名额留一个给人（Agent 全忙时人的消息仍能唤醒已有工作）；**区分「送到了」和「读到了」**——消息进入 Worker 会话不算数，真正进入模型历史才算；Ticket 结束时还没读到的人类消息会退回重新评估（「等一下，先别合，方案有变」必须被正确处理）。

**原型边界（作者自陈）**：状态在单机数据库、一个部署对应一个仓库一套账号、Worker 以运维者系统身份运行（文档明说命令包装不是安全边界）；而且**文章提到的 Watchdog 与投机执行，作者在代码、文档、提示词里都没搜到**；完成判定主要靠外部事实（PR 合并），换到业务工作就不够。

## 四、作者的取舍：Router 不是必须的

**数字员工四级判断**（作者个人观点）：① 你需要每次重新讲背景吗（真正的同事不用，所以不该有「新建会话」这个概念）；② 你走开之后它还在做吗；③ 没人催的时候它会动吗；④ 做错了，能查清楚是谁、为什么吗（企业里没有责任与审计的员工没法用）。四条全过才是员工，形态上必然是 Always-on。

**Router 可以拆**：它其实打包了三份工作——对人的前台交互、判断路由、全局记忆，原文自己也说「部分逻辑未必需要调用 LLM」。Flock 的做法是：**前台就是 Channel 本身**（人和 Agent 看同一条时间线）、**唤醒由程序按任务状态计算**、**判断交给 Coordinator**（Channel 里的普通成员，职责是拆解、指派、跟踪、汇总）、**记忆放 Quest 和文件**。得失很清楚：得到的是协调者不用常驻、上下文不膨胀、权限边界更清；**失去的是常驻 Router 的连续感与「积压事件下一轮合并处理」的批处理红利**——「我们现在基本是一条唤醒一次执行，这恰恰是要向 DSH 学的地方」。

**中心化为什么在 Agent 这里反而对**：人类组织警惕中心化，前提是**人的带宽很窄**，所以必须分层压缩信息；Agent 没有这个约束。DSH 压测有个反直觉结果：**事件从每分钟 1 条涨到 40 条，单个决定的平均推理时间反而从 6.4 秒降到 1.6 秒**（Router 思考时积压的事件下一轮合并处理）。启发：**不要把人类组织的形态直接搬到 Agent 身上**——层级、周会、逐级汇报是为人的带宽发明的，很多多 Agent 系统照着公司组织架构设计角色，可能恰恰学错了地方。

但**瓶颈只是换了地方**，作者列了四个，并对照两边解法：**上下文容量**（DSH 靠直通 + 链式召回并承认跨月是瓶颈；Flock 靠协调者不常驻、按 Channel 切分、用时才查）、**判断质量**（DSH 只在消息明确指向某 Ticket 时才归入；Flock 是 @ 只算沟通、正式建单才算委派）、**成本**（DSH 接受 3.8 倍读缓存；Flock 有事才调模型但还没做合并唤醒）、**爆炸半径**（DSH 靠外部文本只算数据 + 代码强制权限；Flock 按 Channel 隔离、跨 Channel 需双方授权）。切得越细吞吐越高、连续性越低，「在全局记忆问题被解决之前，这一权衡始终存在」。

**中心只该关心结果**：中心一旦开始关心「怎么做」，就要读细节、做规划，立刻退化成很重的 Team Lead，瓶颈又回来。Flock 的任务只定义目标、验收标准、责任人与依赖，**没有「实现计划」这一项**；协调者拆完就结束这轮，不轮询，子任务全结束由平台叫醒。DSH 更极端：Router 连验收标准都不许写。差别在于——**DSH 可以不写，因为研发有 PR/CI 这些客观事实；Flock 必须写，因为很多业务工作没有客观完成信号，验收标准就是任务的接口**。

**切分边界**：2025 年 6 月 Anthropic 公开多 Agent Research 系统（主 Agent 拆、子 Agent 并行搜索），几乎同时 Cognition 发《Don't Build Multi-Agents》，用 Flappy Bird 举例——一个子 Agent 做了超级玛丽风格背景、另一个做了对不上的鸟，因为每个行动都带隐含决策而彼此看不到。作者的结论不是「该不该用多 Agent」，而是**只有能被独立验收的工作才能分出去**。

## 五、Flock：控制面 / 执行面分离

**最重要的结构是控制面与执行面分离**：控制面是业务事实（谁负责、做到哪、结果是哪一版），执行面只管把这一轮跑完（模型调用、工具执行、断点恢复）。执行可以失败、重来、换人，**责任与进度都在控制面不会丢**。这和 DSH「Ticket 不跟随会话」是同一个想法，区别是 Flock 把它做成了人也能直接看到和操作的产品。

**产品形态是一张 Channel 网**：每个 Channel 对应一个项目或业务场景，里面有人、协调者和各种 Agent，甚至包括用户电脑上的本地 Qoder；共享一条时间线，上下文与权限默认不出这个空间。跨边界协作不靠「把对方拉进来」，而是**在对方 Channel 建一个任务**，由对方在自己空间执行；还留了个小设计——**同一交互线往返超过上限（默认 6 轮）会被拒绝，并建议合并空间**，因为聊这么多轮很可能是边界划错了。本地 Qoder 对应 DSH 的「把日常机器接进来」，但被做成 Channel 里的一个成员：同一套任务和验收，只是它主动来领任务。

**Sessionless**：不是底层没有会话，而是**会话不再代表身份与任务，只是一次执行的耗材**——「你不会每次找同事说事都先新建一个同事」。规则各不相同且都有原因：聊天要连续所以续接；任务执行每轮尽量新开（**继承旧会话会让上下文跨轮累积**），只有子任务收口回父任务、人工断点重启才续接；**验收每次新建，因为验收者不该带着执行者的上下文，也没有执行权**。用户没有「新建会话」按钮，系统把几个事实算成一个键，键相同就接着聊——其中「谁能看见」是易被忽略的隐私边界：**Channel 换成员，新对话自动切新会话，新人读不到之前上下文**（单实例的 DSH 不需要考虑，多人多 Agent 的 Channel 必须考虑）。9 月还加了血缘表，节点可以是会话或任务，每条边记录谁触发，一次查询看清「@ 一下之后长出了什么」。

**Quest：比会话活得久的东西**。建表注释只有三个字——**责任状**：可分配、可追踪、可验收，有目标、验收标准与唯一责任人（对应 DSH 的 Ticket）。最关键的状态是「**待验收**」：**Agent 跑成功不等于任务完成**，只代表提交了一版结果，要由人或指定验收 Agent 认可；不满意打回重做，上一版留着。**在企业里，「做完了」必须有人认**。

**任务链不是规划出来的，是长出来的**：不要求先画流程图，每个动作只记录自己和谁有关。三条机制——执行时新建任务默认是当前任务的子任务；建时写明依赖谁，上游完成才唤醒下游；子任务全结束，平台唤醒父任务并把已验收结果带给它汇总。「执行全景」就是把这些关系展开成 DAG，系统并没有单独维护流程图。**但不是放任**：Agent 说不清新任务属于谁，平台会拒绝创建，否则游离任务会让父任务永远等不到收口。

**Quest 链就是引用图**：DSH 靠事件之间的引用做链式召回，而任务链的边是**工作关系，比事件关系更稳定**。一个两周前的问题，线索在第二版批注、证据在上游失败明细、原因在业务人员一句答复里——Agent 不必记住，只要沿工作关系走过去。

**主动推进的朴素实现**：任务状态存在账本里，状态一变就算出该叫醒谁，有事才调用模型；一次执行的产出变成下一次执行的触发。**踩过最大的坑是「互相唤醒」**——预发环境一个「组织一次报数」的任务，理想 3 次执行，实际跑了 10 多次、产生 8 个执行实例，还有 Agent @ 了自己。根因不是模型笨，而是平台把「被点名」和「任务落到头上」放进同一条链路：被 @ 的 Agent 拿到的指令是「完成后必须提交交付物」，于是它认真开始拆任务发通知。修法是把语义分开——**@ 是沟通，Quest 才是委派**：被 @ 只回应、不领执行权，要干活先建任务；再加抄送不唤醒、Agent 间连续唤醒默认最多 3 次、人一介入就清零。**平台的硬约束比提示词可靠**——和 DSH 结论一致。

**跨会话记忆：从推到拉**。早期每次唤醒都拼成员名单、今天的消息、最近动态，结果上下文越来越胖还全是废话；后来全删了，改成按需检索（与 DSH 的 Inline/Spill 同一结论，**是被线上问题逼过去的**）。工具层留了细节：**长消息不再直接截断，而是保留头尾、中间折叠并标明怎么取回**——因为 Agent 每次唤醒都是全新的，检索是它了解过去的唯一通路，截断会让它把残缺内容当成全部。再往前是 **MDC（Meta-Dance-Context）** 思路：**不要让 Agent 记住，让 Agent 能找到**——记忆不放在模型脑子里、也不靠无限长会话，而是放在一个可以自己翻阅的文件接口后面，每次唤醒编译一个干净窗口，需要什么再去读；结果可审计、可引用、换模型也带得走。

## 六、两个趋势

**架构在趋同，因为约束把解空间压窄了**：模型已能把单个任务做完，瓶颈变成人的注意力 → 需要统一对外入口；任务越长越多 → 需要隔离执行单元；任务要比会话活得久 → 需要可持久化可追踪的任务对象。问题定义清楚，答案就收敛——「就像数据库最终都走向预写日志，操作系统最终都走向进程和调度器」。

**Agent 正在回到传统工程**：当 Agent 从「一次对话」变成「长期运行的进程」，它必须面对分布式系统的老问题——进程会崩、机器会离线、消息会重复、副作用不能执行两次。于是我们看到越来越多数据库与分布式的经典手段：预写日志、Outbox、防重复领取的租约、可回放的事件记录。**模型是系统里唯一不确定的部件，工程的职责是用确定性的外壳把它包住**；可靠性不只取决于模型能不能做对，还取决于做错或中断时系统能不能恢复。一句话：**Agent 会越来越像一个系统工程，模型是 CPU，Harness 是操作系统和数据库**。

## 深度分析

### 「注意力才是上限」是一个架构规格，不是修辞

「单任务的上限取决于模型，多任务的上限取决于人的注意力」——这个观察的价值在于把瓶颈定位到模型之外：一个人只能同时跟进 3–5 个活跃会话，卡住的是记性、等待与发起，不是推理能力。于是目标被改写成「让人感觉始终只有一个 Agent，而它能同时做很多事」，连续、高效、主动、持久四个要求逐一对着人的四个卡点。此前的方案各自只拆掉一个瓶颈：Cursor 后台面板解决「要人盯着」，Ambient Agents 拆「要人发起」，Personal Agent 拆「要人在线」，但发起和调度仍以不同形态压在人身上；Router+Worker 第一个把会话降级成「系统的实现细节」。问题从「更强的模型」换成「更少必须由人完成的协调」，后面的一切结构都从这里长出来。

### 双层架构、事件漏斗、窗口当缓存：模型调用被当成稀缺资源

连续性和吞吐量的矛盾被拆到两层分别解决：Router 是全局序点和记忆，管所有对人的沟通与任务间协调，可以不配 Bash、用较轻的模型；Worker 每任务一个隔离 Session，配最强模型，有结论才汇报。事件侧是一道漏斗：实验负载里约 300 条消息只有约 20 条是工作请求，Fast Path 就是规则，Slow Path 才是模型——大部分消息永远到不了模型。订阅直通进一步省的是中心而非任务：消融实验中去掉直通后任务完成时间几乎不变，但 Router 多做约 30% 的决定、读缓存 Token 多约 37%。上下文侧把窗口当 Cache 管：Inline 放近期高局部性信息，Spill 把低频内容留在窗外只留引用，模型沿 Trigger、Thread、Worker Session 构成的引用图逐跳做链式召回；作者坦白这只解决近期任务，跨月后长程记忆仍是瓶颈。Flock 在两点上独立收敛：任务链本身就是一张引用图，「边是工作关系，比事件关系更稳定」；跨会话记忆也被线上问题逼到与 Inline/Spill 相同的「从推到拉」结论。

### 全双工、三分离与 Sessionless：会话从身份降级为耗材

全双工常被误读成 Codex 式插话。插话只解决「消息能不能进来」，全双工还要解决「消息要等多久才被处理」：循环等一个同步工具时，插进来的「先停」可能要等 20 分钟才被看到。DSH 把耗时命令改成异步 start/stop，前台命令超过 5 秒自动转后台，推理步保持很短——模型仍是一步一步跑的，并没有同时做两件事。更结构化的是计算、状态、环境三分离：Agent Loop 放云端无状态容器，Session 存数据库，重启替换不丢进度；离不开本机的操作经轻量 daemon 下发回原机器执行，代价是依赖设备在线；独立的 Watchdog 会话补上存活探测的盲区——进程活得好好的、模型却在原地打转，这种故障只有判断「有没有实质进展」才能发现。Flock 把同一思路推到产品层：控制面只存业务事实——谁负责、做到哪了、结果是哪一版，执行面只管把这一轮跑完，执行可以失败、重来、换人而责任和进度不丢；Sessionless 让会话不再代表身份和任务，只是一次执行的耗材，对话续接、任务每轮开新、验收每次新建由系统算出而非用户选择；真正稳定的是 Quest，建表注释只有三个字「责任状」，而「待验收」状态明确了 Agent 跑成功不等于任务完成。

### 模型提议、程序裁决：五个代码判断与一次独立收敛

原型最核心的架构决定是「模型提议，程序裁决」：确定性核心是 Ticket 状态唯一的写入者，模型接单只是提交申请，模型错了、被注入了，最坏也只是提交了一个被拒绝的申请。四个配套判断围绕它展开：先记账再动手（Outbox，外部动作与状态改动记入同一笔账，崩溃后没做完的接着做）；外部文本永远只是数据（优先级栈压在最底层，Router 转交备注最多 30 词、不许写实现计划和验收标准，防「传话失真」）；主动能力要能灰度（判断与执行分离，试运行只记「如果放开我会接这个单」，接单必须引用消息原文作证据）；人的优先级最高（状态按「在等谁」排，并发名额留一个给人，区分「送到了」和「读到了」）。作者也坦白原型边界：单机数据库、一个部署只对应一个仓库和一套账号、命令包装不是安全边界、Watchdog 与投机执行在代码里搜不到。Flock 在互相唤醒事故后得出同一句话：@ 是沟通，Quest 才是委派，平台的硬约束比提示词可靠。两个系统没有互相借鉴，是约束把解空间压窄了：任务要比会话活得久，就需要可持久化可追踪的任务对象（Ticket/Quest）；中心要薄，就只能关心结果不关心怎么做。当两套独立实现长出同样的骨骼，说明 Agent 工程正在成熟为系统工程：模型是 CPU，Harness 是操作系统和数据库，可靠性来自确定性外壳，而不是更强的模型。

## 实践启示

1. **先定位上限，再选架构。** 单任务质量不够就投模型，多任务跟进不过来就投调度和 Harness；用「同时几个活跃会话、卡在等谁」度量瓶颈位置，不要默认堆模型能力。
2. **把模型调用当稀缺资源做漏斗。** 规则先消化高噪音事件流（300 条里约 20 条才值得问模型），模型放漏斗最后；为跟进消息建订阅直通式旁路，并记住它省的是中心负载不是任务时间，度量别选错。
3. **状态进账本，动作排队执行。** 让确定性核心做状态唯一写入者，模型输出一律按申请校验；外部动作与状态改动记入同一笔账（Outbox），重启后没做完的接着做，模型不能重放的先核对实际状态再决定要不要重做。
4. **外部文本只是数据，转述要最小化。** 优先级栈把外部内容压到最底层；任务转交限制备注长度、禁止夹带实现计划，让执行者回到原始消息——防提示注入和传话失真都要靠结构，不靠提示词。
5. **主动能力必须灰度上线。** 新规则默认试运行：照常判断、只记录不执行，接单引用原文作证据，团队确认判断准了再放开执行；一个乱提 PR 的 Agent 很快会被团队关掉。
6. **中心只验收结果，边界划在「能独立验收」处。** 研发有 PR/CI 这类客观信号，可以省验收标准；业务工作必须把验收标准写成任务的接口。@ 只算沟通、建单才是委派，跨空间往返超限就说明边界划错了。
