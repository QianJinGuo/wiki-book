# AI Friendly 架构与可复制的 AI 迁移：淘宝直播搜推 Emeya 重构的三阶段与三层验证

> 📊 Level ⭐⭐⭐⭐ | 28.0KB

## 一句话结论

淘宝直播搜推团队面对数百万行、多框架多分支的历史应用，**没有先写迁移 Skill，而是先把系统改造成"AI 能用"的形状**：统一物料承载公共能力、声明式编排表达场景差异、受约束的流程语义降低理解成本、结构化执行树提供证据；再用人工迁移建立事实与验收基线，最后把经验沉淀成 Skill 让 AI 迁移新场景——单场景周期从 20 人日 → 10 人日 → 3 天。

## 起点：一个仍能运行、却难以持续维护的系统

早期为了缩短"策略从想法到实验"的路径，算法同学直接写 Java UDF、维护图配置、完成实验上线——在当时的约束下这是务实选择：设计与实现之间链路短，独立分支能隔离单次变化，有限工程资源优先保障试验速度。问题出现在业务进入**多场景长期维护期**、且维护责任从分散承担收敛到更小的工程团队之后：实验分支与场景分支长期保留，成了独立的开发/部署/维护单元；不同场景又各用一套框架。**早期缩短单次实验路径的局部最优，转化为跨场景维护的整体成本。**

作者特别澄清：这**不是早期选择错误**，而是原有生产方式依赖的组织规模、团队分工与资产生命周期变了。

### 复杂度不在图的数量，而在复制后的独立演进

梳理线上实际运行版本后发现：同一套流程与能力被复制到不同方案与代码分支，随后因场景需求、参数配置、兼容逻辑而**各自独立演进**。结果是**同名逻辑图可能行为不同，代码分支的最新提交也未必对应线上部署版本**。一次公共能力升级要先确认各运行版本的行为差异，再评估影响、改代码、分别发布与回归。

### 三类问题共同推高长期成本

1. **分支副本化 + 多框架并存**：长期分支各自维护 Java 实现与图配置，公共能力无法沿一个主干演进；新场景习惯复制完整分支；维护者要在不同框架的组件模型、参数规则、执行机制、排障路径间来回切换。
2. **执行模型缺稳定语义与统一生命周期**：自由图擅长表达连接，却不突出业务阶段、主执行路径与职责边界；串行/并行/条件/数据依赖混在拓扑里，读者要沿边逐个查看才能还原流程；每张图独立定义，请求初始化、公共校验、监控上报、资源清理只能逐图接入。
3. **诊断与监控不足且分散**：历史应用缺少与实际执行树对应的完整节点记录，线上异常时日志回答不了"执行过哪些节点、最早在哪失败、原因是什么、耗时是否超限"；各场景自设计字段与入口，排查经验无法复用。

**"增加人员只能缓解局部排期"**——维护成本随分支、图、场景持续增加，无法被公共能力与历史经验的积累摊薄。所以真正要动的不是某个类或某张图，而是**应用生产方式**。

## 为什么局部措施不够，以及为什么不能直接让 AI 接管

加人、局部重构、换框架、补监控、让 AI 分析改写代码——都有价值，但只改善局部。**AI 尤其不能直接接管一个依赖人脑解释的系统**：模型可以读大量代码，但如果真实行为分散在代码分支、图配置、实验参数、动态开关与外部调用中，它首先面对的不是"怎么写新代码"，而是**"哪一份事实才代表线上"**；流程与参数缺稳定契约时，**AI 生成得越快，错误扩散得越快**。

目标因此被重新定义为：建立一套能支撑多场景长期维护的统一生产方式——**公共能力可复用、场景差异显式表达、流程有稳定语义、执行结果可统一验证**。

## Emeya：四层架构与三项取舍

体系由**轻量执行框架 + 编排管理平台**组成，执行框架与宿主平台解耦，负责流程执行、依赖协调、结构化诊断生成；平台负责组件发现、可视化编排、版本关联与发布治理。四层：

| 层 | 组成 | 职责 |
|---|---|---|
| 物料层 | `AtomicNode`、`ChainNode`（组成 `Chain`） | 细粒度、职责稳定的能力 |
| 编排层 | `Plan`、`Stage`、`ExecutorGroup` | 业务流程与串并行关系 |
| 运行时层 | — | 条件判断、参数传递、并发调度、超时与异常 |
| 诊断与适配层 | `ExecuteRemark` + 扩展点 | 执行树生成、接入日志/监控/宿主 |

三项底座约束：**轻量**（只保留统一模型与执行语义所必需的机制）、**易上手**、**扩展优先**（成熟的配置管理与中间件继续复用，平台差异与业务差异走适配层与扩展点）。

**为什么自研**：现有图执行框架各有侧重，但要同时统一"应用模型 / 场景差异表达 / 流程语义 / 公共生命周期 / 结构化执行信息"并配套平台治理，仍需新建核心抽象与配套能力，还要适配底层模型演进节奏——权衡投入后选择自主维护这一层。

## AI Friendly 的正确定义：四项工程属性

作者明确否定"AI Friendly = 模型能快速生成代码"——代码生成效果受模型版本、提示词、样例数量影响，**只能说明模型能力，不能证明架构适合 AI 长期参与**。真正的判断标准是五个"能否"：

1. AI 能否**只读取与任务相关的局部上下文**；
2. 能否在**有限且稳定的工程语法**内做选择；
3. 能否通过**显式契约**理解数据流；
4. 生成结果能否**被确定性工具检查**；
5. 运行后能否留下**足以定位问题的证据**。

由此，AI Friendly 不是独立功能，而是设计产生的工程属性。这里有一个关键区分：固定流程层级、统一物料、参数契约、`ExecuteRemark` 属于 **Emeya 核心模型**；DSL、Builder、metadata、解析器、校验器是围绕模型建设的 **AI 控制层**。**新体系不替 AI 保证结果正确，它提供的是一组稳定接口，使外部工具能够理解、生成、检查和重跑。**

## 核心设计一：统一物料 + 声明式差异

**从粗粒度 UDF 转向职责稳定的物料**：历史上一个类可能同时做 RPC 请求构造、远程调用、结果解析与业务处理——能快速交付单个需求，却难以被复用；一旦部分逻辑有差异，最省事的做法就是复制类或复制分支。新体系把流程拆成职责清晰的物料：`AtomicNode` 承载独立业务计算，`ChainNode` 承载参数构造/服务调用/结果解析等链式能力，节点通过明确的输入、输出、配置契约参与编排，**不再依赖阅读完整调用链才知道数据从哪来往哪去**。

作者给"细粒度"划了界线——**不是越小越好**，节点粒度需同时满足三条：职责能用一句话说明；输入输出可稳定声明；存在独立测试或跨场景复用价值。**纯为拆而拆只是把代码复杂度转移到编排层。**

**稳定能力进代码，场景差异进编排**：差异通过七种声明表达——选哪些节点、按什么顺序组合、参数如何连接、什么条件下执行、超时多长、并行策略、场景专属配置取值。于是公共能力沿主干一次修改，差异留在可阅读可比较的编排里；新增场景先检索已有物料，判断能否直接/组合复用，**只为真实能力缺口新增代码**。同时明确边界：**统一框架不会自动回收历史分支**，主干开发约束、实验结束合并回收、长尾分支治理仍要靠工程制度——新体系提供的是让治理动作能发生的技术基础。

## 核心设计二：受约束的流程语义 + 统一生命周期

**为什么放弃自由图作主要表达**：自由图表达能力强、天然适合复杂依赖与并发，但**阅读方式不稳定**——同类业务流程可能被画成完全不同的拓扑，主链路与旁路混在一起。团队的取舍很明确：**牺牲一部分自由图的表达上限，换取稳定的阅读范式与可评审的并行边界**；开发者按业务阶段阅读，运行时按并行属性与参数依赖调度——**顺序表达不等于所有任务串行**。

层级是 `Plan → Stage → ExecutorGroup → Node` 自上而下；`Plan`、`Stage` 顺序执行，需要并发时由 `ExecutorGroup` **显式标记**执行方式。

**参数依赖既是运行契约，也是可验证事实**：节点声明输入输出及类型，上下游通过统一 Key 连接。运行时据此协调依赖等待；工具可在执行前检查"输入是否有生产者、类型与配置是否一致、数据依赖是否与执行顺序冲突"。于是参数关系从藏在 `Map`、上下文对象、方法调用里的约定，变成**可枚举、可检查的显式契约**——开发者能看数据来源去向，AI 能依契约生成连接，工具能静态校验。

**公共前后置变成一等能力**：全局前置 `Plan` 与全局后置 `Plan` 由框架统一拼接，公共能力集中维护。价值不止少写配置——它建立了公共治理的控制点：**哪些逻辑必须在所有请求前执行、哪些诊断与清理必须在请求结束时发生**。

## 核心设计三：每次执行留下结构化证据

**日志不是附属能力，而是执行模型的一部分**：若日志完全由业务节点自定，不同场景必然形成不同字段、格式与查询方式——即使"都有日志"，也无法用同一套方法还原执行过程。新体系让每次任务执行生成与实际任务树对应的 `ExecuteRemark` 树：`Plan`、`Stage`、`ExecutorGroup`、`AtomicNode`、`Chain`、`ChainNode` 各层记录名称、状态、耗时、异常与扩展信息（含 `async`、`isProcessorParallel`、`processorName`、`taskType` 等字段）。

这棵树是"统一原料"：日志系统展开为结构化日志、监控聚合节点成功率与耗时、链路平台还原执行拓扑、排查工具定位**第一个失败节点**。**不同场景共用同一模型，查询模板与排查知识才具备复用基础。**

框架只管**产生证据**，不管存储/聚合/大盘/告警：提供两个标准钩子（执行单元完成后处理该层级 Remark、接口完成后处理整条请求 Remark），应用通过这些出口接入既有体系；**钩子执行异常会被记录并隔离，不改变原业务结果**——避免诊断链路反向影响主业务。

## 迁移三阶段：从人工基线到 Skill 复用

新体系建好了，历史应用不会自动迁移。真实行为仍分散在 Java UDF、图配置与实验参数中，**迁移 = 还原旧事实 → 按新模型重建 → 证明新旧等价**。团队没有从"写一个迁移 Skill"开始，而是走三步：

### 阶段一：人工迁移建立事实与验收基线（主播关注页，约 20 人日）

选图结构简单、输出稳定、验证成本可控的场景先做：人工还原旧图、UDF、节点职责与数据依赖，识别实验配置、动态条件与公共前后置行为，再把旧逻辑映射为物料与编排。**目标不是证明人比 AI 可靠，而是建立三类基线**——哪些旧行为必须保留、旧概念如何映射到新体系、什么证据能证明迁移正确。留下的可复用资产：概念映射、节点拆分与参数迁移规则、典型实现与编排样例、新旧对比方法、适合交给工具的重复任务清单。

**"没有这一步，后续 AI 迁移面对的只是一组散乱代码和抽象目标。"**

### 阶段二：让 AI 迁移，同时把失败沉淀为能力（直播频道页，约 10 人日）

把框架知识、迁移步骤与样例写入 Skill，让 AI 参与旧应用分析、目标拓扑设计、代码与配置生成、静态对账、差异修复。**Skill 不是预先设计好的提示词，而是在真实迁移中长出来的工程能力**——错误分两类处理：需要理解业务语义的 → 补知识、规则与样例；可确定性判断的 → 沉淀为解析器/生成器/校验脚本。具体演化的例子很实在：AI 难稳定还原旧图依赖 → 增加图解析、血缘提取与依赖报告；复杂 Plan 手写易错 → 脚本生成；生成结果难走读 → Plan 反解为 Markdown；Java 参数/Bean/配置易漂移 → 跨产物契约对账。**每发现一种可重复错误，不是只修当前代码，而是让下一次更早发现、自动定位、能够重跑。**

### 阶段三：直接复用 Skill 迁移新场景（单场景约 3 天）

标准流程八步：读旧应用与目标接口 → 还原节点/依赖/配置事实 → 生成迁移任务与依赖阶段 → 按拓扑迁移节点 → 生成代码/Bean/Plan → 确定性校验 → 按报告修复并重跑 → 人工审核业务语义与结果。人工收敛为**驱动执行、审核结果、确认新旧差异、决定灰度/放量/回滚**。作者的评价标准是"**迁移经验先从人脑进入文档，再从文档进入工具，最后由 Skill 把知识、任务、工具与验收标准组织成可重复执行的过程**"——而不是"AI 写了多少代码"。

## 拆解历史应用：输入是"一组运行事实"，不是代码仓

一次迁移至少要同时处理五类事实：旧框架的图/流程配置、Java UDF 与 Spring Bean、输入输出与共享上下文、实验参数与动态配置与条件开关、外部调用与异常处理。**只让 Agent 读仓库直接改写，很容易把代码引用关系误当完整业务依赖**，遗漏配置、实验与运行时注入形成的隐式行为。

所以第一步不是写代码，而是**结构化事实基线**：节点清单（类型、职责、输入输出、配置、外部依赖、异常策略）+ 依赖图（从图连接、参数读写、隐式引用生成）。任务按**拓扑**划分 Stage——上游先迁移，无依赖同层可并行，下游必须等前置产物通过检查。分工三角色：**主 Agent 管全局事实/目标拓扑/公共约束/阶段状态；规模化执行任务迁移边界清晰的节点；确定性脚本做图解析、任务生成、Plan 构建、参数闭环、跨产物校验**。三个收益：上下文不膨胀、并行安全、结果可靠（结构/配置/契约判断不依赖模型每次临场推理都得到相同结果）。

## 三层验证：怎么证明迁移前后行为等价

**"代码编译通过"或"接口返回成功"不算迁移完成。** 搜推在线链路依赖持续变化的召回/特征/打分服务，同一请求在相近时刻跑两次也可能因实时数据、实验配置、缓存或服务状态不同而结果不同；分别请求新旧链路比最终响应，**无法区分差异来自迁移逻辑还是外部数据**；且微小差异会沿召回→打分→重排→组装放大，只看最终结果定位不到最早偏差。

1. **静态结构与契约校验**：节点是否完整、Bean 实现是否一致、输入是否都有生产者、输出是否被正确消费、`Plan` 是否引用有效物料、配置类型与默认值是否一致。**能证明结构闭合，不能证明业务语义正确。**
2. **固定外部输入 + 分阶段比较**：**录制旧链路**对召回/打分服务的请求与结果，**回放给新链路**在对应调用点使用同一份数据——新旧关键输入一致，剩下的差异才更可能来自迁移逻辑；比较按召回、特征处理、打分、重排、结果组装**逐层**进行，先定位第一个出现偏差的阶段，再判断属于预期配置差异、顺序无关差异、实时字段差异，还是需修复的逻辑错误。
3. **预发、灰度与生产观察**：Mock 能隔离外部不确定性，也可能掩盖真实集成问题——静态与 mock 通过后仍要走预发真实调用、分批灰度、生产观察；灰度同时看成功率、RT 分布、节点异常/超时与核心业务/策略指标。**AI 与工具可整理证据、聚合差异、给修复候选，但灰度放量与回滚始终由人工授权。**

迁移稳定性的目标不是"证明 AI 永不出错"，而是**让错误尽早暴露、能定位到责任阶段、修复后可重跑、每次生产决定都有证据与责任人**。

## 结果：性能未劣化，但功劳不能记在框架头上

四个已迁移场景的**平均 RT、P99、P999 均未出现劣化**（表内数值=迁移后 − 迁移前，负数为耗时下降，部分场景长尾改善）。作者主动归因：**性能改善主要来自迁移过程中重新梳理执行关系、把不合理的串行改为并行，而不是新框架性能更优。**

效率数据与免责说明：主播关注页人工迁移 **20 人日**；直播频道页 AI 参与并同步建设 Skill **约 10 人日**；后续复用 Skill **单场景约 3 天**。**"这组数字来自不同规模和复杂度的场景，不能直接当作严格效率实验"**——它说明的是研发重心变化：人从逐项理解/设计/编码，转向业务约束补充、架构取舍、差异判断、生产授权；AI 承担批量分析、结构转换、代码与配置生成、重复修复；确定性工具承担事实解析、生成与校验。

## 复盘：四个判断

1. **历史系统迁移必须先建立人工事实基线**——不知道哪些行为必须保留、概念如何映射、什么证据代表正确，AI 只能生成"看起来合理"的代码；人工迁移不是要绕过的低效步骤，而是自动化的事实与验收基础。
2. **先降低系统的解释成本，再扩大 AI 的执行范围**——稳定交付不能建立在"每次重新理解全部历史上下文"上；统一物料、显式参数、受约束流程、结构化执行信息，本质是**把人脑里的隐式知识变成机器也能用的工程契约**。
3. **确定性问题不要长期留给模型推理**——图依赖、参数闭环、Bean 注册、Plan 结构都可程序稳定判断；每遇到可重复错误就问"能否沉淀为解析器/生成器/校验器"。
4. **生成、验证、生产授权必须职责分离**——AI 可以生成代码、归纳日志、提出修复建议，但**不能同时定义通过标准并批准自己的结果**；业务语义、例外判断、灰度与回滚仍需明确人工责任。**可信迁移不是追求无人参与，而是让人工判断集中在真正需要负责的环节。**

## 深度分析

### "AI Friendly"被重新定义成可验收的架构属性

市面上多数"AI Friendly 架构"论述落在"结构化、模块化、文档齐全"这类形容词上；这篇给了五条可检验的问题（局部上下文、稳定语法、显式契约、可工具检查、可留证据），并明确**架构只提供接口，不保证 AI 正确**。这个区分很重要：它把责任边界切清楚了——**架构负责"能不能被检查"，AI 控制层负责"生成得对不对"，人负责"能不能上线"**。

### 真正的杠杆是"先人工后 AI"，而不是更强的模型

20 人日的人工迁移看起来是"低效步骤"，但它的产出不是代码而是**基线**：该保留的行为、概念映射、验收证据。阶段二的 Skill 之所以能长出来，是因为有一个已知正确的参照系可对照；阶段三能压到 3 天，是因为错误类型已经收敛成脚本。**跳过基线直接让 AI 迁移，等于让模型在没有标准答案的空间里自我确认。**

### 录制回放分阶段比较，是"非确定性系统"做等价验证的正解

在依赖实时数据的推荐链路上，"同输入两次结果不同"是常态，端到端 diff 必然噪声淹没信号。**把外部依赖录下来冻结，让差异只剩迁移逻辑**；再按链路阶段逐层比较，把"哪里开始不同"变成可定位的信息。这套方法与 Agent 评测里的"固定评估器 + 固定数据集"同源——**要做对比，先把不可控因素移出比较范围**。

### 把"确定性"从模型手里拿走，是这套方法能规模化的原因

图解析、参数闭环、Bean 注册、Plan 构建、跨产物对账——每一项都被移进脚本。模型只保留语义理解与局部差异处理。这既是成本选择（少烧 token、少重试），也是可靠性选择（同一输入必须同一输出）。**"模型负责语义，工具负责结构"这条分工线，比任何提示词技巧都更能决定迁移能否复制。**

### 诚实的归因让结论可用

性能没劣化，但作者说改善来自并行重排；效率 20→10→3，但作者说场景复杂度不同、不是严格实验；迁移完成的标准不是编译通过，而是三层验证通过。**每一条结论都附了"它不能证明什么"**——这种写法让读者能直接搬用的是方法与判据，而不是几个漂亮数字。

## 实践启示

1. **先改生产方式，再谈 AI 参与**：统一模型、显式契约、稳定语义、结构化证据四件套不到位，AI 只会加速错误扩散。

2. **AI Friendly 用五问自检**：局部上下文可读？语法稳定？契约显式？结果可工具检查？运行留证据？

3. **节点粒度三条线**：一句话说清职责、输入输出可稳定声明、有独立测试或复用价值——否则只是把复杂度挪到编排层。

4. **顺序优先、显式并行**：牺牲部分表达自由度，换稳定阅读范式与可评审的并行边界。

5. **诊断信息属于执行模型**：统一 `ExecuteRemark` 树，让日志/监控/链路/排查消费同一份事实；钩子异常隔离，不影响主业务。

6. **迁移先建人工基线**：概念映射 + 必须保留的行为 + 验收证据，三样缺一不可。

7. **确定性工作交给脚本**：图解析、参数闭环、Bean 注册、Plan 生成、跨产物对账；模型只做语义与局部差异。

8. **等价验证三层**：静态契约 → 录制回放分阶段 diff → 预发灰度生产观察；编译通过不算完成。

9. **生成/验证/授权分离**：AI 可以提修复候选，不能自己定义通过标准并批准上线。
