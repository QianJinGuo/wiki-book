# 评测单元是「一次推荐请求」：上下文驱动的 LLM-as-Judge

> 📊 Level ⭐⭐⭐⭐⭐ | 23.9KB

## 一句话结论

小红书把推荐评测的**最小单元**从"一篇内容"改成了**"一次带完整现场的推荐请求"**——`EvaluationContext = <UserState, RequestTime, OrderedItems>`。这个改动看似只是加字段，实际上重写了采样、执行、聚合与诊断四件事。全文最有价值的一句判断是：**"LLM 让规模化语义理解成为可能，但一次模型调用并不等于可靠评测。"**

## 一、为什么行为指标不够：CTR 会把两种体验压成同一个数字

推荐策略上线后，团队先看 CTR、停留时长、互动率。这些指标"汇总大量用户反馈，能够判断用户行为是否变化，**但不会保留某个用户当时看到了什么、内容如何排序，或者策略实际改变了哪些内容特征**"。

最锋利的例子：

> "两组推荐结果可能得到**接近的 CTR，却由完全不同的内容结构产生**：一组兼顾兴趣匹配与内容探索，另一组依靠更强的**标题刺激**获得点击，同时出现**类目集中**。仅凭 CTR，这两种体验会被压缩成相近的数字。"

反方向同样成立：**"内容结构改善也不能直接推导出用户行为指标一定提升"**——所以实验分析"还需要一组**来自内容侧的证据**"。

他们把这层判断命名为**语义评测**："回到具体推荐请求，描述内容在**质量、兴趣、时效和组合方式**上发生了怎样的变化。"分工是清楚的：**"行为指标用于验证线上效果，语义评测提供可下钻的内容证据；两者对应同一次推荐，但承担不同任务。"**

过去这层靠**人工抽样**——"评测人员需要补齐背景、逐篇检查，再汇总结论，覆盖规模和判断一致性都会受到限制"。LLM 解决了规模，但没解决可靠性：**"一次模型调用并不等于可靠评测；稳定的判断还需要清晰的上下文边界、评分标准，以及规则与模型之间的明确分工。"**

## 二、评测单元：三个要素定义"现场"

> **"推荐评测的最小单元不是孤立的内容，而是一次带有完整现场的推荐请求。"**

```
EvaluationContext = <UserState, RequestTime, OrderedItems>
```

| 要素 | 内容 | 决定什么 |
|---|---|---|
| **UserState** | 用户画像、长期兴趣、近期消费 | "内容是否**适合当前用户**" |
| **RequestTime** | 推荐实际发生的时间 | "内容在**当时**是否仍然有效" |
| **OrderedItems** | 用户看到的内容**及其顺序** | "单篇质量之外的**重复、集中和整刷体验**" |

配套的一句区分很重要：**"EvaluationContext 记录'当时发生了什么'，实验目标则限定'本次想验证什么'。"**

两个例子把"上下文敏感"讲透了："同一篇露营笔记，对长期关注户外的用户可能符合稳定兴趣，对**刚刚连续消费过多篇露营内容**的用户则可能造成重复；同一篇节日攻略，在活动前后也会得到不同的时效判断。"

**关键推论**：三要素任一变化，评测样本就随之变化。所以——

> **"上下文驱动不只是向 Prompt 中增加字段，它还会改变评测系统组织采样、执行和结果的方式。"**

五条系统性后果（这五条才是"上下文进体系"的判据）：

1. **采样以推荐请求为单位**，保存当时的用户状态、请求时间和有序内容列表；
2. **评测同时覆盖单篇、完整列表和用户请求三个粒度**；
3. **每个结果都绑定对应的上下文与评测版本**，不能脱离现场单独解释；
4. **上下文缺失、获取失败和未请求需要分别记录，不能由模型自行补全**；
5. "只有当采样、执行和结果都围绕一次推荐请求组织时，上下文才真正进入评测体系。"

第 4 条尤其值得记：**把"没拿到"和"没要"分开**，且**禁止模型补全**——这是防止幻觉污染评测数据的第一道闸。

## 三、为什么"上下文 + 请打分"不行

最直接的做法是把 `EvaluationContext` 和一句"请打分"交给 LLM。他们说这"可以得到一次判断，却很难形成稳定的评测能力"，理由两条，都是结构性的：

- **"所有证据堆在同一个 Prompt 中，模型可能跨维度使用信息"**——判多样性时偷看了质量证据；
- **"多个问题被压缩成一个总分后，输入缺失、规则命中和模型失败也难以区分"**——错了不知道错在哪。

所以评测 Agent 的职责不是"调模型"，而是**"组织上下文、解析评测配置、调度规则与 LLM 评测器，把一次判断组织成有状态、可追踪的执行链路"**。

## 四、维度设计：先拆开，再谈分数

> **"推荐体验无法直接压缩成一个总体分。"**

理由是按维度各自的**证据来源**不同："内容质量关注内容本身，时效性依赖推荐发生的时间，兴趣匹配需要结合用户状态，多样性则必须观察完整列表，**评价对象和证据不同，就需要拆成彼此独立的评测维度**。"

**两类维度**：

| 类 | 作用 |
|---|---|
| **基础体验维度** | "检查**每次推荐都应满足的质量底线**"（兴趣匹配、多样性、内容质量…） |
| **目标符合度** | "验证**策略希望改变的内容特征**是否真正出现在结果中" |

营销内容治理的例子把两类的关系说清了："目标符合度判断营销感是否下降，基础体验维度继续检查兴趣匹配、多样性和内容质量是否受损，从而将**'策略是否生效'与'是否带来体验代价'分开**。"

**评分设计（三档而非自由发挥）**："当前语义维度采用 **0/1/2 三档**评分，各档条件由**相应的评分规则单独定义，不把'好、一般、差'的尺度留给模型自由发挥**。"

**输出三件套**：**分数 · 理由 · 执行状态**——"分数与理由表达业务判断，**状态记录材料是否完整、评测是否成功**"。

**聚合纪律（三条）**：

1. "各维度结果**首先独立保留**，综合分只用于**任务概览和样本筛选**"；
2. "对于明确不可接受的问题，任务可以设置**门控条件，防止其他维度的高分将其掩盖**"；
3. "进入诊断时，仍需回到具体维度、内容、理由和执行状态，**而不能只看聚合后的数字**"。

**证据边界**："曝光后的点击、停留、互动和负反馈沿**独立链路**输出，**不作为 LLM 语义评分的证据**，两类结果只在分析阶段对齐。"——这条是防止"用结果反推原因"的循环论证。

## 五、三层分工：不是所有判断都该交给 LLM

原则只有一句，但分得很干净：

> **"结构化字段能够确定的结论由代码直接计算；代码能够稳定提取、但仍需语义解释的信息，先转换为统计特征再交给 LLM；只有依赖用户、内容或策略语境的判断，才由 LLM 在限定范围内完成。"**

| 层 | 谁来判 | 例子 |
|---|---|---|
| **确定性** | 代码 | 字段比对、阈值、命中规则 |
| **可提取但需解释** | **先转统计特征**，再给 LLM | 分布、占比、重复度 |
| **依赖语境** | LLM（限定范围） | 营销感、兴趣匹配、语义重复 |

这与支付宝"概率模型做概率擅长的事，脚本保证确定性"、AWS"能确定性判断的绝不用 Judge"是同一条工程律。

**校准方法（很严格）**："评测标准进入批量任务前，**人工与模型需要在相同输入、相同 Rubric 下独立评分**"；对不一致样本，"先区分问题来自**输入缺失、标准边界模糊还是模型理解偏差**，再决定调整数据、规则或 Prompt，**而不是直接迎合人工结果修改分数**"。

最后半句是全文的方法论底线：**迎合人工结果改分，等于把 Judge 训成复读机。**

**一致性度量（不迷信单一一致率）**："一致性也不能只看'完全相同率'，三档分数可能集中在中间档，单一一致率容易高估 Judge 的能力；更有意义的观测包括**加权 Kappa、0 分问题样本的召回率，以及人与人之间的一致性上限**。"

三个指标各治一病：**加权 Kappa** 治"档位分布不均导致的虚高一致"；**0 分召回率** 治"漏判严重问题"（这是业务最怕的）；**人与人的一致性上限** 治"拿人当金标准"的幻觉——**如果两个专家都难一致，就不能要求模型一致**。

**版本回归**："Prompt、规则或模型升级时，除了重新计算一致性，还要在**同一批样本**上对比新旧版本，由评审者标记新结果相对基线是**改善、持平还是退化**。"判据一句：**"这里衡量的是输出是否更符合评测标准，而不是分数是否发生变化。"**

## 六、可比较、可回放：同时钉住"现场"和"尺子"

问题的根源说得很准：

> "推荐侧的用户画像和 Feed 候选状态会变化，评测侧的 Prompt、规则阈值、输入裁剪方式和模型版本也会迭代。**如果这些变量没有被同时记录，两次评分的差异就无法解释**——它可能来自推荐结果，也可能只是输入数据或判断尺度发生了变化。"

解法是**双固定**：

| 固定什么 | 记录什么 | 回答 |
|---|---|---|
| **输入快照** | 评测发生在**什么现场** | 用户、请求时间、内容集合、数据状态 |
| **评测版本** | 系统依据**什么标准**判断 | Prompt、规则、权重、模型配置 |

> **"只有两者能够分别追溯，分数变化才有明确的比较基础。"**

回放时："核对快照版本、用户、请求时间、内容集合及数据状态"；在同一份输入快照上，"使用原评测配置可以**追溯历史结果产生的条件**；显式替换 Prompt、规则、权重或模型配置，则可以**比较新旧评测器的判断差异**"。且"每份结果都会记录**实际生效的配置版本**，作为解释差异的坐标"。

这一节其实是**评测领域的可复现性（reproducibility）**：**没有快照，分数不可比；没有版本，差异不可归因。**

## 七、从请求级到实验级：双向索引与下钻链

实验决策面对的不是一个请求，而是成组的请求。核心问题是：**"如何把局部的语义判断组织成可比较的实验级证据，同时保留返回原始推荐现场的路径。"**

**存储设计**是关键："不会只保存一个综合分或一段模型结论。每条有效结果都与**评测维度、单篇或整刷粒度、内容位置、分数和判断理由**关联，并保留实际输入、执行状态与评测版本。"

于是同一份结果有**两个方向的能力**：**"向上可以按实验分组聚合，观察不同维度的整体变化；向下可以回到用户请求、有序内容列表和单篇证据，复查判断是如何产生的。"**

**分析顺序**：先**分别**看策略目标与基础体验。例子很具体："一项希望降低某类内容曝光密度的策略，**目标内容占比下降只能说明调节方向可能已经生效**；如果兴趣匹配或整刷多样性同时下降，还需要判断**策略是否以其他体验为代价**。"

**反均值（本节最有价值的一条）**：

> "实验级比较也不能退化为**两个平均分相减**。相同均值可能对应完全不同的样本结构：变化可能只集中在**少量低分请求**，也可能出现在**特定内容位置**；单篇质量保持稳定时，整刷仍可能出现类目集中或语义重复。"

所以要结合"**有效样本数、分数分布、低分请求以及单篇与整刷结果**"判断差异发生在哪里。

**下钻链**：**维度分布 → 用户请求 → 有序内容列表 → 单篇结果 → 输入证据与判断理由**。以多样性下降为例："实验级结果只能说明整刷结构发生了变化。展开代表请求的内容列表，才能进一步区分类目集中、作者类型集中、标题近似或语义重复。"结论一句：**"分数在这里承担定位索引的作用，真正支持诊断的是与分数绑定的内容、证据、理由和执行状态。"**

**能力边界（自我限定三段，很克制）**：

1. "这套诊断回答的是**推荐结果发生了什么变化**，并不直接证明用户行为已经改善，也不能单凭内容证据确定系统根因"；
2. "CTR、停留时长和互动率仍用于验证用户是否作出了不同响应，语义评测则解释变化发生在哪些内容和请求中，**两者共同进入实验分析但不能彼此替代**"；
3. "至于问题是否来自**召回、融合或打散**环节，还需要结合推荐链路数据或后续实验继续验证"。

## 八、LLM-as-User：只做预筛，不替代 A/B

当前这套的边界是"一次固定请求"——"不会预测用户接下来会点击还是跳过，也不描述一次消费如何改变后续兴趣"。下一步是 **LLM-as-User**：

```
观察当前内容 → 行为模块生成经过校准的动作概率
  → 根据曝光与消费更新短期兴趣、重复感与疲劳状态 → 进入下一轮推荐
```

"除语义判断外，这条链路还必须处理**行为生成和状态转移**。"验证要分三问：**单次动作是否准确 · 群体行为分布是否接近真实日志 · 在历史实验中能否判断正确的策略方向**。

风险也点明了：**"偏正向、过度理性和多轮误差累积，都会让一段看似合理的模拟轨迹偏离真实用户。"**

**定位极其克制**：**"LLM-as-User 目前更适合作为策略上线前的离线预筛和问题探索工具，不替代线上 A/B 实验。"**

## 结语原话

"它不追求用一个总分概括体验，重点在于补充**可定位、可下钻的内容证据**。Agent 的价值来自模型、规则、数据和人工校准之间的**受控协同**，它**不会替代真实行为，也无法消除模型偏差**。但当每次判断都能对应到具体现场、证据、标准和版本时，推荐体验就能从依赖专家感受的模糊问题，转化为**可观察、可比较、可追溯的工程对象**。"

## 深度分析

### "评测单元"的选择，决定了后面所有设计

大多数 LLM-as-Judge 的讨论从"怎么写 Rubric"开始，这篇从**"判什么"**开始。一旦承认单元是"一次推荐请求"而不是"一篇内容"，五条后果几乎是被迫的：采样要按请求、粒度要三层、结果要绑上下文与版本、缺失要区分、禁止补全。**评测系统的质量上限，首先由单元定义决定，而不是由 Prompt 决定。** 这个视角可以平移：Agent 评测的单元是"一次任务"、Skill 评测的单元是"一次调用"、运维评测的单元是"一次工单"——**单元选错，后面全是补丁**。

### 它把"上下文"从 Prompt 技巧升级为数据契约

"上下文驱动不只是向 Prompt 中增加字段"这句是关键。他们的做法是：上下文成为**可存储、可校验、可版本化**的结构（UserState/RequestTime/OrderedItems），且**缺失、失败、未请求三态分列**。这实际上是把上下文当**数据库表**在建，而不是当**提示词片段**在拼。与冯若航"Context 是一组边界"、RAGFlow"知识编译成证据链"是同一路数：**上下文要工程化，先要结构化。**

### "0 分召回率"是这套指标里最业务化的一条

加权 Kappa 衡量整体一致，人与人的上限校准金标准——但**0 分召回率**直接对应业务风险：**严重问题有没有被漏判**。评测系统最危险的失败不是"打分偏高一点"，而是"该报 0 的报了 2"。把这一项单列出来，说明设计者想清楚了**哪类错误不可接受**。这与 AWS Skill Eval 的"该触发没触发直接失败"、易点天下"只关注小于 0.5 的低分是否消失"是同一种**异常优先**的度量哲学。

### "不迎合人工结果改分数"，是 Judge 校准的分水岭

不一致样本的处理方式有三种：改 Prompt、改标准、改分数。前两种在**修尺子**，第三种在**迁就答案**。他们明确选了前两种，并先把不一致归因到"输入缺失 / 标准边界模糊 / 模型理解偏差"三类——**先归因，再修**。这条纪律的价值在于：**一旦开始迎合人工分，Judge 就失去了独立判断能力，评测退化为复述。**

### 双固定（快照 + 版本）解决的是评测领域最古老的问题

"两次评分的差异无法解释"——这是所有离线评测的通病：模型换了、数据变了、Prompt 改了，分数涨了 3 个点，没人说得清是哪个原因。**输入快照 + 评测版本分别追溯**，把这个问题拆成两个可回答的问题：**现场变了吗？尺子变了吗？** 这也是"分数能不能进实验结论"的前提条件。

### 它明确拒绝了"总分"这个诱惑

"不追求用一个总分概括体验"、"综合分只用于任务概览和样本筛选"、"门控条件防止高分掩盖"——三句话构成一套**反聚合**的纪律。理由在实验级诊断那节说透了：**相同均值可以是完全不同的样本结构**。这与易点天下"不以综合分值评比两次评估"、SkillHone"不看平均分要看分档"是同一种统计学自觉：**均值是最容易骗人的汇总。**

### 与"推荐系统 Agent 化"的更大图景

这篇属于小红书《Agent 驱动的推荐系统工程实践》专栏，覆盖"需求理解、代码开发、变更风险分析、效果与质量评测、发布执行、线上观测和问题诊断"。本篇是其中**评测**一环，而它展示的模式（把一次业务动作变成可复查的评测单元）与专栏其他环节（发布、观测、诊断）应当是同一套骨架。**这提示了一个判断：推荐系统的 Agent 化不是"加个 Agent"，而是把每个研发环节都重写成"有现场、有标准、有版本、可回放"的单元。**

## 实践启示

1. **先定评测单元**：一次请求 / 一次任务 / 一次调用——单元定义决定采样、粒度与归因方式。

2. **上下文要结构化到可存储**：`<用户状态, 时间, 有序内容>` 这类三元组比"多塞几个字段"有用得多。

3. **缺失、失败、未请求三态分列**，且禁止模型自行补全。

4. **把"策略是否生效"与"是否带来代价"分成两类维度**：目标符合度 + 基础体验底线。

5. **评分档位由规则定义，不让模型自由发挥**（如 0/1/2 三档，各档条件写清）。

6. **输出分数 + 理由 + 执行状态**三件套；状态记录材料是否完整、评测是否成功。

7. **综合分只做概览与筛选**，诊断必须回到维度、内容、理由、状态；对不可接受问题设门控，防高分掩盖。

8. **结果指标不能当语义评分的证据**：点击/停留沿独立链路，两类结果只在分析阶段对齐。

9. **三层分工**：确定性给代码，可提取的转统计特征，只有依赖语境的才给 LLM。

10. **人工与模型同输入、同 Rubric 独立评分**；不一致先归因（输入/标准/模型），**不要为迎合人工而改分**。

11. **一致性看加权 Kappa + 0 分召回率 + 人与人的上限**，别只看完全相同率。

12. **双固定**：输入快照（现场）+ 评测版本（尺子），二者分别可追溯，分数才可比。

13. **实验级比较拒绝"两个均值相减"**：看样本数、分布、低分请求、单篇与整刷。

14. **下钻链要能走到底**：维度分布 → 请求 → 有序列表 → 单篇 → 证据与理由；分数只是索引。

15. **LLM-as-User 只做离线预筛**，别拿模拟轨迹替代线上 A/B。
