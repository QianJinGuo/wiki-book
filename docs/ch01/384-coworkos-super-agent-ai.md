# CoworkOS：三层协作 + 共享作品 + 持久状态，把 Super Agent 做成「AI 同事」

> 📊 Level ⭐⭐⭐⭐ | 14.6KB

## 一句话结论

人大 RUC-NLPIR 联合复旦、北大、NUS、上交、华东师大做的 CoworkOS，把 DeepSeek 提出的 Super Agent 四标准（**连续、高效、主动、持久**）落成一套可运行系统。它沿两个维度扩展：**任务复杂度**（通过多轮环境交互完成复杂办公交付）与**时间跨度**（跨天跨会话持续工作、中断后接续）。三项核心设计——**三层协作架构**、**共享应用环境**、**持久状态与异步执行**——回答的是"AI 同事"与"AI 工具"的差别：**工具执行指令，同事围绕同一份作品持续负责。**

## 设计一：三层协作——主智能体定策略、协调运行时管状态、子智能体干活

| 层 | 职责 |
|---|---|
| **主智能体（Main Agent）** | 制定计划、把具体工作分给子智能体、**根据返回成果决定下一步**；子智能体提交后**检查是否满足要求**，发现遗漏或错误就继续安排修改 |
| **协调运行时（Coordinator Runtime）** | 调度任务、记录状态、传递结果；支持**同步等待**（需立即拿结果）与**异步执行**（耗时长，主智能体继续做别的事）；把用户追加的指导、子智能体的提问转达上去 |
| **子智能体（Subagent）** | 执行具体子任务；**遇到不确定可以带着暂定方案提问**（不是卡住等指令） |

外挂一个 **Watchdog**：检查子智能体是否停滞或异常，把问题报告给协调运行时，为**恢复或调整任务安排**提供依据。

这套结构解决的是"分工之后如何持续推进"：**分头执行容易，进度与问题能否及时传回来才是难点**。同步/异步双通道 + 带暂定方案提问 + Watchdog 三件事合起来，才让"多环节并行 + 最终交付围绕同一目标"成立。

## 设计二：共享应用环境——把人改的东西变成智能体的新事实

真实办公里，人不会只用对话表达意见，而是**直接改一段文案、调一页演示**。CoworkOS 因此把**作品本身**作为协作基础：文档、演示、CAD、Blender 等应用接入共享环境，人与智能体操作同一份作品；**用户改完后，智能体下一次读取就以更新后的状态为依据**。

多人多智能体并发修改的冲突处理，是全篇最工程化的两段：

1. **写入时核对预期版本**：如果智能体读完后用户又改了内容，继续按旧版本写入就会覆盖用户的工作——所以写之前核对预期版本，**版本已变就暴露冲突，让智能体重新读取并判断如何处理**（不是静默重试，也不是强制覆盖）。
2. **子智能体改动先存独立候选**：由**主智能体审查后再合入**，于是不同参与者可以分头准备改动，同时保留检查与调整的机会。

这两条把"乐观并发控制"（版本核对）与"变更评审"（候选合入）搬进了 Agent 协作——**比"共享一个文件夹"可靠，也比"全局加锁"实用**。

## 设计三：持久工作状态——三份存储 + 后台任务 + 事件唤回

要持续承担工作，需要保存的**不只是对话**，还有材料、决策与执行进度。CoworkOS 把它们分开存：

| 存储 | 存什么 |
|---|---|
| **工作区** | 材料与成果（作品本体及其产物） |
| **语义记忆** | 关键决策与待办 |
| **任务台账** | 执行过程与指标（进度、结果、度量） |

**恢复策略**：切换会话时**先恢复一份精简的工作状态摘要**，再按需查阅原始材料与证据——于是后续行动建立在已有进展上，**避免从头梳理整段历史**。这一条与"上下文压缩"的区别在于：压缩是被动丢信息，摘要是**主动构造一份可导航的入口**。

**执行侧**：耗时操作（训练、构建）托管为**后台 Job**，保留可查询的状态与日志，供跨会话继续跟进；需要持续观察的事项按**时间或外部事件唤回主智能体**，条件变化后再判断"继续执行 / 调整方案 / 请求用户参与 / 结束任务"。**后台运行与智能体判断由此衔接**——这是"持久"从"存得住"走到"接得上"的关键。

## 实验结果一：12 项基准，四类任务，与三个系统对比

统一用 **GLM-5.3** 作底层模型，对比 OpenHands、Codex、DeepSeek Harness（DSH）：

| 领域 | CoworkOS | 对照 |
|---|---|---|
| 工具使用 | 55.22 | DSH **55.31**（略高） |
| 搜索 | 82.14 | OpenHands **82.22**（略高） |
| **生产力** | **57.54**（四系统最高） | — |
| **机器学习编程** | **56.26**（四系统最高） | — |

**12 项中 6 项最优**（SkillsBench、JobBench、GDPVal、WideSearch、两项 ML 编程基准）；DSH 在 Tau-3、AutomationBench、WorkspaceBench-Lite 领先；OpenHands 在 BrowseComp 与 Harvey 更好；Codex 在 OfficeQA Pro 最高。作者的解读是：**真实工作把"工具操作、信息查找、专业判断、最终交付"分开考，没有一个系统全通吃**——这正是"不分伯仲"的准确含义。

## 实验结果二：24 个真实交付（六类场景）

网站、游戏、办公演示、交互可视化、CAD、Blender 六类，共 24 个任务，三方（CoworkOS / Codex / DSH）的作品并置呈现供直接比较。代表性案例：`After the Fall`（末日废土 Blender 场景，考空间·材质·光照组织）、`Turbofan Engine`（涡扇发动机 CAD，考部件结构）、`KESTREL`（救援无人机交互可视化，考内容·布局·操作连接）、`Courtyard House`（四合院网站）。

## 实验结果三：把 RSI 落在"自动化后训练"上

这是本篇最有信息量的一段——**用一个真实的长周期任务检验"持久 + 协作"是否真的有用**：

- **角色分工**：GLM-5.3 任**控制器与数据教师**，CoworkOS 的 harness 组织流程，**Qwen3.6-35B-A3B 是被训练的模型**；
- **起点**：R0 = 用 **1,345 条种子轨迹**做监督微调的模型；
- **循环**：CoworkOS 衔接**评测 → 诊断 → 数据生成 → 训练**，每轮根据反馈调整后续方案，共五轮；
- **结果**：八项平均分 **33.19 → 42.95（+9.76）**；单项 Automation **11.00 → 44.15**、SkillsBench **20.85 → 35.76**、BFCL **63.48 → 70.83**；
- **依据反馈的具体调整**：第一轮聚焦"工具选择、参数填写、反馈处理"三类失败模式补数据；**第二轮平均分下降后**继续调整数据覆盖与训练安排；到第五轮针对 BFCL 补函数调用轨迹，**这类轨迹占当轮新增数据的 61.1%**，BFCL 明显回升。

**诚实披露的部分同样重要**：最终八项里七项超过起点、六项达到 R0–R5 期间最高（含并列），但 **GDPVal 的最高分出现在第二轮，JobBench 的最终得分仍低于起点**——"多数能力提升，不同任务变化并不同步"。

## 六条演进方向（作者自己的路线图）

连续（跨设备跨会话，上下文与作品无缝承接）→ 高效（更大规模、更细粒度任务组织与资源调度）→ 主动（更可靠的事件理解与价值判断，**减少误判与打扰**）→ 持久（**异常自愈**与更长时程无人值守）→ 生态扩展（科学计算与多模态工具，人与智能体在更多专业环境共同完成工作）→ 自我改进（RSI：诊断问题、调整方案、验证效果，扩展到更广泛的研究与工程任务）。

## 深度分析

### "共享作品"是 AI 同事与 AI 工具的分水岭

工具范式的接口是**指令**（你说、它做）；同事范式的接口是**作品**（同一份文件、同一个模型、同一页演示，双方都能改）。CoworkOS 把作品接进共享环境，于是**人的修改天然成为智能体的新输入**——不需要"把意见翻译成 prompt"。这是"连续"最实的落地方式，也解释了为什么它要接 CAD/Blender 这类**原生应用**而非只做文本：**作品的形态决定协作的深度**。

### 版本核对 + 候选合入，是把协同编辑的成熟经验搬进 Agent

这两个机制并非新发明（分别对应乐观并发控制与变更评审），但迁移到 Agent 场景后价值更大：**Agent 会长时间持有旧上下文**，静默覆盖的风险比人类协作者高得多；而**子智能体的改动由主智能体审查**，等于给"并行"加了"合并前的门"。对比 Harmony/DGM 一类"演化出多个候选再选优"，这里是**运行时的候选合入**——同一套评审思想在两个时间尺度上重复出现。

### 三份存储的划分，暗合"材料 / 决策 / 过程"三分

工作区=材料与成果、语义记忆=关键决策与待办、任务台账=执行过程与指标。这个划分的好处是**恢复时可以只取摘要、按需下钻**：摘要是入口，材料是证据，台账是进度。相比"把全部历史塞回上下文"，它把"恢复"变成**有损但可导航**的操作——与记忆设计里"摘要记说过什么、用户模型记现在是谁"是同一条思路的不同侧面。

### RSI 实验的真正贡献：证明"长周期编排"能带来增益，且增益不整齐

五轮里第二轮下降、GDPVal 峰值在第二轮、JobBench 最终仍低于起点——**这些"不整齐"才是可信证据**。如果八项全都单调上升，反而要怀疑"数据泄漏或指标挑选"。作者把"第五轮为 BFCL 补的函数调用轨迹占当轮新增 61.1%"写出来，等于给出了**归因链**：失败模式 → 数据构成 → 指标回升。这比 +9.76 这个总分更有复用价值。

### 与 DSH 的关系：同标准、不同取舍

两者都强调"连续/持久/协作"，但 DSH 的重心在**双层架构 + 事件驱动 + 存算分离 + Watchdog** 的通用骨架，CoworkOS 的重心在**作品级共享 + 交付物质量**（六类真实交付、CAD/Blender 原生接入）。基准上互有胜负（工具使用 DSH 55.31 vs 55.22、搜索 OpenHands 82.22 vs 82.14），说明**这一代"超级智能体"还没有压倒性架构**，差异主要落在任务类型与交付形态的适配上。

## 实践启示

1. **三层协作要配"状态总线"**：主/协调/子三层之所以能并行，是因为协调运行时统一记状态、传结果；没有它，分层只是把串行变复杂。

2. **同步/异步双通道**：短任务同步等，长任务异步跑，让主智能体不被阻塞——这是"高效"的最小实现。

3. **允许子智能体带暂定方案提问**：比"卡住等指令"节省一整轮往返，也逼它先把假设写清楚。

4. **Watchdog 只报告不接管**：把"停滞/异常"作为事实交给协调运行时判断，避免看门狗自己变成第二个决策者。

5. **共享作品而非共享对话**：把文档/演示/CAD 原生应用接进来，人改完即成为智能体的新输入。

6. **写入前核对版本**：冲突要显式暴露给智能体重读，禁止静默覆盖或强制重试。

7. **子智能体改动走候选 + 主智能体审查**：并行产出，合并设门。

8. **持久状态分三份存**：材料与成果 / 关键决策与待办 / 执行过程与指标；恢复先给摘要，再按需下钻。

9. **长任务托管为 Job**，保留可查日志；按时间或事件唤回主智能体，条件变化后再决定继续/调整/请求人/结束。

10. **拿真实长周期任务验证"持久"**：像自动后训练那样，评测→诊断→数据→训练的循环才能暴露"跨会话接续"到底有没有用。

11. **报告要写"不整齐"**：哪一轮掉了、哪一项最终仍低于起点、峰值停在第几轮——这些比平均分更能说明系统边界。
