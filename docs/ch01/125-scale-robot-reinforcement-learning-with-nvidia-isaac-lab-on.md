## 深度分析

### 持久集群 vs 临时作业：把计算形态对齐到训练的两个阶段
这篇方案真正有价值的设计判断，是把机器人策略 RL 的开发生命周期拆成两个相位，再让两种 SageMaker 计算形态各管一段。研发期需要频繁改 reward 函数、观测空间和网络结构，对应的是大量短平快的运行——SageMaker Training Jobs 按作业生命周期计费、跑完即释放实例、无闲置成本，还天然适合超参扫描这种"并行发一堆短跑"的形态。而调好配置之后的生产级收敛训练是长程、多节点、GPU 密集的，HyperPod 的持久集群才有意义：每个节点跑健康监控 agent，故障时自动重启或替换实例，并从最近检查点自动续训，全程无需人工介入。

两个形态的成本曲线也因此完全不同：HyperPod 按集群内的实例持续计费（FSx for Lustre 另按预置容量按小时收费，可视化 pod 也会长期占住一个 GPU 节点），Training Jobs 只为每次作业的实际运行时长付费。所以"用哪种"不是技术偏好问题，而是"当前处于哪个阶段、GPU 是否在有效燃烧"的问题。

### 单镜像双后端：分布式拓扑的注入点差异
方案在工程上的关键收敛点是"一个 Docker 镜像 + 一份 config.yaml + 一个生成脚本"：镜像基于 Isaac Sim 5.1.0 并装入 Isaac Lab v2.3.2，`generate.py` 从同一份配置渲染出 HyperPod 的 Kubernetes manifest 或 Training Jobs 的启动脚本，训练代码本身零改动。

两条路径最终都落到同一句 `torchrun` 调用 skrl 训练器，差别只在"拓扑信息怎么进容器"：HyperPod/EKS 侧由 Kubeflow Training Operator 给每个 pod 注入 `MASTER_ADDR`、`MASTER_PORT`、`RANK`、`WORLD_SIZE`，entrypoint 转交给 torchrun，每个 GPU 拉起一个进程，再经 c10d rendezvous 组成全局进程组；Training Jobs 侧则是 SageMaker 把主机列表写进 `resourceconfig.json`，entrypoint 启动时自行解析出 rank 和 master 地址。 一个容易踩的坑在日志里很直白：pod 级的 `WORLD_SIZE: 2` 是 pod 数，不是全局进程数——2 pod × 每 pod 4 GPU，torchrun 启动后进程内的 `WORLD_SIZE` 才变成 8。排障时必须分清这两层拓扑。

### RT Core 硬约束：越贵的卡不一定能跑
Isaac Sim 基于 Omniverse 的 RTX 渲染器，要求 GPU 具备硬件 RT Core——这给出一条反直觉的选型约束：AWS 的 G 系列实例（A10G、L4、L40S、RTX PRO 6000）都兼容，而算力档次更高的 P 系列（A100/H100/H200/B200/GB200）因为数据中心卡没有 RT Core 反而全部不可用。选型时不能按"更贵=更强"的惯性走，必须先对着 Isaac Sim 的硬件兼容清单查。

多节点扩展的另一半在网络侧：`ml.g6/g6e/g7e` 从 8xlarge 起支持 EFA，给 NCCL 提供内核旁路、RDMA 能力的集合通信通道。开启方式在两种后端上也不一样——HyperPod 需要装 EFA device plugin 并在 pod spec 里申请 `vpc.amazonaws.com/efa` 资源；Training Jobs 则要在容器镜像和 VPC 配置里都做适配。该方案把两条路径的 EFA 都自动化配置了，这对复现者是实打实的省事点。

### 检查点与故障恢复：从节点替换到 S3 近实时同步
整套方案的可靠性叙事由三层检查点机制串起来。第一层在 HyperPod：训练 manifest 启动时检查 FSx 上是否已有上次留下的 `best_agent.pt`，有则自动加 `--checkpoint` 续训，与节点的自动替换机制天然咬合——被换掉的节点重新加入后从最近检查点继续，训练进度不丢。第二层在 Training Jobs：配置 `checkpoint_s3_path` 后，SageMaker 把 `/opt/ml/checkpoints` 近实时同步到 S3，作业中断后用同一个 `checkpoint_prefix` 重启即可恢复。 第三层是可观测性：MLflow 是 opt-in 的（不配 tracking URI 就完全跳过），且有两种授权模型——tracking server 走 `sagemaker-mlflow` IAM 前缀，Studio MLflow App 则要求训练角色 `sts:AssumeRole` 到 Studio 执行角色，跨域集成前要先改好信任策略。

更宏观地看，这条"GPU 并行仿真 + 托管分布式训练"的路径是 [云 AI 基础设施](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/cloud-ai-infrastructure.md) 在具身智能方向的典型落法：仿真侧把数月真实经验压缩为小时级训练，基础设施侧用托管服务吸收集群运维的重活。[Isaac Lab on SageMaker 机器人 RL 人形训练](https://github.com/QianJinGuo/wiki-public/blob/main/entities/nvidia-isaac-lab-sagemaker-robot-rl-humanoid.md) 是同一主题的姊妹条目；HyperPod 上基于 Kueue 的队列/配额治理和 [HyperPod MIG GPU 虚拟化](https://github.com/QianJinGuo/wiki-public/blob/main/entities/gpu-virtualization-using-mig-technology-on-amazon-sagemaker-hyperpod.md) 属于同一套算力治理谱系；PPO 在这套流程里只是 `framework` 字段的一个取值，算法谱系背景见 [RL 算法演进](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/llm-rl-algorithms-ppo-dpo-grpo-marl-evolution-2026.md)。

## 实践启示
1. **按训练阶段选计算形态，而不是选一次就锁死。** 调 reward 函数/观测空间/网络结构的迭代期用 Training Jobs（无闲置成本、适合超参扫描），配置收敛后的长程生产训练放 HyperPod（持久集群 + 自动故障恢复）；同一镜像让两者切换只是改配置。
2. **1000 次 PPO 迭代只够冒烟测试。** 官方示例的 `max_iterations: 1000` 是验证流水线用的，H1 在粗糙地形上的生产级收敛通常还要再高一个数量级，别拿冒烟参数当生产配置。
3. **GPU 选型先查 RT Core 兼容性。** Isaac Sim 依赖 Omniverse RTX 渲染器的硬件 RT Core，G 系列（A10G/L4/L40S/RTX PRO 6000）可用，而 A100/H100/B200 等高端数据中心卡全部不可用——按算力档位选卡会直接选错。
4. **多节点训练记得开 EFA，并分清两层拓扑。** 8xlarge 及以上机型支持 EFA 给 NCCL 走 RDMA；同时日志里的 pod 级 `WORLD_SIZE` 是 pod 数，全局进程数 = pod 数 × 每 pod GPU 数，排障时先确认自己看的是哪一层。
5. **检查点链路要默认开启而非事后补救。** HyperPod 侧靠 FSx 上的 `best_agent.pt` + 节点自动替换 + `--checkpoint` 续训，Training Jobs 侧靠 S3 近实时同步 + 同 `checkpoint_prefix` 重启；多节点 RL 运行一次节点故障就可能吞掉数小时进度，这层保险不该省。
6. **MLflow 集成是 opt-in 且有授权分叉。** 不配 tracking URI 则整个跳过；tracking server 与 Studio MLflow App 的鉴权模型不同，后者要求训练角色能 assume Studio 执行角色——跨 Studio 域集成前先改信任策略，否则训练跑完指标全丢。
