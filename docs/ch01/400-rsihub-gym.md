# RSIHub：给递归自我改进修一座 Gym，让方法可比、可换、可查

> 📊 Level ⭐⭐⭐⭐ | 12.5KB

## 一句话结论

字节跳动 + 上海交大 + UC Berkeley 联合开源的 RSIHub，把 AHE、Hyperagents、A-Evolve、GEPA 等"让 Agent 自己改自己"的方法接入**同一套执行与评测流程**。作者给的类比很准：**它是 RSI 的 Gym、是分布式训练里的 PyTorch Lightning**——**把算法与底层设施分开，让研究者集中研究进化策略**。它要回答的不是"能不能自己改"，而是：**怎么判断它改得更好。**

## 一、问题：方法越来越多，却没法放在一起比

Agent 已经能自己改 Prompt、补技能、调整运行代码；但**不同进化方法往往各搭一套系统**——如何选旧版本、如何分析失败、如何保留改动，各自设计。于是"方法越来越多，究竟谁更有效，却很难放在一起比较"。

## 二、抽象：七个阶段 + 算子 + Recipe

RSIHub 把各方法中**重复出现的流程**拆成七个阶段：

> **选择父代 → 执行任务 → 分析轨迹 → 提出修改 → 检查边界 → 评测 → 吸收结果**

每一步"具体怎么完成"由不同的**算子**负责；**Recipe 选择这些算子，并配置它们的工作方式**。这个拆法让原本揉在一起的设计选择变成可独立实验的变量：

| 阶段 | 可替换的选择（文中举例） |
|---|---|
| 选择父代 | 沿当前最高分版本继续修改 / 按多个目标保留不同候选 |
| 分析失败 | 用完整轨迹 / 先整理成更紧凑的修改依据 |
| 其余阶段 | 同理，差异都成为**可单独测试的对象** |

项目提供 **A-Evolve、AHE、GEPA、Hyperagents** 四套配方，分别覆盖**提示词与技能优化、Harness 修改、以及目标 Agent 与部分进化策略的共同演化**。对研究者最实际的好处：**测试一个新想法不必再从候选版本管理、任务执行、结果归档重做**——**替换某个环节后，其余实验流程可继续沿用**。

## 三、"改不动了，那'怎么改'也可以调"

这是全篇最值得记的一层——**把改进策略本身纳入改进范围**。两条路径：

1. **把选定的进化算子放进允许修改的范围**：候选版本变化的同时，**负责分析或提出修改的那部分代码也可以变化**（Hyperagents 配方支持的正是这类共同演化）；
2. **在两轮迭代之间**，由**外层 Agent** 根据允许使用的反馈，调整下一轮 Recipe 中的**算子绑定与策略设置**。

一句话区分：**"前一种修改组件实现，后一种调整组件的选择与配置。"** 于是**一次失败有两种处理方向**——继续修正执行任务的 Agent，或者**重新检查产生修改的那套策略**。作者点出这带来的研究价值：**RSI 不再只有"改任务执行"一个入口，还可以研究"怎样提高后续改进的效率"**。

## 四、边界与防作弊：涨分必须能被查清楚

三段机制，直接针对自进化系统的作弊面：

1. **Recipe 必须声明哪些资源允许变化**（改动范围是契约的一部分）；
2. **评测器与认证结果记录由框架控制**——**候选版本不能通过修改评分规则来获得更高成绩**；
3. **框架检查实际文件差异，并从干净的候选快照开展评测**。

判据一句：**"可以尝试更多修改，但每次涨分究竟对应什么版本、什么测试条件，仍然要能查清楚。"**

## 五、结果：增益真实，但高度依赖起点与方法

设置：初始 Agent = **MiniSWE / Codex**；基准 = **Terminal Bench 2 / τ³ Banking**；目标模型统一 **GPT-5.4 high**，负责提修改的 Agent 用 **GPT-5.4 xhigh**，每次进化最多 **10 代**。

| 基准 / 初始 Agent | 最佳方法 | 结果 |
|---|---|---|
| **Terminal Bench 2 · MiniSWE** | Hyperagents、A-Evolve | **pass@1 56.2% → 69.7%（+13.5pt）** |
| **Terminal Bench 2 · Codex** | AHE | **71.9%（+2.2pt）** ——起点越高，增益越小 |
| **τ³ Banking · Codex** | AHE | **24.7% → 34.0%** |
| **τ³ Banking · MiniSWE** | Hyperagents | **27.8% → 33.0%** |

**"换一个起点、换一类任务，领先的方法就可能变化。"**

## 六、最该记住的负面结果：总分涨了，保留任务退步

RSIHub 专门设了**封存保留任务**（不参与修改反馈，用来检验改进能否迁移到未见任务）。结果相当刺眼：**τ³ Banking 的 MiniSWE 实验中，Hyperagents 整体成绩提高，但封存保留任务上的表现下降；AHE 与 GEPA 在该设置下也出现保留任务退步。**

推论被写得很直白：**"总分上涨，可能伴随着部分能力损失。参与优化的任务做得更好，也不能直接说明新任务上的表现同样改善。"** 因此实验必须同时看两件事：**修改有没有带来收益、这些收益能不能迁移。**

结语也克制：**自动修改在部分设置下能带来明显提升，但效果取决于初始 Agent、任务与具体方法；"持续进化还不能等同于持续变强"。** RSIHub 保留的候选历史、执行轨迹与结果记录，正是为了让研究者继续排查**哪些改动修复了问题、哪些改动引入了退步、下一轮是否该换策略**。

## 深度分析

### Gym 类比点出的是"缺失的那一层"，不是"又一个框架"

RL 之所以能进步，是因为有环境与评测的公共契约（Gym），让算法可以互换、结果可以横向比。RSI 领域此前每篇论文自带系统与自带评测，**结果是"方法学"无法积累**。RSIHub 把七阶段与算子抽出来，等于给这个领域**定义了一个 ABI**——**一旦接口固定，进步就可以发生在接口两侧的任何一侧**。这与 PluginRSI 抽"插件"、HarnessPro 抽"三档"是同一波"把整体拆成可替换件"的思路，但层级更高：**它拆的是研究流程本身**。

### 把"进化策略"也放进可进化范围，是递归真正闭合的标志

只改任务执行，递归是"Agent 改 Agent"；连"怎么改"都能被外层调整，递归才变成"**改进改进本身**"——文中两条路径（改组件实现 / 改组件绑定与配置）恰好对应**结构演化**与**超参演化**。这也是为什么它强调"一次失败有两种处理方向"：**归因错了层级，努力就白费**——一个失败可能不是执行能力问题，而是"选父代/看什么反馈/何时放弃"这些策略设置错了。

### 三条防作弊机制，是自进化评测的最低标准

"评测器由框架控制 + 校验实际文件差异 + 从干净快照评测"——三件事分别堵住：**改评分规则**、**改文件却声称改了别处**、**在脏环境里评测**。任何声称"自进化涨分"的工作，如果没有这三条，就根本无法排除"优化了度量而不是优化了能力"。**这套要求迟早会变成审稿与采购的默认门槛。**

### "总分涨、保留任务跌"是自进化的通用风险，不只某个方法

三个配方在同一设置下都出现保留任务退步，说明这不是实现 bug，而是**机制性风险**：进化会朝"被反馈覆盖的那部分任务"过拟合，而**未被反馈覆盖的能力会被悄悄换掉**。这与 Harmony Harness 的负迁移（−103%/−197%）、HarnessPro 的"必须保留 h₀ 地板"是同一个现象的三次独立观测——**只要优化目标可被度量，度量之外的就会流失**。

### "起点越高增益越小"（+13.5 vs +2.2）说明这波技术更像补齐而不是突破

MiniSWE 从 56.2 涨到 69.7，Codex 只从 69.7 涨到 71.9——**自进化主要在补"harness 工程欠账"**，而不是突破能力上限。这个判断对落地很关键：**如果团队已把 harness 打磨得不错，指望自进化带来数量级提升是不现实的；它的价值更多在长尾场景与成本侧。**

## 实践启示

1. **先固定实验底座，再谈方法优劣**：七阶段（选父代/执行/分析/提案/边界检查/评测/吸收）可直接当自建评测流水线的骨架。

2. **把方法拆成"算子 + Recipe"**：同一步的两种做法要能替换，否则永远无法归因是哪一步带来收益。

3. **换起点、换任务复测**：领先方法会随初始 Agent 与任务类型变化，"通用最优"目前不存在。

4. **必设封存保留任务**：不参与反馈的那部分才是"能力有没有涨"的裁判；总分是给优化看的，保留任务是给决策看的。

5. **报告必须同时给两个数**：整体增益 + 保留集变化，只报前者等于隐藏风险。

6. **防作弊三件套写进流程**：评测器归框架管、校验真实文件差异、从干净快照评测。

7. **允许"策略层"被调整**：两轮之间调 Recipe 的算子绑定与策略设置，往往比继续改执行代码更有效。

8. **失败先分两层归因**：是执行能力不足，还是"选父代/看什么反馈/何时放弃"这套策略错了。

9. **对增益保持相对预期**：起点越强增益越小（+13.5pt vs +2.2pt），自进化更像补欠账而非换引擎。

10. **保留候选历史与轨迹**：否则无法回答"哪次改动修复了问题、哪次引入了退步"。

## 与相关实体的关系

- [PluginRSI](https://github.com/QianJinGuo/wiki-public/blob/main/entities/pluginrsi-plugin-level-harness-evolution-ustc-meituan-2026-11-03.md) 拆的是**harness 内部结构**（插件 + 短小 Workflow）；RSIHub 拆的是**研究流程**（七阶段 + 算子 + Recipe）。层级不同，方向一致：**可替换才能归因**。
- [HarnessPro](https://github.com/QianJinGuo/wiki-public/blob/main/entities/harnesspro-pareto-self-evolution-cost-performance-thu-zhipu-2026-11-04.md) 用"不低于基线 h₀"做地板、用固定测试集防评分漂移；RSIHub 用"封存保留任务 + 框架控评测"防作弊——**两套独立工作收敛到同一组防线**。
- [Harmony Harness](https://github.com/QianJinGuo/wiki-public/blob/main/entities/harmony-harness-multi-objective-self-evolution-google-2026-11-03.md) 观测到负迁移（保留率 −103%/−197%），本篇观测到"整体涨、保留跌"，**同一现象的两个证据点**。
- [ScholarEvolve](https://github.com/QianJinGuo/wiki-public/blob/main/entities/scholarevolve-research-guided-harness-evolution-ucsb-ms-2026.md)、[Meta-Harness / AutoDesign](https://github.com/QianJinGuo/wiki-public/blob/main/entities/autodesign-meta-harness-optimization-2026.md) 提供具体进化方法；RSIHub 提供**容纳它们并横向比较**的底座。
- [RSI 与持续学习](https://github.com/QianJinGuo/wiki-public/blob/main/entities/rsi-to-continual-learning-compounding-intelligence-overseas-unicorn-2026-10-20.md) 给的是"RSI vs CL"的框架与路线图；本篇给出**"RSI 目前只是补齐 harness 欠账"的实证约束**——两篇合读可校正对 RSI 速度的预期。
