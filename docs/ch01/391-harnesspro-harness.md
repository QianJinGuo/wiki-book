# HarnessPro：把成本做成第一等目标，用帕累托自进化产出三档 Harness

> 📊 Level ⭐⭐⭐⭐ | 13.3KB

## 一句话结论

清华 + 智谱的 HarnessPro（arXiv 2610.26770）指出 RHO 一类"自动改进 Harness"的共同病灶：**想要更高通过率，就得多探索、多轮校验，token 随之暴涨**，于是在有预算约束的生产环境里不可落地。它的解法是把这件事当成**多目标优化**：不输出"最好的那一套"，而输出**帕累托前沿上的三个代表点——lite（成本优先）/ medium（均衡）/ heavy（性能优先）**，并且**全程不需要标准答案或官方测试集**。结论一句话：**效率瓶颈常常不在基座模型，而在 Harness 本身。**

## 一、问题定义：三个指标、一个约束

| 指标 | 定义 | 地位 |
|---|---|---|
| **Pass Rate** | 任务最终产出全部通过测试用例的比例；**训练/验证/测试三分，测试集在全部进化结束后才打开** | 核心能力指标，有"不低于初始基线"的硬约束 |
| **Cost** | 完成一个任务全过程所有模型调用的 token 开销，**区分缓存输入/非缓存输入/输出三种单价**后换算成钱 | 与通过率并列的优化目标 |
| **Latency** | 任务从启动到结束的墙钟时间 | **仅辅助观测**——受服务器负载波动大，不作主目标 |

优化目标写得很克制：**在不低于初始版本通过率的前提下，尽可能同时提升通过率、压低成本**。这个"不低于"是后面第一层过滤的依据。

## 二、三阶段闭环

**① 轨迹诊断**：同一任务跑 **G 次重复 rollout**（降低单次随机噪声），分析智能体**同时读同一任务的全部运行记录**，输出结构化诊断报告——**识别出的问题 + 该问题对正确率与成本的影响 + 证据来源（轨迹片段、日志位置）**。

论文附录的例子很典型：某配置任务**所有运行都成功**，但 Agent 反复 dump 完整的大配置文件、重复执行已完成的校验步骤，产生大量**没有收益的 token 消耗**——这正是"成本优化"要消灭的对象，而不是靠牺牲正确性。

**② 规划与编辑**：**Evolution Planner** 对每个现有候选生成三份不同导向的改进方案——**I₁ 成本优先**（保正确性前提削无效开销）、**I₂ 均衡**、**I₃ 性能优先**（重点修失败模式，同时仍剔除不必要消耗）；并要求横向对比其他候选、借鉴有效设计、规避缺陷，方案须**具备通用性**（不能只针对某个具体任务打补丁），写明**改动点、预期收益、潜在风险**。**Harness Editor** 据此实际修改代码/配置/提示词，产出可直接运行的新候选，**每份修改做 Git 提交**便于追溯。

**③ 评估与筛选**——这里有全文最实用的一处工程细节：

> **LLM 自评判容易过度乐观，把有缺陷的输出判为正确。** 因此 HarnessPro 在进化**开始之初**就用"任务描述 + 初始 Harness 轨迹"合成一批**可执行测试用例**，并**在整套进化周期内固定不变**，保证候选间公平对比。效果：**故障识别召回率 41.7% → 83.3%**。

随后两层过滤：**第一层**直接剔除验证集通过率低于初始基线 h₀ 的候选（**杜绝"为省钱牺牲基础能力"**）；**第二层**帕累托支配过滤——若 A 的通过率 ≥ B 且成本 ≤ B，至少一项严格更优，则 B 被淘汰，留下**非支配集合（帕累托前沿）**。代表点用**归一化加权平方距离**挑：lite 权重偏向成本、heavy 偏向通过率、medium 相等；**每轮最多保留 3 套**，避免候选集合爆炸。

## 三、结果：同样更强的同时更便宜

**基准**：Terminal-Bench2（Linux 终端运维/编译配置）、SWE-Bench Pro（真实仓库级 bug 修复长序列）、ProgramBench（按文档从零重建程序）。**两组基座**：GPT-5.5 + Codex、GLM-5.2 + Claude Code。**基线**：Vanilla Harness、Dynamic Cheatsheet、ReasoningBank、Sleep-time Compute、RHO（及 Balance、RHO+Iteration 两个变种）。

| 场景 | 通过率 | 单任务成本 | 解读 |
|---|---|---|---|
| **Terminal-Bench2 · Heavy**（GPT-5.5+Codex） | **80.8%** vs RHO 76.3% | **$0.72** vs $1.09（**−33.9%**） | **更高成功率不必付更高 token 代价** |
| **SWE-Bench Pro · Heavy** | 略高于 RHO | 约 **−26%** | 同上 |
| **SWE-Bench Pro · Medium** | **79.0%** vs RHO 80.0% | **$2.68 → $1.26（−53%）** | 几乎追平 SOTA，成本砍半，"最适合绝大多数生产业务" |
| **Lite** | 高于 Vanilla 基线 | 大幅压缩 | 预算极度受限场景 |

延迟虽不是优化目标，但因为 token 总量下降，**多数场景运行耗时也随之变短**；上述结论在 GLM-5.2+Claude Code 组合同样成立，**说明不绑定特定基座**。

## 四、双赢来自什么：三机制协同，而非压缩上下文

论文对演化出的 Harness 源码做了分析，明确否定"简单粗暴压上下文"的解释：

1. **任务自适应推理与工具预算路由**：按任务描述自动选一套执行配置（profile），含**推理强度 + 工具调用上限**——简单任务用低开销配置，复杂任务才启用高推理强度；**运行时 hook 在工具调用达阈值时提醒 Agent 停止无边界探索，转向收敛与结果校验**；
2. **工具输出压缩（RTK）**：对重复日志、超长命令输出做**摘要折叠**，保留关键诊断信息、剔除重复冗余，控制上下文膨胀；
3. **精简静态提示词**：删减 prompt 中的重复内容，**同时保留完成任务必需的校验逻辑**——保证不会因为删提示词导致正确率下跌。

三条各管一件事：**预算（要不要继续探索）、带宽（喂进上下文的东西有多胖）、底座（系统提示里有多少废话）**。

## 五、迭代动态：单轮有天花板

观察多轮 epoch：**第一轮进化通常能降成本但性能提升有限；第二轮同时改善部分指标；到第三轮在维持甚至继续提升通过率的前提下继续压低成本**。这直接支撑了"递归"的必要性——**单轮进化会撞墙，多轮递归才能持续向外推帕累托前沿**。

## 深度分析

### 把"成本"抬成第一等公民，是对 RSI 叙事的一次纠偏

前几波 harness 自进化（DGM、Meta-Harness、PluginRSI）都在比"能不能更高分"，隐含假设是**算力不要钱**。HarnessPro 直接把这个假设拆了：**在生产里，通过率与成本是同一条曲线上的两个坐标**。一旦承认这一点，"最好的 harness"这个概念本身就不成立——只有"**在给定预算下最好的 harness**"。三档输出不是产品化包装，而是**多目标优化的必然产物**。

### 固定测试集 = 把"评分标准"也冻结成基础设施

无标签自进化的死穴是**自己给自己打分**，而 LLM 评判系统性偏乐观（召回 41.7% 就是证据）。HarnessPro 的处理不是"换个更强的 judge"，而是**在进化开始前合成一套可执行用例，然后整个周期不许改**——这让评分标准从"每轮重新判断"变成"一次性冻结的度量"，消除了候选间的评分漂移（同一现象在别的领域叫 benchmark contamination 的反面：**固定才能公平**）。召回 41.7%→83.3% 说明**"可执行"比"更聪明"重要**。

### "不低于基线"这条硬约束，防的是最典型的退化解

多目标优化最容易滑向"极限省成本、性能略降"的解——纸面上帕累托最优，业务上不可接受。第一层过滤把**初始版本通过率设为地板**，等于声明"**优化只能在不变差的前提下进行**"。这条约束在工程上等价于"回归门禁"，值得所有自改进系统照抄：**先设地板，再谈前沿**。

### 三机制指向同一个根因：Agent 不知道"什么时候该停"

预算路由的 hook 在工具调用达阈值时提醒收敛、RTK 折叠重复日志、精简提示词去掉重复——三件事都在治"**无边界探索**"。而"无边界探索"的成因往往不是模型笨，是**Harness 没给它停止条件**。这与淘宝智能建场那篇的"状态机决定允许做什么"是同一件事的两种写法：**一个是时间维度的预算，一个是空间维度的权限**。

### 三档并存的实践含义：别再找"一套打天下"

作者的结论很落地：**生产环境不需要追求一套 Harness 打天下，应当按业务预算准备多套版本**。这条与"用同一套 Prompt 服务所有场景"的旧习惯直接冲突——它要求团队把**成本档位**当成产品维度来设计（哪些请求走 lite、哪些升级到 heavy、升级由谁触发）。**这其实是"模型路由"思路向 Harness 层的平移。**

## 实践启示

1. **把成本写进目标函数**：只追通过率的自进化会自然漂向"更贵更强"，在有预算的场景里等于不可用。

2. **输出档位而非单一最优**：lite/medium/heavy 三档 + 各自权重，比"一个最佳 Harness"更贴近生产。

3. **固定测试集，且要可执行**：进化开始前合成、全程冻结；LLM 直接评判偏乐观（召回 41.7%），可执行用例把召回拉到 83.3%。

4. **先设地板再谈前沿**：过滤掉通过率低于基线 h₀ 的候选，杜绝"省钱牺牲能力"的退化解。

5. **采集要重复 rollout**：同任务跑 G 次再诊断，否则噪声会被当成"问题"。

6. **诊断报告必须带证据**：问题 + 对正确率/成本的影响 + 轨迹片段与日志位置，否则规划器只能猜。

7. **改动用 Git 记录**：每份候选 Harness 一次提交，才能追溯"哪次改动带来了降本"。

8. **三处降本点按顺序查**：有无无边界探索（加预算 hook）→ 上下文是否被冗余日志撑胖（RTK 折叠）→ 系统提示是否有废话（精简但保留校验逻辑）。

9. **别把延迟当主目标**：受负载波动影响大，用 token 成本做优化代理更稳。

10. **预留多轮**：单轮进化有天花板，第三轮才看到"维持通过率同时继续降本"。
