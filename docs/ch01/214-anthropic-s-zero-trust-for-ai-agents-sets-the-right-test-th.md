## 核心要点

1. **Anthropic's policy paper on AI agent security** — Anthropic published a position paper advocating Zero Trust architecture for AI agents: every tool call should be authenticated, authorized, and audited independently, not relying on session-based trust.
2. **The bearer token problem** — The author argues that long-lived bearer tokens (OAuth access tokens, API keys) are fundamentally incompatible with agentic AI. Agents accumulate tokens across services; if one token is compromised, the attacker has the agent's full delegated authority. The paper calls for short-lived, scoped, refresh-able credentials.
3. **The test the bearer token fails** — A Zero Trust agent should NOT be able to perform an action it wasn't specifically authorized for in the current scope, even with a valid token. Current bearer token models fail this test: a valid `repo:read` token can sometimes be escalated to `repo:write` via confused deputy attacks.
4. **Practical recommendation: per-action credential injection** — Instead of giving an agent a token at session start, the runtime should fetch a fresh, narrowly-scoped credential for each tool call, ideally with user-in-the-loop confirmation for high-risk actions (delete, send-money, modify-permissions).

## 深度分析

1. **The framework's own test retires its baseline recommendation** — The strongest idea in Anthropic's paper is a design test: does a control make the attack *impossible*, or merely *tedious*? Applied honestly, it disqualifies the paper's own credential baseline. A short-lived, narrowly scoped bearer token is still a bearer credential: whoever holds it can use it. Shortening its life shrinks the window a stolen secret is useful — it raises attacker cost without closing the door. By the paper's own standard that is a throttle, not a removal. The control that actually passes the test is a credential with no secret to steal: proof-of-possession bound to a non-exportable private key, where the agent signs each request and a compromised host yields no reusable string. Notably, the framework never mentions sender-constrained tokens (DPoP, OAuth Token Exchange, Rich Authorization Requests); it reaches toward non-exfiltratable credentials only at its Advanced tier, framed as PKI hardening rather than as the recognition that the bearer token is the residual flaw at every tier below. Its principle points past its prescription. See [Agent Security Architecture](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/agent-security-architecture.md).

2. **Agent+tool grants authorize the wrong unit** — The framework's authorization ladder (RBAC → ABAC → continuous authorization) is a taxonomy of control families, not a mechanism for authorizing a specific call. In its model the unit of authorization is "this agent may use this tool"; the actual call parameters are handled downstream as input validation — a filter against bad input, not an authorization decision. For agents that distinction is the whole game: "an agent has access to the payments tool" is not a useful grant, while "this agent may move at most $3,000, to this payee, once, before Friday" is. The parameters are the authorization context and must be evaluated per request, at call time — which is exactly where plain bearer-token models structurally fail, since a valid token can be re-used on calls far outside the intent of the original grant (the confused-deputy escalation path in [Agent Security Threat Models](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/agent-security-threat-models.md)). The paper gestures at the right instinct — "evaluate authorization at each action rather than session start" — but lists it as an aspirational top-tier capability without saying what the evaluation binds to. The constrained call itself, with its parameters as the evaluated context, is the missing authorized artifact.

3. **Delegation-by-logging is detection, not delegation** — The threat analysis is sharp: it names unscoped privilege inheritance (a manager agent passing its full access context to a worker that should have less) and confused-deputy amplification (a low-privilege agent relaying plausible instructions to a high-privilege one that executes without checking original intent). But the prescribed remedy is telemetry: trust boundaries, per-hop identity verification, logging inter-agent traffic to flag unusual patterns. Logging tells you afterward that authority leaked; it does not stop authority from leaking. The paper is candid that its own sub-agents can inherit up to the parent's full permissions, with the distinction captured in telemetry rather than enforced in scope — the flagged failure mode exists by design, mitigated by visibility. The removal-not-throttle answer is derived authority: the sub-agent receives provably narrower, purpose-bound, time-bound, subtask-scoped authority, so delegation narrows as it travels. Detection is the backstop for when structure fails, not a substitute for it. This ordering — structure before monitoring — is the same lesson drawn in [Youre Building Agent Security In The Wrong Order](https://github.com/QianJinGuo/wiki-public/blob/main/entities/youre-building-agent-security-in-the-wrong-order.md) and echoes the governance-before-identity sequencing in [Agent Security Three Step Sequence Harness Governance Identity Crewai](https://github.com/QianJinGuo/wiki-public/blob/main/entities/agent-security-three-step-sequence-harness-governance-identity-crewai.md).

4. **Tamper-evident logs prove integrity, not authorization** — The evidence ladder tops out at immutable, integrity-verified audit trails and full provenance chains. That is good observability, but cryptographic log integrity proves only that the record was not altered — not that the action was authorized, under whose authority, within what constraint. A perfectly tamper-evident log of an unauthorized action is still a log of an unauthorized action. What actually proves authorization is the authorization token itself: a verifiable artifact, standing on its own signature, showing that this agent was granted this specific access for this specific call — checkable independently of whoever holds the log. There is also a boundary lesson here: pushing delegation evaluation out to the resource recreates the hard problem in a new place, because resources lack the context to evaluate delegation intent. What a resource needs is an anchor — proof that authority existed and the action is attributable — while the evaluation stays where the context lives and only the outcome travels. Credential-vaulting, which keeps the bearer token but holds it server-side, proxies the secret rather than eliminating it; platform examples of binding identity to agent actions include [Aws Bedrock Agentcore Identity Security](https://github.com/QianJinGuo/wiki-public/blob/main/entities/aws-bedrock-agentcore-identity-security.md).

5. **The missing concept is a principal, not more primitives** — Beneath all of these gaps sits a concept the framework does not have. It treats agent identity as a starting condition — assign a cryptographic identifier, issue a certificate, attest the hardware — and builds controls outward. But agents do not pop into existence: a person or organization stood the agent up and delegated a slice of their own authority to it. That enrollment-time binding, ideally with confirmed human presence on the initial agent-to-person link, is the root of the chain; skip it and agent identity is only a name — cryptographically unforgeable, connected to no one. Post-hoc attribution (a user ID on session telemetry, or telling a high-privilege agent it "should verify the original user's intent" with no mechanism for how that intent was bound) is a guess recorded after the action. "Who acted, under whose authority" has to be established at the root and carried forward, not reconstructed at the end — the difference between knowing *what* acted and knowing *who is accountable*. The broader move is counterintuitive: not a better OAuth but fewer primitives — deleting API keys, bearer tokens, pre-registered clients, and redirect-based bootstrapping rather than tuning them. The right test has been written down; the bearer token fails it.
