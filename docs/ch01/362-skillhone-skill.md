# SkillHone：把 Skill 当活物维护，把决策历史当资产继承

> 📊 Level ⭐⭐⭐⭐ | 20.7KB

## 一句话结论

腾讯微信团队的 SkillHone（arXiv 2606.08671）指出现有 Skill 改进的两条路线有一个共同盲区：**都以工件为中心（artifact-centered），丢掉了决策上下文**。给后来的 Agent 的只有"改好的 Skill"，没有"当时为什么这么改、否决了哪些方案、靠什么证据判断改对了"。它的主张因此很朴素也很硬：**Skill 不是静态工件，而是需要持续维护的活物；要让它持续进化，就必须把支撑进化的决策历史一并保留。**

## 一、问题陈述：修复留下了文件，却没留下判断

开场场景几乎是通识：一个联网搜索 Skill 跑得不错，接口改版、加限流、页面结构换了，Skill 失灵；你修好、测试通过；过一阵环境再变，**老毛病复发，甚至重复修复同一个早已修过的问题**。

> **"问题的关键，不是修没修好，而是每一次修复背后的思考过程没有留下来。你只把修好的 Skill 文件交给了未来的自己，却没把'当时为什么这么改、否决了哪些方案、靠什么证据判断改对了'这份思路交出去。"**

**两条路线的共同盲区**：

| 路线 | 代表 | 做法 | 局限 |
|---|---|---|---|
| **生成式构建（Synthesis）** | **Skill-Creator** | 任务描述 + 示例 + 参考文档 → 直接翻译成可加载 Skill 包 | "**基本是一次性产出，改不动、也解释不了**" |
| **反思式优化（Reflective）** | **Hermes-SE / GEPA** | 跑"变异—评估—选择"循环，反复生成变体逐个评测选优 | 更强，"但**把改进看成一次有边界的运行，最终输出的还是一个更优的工件**" |

两者都漏掉了同一组问题：**"当初是哪个诊断触发了这次修订？否决过哪些备选方案？评估时观察到什么证据？为什么最终接受或拒绝了某个结果？"** 后果很具体——"**没有决策历史时，Skill 从 v0 迭代到 v3，中间可能反复重复旧的修复**"。

## 二、最关键的机制：双仓库 + 双权限边界

SkillHone 是**包在 Skill 改进过程外面的 Harness**——"负责组织执行、权限、反馈和记录的运行框架"。模型后端与外部工具固定，被持续修改的只有 Skill 本身（说明、操作流程、脚本、参考资料）。它解决的不是"从无到有造 Skill"，而是**"Skill 造好之后，怎么在无数个开发会话之间被持续改进，而不丢失每一次改动背后的理由"**。

| 仓库 | 装什么 | 类比 |
|---|---|---|
| **Skill 仓库** | 正在被修订的 Skill 包（`SKILL.md`、脚本、引用、模板） | 待改进的**产品** |
| **Skill 评估仓库** | 练习探针、oracle targets、校验器、执行轨迹、脱敏报告 | 检验产品的**测试设施** |

两者之间**"有一条严格的权限隔离线，这是 SkillHone 最关键的机制设计"**。理由一问就透：

> **"假如让同一个 Agent 同时查看标准答案、修改 Skill、运行测试并宣布成功，就很难判断：它是在改善通用方法，还是在迎合眼前的测试？"**

| 侧 | 可做 | 不可做 |
|---|---|---|
| **优化侧** | 读 Skill、历史决策、**脱敏**反馈；分析问题、提出修改、改 Skill | **不能读未脱敏的参考答案、校验器、执行轨迹** |
| **评估侧** | 运行候选 Skill、查看评估材料、分析失败 | **不能修改 Skill 仓库** |

一句话：**"一边负责想办法修，另一边负责拿证据检验。"**

## 三、脱敏不是礼貌，是防"背答案"

"**如果优化侧直接看到标准答案和校验器，Skill 很容易退化成背诵考试答案**，记住特定探针的正确答案，却没有形成真正可迁移的能力。" 所以评估侧跑完、分析完之后，**只产出脱敏问题报告**——失败模式的归纳、聚合结果、诊断假设，**绝不包含未脱敏的目标答案、校验器或完整轨迹**；而**"最终的大规模评测也始终在优化循环之外进行，确保 Skill 是被能力而不是被记忆推上去的"**。

这和 RSIHub"评测器归框架管、候选不能改评分规则"、HarnessPro"测试集冻结"是同一族防线，但方向不同：**那两条防的是"改尺子"，这条防的是"背答案"**（优化侧看得到证据、看不到答案）。

## 四、角色按需创建，稳定的是权限边界

论文特意澄清：**"各类角色并不是必须长期在线、数量固定的一群 Agent。"**

| 侧 | 角色 |
|---|---|
| 优化侧 | Proposer（提议者）、Explorer（探索者）、Developer（开发者）、Reviewer（评审者）、Decider（决策者） |
| 评估侧 | Executor（执行者）、Diagnoser（诊断者）、Reporter（报告者）、Auditor（审计者） |
| 中间 | **Dispatcher**：只负责创建子智能体、在两侧之间路由证据——**自己既不改仓库，也不碰未脱敏数据** |

判据一句：**"结构上稳定的是两侧的权限边界，具体角色则按任务派发。"** 这比"固定几个 Agent 组成团队"更可实现——**边界是架构，角色是调度**。

## 五、每步留下四类信息：决策记录 vs 文件 diff

**"文件 diff 能告诉我们'哪一行变了'，决策记录则把修改与问题、证据和结论连接起来。"** 论文的例子很实在：

> 一次修订加入了更严格的执行预算。只看文件差异，我们知道预算被收紧了；**结合决策记录，后续 Agent 才可能理解，当时是为了减少无效搜索，但评估发现它也截断了必要核验。**

关键一句：**"这样的经验即使没有进入最终 Skill，也有保留价值。"** 于是后续 Agent 能回答四个具体问题：

1. 这是新问题，还是过去处理过的问题？
2. 相似方案是否已经试过？
3. 此前失败是方案无效，还是适用条件不满足？
4. 这次应该撤销整个改动，还是只撤销其中一部分？

**定位也很清楚**：SkillHone 保存的是**"Skill 演化过程的维护记忆"**——与"记住用户偏好、保存任务事实"不同，这些历史**主要服务于下一次 Skill 修改**。而且——

> **"历史并不意味着旧结论永远正确。环境改变后，过去被拒绝的方案可能值得重试；过去成功的补丁，也可能已经过时。有用的历史应当帮助重新判断。"**

## 六、一轮进化怎么走：两份产物

流程：**评估侧让当前 Skill 跑一批练习任务 → 分析结果、输出脱敏反馈 → 优化侧读反馈、检索相关历史、形成诊断与候选修订 → 评估侧运行候选、返回新证据 → 按权限内可用的材料决定（接受 / 继续调整 / 拒绝 / 暂缓）→ 无论是否更新，这一轮的诊断·修改·证据·结论都进入历史**。

> **"一轮优化有两份产物：一份是当前 Skill，另一份是维护它所需的历史。"**

还有一句特别值得记住的话：**"即便某轮没有找到更好的版本，只要可靠地记录了失败原因，也可能为下一轮减少重复劳动。"**

## 七、实验与诚实的限定

- **场景**：深度调研（需搜索·导航·提取·核验·失败恢复，且外部网页常变）；
- **基准**：**GAIA 纯文本验证子集** + **WebWalkerQA 英文部分**；
- **开发数据**：WebShaper 的 **20 个样本**，与最终评测集分离，**最终基准不进入优化循环**；
- **双模型分工**：改 Skill 的控制模型 **Claude Opus 4.6**；执行任务的骨干模型 **Qwen3.6-35B-A3B**——"帮助改 Skill 的模型与最终执行任务的模型承担不同职责"；
- **结果**：相比论文中的商业检索参照高 **15.8 / 3.2 个百分点**；相比 **Hermes-SE 高 14.2 / 13.4 个百分点**。

**三条自我限定，写得很专业**：①"这些结果支持的是特定实验条件下的效果，**不能扩大成超过所有商业深度研究产品**"；②"平均分最好，也不意味着每个难度档位都领先"——**GAIA 的 L3 档，SkillHone 与 Hermes-SE 同为 31.6%**；**WebWalkerQA-EN 的 Easy 档，商业检索参照成绩更高**；③一个值得注意的现象：**"放入相关 Skill，并不保证 Agent 就能把事情做好。Skill 是否被整理成连贯、可恢复、能核验的任务流程，同样影响执行表现。"**

## 七·补、消融与内部实验（EMNLP 2026 Industry Track 版补充）

作者投稿的短版报道补上了三组此前缺失的硬证据：

**① 发表信息**：**"相关论文已发表于 EMNLP 2026 Industry Track。"**

**② 消融（最关键）**：

> **"表 2 采用相同执行模型进行消融。移除决策历史后，两项准确率分别下降 13.4 和 10.9 个百分点。"**

这把"决策历史有用"从**论证**变成了**因果证据**——注意消融控制的是**执行模型相同**，即差距不是模型差异带来的，而是决策历史这一项被拿掉的结果。**13.4 / 10.9 个点，是这套设计里最有力的一个数字。**

**③ 内部工具分析实验**：**七个场景**，相比初始技能**六个改善、一个持平，平均提高 18.8 个百分点**。

**④ 使用形态（比论文更能说明工程可行性）**：

> "完成安装、模型配置并让 Agent 加载相关 Skill 后，**用户继续原来的任务即可**；Agent 遇到**可复现故障**时，按已配置策略**记录 Issue 和回归测试，进入修复队列**。"

"这里的'无感'指**问题发现与修复触发融入原有任务**；默认**仍需审阅合并**，首次配置也需完成。"——**维护不是额外的一轮优化，而是日常任务的副产品。**

**⑤ 修复载体**："**DeepSeek Harness 在隔离分支上修复并运行关联测试，返回本地 PR**"；用户在工作台可看"**文件改动、运行记录和测试结果**"。

**⑥ 公开复现案例**（可验证性的证据）："项目提供了 **Phoenix tracing Skill** 的公开复现案例：**索引指向四份未随包发布的文档**，Agent 因而读不到承诺的指导。读者可以沿着**公开 Issue、已合并修复和固定版本样例**，检查问题与修复过程。"

**⑦ 与"冻结评估集优化"的分野**：

> "与从冻结评估集启动的能力优化流程相比，SkillHone 的日常维护模式可以**直接从真实故障开始，无需先造 Benchmark**；需要衡量更广泛能力时，再启用独立评估流程。"

这一句划清了它与 RSIHub / HarnessPro 那类"先建评测集再进化"路线的边界：**一种是"考试驱动"，一种是"故障驱动"**。故障驱动的好处是零启动成本、贴合真实分布；代价是**覆盖不全**（只修遇到过的错），所以需要"独立评估流程"兜底。

**⑧ 可接入的 Harness**："**Codex、Claude Code、Cursor** 等可调用 CLI 的 Agent 可以接入"。

**⑨ 边界声明**（口径意识）："商业检索基线使用托管检索，其余方法运行于**无预集成搜索工具的开放网络设置**，结果**仅适用于论文配置**。"

## 八、三条相关线的定位

| 线 | 研究什么 | SkillHone 的位置 |
|---|---|---|
| **Skill 获取** | 自动化 Skill 发现 / Skill-R1·SkillRL 的强化学习进化 / Skill-Forge 的领域构造 | 问的是"怎么得到好 Skill"；SkillHone 问**补集**：Skill 已存在并成为工作环境一部分之后，任务·工具·API·失败模式都在变，**后来的 Agent 怎么持续维护它** |
| **提示词/系统/Skill 优化** | Prompt 优化、Reflexion 口头反馈、DSPy 声明式编译、GEPA 反思进化 | 擅长"在一次优化运行内把工件改得更好"；SkillHone **换了一个轴**：把进化看作持续维护过程，继承的不仅是工件，还有"**失败—候选修订—评估—结果**"的结构化历史 |
| **多智能体协作** | MetaGPT 等角色分工 | 共享"角色分离"，但用于一次性产出；SkillHone 用于持续维护，且**子智能体由轻量调度器按需创建、按权限隔离** |

**自陈两点局限**：评测**只用英语基准**；**一次只进化单个 Skill**，多个相互依赖 Skill 的联合进化尚未处理。

## 深度分析

### 它把"记忆"的讨论从"用户"和"任务"挪到了"工件维护"

现有 Agent 记忆研究大多分两类：**用户偏好**（你是谁、喜欢什么）与**任务事实**（这次做到哪了）。SkillHone 提出第三类——**Skill 演化过程的维护记忆**：不是关于世界，也不是关于任务，而是**关于"这个东西以前为什么长成这样"**。这类记忆的对象是**工件自身的历史**，服务于下一次修改。**一旦承认记忆有这第三种用途，"每个 Skill 都该带一份变更说明书"就从好习惯变成了系统能力。**

### 双权限边界，是把"优化"和"评审"的机构分离搬进了 Agent

软件工程早就知道：**写代码的人和放行的人不能是同一个人**（否则无法排除"迎合测试"）。SkillHone 把这套制度做成了**运行时权限**：优化侧看不见答案，评估侧改不了代码。妙处在于它同时解决了两个问题——**公平性**（不迎合测试）与**可归因**（谁提出的、谁验证的，各有记录）。这与速卖通"主 Agent 不生产业务实体"、vivo"授权绑 Subject/Resource/Action"是同一种思路：**用权限做架构，不用提示词做纪律。**

### "脱敏反馈"是个被低估的设计点

大多数自进化系统的信息流是单向透明的：优化器能看到一切评估细节。这很方便，也很危险——**它会让优化目标悄悄从"泛化"漂移到"过拟合探针"**。脱敏的做法是**降低反馈带宽**：只给失败模式、聚合结果、诊断假设，不给答案与校验器。代价是优化更慢、需要更多推理；收益是**能力必须自己长出来**。这与 RSIHub"封存保留任务"、HarnessPro"固定测试集"构成三种互补的防作弊手法：**藏答案、留保留集、冻结尺子。**

### "失败轮次也是有价值的产物"——这条改变了迭代的记账方式

一般迭代只记"成功版本"，失败的尝试被丢弃。SkillHone 明确说：**"即便某轮没有找到更好的版本，只要可靠地记录了失败原因，也可能为下一轮减少重复劳动。"** 这条把优化从"版本序列"改成了**"判断序列"**——版本可能有几十个，但真正稀缺的是"哪些路走过、为什么不通"。它也是"两份产物"这个说法的真正含义：**Skill 是给系统用的，历史是给下一个 Agent 用的。**

### "历史不等于正确"这句限定，防止了另一种教条

"环境改变后，过去被拒绝的方案可能值得重试；过去成功的补丁，也可能已经过时。**有用的历史应当帮助重新判断**。"——这把决策历史从"权威档案"降级为"参考证据"，避免了"因为以前否过所以不能再提"的僵化。**这也是它区别于"知识库"的关键：知识库存结论，决策历史存判断过程，前者可复用，后者只能重估。**

### "放入 Skill ≠ 能做对事"，是对 Skill 生态的一记提醒

实验里那个现象值得单独记：**"放入相关 Skill，并不保证 Agent 就能把事情做好。Skill 是否被整理成连贯、可恢复、能核验的任务流程，同样影响执行表现。"** 这解释了为什么很多团队装了一堆 Skill 却不见效果——**Skill 的价值不在"有这段知识"，而在"这段知识能不能被组织成一条能跑、能恢复、能自检的流程"**。这与 RAGFlow"传统树状结构是负资产"是同一种反直觉：**结构/资产本身不是价值，被正确组织才是。**

## 实践启示

1. **给每个 Skill 建"决策历史"**：不只存版本，还要存"哪次诊断触发了这次改动、否决了什么、凭什么证据接受"。

2. **把 diff 和决策记录分开存、一起读**：diff 说明改了什么，记录说明为什么改、代价是什么。

3. **优化与评估做权限隔离**：改 Skill 的一侧看不到标准答案与校验器；评估侧改不了 Skill。

4. **反馈要脱敏**：只给失败模式、聚合结果、诊断假设——带宽换泛化。

5. **最终评测留在优化循环之外**：否则"被记忆推上去"会伪装成"被能力推上去"。

6. **角色按需创建，边界固定**：调度器只创建与路由，不碰仓库、不碰未脱敏数据。

7. **失败的轮次也入库**：记录失败原因，下一轮少走重复路。

8. **定期重估历史**：旧结论可能因环境变化失效，被否的方案可能值得重试——历史帮判断，不替判断。

9. **Skill 要整理成"可恢复、能核验"的流程**，而不只是塞知识；否则装了也不见效。

10. **别只看平均分**：分档位看（GAIA L3 打平、Easy 档落后都是信号）。

11. **改 Skill 的模型与执行任务的模型可以不同**：控制层用强模型、执行层用高性价比模型。

- [PluginRSI](https://github.com/QianJinGuo/wiki-public/blob/main/entities/pluginrsi-plugin-level-harness-evolution-ustc-meituan-2026-11-03.md) 用"插件库"积累可复用零件；SkillHone 用"决策历史"积累判断依据——**一个存产物，一个存理由**。
- [HarnessPro](https://github.com/QianJinGuo/wiki-public/blob/main/entities/harnesspro-pareto-self-evolution-cost-performance-thu-zhipu-2026-11-04.md) 冻结测试集防尺子漂移；SkillHone 脱敏反馈防背答案；[RSIHub](https://github.com/QianJinGuo/wiki-public/blob/main/entities/rsihub-unified-rsi-experiment-benchmark-bytedance-sjtu-berkeley-2026-10-28.md) 用封存保留任务防过拟合——**三种互补的防作弊手法**。
- [Harmony Harness](https://github.com/QianJinGuo/wiki-public/blob/main/entities/harmony-harness-multi-objective-self-evolution-google-2026-11-03.md) 处理多目标与负迁移；SkillHone 处理"单 Skill 跨会话维护"，并自陈多 Skill 联合进化未解。
- [RAGFlow](https://github.com/QianJinGuo/wiki-public/blob/main/entities/ragflow-knowledge-compilation-context-supply-layer-agent-native-db-2026-11-05.md) 的"结构本身不带来收益，装在叶节点里的东西才带来收益"与本篇"放入 Skill 不等于能做对事"是同一条反直觉。
