# Apple Silicon costs more than OpenRouter

> 📊 Level ⭐⭐⭐⭐ | 13.3KB

## 核心发现：本地推理成本是云端的 3~10 倍

文章通过四个维度的详细计算，揭示了 Apple Silicon 本地推理的真实成本结构 ：

### 电力成本极低

在 50~100W 功耗、$0.18/kWh 电价下，每小时电费仅 $0.009~$0.018，日均满负载运行约 $0.48 美金。电力成本在总成本中仅占 10~20% 。

### 硬件折旧主导成本

一台 M5 Max MacBook Pro（$4299）在 3/5/10 年折旧期限下，每小时摊薄成本为 $0.164/$0.098/$0.049——是电力成本的 5~10 倍 。这意味着**硬件折旧才是本地推理的最大成本项**，而非电力。

### Token 生成效率受限

M5 Max 运行 Gemma 4 31b 的吞吐量为 10~40 tokens/秒，对应每小时 36,000~144,000 tokens。OpenRouter 上同类模型可达 60~70 tokens/秒，速度是本地 MacBook Pro 的 3~7 倍 。

### 成本区间对比

以 $0.18/kWh 计算，本地推理的百万 token 成本约为 ：

| 场景 | Token 速率 | 使用年限 | 百万token成本 |
|------|-----------|---------|--------------|
| 悲观 | 10 tokens/秒 | 3年 | ~$4.79 |
| 基准 | 25 tokens/秒 | 5年 | ~$2.00 |
| 乐观 | 40 tokens/秒 | 10年 | ~$0.40 |

OpenRouter 上 Gemma 4 31b 的价格约为 $0.38~$0.50/百万 token，这意味着：

- **最乐观假设下**：本地与云端成本持平
- **常规场景下**：本地贵约 3 倍
- **极端场景下**：本地贵 10 倍

## 为什么本地推理仍然有吸引力

尽管数字不划算，作者指出了本地部署的不可替代价值 ：

- **隐私合规**：数据不离本地，适合处理敏感信息
- **离线可用性**：无网络依赖，适合野外/受限环境
- **高度定制**：可自由选择模型版本、量化方式、系统提示词
- **无速率限制**：不受 API 调用配额约束

## 关键变量：折旧期与利用率

"5 年折旧"是基准假设，但实际硬件寿命受以下因素影响 ：

- **加速折旧风险**：持续 100W 满负载运行会显著缩短电池和芯片寿命
- **真实利用率**：如果每日只跑几分钟推理，摊薄成本会远高于计算值
- **换机周期**：企业通常 3 年换机，实际折旧成本更高

## 深度分析：与专用推理引擎的技术路线对比

### 通用引擎估算的隐含假设，与专用路线的反例

原文的成本模型本质上是一个"通用引擎 + 消费级硬件"的统计视角：M5 Max 上用通用推理栈跑 Gemma 4 31b，吞吐量落在 10~40 tokens/秒的中位区间，硬件折旧按小时摊薄后自然远高于电力成本。 这个估算给出了成本的可信区间，但它隐含三个假设——引擎不做深度定制、量化采用通用配方、利用率按满负载或人机交互节奏计算——每一个在专用路线下都可以被改写。

[ds4.c](https://github.com/QianJinGuo/wiki-public/blob/main/entities/deepseek-v4-ds4c-antirez-local-inference-qbitai.md) 是对这三个假设同时发难的反例：antirez 用 C + Metal 从头实现、只服务 DeepSeek V4 Flash 一个模型（284B 总参数、13B 激活参数），在 M3 Ultra 512GB 上达到长 prompt 预填充 468 token/s、生成 27 token/s；KV Cache 写磁盘则用 token 序列的 SHA1 作为 cache key，下次请求匹配前缀直接加载，跳过重复 prefill——这对 Claude Code 这类每次发 25K token 初始 prompt 的 agentic 负载尤其有效。 换算到成本方程上：预填充速度提升约一个数量级，意味着同样的折旧费被分摊到多得多的 token 上——"折旧 ÷ 吞吐量"这个分式分子不变、分母变大，单位成本随之下降。这说明原文的 ~3 倍溢价结论是**技术路线选择的函数**，而非 Apple Silicon 的物理上限。

### 抽象层税：通用引擎为兼容性付出的代价

llama.cpp、vLLM 这类通用引擎的价值在于跨模型兼容，但兼容必须靠抽象实现，而抽象即妥协：通用的算子、内存布局和调度策略无法针对"某一个模型 + 某一块 GPU"的组合做极致优化。antirez 的判断是，本地推理领域新模型发布太快，通用引擎社区的注意力立刻被下一个要支持的模型吸走，深度优化永远轮不到单一组合。 专用引擎因此走一条"刻意的窄路"：一次只赌一个模型，配套的 GGUF 量化、HTTP API 与 coding agent 对接测试作为"本地推理三件套"整体交付。代价同样明确——模型一旦过时，一切从头来过；ds4.c 甚至连 CUDA 支持都要单独权衡。对成本计算的含义是：通用估算（如原文的 $0.40~$4.79/百万 token）代表的是**抽象层税后的基准价**，只有当模型 + 硬件组合足够固定、负载足够稳定时，为消掉这层税而重写引擎的工程投入才划算。Apple 自家的 MLX 框架介于两者之间——比 llama.cpp 更贴近 Metal 与统一内存，但仍以多模型通用性为目标，因此同样保留了一部分抽象层税。

### 非对称量化：信息论驱动的精度分配改写内存上限

ds4.c 的量化策略不是均匀降精度，而是按误差的**作用范围**分配预算：共享专家层、投影层、路由层保留 Q8，MoE 专家内部压到 IQ2_XXS/Q2_K（2-bit）。原理在于共享层误差会进入所有 expert 的输入/输出，具有全局性；专家内部误差只影响局部路径。 实测结论是 2-bit 专家在 coding agent 场景下仍能可靠调用工具。 这直接改写了原文的成本方程中的一个关键自由度：内存容量决定"哪一档模型能在本地跑"，而非对称量化让 284B 总参数级别的模型塞进消费级统一内存成为可能。原文用 $4299/64GB 的 M5 Max 配置估算 Gemma 4 31b，若目标换成更大 MoE 模型，2-bit 专家方案意味着不需要跳到 512GB 工作站档位——折旧分子可以从 $4299/5年 的假设切换到更低的硬件档位，或用同等预算换取更长的折旧期。

### 利用率与折旧期：两条路线共享的剩余变量

无论通用还是专用路线，成本方程中未被引擎优化消掉的是折旧期与利用率两个假设。原文给出 3/5/10 年折旧下每小时 $0.164/$0.098/$0.049 的摊薄，并承认持续满负载运行会加速电池与芯片老化，使 3 年档反而更现实。 利用率则是最容易被高估的变量：设备若每天只跑几分钟推理，摊薄成本会远高于满负载假设。 IER 框架把这个判断从"每百万 token 多少钱"提升到"每美元推理支出产生多少收入"：AI-infused 产品需要 10:1 以上的健康 IER，AI-native 产品可接受 5:1。 两条路线的适用边界因此可以统一表述——当单位任务 token 消耗被 agentic 工作流系统性推高时，专用引擎的吞吐优势与本地部署的隐私价值都只有在 IER 落入健康区间、且利用率接近满负载的交集里，才真正兑现为成本优势。

## 与 OpenRouter 的战略差异

| 维度 | Apple Silicon 本地 | OpenRouter 云端 |
|------|-------------------|-----------------|
| **速度** | 10-40 tokens/s | 60-70 tokens/s |
| **成本（百万 token）** | $0.40-$4.79 | $0.38-$0.50 |
| **延迟** | 高 | 低 |
| **隐私** | ✅ 数据不离设备 | ❌ 数据上传云端 |
| **离线可用性** | ✅ 完全离线 | ❌ 依赖网络 |
| **速率限制** | 无 | 有（受套餐限制） |
| **模型更新** | 需手动下载 | 自动更新 |
| **适合规模** | 小规模（<10万 token/天） | 大规模（>100万 token/天） |

对于**需要高速推理的生产场景**（每日处理百万级 token），直接使用 OpenRouter 更经济。但对于**私密数据处理、离线开发、定制化工作流**等场景，本地 Apple Silicon 的溢价有其战略合理性 。

## 成本计算框架：IER 视角

Inference Efficiency Ratio（IER） 提供了一个更系统的成本评估框架：

- **AI-infused 产品**（AI 是附加功能）：需要 10:1 以上的健康 IER 才能保持与传统 SaaS 可比的毛利率
- **AI-native 产品**（AI 是核心价值交付）：接受低至 5:1 的健康 IER

本地 Apple Silicon 推理的成本结构更适合 AI-infused 场景中的特定用例——当隐私和离线需求是硬约束时，溢价成本可以被其他维度的价值吸收。

值得注意的是， 还指出 **Agentic 工作流正在系统性推高单位任务的 token 消耗量**，可能抵消 per-token 定价下降的收益。这意味着即便是云端 API，总拥有成本（TCO）也不一定会随着模型降价而线性下降 。

## 推理优化技术对本地部署的启示

[推理系统优化](https://github.com/QianJinGuo/wiki-public/blob/main/concepts/inference-optimization.md)领域的关键技术（如 KV Cache 优化、连续批处理、Prefix Caching）对本地 Apple Silicon 部署有直接意义 ：

- **KV Cache 磁盘化**（ds4.c 采用）：用 SSD 带宽换 GPU 计算，对 Apple Silicon 统一内存架构下的超大规模模型特别有价值
- **Prefix Caching**：系统 prompt 和工具描述在多轮对话中复用，可以显著降低重复计算成本
- **非对称量化**：不同层分配不同精度，在降低显存占用的同时最大化了模型质量

这些优化技术的组合应用，使 Apple Silicon 本地推理从"不可能"变为"可实现但贵"——对于有特定隐私或离线需求的场景，这是值得评估的技术路径。

## 实践启示

1. **成本计算公式**：本地推理真实成本 ≈ 硬件折旧 ÷ 预期吞吐量，而非单纯计算电力成本。电力通常只占 10~20%，硬件折旧才是大头 。

2. **选型建议**：如果追求本地推理性价比，选择更新一代芯片（如 M5 Max 相比 M3）和更大内存配置，可以通过更高吞吐量摊薄单位成本 。

3. **适用场景判断**：

   - 日均 token 消耗 <10 万的小规模个人项目，本地 MacBook Pro 成本可忽略
   - 日均 >100 万 token 的高频场景，云端 API 更经济
   - 隐私敏感场景，无论规模，本地都有战略价值

4. **折旧估算**：文中 $4299/5年 的假设适合个人开发者；企业采购需根据实际换机周期重新计算，并考虑批量采购折扣 。

5. **速度差距不可忽视**：本地 10-20 tokens/秒 vs 云端 60-70 tokens/秒，在需要快速反馈的场景（如交互式 coding assistant），延迟差异会影响实际工作效率 。

6. **混合架构可行性**：一种折中方案——将需要隐私的低频高价值任务放本地，通用高频任务走 OpenRouter——可能是当前最具成本效益的架构选择 。

7. **专用引擎评估**：如果使用固定模型（如 DeepSeek V4 Flash），评估 ds4.c 这类专用引擎是否能通过极致优化弥补成本劣势。M3 Ultra 128GB + ds4.c 的组合在特定场景下可能比通用方案更具性价比 。
