## 深度分析

这份 AWS 官方方案的真正价值不在"怎么跑 H1"，而在它把物理 AI 训练基建抽象成一组可复用的工程决策：一个镜像、一份配置、两条计算路径，训练栈为 `nvcr.io/nvidia/isaac-sim:5.1.0` + Isaac Lab v2.3.2 + skrl/PPO。

### 双后端共用一个镜像，分界只在拓扑注入
HyperPod 与 Training Jobs 最终收敛到同一个 torchrun 调用 skrl trainer；差异被压缩进环境变量注入方式——Kubeflow Training Operator 给每个 pod 注入 `MASTER_ADDR`/`RANK`/`WORLD_SIZE`，Training Jobs 则把主机列表写进 `resourceconfig.json` 由 entrypoint 解析。于是"换后端"退化为配置变更而非代码分叉，不可移植性被隔离在 entrypoint 单层。

### 实例选型被 RT Core 硬性锁死
Isaac Sim 基于 Omniverse RTX 渲染器，要求 GPU 带硬件 RT Cores：G 家族（A10G/L4/L40S/RTX PRO 6000）全部可用，算力更强的 P 家族（A100/H100/B200/GB200）全部不可用——对机器人 RL 而言"最贵的卡不是可用的卡"。多节点集合通信在 8xlarge 及以上规格挂 EFA，为 NCCL 提供 RDMA 内核旁路传输。

### 故障恢复是三层设计
集群层：HyperPod 每节点健康监测 agent 做深度检查，故障自动重启或替换实例，并从上个 checkpoint 自动续训；任务层：启动时检测 FSx 上遗留的 `best_agent.pt`，命中即带 `--checkpoint` 续跑而非从头训练；存储层：配置 `checkpoint_s3_path` 后 `/opt/ml/checkpoints` 近实时同步 S3，中断重跑自动恢复。三层叠加把节点故障从人肉事故降级为自动事件。

### 4096 并行环境是规模化杠杆，也是成本叙事
单节点 2×`ml.g6.12xlarge`（8×L4）即可并行 4096 个 H1 环境；多节点进一步放大每次策略更新的经验多样性、加速收敛。但 1000 次 PPO 迭代只是冒烟量级，H1 粗糙地形的生产训练需再高一个数量级——GPU 并行仿真把月级真实经验压进小时级模拟，瓶颈随之从仿真速度转移到集群运维。

## 实践启示

1. **研发/生产两阶段映射两种计费后端**：调 reward 与网络结构的短迭代用按运行时长计费的 Training Jobs（无空闲算力成本），长程收敛训练用 HyperPod 常驻集群；MLflow 追踪是 opt-in，留空 URI 即关闭。
2. **先查 RT Core 兼容表再申请配额**：P 家族配额再充足也跑不了 Isaac Sim，选型第一步是对照兼容性表而不是跑分。
3. **把拓扑差异关进 entrypoint**：多后端方案的验收标准是训练代码零修改，所有差异收敛到 manifest 生成器与启动脚本。
4. **检查点要"三层都做"**：集群自动替换、任务启动检测、近实时 S3 备份缺一不可，否则一次节点故障就回吐数小时训练进度。
5. **可视化要进管线而不是事后导出**：WebRTC viz pod 与训练任务共用 FSx 卷，任意 checkpoint 即时回放，且 krelay 补上了 `kubectl port-forward` 不支持 UDP 的缺口。
