# RAGFlow 1.0：Search Harness 负责找到，知识编译负责省着用

> 📊 Level ⭐⭐⭐⭐ | 24.6KB

## 一句话结论

RAGFlow 联合创始人张颖峰把"RAG 已死/Grep 就够了"的行业叙事往前推了一步：**Harness 是 Agentic Search 的引擎，知识编译是它的上下文供给层**。理由是一组很实的账——**Pinecone 估算 Agent 有 85% 的计算精力耗在"重新发现"上**；而编译好的证据链"**命中时省 Token 90% 以上，没命中只损失约 2%**"。于是 RAGFlow 1.0 用 **Go 重写**并把自己重新定位成 **Agent Native Database**："**Harness 负责编排，RAGFlow 负责供给。**"

## 一、RAG 的四重困境

| 困境 | 核心判断 |
|---|---|
| **朴素 RAG** | "**相似不等于相关，相关不等于正确**"——单一通路（查询→嵌入→相似度）覆盖不了多样化查询：精确日期查询会被语义相近的噪音淹没；模糊概念问题用 Grep 又找不到，因为"没有人会在文档里写下那句与你查询一模一样的句子"；**有时答案要先定位一批候选文档，再逐个深入精读** |
| **高级 RAG** | "**复杂度换不来效果**"——GraphRAG/RAPTOR/Contextual Retrieval 各有论文与 Benchmark，但"部署和维护成本急剧上升，效果提升远未达到预期"；GraphRAG "在消耗大量 Token 之后并未带来检索效果的根本提升，仅在部分多跳问答场景有所改善"；**"一个需要专家才能调优的 RAG 系统，在真实企业生产环境中是站不住脚的"** |
| **Harness + Grep** | 见下节，是"极强的 Baseline，却并非终点" |
| **冷启动（最深层）** | 传统 RAG "**每次查询从零开始**"，"没有积累，没有状态，没有一个可以持续演进的认知基座"；同一任务同样数据跑两遍，答案可能不同，且"没有任何记录说明两次结果的差异来自哪里"；**Pinecone 估算 85% 精力耗在"重新发现"**——"这不是 RAG 的 bug，这是 RAG 的范式缺陷" |

## 二、Grep 为什么在 Agent 手里这么强

**先区分两类问题**：**语义发现问题**（答案藏在概念层，需要理解语义）与**证据定位问题**（答案存在于字面证据——名称、日期、文件路径、函数名、错误字符串）。Coding Agent 的大量工作属于后者，"一个精确字符串匹配工具远比语义搜索直接有效"。

**最硬的一条实证**：OpenAI 对 GPT-5 在 BrowseComp-Plus 上的搜索行为分析显示——**98% 的会话使用引号搜索**（远高于人类），且**查询长度中位数超过人类 99th 百分位**。结论一句：**"Grep 本身没有变，但它的用户从人类变成了 Agent，使用方式发生了质变。"**

**PwC 那篇的正确读法**：真正的洞见在结论——"**检索并非简单地把知识返回给 Agent，重要的是框架——它决定了什么可以填充到上下文，以及在利用上下文之前 Agent 必须执行哪些操作**"。所以"Grep 取代 RAG"是误读；准确表述是**"一个设计良好的 Agent Harness，即使只配备 Grep 这类简单工具，也能在很多场景下达到接近甚至超越复杂 RAG 的效果"**。

**Harness + Grep 的边界**：数据规模扩大后，"Agent 需要反复 Grep 才能找到答案区域"——**慢**（每次 Grep 都是一次 IO，迭代次数线性增长）+ **Token 消耗高**（每次迭代都把结果载入上下文，多轮累积巨大）；且"面对每一个新的上下文窗口，以 Harness 为中心的 Agentic 检索都会浪费调用次数，一遍又一遍地重新学习什么是有效的搜索策略"。

**工具该有几把**（微软 AgenticRAG 的启示）：**SEARCH**（广域召回，发现相关文档）/ **FIND**（单文档内精确定位）/ **OPEN**（带窗口读完整上下文）——"将搜索行为提升为 Agent 可编排的原子操作"；在 BRIGHT、WixQA、FinanceBench 均有提升，**消融显示最大提升来自"从单次检索转向 Agentic 工具使用"**。另一条实用发现：**"BM25 + Grep 的组合就可以让 Harness 表现更好——BM25 在单次检索中表现较弱，但在 Agent Loop 内部却强得多。"**

**由此得出的中性结论**：**Retrieval 本身就是一个 Harness 问题**——不只是"提供什么工具"，还包括：查询如何被鼓励或约束、结果如何呈现、返回是否含足够上下文、能否发出后续搜索、**何时判断信息已足够**、如何在工具间路由与编排。

## 三、知识编译：把"理解"从查询时移到索引时

> "不是每次提问时临时拼凑几个相似片段，而是**知识被编译一次，然后保持更新，而不是在每个查询上重新推导**。"（Karpathy 的 LLM Wiki）

Pinecone 在 Nexus 里把它做成 **Context Compiler**：用内置 Skills（文档处理、实体抽取、分块）把用户数据加工成结构化 Artifacts，**检索对象不再是未处理文本碎片，而是预编译、富含语义与实体关系的知识工件**。内部基准里"一个原本消耗 280 万 Token 的金融分析任务，在 Nexus 上仅用 4000 个 Token 完成"（**-98%，但"尚未在客户生产环境中广泛验证"**）。

RAGFlow 的形态更宽：**树状导航（含证据链叶节点）· 图状关联探索 · 时间线追踪 · LLM Wiki（图之上的可选合成层）· 本体模板 · Memory 模板**。

### 反直觉发现：树状结构本身是"负资产"

> "**并非把文档组织成树状结构，就可以给 Agentic Search 带来显著收益。** 这跟行业很多类似开源项目实践的结论——仅依据章节目录、或通过层次化聚类形成的语义结构提供导航就能带来更好效果——**截然相反**。这些传统树状结构在设计良好的 Agent Harness 中，**不仅没有带来增益，反而是负资产**：Agent 仍然主要依赖 Search 和 Grep。**真正让树状导航产生价值的是证据链叶节点。**"

也就是分工：**树负责组织（章节/小节/段落层级骨架），证据链叶节点负责压缩（导航到叶节点后拿到的是证据链而不是整段原文）**。

### 证据链的经济学：不对称收益

- **命中时节省 Token 90% 以上；没命中只损失约 2%**；FRAMES 多跳数据集上**平均节约 30–40% 以上**；
- **构造不需要强模型**（小模型即可，降低索引成本，大规模编译才经济可行）；
- **可追溯可审计**（每条 Claim 绑定 Evidence）；
- **不取代 Search/Grep**（后者负责找候选区域，证据链负责"省着用"）。

**两条进入路径**：①经专用工具读取（沿导航钻取、图探索、元数据选择）；②**直接作为上下文填充物**——"在 Harness 读取原始 Chunk 之前，先读取对应的 Claim/Evidence；如果判定证据与问题一致，就直接用证据作答，不再读取 Chunk"。第二条"把 Token 压缩点提前到了 Chunk 读取之前，是本架构中最省 Token 的路径"。

### 本体与模板体系

**本体不独立成引擎，而是编译模板之一**：业务人员配 TBox（概念、关系、属性、约束），编译生成 ABox 断言，"和证据链一样携带逐字证据与血缘"；断言可**独立搜索**（概念/实体/关系的直接查找）、**增强搜索**（规划阶段识别查询涉及的本体域，用断言扩展同义词、上下位关系、关联实体）、**约束搜索**（限定实体类型、关系路径、属性范围）。

**模板体系才是可扩展的关键**：**"编译能力的扩展以配置为单位，不以引擎分支为单位。"** 三个层面可扩展——编译形态（新增产物=新增模板）、抽取规则（同文档可按不同模板抽不同粒度命题与实体关系）、输出格式（综述段落/结构化字段/逐字引文）。**Memory 模板**的例子很说明问题：会话数据不按章节组织而按 `session_id` 聚合，新增模板后"Harness 在需要回忆历史会话时，可以像读取文档证据一样读取记忆证据——**同一套工具、同一套引用编号、同一套证据闸门**"。

## 四、Retrieval Harness 的纪律：把"谁来决定"分清楚

作者做了一次减法：**去掉按延迟、新鲜度、查询类型分流的多路路由器，只留一条循环**，但把决定权重新划分：

| 谁 | 负责什么 |
|---|---|
| **框架必须保证** | 每轮开始前先取回已编译证据并判断够不够；**不够就丢掉，而不是塞进上下文**；工具在这份语料上被证明无用就摘掉；模型调用不稳时按预算重试或降级；**引用编号在证据送达那一刻分配** |
| **模型擅长** | 用什么词去搜、先读哪篇文档、这段内容是否相关 |
| **检索引擎** | 正则匹配、排序、过滤——**精确执行，而不是让模型用自然语言模拟** |

判据一句：**"不追求'让模型自由选择工具'，而追求进入上下文的证据，是此刻最小的充分集合。"**

### 一次提问的五站旅程

1. **确认这份语料值不值得用结构化方式查**——从未做过知识编译的数据集，**导航、图探索工具连说明都不发**："没有编译过的语料，不为它用不上的能力付一分钱"；
2. **证据先行**——模型思考怎么搜之前，框架先做一次**跨整个语料库的扁平证据召回**；**不做文档路由**，因为"导航树对问题的路由是有偏的，一个小树会把每个问题都导向同一两篇文档，预取就退化成背景噪音"；
3. **二选一**——证据足够（数量够、来源够分散）则**一次模型调用直接成文，整轮不读一段原文**；不足则**整块丢弃**：**不写进系统提示（会被循环里每次调用重复计费），也不分配引用编号（模型从没见过它）**；
4. **带着工具的循环**——同一轮多个检索动作并行；**工具报错不中断整轮，而是变成模型能读懂的一条结果**（"一次写坏的正则，不该让整轮检索就此结束"）；步数上限与整轮时间预算双重收敛；
5. **确定收尾**——循环异常结束（只留旁白或超时）时，框架用问题+已到手证据合成真答案：**"问一次问题，不该得到一句'让我再查一下'。"**

### 工具按"为什么没找到"分工

| 症状 | 该用的工具 |
|---|---|
| 记得措辞，只是词形不对（拼写/派生/单复数） | 正则定位，一条正则扫过整库 |
| 记得意思，但不知道语料怎么说 | 纯语义召回——"关键词还留在查询里当过滤器，语义搜索就只是自我设限" |
| 只知道主题，不知读哪篇 | 沿编译好的导航树路由到文档，再钻取带逐字引文的命题 |
| 关系型（谁和谁相连） | 沿实体关系做子图探索 |
| 只想先圈定范围 | 元数据选择器只返回文档、不碰正文，**且句柄可在后续动作间传递**，使工具形成组合而非独立调用串 |

**最见功力的是零命中的解释**：词法检索零命中"不代表语料里没有这件事，而是意味着'**你的说法不是语料的说法**'"——两者对应完全相反的下一步。所以"结果返回的那一刻，工具就把判断和下一步直接告诉模型"：换一次语义描述，或换一类事物去描述。**"反馈写在证据返回的那一刻，而不是写在系统提示里等模型自己想起来。"**

### 深读：片段只能定位，不能作证

"一段被截断的窗口，很可能正好切掉了答案所在的那句话。"所以深读是**锚点式**：从刚才看到的内容里点名要读哪几段，系统先取回整篇文档的**阅读顺序索引**，再按点名精确取回全文；前后可扩几段、重叠窗口自动合并；每次告诉你这篇文档共有多少段、读到哪、还差多少。**边界从不含糊：任何被截断或根本没命中所查关键词的片段，都被明确标注"这只是一段窗口"，不允许被当作证据直接引用。**

### 引用是机械的

"证据在送达模型的那一刻就获得编号，**同一个片段在整个会话里始终是同一个号**"，答案里的引用标记最终被逐一解析回真实片段——**"模型不可能引用一段它没读过的内容"**。对照句很狠：**"靠提示词叮嘱模型'别瞎编引用'、再靠向量相似度反推句子来源的做法，本质上还是在赌概率。这里没有赌。"**

### 证据闸门：价值在"决定不发"

用 Jev 类决策模型回答一个比排序更靠前的问题：**"这批证据，现在有必要发给大模型吗？"** 够就放行、一次成文；不够就拦下、让循环继续找。**"它不做 rerank，不解决'怎么排序'……它的价值不在'发得更好'，而在'决定不发'——把 Token 降在渲染之前，而不是等塞进上下文再靠摘要压缩。"** 对称面是**"决定不读"**：深读前先用 Claim/Evidence 判断是否足以作答。**发与读两个决策合起来，才是 Token 压缩的完整闭环。**

## 五、架构与工程

- **编译层**：把同一份原文翻译成几种结构——层级导航、实体关系、时间线、思维导图、页码索引、Wiki，以及最关键的**原子命题**（"一句话的事实，配一段必须是原文连续子串的逐字引用"）。所以"**命题之所以能被直接引用，是因为它自带证据，而不是因为它被压缩过**"；每条产物携带血缘，**文档删除时相关贡献被精确摘除**；**重建是幂等的整体重算**——"宁可重算，也不留半新半旧的结构"；
- **执行层**：正则与排序**下推到引擎内部**而不是取回内存过滤；深读的"读索引"与"取全文"共用同一套阅读顺序；**原文通道与派生内容通道严格隔离**——"面向模型阅读的正文检索，永远排除编译产物；编译结构只通过编译工具进入上下文。**派生知识不冒充原文，原文也不被结构淹没**"；
- **运行时**：会话是一份事件日志，失败的一轮**回滚**，不把"有调用、没结果"的残骸带到下一轮；**跨轮持久化只保留每轮最终答案，不保留取证轨迹**（长对话成本不随轮次线性爆炸）；限流/过载/抖动按退避重试、客户端错误快速失败、有故障转移链；**兜底成文的模型与检索用模型分开实例**；
- **上下文可审计**：每条真正进入模型的证据都有记录（命中哪些词、是否被截断、原文多大），每轮成本按阶段归因（取证 / 证据直答 / 汇总）——"**回答错了时，我们能分清是'没找到'还是'找到了没用上'，这两种问题需要完全相反的修法**"；
- **闸门接入**：落在工具结果渲染与提示词组装之间，**不改变任何工具的调用契约**（工具返回的始终是候选，不是结论）；三处必经=证据召回的充分性判断、循环中每一轮的证据准入、成文前的证据裁剪；**先进影子比对**再按环节替换，因为"证据闸门的价值必须用'省了多少 Token、有没有把该发的证据拦掉'来验证，**而不是用'模型觉得它好不好'来验证**"。

**产品**：RAGFlow 首个 **1.0 正式版**，**完全用 Go 重写**（原 Python）——不只是性能，"编译层的并发编译、工具层的并行调用、Harness 的长会话状态管理，在静态类型与原生并发模型下更可控"；定位从"端到端 RAG 引擎"升级为 **Agent Native Database**："不论 Harness 需要原文片段、编译后的证据单元、导航结构、关系骨架还是记忆事实，都可以从 RAGFlow 获取。"

## 深度分析

### 它把"RAG vs Grep"的辩论升级成了"引擎 vs 供给层"

双方观点其实不冲突：Grep 派证明**编排比召回算法更重要**，RAGFlow 承认这点，然后指出**编排再强也要付探索费**。于是分工变成：**Harness 决定"怎么找"，编译层决定"找之前手里已有什么"**。这个拆分的好处是两者可独立演进——换 Harness 不影响编译产物，换编译模板不改变工具契约（作者特意强调闸门"不改变任何工具的调用契约"）。**"Grep 取代 RAG"和"RAG 必须复杂"两个口号，在这个框架下都变成了错的提问。**

### "树状结构是负资产"是全文最反常识、也最需要被听见的一句

行业里大量"给文档加目录树/层次聚类"的工程，默认假设结构本身带来导航收益。这里的实测结论相反：**在已经很强的 Harness 里，纯结构没有增益，甚至是负资产**——因为 Agent 仍靠 Search/Grep 找，结构只是多了一层要被消化的东西。真正的增益来自**叶节点承载的压缩单元（证据链）**。这条对做知识库的人是个硬提醒：**结构不是价值，结构里装的东西才是。**

### 90% / 2% 的不对称，才是"预编译"能成立的经济学

任何"索引时多干活"的方案都要回答"如果没用上，白干多少"。这里的账很清楚：**命中省 90%+，未命中只损失 2%**——因为证据链是**叶子上的压缩单元**，体积小、可随时丢弃；反例是"预取整篇文档"或"预生成整页摘要"，未命中时的浪费就变成灾难。**所以"预编译什么"比"要不要预编译"更重要：越小、越贴着答案形态的产物越值得预编译。**

### "决定不发"与"决定不读"，把 Token 治理从生成后挪到了生成前

大多数团队优化 Token 的方式是摘要、截断、压缩——都发生在**内容已经进了上下文之后**。这里的两个决策发生在更早的位置：闸门在**渲染前**拦一道，深读前用证据判断**要不要读原文**。这与 HarnessPro 的"预算 hook"、高德的"校验分档"是同一族思路：**在成本发生之前做决策，而不是在成本发生之后做优化。**

### 零命中的解释权，是被低估的能力

"词法零命中 = 你的说法不是语料的说法"——这条把失败从"没有答案"重新定义为"**换一种说法**"，而"没有答案"和"换一种说法"的下一步完全相反。多数工具只返回空结果，把解释责任推给模型（于是模型开始换关键词瞎试，或者干脆编）。**在工具返回值里就带上诊断与下一步，是 Agent 时代接口设计的一条通用原则**（这与 Anthropic 那篇"截断要给出可执行下一步、错误要给可操作修正"完全同源）。

### 机械引用 vs 概率引用，是"可交付"的分界线

"编号在证据送达那一刻分配、模型不可能引用它没读过的内容"——这件事看起来只是工程细节，但它决定了答案能不能被审计。**用相似度反推引用来源，本质是在事后猜"这句话大概来自哪里"**；服务时分配编号，则让引用成为**事实**而非**推断**。对任何要进企业流程的 Agent，这条都是硬要求。

## 实践启示

1. **先算探索成本**：如果你的 Agent 在有强 Harness 时仍反复搜索同一批数据，问题不在检索算法，而在"每次从零开始"。

2. **把"理解"前移到索引时**：在索引期产出**原子命题 + 逐字引用**，比在查询期做更复杂的召回更划算。

3. **只预编译"小且贴答案形态"的产物**：命中省 90%、未命中只损 2%，是因为证据单元小；别预生成整页摘要。

4. **别指望结构本身带来收益**：目录树/层次聚类在强 Harness 里可能是负资产；价值在**叶节点承载什么**。

5. **原文与派生内容两条通道严格隔离**：正文检索排除编译产物，编译结构只经编译工具进入上下文——**派生知识不冒充原文**。

6. **决定权三分**：框架管"够不够、丢不丢、编号何时分配"，模型管"搜什么词、读哪篇、相关与否"，引擎管"正则/排序/过滤"。

7. **证据最小充分集**：不够就整块丢弃（不写系统提示、不分配编号），别用无关证据填满上下文。

8. **闸门做在渲染前**：问"这批证据现在有必要发给大模型吗"，而不是塞进去再压缩；对称地，深读前先问"是否已足以作答"。

9. **工具按"为什么没找到"设计**，并在返回值里带诊断与下一步（尤其零命中的解释）。

10. **片段只能定位不能作证**：截断/未命中关键词的片段必须显式标注"只是窗口"。

11. **引用编号服务时分配**，别用相似度反推——这是可审计性的底线。

12. **可观测要能区分"没找到"与"找到了没用上"**，因为两者的修法完全相反。

13. **闸门上线用影子比对**，并以"省了多少 Token、有没有误拦"验收，而不是"模型觉得好不好"。

14. **扩展以配置为单位**：新增一种编译形态=新增一个模板，而不是新增引擎分支。
