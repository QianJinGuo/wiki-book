# PluginRSI：把 harness 拆成插件，让自进化能「攒零件」

> 📊 Level ⭐⭐⭐ | 12.0KB

## 一句话结论

中科大 + 美团 + 武大 + NUS 的 PluginRSI（arXiv 2609.32423）指出旧范式（Meta-Harness、DGM 一类）的两个致命短板：**很难单独测试某一个想法**（记忆/工具/角色/流程耦合在一起，改了记忆模块，流程与工具也跟着变，你分不清收益来自哪）、**来之不易的好机制容易被覆盖丢失**（这一轮摸出的"终端报错反馈逻辑"，下一轮全盘改写时被 AI 顺手删掉）。它的解法是**零件化**：**Harness = 一批标准插件 + 一段只做调度的 Workflow（<300 行）**，业务能力全部下沉到插件；进化分**插件变异**与**Harness 重组**两阶段，并把验证有效的零件存进**共享插件库**反复复用。

## 一、组件模型：插件与工作流的分工

| 组成 | 内容 | 约束 |
|---|---|---|
| **插件** | 一份 YAML 配置（输入输出格式、参数）+ 一份 Python 实现，标准接口，四大类 | 独立、可替换、可单独测试 |
| **Workflow** | 只负责调度：何时调用哪个插件、输出如何流转、控制任务循环 | **不写复杂业务逻辑**；实测 <300 行 |

两个角色分工也清楚：**Solver** 用当前 Harness 做任务、留下工具调用与执行轨迹与评测结果；**Proposer** 读这些材料提出插件与工作流的修改方案。**搜索过程中两个底座模型都保持固定**，递归发生在"上一轮的 Harness、插件与运行反馈进入下一轮"这个优化闭环里。

这套拆分把两个容易混的问题**分开**了：**一个机制本身能不能改好 → 换插件来试；几个机制怎样配合 → 交给工作流来试。**

## 二、阶段一：插件变异——一次只改一个零件

每轮并行生成多组实验：取**均衡小批量**（一半做对、一半做错的案例）→ Proposer 看执行轨迹**定位失败根源** → **只选中一个插件修改，Workflow 与其余插件原封不动** → 在小批量上测试 → **提升则入库，否则丢弃且不影响当前 Agent**。

两个收益直接对应旧模式的两个短板：**变量只有一个，性能变化可明确归因到这个插件改动**；**优秀改动永久入库，不会被后续整机改写删掉**。

论文里三个真实的插件改进例子，都很具体：

- **记忆插件**：原本按关键词匹配召回，常返回大量重复；变异后**加去重逻辑，优先返回"从未展示给模型的新证据"**；
- **终端工具插件**：进化出**失败感知反馈**——不只返回命令输出，还识别"藏在成功返回码下的测试报错"并补充失败提示；
- **角色插件**：进化出**修复范围控制**，约束 AI 不要大范围乱改代码。

## 三、阶段二：Harness 重组——挑零件、编流程、装新机

Proposer 读取本轮插件变异的全部结果 → 从插件库**挑一批有价值的新旧插件** → **修改 Workflow 调度逻辑**（调用顺序、信息传递方式、协作流程）→ 拼成完整 Harness 在**完整验证集**评估 → 更好则成为新一代 **incumbent** 进入下一轮。

**消融证明两个阶段缺一不可**：去掉任一阶段性能明显下滑；**只拥有插件库、但没有"变异 + 重组"流程，不会带来明显收益**——也就是说，零件本身不是资产，**"会改零件 + 会编流程"才是**。

## 四、结果：跨模型迁移与"热启动"是最大亮点

**SWE-bench Verified（真实 GitHub 修复，held-out）**：

| 提案模型 | PluginRSI | Meta-Harness | 差值 |
|---|---|---|---|
| Kimi-K3 | **69%** | 63% | +6 |
| GPT-5.6 Terra | **65%** | 55% | **+10** |

**关键特性一：进化得到的 Harness 能跨模型迁移**——用 Kimi-K3 迭代出的外壳**直接套给 GPT、GLM，不再优化**仍维持明显优势。作者点出现实价值：**经常需要把一套 Agent 方案迁到不同底座模型**。

**关键特性二：插件库能"热启动"新 Agent**——插件库从初始 **75 → 132** 个，而 **Workflow 调度代码仍不到 300 行**（复杂度沉到零件里，调度保持可控）；从头启动一个全新 Agent 时，**直接加载已进化的插件库仅两轮，未见任务解决率就到 69%**，而**从零进化同样步数只有 65%**——沉淀的工具箱**加速了未来其他 Agent 的迭代**。

**效率与过拟合**：相比 Meta-Harness，PluginRSI **用更少的累计模型调用拿到更高性能**，且**验证集提升能同步反映到未见测试集**（过拟合风险更低）；而 Meta-Harness 常"在训练任务上越来越好、陌生任务性能波动且提升有限"。**跨领域问答**（数学/法律/医学/金融/科学）：见过的训练域提升巨大，**跨完全陌生领域收益变小**——作者承认"不同学科需要完全不同的策略，插件跨领域复用存在天然天花板"。

## 五、作者自报的四个短板（可直接当风险清单）

1. **固定任务集迭代** vs 现实任务分布持续变化；**插件库越来越庞大，如何管理与裁剪是待解问题**；
2. **跨差异巨大的领域时迁移增益有限**，需多领域联合优化；
3. **单插件假设的边界**：流程假设"改一个插件、其余不变"，但有些能力提升需要**多插件 + Workflow 协同改动**，当前流程很难发现这类机制；
4. **成本**：插件变异阶段有 token 开销——相比 Meta-Harness，**输入 token +7.5%、输出 token +19.8%**。

## 深度分析

### "零件化"的真正价值是把进化的**单位**从系统改成假设

旧范式的进化单位是"整个 harness"，于是每次改进都是一次**不可分解的假设检验**——一旦性能变了，你无法判断是哪个想法起作用。PluginRSI 把单位降到单插件，等于**把一个大假设拆成一组可独立验证的小假设**。这与科学方法的关系是直接的：**能独立证伪的改进，才能被积累**。

### 插件库是"经验资本"，而 Workflow 短小是它的必要条件

插件 75→132 而 Workflow <300 行，这个对比说明了一件容易被忽略的事：**复杂度必须有地方沉淀**。若把机制堆在调度脚本里，脚本会变成一个不可读的巨物，也就无法被单独测试和复用。**"能力下沉到插件、调度保持声明式"**——这条约束同时服务了可测试性、可复用性与可维护性。

### 跨模型迁移，暗示进化出的其实是"工程知识"而非"模型适配"

如果进化只学到"这个模型的脾气"，换模型必然失效。Kimi-K3 进化的外壳套给 GPT/GLM 仍有效，说明被沉淀的是**关于任务与工具的通用工程知识**（如何反馈失败、如何避免大范围改动、如何避免重复证据）——这类知识本来就与底座无关。**这为"harness 是可迁移资产"提供了实证**。

### 热启动的 69% vs 65%，是"递归"最实的一次兑现

递归自我改进常被质疑"只是多跑几轮"。这里给出可测形态：**加载旧插件库两轮 = 69%，从零同步数 = 65%**——**前者省下的不是轮数，而是"重新发现已被验证的机制"的成本**。但要清醒：这 4 个点的差距来自同一任务族，**跨领域迁移收益会变小**（作者自己也这么说）。

### 与 Harmony Harness 的分工：一个管"目标"，一个管"结构"

同一批"harness 自进化"研究正在分头解决不同瓶颈：**Harmony Harness 解决"优化什么"**（多目标 + 留出集 + 过拟合门），**PluginRSI 解决"怎么改才不丢经验"**（零件化 + 共享库 + 变异/重组分层）。两者可以叠加：**用 PluginRSI 的结构承载 Harmony 的多目标选择**——这也提示这一领域的下一波工作会在"结构 × 目标 × 验收"三维上组合。

## 实践启示

1. **先问"能不能单独测"**：如果一次改动会同时影响多个机制，收益就无法归因——先把 harness 拆成标准插件。

2. **能力下沉、调度声明化**：插件承载业务能力，Workflow 只负责顺序与流转，保持短小（<300 行是可参照的量级）。

3. **变异阶段用均衡小批量**（一半对一半错），一次只改一个插件，其余冻结——这是最便宜的归因方式。

4. **改动先小批验证再入库**：提升则入共享库，无提升直接丢弃且不影响线上 incumbent。

5. **重组阶段必须在完整验证集评估**，否则"零件好"会掩盖"组合差"。

6. **把插件库当资产运营**：它带来热启动收益，也需要**管理与裁剪策略**（数量膨胀是已知风险）。

7. **拿跨模型迁移当质量检验**：进化产物若只在原模型上有效，说明学到的是适配而非知识。

8. **别指望单插件假设覆盖一切**：需要多插件协同的机制，要另设搜索路径。

9. **算清楚成本**：零件化带来 +7.5% 输入 / +19.8% 输出 token（相对 Meta-Harness），换的是可归因与可复用。
