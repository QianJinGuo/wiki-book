# 支付宝大促 Harness：把三年工程积累翻译成 AI 能执行的语言

> 📊 Level ⭐⭐⭐⭐⭐ | 31.4KB

## 一句话结论

支付宝大促技术团队用三年给出了一条**没有跳步的演进曲线**：2024 做工程化（一天一发、800 行变更、90% 覆盖）→ 2025 做组件化 + AI 补全（省 106 人日、30% AI 代码）→ 2026 上半年被 Claude Code 改变认知（"AI 第一次能'接活'了"）→ 618 裸用 Agent 交出代价（32 个需求、**1332 次人工澄清**）→ 双11 用 **六层 Harness** 接管。他们的核心判断是：**"要让 AI 真正接管交付，光等更强的模型是等不来的"**；而 Harness 的原料**不是新造的东西**，正是前两年的工程积累——**"它们没有被 AI 淘汰，而是被翻译成 AI 能执行的语言"**。

## 一、大促的四个约束（决定了什么方案能活）

| 约束 | 原文 |
|---|---|
| **时间刚性** | "排期和集团大促战略时间强绑定……交付窗口以周计、**全倒排**——'延期'这个选项在大促字典里不存在" |
| **质量底线** | "优惠、权益、资金全是高敏感业务……事故代价被数倍放大，**质量标准只升不降**" |
| **需求脉冲** | "平时细水长流……大促前集中爆发，横跨直播、互动多个会场与**几十个功能模块**" |
| **唯一不变的是变化** | "每年的会场玩法、权益形态、对接方都在换，**去年沉淀的经验今年只剩部分适用**，再加上每年都有新人进场" |

最后一条是全文的隐藏主线：**体系必须能应对"变化"这个常态**——这也解释了为什么后面要花大篇幅做知识库保鲜和自进化。

## 二、三年演进：每一步都在把瓶颈往后推

| 年份 | 做了什么 | 数字 | 留下的瓶颈 |
|---|---|---|---|
| **2024** | 主干研发 + 小 PR 合入 + Feature 化拆分 | **一周一发 → 一天一发**；**单次变更 ≤800 行**；**变更行/分支覆盖 90% 才合入**；首个大促 **0 故障 / 0 线上问题 / 0 重大舆情** | "需求规模量级变大，**人力投入线性上涨**" |
| **2025** | 组件化沉淀（签到/抽奖/发奖/弹窗）+ CodeFuse 补全与单测 | 节省约 **106 人/日**；AI 生成代码占比达 **30%** | "补全的本质是'**Coding 加速器**'……系分、自测、联调仍一条条是人工，**模块怎么拼还是要人来决策**。瓶颈没有消失，只是从'写代码'转移到了'**串流程**'" |
| **2026 上半年** | **Claude Code 引爆 Agent Coding** | — | "关键变化不是代码写得更快，而是 **AI 第一次能'接活'了**……从'补全工具'升级为'**可以委派的执行者**'" |
| **2026·618** | Agent Coding 首次实战 | **32 个需求** | "**人工澄清 1332 次**，AI 协作的人力成本全部压在人身上" |
| **2026·双11** | **六层 Harness** | 见下文 | 自评"第三层半" |

618 的复盘结论是全篇最贵的教训，一句话：

> **"裸用 Agent 不可行——AI 产物质量不可控、对业务上下文一无所知，每一分不可控都要人来兜底。"**

注意这两个病因的措辞：**质量不可控**（产物问题）与**对上下文一无所知**（信息问题）。双11 的六层里，正好有两层专门治它们。

## 三、六层 Harness

> Harness = "模型外层的运行框架：环境、工具、上下文、编排、可观测、验证、治理"。

| 层 | 目标（原文） | 治的是 |
|---|---|---|
| **上下文精细化** | "让流程每步拥有'**恰好够用且正确**'的信息" | 618 的"一无所知" |
| **执行编排** | "把'散装工具的人工串联'升级为可编排的自动流水线，**模型知道下一步该干啥，人只做裁决**" | 618 的 1332 次澄清 |
| **工具/能力资产** | "每个编排节点都有'够用、可复用'的执行 Skill，且**运行环境一致、产物稳定**" | 复用与环境漂移 |
| **记忆与状态** | "跨阶段状态**外化可接力**，并把澄清与现场经验**晋升为知识回流上下文层**" | 长任务断链 |
| **评估与观测** | "可量化、可下钻、可归因，优化从'感觉'走向'证据'" | 无法归因 |
| **约束与恢复** | "错误**结构上不能犯**、出错可回退重试，**而非靠 AI 自觉**" | 概率性漏网 |

三层业界对照也给了（OpenAI=环境即产品；Anthropic=架构简单可检查、工具为 Agent 设计、上下文渐进给、长任务可恢复+交接产物；LangChain=评测是护城河、单步/回合/多轮三层评测 + 可重置可复现环境）——但他们没照抄，而是**从自己的四条业务约束反推**。

## 四、知识库：四个触发源、三层加载、每日保鲜

**建库动机**：**"AI 与人对大促业务知识断层，导致每次需求都要从零解释业务背景、反复澄清"** → 建 `appcampaignocb_kis`，"沉淀为**标准事实**，作为大促上下文管理的底座"。

**生产链路（现场蒸馏，准入成库）**：

```
四个候选触发源：人工沉淀 / CC 会话蒸馏 / Aflow 复盘节点 / 代码与知识库比对
   ↓ 筛选闸门：属本应用 · 可复现 · 无已有覆盖
   ↓ 六大板块套模板成文
   ↓ 准入门禁：AI 预审 + 评测集回归人工 check
   ↓ 合入并挂 AGENTS.md 索引
```

关键判断：**"研发现场出现的澄清与结论都是潜在候选"**——知识不是坐下来写的，是从澄清里捡出来的。

**使用：三层渐进式加载**（这一层设计最值得抄）

| 层 | 内容 | 加载方式 | 为什么这么设计 |
|---|---|---|---|
| **规则层** | "编码前必查规范、澄清前必查知识库" | **随会话自动注入** | "是**硬约束，不依赖模型自觉**" |
| **导航层** | **AGENTS.md 文档地图** | 常驻上下文 | "**先看地图再取正文**" |
| **召回层** | knowledge-search | 按任务语义检索 | "**不全量灌注**" |

**检索命中后的三档处置**（把"不知道"变成可操作分级）：**高置信 → 直接采纳不澄清；中置信 → 确认式提问；未命中 → 才开放问人**。这三档直接对应 618 的 1332 次澄清——**把人力澄清压缩成只有真空白才发生**。

**保鲜：巡检比对，自动回流**——"每天跑一次全量巡检，逐篇将知识与代码现状比对，找到过时段落、失真章节与失效结论。**偏差自动生成修复 PR**，走与入库相同的准入门禁，合入即完成一轮保鲜"；另有"按模块出题的评测集持续'考试'，保鲜度与准确率以答题结果度量"。

**数据（真实指标，含口径）**：

| 指标 | 值 | 口径 |
|---|---|---|
| 规模 | **122 篇 / 六大板块** | 产品·技术方案·架构决策·业务术语·测试·问题排查 |
| **保鲜率 H_fresh** | **88.10%（优）** | **全量比对 14 模块**，每天定时跑 |
| **准确率 H_acc** | **86.11%（优）** | **14 模块 196 道**问答评测集（基于规则生成） |
| **采纳率** | **76.2%** | 本轮巡检提交 **68 个修复 PR**，**89.7% 已合入**，**一次通过率 72.1%** |

**四条经验（要 / 不要）**：

| 环节 | 要 ✅ | 不要 ❌ |
|---|---|---|
| 内容取舍 | 与代码保持一致，**只存结论与关键决策** | 罗列过多代码详情——**保鲜成本高、检索噪音大** |
| 组织方式 | 分模块 + AGENTS.md 导航；**全局约束以 ADR 模式全局生效** | 一篇方案留多个结论，"AI 检索到无所适从" |
| 加载消费 | 渐进式：索引常驻、规则注入、按需召回 | **全量灌进提示词——上下文膨胀、关键事实被稀释** |
| 质量准入 | 版本控制 + 定时巡检自动提 PR | **AI 自审直接通过**，跳过人工 check |

## 五、Aflow + Multica：编排层与界面层

**Aflow（自研编排平台）**："让 AI 与人按业务自己的流程协作，**过程可看见、可感知、可干预**"。能力：流程编排 + **产物上传与传递** + **节点级 checkpoint** + 后置 Prompt + 钉钉通知。

它解决的是长任务的两个顽症：**"每个节点都有干净上下文"**——"很好解决长任务执行过程中**上下文污染和爆炸**的问题"；以及**断点恢复**。

**三条关键经验**：

- **多 Agent 对抗性检查**："系分、代码以及自测报告都有准出标准"；
- **门禁节点必选**："AI 预审 + 约束条件 + 项目规范，必须遵守，保障 AI 产物在可控范围，**不跑偏**"；
- **断点恢复：重启胜过修补**——"**状态沉到文件里**，Agent 随时可以在一个**干净的上下文窗口**里接力继续"。

第 3 条是全篇最反直觉的工程判断：**长任务出问题不要修，要重启**——因为修补会在脏上下文里越修越乱，而重启只要状态外化过就能无损接力。这与 Claude Code 的"长任务可恢复 + 交接产物"、腾讯 DSH 的"Session 藏起来"是同一种解法。

**Multica（多 Agent 协作平台，基于开源改造）**："以**任务（Issue）**为载体统一承载需求上下文与过程产物，通过**分布式 Agent 网络**连起个人与团队运行环境"。

| 能力 | 说明 |
|---|---|
| **多 issue 并行** | 一个 issue = 一个需求，人可并行跑多个 |
| **Agent 与运行时解耦** | 本地或云端执行，"**不用本地电脑一直开着**" |
| **多 Agent 协同** | 前端/后端/质量多角色，承接 Aflow 三档流程 |

注意这层设计的分工：**Aflow 管"流程怎么走"，Multica 管"人怎么看"**——"开发同学只需要关注产物，不需要关注是多少个 Aflow 节点在运行"。

## 六、L3 小队：把"后端全自动"推到"全链路全自动"

> "一次需求交给一个 Agent 小队：**TL 负责调度，后端、前端、质量三个交付角色按棒接力，每棒产物 review 齐全才算交棒。质量不通过自动进 BUG 修复循环，连续两次不过才升级人工。人只做两件事——验收和机器跑不动时的协调。**"

三个设计细节值得单独拎出来：

- **接棒制而非并行制**："每棒产物 review 齐全才算交棒"——把"完成"定义成**可交接**，而不是"我这边跑通了"；
- **修复循环有次数上限**："连续两次不过才升级人工"——**自动修复不能无限重试**，否则会陷入无效循环烧钱；
- **人只做验收与协调**：人的角色被压缩到两个动词，边界非常清楚。

## 七、三个工具的打磨方式（方法论最可复用）

### 系分工具：从"AI 味"到过得了评审

痛点很实在："系分是大促交付链的**第一环**，也是**协同面最宽的产物**——前端、质量、SRE、下游系统都照着它干活，**评审不过就是全链返工**"；而"裸用 AI 写系分有四个顽疾——信息收集不全、图表制作繁琐、技术选型不靠谱、文档质量不可控，**AI 味重到评审直接打回，返工反而更慢**"。

四招：

| 招 | 做法 |
|---|---|
| **先建尺子** | 蒸馏 24 年至今的系分思路与优秀产物特性，"固化为模型的编写参考与准出标准"——**"AI 照着最好的样子写，Reviewer 按同一把尺子判"** |
| **定死分工** | "**人做决策、AI 做执行**"：架构分层、技术选型**动笔前由人拍板**，AI 只做信息整理、图表生成、文档组织——避免"**AI 写 AI 看**" |
| **管住过程** | 渐进式确认七步：信息收集 → 资料分析 → 大纲 → 关键决策 → 逐章撰写 → 准出审阅 → 发布；"**方案先行于写作，方向错了当步拉回**" |
| **守住终点** | 独立 Reviewer Agent **六维度评分**（推导过程、架构合理性、技术专业性等），不达标循环修改——**"质量是检查出来的，不是期望出来的"** |

### 编码工具：Loop 出来的高质量 MR

痛点列举得极准（这些是真实暗伤清单）："**事务内直接调下游、一锁二判三更新没走、ThreadLocal 不做清理、只让改 A 却顺手改了 B**"；以及"MR 通不过静态检查、**Agent 干到一半自认完成**、改了动态配置代码却漏掉配套默认值声明，运行时直接报错"。根因一句：**"单次交互难以稳定产出高质量交付物。"**

三招：

**① 先立铁律（结构约束）**——"上下文未确认不写代码、骨架未批准不写实现、审查未完成不交付。任何一项未通过就回退重来，**模型在结构上无法跳步**"。

自审清单的来源极有说服力：**2457 个真实 PR 的 1833 条 CR 评论 + 蚂蚁军规**，按 **P0/P1/P2** 分级逐项过——**"不再是'请仔细检查'式的空泛嘱咐，历史踩过的每一条坑都变成模型的必答题。"**

**② 再上 Loop**——"铁律降住了暗伤，**降不住概率**"。于是把编码做成 Loop：**输入明确**（系分 + 编码计划前置，**人的澄清全部前移到编码前**）、**准出客观**（单测与 CR 预审以业务用例为判断依据，**双通过才放行**）、**过程不依赖人**（两路检查的问题以报告形式流转回编码，自动修复重试）。

**③ 确定性的事交给确定性工具**——"Gate 检查用 **Shell 脚本**强制执行、编译验证跑**真实 mvn**、PMD 升级为 **JavaParser+AST** 脚本判断。**概率模型做概率擅长的事，脚本保证确定性。**"

### 测试工具：从人工构造 case 到全自动自测

- **分层推进**：单元（分支与行覆盖）→ 接口（输入输出行为）→ 端到端（完整链路），"**三层互补不互替，逐层向后收网**"；
- **真实请求数据回放**："把预发真实请求拉到本地回放——接口正确的前提下，**不再反复造数联调**"；
- **知识库托底**：预发资产、接口前置准备、端到端 case 沉淀入库，"从'每次手工攒'变成'按需取用'"；
- **报告结构化**：每条用例带编号 + **"预期结果 + 实际结果 + 判定依据"三件套**，判定依据落到**配置单据、日志断言与 trace 留痕**——"覆盖情况可检查，**每条结论可复核**"。

**单 case 端到端 3~6 分钟**（流程：预读知识库与报告取真实数据 → 拉起本地模拟器按 case 模拟点击 → 截取关键动线图与日志、返回数据对比 → 对比成功自动回写报告）。

## 八、自进化：把"这次跑得不好"翻译成问题清单

**触发链路**：需求完结 → 采集 → **T+1 提 PR → T+2 合入**（含人工 review）。

| 步 | 动作 | 关键设计 |
|---|---|---|
| 1 | 需求完结自动采集 | 回放主会话与子 Agent 会话，产出**上下文观测报告**——"**不靠人回忆，现场证据完整落盘**" |
| 2 | 指标提取，问题清单化 | **7 项运行时指标**：人工澄清次数·可优化澄清数·应答未答澄清数·自主解答次数·可优化自主解答数·知识库检索次数·回答率 |
| 3 | 定时分析，分类归属 | 归到**三大改进面**：Aflow 流程（节点提示词）· 大促工具链 · 大促知识库 |
| 4 | 分支路由 | 知识缺口 → 走知识晋升流程自动提 PR；流程/工具问题 → 建 issue 打标签排队 |
| 5 | 人工裁决 | 所有 PR 经 AI 预审 + 人工 review；**"人工只出现在链条末端"** |
| 6 | 回流生效 | 改进后的 Harness 在下个需求中重新被采集度量 |

第 2 步是精髓：**"把模糊的'这次跑得不好'翻译成可归因的问题清单"**——7 个指标全部围绕"人被迫介入"的场合设计，等于把"人力成本"直接做成了可优化的目标函数。

**当前数据（团队自己给的，包含不好看的部分）**：真实需求 **35 个 → 35 轮自进化、5 轮大迭代**；针对 Aflow 流程发现有效 issue **51 个**；排除非通用、重复后**落地优化 PR 12 个**。

**下一步（也很诚实）**：
- **采集前移**：从"需求级后置复盘"到"**节点级实时触发**"，低风险优化 AI 直接合入，人工只裁决高风险与跨模块改动——"**闭环周期从天级压到小时级**"；
- **issue 质量**："51→12 的落地差主要来自非通用、重复类 issue"，要加强自动去重与分类；
- **可视化看板**：澄清轮数、检索命中率、issue 分类流向、PR 合入状态、知识保鲜度。

## 九、体系的天花板在哪：只能做存量

**这一段是全篇最清醒的地方**：

> **"当前 Harness 体系建在双11 存量会场之上，需求以'模块迭代'为主，知识库沉淀的也是存量模块的标准事实。换成全新营销活动从零搭建，知识库无可检索、系分无可对照，体系优势会大幅衰减。"**

处方两条：**知识库冷启动**（"新业务进场即自动蒸馏 PRD、系分、评审结论入库，**边交付边沉淀，让知识随需求'长出来'**"）+ 用 **CY27 五福**作新场景验证，重点打磨"**架构先行**"的并行编排——**总体系分作为门禁先行，再拆子需求 Aflow 流并行，把全局架构约束注入每个子需求上下文，保证并行产物与整体设计一致**。

## 十、终局判断：从 Harness 到 Loop

**五层叠加**：**Prompt → Context → Harness → Loop → Graph**。"Harness 解决完'活得稳'之后，竞争焦点上移到第四层 **Loop Engineering**——你不再逐轮提示 AI，而是设计一个**自己发现工作、执行、验证、改进的循环**。"

引 **Claude Code 负责人 Boris Cherny**：**"I don't prompt Claude anymore. My job is to write loops."**

| | **Harness Engineering** | **Loop Engineering** |
|---|---|---|
| 隐喻 | 新手上路，每一步险都兜住 | **一支车队** |
| 组成 | 交规手册（上下文精细化）· 限速车道（门禁规范）· **安全员坐副驾随时踩刹车**（human in the loop）· 拖车返厂（约束与恢复） | 车自己接单、自己跑、**跑完自动回场检修**，每天的行驶数据转化成第二天的驾驶策略 |
| 回答 | "**这一趟，能不能安全到达**" | "**这支车队，怎么持续地跑、越跑越好**" |

**自评位置："第三层半，human in the loop"**——"六层 Harness 体系已建成……自进化闭环也已具 Loop 的雏形，**但循环的每一圈都要人推**"。

> "往 Loop Engineering 演进，**本质就是把'必须由人确认'的环节收敛到最小**，把副驾上的安全员逐步请回站场，只在他真正需要出现的地方拦截。"

**两个已在探索的 Loop**：

- **高风险代码的自动化检查与修复闭环**——现状是"资金安全巡检每日定时 → 自动识别 → 提 PR 等人合入，**发现是自动的，闭环是断的**"；目标是接上"发现—修复—验证—回归"整链，人只抽检**资金幂等、并发锁**这类真红线，"让高危代码问题以**小时级**被发现并修复"。
- **基于线上问题的自动解决闭环**——"值班目前的问题定位 Agent **止步于'给出根因'，处置仍在人**"；要补后半段：定位 → 生成处置方案 → **低风险操作（开关回滚、配置调整）自动执行、高风险止损保留人工确认** → 处置结果归档、经验沉淀回知识库。"值班人力从**执行者**退到**裁决者**，**同一个问题第二次出现时循环应该自己接住**"。

**收尾一句**：**"Build the loop, stay the engineer."**

## 深度分析

### 它证明了 Harness 的原料是"旧工程"，不是"新框架"

几乎所有 Harness 文章都在讲"要建什么层"，这篇讲的是**这些东西从哪来**：CR 纪律、质量门禁、复用抽象、准出标准——"**它们没有被 AI 淘汰，而是被翻译成 AI 能执行的语言**"。这句话把 AI 落地的成本结构说清了：**不是推倒重来，而是把既有工程规范改写成机器可执行的形式**（门禁 → Shell 脚本、评审标准 → 六维度评分、军规 → P0/P1/P2 清单）。这也解释了为什么很多团队"买了同样的模型却没有效果"——**它们缺的不是 Harness 的框架，而是可被翻译的工程积累**。

### 1332 次澄清是全文最诚实的一个数字

618 的 32 个需求换来 1332 次人工澄清——**平均每个需求 41 次**。这个数字把"AI 提效"的幻觉打穿了：代码写得再快，只要**上下文没到位**，人力就全部转移到澄清上。而双11 的应对不是"让模型更懂业务"，而是**把澄清变成可工程化的东西**：知识库四个触发源（现场蒸馏）+ 三档处置（高置信直接采纳/中置信确认/未命中才问人）+ 自进化 7 项指标里的 3 项直接度量澄清（澄清次数、可优化澄清数、应答未答澄清数）。**这是把"沟通成本"当成可优化指标在治理。**

### "重启胜过修补"是一个可以推广的架构原则

长任务出问题时，人的直觉是"在现有上下文里修"。他们反过来：**状态沉到文件，然后在干净窗口里重启**。理由是概率性的——**脏上下文里的修补会让错误累积**（模型看到自己的失败轨迹，容易越修越偏），而**重启的成本只取决于状态外化得好不好**。这条原则与"节点级 checkpoint""产物上传与传递"是一套的：**checkpoint 不是为了回滚，是为了能重新开始。**

### "铁律降住暗伤，降不住概率"——这句话定义了 Harness 与 Loop 的分界

结构约束（不能跳步）能防住**已知的坑**，防不住**同一份正确流程在不同输入下的抖动**。所以必须加 Loop：**输入明确（澄清前移）、准出客观（双通过）、过程不依赖人（报告回流自动修复）**。这也解释了为什么他们自评"第三层半"——**Harness 已完整，Loop 还缺"自动合入"这一环**。判断很准确：一个需要人推的循环，只是"自动化流水线"，还不是"循环"。

### 知识库的三个指标，是一套完整的"知识资产会计"

**保鲜率**（内容还对不对）、**准确率**（检索答得对不对）、**采纳率**（提的修复有没有被接受）——三个指标各自管一件事，且都有明确口径（14 模块全量比对 / 196 道题 / 68 个 PR 中 89.7% 合入、72.1% 一次通过）。**大多数团队的知识库只有一个指标：篇数。** 而篇数恰恰是最没用的那个——它不告诉你知识是否过期、是否可检索、修了有没有用。这套会计方式值得直接搬：**保鲜看"与代码的一致性"，准确看"评测集答题"，采纳看"PR 通过率"。**

### 自陈"只能做存量"，比任何成功叙事都可信

"换成全新活动，知识库无可检索、系分无可对照，**体系优势会大幅衰减**"——这句话主动划出了体系的能力边界：**它的强项是把已有经验的复用率推到极致，弱项是从零建立认知**。而他们的解法（冷启动蒸馏 + 五福验证 + 架构先行并行）也正好对应这个短板：**用总体系分作门禁，把全局约束注入每个并行子需求的上下文**——这是"在无存量知识时，用架构约束代替经验约束"。

### 与今天另外几篇拼起来，是一张完整的图

- **SkillHone**：Skill 要维护、要留决策历史 → 本篇是**知识库 + 自进化**的工业级实现（每天巡检、自动提 PR、末端人工裁决）；
- **AWS Skill Eval**：Skill 要测三层（触发/选择/执行）→ 本篇的**多 Agent 对抗性检查 + 准出标准 + 双通过放行**是同一思路在研发流程里的落地；
- **易点天下**：Agent 会退化、要设"运营 Agent"常驻岗位 → 本篇的**自进化飞轮 + 知识保鲜巡检**就是那个岗位的自动化版本；
- **冯若航**：状态与身份才值钱 → 本篇的"**状态沉到文件**、产物上传传递、断点接力"是同一判断的工程注脚。

**四篇独立来源，指向同一套结论：Agent 系统的价值不在模型，而在"能被持续维护的状态与约束"。**

## 实践启示

- **别跳步**：没有工程化（门禁、覆盖、小 PR）就没有可翻译的 Harness；先有纪律，再有 AI。

- **把瓶颈当路标**：每解决一层，问"瓶颈现在转移到哪了"——写代码 → 串流程 → 澄清 → 验证。

- **知识库只存结论与决策**，不存代码详情；否则保鲜成本高、检索噪音大。

- **三层加载**：规则自动注入（硬约束）、AGENTS.md 导航常驻、检索按需召回——**绝不整库灌提示词**。

- **检索三档处置**：高置信直接采纳、中置信确认式提问、未命中才问人——把人力澄清压到"真空白"。

- **知识库要每天巡检**：与代码比对，偏差自动提 PR，走同一套准入门禁；用保鲜率/准确率/采纳率三个指标度量，而不是篇数。

- **节点级 checkpoint + 状态外化**：长任务出问题**重启胜过修补**。

- **门禁节点必选**，且每个关键产物都要**多 Agent 对抗性检查**。

- **能确定性判断的交脚本**：Gate 用 Shell、编译跑真 mvn、静态检查用 AST——别让模型判可断言的事。

- **自审清单要从真实 CR 评论长出来**（2457 PR / 1833 条评论 → P0/P1/P2），而不是"请仔细检查"。

- **人的澄清前移到编码前**：编码计划先出、确认后动手，比事后返工便宜一个数量级。

- **把"跑得不好"翻译成指标**：澄清次数、可优化澄清数、未答澄清数、自主解答数、检索次数、回答率——**没有指标就没有自进化**。

- **自动修复要有次数上限**（连续两次不过升级人工），否则会烧钱在无效循环里。

- **承认体系边界**：存量迭代靠知识复用，全新业务要靠"架构先行 + 全局约束注入"。

- **往 Loop 演进的唯一动作**：把"必须由人确认"的环节逐个收敛——先低风险自动合入，再高风险抽检。
