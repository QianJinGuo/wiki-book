# 从 OpenClaw 到 Super Agent：入口、环境、交付三条线如何收敛

> 📊 Level ⭐⭐⭐⭐ | 17.6KB

## 一句话结论

腾讯游戏数据团队负责人 spike 用一年的产品观察回答"为什么会走到 Super Agent"：**Bot（聊天入口）与 Working Agent（IDE/桌面 App）并不是两条会有一方胜出的路线，而是被两条朴素需求推着向彼此靠拢**——① **Agent 要把事做好，就得接近人的实际工作环境**；② **上下文越多、人 coach 越多，人就越希望随时找到它、并把它交给别人用**。到了 DSH 这一代，多出的第三个变化是：**建设环境、接通能力这件事本身，也可以让 Agent 参与**。

## 一、演进轨迹：Bot → Working Agent → 又回到 Bot

- **年初（OpenClaw 那一波）**：大多数产品就是个 Bot，人从熟悉的聊天工具里找它，"新手更容易使用"；
- **4–5 月**：WorkBuddy 这类桌面应用起来，IDE 类、桌面 App 类变多，**处理工作的环境**成为竞争点；
- **最近两个月**：**两边开始往对方方向走**——Bot 产品补工作台、文件处理、工具/连接器；桌面 Agent 开始 Bot 化，支持更好的手机入口、channel 入口与协作。

看起来像"从 Bot 出发又回到 Bot"，但作者指出这是**两条需求线在收敛**，不是回到原点。

## 二、"能找到它" ≠ "它能把活干好"

这是全文最核心的区分。作者留了一段内网版 OpenClaw 的对话：他在聊天里问它知不知道自己在做的项目，它回答"在对应代码仓库里，准备继续查看项目结构"——**前面是聊天窗口，后面已经接着一个能干活的环境**。

但用久了会发现差距：**它知道我今天在做什么吗？文件是不是最新的？上次那个方案为什么没采用？我刚补的条件这次有没有带上？** 这些背景多数不在一句任务描述里——**模型能力当然重要，但它这次能看到什么、能调用什么，也会直接影响结果**。

于是 IDE/桌面 App/工作台的价值显现：**它越来越像一个共同工作的地方**——左边资料与文件、中间看内容改东西、旁边是与 Agent 的会话、下面跑工具看结果。**人和 Agent 围绕同一件事工作，背景就不只来自最后发出去的那句话**：改了哪里、为什么改、哪个尝试没成功，都有机会留下。

**但判据不是形态**：作者明确反对以"前面是不是聊天窗口"论高下——**Bot 类产品背后也可以有完整的工作区和记忆；真正要看的是"实际工作在哪里发生、Agent 能不能拿到相关背景并继续做下去"**。他还补了一条与直觉相反的观点：**给 Agent 一台云端电脑，不等于它已经和我在同一个工作环境里**（文件可能在本地、讨论在群里、刚做的修改留在另一个会话）；资料也不必都搬到一台机器上，**能按权限找到需要的内容、接上后续变化，比"存得很多"更重要**。

## 三、入口改变的是"积累的质量"，不只是便利

第二轮 Bot 化与第一轮的区别，就在这一句：**那时想联系的是"一个随时能问的助手"，现在想联系的是"已经知道事情经过、手上还有工作在做的 Agent"**——前者是体验入口快捷，后者是**同一件事能接着做**。

作者的亲历例子很小但很说明问题：在手机上让它看一份材料，他补了一句"某个讨论群里有"，它**去找对应消息里的文件再读**——方便的不是"手机上能聊天"，而是**不用先回电脑找文件、下载、再发给另一个助手**，原本接好的工具与可访问背景**可以从这个入口继续用**。

由此推出一条常被忽略的因果：**入口方便 → 更愿意把刚发生的变化、还没整理好的想法交给它 → 这些背景留下来 → 下一次它更容易理解我**。所以"又回到 Bot"不是做遥控器，而是**新的讨论可以回到原来的工作里**。前提条件也讲清楚了：**换入口不等于完整上下文自动同步**——是接同一个执行会话，还是通过共享资料与工作记录接力，需要相应支持。

## 四、从"自己用"到"和别人一起用"：交付能力而非分享经验

第三类需求：**我建好的 Agent，别人能不能用上？** 作者的判断很关键——**这不是"把一个 Prompt 分享给大家"**：

> 用户在自己原来的 Agent 里提问，需求进入一个**有专业同学和数据 Agent 参与的工作群**；需要补充业务背景、确认口径就在这件事上继续沟通；处理完成后，**结果再回到用户原来的工作里**。

这样的分工保留了双方各自的优势：**专业同学继续维护知识、工具与处理方法；使用者带来自己的业务问题并参与判断结果；双方不必使用完全相同的 Agent，也不必每个人都学会怎么建设这套能力**。

作者把它提炼成两种带动方式的对立：**一种是把经验分享出去、让别人也学会搭；另一种是把已经建设好的能力交出去、让别人先用起来**——"**不是每个人都要先变成 Agent 建设专家，才能获得帮助**"。但底线同样明确：**群里多了一个头像并不会自动解决问题，背后仍需要有人维护专业能力、也需要实际可执行的环境**。

## 五、Agent 参与建设自己的工作环境（Context / Harness 的重新定义）

作者的用词很朴素但准确：**Context = 它做事时能取得的背景**；**Harness = 让模型实际工作的那套安排**（工具、记忆怎么用、任务怎么执行、遇到问题怎么处理）。

由此给出一条诊断顺序：**一个 Agent 总做不好，原因不一定是 Prompt 没写清楚——可能是读不到资料、拿了旧版本、工具没接好；只加一句"你要认真一点"通常解决不了这些问题**。他的做法也值得抄：**不满意时先让它看实际过程**（刚才用了哪些材料、哪一步出了问题、我们对"做好"的理解差在哪里），**找到了再决定是补背景、改说明，还是调整工具**。

**新变化是"建设"这一层也开始由 Agent 参与**：海外产品的 Mods 机制允许用户改提示、工具行为与界面，**也能让 Agent 自己编写 Mod**；DSH 的 Creator mode 支持**通过对话创建插件**扩展工具、Skill 与界面。作者因此重新定义"养"：**能调整的不只是它说话的方式，还包括它取得什么背景、调动哪些工具、在哪个环境里做事**。

他同时划了安全边界（这段是全文最"工程"的部分）：**插件和程序依然是要在机器上执行的东西——来源、权限、可恢复的版本都要看；涉及账号、外发或付费，不能因为"AI 帮我装的"就省掉确认；改完以后还得用实际任务看看有没有变好。**

## 六、成熟 Agent Coach 新 Agent：一条低成本的"能力分家"路径

作者最近常用的办法：**主 Agent 已经比较了解我，也一起做过不少事；想分出一部分能力给新 Agent 独立处理时，先让它帮忙带**。

流程是渐进的：**先跟用顺的 Agent 做几个例子，确认"什么应该记、什么不能混在一起"，再让新 Agent 去做，回来一起检查**。过程中出现的失败很具体、也很有共性：

| 失败形态 | 说明 |
|---|---|
| **把"已记下来"当成"人已接手"** | 记录与责任的混淆 |
| **没注意安排已被取消，继续按旧信息提醒** | 状态更新未消费 |
| **纠正后过度谨慎，只列事实、把判断全交回来** | 从"乱判断"跳到"不判断" |

作者的期望说得很清楚：**希望它补上的恰恰是"有依据的判断"，不是再给我一张需要自己处理的清单**。而 coach 靠的是：**成熟 Agent 去看目标 Agent 的会话、回到来源核对、帮它调整再继续试**；人只盯真正有分歧的地方（"这个判断是不是我想要的，哪里还理解错了"）。

他也补了两条防止自欺的规则：**①不能最后都是老 Agent 替新 Agent 完成工作，然后宣布"教会了"**——还是要让新的自己做，**换个例子、换个会话再看**；**②准备给别人使用时，要把必要的专业能力和私人资料分开**，不能为了让它像自己就复制整份私人记忆，更不能默认自己的偏好适合所有使用者。

还有一条自省：**带它的 Agent 也会判断错**——他曾让 Agent 自动做"Jev 对 IM 消息分流实验"，纠正过它的评测标准（有人已找对应负责人，不一定需要再介入；**它以为"更主动"就是更好，但那不是我的意思**）。结论是"**人并没有消失，只是不用亲自完成那么多配置、检查和反复操作**"。

## 七、收敛点：什么样的 Agent 能"在具体事情上代表我"

作者对市面路线的定位：Dots 把云端电脑、可连接应用与 ChatGPT/Slack/Teams 入口放在一起；Grok Bot 把持续工作的云端环境、文件与记忆，与消息、群聊、Bot 间协作结合；Muse 从个人生活（邮件、出行、长期目标）出发而不进代码仓库。**背景来源不同，问题相似**。

他的收束判断（也是最能迁移的一段）：**只记得很多信息，不一定就理解我的取舍；只知道我喜欢什么、没有工具和权限，也做不了事；它还需要能接到新变化、遇到拿不准的地方找我、做错以后能够调整；有时还应该提醒我"原来的判断可能不适合现在了"，而不是越来越顺着我说。** 并且他不相信会出现"一步到位的全能助手"——**先在具体事情上做得可靠（能接续、能纠正），再慢慢扩大范围，这条路更实际**。

## 深度分析

### 这篇的真正贡献：把"形态之争"换成"三个可检验的问题"

Bot vs IDE 的争论容易停在界面偏好，作者把它拆成三个问题：**工作在哪里发生？Agent 能不能拿到相关背景？能不能继续做下去？** 三个问题都能被检验，也都能被不同形态满足——于是"云端电脑 ≠ 同一工作环境"、"Bot 背后也可以有完整工作区"这些结论就自然成立。**判据换了，路线之争就变成了工程问题。**

### "入口改变积累质量"是一个被低估的飞轮

多数人把入口当作分发问题（多一个渠道 = 多一点触达），作者看到的是**数据质量**问题：**越容易接着聊，人越愿意交付"刚发生、还没整理"的上下文**，而这恰恰是模型最缺、也最难事后补的信息。反过来说，一个体验上"要回电脑才能继续"的产品，会**系统性地丢弃**这类高价值片段。这解释了为什么 Bot 化不是倒退，而是**收集端的扩张**。

### "交付能力"与"分享经验"的分野，决定了 Agent 能否组织化

分享经验是让**每个人重建一遍**（成本高、质量参差），交付能力是让**建设者维护、使用者使用**（分工明确）。作者举的工作群模式之所以成立，是因为它同时解决了三件事：**专业知识的维护责任有归属、业务判断仍由使用者参与、结果回到原工作流**。这三条任何一条缺失，"群里多个头像"就会退化成噪音。

### Coach 新 Agent 的三类失败，本质都是"责任边界"没写清

"已记下来"≠"人已接手"（记录 vs 责任）、"安排取消仍提醒"（状态 vs 事实）、"只敢列事实"（判断 vs 信息）——三条都在同一个维度上出错：**Agent 不知道该对哪一层负责**。而这恰好是可以用**例子 + 会话回看 + 来源核对**修的东西，不需要重训模型。**这也解释了为什么"成熟 Agent 带新 Agent"在工程上可行：它交付的不是参数，而是判据与边界。**

### 安全边界那段值得单独抄：AI 装的也要走确认

"来源、权限、可恢复的版本都要看；涉及账号、外发或付费，不能因为'AI 帮我装的'就省掉确认；改完以后还得用实际任务看看有没有变好。"——**三句话覆盖了供应链、授权、验收**。当"让 Agent 改自己的环境"成为常态，这套要求会从最佳实践变成准入条件。

## 实践启示

1. **别用形态判断 Agent**：问三个问题——工作在哪发生、能否拿到背景、能否接着做下去。

2. **云端电脑 ≠ 同一工作环境**：文件在本地、讨论在群里、修改在另一个会话，这三处接不上，Agent 就得等人搬运。

3. **资料不必都搬到一台机器**：按权限找到 + 接上后续变化，优于"存得很多"。

4. **把入口当数据质量工程**：越容易继续聊，越能收到"刚发生、没整理"的高价值上下文；设计时优先保证"同一件事能继续"。

5. **换入口要显式设计上下文接力**（同一执行会话 / 共享资料与工作记录），否则就是"每换一个地方就认识一个新助手"。

6. **能力交付优于经验分享**：建设者维护知识与工具、使用者带业务问题参与判断、结果回原工作流——三者缺一不可。

7. **诊断顺序：先看过程再改 Prompt**（用了哪些材料、哪步出问题、"做好"的理解差在哪），再决定补背景/改说明/调工具。

8. **让 Agent 参与建设环境，但守住三条**：来源与权限可查、版本可恢复、账号/外发/付费仍要人确认；改完用真实任务验收。

9. **用成熟 Agent 带新 Agent**：先做几个例子定"什么该记、什么不能混"，再放手；人只审有分歧的判断。

10. **防自欺两条**：不让老 Agent 替新 Agent 干完再宣布教会（换例子、换会话复测）；对外交付前把专业能力与私人资料分开。

11. **对"更主动"保持警惕**：主动不等于更好，判据是"是否符合我的取舍"。
