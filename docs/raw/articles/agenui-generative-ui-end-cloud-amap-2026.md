# 从用户意图到三端原生界面：高德端云一体化的生成式 UI 实践

> 作者：高德技术（应用基建智能部），高德官方技术号
> 介绍高德端云一体的生成式 UI 方案 **AGenUI**：云侧把用户意图与业务上下文转化为可执行的生成式 UI 协议，端侧渲染器把协议数据实时渲染为 iOS、Android、HarmonyOS 三端原生界面。已开源（github.com/AGenUI/AGenUI，官网 genui.amap.com）。

## 背景：从"直接给出答案"到"提供可交互界面"

传统"对话框 + 纯文本"交互难满足用户期待——用户期待的不只是一段回答，而是一个符合意图、可交互的界面。生成式 UI 基于大模型理解用户意图并动态生成交互界面。规模化落地必须同时回答两个基础问题：**如何生成协议**（驱动大模型低成本、稳定、可控地生成页面描述协议）和**如何渲染界面**（端侧将协议转化为高性能、可交互、跨端一致的原生界面）。

**AGenUI** 端云一体方案：云侧把用户意图与业务上下文转化为可执行的生成式 UI 协议，端侧渲染器把协议实时渲染为 iOS/Android/HarmonyOS 三端原生界面。

**在线业务量级**：已在线支持 30+ 业务场景，覆盖目的地及沿途推荐、信息展示与出行工具、生活服务交易、内容商业化、出行规划与运力服务 5 大方向；整体约 5k QPS，单卡小时级上线，业务从信息展示扩展到"推荐—决策—交易—出行服务"完整链路。

## 生产级卡片缺什么：样式、数据绑定、算子

要生成并稳定交付生产级卡片，核心解决三要素：
- **样式**（好不好用）：信息是否清晰、体验是否一致
- **数据绑定**（敢不敢信）：页面是否连接真实、可追溯的业务数据
- **算子**（能不能跑）：后端字段与卡片需求不一致时，数据能否被正确转换并执行

三者缺一，卡片都无法成为真正的生产能力。

## 云侧：从用户意图到可执行卡片包

云侧目标是把用户意图收口为一份可发布、可执行的卡片包（含样式协议、数据绑定计划、算子引用与版本化执行信息）。链路以**契约生成**为起点，围绕样式、数据绑定、算子完成卡片生产，再通过可控演进支持后续修改。

### 契约生成：先把"要生成什么"说清楚

自然语言请求通常只说"想要什么"，不完整说明对象范围、内容优先级、缺失策略和动作语义。若直接进入样式/数据/算子环节，每层都会基于自己上下文重新解释用户意图，导致三问题：**目标漂移**（样式为画面完整擅自加内容，数据因接口有某字段反过来改变业务语义）、**交付失真**（必需/可选内容没边界，关键字段缺失仍生成"看起来完整、实际上不能交付"的卡）、**修改失控**（没有稳定基线，改价格时标题/布局/绑定/动作一起漂移）。

主 Agent 先把用户意图收口为 **Content Contract**（内容契约），明确任务目标、必需内容、可选内容、动作语义与缺失策略，后续样式/数据绑定/算子都以契约为共同输入。三项关键约束：**统一目标**（冻结有限任务/业务对象/场景范围）、**冻结边界**（必需/可选/动作语义/缺失策略）、**稳定引用**（为内容和动作生成稳定 ID，各层引用同一事实不再重复猜测）。

### 样式：规则驱动生成可落地的协议

样式生成由设计规则、端上渲染器能力、生成式 UI 协议共同约束。设计规则决定布局/信息层级/品牌 Token/元素关系；Renderer Catalog 提供目标端可用组件及语义能力视图，并计算最小 Renderer Gate；生成式 UI 协议作为跨端标准承载最终结构。样式 Agent 按内容契约召回并精排 Layout 与关联规则，在渲染器能力边界内生成界面，为标题/价格/图片/动作声明稳定语义槽位。产物记录规则版本、哈希和引用证据。**规则不会整体塞入 Prompt**——先按内容契约选布局候选，再通过工具读取关联规则闭包，每次读取形成带 Revision 与 Hash 的 Receipt。

### 数据绑定：知识库召回、精排与真实字段绑定

Requirement Compiler 先把样式中的语义槽位编译为确定的数据需求，并产出动作相关协议约束（作用域/类型/必需性/缺失策略），避免绑定层重新猜测意图。Bind Agent 围绕每个需求从**字段能力知识库**召回与精排，综合业务语义、单位口径、实体身份、接口可用性等证据选择真实字段形成 Binding Plan。单源不能满足时，仅允许一层、并行、同实体补全；必需字段没有可信结果则阻断自动发布，返回结构化缺口。

### 算子：版本化转换弥合字段错位

后端字段真实存在但往往不能直接满足卡片需求（米转公里、金额格式化、条件文案、过滤、排序、聚合）。算子以知识资产维护输入输出 Schema、适用语义、参数约束、版本和 Runtime 支持信息。字段不满足时 Bind Agent 召回精排已发布算子；**模型只选择算子和受约束参数，由 Runtime 受控执行并校验结果**。不把模型临时生成代码直接带上线，也不把多接口编排扩展为通用 DAG；数据组合限制为单层/并行/同实体补全，字段转换限制为已发布/带 Schema/版本的算子。Runtime 执行拓扑有界、失败可定位、算子可灰度和回滚；更复杂依赖沉淀为后端聚合能力。

样式协议、Binding Plan、算子引用最终固化为 **Card Execution Package**，Runtime 只执行已批准计划。规则版本、字段证据、算子版本与运行结果作为 Artifact 留存，整张卡可追踪、回放、局部编辑。

### 可控修改：只改该改的，其他保持不变

用户更常见需求是在现有结果上继续调整（"图片再大一点""价格改成含税价"）。若每次都整卡重生成，即使目标改对，标题/样式/数据绑定/交互也可能无关漂移。引入**目标集/保护集/影响集/复用集**：
- **目标集**：本轮必须改变的内容，确保用户点名修改真正发生
- **保护集**：未被点名的内容保持不变，防无关漂移
- **影响集**：沿依赖关系找出必须重做、重新校验的下游产物
- **复用集**：未受影响的 Design/Binding Plan/Package 直接沿用，避免整卡重算

"只改图片大小，其他保持不变"不再是 Prompt，而是一份可执行、可验证的变更计划。

### Agent 底座：多 Agent 生产成为可恢复的事实链

多 Agent 不等于把复杂任务拆成多段 Prompt 让模型自由接力。对制卡这类需发布和长期维护的任务，真正要管理的是每一步产生的生产事实。以一次**离线 Run**作为制卡最小执行单元：内容契约、样式协议、Requirements、Binding Plan、算子引用、Gate 结果等关键产物以带类型/版本/Hash/来源引用的 **Artifact** 持久化，下游步骤只消费已确认的上游 Artifact，不从对话上下文猜测前序结论。三项工程收益：
- **过程可恢复**：中断时从最近可信检查点恢复，已完成未受影响的产物无需重新生成
- **决策可追溯**：为什么选某布局/绑某字段/引某算子/被 Gate 拒绝，都能回溯到知识版本、工具读取证据、Artifact
- **修改可控**：多轮编辑不依赖模型"记住上一轮"，Edit Contract 以既有 Artifact 为基线声明目标/保护/影响集

模型负责开放决策，工具负责读取受控知识，系统负责校验、固化和发布。Run 只属于离线卡片生产；在线 Runtime 只加载已发布执行包，确定性完成数据获取、算子执行、DataModel 生成，不承担 Agent 决策。

## 端侧：从 UI 描述协议到三端原生渲染

AGenUI 是行业首个覆盖 iOS/Android/HarmonyOS 三端的 **A2UI 原生渲染引擎**。采用**共享 C++ 核心引擎 + 三端原生渲染**架构：C++ 引擎统一承载流式协议解析、虚拟组件树管理、布局计算、样式解析与变化 diff 等平台无关核心逻辑；三端渲染引擎基于核心引擎下发的组件协议用系统原生能力绘制。三大特点：

### 原生渲染：确立性能基线
- **零中间层损耗**：界面最终以系统原生组件呈现，没有 WebView/跨端框架的中间抽象层性能折损，自然融入宿主 App 交互/动画/无障碍/手势体系
- **异步渲染 + 差分更新**：协议解析、布局计算、节点 diff 等计算密集逻辑全部在工作线程完成，主线程只提交轻量级绘制；流式更新支持差量更新变化节点
- **平台深度优化**：HarmonyOS 基于 ArkUI 原生组件体系，通过 C API 打通高性能渲染链路，绕开脚本语言运行时开销

### C++ 共享引擎：一次布局计算，三端像素级一致
平台无关逻辑全部下沉共享 C++ 引擎，三端共享同一份计算结果：**单一事实源**（同一协议三端完全一致布局，从根源消除多端差异）、**计算性能**（C++ 为流式场景稳定帧率提供底层保障）、**可移植性**（未来扩展到车机/IoT 只需新增对应原生渲染层）。

### Streaming-first 渲染：生成过程即呈现过程
组件到达即可挂载、文本到达即可追加、数据到达即可绑定——生成过程本身就是用户可感知的界面呈现过程。**组件级流式**：组件以独立单元逐个到达/解析/上屏，协议数据未闭合时解析自动挂起，下一段数据到达后从断点继续，不丢中间状态。**流式容错**：针对 LLM 流式输出的多余字符/未闭合片段/突然中断，建立完整边界保护机制，任何异常输入不破坏渲染状态。

### 渲染品质：组件、样式与主题
- **组件体系**：内置 22 个组件——18 个生成式 UI 协议标准组件（文本/图片/卡片/列表/表单控件/媒体播放器）+ 4 个 SDK 扩展组件（表格/轮播/内嵌 Web/富文本）。SDK 三端统一提供自定义组件注册 API，开发者注册的原生 View 可像内置组件一样被模型引用
- **样式与主题**：以 DesignToken 为基底，内置 60+ 语义化颜色 token（每个带亮/暗双色值），支持 45+ CSS 样式属性（盒模型/Flexbox/文本/背景/边框/圆角），主题体系开放可加载自定义配置实现品牌定制

## 质量闭环与演进

### 端侧：三条测试防线
集成测试（三端自动化流水线覆盖协议解析/组件渲染/事件分发/数据绑定）、稳定性测试（全接口极端压力场景，可持续数小时自动监控异常）、三端一致性验证（自动化效果对比确保同协议三端渲染一致）。

### 云侧：分层门禁与会话级评测
围绕 4 维度评估：样式是否符合规则与视觉目标、内容与数据是否真实满足、逻辑与协议是否可运行、多轮是否保持连续性。评测以**会话脚本**为最小单元而非单条 prompt（含初始制卡/选择规则/数据预检/局部编辑/补充数据/用户确认/运行中断与恢复，每步校验该步应新建/复用/保持不变的 Artifact；编辑步骤验证目标集确实变化/保护集没漂移/影响集完成重算）。刻意把不同质量问题分开归因：视觉 Judge 通过 ≠ 字段绑定正确；Binding Plan 结构正确 ≠ Runtime 调用成功；Renderer Gate 只确认目标 Catalog 组件可用，不替 Action/属性路径/业务协议背书。分层 Gate 价值不在多拦截，而在失败后给出正确处理者和修复方向。

### 知识演进：线上反馈不自动改写线上规则
线上 Trace、用户反馈、人工结论、评测失败形成新知识候选，但候选必须经过冲突与影响分析、目标集/保护集/边界集成对评测和发布门禁才能成为新版本；失败版本不覆盖线上规则，影响报告与来源证据保留给设计/产品/研发查看。得到的不是"模型自动自我修改"，而是一条能持续积累且不会失控的工程闭环。

## 业务落地与开源

已在高德地图多业务场景落地。以导航规划页为例：用户在规划行程时，系统结合路线与目的地上下文实时选择推荐卡片；不同行程目的地、不同时间节点，卡片内容动态更新。真实数据绑定、三端一致、原生高性能渲染在真实业务链路持续运行。AGenUI 端侧渲染器已正式开源（GitHub: AGenUI/AGenUI）并快速迭代。

## 结语与未来方向

生成式 UI 的难点从来不只是让模型画出一个界面，真正的挑战是让它在每次设计、数据选择、逻辑执行、编辑和发布中保留清晰边界与可追溯证据。AGenUI 云侧明确大模型与 Agent 确定性机制分工（模型承担开放决策，确定性机制收口必须稳定的生产事实）；端侧以共享 C++ 引擎统一布局/样式/流式解析为单一事实源，三端原生高性能渲染像素级一致。当样式、数据和逻辑都能被分别生成、确定性收口并在运行中验证，卡片才不再是一段偶然成功的模型输出，而成为可持续交付的界面资产。

未来方向：协议能力升级（跟进生成式 UI 协议新版本）、性能基线建设（生成式 UI 渲染性能度量体系）、端云全链路完善（协议生成→效果评测→端侧渲染）、多终端形态扩展（依托 C++ 引擎可移植性探索车机/IoT）。
