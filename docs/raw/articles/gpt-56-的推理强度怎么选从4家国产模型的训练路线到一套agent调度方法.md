架构师（JiaGouX）我们都是架构师！  
架构未来，你来不来？

  


  


一个写代码的 Agent 卡在 CI 报错上，最顺手的动作往往是把推理强度拉到最高。

它确实会想得更久，问题却未必更接近解决。依赖仓库可能超时，测试环境也可能已经污染。此时多花不少推理 token，得到的很可能只是一份更长、更笃定的错误诊断。反过来，一次便宜的快速分类，有时就能把任务送到正确的工具和验证器。

所以，看到 GPT-5.6 把推理强度做成下拉菜单时，我先想到的是另一件事：**过去藏在后训练里的计算策略，正在变成 Agent 运行时可以调度的一项资源。**

这个简单菜单背后，模型要学会什么时候展开推理、在哪一步继续思考、需要推理多深，以及怎样缩短过程又不丢掉解决难题的能力。

GPT-5.6 的具体训练方法并未公开。这个下拉菜单只是一扇观察窗口，并不表示 GPT-5.6 采用了国产模型的训练方案。沿着 Qwen3、GLM-5、DeepSeek V4 和 Kimi K2.5 的公开材料往下看，我们能找到四种不同的工程思路。

* * *

## 太长不看版

  * • **Effort 是计算策略，budget 是硬边界。**  前者决定模型倾向怎样使用推理计算，后者限制 token、时间和费用最多花多少。
  * • **四家模型分别处理开关、时机、深度和压缩。**  训练方法不同，但都在尝试让模型按任务分配计算。
  * • **Agent 不能只按任务名称选档。**  当前阶段、工具状态、动作是否可逆、结果能否验证，往往比初始输入本身更重要。
  * • **高档只对“推理不够”有帮助。**  权限拒绝、环境污染、依赖超时和输入缺失，应该先修外部条件。
  * • **团队最终要优化每个成功任务的总成本。**  默认从中档开始，用真实任务证明升档或降档是否值得。

四条路线回答的是不同问题，可以组合使用，也不能据此给模型排座次。

顺着这四个问题往下看，会比直接比较谁的 `high` 更容易看清差别。

* * *

## 先分清三只旋钮和一条硬边界

很多人第一次看到 `low / medium / high`，会自然地把它理解成不同的 token 上限。实际做选型时，至少要分清三只旋钮：

  * • **模型选择** 决定能力边界、工具适配和单位 token 的价格；
  * • **Reasoning effort** 决定同一模型在当前步骤倾向投入多少推理计算；
  * • **回答详略** 决定最终文本展开到什么程度。

一份面向人的长报告，可能需要更详细的回答，却未必需要很重的推理。一个只有几行的故障结论，反而可能经过了复杂诊断。把回答长度和推理深度绑在一起，调度策略很快就会失焦。

三只旋钮之外，系统还需要一条硬边界。Token budget、时间、费用和工具轮数达到上限时，请求要能够停止，不管模型是否已经想完。

Nemotron 3 Ultra 的公开模型卡提供了一个旁证：它同时支持学习到的 medium-effort 模式和独立的 `reasoning_budget`。前者管使用方式，后者管最多能用多少。

放到架构里，可以把 effort 相关链路拆成三层：

  1. 1\. 产品或 API 把用户选择转换成控制信号；
  2. 2\. 模型通过 SFT、RL 或蒸馏学会对应行为；
  3. 3\. Harness 再叠加 token、时间、费用和重试上限。

只做第一层，下拉菜单很可能只是标签。只有第二层，没有第三层，长任务仍可能耗尽上下文和预算。三层接起来之后，档位才有工程意义。

* * *

## Qwen3：先让模型学会开和关

Qwen3 先回答了一个基础问题：**同一个模型，怎样学会展开推理，也学会直接回答？**

根据公开技术报告，Qwen3 的后训练包含 long-CoT SFT、reasoning RL、Thinking Mode Fusion 和 general RL。Thinking Mode Fusion 会混合 thinking 与 non-thinking 样本，通过 SFT 建立两种行为。后续的 general RL 再强化模型对模式的遵循。

在提示词里多写一句“请仔细思考”还不够。训练数据里需要同时出现不同模式，控制信号才可能变成稳定能力。

这和研发团队培养新人很像。

改一个确定的字段名，按规范直接完成即可；设计跨服务的数据一致性方案，则要先列约束、找失败路径、比较取舍。如果所有任务都要求写完整方案，效率会很低；如果所有任务都直接动手，复杂变更又容易漏掉边界。

模型也需要在训练中见过这两种工作方式。

Qwen3 还支持推理时硬预算。公开报告提到，推理过程被截断后继续给出最终答案的能力没有经过显式训练，而是在 Thinking Mode Fusion 之后出现。这个现象值得关注，但目前还不适合把它外推成所有模型都具备的通用能力。

工程侧可以先把任务分成需要展开推理和可以直接执行的两类，再谈更细的档位。

* * *

## GLM-5：思考应该发生在哪一步

真实工作很少是一问一答。

一次线上故障定位，可能要先查日志，再看监控，接着跑 SQL，最后回到代码里验证假设。行程规划也类似：先筛日期，再查交通和住宿，发现预算超了，还得回头调整路线。

这类任务的难点已经从“要不要思考”变成“在哪一步继续思考，以及上一轮的思路要不要保留”。

GLM-5 公开的 interleaved、preserved 和 turn-level thinking，正好沿着这条线展开：

  * • interleaved thinking 允许模型在工具调用之间继续处理；
  * • preserved thinking 关注跨轮保留已经形成的推理状态；
  * • turn-level thinking 允许同一会话逐轮开关。

这三种行为需要单独看：**它们是推理调度方式，不能写成 low、medium、high 三档 effort。**

Raschka 对 GLM-5 技术报告的归纳是，这些行为由 multi-task SFT 引入，随后经过 reasoning RL、agentic RL、general RL 和最终的 on-policy distillation。

放到 Agent 架构里，调度器不能只看用户最初输入。它还要知道当前处于探索、执行还是验证阶段，工具刚才是否失败，以及已有上下文是否还值得保留。

例如一个接口开发任务，可以这样分配：

  * • 读取已有接口和类型定义时，用较低成本建立上下文；
  * • 设计兼容方案时，提高推理强度；
  * • 写确定性代码时回到中低档；
  * • 测试失败后，只在诊断阶段升档一次；
  * • 最终结论由测试、静态检查和代码评审确认。

GLM-5 展示的重点，是把推理从单次回答扩展到完整工作流。

* * *

## DeepSeek V4：同一个模型，推理多深

开关和时机解决之后，还剩一个更细的问题：展开推理时，到底该走多深？

Raschka 对 DeepSeek V4 技术报告的归纳是，Non-think、Think High 和 Think Max 在后训练阶段采用不同的上下文窗口和长度惩罚，形成不同模式，再通过 on-policy distillation 合入单一 checkpoint。

低档对长度成本更敏感，高档给长推理留下更大空间。最终又收进同一个 checkpoint，对服务架构很有价值：调用方不必为每个档位维护一套独立模型和部署链路。

日常接口开发、跨服务故障定位、核心架构迁移，需要的分析深度完全不同。团队可以为三类任务建立各自的成功样本、检查项和成本边界，再把选择入口统一到一个平台里。

不过，公开材料还不足以重建 DeepSeek V4 各专家与三种模式的完整映射，长度惩罚的精确实现也没有完全披露。我们能看到路线，不能自行补齐训练细节。

对使用方同样如此。`medium` 只是产品标签，并不天然等于另一家模型的 `medium`。不同模型的训练数据、奖励设置、上下文窗口和服务实现都可能不同，跨模型比较仍要回到同一组真实任务。

* * *

## Kimi K2.5：先会做，再练得更省

如果训练一直奖励短答案，模型可能学会少用 token，也可能逐渐失去利用长推理解决难题的能力。

Kimi K2.5 的 Toggle 方法处理的就是这个矛盾。

它在两种 RL 阶段之间交替：

  * • 有预算阶段，鼓励模型在题目对应的 token 预算内正确完成；
  * • 无约束阶段，恢复常规最大生成长度，保留从长解法中学习的机会。

预算并非一开始就强行压上去。它来自正确 rollout 的长度分布，而且要等题目的平均准确率超过阈值后才激活。

这很像做性能优化。一个服务连正确性都不稳定时，先压延迟通常只会制造更多偶发错误。更稳的顺序是先建立正确基线，再用真实分布定预算，最后确认优化没有破坏长尾任务。

Raschka 对技术报告结果的归纳是，Toggle 让生成 token 减少约 25% 到 30%，基准表现变化很小，并迁移到 GPQA 和 MMLU-Pro。这个数字来自 Raschka 对报告的归纳，不能写成所有任务都能获得的节省承诺。

Kimi K3 已经对外提供 `low / high / max`，但 Moonshot 尚未公布三档的具体训练方法。K2.5 提供的是一条可参考路线，不能直接当成 K3 的已知实现。

* * *

## Agent 现场，难点还在状态

聊天场景里，effort 看起来只是一次请求的参数。进入工具调用后，它会牵动整个任务链。

DeepSeek 的 Thinking Mode 文档给出了一条很具体的接口合同：普通多轮对话可以不把上一轮的 `reasoning_content` 带入后续上下文；一旦该轮发生工具调用，后续请求就需要把这段内容完整传回，否则接口会报错。

这只是 DeepSeek 的接口行为，并非所有模型都遵循的 Agent 协议。它至少说明了一件事：中间状态怎样保存、什么时候恢复、哪些内容继续占用上下文，会直接改变推理效果和成本。

此前梳理多模型协作时，我一直在意交接损耗。原始轨迹可以保留，当前工作集却不能无限膨胀。工具结果、任务状态和仍然有效的推理要有明确合同；过期探索、失败分支和无关日志，也要能退出当前窗口。

Andrew Ng 曾公开讨论输出 token 速度对 Agent 工作流的重要性。Artificial Analysis 又补充了一个运行时视角：多步工作流里，不少模型输出还要继续交给下一个模型处理。这两条公开观点只用于说明运行时影响，不承担性能证据。一段冗长推理会同时增加等待时间、后续上下文和总成本。

Kimi 的官方文档又补了一项容易漏算的成本：切换 reasoning effort 会使上下文缓存失效，长会话需要重新预填充。

长会话里的档位，最好在开始前选好并尽量保持。确需切换时，新建会话往往比来回调档更省。

## 四种配方，落到一条控制链

四条公开路线最终可以收进一条控制链：

  
图 2：Agent 的 effort 调度要把模型、预算、工具状态、验证与人工接手连起来

这张图回答的是运行时问题：什么时候升档，什么时候先修环境，什么时候应当停止自动执行。

每个环节解决的问题不同：

  * • **任务分类** 借鉴 Qwen3，先判断是否需要展开推理；
  * • **阶段调度** 借鉴 GLM-5，决定在哪个工作步骤使用更多计算；
  * • **深度选择** 借鉴 DeepSeek V4，为不同失败代价设置不同档位；
  * • **预算训练与回退** 借鉴 Kimi K2.5，先保证正确，再逐步收紧成本；
  * • **硬预算和验证** 由 Harness 负责，避免模型无限消耗，也避免把“想得更久”当成正确证据。

这条链来自前述公开路线的工程归纳，四家公司并未声称自己实现了同一套调度器。

我的看法比较保守。团队起步时，暂时没有必要训练一个“智能 effort 路由器”，先把每个任务记成三本账更有用。

  * • **结果账** ：目标是否达到，测试、规则或人工复核是否通过；
  * • **成本账** ：模型、档位、推理 token、工具轮数、时延和外部调用花了多少；
  * • **状态账** ：任务使用了哪版输入，调用过什么工具，改了哪些对象，产生了什么副作用。

三本账记下来，升档才有依据。失败后可以先做一次简单分类：

  * • 验证器发现逻辑漏项，或者多个约束仍有冲突，增加推理计算可能有帮助；
  * • 工具超时、环境污染、依赖缺失和权限拒绝，应先修复外部条件；
  * • 涉及生产写入、对外发送或正式发布时，再高的 effort 也不能代替审批、回滚和责任边界。

线上策略可以先从 `medium` 基线起步：

  1. 1\. 任务确定、可逆、容易验证时降档；
  2. 2\. 任务存在多重约束，或失败代价较高时升档；
  3. 3\. 每次调用都保留 token、时间和费用上限；
  4. 4\. 结果先过测试、规则或人工复核；
  5. 5\. 失败后最多自动升档一次，再失败就换策略或转人工。

如果不限制升档次数，系统很容易把低档失败变成高档重试，再变成更长的高档重试。成本增加了，根因仍可能是工具错误、上下文缺失或需求本身不完整。

## 选档前，我会先问五个问题

档位名称没有统一标尺。下面说的低、中、高，只表示同一模型内部的相对选择。

比“这个任务复杂不复杂”更有用的，是先检查五件事：

  1. 1\. 输入和目标是否完整，还是缺少关键上下文？
  2. 2\. 执行路径是否确定，能否按规则直接完成？
  3. 3\. 结果能否用测试、规则、Diff 或人工复核验证？
  4. 4\. 动作是否可逆，失败会影响草稿、代码库还是生产数据？
  5. 5\. 当前障碍来自推理不足，还是工具、环境、权限和依赖？

同样叫“开发一个接口”，读取已有类型、设计兼容方案、写代码和排查 CI，适合的档位可能完全不同。按任务阶段调度，通常比给整类任务固定一个档位更稳。

* * *

## 四个现场，档位怎么落

工作、生活、研发和架构的具体任务差别很大，选档规律却很接近：低档处理确定动作，中档处理多重约束，高档留给失败代价较高、确实需要取舍的阶段。

  
  
图 3：工作、生活、研发和架构场景中的 effort 相对选择

### 工作：从会议纪要到供应商评审

整理会议记录、提取负责人和截止日期，输入清楚，也容易和原始记录核对，低档通常够用。

比较三家供应商方案时，模型需要同时处理价格、交付周期、现有系统兼容性和合同条件，中档更适合作为起点。如果方案会影响年度预算或核心系统，评审阶段可以升档，但原始报价、合同条款和负责人确认仍要独立保留。

这样分档至少能避免把计算浪费在确定性整理上，也把人的复核时间留给真正存在冲突的方案比较。

### 生活：一次带约束的行程规划

把日期转换成统一格式、按城市归类景点，用低档即可。加入老人同行、儿童作息、预算、交通换乘和退改规则后，任务进入多约束比较，中档更合适。

如果行程涉及用药、保险、签证或重要合同，高档最多用于整理问题和发现遗漏。最终决定仍应回到官方规则或专业人员。模型想得更久，也不会自动获得最新政策和专业责任。

### 研发：一个接口，分阶段调档

读取类型定义、搜索调用方和做确定性改名，可以用低档。设计向后兼容方案、补测试和处理几项业务约束时，切到中档。

CI 失败后，先看环境和工具状态。依赖下载超时、测试环境污染、权限不足，升到高档没有意义。只有验证器发现逻辑漏项、多个约束互相冲突，或者跨服务调用链难以定位时，更高 effort 才可能带来收益。

修复完成后，结论交给测试、静态检查和代码评审确认。推理档位不参与签字。

### 架构：把高档留给取舍阶段

跨服务迁移需要梳理依赖、容量、数据一致性、切流顺序和回滚条件。方案比较阶段的不确定性最高，可以给模型更多推理空间。

进入执行阶段后，更稳的做法是把方案压成确定的 runbook、检查项和门禁，让大部分步骤回到中低档或规则系统。全程高档不仅慢，也容易让执行步骤混入新的临场判断。

架构决策最终还要接受容量数据、故障演练和业务负责人的检验。模型可以补思路，不能替团队承担变更风险。

## 调档要看真实任务数据

团队刚接入 effort 时，不必急着做智能路由器。可以先从最近 2 到 4 周里抽 30 到 50 个真实任务做起步样本；它未必足够下最终结论，但通常已经能暴露一批明显问题。

起步时可以先跑一版最小评测：

  1. 1\. 选 `medium` 作为基线；
  2. 2\. 同一任务分别跑低、中、高档；
  3. 3\. 用测试、规则校验或人工审核判断是否成功；
  4. 4\. 记录端到端指标，不只记录生成 token；
  5. 5\. 只有评测证明收益足以覆盖成本时才升档。

指标不必一开始就铺得太满，我会先记这些数据：

  * • 任务成功率；
  * • P50 和 P95 时延；
  * • 推理 token、总 token 和费用；
  * • 每个成功任务的总成本；
  * • 重试次数与工具失败次数；
  * • 上下文缓存是否命中，是否发生重新预填充；
  * • 最终结果是否通过测试、校验或人工复核。

“每个成功任务的总成本”比“单次调用用了多少 token”更有意义。高档一次成功，可能比低档连续重试三次便宜；一个简单分类任务如果低档已经稳定，高档多用的 token 就很难产生价值。

最终留下的是一组经过本团队任务验证的路由规则。固定档位表很快会过期，因为模型、工具和任务分布都在变化。

* * *

## 三个边界，要留在系统里

第一，GPT-5.6 的训练细节没有公开。我们可以借它的下拉菜单理解问题，不能反向推断它用了哪种配方。

第二，同名档位不能跨模型直接比较。`high` 代表的是某个模型内部的资源偏好，不是行业统一刻度。

第三，**更长的推理过程不构成可审计证据。**  测试、编译器、规则校验、事实核对和人工审批，仍然要放在模型输出之后。

坦率说，现在还很难判断哪种训练路线最终会成为主流。但工程侧不必等这个答案。模型会不会想、在哪一步想、想多久，已经开始成为可测量、可调度的参数。

模型把可变的推理能力交出来，Harness 再决定何时使用、最多花多少、用什么证据停止。走到这一步，effort 才从菜单选项变成工程能力。
