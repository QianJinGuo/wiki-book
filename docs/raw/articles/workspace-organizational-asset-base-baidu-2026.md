# Workspace 实践：从个人提效到组织提效

> 百度Geek说（何雪源）第一方实践：个人提效 ≠ 组织提效。一个人变成「超级兵」并不能提升团队需求交付数据。本文讲清三件卡在中间的事，以及用 Workspace 这个「面向 Agent 的组织资产基座」怎么解。

## 一、业务提效的困境：三类卡点
三个卡点挡在团队吞吐前面：①个人经验难以复制、②跨角色背景对齐成本高、③工具生态各自为政。共同点：都不是「模型不够强」造成的，换更强模型也不会消失。

**① 个人经验难以复制**：举例 iCafe skill 返回 403 权限错误，实测是后端接口限流与权限无关，作者在自己 CLAUDE.md 加规则「当 iCafe 返回 403 时最多重试两次，sleep 3 秒和 5 秒，仍报错按失败处理」。但其他人遇到同样报错得把走过的流程重走一遍，甚至真以为是权限不够然后卡住。问题：怎么把经验低成本传播给团队？

**② 跨角色背景对齐成本高**：一个需求从前到后要开很多对齐会（PRD 评审/代码设计评审/前后端接口对齐/测试 case list 评审），涉及角色配合就得约人，约前准备文档、开完还可能改几版再对齐。整个需求交付中「背景对齐」最难压缩——事事对齐消耗大量时间成为流程瓶颈，不对齐则方案清晰度/决策合理性无法引入对抗视角。问题：多角色如何高效沟通协作？

**③ 割裂的工具生态**：一个人在 Claude 上做了套好用的 skill 集合，其他人在 Comate、Codex 上没法用或效果差。问题：能否构建与具体 Harness/Agent 无关的基座，让各 harness/agent 都能运行在上边？

## 二、早期探索：Devflow
基于 SDD 理念在内部 Agent 平台搭建研发工作流 devflow。两个有价值的地方：✅厂内生态接得深（通过提示词让 Agent 知道 iCafe/iCode/知识库/iAPI 是干啥的，能自己取需求、取接口契约、写代码提评审——一个百度 Native 研发工作流）；✅工作流框架的约束力（讨论/设计/编码/测试/评审修改/合入/整理文档每阶段有硬门禁，必须先做完这步才能下一步——大模型能力不稳定时让交付质量相对稳定产出）。

有了 devflow 后个人产出量确实涨了（tmux 开 3-5 个终端会话并行），但从整个团队看需求交付数据没改善。**纵向的短板决定交付周期，横向的断点决定经验能不能变成组织能力。两条路都不通，个人产出涨了也传导不到团队数据上。**

### 组织提效要解决的四件事
1. **团队资产怎么攒起来**：第一步文档工程，找低成本把每个人脑子里的经验记下来的办法（低成本是关键，不然被本职工作挤掉）。
2. **攒起来的东西怎么流动**：前人的文档/报告/代码/经验后人得能用上；新产生的信息/经验/设计决策也得及时写回。东西要用起来才能产生新价值。
3. **流程和角色职责变化**：AI 对不同角色效率提升出现明显差异后，角色关系需调整（谁写测试/谁做评审/谁对质量负责，边界在 AI 进来后都挪位置）。
4. **交付质量要持续稳定**：让 AI 自由发挥可能这次完美下次完全没法用；不同人/不同 Harness/不同 Workflow/不同模型影响很大，需构建在一定范围内相对稳定可靠的结果。

## 三、殊途同归的解法：Workspace
### 3.1 Workspace 是什么
不是文档库、不是 skill 库、也不是把几个仓库放在一起。它解决的是「组织资产用什么形式组织、怎么流动」的问题，文档/skill/代码库都算在里面。它是**面向 Agent 的组织资产基座**——Agent 通过它了解业务、参与业务。把团队的知识库、代码库、iCafe 空间、skill 都放到一个代码库下面，Agent 能访问所有业务资产还能自行验证产出。

**关键实践经验：Workspace 不存知识的快照或备份，只存摘要和索引。** 不是把外部知识库/代码库/卡片内容整理成文本存进 Workspace，而是构建外部资产的索引，让 Agent 知道查询某个问题该去哪些平台获取。固有流程和方式不变（依旧在知识库写文档、iCafe 记录任务）——Workspace 不直接改变你的工作模式，这也是它推广起来的重要原因。

### 3.2 最小 Workspace 结构（俄罗斯方块示例）
```
tetris-workspace/
├── README.md                 # 唯一源：workspace 组织 + Agent 规则
├── AGENTS.md -> README.md    # 软链
├── CLAUDE.md -> README.md    # 软链
├── .claude/                  # 三端桥接，只放软链
│   ├── skills -> ../skills
│   └── agents -> ../agents
├── .codex/  .comate/         # 同上
├── agents/                   # tetris-playtester.md 等
├── docs/
│   ├── README.md             # 路由表，不放内容
│   ├── INDEX.md              # 资产索引，一行一条，供精确检索
│   ├── LOG.md                # 资产维护日志
│   ├── knowledge/            # 知识层：游戏规则/经验/外部源入口
│   └── activity/             # 活动层：每次迭代记录
├── skills/                   # ku-doc-manage/icafe-official/icode/summarize
└── repos/                    # 代码库，git submodule 引入
```
docs 分两层，按「内容会怎样失效」划分不按主题划分：知识层（docs/knowledge/）放概念定义/外部系统入口/带条件的经验判断——被新证据推翻时回头改旧页不另写一页；活动层（docs/activity/）放每次迭代做了什么/怎么做的/验证结果——不失效只增不改。两层都放不下时停下来问用户。通过软链把 agents/skills 适配给 Claude/Codex/Comate 等 harness——新增 agent 或 skill 只改一个地方，解决多种工具生态问题。

### 几个重要文件
- **README.md——规则唯一源·三端共读**：AGENTS.md/CLAUDE.md 都是指向 README.md 的软链，规则只在 README.md 维护，不把软链替换成副本。
- **docs/README.md——docs 唯一入口·管路由**：只描述信息怎么找，不承载动态状态、不复制外部平台内容。外部平台（iCafe 空间/如流知识库/iCode）是权威源，docs 只是索引层与本地沉淀层。含「场景路由」表（精确找某资产→INDEX.md、约定当初为什么这么定→LOG.md、游戏规则→knowledge/tetris-rules.md、外部平台入口→knowledge/sources.md、踩过什么坑→knowledge/experience-*.md、某功能哪次迭代做的→activity/ 文件名带日期主题）。
- **docs/INDEX.md——一行一条资产·供检索**：资产表（类型/ID/内容/签名），签名列是内容摘要短哈希，用于判断本地缓存是否落后于权威源。
- **docs/LOG.md——按日期倒序变更日志·留依据**：格式 `## YYYY-MM-DD` 下挂条目，每条一句话说清改了什么、为什么——用途是半年后还能搞清楚某个约定当初为什么这么定。

### 最重要的一环：summarize skill
Workspace 能不能越来越好用，关键在 summarize skill（资产流动闭环的最后一环）。没有写回，Agent 每次都从零开始，Workspace 就退化成一个静态文档库。三条设计取舍：①**强制执行**——设计为会话最后必须执行，把决策判断/踩坑经验/结论变更/新外部源/活动记录写回，写回不靠自觉；②**尽可能不打扰用户**——让 summarize 自动记录+定期资产治理维护质量，减少人的决策（写回一旦变成需要人配合的手续就会被跳过，闭环就断）；③**宁多记不漏记**——一条略显多余的经验页只是噪声，一条丢掉的经验是下次重新踩一遍，拿不准写进不会失效的 activity 层。

summarize 的流程：①判断这次产生了什么（有没有需要判断的地方/踩坑/推翻结论/新数据源/做了什么怎么验证）；②分流（客观事实概念规则→knowledge 对应页、带条件判断踩坑→knowledge/experience-<主题>.md、外部系统入口→knowledge/sources.md、做了什么怎么验证→activity/<日期>-<主题>.md、本版参数阈值数值→**留 activity 页不进 knowledge**——参数会随下次调整而变，进知识层会立刻过期还被当规则引用）；③旧页被推翻时回头改原页（否则库里同时存在两份矛盾真相，下次检索命中哪份是随机的，活动层不改、历史错误决定原样保留作为经验页来源证据）；④同步 INDEX.md 与 LOG.md（日志为什么不能省）；⑤补双向引用（新页 Related Docs 指向相关页，同时回被指向页补反向引用，单向引用等于没引用）。

## 四、基于 Workspace 的实践：RocketMQ Workspace（组织级）
核心产品 Workspace，所有产品和业务相关信息都可在上面查询。文档组织分三层。沉淀 20 个 skill 按用途分六组，覆盖从需求讨论、开发验收到排障、封线、资产沉淀的完整链路。Workflow 四阶段 Spec Driven Development。实践例子：Bug 修复（打开新会话→调用 diagnosing-bugs 基于历史 bug/现象/日志/代码/社区 issues 定位原因→确认产品 Bug 后调用 to-icafe-card 创建卡片→调用 spec-workflow 走完方案设计/开发/验收/收尾四步→得到 Bug Fix 的 Patch 和完整交付报告）；新功能开发（打开新会话→调用 spec-workflow 走 spec driven 流程）。
