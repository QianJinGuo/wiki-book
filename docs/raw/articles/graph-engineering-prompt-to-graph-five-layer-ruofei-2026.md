# 从 Prompt 到 Graph：一文理解五层 Agent 工程

## 摘要

以 Peter Steinberger 的玩笑（"Are we still talking loops or did we shift to graphs yet?"）切入，回应 Agent 领域新词焦虑：Prompt、Context、Harness、Loop、Graph 不是互相取代的关系，而是各管一段边界的五层工程。系统不稳时先看缺的是哪一层的能力，Graph 不是每个 Agent 的下一站，Loop 也没有过时。

## 五层各管一段边界

| 层 | 职责 | 常见问题 |
|----|------|---------|
| **Prompt** | 一次任务的工作约定：目标、范围、限制、输出、完成条件 | 答非所问、遗漏约束 |
| **Context** | 模型眼前的工作集：事实、代码、状态、版本、时效 | 引用旧版本、漏文件 |
| **Harness** | 模型外面的运行现场：工具、权限、预算、验证、日志、回滚 | 工具时好时坏、结果无法复现 |
| **Loop** | 一个工作单的推进与收敛：反馈、停止条件、回退 | 反复绕路、停不下来 |
| **Graph** | 跨工作单元的稳定关系：状态、依赖、失败路径、审批 | 一协作就乱 |

控制范围由内向外扩大，外层建立在内层之上。Prompt 写得再细也解决不了旧事实；模型再聪明也替代不了幂等键、检查点和发布审批——每层处理的对象不同，不能互相顶替。

**运行时嵌套**：概念上由内向外展开，运行时反复嵌套——一个"调查根因"的 Graph 节点里可以跑一条 Loop，Loop 每轮又重组 Context、调用 Harness 工具、使用更具体的 Prompt。

## 任务穿过五层：修复支付回调偶发重复入账

- **Prompt**：说清可改哪些服务、哪些账务数据不能直接动、什么测试通过才算完成
- **Context**：当前分支代码、最近失败日志、回调协议、数据库结构、复现条件——最小充分工作集，不把整家公司文档塞进对话
- **Harness**：能用什么工具、隔离环境、预算、写操作确认、结果验收——模型真正开始碰到外部世界的地方
- **Loop**：新日志推翻假设、测试失败继续修复或转人工——反馈、停止条件和回退
- **Graph**：复现→修复→CI→审批→灰度→回滚的稳定依赖和失败路径，让系统知道自己走到哪里、什么可重跑、什么必须有人放行

## AutoResearch：把五层接在一起

Karpathy 的 AutoResearch（Coding Agent 修改小模型训练代码→跑固定时长训练→读验证指标→决定保留/放弃）压缩成一行：提出想法 → 修改 train.py → 提交 → 训练 → 读取 val_bpb → 保留或回退 → 下一轮。

五层分工：Prompt=program.md 写明目标/可改范围/记录方式/取舍标准；Context=任务说明+当前代码+Git 状态+results.tsv 实验历史；Loop=单条循环。效果数字只对应特定代码库/训练任务/指标，不能换算成"研发效率普遍提升 11%"——它说明的是：目标单一、指标可测、动作受限、失败可回滚时，一条 Loop 可以稳定连续工作很久。

**经验**：先把目标、尺子、权限、历史和回滚做扎实。单条 Loop 够用时，没必要追新名词把系统提前改成复杂的图。Karpathy 自己写 "I'm not actually exactly sure what this should look like"——多 Agent 异步协作仍待探索。

## Loop 与 Graph 的控制边界

- **Loop 适合**：运行前说不清的路径（线上故障调查：先看日志还是先看最近发布取决于告警和第一批证据）
- **Graph 适合**：已经能说明白的关系（复现通过才能修复、CI 通过才能灰度、灰度恶化必须回滚）
- **三个分界问题**：①关系是否稳定（运行前能否写清依赖/分支/汇聚条件）②失败是否昂贵（中断后需局部恢复？重试会不会重复扣款/写库/发布）③过程是否需要负责（审计/审批/预算/跨团队交接）——信号都很弱时一条 Loop 更省事；任意一个变强就该上 Graph

## 场景化的边界判断

- **旅行规划**：Prompt=日期/预算/不可接受条件；Context=实时车次/天气/房态/退改规则；Harness=查询工具/证件保护/付款权限；"确认库存→人工确认→下单→付款"走 Graph
- **周报/经营简报**：数据并行采集留 Loop，Graph 盯汇聚门（时间范围一致、空列表是真空还是接口失败、少一个数据源能否继续发布）
- **线上故障**：根因调查+修复随证据换路留 Loop；复现/CI/审批/灰度/观测/回滚进 Graph
- **批量数据回填**：按租户/时间分片只画出并行拓扑，能否恢复取决于每片是否有输入版本/分片 ID/幂等键/完成标记，调度层是否限制并发/保存检查点/准备对账补偿

## 系统不稳时先缩小问题范围

| 症状 | 先查 |
|------|------|
| 误解目标、输出格式反复跑偏 | Prompt（目标/范围/限制/完成条件冲突？示例带偏？） |
| 引用旧版本、漏文件、忘记状态 | Context（工作集过期？检索漏关键事实？历史噪声挤窗口？） |
| 工具时好时坏、权限太大、无法复现 | Harness（环境/工具契约/权限/日志/评测/回滚） |
| 能推进但反复绕路或停不下来 | Loop（反馈可信？预算怎么扣？失败怎么退？停止条件能执行？） |
| 单任务能做、一协作就乱 | Graph（状态互相覆盖？依赖藏在对话里？分支失败全量重跑？外部操作重复？） |

## 从能跑到可恢复：先补五件事

1. **记录真实路线**：Agent 调过哪些工具、在哪失败、哪些步骤每次出现、哪些路径总在变化——没有运行数据，提前画的只是想象中的流程
2. **把状态移出对话**：保存 task_id/input_version/stage/status/attempt/budget_remaining_seconds/artifact_uri/last_error——字段不必多，进程中断后至少知道做到哪一步
3. **把验证器放到明确的门上**：测试/指标/数据结构/代码差异/权限规则在固定位置检查；模型评审提供线索，不天然充当真值来源；标准偏主观时备好证据交人确认
4. **隔离有副作用的动作**：发布/写库/付款/通知单独成节点，补齐最小权限/幂等/审计/失败补偿；外部接口超时先查询真实结果再决定是否重试
5. **证明独立后再并行**：数据依赖/写集合/资源上限/汇聚规则说清后并行才增加吞吐，否则 Agent 数量先上去，冲突/重试/token 账单也一起上去

## 评审一张 Graph 的八个问题

1. **状态**：谁拥有任务状态？有任务 ID/状态结构版本/当前阶段/剩余预算/产物位置？
2. **节点**：输入输出有明确结构？允许哪些工具和权限？超时/取消/重跑如何表达？
3. **边**：B 为什么等 A？依据是数据依赖、控制依赖，还是书写顺序？
4. **验收**：通过靠什么证据？哪些可机械检查，哪些仍需人的经验？
5. **失败**：哪些错误值得重试、最多几次？继续失败后降级/回退/跳过/转人工？
6. **副作用**：写库/发布/付款/通知有没有幂等键与审计记录？部分成功怎样补偿或对账？
7. **恢复**：检查点保存在哪里？保存的是完整可验证产物，还是"已完成"标记？
8. **可观测**：能否看到节点耗时/成本/失败率/重试次数/人工等待时间？

如果大半问题只能用"Agent 会自己处理"回答，这张图多半还停在示意层——补状态、证据和失败路径，通常比继续拆节点更有用。

## 要点提炼

- 五层分工一句话：Prompt 说清工作，Context 提供当下事实，Harness 管住运行现场，Loop 负责探索和收敛，Graph 保存跨工作单元的稳定关系
- 历史类比：Kubernetes Controller 是控制 Loop，GitHub Actions 的 needs 是任务图——分工不新鲜，Agent 带来的新变量是节点内部多了一段会依据现场信息改变路线的执行过程
- 行动原则：熟悉的路径写成边，未知的路径留给 Loop；高风险决定保留一道有人负责的门；给 Agent 留出行动空间，同时让系统能说清看到了什么、做到哪一步、出了问题该从哪里继续
