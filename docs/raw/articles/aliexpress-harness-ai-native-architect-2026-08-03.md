## 1. 背景

半年前我写过一篇《AliExpress 终端智能生成能力建设》，讲的是我们怎么从 0 到 1 搭起 D2C 楼层生成、X2C 整页生成、Native 转码三条链路。那篇文章基于 Spec Coding 编程范式和 LangGraph Agent 架构，核心是"能力"——视图解析怎么做、生成流程如何编排、ReAct 决策怎么跑。

随着业界技术的快速演进（Harness Engineering、Context Engineering、Loop Engineering 等范式相继提出），我们的架构和方法论也经历了一轮升级。同时，我们还拓展了中后台智能生产场景。本文主要聚焦在 H5 B/C 端的 Harness 生成能力建设（X2C 整页智能选品和基础链路 Native 全栈生成暂不涉及），讲述我们做了什么、过程中有哪些关键判断，以及我的思考。

## 2. 架构设计

### 2.1 Harness 架构

通过注册生码 command，实现 IDE 端生成调度。先看全貌——管线和调用方式：

```
/ait --prd=<url/path> --spec=<url/path>
  │
  ├─ init       → 扫描工作区、生成/刷新 docs、校验环境与 MCP
  ├─ clarify    → PRD 结构化 + 页面 spec + 组件 spec（并行）+ 执行计划
  ├─ generate   → 按 plan.yaml 驱动脚手架创建 + 模块代码 + 页面代码生成
  ├─ docs       → 知识库文档生成与同步
  ├─ evaluation → 质量评测（pre-check / logic / ui / e2e）
  ├─ verify     → 发布卡口（性能 / 视图标准化 / 数据 / i18n / 埋点 / 稳定性）
  ├─ publish    → 代码提交 + 预发构建部署
  └─ evolve     → 自进化（session 归因 + harness 工程优化 PR）
```

Harness 的完整能力由两层组成：

**七层工程基础设施**——规则、记忆、上下文、执行、循环、反馈、恢复。这是让 Agent "能跑起来"的基座。

**四层确定性模型**——在七层基座之上，针对生码场景编排的确定性约束。这是让 Agent "做得对"的业务层。

Harness 的管线和分层设计，ATA 上已有很多优秀文章讨论，这里不赘述。我更想聚焦在一个实际落地中绕不开的问题：当 Agent 面对一个生成任务时——评测的断言依据是什么？方案有多条路径可达成时，哪个是最优的？最优的标准是什么？这些标准的延续性、有序性、可解释性如何保障？

这组问题推导出我们在 Harness 之上重点建设的三个能力：**标准化、评测、自进化**。

### 2.2 标准化

Harness 框架是通用的，但领域适配层决定了产出是否"对"。

从需求交付的最小单元——模块——来看，标准是什么？我们的定义是：**每个标准模块 = UI 契约 × 数据契约 × 功能契约，三位一体的最小封装单元。**

标准化相应覆盖三个维度：

#### UI 标准化

面向 D2C 生码场景，建立设计-代码协同的组件契约体系。核心思路：组件是设计与开发的共同语言，标准化组件库 = 双方契约层。

组件库分两层：

- 基础组件（契约层）：原子级，一一映射代码组件，进组件映射表。如商卡现价、Button 等——设计师和开发共同感知。
- 业务组装组件（模板层）：业务级，仅作设计师建稿模板，不进映射表。如 ItemCard = 多个基础组件 Slot 拼装。

协同走双轨制：

- 存量直出（主路径）：设计师拖标准组件 → 通过 componentKey 硬绑定代码组件 → D2C 直接生成对应代码
- 自定义生成（补充路径）：未命中设计组件库 → AI 自定义生成 → 评估后沉淀回组件库，下次走直出

#### 数据标准化

核心目标：让接口契约和字段命名在全链路中有唯一确定的定义，AI 生成时无需猜测。AI 的角色是在规则已确定的前提下按规则生成和校验。

数据标准化包含三个维度：

- **接口标准化** — 跟着系统接口定义走，包含接口命名标准化和接口数据协议标准化。接口按领域归属统一命名，命名即架构归属。B 端和 C 端在网关协议上有差异，但命名规则一致。
- **场景数据协议** — 跟着业务场景设计走。不同场景模块（表格、表单、详情、商卡等）有各自的标准数据结构——如表格场景固定包含 list/total/pageSize/current 等场景预设字段。B 端和 C 端的场景类型不同（B 端以表格、表单为主，C 端以商卡、瀑布流为主），但协议设计原则一致。
- **字段标准化** — 字段按语义和使用方式分三类，每类有独立的注册规则和推导规则。
- **领域治理** — 数据标准化的组织承载。标准化不是一份文档能解决的——它需要回答"这个字段归哪个域管"、"命名冲突谁仲裁"、"新字段谁审批"。我们建立了 13 个一级领域、细分子域的治理体系：每个领域有明确的 Owner，负责字段注册和命名审批；实体归属遵循"业务能力聚合"原则——同一实体的所有属性字段归属同一领域，不允许跨域散落；领域划分一旦确定，接口归属、字段归属、审批权限均可自动推导。

#### 功能标准化

一方面是原子级功能组件——高频复用的交互能力（如埋点、国际化、加购、收藏）封装为 SDK 或内置在原子组件中，生成时直接调用，不重复实现。

另一方面是复合型/新增功能——涉及多状态、数据流转、动效、复杂交互等场景，无法用现成组件覆盖。这类功能通过三层 Spec 做结构化澄清——每层 Spec 都内置了对应复杂场景的描述框架，让 AI 有明确的"填空结构"而非自由发挥：

| Spec | 解决什么问题 | 关键内容 |
|---|---|---|
| PRD Spec | AI 理解"要做什么" | 模块分解、功能点列表、状态枚举与转换条件、验收标准。禁止补充原文没有的内容，模糊处标注 [待澄清] |
| Tech Spec | AI 理解"怎么做" | 组件选型、Props 映射、状态机定义（状态×事件→转换矩阵）、动效触发条件与参数、交互流转路径、任务 DAG |
| Data Spec | AI 理解"数据怎么流" | 接口 Schema、字段映射、数据流转路径（请求→转换→渲染）、多状态下的数据切换逻辑、Mock 数据 |

### 2.3 评测

生成阶段按 Tech Spec 产出的任务 DAG 逐层执行（同层并行、跨层串行），通过复杂度路由将任务分为 fast path / 标准 / SubAgent 分派三档。这里不展开生成编排细节，聚焦在更核心的问题：**生成的代码怎么保证是对的？**

**评测维度** — 覆盖代码上线前需要验证的 5 个方面：

| 维度 | 检测什么 | 检测方式 | 为什么需要 |
|---|---|---|---|
| 结构正确性 | TS 类型错误、导入缺失、组件引用错误、运行时崩溃 | tsc --noEmit 全量编译 + Vite DevServer 启动 + 首屏无 console.error | 编译不过的代码没有讨论其他维度的意义 |
| 数据完整性 | Data Spec 定义的字段是否全部在代码中消费，接口返回值类型是否与 VO 定义一致 | AST 扫描代码字段引用 vs Data Spec 字段清单，diff 输出遗漏/多余字段 | 前后端契约不一致 = 上线后白屏 |
| 逻辑正确性 | PRD 功能点是否逐条实现（含边界条件和异常路径） | 逐条对照 PRD Spec 功能点列表，检查代码对应实现 + 条件分支覆盖 | 功能遗漏 = 需求未交付 |
| UI 保真度 | 布局结构、间距、字体、颜色是否与设计稿一致 | Chrome DevTools MCP 运行时截图 vs 设计稿（Figma snapshot）AI 视觉识图对比 + DOM 嵌套合规性检查 + Figma JSON 精确间距校验 | 还原度不达标 = 设计师不验收 |
| E2E 功能 | 用户操作流程（点击、输入、跳转、状态切换）是否按预期执行 | Chrome DevTools MCP 自然语言驱动测试用例 + 模拟用户操作（点击/输入/滚动）+ AI 视觉观测断言（Observation-First）+ 网络请求验证 | 逻辑对但交互不通 = 用户无法使用 |

**实施方式** — 多 SubAgent 并行检测，每个维度一个独立检测 Agent：

```
Phase 1: 并行检测（仅检测，不修复）
  ├─ pre-checker    → 结构正确性
  ├─ data-checker   → 数据完整性
  ├─ logic-checker  → 逻辑正确性
  └─ tc-generator   → 测试用例 + Mock 预生成（为后续 UI/E2E 准备）
Phase 2: 串行修复（按顺序修）
  pre → data → logic（先结构后语义）
Phase 3: UI/E2E 检测 + 修复
  ui-checker（含内置修复循环）→ e2e-checker
```

**客观性保障** — 如何确保评测结果可信：

- 检测与修复分离：Phase 1 的 SubAgent 只报告问题，不做修复。报告写入独立文件，后续修复基于报告而非"自己觉得哪里有问题"。
- 多 Agent 交叉验证：同一份代码被多个独立 Agent 从不同维度检测。logic-checker 发现的问题和 data-checker 发现的问题可以交叉印证。
- 不可篡改的检测结果：每轮检测结果写入 evaluation/{dimension}/report.json，一旦写入不可被后续修复 Agent 修改。综合 Review 阶段读取所有 report 做交叉分析。
- 人工兜底：verify 阶段始终由人确认，系统给出 verdict（PASS/FAIL + 理由），人做最终决策。

**自修复流程**：4-Gate 顺序执行，每个 Gate 是一道质量卡口：

```
生成产物
  │
  ▼ Gate 1: 能跑 ─── 编译通过 + DevServer 启动 + 无 runtime crash
  │   [未通过] → 修复类型错误/导入缺失/语法问题 → 重试（≤3轮）
  ▼ Gate 2: 数据足 ─── 字段完整 + 接口对齐 + Mock 数据合理
  │   [未通过] → 修复 VO 映射/字段补全/类型转换 → 重试（≤2轮）
  ▼ Gate 3: 用法对 ─── 组件 Props 合规 + Hooks 用法正确
  │   [未通过] → 查阅组件文档修正 Props/调用方式 → 重试（≤2轮）
  ▼ Gate 4: 功能通 ─── E2E 测试全部通过
  │   [未通过] → 补充逻辑/修正状态管理/修正交互 → 重试（≤2轮）
  ▼ 评测通过 → 进入 verify
```

核心约束：前置 Gate 未通过时，后置 Gate 的结果无效。编译不过去检查 UI 保真度没有意义——先把结构性问题解决干净，再处理语义性问题。

### 2.4 Evolve 自进化

Evolve 解决一个问题：修过的 bug 下次不再出现。每次生成过程中发现并修复的问题，自动转化为系统知识，让下一次生成更好。

核心流程（三阶段）：

- 阶段一：发现问题（Python 自动完成）——收集本次生成的修复记录 → 检测是否有重复模式 → 跨多次生成聚合判断"这是个例还是通用问题" → 过滤噪声（单次出现的不算，要多次交叉验证）
- 阶段二：定位根因并修复（LLM 完成）——分析问题根因 → 判断该修哪里（Skill？Spec？Rules？）→ 生成修复补丁（可能同时修多个文件）
- 阶段三：审查合入（Python + LLM + 人）——自动校验补丁格式 → LLM 评审质量（≥85 分通过）→ 创建 MR 供人工最终确认

关键设计决策：

- 修复方向优先级：skill > spec > hooks > rules > knowledge。优先改源头——修 Skill 的执行步骤比加一条 rule 更彻底。
- 永不降级：证据不足时暂缓（deferred），不会退而求其次写一条没人用的 knowledge。
- 消费保障：每条新知识必须有明确消费者——某个 Skill 会读它。没有消费者的知识 = 拒绝合入。

## 3. 过程思考和判断

### 3.1 目标边界：生成准确度、效率与用户体验的三角平衡

问题：生成准确度、生成效率、用户体验——三者不可能同时最大化。早期业界、集团内很多团队选择了"效率优先"——做类似 Manus 的通用生成产品，给一张图就尽可能还原。我们也曾是其中一员。但很快发现：追求速度的同时，准确度和体验全崩了。

碰到的现实：

- 生成准确度无法保障——通用生成不了解业务上下文，无法做正确的交互决策和数据绑定
- 生成效率看似快实则慢——"生成 5 分钟，人工修正 1 天"，全链路总耗时反而更高
- 用户体验无法达标——没有设计规范约束，一致性、组件复用、响应式布局全部缺失

分析："通用生成"和"生产可用"是两个完全不同的目标。前者追求覆盖面，后者追求三个维度的平衡：生成准确度（一次生成能否直接上线，而不是"能跑起来但还得改"）；生成效率（全链路总耗时（生成 + 人工修正 + 评测）是否低于纯人工开发）；用户体验（产出的代码是否符合设计规范、性能基线、无障碍标准）。

决策：三者不可兼得时，要保持克制——先保准确度（生成就能上线），再追效率（更快交付），体验由标准化组件库兜底。我们今天承载的是组织转型和生产提效的命题，不是做一个可以讲故事的产品。

### 3.2 持续交付：业务落地与标准化的平衡

问题：数据协议、接口命名、组件选型——"按现有方案凑合"短期交付最快，但全局视角下这是正确的选择吗？

用户原声："迁移到新的平台，上下行数据结构改动较大，需要新建接口——能否提供数据适配层来适配老接口？"、"商家订单管理现有场景下，Seller APP 和 PC 是同一套水滴协议接口。如果 PC 端使用新接口、Seller APP 继续用老接口，相当于要维护两套，需求支持成本偏高。"

每个业务方的诉求都合理——需求下周要上线，你让我现在重写接口？但如果每次都让步，半年后就是 N 套并存的协议、N 套无法复用的字段命名、N 套互不兼容的接口规范。

分析：核心冲突：局部最简 = 短期快 + 全局碎片化债务；全局最优 = 当下慢 + 长期复利。这里的难度 80% 不在技术定义本身，在组织共识——让所有相关方认同"现在多投入是值得的"。而组织共识的达成需要一个前提：让业务方看到"标准化不是加负担，是减负担"。全栈工程师大部分没有前端背景，必须尽可能少干预、高质量——规则越确定，AI 生成质量越高，人工修正越少。这就是标准化的直接收益。

决策：充分调研业务方意愿后，我们在规范性与灵活性之间找到平衡点，划定了明确的"可动/不可动"边界来降低落地阻力："不可动"的是 AI 生成的确定性基座——越是影响生成质量的规则越不能松动；"可动"的留给服务端灵活实现，降低迁移阻力。这让业务方看到"不是让你全重写，是告诉你哪些必须遵守、哪些你自己定"——共识的达成起点是让步的边界清晰可见。

技术选型和组织选型始终是同一问题的两面：晓斌老师在《AI Native 时代——研发组织何去何从》中提到："脱离组织承载力的技术方案，是正确但无法存活的方案。"这正是我们的体感。标准化的尺度不由技术完美性决定，由组织能承载的极限决定。

### 3.3 能力迭代：范式演进中的判断力

问题：去年同期，我们就未来的生产模式和生成结果做过完整的推演。从最早模型能力不足时，需要做很重的工程能力补全（LangGraph Agent + ReAct 决策树 + 多轮自修复）；到现在研发范式越来越明朗（Harness Engineering + Loop Engineering），效果越来越好。但每一次范式变更都要面临同一个问题：保留哪些，丢弃哪些？

分析：判断力需要三个输入——对现有系统的深度理解（哪些是经过验证沉淀下来的资产，哪些是当时模型能力不足的补丁）；对新范式的本质认知（它解决的是什么层面的问题——是执行效率？上下文管理？还是决策质量？不是"看起来新所以跟"）；真实场景的验证数据（概念推演不能代替结论，要靠实际业务场景跑出来）。

决策：我们的判断原则——区分"资产"和"补丁"：

- 保留（跨范式不变的资产）：标准化体系（数据-UI-交互）、领域知识库、Spec-Driven 规范、端到端评测能力、上线卡口等。
- 丢弃（模型增强后自然消解的补丁）：自建 RAG 检索链路、LangGraph 多轮决策树、过度设计的智能路由矩阵等。

## 4. AI 时代，架构师做什么

### 4.1 瓶颈转移：从模型到人

分享一个真实 case：早期设计 d2c Agent 时，测试一个简单模块（一句话的文本模块），跑了 50 分钟。最后排查发现，加载了 1424 行 SKILL.md，并索引加载了许多无用的上下文。完整走完了每一个流程，实际代码生成环节 LLM 工作只有 94 秒，90%的流程是无用的，最终生成业务代码行数也只有 50 行。

和这个 case 类似，大多数情况下，系统的天花板都不在模型能力，而在架构设计。也就意味着，当执行不再是瓶颈时，判断力成为最稀缺资源。

### 4.2 架构师的新定位

阿伦特在《人的境况》中区分了三种人类活动：Labor（维持生存的重复性劳动）、Work（创造持久物的技艺）、Action（在人群中发起新事物、揭示行动者独特立场）。

- AI 正在替代 Labor 层——执行已不是人的价值所在。
- AI 参与 Work 层——但需要人注入"持久性标准"，否则 3 天后就要重构。
- 而 Action 层——在不确定中判断、发起、承诺——AI 无法触及。

架构师的新定位正是 Action 层："定义什么是对的 + 设计让对的事自动发生的机制"。具体而言，这意味着五种核心行为：

- 判断（在信息不完整时做出选择，并承担后果）
- 诚实（承认不确定性，不用"技术复杂度"掩盖"还没想清楚"）
- 体感（从现象中提取正向/异常信号）
- 发起（在组织中推动变化——标准化共识、架构升级、技术债清理）
- 组织感知（理解一个技术方案能否在这个组织中存活）

这些行为的共同特征：需要在不确定中做出选择，并为选择的后果负责。

### 4.3 约束是主动选择

对系统施加约束（Harness）= 让 AI 只做对的事。对自己施加约束（收敛需求边界、延迟决策、拒绝跟风）= 让注意力聚焦在最高杠杆的判断上。

### 4.4 总结

回到企业场景，我认为这三件事是 Architect 在这个时代的定位：

- 给 AI 系统建 Harness——确定性约束，让生成结果可预期、可上线
- 给领域建标准——知识资产，让第 100 次生成比第 1 次更好
- 给组织建机制——让标准自动执行，不依赖个人记忆

模型会越来越强。但"定义正确性"这件事——需要在具体业务中承担过后果、见过失败模式、做过取舍的人来做。这不是能力不可替代，是愿意为判断承担后果不可替代。
