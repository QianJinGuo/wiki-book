# AI Infra 综述：模型之外，任务怎样真正跑起来

> 若飞（架构师 JiaGouX）AI Infra 综述：模型选好了、接口通了、Demo 看起来不错，但 Agent 真去做事时麻烦出在模型之外——工具参数填错、查询越权、环境被回收、审批回来进程不知从哪继续、答案完整却找不到证据。这些靠调 Prompt 解决不了，都要回到基础设施。

## 核心命题：AI Infra 的讨论重心在模型服务之上

IBM 对 AI Infrastructure 的解释很宽（创建、部署和管理 AI 应用及工作负载所需的硬件和软件）。但团队已通过云 API 或内部模型网关取得模型能力后，新的工程工作主要发生在接口上方，需要解决三组问题：

- **怎么行动**：模型能调用哪些工具，代码在哪里运行，什么操作必须拦住
- **怎么连续工作**：任务做到哪一步，暂停或重启后怎样继续，过去的信息哪些值得留下
- **怎么验证**：一次运行发生了什么，系统改动后有没有变好，最后的业务结果是否成立

三组核心能力：模型服务提供推理能力；**任务运行时**负责行动、连续性和反馈；业务系统确认结果。从 Agent 应用看，AI Infra 的任务不是把模型"包起来"，而是把模型提出的下一步，变成一次**受控、可继续、能核验**的行动。

## 一、工具与沙箱：能做什么，在哪里做

### 工具不是一张函数清单

MCP 规范把工具的名称、说明、输入参数和输出结构做成明确 Schema，解决了"模型怎样理解和调用工具"，没解决"这次调用能不能执行"。最新规范（2026-07-28）区分协议连接与工具状态：MCP 没有协议级会话；有状态工具需返回显式句柄，后续每次调用仍应核对授权并说明句柄有效期。

**工具接入至少要说明五件事（工具合同五要素）**：
1. 输入是什么——时间窗、环境、资源标识是否必填，未知字段是否拒绝
2. 调用者是谁——用户身份、服务身份，还是临时任务凭证
3. 会产生什么影响——只读查询、创建草稿、修改配置，还是不可逆操作
4. 失败后怎么办——能否安全重试、是否需要幂等键、超时是否代表操作没有发生
5. 留下什么证据——返回结果要带来源、时间、版本或回执编号，不能只有一句 success

工具说明写得含糊，模型选错工具并不奇怪。第一批工具宁少而清楚：故障初查只开放三个只读动作（读指定时间窗指标、按服务和时间查日志、读取已发布版本），每个动作限制环境和资源范围，结果返回证据引用。链稳定后再讨论写操作。

### 沙箱解决执行边界

OpenAI Sandbox Agents 文档把系统分两部分：**Harness 是控制面**（模型调用、工具路由、审批、追踪、恢复、运行状态）；**Sandbox 是执行面**（文件、命令、依赖、挂载、端口、快照）。敏感信息归属：
- 身份认证、账务、审计、人工审批留在可信控制面
- 沙箱只拿当前任务需要的目录、短期凭证和网络范围
- 执行时间、CPU、内存、磁盘、进程数、出网目标分别限制
- 生成物先进待验收区，不直接覆盖正式版本

E2B 等沙箱产品提供超时、暂停、恢复、终止等生命周期能力，但"用了沙箱"不能推出已经安全合规——挂载了什么、允许访问哪些网络、凭证能做什么仍取决于接入配置。**沙箱限制代码在哪里运行，权限系统决定它可以碰什么。**

## 二、状态与记忆：做到哪一步，以后记住什么

聊天历史一长，团队容易把消息列表同时当上下文、任务状态和长期记忆。设计时应拆成**四类**：

1. **当前上下文**：这一轮交给模型的信息，尽量精简（指令、证据摘要、工具定义）
2. **任务状态**：这次工作做到哪里——当前步骤、已执行动作、待审批调用、重试次数、下一步、完成条件
3. **记忆**：跨会话/跨任务仍有用的信息（用户确认过的报告格式、稳定服务归属、长期项目约定）
4. **事实与证据**：留在原系统或证据存储（当前发布版本、某分钟错误率、原始日志都不该因写进"记忆"就变成真相）

### 状态要能恢复一项任务

LangGraph Persistence 用 checkpointer 按 thread 保存图状态，支持暂停、人工介入、回放、故障恢复。OpenAI Agents SDK 把中断项和可恢复状态作为运行结果的一部分（审批未结束时返回待处理调用与状态快照）。框架提供保存/恢复接口，业务仍要定义保存什么。

故障初查检查点示例：
```
task_id: incident-20260812-017
status: waiting_for_approval
current_step: query_production_logs
completed:
  - metric_window: evidence/metric-02.json
  - release_version: evidence/release-01.json
pending:
  tool: query_logs
  arguments_ref: requests/log-query-03.json
  approval: required
attempt: 2
acceptance_missing:
  - related_logs
```

这份状态没复制整段日志，也没保存模型总结——记录恢复任务需要的最小信息：做过什么、证据在哪、卡在哪步、回来该做什么。

**进程恢复 ≠ 任务恢复**：Kubernetes Job 失败可重试或新建 Pod，却不知道上一轮外部调用是否已成功；工作流框架可从检查点继续，也不能自动撤销已产生的副作用。只要工具可能写数据，就需要幂等键、操作回执和明确的重试条件。

### 记忆不是聊天记录仓库

LangGraph 把 thread 内短期状态与跨 thread 的 Store 分开；Anthropic 上下文工程文章把结构化笔记描述为上下文窗口之外的持久记录。关键不在"存得多"，而在下次能否取回**少量、相关、仍然有效**的信息。记忆系统至少要回答：谁能写入（模型提议后是否需规则/人工确认）、属于谁（个人/团队/项目/任务）、何时取回（关键词/语义检索/业务规则直读）、来源是什么（何时写入、多久需重新确认）、怎样更正和删除（删除后索引/缓存/备份如何处理）。

分界一句话：**状态服务于这次任务的继续，记忆服务于以后任务的取用。两者都不能代替事实系统。**

## 三、追踪与评测：发生了什么，改完有没有变好

### Trace 要串起整条运行链

OpenAI Agents SDK 内置追踪记录模型调用、工具调用、Handoff、Guardrail、自定义跨度。OpenTelemetry 推进生成式 AI 语义约定（统一属性描述模型/Agent/会话/工具操作），规范仍在演进，接入时不宜把某组字段当永久标准。Trace 至少应让人顺着同一 task_id 看到：任务开始 → 模型调用 → 工具策略 → 人工审批 → 工具执行 → 状态更新 → 业务验收。

Trace 要保留因果关系，同时避免把所有内容原样落盘——提示词、工具参数、工具结果可能含业务数据、密钥或个人信息，是否采集、保留多久、谁能查看、何时脱敏需单独设计。**Trace 越详细，数据治理责任越重。**

### Eval 要评过程，也要评结果

追踪回答"这一次为什么失败"，评测回答"改了模型/提示词/工具/工作流后整体有没有变好"。OpenAI 评测文档路径：调试阶段先看代表性 Trace + 结构化标准给运行轨迹评分 → 知道什么算好后固化样本成数据集 → 反复评测。

故障分析 Agent 可从五位置分别评：
- 是否选对工具，参数中的服务、环境和时间窗是否正确
- 是否绕过只读范围，审批被拒后有没有换一种方式继续
- 超时、重启或重复回调后是否从正确检查点继续
- 结论能否回到监控/日志/发布记录，证据是否真的支持表述
- 质量相近时，延迟、Token 和外部工具成本是否可接受

样本不能全是"正常路径"——权限拒绝、工具超时、空结果、相互矛盾的证据、过期记忆、审批等待才是运行时经常出问题的地方。评测通过后业务验收仍要单独做：Trace 能证明 Agent 调过回滚工具、工具回执可能写着成功，但当前版本和错误率是否真的改变，要回发布系统和监控平台确认。

## 四、把六个部分放回一项工作（故障初查链路）

告警系统创建任务（写明完成条件）→ 运行时读取任务状态与必要记忆 → 模型提出日志查询 → 工具层校验参数/身份/环境/资源范围 → 需脚本时沙箱提供临时工作目录和受限执行环境 → 每得新证据更新检查点 → 任务因审批暂停，恢复时从待调用工具继续（不重跑整段聊天）→ Trace 记录模型为何选这工具、策略为何放行、结果写哪 → 报告生成后监控和发布系统验收关键结论。

报告错了不必笼统说"Agent 不稳定"：
- 工具选错 → 查工具说明、能力重叠、评测样本
- 查询越权 → 查身份、资源范围、审批、服务端授权
- 重启后重复操作 → 查状态、回执、幂等与重试条件
- 引用旧版本 → 查记忆来源、有效期与事实读取路径
- 结论没证据 → 查 Trace、证据引用、业务验收

## 五、落地：先做一条最小任务链

不必一开始建"大而全 Agent 平台"。现有模型网关、权限系统、数据库、对象存储、工作流、可观测平台大多可继续用，缺的常是它们之间的接口约定。选一项高频、只读、结果容易核对的工作（故障初查、PR 只读审查、预发布核验 > 全自动运维）作为起点：

1. 写清任务完成条件，以及哪些情况只能标记"待确认"
2. 定义最小状态结构，用统一任务 ID 串起模型、工具、证据和交付物
3. 只接两三个职责清楚的只读工具，给输入/输出/权限/超时/回执定合同
4. 需要文件和命令时再引入沙箱，收紧凭证、网络、挂载、资源、存活时间
5. Trace 先覆盖模型选择、策略检查、工具执行、状态变化与最终验收
6. 从真实失败类型整理一小组脱敏样本（权限拒绝/超时/空结果/重启/证据冲突）

跑完看数据：时间花在模型排队 → 优化服务容量；经常选错工具 → 收缩工具集和说明；恢复后重复执行 → 补状态与幂等；答案看着不错但验收失败 → 回到证据链和评测标准。**投资方向来自运行记录，不必从产品清单反推。**

写操作晚点开放：先选影响范围小、能预演、可审核、易回滚的动作，沿用团队已有发布和审批制度——Agent 不需要另起一套生产规则。
