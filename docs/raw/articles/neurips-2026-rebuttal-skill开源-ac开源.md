Rebuttal该回答什么  ？

实际写 rebuttal 时，不少作者会顺着审稿意见一条条往下回复。  几位审稿人的问题依次展开，篇幅越写越长，  真正可能影响最终决定的核心问题反而被淹没。

李磊此前分享 rebuttal 攻略时，先讲的就是 rebuttal 究竟写给谁看。

rebuttal 直接回应审稿人，AC 同样是重要读者。  NeurIPS 要求审稿人阅读作者回复并参与讨论，AC 则要综合多份 review 和作者回应完成 meta-review。

作者既要回答审稿人的疑问，也要主动整理主要争议和新增证据，方便 AC 快速抓住重点。

审稿意见的字面问题，也未必就是审稿人真正担心的地方。

要求增加 baseline，真正关心的可能是比较是否公平。认为实验不足，可能是在质疑结论的可靠性。认为创新性有限，则需要讲清与最接近工作的实质差别。

回复不必完全按照 review 原有的顺序展开。多位审稿人共同关心的问题可以合并回答，核心问题放在前面，结论和新增结果优先说明。

能按时补完的实验，就用数据直接回应。暂时做不完，也要写清实验设计、验证目标和后续修改计划。

语气同样需要克制、专业。作者可以纠正误解，也可以指出评价与事实不符，但不要攻击审稿人，更不要直接要求改分。

视频末尾还展示了一个 ICLR 投稿案例。案例中，作者围绕多位审稿人共同提出的问题补充实验，rebuttal 后评分有所上升。

Rebuttal Skill怎么运行

Rebuttal Skill 可直接加载到 OpenCode、Claude Code、Gemini CLI 等支持 skill 的工具中。

两阶段工作流

第一阶段分析 review，把长段审稿意见拆成相互独立的问题，判断其背后的真实疑虑和严重程度，再生成 P0 至 P3 实验计划。

正式规划实验前，Stage 0 会先判断当前更适合继续 rebuttal，还是转向论文修改和重投。

第二阶段在作者提供真实结果后启动，先核验结果能否回应对应问题，再按  直接回答→证据→论文修改  组织回复。

覆盖的任务与输出

skill 可以处理澄清误解、承认局限、汇报新增实验、回应创新性质疑、baseline 缺失、统计可靠性，以及评分与文字评价不一致等情况。

五种输出模式分别对应 review 分析与实验规划、结果整合、完整 rebuttal、重投计划和已有回复质量检查。

** 证据和输入要求  **

**
**

skill 禁止编造实验数字，不能把计划中的实验写成已经完成，也不能隐藏负面结果。信息不足时，会保留明确占位符。

第一阶段需要论文摘要、完整 review、评分、会议评分标准、剩余时间和可用资源；第二阶段还需要真实实验结果、实验设置、论文位置，以及作者准备调整的论文主张。

实验优先级怎么定

很多 rebuttal 工具拿到审稿意见后，就开始分析问题和生成回复。Rebuttal Skill 先结合分数、审稿意见和剩余资源，  判断这轮 rebuttal 还有多少可操作空间  。

它会确认会议的评分区间、各档分数的含义、审稿人能否改分，以及是否允许补充新实验，再结合分数分布、审稿人的整体倾向和问题性质作出判断：

* 已有正面信号，主要问题能通过澄清或少量关键实验解决，会被归为  PROMISING  ；

* 分数处在边缘区，一项关键实验或更准确的解释仍可能改变最终判断，则属于  BORDERLINE / UNCERTAIN  ；

* 整体评分偏低，多位审稿人又同时质疑正确性、创新性或实证有效性，就会进入  LOW EXPECTED RETURN  ，后续重点转向事实澄清、论文修改和重投准备。

确认值得继续投入后，实验才进入 P0 至 P3 排序：

* ** P0 是必须立即完成、最可能影响判断的任务；  **

* ** P1 在 P0 之后推进；  **

* ** P2 用于补充完整性；  **

* ** P3 留到论文修改或重投。  ** 无法回应核心疑虑、缺少有效对照或耗时过长的实验，会被标记为  ** ` DO NOT RUN  ` ** 。

排序依据也不只是实验难度，还包括问题是否被多位审稿人共同提出、对最终决定的影响，以及一项实验能否同时回应多个问题。例如，一组计算量对齐的 baseline 比较，可以一起回应公平性、效率和对照不足。

这也是 Rebuttal Skill 与普通 rebuttal 写作工具最明显的区别：  ** 先决定哪些问题值得投入，哪些实验应该优先，哪些任务可以放弃，再开始组织回复。  **

NeurIPS 出分后，可以先让 agent 跑一遍 stage 0，  ** 把该做和不该做的任务排清楚。  **
