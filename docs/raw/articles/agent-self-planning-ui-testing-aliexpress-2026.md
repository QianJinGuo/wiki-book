# Agent自规划执行实践：让新需求 UI 测试自动跑起来的能力体系

> AliExpress技术（简礼）。AE 业务测试融入开发后的新需求（测新）UI 自动化——六层能力体系（C1 用例生成 → C2 前置构造 → C3 环境编排 → C4 自规划执行 → C5 断言与归因 → C6 报告与知识回流）。核心立场：Agent 只优化用例生成及执行，测新自动化整体价值上限就是 20%；剩下 80 个百分点的空间在前置构造、环境编排、断言与归因、报告与知识回流四层的工程化上。

## 一、背景：业务测试融入开发后，新需求如何测

AE 业务测试融合进各业务开发团队，新需求的业务测试归于开发自测，新需求自动化测试诉求与日俱增。「测新」是新需求在预发环境的验证，面对「每次都在变的预发环境 + 每次都是全新的用例 + 每次可能带着新的账号/配置/数据」——没有稳定选择器、没有历史录制可用，全靠 Agent 现场理解需求、现场规划、现场判断，这是 UI 自动化里最难的一档。

过去两个月把测新推到「AI 从用例生成到执行报告端到端交付一份可信结论给产研做验收」。最大教训：AI Coding 让写用例变快了，但真正卡住测新自动化的从来不是「AI 会不会生成用例」，而是「用例跑起来之前那 75% 的配置/环境/账号/前置数据能不能在预发就绪，跑起来之后那些『AI 假通过』能不能被识别」。

## 二、测新为什么难：不是「AI 让写用例变快了」就完了

新需求带来的 UI 变化：用什么账号（可能是新增权限白名单里的账号）、什么配置（新 Diamond/Switch/GOP）、什么数据（新造 SKU 或用户圈选，哪个国家语言、是否有实验）……预发环境本身还在动——每天多个应用提测、部署、切流、改配置。Agent 在预发环境跑用例，面对的是「每一步都可能是这次需求刚变过的东西」。

5 月把 SmartUI（APP 端）和 Midscene（PC 端）测新 skill 放给各场域（首页、频道、详情、搜索、购物车、招商、广告、商家基础），收到四大诉求：端到端执行、Trace 集成的可排查性、可信断言、数据构造。表面四件事，本质同一件事——AI 只是把「写用例」变快了，一条测新用例从「生成」走到「可验收的可信结论」中间还有五个环节。

**用例生成这一环，测新自动化的整体价值上限就是 20%**——多个新需求测试实测得出的数字。剩下 80 个百分点不在模型能力上，在中间四个环节的工程化上。从 5 月开始不再单点优化，把测新能力当作一个六层结构来建。

## 立场：这是 Workflow，不是纯 Agent

Anthropic《Building Effective Agents》的区分：Workflow 是「LLM 和工具通过预定义代码路径编排」；Agent 是「LLM 动态自主决定流程和工具使用」。六层结构中环节 1/2/3/6 都是预定义 workflow（什么时候改写、切环境、造数据、生成报告，路径写死）；真正给 Agent 自主决策的空间只在环节 4（执行循环里下一步动什么、点哪里）和环节 5（断言判定的证据充分性）。这条边界是把稳定性做上来的核心工程决策——agentic 能力用在需要「根据环境反馈动态决定」的地方，其他一律走 workflow。

## 三、六层能力体系总览

判断哪一层是当前瓶颈的直接方法：拿一条业务同学口中「跑不通」的用例，从 C1 往 C6 挨个问「这一层做对了吗」，第一个答「没做对」的那层就是瓶颈。5 月推广时，所有场域的瓶颈都停在 C2/C3，不是 C4/C5——**Agent 自规划执行的建设重点不是 Agent 本身，是它周围那些函数化能力**。

### 3.1 C1 用例生成：从「生成即用」到「生成即可执行」

测新场景下「AI 生成用例」和「AI 生成可执行用例」是两件事：前者只输出中文步骤描述，后者要求每一步都能直接被下游 Agent 消费。改写层三件事：

- **改写引擎**：把 AI 生成的自由格式指令统一改写为 `- action / - assert` 结构化步骤。基础模板来自语雀手写模板，Prompt 嵌入 few-shot 覆盖点击/输入/滚动/断言四大类
- **多信源降级**：需求 Spec 首选，其次前后端 Diff、pageUrl、历史用例语义。五级降级：Spec 完整 → Spec + Diff → Diff + pageUrl → pageUrl + 场域知识库 → 通用兜底
- **语雀知识库优先 + 本地兜底**：每小时刷新业务域知识（如「心智条 = 搜索结果页底部红色横条，显示可领金额」语义），走 aone knowledge base 开放接口，改写时给 AI 塞正确业务语义而非靠字面猜

当前状态：SmartUI 侧测新不走改写，直接用用例文本+首屏截图让规划 Agent 自主规划（保证端侧语义保真）；PC 端 Midscene 走另一条改写路径。

### 3.2 C2 前置构造：卡住 75% 用例的地方（最深的坑）

6 月中拆解：SmartUI 目前能覆盖的执行能力只占约 25%（页面访问 + 点击/滑动 + 抓包四件事）。剩下 75% 卡在：

- **配置变更**（GCP、GOP、Switch、Diamond 各一套后台）
- **多维环境编排**（美东预发、美西预发、灰度、多国家、多语言、暗黑/RTL）
- **账号体系**（不同角色、不同权限、不同实验分组）
- **业务流程背景化**（「已下单未支付」态、「购物车 3 商品」态、「Coupon 已领取」态）
- **用例语义保真**（AI 把「检查限时秒杀标签颜色」改写成「检查限时秒杀标签存在」）

以广告场域为例：ODPS 离线数据 T+1 才生效，测试当天生成的用例若依赖新造实验数据，Agent 跑 100 次挂 100 次——不是 Agent 的问题，是数据源没就绪。当前建设方向：配置类优先接入搭建平台/Diamond（UI 执行直接对接后台接口 → 或通过测试数据智造平台对接）；数据类与业务测试同学沉淀各场域数据构造 skill（业务域单独定制能力可达 80% 成功率，通用能力只有 20%，必须允许业务域自定义）；前置流程类用 Provider 函数封装（`login → add_to_cart → checkout_to_pending`，避免 Agent 花 15 步 UI 操作点出状态）；后端痛点侧把 Diamond/Switch/GOP 常用配置暴露为 `set_diamond(module_id, config)` 函数，允许执行前/中/后插入——SmartUI 从「只读型执行器」升级为「可编排型执行器」。

### 3.3 C3 环境编排：Provider 服务和它背后的函数库

解决 C2 决定「环境应该是什么」之后「怎么切到这个环境」。APP 端真机跑一个 Provider 服务（9003 端口），暴露给 Agent 语义化函数：页面直达（`ae://goto?url=xxx` Deep Link 协议跳转 H5/Native，参数透传）、账号登录（Provider login 命令免 UI 快速登录，或 UI 模拟输入）、国家/语言/币种切换（`change_locale` 命令）、环境设置（`change_env` 切换 online/pre/daily 及 dpath 项目环境）、RTL（切 SA/ar 触发）、暗黑模式（`adb shell setprop xxx dark_mode true/false` + 重启 APP）、文本输入（兼容系统输入法与 setText）、截图与录屏（screencap/screenrecord，供 AI 视觉理解/断言校验/回溯）、弹窗处理（系统权限/Google Passkey/广告弹窗）、mtop 录制（记录 ui 操作对应 mtop 请求与 trace）。

**Prompt 硬约束：前置能用函数完成的，禁止走 UI 点点点。** 量化对比：函数化之前 Agent 完成一次环境切换平均 5-8 步 UI 操作、耗时 40-90 秒；函数化之后 1 次函数调用、耗时 3-5 秒——前置阶段耗时降低约 60%，稳定性从「偶尔卡在国家选择器 dialog」变成 100% 成功。PC 端 Midscene 同样有账号免登（15+ 平台）+ Cookie/dpath 注入函数库。

### 3.4 C4 自规划执行：APP 端三段式

C1-C3 建好的能力都是 Agent 手上的工具，这一层解决「Agent 怎么组织这些工具跑完一条用例」。测新核心复杂度在端侧（真机、多设备、系统级操作），主要展开 APP 端 SmartUI 三段式（PC 端 Midscene 是同一套思路的另一种实现：预处理→调度执行→分析回流）。

**SmartUI「自主规划-执行-断言」架构**：

- **全程自主规划**：将用例信息及当前截图页面信息输入规划 agent 做用例执行全程编排；根据用例及现有知识库、场景能力产出执行过程 todolist；环境切换、账号分配、配置变更、前置流程等编排动作函数化执行；页面维度操作采用执行机 adb 操作能力
- **执行循环步骤**：将当前页面截图输入规划执行 agent → 解析屏幕截图、识别页面内容，结合用例自然语言指令与知识库召回信息规划下一步操作（点击/输入/滚动）→ 解析 agent 返回指令下发到执行机 → 操作完成后再截图返回给规划 agent，生成下一步操作，循环执行
- **执行结果汇总断言**：所有操作步骤执行完成后，调用断言 agent 进行各步骤预期结果确认

**8 类原子操作 + aiAction 循环**：端侧最底层收敛到 8 类原子操作——aiTap / aiRightClick / aiDoubleClick / aiHover / aiInput / aiKeyboardPress / aiScroll / aiPinch；上面套 aiAction 高级循环 Observation → Thought → Action → Replanning。上层业务多变，但底层能被 Agent 稳定调用的操作原语必须收敛。

### 3.5 C5 断言与归因：「AI 假通过」的专门治理

Agent 跑完用例给结论最容易，难的是敢不敢相信结论。6 月复核：拿一份 AI 报告通过率 56% 的执行结果，逐条对着断言意图重新审——52 条 pass 里有 34 条站不住（断言目标从没在页面出现过；环境异常跳桌面/白屏 Agent 仍写「符合预期」；没滑到楼层就下结论「该楼层未出现所以不通过」）。真正跑到位、判对了的只有 18 条。**AI 报告 56%，真实有效率 19.5%，三倍虚高。**

这不是模型不够聪明——是 AI 在断言这一步有系统性偏差：默认朝「通过」倾斜，因为「通过」是不需要额外说明的结论。常规错误归因（timeout / browser-crash / assertion-failed / element-not-found / login-fail / empty-target / popup-fail / nav-fail 等）覆盖「AI 承认自己失败」的场景；覆盖不了「AI 说自己成功但其实是假的」。SmartUI 侧建了 **v2 严口径 9 条**专门抓 AI 假通过：

| # | 规则 | 触发条件 | 处置 |
|---|------|---------|------|
| 1 | 前置态未构造 | 关键前置态首屏不可见 | blocked，禁滑 10 屏找 |
| 2 | 单帧终态推时序 | 只凭最后一帧判动态过程 | invalid |
| 3 | 「没看到就是通过」 | 断言目标未在任何帧出现 | invalid |
| 4 | 环境异常页当降级 | SPMC LOSS / 白屏 / 404 / 桌面 / 骨架屏 | blocked |
| 5 | UI 判后端 payload | 断言依赖 mtop/ODPS/后端参数 | blocked（迁接口测试） |
| 6 | Agent 未完成关键动作 | 只到入口页就 finish | invalid |
| 7 | 平台不支持 | 当前 build 不支持（如暗黑模式） | unsupported |
| 8 | 断言意图错位 | 断言写 A 实际验证 B | invalid |
| 9 | 配置对照缺失 | 需 before/after 对照场景无对照 | blocked |

配套 **BLOCKED 快速路径**：命中 Rule 1/4/5/7/9 立刻 finish 并标 blocked，不再硬滑找目标——再滑也找不到，只会烧 token 和时间。BLOCKED 的意义：把「AI 失败」和「环境/基线本身不合理」分开——前者是该优化的，后者需要业务方改数据集/迁出基线；混在一起就无法向业务方解释「为什么这一批用例注定过不了」。

### 3.6 C6 报告 & 知识回流：让每一次执行都变成下一次的燃料

单次执行报告包括：mtop 接口抓包、录屏、每步截图、客户端日志、Trace、错误用例节点、接口/数据 Case 通过率、埋点校验。30 条用例约 5 分钟完成一次执行。报告只是一半，另一半是知识回流——每次执行的成功/失败样本必须变成下一次改写/规划/断言的输入。

自更新知识库三层知识分别在改写 / 规划 / 断言三环节注入：改写时用 business_concept 保证业务语义不丢；规划时用 page_knowledge 快速决定动作空间；断言时用 page_visit_record 里的历史证据做对照。C6 不是终点——它闭环回 C1，整个架构是一个循环：执行的每一条用例都在改写这个体系本身。

## 四、如何度量能力：能力探针基线，而不是通过率

摒弃「跑一次全量看通过率」的度量方式——基线不锁版、方差不控制，通过率是大杂烩指标，无法归因到某一层改动。替代方案是**能力探针基线数据集**：v1.0 锁版 XX 条 Android 用例，按能力分 5 桶（B1 基础 UI 25% / B2 配置变更&异常数据 50% / B3 多端多环境 10% / B4 账号&权限&实验 5% / B5 数据&接口 10%）。每条 case 是一根探针——扎在某项具体能力上，能力没建好必然失败，建好必然通过。

配套三条硬门槛：**稳定性方差**（同基线连跑 3 次成功率方差必须 < 3%，否则踢出）；**分桶 delta 表**（每次能力升级前后必跑全量，按桶输出 delta 表作为上线卡口——涨在哪个桶、代价在哪个桶一目了然）；**v2 严口径复核**（AI passRate 之外必须复核 v2 有效率，两者差距就是「作弊空间」）。度量原则一句话：不追通过率，追「通过率与有效率的一致性」。

## 五、测新实践效果

### 5.1 实战：AE 首页卖场改版

传统流程是业务同学在预发环境挨个国家/语言/设备手动点检，这次全程走 Agent 自规划执行。六层能力串起来跑：C1 从需求 Spec + 卖场模块 Diff 生成端到端 UI 用例（模块渲染/价格样式/RTL/暗黑）；C2 切美东预发 + 目标场域 pageUrl + 卖场专项配置生效；C3 并行覆盖 US/en（默认态）、SA/ar（RTL 态）；C4 端侧三段式自主推进逐用例产出证据帧；C5 v2 严口径全程复核（「划线价 vs 原价」样式细节断言意图对齐）；C6 截图/录屏/mtop/Trace 全量沉淀。

结果：已支持能力（前置构造及测试数据）用例执行有效率 **85.7%**，判定有效的失败用例中发现 **2 个真实缺陷**：

1. **首页卖场专项一排三模块划线价与原价一致**（默认态卖场模块渲染）——靠 C5 严口径 Rule 8（断言意图错位）生效：老 prompt 只检查「划线价元素是否存在」会直接 pass；严口径把断言意图对齐到「划线价 ≠ 原价」语义关系后，才把视觉上不起眼但业务上严重的样式 bug 挤出来
2. **首页卖场专项 RTL 下模块箭头方向错误**（SA/ar RTL 布局）——靠 C2 前置构造 + C3 环境编排已支持 SA/ar 切换到位；切不到 RTL 环境 Agent 根本触发不到这个 bug；C4 端侧真机真实渲染 RTL 布局 + C6 对比截图让业务方一眼看出箭头方向反了

可复用观察：缺陷密度与用例覆盖的多维度组合强相关（US/en × SA/ar × 一排三 × 划线价 × 箭头方向），单一维度覆盖挖不到这类 bug；样式细节类缺陷（价格样式、方向、颜色）恰是老 UI 自动化最容易假通过的一档，v2 严口径专门治理这一档很关键。当前该测试计划仍有很多无效用例执行，根因是前置配置能力建设不足，是后续建设重点。

### 5.2 当前状态 vs 后续计划

按六层盘点：C1 已建 Spec/Diff/PageUrl 五级降级 + 语雀高标准模板 + 本地兜底每小时刷新 + 15+ 场域改写，缺口改写率未达目标（Prompt 迭代 + 场域知识库扩充）；C2 已建环境切换/账号登录/dpath 注入函数化，缺口搭建平台/配置平台未接入、数据构造未对接（优先接配置平台 + 对接业务域数据构造 skill）；C3 已建端侧 Provider 12 项能力 + 15+ 平台账号免登 + PC 端 Cookie/dpath，缺口多国家切换偶发真机网络波动（Provider 重试 + iOS 端接入手机中台）；C4 已建端侧三段式 + 8 类原子操作 + 子 todo 自闭环，缺口长上下文规划 Agent 早停、单条耗时 P90 89.6s（父子 Agent + 断言 Agent 拆分 + 深度思考按需开启）；C5 已建常规 8 类错误归因 + v2 严口径 9 条 + BLOCKED 快速路径，缺口多帧证据强制未全量落地、断言 prompt 三段式未沉淀（多帧证据强制 + 断言 prompt 意图/证据/判定三段式）；C6 已建 mtop/录屏/截图/日志/Trace 完整 + analyze-logs requestId 查询 + page_knowledge 首批入库，缺口 business_concept 覆盖 <20%、负反馈回流未成闭环（三层知识库全量入库 + 负反馈周更新）。

## 六、经验输出：可迁移的原则与反模式

### 6.1 踩坑与反模式

1. **把所有能力都交给 AI 自主规划**：一开始想追求「用例文本→执行结束全自动」，环境切换/账号登录都让 AI 自己点，跑下来 5-8 步稳定卡点、耗时长、失败率高。能用函数就别让 AI 点——Agent 的自主性用在真正需要理解语义的地方
2. **只做用例生成不做前置构造**：AI 用例生成 skill 铺开很容易，但 C2 前置构造没建，业务同学装完 skill 第二天就会发现「生成挺快，但跑不动」。用例生成 skill 铺开进度应被 C2/C3 能力建设速度约束，不然只是把不可执行的用例批量化生产
3. **把通过率当作首要指标**：通过率单调上升可能意味着「AI 学会了作弊」。通过率下降不一定是坏事——如果 v2 严口径把之前虚高挤出来，通过率应该下降。要追通过率与有效率的一致性，不是通过率本身
4. **把不该 UI 层验证的用例硬塞进 UI 基线**：B5 数据接口类用例（后端 payload、MDS Key、ODPS 底表）在 UI 层验证 100% 命中「UI 判后端 payload」或「不可 UI 验证」。分层测试的边界要严格——UI 层验 UI，接口层验接口，数据层验数据

### 6.2 结论：三条可迁移原则

- **原则一**：Agent 只优化用例生成及执行，则测新自动化整体价值上限就是 20%。剩下 80 个百分点的空间在前置构造、环境编排、断言与归因、报告与知识回流四层的工程化上。做 UI Agent 的团队应把精力从「让 AI 更聪明」转向「让 AI 周围的函数化能力更完整」
- **原则二**：Agent 的自主性应该用在真正需要语义理解的地方。识别页面状态、决定下一步动作、判断断言证据——这些让 AI 做；环境切换、账号登录、dpath 注入、配置变更——这些必须函数化。前置能标准化的一律标准化，能用函数就别让 Agent 点
- **原则三**：AI 假通过是系统性偏差，需要专门的归因规则去挤。常规错误归因只覆盖「AI 承认自己失败」，覆盖不了「AI 说自己成功但其实是假的」。v2 严口径 9 条 + BLOCKED 快速路径的价值不是发现更多失败，而是把 AI 会本能掩盖的那部分暴露出来。任何做 UI/浏览器 Agent 的团队都建议自建一份「AI 假通过模式」清单

三者本质是同一件事：把 Agent 该做的和不该做的边界画清楚，然后在 Agent 该做的部分给它最好的工具与最严格的复核。
