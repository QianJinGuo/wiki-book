# Harness Engineering：快手电商用 AI 流水线重塑研发范式

> 快手技术（快手电商商家和运营赋能中心技术团队）。讲清"AI 提效冰火两重天"的结构性根因（工具使用 vs 流程重构），并给出快手电商 B&M 端系统（6+ 角色、20+ 业务域、小几百服务）用 AI 流水线做需求全生命周期自动化交付的完整实践：对抗式设计、领域知识库、组织演进、两个坑、避雷清单。

## 一、场景与问题（冰火两重天的数据证据）

**核心洞察**：个人生产力可扩张 10 倍，但企业规模化提效隐晦不明——因为大多数团队停留在**工具使用**而非**流程重构**。工具替换只产生局部加速。

**数据说话（2026年1~4月）**：人均周 token 消耗大几千万、人均代码量 +170%，但**平均需求交付时长几乎没缩短**。结论：单纯 coding 环节提效极其有限，必须让 AI 贯穿**需求全生命周期**。

**三个结构性难题**：
- **需求侧理解分析成本高**：电商 B&M 需求复杂，需求预评审/需求评审/技术方案评审/TC 评审多轮，易少做漏做，评审消耗大量时间。
- **交付侧协同成本高**：一个需求涉及招商入驻/店铺管理/交易履约/资金/客服/结算清退；产品/前端/后端/测试多角色。前端 3PD + 后端 3PD + 测试 2PD ≠ 5PD，而是约 10PD——人际沟通复杂度几何级数增长，耗时大头是协同和相互等待。
- **新同学学习曲线陡**：B&M 系统 5 年+ 迭代积累大量领域知识且业务规则常变，新同学缺系统上下文、知识传递成本高。

## 二、目标与设计原则

**目标**：构建需求交付自动化流水线，让需求交付 7x24 自动运行。量化目标：**吞吐率 +30%、平均交付时长 -40%**。交付模式从"前后端/测试分工"转"业务全栈开发"；L3 占比 5%→15%+；单元测试 100% AI 生成、AI 分析错误日志、自动联调；测试用例 AI 生成调试后准确率 100%、AI 自动执行率 80%+、测试交付效率 +45%；发布阶段自动部署 + AI 按 PRD 验收。

**核心原则（4 条）**：
1. **全生命周期**：沿需求全生命周期（知识建设→需求生产→研发执行→测试上线）构建端到端 AI 提效体系，不是单点工具。
2. **工程化工作流**：把 AI 放进可控制/可审计/可复用的工程工作流，大多数需求澄清清楚就能执行自动化研发流水线（Harness Engineering）。
3. **云 + 端协同（Agent Swarm）**：云是"指挥官"（结构化需求、分发任务、编排、协同多 agent）；端是"执行器"（具体实现）。
4. **链路打通**：需求侧"对话式 PRD 生成 + 结构化需求生成"自动化 + 打通前端/后端/测试全链路 + 构建领域知识库（PRD/技术方案/TC 生成时更精准）。

## 三、对抗式设计：open-door 和 close-door

流水线各节点是"房间"。两个 skill 串联全部节点：
- **pandoraFlow-delivery**：尽可能 open-door，让需求到达下一个房间。
- **pandoraFlow-review**：尽可能 close-door，上一个阶段产出物完全验收通过才能进入当前节点。

中间产物用**文件系统 + git** 存储和做状态持续化管理。AI code 链路核心判断：**验证比生产更重要**，且不只对功能完成做验证，而是**对每一步中间产物做验证**。全生命周期每阶段都遵循 **plan → execute → verify**：阶段产出立即验收，不通过返回修改。推拉式设计让需求交付自动化跑起来。

## 四、全链路拆解（5 阶段）

### 3.1 需求侧：产运研协同升级
- 之前：人工梳理跨域交互逻辑和边界条件、PRD 依赖个人经验、MRD/PRD/视觉多轮评审。
- 现在：**需求自动生产工作台**，在领域知识库（历史 PRD/行业材料/业务规则/领域概念）支撑下，产品经 agent 对话澄清 → 自动生成 PRD + 结构化需求（EARS/BDD）→ 一键流转研发。"多轮评审+人工对齐"→"知识库驱动生成+原型确认+一键流转"。

### 3.2 Spec 阶段：需求交付模式升级
- 现在：基于领域知识（领域负责人一次性初始化，从存量代码挖掘系统 API/数据结构/业务调用链 + 从历史 PRD/技术方案抽取业务规则/功能边界/架构决策），AI 自动完成上下游接口解析，结合代码调用图谱精准定位变动点，推导接口依赖关系和影响范围，一键生成 **proposal.md + design.md + tasks.md 结构化需求三件套**。Spec 阶段变"知识库驱动、自动生成、review 门控流转"。

### 3.3 Dev 阶段：开发阶段
- tasks.md 编码任务已含 Spec 自动推导的变动点和影响范围；领域知识库提供上下文约束（API/数据结构/调用链/架构决策）——自动识别业务规则边界、判断新增/调整、识别配置冲突或漏改风险。**测试驱动开发**，每个功能都有验证，新同学依托知识库快速进入状态，"改得准改得稳"。

### 3.4 Test 阶段
- 现在："人工写用例→手动备数据→等待修复→再轮回归"→"skill 生成→执行→问题自动闭环"。基于 BDD/EARS + 变动影响范围自动生成测试用例（主流程/异常路径/边界）；测试数据结合领域知识库自动构造（理解跨域数据依赖）；多端精准回归、高覆盖边界用例、AI 全路径遍历探索和跳转链路验证。bug 自动记录定位，回传测试报告直接驱动修复，循环至无 bug。

### 3.5 Oncall 阶段：日常线上运营
- 现在：oncall 排查由 skill 统一接入日志源，运行时日志和链路上下文自动注入大模型，**运行态完成多服务日志关联分析和根因定位**。定位根因后 agent 结合代码调用图谱和领域知识库自动圈定最小影响范围，形成有链条证据支撑的修复方案（问题日志→根因分析→影响范围→最小改动建议）。修复完自动部署测试环境并回捞日志验证。"告警→定位→最小范围修复→验证"一个上下文闭环。

## 五、组织演进（《人月神话》命题的 AI 改写）

从《人月神话》两个经典难题切入：
- **加人悖论**：10 人一年 vs 20 人半年——做不到，因人际沟通几何级数增长 + 新成员缺上下文。**AI 改写**：加 AI Agent 不同于加人——Agent 可无损拿到上下文、规模化从存量代码解析上下文，不需要人与人之间几何级数的沟通消耗，底层逻辑不同了。
- **左移悖论**：左移想法对但投入大 ROI 低——本质是跨部门转移责任，左边的人接不接/认不认/有没有能力承担要付出巨大软件工程能量+组织摩擦力。**AI 改写**：AI 可从存量代码抽取上下文/知识资产 + 增量 PRD/Spec，业务复杂系统简化成大家可理解上下文框架，跨岗位低成本对齐。

**组织转型：职能分工型 → 超级个体型**，五维变化：
1. **研发模式**：之前运营/产品/研发/测试多角色 + MRD/PRD/技术方案/TC/code review 多轮评审 + 前后端联调上下游联调。现在**两种角色**完成全生命周期：产品经理 + 交付负责人（全栈）。两人开会和 AI 对话形成结构化需求；交付负责人会后和 AI 对话生成技术方案/TC/plan 并 review；AI 自动写代码/联调/测试；产品经理验收。
2. **领域负责人职责**：之前整理架构文档、通过技术方案评审和 code review 约束工程代码。现在**领域初始化**——从存量代码/PRD 抽取上下文和知识资产、挖掘 API/数据结构/业务流程、按规约模板引导 AI 生成结构化 Spec 知识库、配置研发工作量/约束/校验条件。
3. **需求左移**：交付负责人专注用户流程/产品价值/客户体验，通过 Zeta PM 工作台快速生成原型"所见即所得"确认，把上线后的验收前置到需求最左侧。
4. **质量左移**：AI 让覆盖度梳理变轻、测试编写变快，测试左移从"正确但昂贵"变可执行工程实践。测试重心在用例生成/数据准备/执行，前置到研发阶段并打通 AI 问题定位和自动修复。
5. **职责合并**：产品经理/交互设计师/DA 三合一（业务沟通到 Demo 确认）；前端/后端/测试三合一（前端开发/数据结构/状态机/API/高可用高可靠，业务模型到系统稳定性）。

## 六、两个坑

**坑一：不要花大成本构建平台，而是建立标准和流程**。平台化问题：改变开发者习惯难、业界方案/工具/skill 迭代快（深度定制比不过业界迭代）；开发者对重复造轮子有执念 + 横向团队要有平台作为立身之本。解法：**不建平台建标准**，极简工具监控，工具和 skill 保留开放能力。两件事：①引入流水线不同节点正向推进+反向验收流程，强行用两个 skill（delivery/review）串联所有节点，中间工具（openSpace/superPower 全家桶）由领域负责人初始化时自选定义；②强行收集所有研发流程数据（需求/技术方案/前后端/联调/测试/等待/提测各阶段耗时和自动化能力），用管理手段力求每阶段高自动化。

**坑二：Harness 好搭，但领域实践困难**。引入业界 skill 直接用或魔改不难，但驱动工具和流程的还是人，协作成本摩擦不会消失。经验：①建立领域自动化需求交付观察体系，**用交付链路人工介入次数判断领域自动化能力**，列入考核模板；②让真正懂业务的领域负责人进去看细节、review 知识库和 SOP、搭建自定义 workflow。

## 七、避雷清单

- 不要花极大成本构建平台，构建标准并借力开源界解决平台工具问题。
- **领域知识沉淀极其重要**：研发提效三大核心要素"**基模 + harness + 领域知识**"——基模属全球 Top3 玩家、harness 属开源界、**只有领域知识属于自己**。把历史代码+PRD+技术方案构建成以流程/规则/实体为核心的领域知识层，用知识图谱承载。
- 指标上最核心要求 **AI 自动化率**（AI 能接手人的工作、人需介入几次）——所有复杂动作应在 AI 在需求交付开始之前完成，让 AI 写代码/单测/测试/发布达到极高自动化比例，为达目标一定管理手段必须。

## 八、双轮驱动总结

**工具提效 + 组织结构**两个维度一起看，指数级效率提升往往来自第一步技术革命 → 倒逼组织结构调整。

- **交付模式（工具提效）**：①需求提效——关注整体需求研发交付全生命周期自动化，局部工具替换只有局部加速；②验证大于生产——拜托生成代码的兴奋幻觉，站在领域负责人角度分解问题和验证阶段性产物，用对抗式 AI Agent（一个往前跑、一个往后推）设计让自动化真正跑起来。
- **组织（组织结构）**：①纵向——需求左移、测试左移，从流程分工式交付变全栈超级个体式交付；培养领域负责人从"技术专家"→"领域专家"（关注用户流程/产品价值/客户体验）。②横向——减少横向职能部门（算法/中台/效能/测试/前端），重组为业务单元（资金/分销/运营平台），推行阿米巴经营，AI 时代更易实现。
