# 从基础问答到事实核查：高德内容数字员工实践

> 原始来源：https://mp.weixin.qq.com/s/tKj-leN4fYdgaWBRMWUnGg
> 作者：高德信息业务中心（高德技术账号，2026-08）

## 全文速读

高德信息业务中心的「内容数字员工」工程化探索：把端到端能力从「需求到代码」延伸至研发全生命周期，让 AI 先完成重复但必要的信息收集与证据整理。核心命题：**从「会回答」到「会查证」，中间隔着的不是一个更大的模型，而是一张真正能工作的工位**。关键洞察：Prompt 适合写原则，但可靠性最终要落在环境里——「不要重复查」需要状态记录、「证据不足不要下结论」需要工具返回明确的失败含义、「大文件不要丢证据」需要可恢复的证据索引。本文覆盖：入职体系、业务地图、LLM Wiki、五层工作台、告警 RCA 五步、证据信封压缩、业务排查三轴、质检与权限分级。声明为试点实践，部分能力已在特定场景跑通，治理与评测机制仍在补齐。

## 一、研发 Agent 的难点：不是再多一个模型

编码 Agent 的起点通常是明确代码工程（仓库/分支/目标文件已知、成功标准清楚）；内容数字员工的起点可能只有一张告警卡片、一个匿名业务标识或一句「这个用户看到的结果不对」——甚至不知道第一步该查哪个系统。上下文不是文件目录，而是监控/日志/代码/变更/服务依赖/业务规则构成的动态证据。成功标准变化：不是「答案听起来合理」，而是证据是否完整、候选根因是否可信、反证是否被看见、建议是否可执行。

第一判断：Prompt 适合写原则，可靠性最终落在环境里。「不要重复查」不能只靠提醒，需要状态记录；「证据不足不要下结论」需要工具返回明确失败含义；「大文件不要丢证据」需要可恢复的证据索引。

## 二、数字员工「入职」：约束开放能力为工作单元

入职不是拟人化或开通账号，而是把开放能力约束成职责清楚、过程可查、结果可评的工作单元，至少四样东西：

- **岗位边界**：受理哪些任务、交付物包含什么、证据不足时何时停止、哪些动作必须交给人决定
- **地图与知识**：业务地图提供组织架构与第一跳，LLM Wiki 和 Skills 补充业务语义与处理方法，最终结论仍需回到代码、配置和运行证据核验
- **工位与权限**：必要查询入口、工作记录和上下文；默认只读、最小授权；写入知识/修改配置/发布内容保留人工确认
- **带教与评测**：从历史案例、旁路验证和只读任务开始，用失败案例校正路由、反证意识和停止条件，再逐步扩大通过验证的任务范围

「转正」≠全场景自治，而是在某一类边界清楚、结果可复核的任务上通过验证。最先需要补的通常不是更多工具，而是一张能说明职责与关系的业务地图。

## 三、业务地图：Agent 的「组织架构认知」

让 AI 接上代码/日志/监控/变更只解决「能查什么」，没解决「应该先去哪查」。业务地图是数字员工的组织架构认知——不是静态项目清单，而是「可导航的地图」：不要求一次记录所有节点，要保证 Agent 能从用户语言出发找到可信第一跳，并知道接下来还有哪些方向值得验证。

最小可用地图五类信息：

1. **业务域**：这句话描述的是内容生产、审核、分发、消费还是运营干预
2. **能力与责任边界**：某服务负责接入/编排/存储/消费，哪些明确不由它负责
3. **入口索引**：常见页面、接口、事件、任务或模块从哪里进入
4. **关系边**：调用、依赖、数据流、事件流，新旧链路之间的替代或并存关系
5. **证据入口**：对应问题通常去哪里找代码、日志、指标、配置与原始文档

最重要的不是节点数量，而是**边界和关系**（「内容服务」可能只做展示整形；两个名字不同的系统可能是同一业务新旧代际）。地图节点不应该是没有出处的结论——为关键关系保留来源、更新时间、置信状态和待确认项；两个来源不一致时先并列保留，不让模型替人裁决。

地图质量落到具体问题：第一次路由能否进入正确业务域、找到第一份有效证据需要多少次尝试、全局盲搜是否减少、过期关系能否被发现。

### 踩坑：Agent 不知道怎样「问地图」

模型从「评价」开始，未命中后不断补限定（「评价发布」「评价发布逻辑」），最后变成带现象和判断的整句——参数每次变化导致缓存和重复调用拦截失效，检索范围越来越窄，模型围绕未经验证的假设打转。解法不是更复杂的检索策略，而是把工具说明改成**操作协议**：第一次只取 2~4 个核心业务词不写推断；一次无结果先换同义词或上位业务词；连续两次无结果停止细化，离开地图检索转查原始资料和代码。**给探索加上明确的换路条件——知道何时停止也是一种能力。**

地图粒度取舍：只做服务级找不到入口，细到方法级节点膨胀且代码一改就大面积过期。现阶段落点是**服务+接口级**：地图记录职责边界、稳定入口和跨系统关系，具体方法与字段留给 Agent 去当前代码核验。地图负责把第一跳送对，不替现场证据下结论。

### 地图 + Skills + LLM Wiki 分工

- 业务地图提供显式导航（开放问题先给业务域/入口/下一跳，长尾回到原始资料与语义搜索）
- Skills 编排高频场景（稳定排查顺序/停止条件/判断边界沉淀为操作手册）；**Skills 不应抄录类名/字段名/配置开关**（代码实现变化快，易过期细节写成前提会诱导模型跳过验证），应保存「这个问题通常经过哪些业务关卡、从哪里开始」
- 地图逐步生长：服务目录/路由元数据/依赖/代码目录提供骨架，LLM 提聚类建议人确认边界；Agent 真实排查留下的有效路径反向暴露缺失入口和过期关系；更新先成建议经确认再进地图，避免一次错误排查自动污染后续任务

## 四、LLM Wiki：企业知识场景的四阶段建设

业务地图解决「去哪找」但表达能力有限（难以解释新旧链路并存原因、业务状态 vs 运营状态 vs 展示状态、规则关卡顺序）。借用 LLM Wiki 思路：在原始资料与使用者之间持续维护一层结构化、相互链接的知识页面。原始资料是事实来源，LLM 负责整理/交叉引用/更新，人负责提供来源/阅读/提问/校正。

企业场景四层分工：业务地图负责导航（去哪找）；LLM Wiki 负责综合（怎样理解）；代码 Wiki 负责实现导航（去哪看代码）；原始资料与实时证据兜底核验（此刻的事实是什么）。**一句话：业务地图是导航，LLM Wiki 是讲解员，代码 Wiki 是实现目录，原始证据才是现场。**

不一步做 LLM Wiki 的原因（半年后仍可信的四个难点）：

1. **知识筛选**：会议纪要/操作记录/一次性排查日志全进 Wiki 会淹没高价值知识；只沉淀跨来源可综合、相对稳定、被反复查询的主题
2. **冲突与时效**：文档描述目标架构、代码反映当前实现、故障复盘记录历史时间点——不能强行揉成唯一答案，应标出来源/更新时间/置信状态/内容分歧/开放问题
3. **颗粒度**：页面太碎 Agent 遍历大量链接，太大变成长文难定位；合并/拆分/降级需持续治理
4. **写回边界**：一次问答发现新关系不直接改写组织知识；Agent 提出变更建议（新增关联/修正旧结论/补充主题），展示来源和差异，人确认后写入并留更新记录

四阶段建设顺序：①先把地图做对（核心业务域/责任边界/入口/下一跳）→ ②少量种子主题（高频/跨系统/单篇文档讲不清）→ ③接入三路查询（概念看 LLM Wiki，长尾事实搜原始资料，实现用代码 Wiki 定位再回代码/配置/运行证据核验）→ ④维护闭环（真实查询的纠错/缺口/冲突变成待审核知识更新）。**即使 LLM Wiki 尚未成熟，业务地图已经能改善第一跳；每一次有证据的排查又为 Wiki 提供更可靠种子——不是等知识工程全部完成才让 Agent 工作。**

## 五、五层工作台：一句话进来，一条证据链出去

不按场景写固定流水线，收敛成统一 Agent 工作台五层：

1. **入口与受理门禁**：告警事件/群消息/接口请求整理成统一输入；区分用户明确给出的事实和模型推断；检查主体/目标对象/现象/时间范围等必要信息；缺信息能自查就先查证，确实无法补齐再向人澄清
2. **路由与计划**：不靠关键词匹配，让模型显式选择任务类型（错误告警/超时/系统水位/业务排查/影响面评估），再加载对应原则/Skills/工具范围
3. **Agent 执行循环**：证据调度器——每轮判断缺什么证据，选择工具、读观察结果、更新候选假设，直到证据收敛或明确进入「证据不足」终止状态
4. **知识与证据上下文**：业务地图/LLM Wiki/代码 Wiki/Skills/原始检索/工具网关/执行状态/证据索引共同构成；状态层记录查过什么/怀疑过什么/排除了什么/每项判断来自哪层证据，但不把所有原文反复塞进上下文
5. **质量与权限边界**：默认优先只读；写入/发布/删除等不可逆动作设人工确认点；关键路由/工具调用/结论保留可回放轨迹供评测

业务请求分工示例（「这条内容为什么没有展示」）：受理门禁分离事实与推断 → 路由层借业务地图判断生产/审核/消费环节 → LLM Wiki 提供业务关卡与新旧链路关系 → 代码 Wiki 定位实现入口 → 涉及当前状态与用户结果时回当前代码/配置/日志/指标逐项核验。**业务地图和 LLM Wiki 不是塞给模型的「标准答案」，是调查的导航与背景材料——最终结论必须由实时工具和原始证据支撑。**

## 六、告警 RCA 五步（最早验证的场景）

1. **先锚定告警本身**：提取应用/时间/指标/规则结构化信息，判断错误量/超时/系统水位/业务计数；路由错了后面查得越深离真实问题越远
2. **回到规则与配置**：告警标题是给人看的摘要，统计口径由规则与监控配置决定——确认阈值/触发条件/统计方式/维度，避免根据中文标题猜指标
3. **看趋势也看分布**：瞬时尖刺 vs 持续异常、单机 vs 全局、入口流量 vs 错误率变化、集中在某接口/机器/错误类型；监控工具先整理成整体统计/分组摘要/峰值分布/关键时间线——**工具把重复数据处理做掉，模型把注意力留给判断**
4. **日志与代码互相验证**：错误类告警看错误分布/堆栈/业务帧；代码解释触发条件和下游依赖，日志确认真实路径与时间；日志显示异常来自下游 + 代码确认调用关系 → 继续追下游证据，不把当前应用直接判成根因
5. **把变更放回时间线**：发现发布/配置变更 ≠ 根因已找到；判断变更是否早于指标变化、代码路径是否与异常堆栈一致、回滚/灰度后指标是否恢复；时间和路径同时对齐后变更才有资格进候选根因，还需排除替代解释并验证

防「越查越像」的五类闸：短暂异常快速恢复先保留为低优先级观察项；单机异常先查机器事件不直接业务归因；当前应用只是下游受害者时继续沿依赖追查；指标不可用或口径不明明确输出证据不足；发现变更必须同时给出时间/路径/反证。

最终输出结构（不是一句「根因是」）：异常类型与范围、关键时间线、候选根因、支持证据、反证与不确定性、处置建议、需要人工确认的决策点。

## 七、证据压缩：不是删除，而是把证据变成索引

早期给所有工具结果设同一道约 8 KiB 截断线，很快暴露问题：同样的 8 KiB 对不同证据意义完全不同——日志还能看到异常现场，代码可能刚读完依赖和字段定义、核心方法已被切掉。统一放大上限又会让长代码占满上下文、挤走日志/监控/变更证据。**排查需要的是几类证据同时留在桌面，不是把某一份材料读得最多。**

解法：按证据类型分配预算（代码保住结构和关键实现，日志覆盖异常时间窗，监控看趋势/峰值/分组差异）。预览不做随机抽样（头尾各截一段可能跳过中间核心方法），改成**可导航索引**：代码列类/方法/行号，搜索列命中文件和位置，日志列时间/机器/级别/记录序号——模型先判断哪里值得精读，再按片段取回原文。

跨上下文窗口时同样不保存全部正文，压缩结果只保留可回读资源索引；工作记录只记查过什么/形成过哪些假设/排除了什么/原始证据在哪里（否则工作记录很快变成第二份上下文）。

「证据信封」四件套：**摘要**（低成本说明这份结果大致说明什么）+ **结构预览**（有哪些可继续导航的信息）+ **证据指针**（按片段把原文读回来）+ **回读提示**（明确下一步如何精读，避免重新执行同一次查询）。这是一种面向下一步推理的工具观察结果（observation）设计——模型先看结构决定精读哪里，不在全文与失忆之间二选一。

知识层同理：LLM Wiki 返回不应只有正文，还要附带引用来源/更新时间/适用范围/置信依据/已知冲突/开放问题；只有能回到代码/正式文档/运行证据的部分才有资格进入高置信结论。Agent 输出区分三种状态：已被原始证据验证的事实、由多条信息推导的候选判断、仍未回答的问题。来源冲突不强行合并，证据过期主动降级，地图未命中转入原始层检索。

## 八、业务排查（VOC）：不能直接套用告警 RCA

告警是系统告诉你「我某个时间点异常了」；业务/用户反馈（Voice of Customer）是用户告诉你「我看到的结果不符合预期」——前者找异常源头，后者像一次规则对账。业务排查三轴：

- **事实轴**：主体/目标/时间/行为路径/结果状态分别是什么；哪些是用户明确提供，哪些只是推断
- **规则轴**：触发/过滤/互斥/兜底逻辑分别是什么，代码如何实现
- **差异轴**：把事实代入规则，预期和实际究竟在哪个条件上分叉

每条归因必须落到一个**可证伪的「关卡」**（入口参数/资格/业务配置/下游结果/风控或审核过滤/状态机/端上展示逐级确认），不停在「可能是数据问题」。

业务排查受理门禁：用户给的时间可能是行为发生时间不一定是对象创建时间；自然语言事实可能混有假设；主体/目标/现象/时间范围等结构要素用确定性规则校验而非全交 LLM。**反问不能太早**：缺的标识能从现有信息反查就先自查，确实查不到再说明已尝试来源并向人澄清——解决的不是「能不能问人」，而是「什么时候才有资格问人」。

## 九、质检与主管：评测分层 + 风险分级权限

试点声明：部分能力已在特定场景跑通，治理与评测机制仍在补齐；现阶段先验证能否在边界清楚、结果可复核的任务上稳定工作。

评测不只盯最终文本，优先检查：最终状态是否满足目标、关键证据是否完整、是否发生越权、成本与时延是否可控；再结合轨迹检查安全关键步骤是否执行、工具选择是否有效、是否无效重复调用。不同有效路径不必被强行约束成同一个工具顺序。

地图和 LLM Wiki 单独评测：地图看第一跳是否进入正确业务域、过期关系是否被识别；LLM Wiki 看关键结论能否追溯来源、冲突是否显式保留、长尾问题是否知道回原始层。**知识层和执行层分别可测，最终任务失败时才知道修地图/知识页/工具/决策策略。**评测拆结果和轨迹两层：确定性规则检查硬约束，模型评分辅助开放质量，人工抽检校准；线上真实失败案例沉淀为回归测试。

权限不做「完全自动 vs 每步确认」两个极端，用**风险分级**：低风险可回滚的只读查询自主执行；写入知识库/修改配置/发布内容/通知外部人员进入明确人工确认点。数字员工边界：先完成信息收集/证据整理/候选判断，人保留关键决策与最终责任。

## 建设顺序与未解决问题

业务地图先行，LLM Wiki 从少量高价值主题开始验证；已探索方向：影响面评估、上线风险梳理、线上告警分析、业务问题排查、知识沉淀。未解决问题：业务地图粒度、Skills 老化、复杂根因质量标准、多 Agent 上下文合并、真实案例衡量长期收益。

结语观点：**AI 更像一个放大器**——平台质量高/工作流清晰/反馈速度快才更容易产生稳定收益；基础设施混乱时它会把混乱一并放大。建设内容数字员工也是倒逼研发基础设施变得更可理解、更结构化、更可验证的过程。

三条推进线：①真实案例扩充回归集，把第一跳/证据完整性/失败交回/成本时延做成稳定指标；②从少量高价值主题建设 LLM Wiki，形成「地图—调查—知识更新」维护闭环；③只读任务验证稳定后再谨慎扩大到有明确人工确认点的协作动作。
