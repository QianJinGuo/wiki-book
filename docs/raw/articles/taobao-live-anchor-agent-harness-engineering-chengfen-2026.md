# 淘宝主播Agent的Harness工程实战

> 作者：澄沨，淘天集团-直播技术团队（大淘宝技术）。聚焦为主播和运营提供全链路工具与智能化能力支撑。

## 为什么主播 Agent 需要 Harness

OpenClaw、Claude Code、Hermes 等把 Harness Engineering 带火：模型能力是概率的、会漂移的、偶尔失控的，真正让 Agent 可用、可控、可演化的，是模型外那层工程化「骨架」——结构化上下文、约束性工具协议、生命周期钩子、可恢复状态、可观测评估。

大部分公开 Harness 实践验证场景是「个人助手」形态（单用户、本机、可重跑、延迟成本不敏感）。主播 Agent 是极端压力测试场：

1. **操作即时生效且面向公众**：指令一旦下发错误无法撤回，代价是真金白银
2. **主播注意力极度稀缺**：镜头前要讲解互动看数据，无余力逐条核验 Agent 动作 → 安全边界必须工程兜底而非人工复核
3. **多话题高频交织**：播前准备/中控指令/商品操作交替出现，单轮对话可能同时涉及选品、组货、排序、控场，上下文极易污染漂移
4. **长程、可中断、要恢复**：直播动辄数小时，跨设备跨端切换常态，中断后必须精确续连不能「失忆」

## Harness 六元组定义

把 Harness 形式化：**H = (E, T, C, S, L, V)**

- **E（Execution Loop）**：执行循环
- **T（Tool Registry）**：工具注册
- **C（Context Management）**：上下文管理
- **S（State Storage）**：状态存储
- **L（Lifecycle Hooks）**：生命周期钩子
- **V（Evaluation Interface）**：评估接口

价值：把「Agent 工程」从零散 Prompt 技巧和 if-else 升级为有明确分工的系统架构。任何 Agent 项目都可拿六维度对照看缺哪块。

**水流理论**（ATA 常提）：人负责控制方向、设定边界与检查点，AI 负责在边界内自主推进。工程师建设的是「河道、闸门、护栏」即 Harness。模型再强没有河道会泛滥；河道修好，水流有波动整体可控。

## 分层结构：业务方写 Skill，框架层兜底

- **框架层 vs 业务层责任边界划干净**：把「会变的」和「不变的」彻底拆分。框架层提供执行循环、上下文治理、安全防护、状态持久化、审计观测这些「不变的工程能力」；业务方以 Skill 形式声明「技能能干什么、风险等级多高、参数怎么校验」，其余框架兜底
- **安全是纵深防御非单点**：从 Prompt 边界到执行审计五层
- **长程任务可恢复、可观测、可干预**：三层 Checkpoint 任意时刻中断精确续连；DAG 全局规划替代 ReAct 单步局部决策

## 工程载体：逻辑统一工作区，物理分而治之

业界 Harness Framework 喜欢文件系统 Workspace 作为唯一事实来源（单机个人助手形态优雅），但主播 Agent 要服务海量主播、多副本水平扩容、高并发实时读写，单一文件系统假设不成立。取舍：逻辑视图上仍暴露统一「工作区」抽象，物理落地上按三类资产读写特征选最合适存储后端：

- **记忆存 Hologres**：长期记忆数据模型「向量+全文+标量」三位一体——记忆节点表每条含内容原文（全文检索）、内容向量（语义检索）、JSONB 元数据（记忆类型/目标实体/来源平台设备/信任分/使用采纳次数等标量，支持精确过滤）。Holo 向量索引做混合检索：按语义找相关记忆 + 按主播 ID/场次/平台精确过滤
- **技能存 GitLab**：Skill 本质是带 Schema 约束、能力域声明、校验规则的代码资产，天然适合 Git 维护；新 Skill 上线前走预检平台校验 + Code Review + 灰度发布
- **会话存 MySQL**：一致性点查要求最高，agent_session 表以 user_id + session_id + state_key 索引按需点查加载。state_key 对应一类状态（会话基础信息/场次信息/原始消息/运行时消息/卸载上下文/压缩事件/Plan 规划等）。状态落共享存储而非副本本地内存 → 多副本对等部署、跨节点状态一致、服务不中断

收益：检索密集的记忆走 Holo、版本化技能走 GitLab、强一致会话走 MySQL，不用一套存储硬扛所有负载；框架层封装统一工作区抽象后，业务逻辑只面向「加载上下文、读写记忆、调用技能、持久化状态」语义接口，不感知底层，存储演进不反向冲击业务代码。

## 八项实战一：上下文工程——看得清、记得住、不漂移

直播对话多话题交织高频切换，放任聊天历史增长撞两堵墙：上下文膨胀（Token 耗尽/延迟飙升/成本失控）和注意力漂移（关键信息淹没流水账）。三个手段：

1. **分层压缩而非无脑截断**：Token 超压缩阈值走 3 层压缩（压缩历史工具调用/摘要历史对话轮次/压缩当前轮次消息）；对话超 N 轮触发 Session 级话题分段，多轮对话压缩为结构化摘要并打场景标签（pre-live/on-live/post-live），支持按场景聚合检索
2. **Reducer 模式更新状态，不把工具结果一股脑塞历史**：传统做法每轮工具调用完整 JSON 结果直接追加聊天历史，三个严重问题——状态模糊（LLM 要从 20 轮对话推断「现在讲哪个商品、价格改多少」极易出错）、上下文膨胀（完整 JSON 进历史 Token 快速耗尽）、不可回放（无法精确复现某步状态）。借鉴前端 Reducer 思想职责分离：**LLM 只负责决策（产生 Action），Reducer 函数负责状态变更（纯函数、确定性）**。每轮对话前把最新结构化 State 序列化通过 system-hint 注入，替代冗长系统提示词——「当前商品 SKU、当前价格、当前库存、本场目标」一目了然
3. **大上下文卸载**：体量大但不必时刻在场的内容（完整商品列表/长篇历史数据/大文件）外存储卸载到 oss/tair（路径 id + 预览）；消费时读 fileKey，沙箱执行 shell 过滤文本取摘要

## 八项实战二：工具调用——能力边界、强约束与错误恢复

Tool Registry 解决「Agent 能做什么、不能做什么、做错了怎么反馈」，三个层面强化：

1. **能力边界声明**：每个 Skill 注册时声明能力范围和限制，Agent 调用前校验请求是否落能力域内；新 Skill 上线前过预检平台验证定位声明。源头避免越权调用
2. **Schema 强约束 + 幂等设计**：所有工具签名和决策输出 JSON Schema 约束，结构层面杜绝非法参数。**幂等性**：任何有副作用的写操作（改价/切品/发券）必须携带幂等键（UUID），框架层执行前做去重校验，维护幂等键缓存——即使网络重试或 Agent 重新规划导致同一指令发两次，也绝不出现「双切品」「双改价」
3. **结构化错误码 + 自动修复**：工具执行返回结构化错误码体系而非模糊报错字符串，框架按错误码类别采取不同恢复策略

## 八项实战三：生命周期 Hook——关键时机插入强规则

设计哲学：不改写模型推理循环，在循环关键时机插入钩子做拦截、注入、记录——保留模型自主推理灵活性，同时在必要处施加确定性工程约束。五个 Hook 时机：

- **PreReasoning**：注入上下文。最新 State、当前场景预加载记忆注入 system prompt；按用户 query 按需加载长期记忆
- **PreToolCall**：安全拦截。校验能力边界、检查幂等键、判断风险等级是否需要审批
- **PostToolCall**：结果校验与状态更新。对照实时注入业务数据交叉验证，触发 Reducer 更新 State
- **PostReasoning**：幻觉检测。验证模型输出与真实数据一致、正确调用工具（不凭空编造商品信息）
- **OnSessionEnd/LiveEnd**：记忆回写。提炼本次对话/本场直播场景轨迹事件写入记忆文件，触发后台记忆轨迹整合

Hook 把「安全」「可观测」「持续演化」横切关注点从业务逻辑解耦，统一收敛框架层管理。业务方写 Skill 不操心，框架自动触发。

## 八项实战四：沙箱执行防护——不可信代码隔离边界内运行

工具调用解决「调什么、怎么调」，沙箱解决「落地执行时怎么不搞挂宿主机、不泄露密钥、不被注入攻击」。Agent 执行 Shell、跑用户/模型提供的代码或第三方 Skill 脚本，输入必须当不可信对待；上服务后任意输入直接在宿主机执行是严重攻击面。框架层为所有代码类执行统一套沙箱：

- **身份与文件系统**：容器非特权用户运行，根文件系统只读
- **资源配额**：CPU 限额 ≤50%、进程数上限 ≤64，掐死资源耗尽型攻击
- **网络**：默认禁止所有出站连接，仅按最小化 allowlist 放行必要目标
- **系统调用**：白名单收敛，禁用高危调用
- **环境隔离**：绝不向沙箱注入任何宿主机环境变量
- **执行约束**：工具层强制 timeout 上限，Agent 传入 timeout 只能缩小不能放大（杜绝模型超长超时占死沙箱）；stdout/stderr 上限 64KB 超出截断（防海量输出污染上下文）
- **可观测**：system prompt 声明「沙箱输出不可信」；所有执行记录（代码+输出+user_id+session_id）完整写审计日志——事后追溯定责 + 为模型优化沉淀数据

## 八项实战五：五层安全防护体系——纵深防御

从 Prompt 边界到执行审计五层，每层拦不同风险，前层漏掉后层兜底：

1. **第一层：Prompt 边界硬编码**。系统提示词硬编码 Agent 能力边界与行为禁区；配合 Skill 定位声明 + Skill 预校验
2. **第二层：Schema 强约束**。强类型约束 + 幂等性设计，结构层面杜绝非法参数和重复执行
3. **第三层：Approval 审批分层**。平衡「安全」与「流畅」的核心机制：直播操作不能每步都让主播确认（Agent 就没意义），也不能全部放行（风险太高）。按操作风险等级分层审批：平台级红线框架层定义，Skill 级风险业务方声明（调价范围/商品排序间隔），Skill 提供对应校验规则
4. **第四层：工具执行验证层**。业务方控制，工具执行时做业务规则校验，返回结构化错误码 + 框架自动修复机制
5. **第五层：执行审计记录**。所有工具调用完整生命周期记录，四个用途：实时监控（循环执行/调用超时/调用失败等异常操作频率告警）、事后复盘（按时间线回放完整操作序列）、模型优化（积累高质量工具调用数据集）、争议处理（不可篡改操作证据链）

## 八项实战六：异常处理与降级策略

模型一定会出错，关键是出错时 Harness 优雅兜底。针对 Agent 推理层面几类典型异常，设计对应检测与降级策略。

## 八项实战七：LLM 驱动 PlanEngine——从 ReAct 单步到 DAG 全局

主播指令常是复合的（开播提案→创建直播间→同步历史商品→生成讲解手卡→开启智能标题，一句含多个子任务带先后依赖）。ReAct 单步局部决策顾此失彼、效率低下。升级为 DAG 全局规划，从「逐步推理局部最优」到「基于 DAG 全局最优」，五个目标：

1. **可恢复**：三层 Checkpoint 机制——每轮对话结束持久化当前状态；每个子任务完成写 Checkpoint；整体计划变更保存完整快照。恢复时状态归一支持断点续连；计划变更支持人工干预确认
2. **可观测**：三级状态可视化——每个子任务独立 TraceID 全链路追踪；Plan/SubTask/Tool Call 三级状态实时监控，主播和运营能看到执行到哪一步
3. **提升执行效率**：DAG 里无依赖子任务并行调度
4. **提升执行成功率**：局部最优升级全局最优；输出做固定规则 + 语义双重 Schema 校验；失败子任务自动重试；**增量 Replan**——子任务失败只对受影响后续节点重新规划，不推倒重来；Token 额度控制（单任务/单场次预算上限）防资源耗尽
5. **降低上下文漂移**：执行进度外挂（计划步骤进度独立于对话上下文维护，不占 Context Window）；SubAgent 上下文隔离（复杂任务拆独立 SubAgent 执行避免交叉污染）；Plan 快照持久化（上下文压缩前先落盘 Plan 状态防丢失）；System-Hint 动态注入（任务状态实时注入把模型注意力拉回正轨）

planner 可基于小模型 SFT 微调及强化学习，提升主播垂直领域效率准确性。

**对比结果**：PlanEngine vs ReAct，选取播前规划/直播策略/商品操作等工具组合构造的复杂步骤（平均 7 步）测试集 query，PlanEngine 在执行效率（工具执行冗余率/迭代轮次）和准确率（执行成功率/子任务覆盖率）都优于原生 ReAct（基模 qwen3.7-max）。

## 八项实战八：评测体系——质量可量化可追踪

Harness 六元组 V（Evaluation Interface）落成可追踪、离线 + 在线两个维度的评测体系：

- **trace 分析**：接入 Langfuse 可视化 trace
- **离线评测**：构建播前/播中/播后各典型场景标注数据集；特别加入对抗样本（极端改价/违规诱导/模糊指令边界 Case），专门验证五层防护是否有效
- **在线评测**：实时指标看板盯核心指标——操作成功率（工具调用成功数/总调用数）、审批通过率（soft-gate/hard-gate 通过率，过低说明 Agent 决策质量下降）、主播干预率（主播主动纠正 Agent 行为的频率，直接反映自主决策可靠度）、端到端延迟（指令发出到操作完成全链路耗时）
- **主播满意度评测**：每场直播结束主播给 Agent 表现打分（1-5 分），会话级主观质量信号

## Harness 记忆：主播记忆可靠性提升

主播 Agent 记忆体系被 Harness 工程思想深度重塑，与上下文管理（C）、状态存储（S）、Hook（L）、评估（V）紧密咬合。

### 与通用记忆系统关键差异

按「信任来源」分三层，这是区别于通用记忆最核心的设计：

- **L1 会话层**：反映主播的主观行为和声明（说什么）
- **L2 事实层**：客观信息补充
- **L3 行为层**：对 L1 进行客观信息补充和信任度评分（做什么）

冷启动阶段 Agent 基于 L2/L3 历史数据给主播推荐方案；随使用基于交互反馈不断进化。

### 记忆对账与信任度进化

洞察：主播「说的」和「做的」不一定一致（嘴上说「开场先上引流款」，L3 行为记忆显示近 3 场开场实际都上氛围款且效果不错）。通用记忆遇到矛盾要么简单覆盖要么忽略。做法：

- **记忆对账机制**：矛盾时不粗暴覆盖，累积证据、达到阈值后由 Agent 主动和主播确认——既尊重主播主观意图（L1 第一优先级），又让记忆基于客观事实持续进化，避免「AI 自作主张改设定」破坏信任
- **Decision Trace Log**：每条 trace 记录「问什么/Agent 答什么/主播选什么/最终效果」——把 Harness 评估接口（V）的可观测数据反向喂给记忆系统做自进化
- **trust_score 信任度更新**：衡量「主播对 Agent 建议的信任程度」，播后逐条 trace 归因后立即更新；反向决定 Agent 输出形态——信任度高大胆给建议，信任度低只摆数据不下结论

这套「Decision Trace、信任度更新、输出形态自适应」闭环是主播 Agent 记忆体系的灵魂：信任关系从模糊感觉变成可度量、可演化、可解释的工程量。

### 直播场景多因子遗忘

比通用「时间衰减」精细，多因子加权衰减：

- **直播场景相关性**：品类集中度、常播品类策略等
- **信息新鲜度分级**：偏好/话术模板等经验型记忆慢衰减；价格/平台规则等波动型记忆快衰减
- **时间衰减**：常规时间维度
- **可信度因子**：经过验证、使用频率高的记忆获得加成；被证伪的记忆急剧降权；未验证保持基础衰减

配合定时任务清理策略（采纳次数/召回次数 ≤ 遗忘阈值则清理、超期清理），以及记忆冲突处理（Last-Write-Wins + 自定义优先级，或召回时把冲突呈现给 Agent 主动确认），保证记忆库长期不失控、不腐坏。

## 总结

主播 Agent 工程实践回答同一个问题：模型能力不确定，怎么工程化成高风险直播场景里可用、可控、可演化的系统？答案就是 Harness 这层骨架。

- H = (E, T, C, S, L, V) 六元组划清工程边界
- 「业务方写 Skill、框架兜底脏活」分层把迭代效率和工程质量解耦
- 上下文工程、强约束工具调用、生命周期 Hook 搭好通用底座
- 五层纵深防御、DAG 全局规划、离在线评测扛住直播场景极端要求
- Harness 思想深度重塑的记忆体系：三层记忆、记忆对账、信任度自进化、事件驱动检索、多因子遗忘，让 Agent「越用越懂主播」

模型会一代代变强，但包裹模型的这层 Harness 工程，才是把「能用的 Demo」变成「敢上线的产品」的真正壁垒。
