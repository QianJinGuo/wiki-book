# 从商品质检到供给质量自进化：高德供给质量 Agent 实践

> 高德技术（信息业务中心）第一方实践：如何把业务运营的判断方法外化为可管理的 Skills，用人机共创和"生产稳定、旁路进化"的非对称机制让供给质量持续变好。

## 问题：供给质量治理
在本地生活交易中，供给质量指商品与服务信息是否准确、价格是否有竞争力、库存是否稳定、履约规则是否清晰。它直接影响用户决策，也影响点击、转化、成交和履约体验。过去标准主要依赖专家经验和人工巡检；当商品规模、品类差异和市场变化同时放大时：标准难复制、长尾问题难覆盖、整改与复审相互割裂、交易结果也很难及时反哺下一轮判断。

目标不是把人工审核简单搬给大模型，而是把运营人员的目标、标准和边界沉淀为可执行能力：Agent 负责稳定执行、收集证据和推动整改，运营人员负责定义目标、校准争议案例和决定是否发布，真实业务结果再成为下一轮改进依据。

## 核心设计：非对称进化
最关键的设计，不是让生产环境中的 Agent "自己改自己"，而是把业务执行与能力进化分开：
- **业务 Agent 只加载经过评测并发布的稳定 Skill**，负责生成巡检计划、审核商品和查询分析；即使发现新问题，也不能直接改写正在使用的规则。
- **旁路运行的进化器 Agent** 从业务结果和人工复核中抽取失败案例（Bad Case），区分数据缺失、工具调用、评测口径、Skill 表达、模型能力和后处理等根因，再生成候选版本。候选版本必须经过隔离测试、运营确认和小流量试运行，进化器本身没有直接发布或修改生产规则的权限。

这种"稳定执行、旁路进化"的非对称机制，把人放在目标设定、边界判断和发布决策上，把 Agent 放在规模化执行、证据整理和候选改进上。系统既能持续学习，又不会把一次偶然反馈直接放大成生产风险。

## 真实端到端案例：从生产误判到候选版本验证
来自两个实际生产误判请求（均有工人确认的正确答案，用相同完整输入在候选版本上重新执行）。第一个案例把儿童体验套餐错误匹配为成人体验套餐；第二个案例本应只返回 3 对同人群商品，却在正确结果外又生成"长者专享→儿童专享"和"儿童专享→长者专享"两对交叉匹配。

根因不在消息处理或模型调用，而在**结果处理规则**：旧版本会删除商品名称中括号标注的"儿童""长者"等人群信息，再把归一化后同名的商品强制判为同款——这个确定性兜底覆盖了模型对人群差异的判断。进化器沿输入、模型结果和结果处理逐层排查后，没有泛化为"模型不够聪明"，而是生成最小候选改动：移除强制同名兜底，同时保留人群与价格差异的硬约束。

指标对比：旧版本 TP=3、FP=3、FN=0，精确率 50%、召回率 100%；候选版本用原始完整请求回放后，案例一不再产生错误匹配，案例二只保留 3 对正确结果，合计 TP=3、FP=0、FN=0，精确率和召回率均 100%。单条耗时约 1-2 分钟。实践覆盖"生产失败案例发现→人工答案确认→根因定位→候选改动→同输入回放→成对指标比较→发布门槛判断"完整链路，说明**进化不一定要修改 Skill 文本：如果根因在结果处理，就应该修结果处理**。两条定向回归只能证明这类跨人群误判被修复，不能代表整体准确率 100%，也不能推导出交易转化提升——扩大范围前仍需更大隔离测试集和小范围试运行。

## 系统如何落地：从共创到执行
整条链路只有三个核心动作：运营人员与 AI 共创标准，业务 Agent 按稳定版本执行治理，交易与人工反馈验证标准是否有效。
- **标准共创**：运营人员直接描述不同品类/城市/场景下的竞争力、质量标准与巡检范围；AI 追问适用条件、反例和人工兜底边界，把自然语言经验整理成结构化 Skill 草案。
- **执行**：商品发布前触发准入审核，上线后按策略定期巡检；未达标商品 Agent 给出问题/证据/优先级/复审条件，由商家运营团队整改，整改后再审核形成可追溯任务链。
- **效果验证**：把审核、整改与后续曝光/点击/转化/履约/投诉等结果关联；标准只有质量指标和业务结果都支持才扩展到更多品类/场景；没收益或误伤的标准降优先级或撤回。

工程上分四层：任务编排（识别场景）、业务 Skills（承载判断）、工具与数据（可信工具提供事实执行动作）、评测与治理（版本比较/小流量试运行/观测/回退）。分层的价值：业务策略不再散落在代码/提示词/运营文档里，每个结论都能追溯到当时的 Skill、事实证据和人工反馈，每次改动有清晰责任边界。

## Skills 外化：把经验变成工程资产
传统业务规则写进代码（稳定但迭代慢）或提示词（灵活但易失控）。Skills 提供第三条路径：把业务判断写成独立、可版本化的能力说明，既能由 Agent 加载执行，也能像代码一样接受评测、审阅和回退。一个合格 Skill 需同时说明：适用范围、判断标准、执行顺序、正反例和边界案例、人工介入条件、结果表达方式、哪些事实必须来自可信工具。

当前最值得优先外化的是三类主流程能力：**巡检规划**（根据品类/城市/节假日/交易异常/库存波动/用户反馈/平台榜单，生成巡检主题/范围/频率/优先级——把运营对风险与机会的判断变成可执行计划）、**商品质量审核**（发布前审核和上线后巡检，检查标题/详情/价格/库存/履约，输出结论/证据/整改建议，质量标准作为 Skill 版本化内容持续迭代）、**数据查询分析**（为前两者提供事实支持，查询曝光/点击/转化/成交/履约/投诉/库存/价格，帮助解释为什么巡这批商品、问题是否影响交易、新标准是否有效）。

## 一条生命周期，只有一个发布入口
完整生命周期只保留一条：运营与 AI 共创经验→生成候选 Skill→在历史样本和隔离测试集上与稳定版本对比→通过门槛后小范围试运行→持续观测质量与业务指标→结果稳定才扩大范围，出现误伤/漏检/效果下降则回退上一稳定版本。生产环境业务 Agent 只能读取已发布版本，旁路进化器无权绕过这个入口。外化真正价值不是"文档换名字"，而是把专家经验变成可复现、可比较、可审计的业务资产。先跑通少数主流程，再按真实复杂度拆分能力，比一开始追求庞大 Skill 数量更重要。

## 进化的两个目标：能力质量与业务结果
持续进化不等于不断增加功能。真正需要长期优化的只有两件事：判断是否越来越可信（能力质量，解决"敢不敢用"）、判断是否带来更好用户体验和经营结果（业务结果，解决"值不值得用"）。

**能力质量：从失败案例修到通用规则**。每次巡检/审核沉淀为可追溯样本（业务场景/商品输入/Skill 版本/Agent 输出/事实证据/人工复核）。抽取误召回/漏召回/误判/漏判/证据结论不一致等失败案例，不只保存"对/错"标签。根因分析沿真实执行链展开：先检查输入是否完整、工具是否返回正确事实、评测标准是否一致，再检查 Skill 是否含糊/步骤示例不足，最后才判断是否模型能力或结果处理问题——避免把数据和规则缺陷笼统归咎大模型。进化器只针对已证实根因生成最小候选改动（澄清边界条件/补反例/调整证据要求/修正输出结构），每项改动关联原始失败案例和变更说明，防止修复单样本造成过拟合。能力评测逐条核对结论/原因/证据，关注准确率/召回率/误伤率/漏检率/失败案例修复率；候选版本只能在隔离测试集上证明相对稳定版本有收益且关键场景不退化，不能用参与优化的样本为自己打分。

**业务结果：让标准接受真实交易检验**。准确判断只是中间结果。标准还要接受曝光/点击/转化/成交/履约/投诉等结果检验，否则系统只是在更准确地回答一个不重要的问题。许多标准起初只是待验证假设（更低价格是否提升转化/标题突出核心权益是否优于品牌/规则表达更完整是否减少疑虑）。Agent 把每次判断和整改与后续结果关联，帮运营判断哪些假设值得保留。效果回收把标准分三类：有效标准扩展到相似场景；看起来合理但无收益的标准降优先级；对特定品类误伤的标准缩小范围或撤回。外部研究能力补充新标准假设（分析公开行业规则和优秀商品案例），但外部发现只能成为候选假设，不能绕过内部数据验证和人工确认。**能力指标和业务指标必须同时成立：前者证明 Agent 判断可靠，后者证明判断值得规模化。任一缺失都不能视为进化成功。**

## 工程边界：可靠比自治更重要
事实获取与模型推理必须分离（价格/库存/履约/交易指标/外部信息来自可信数据源或工具，模型负责比较/归因/生成建议；最终结果保留数据来源/适用标准/版本信息供运营复核）。评测门槛和回退能力必须在发布前设计而非出问题后补救（任何新标准/Skill 需与稳定版本比较并限定初始影响范围；准确率/召回率/误伤率/业务结果异常时系统能停止扩量并恢复上一稳定版本）。人机协同边界清晰：高置信度/低风险/可复审问题自动处理；高价值商品/争议标准/低置信度结论进入人工确认。自治不是"完全无人"，而是把人的时间从重复执行转移到目标/边界/例外判断上。

## 总结
供给质量 Agent 的核心，不是把更多判断交给大模型，而是把运营知识外化为 Skills，再用非对称进化守住生产稳定性：业务 Agent 稳定执行，进化器旁路提出候选，人负责目标、边界和发布决策。真正有价值的进化，不是系统频繁改写自己，而是每次改动都有真实失败案例、有可信评测、有明确责任边界，并最终经得起业务结果检验。
