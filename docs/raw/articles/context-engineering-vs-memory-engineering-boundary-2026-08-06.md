# 智能体系统中的上下文工程与记忆工程

> 原始来源：https://mp.weixin.qq.com/s/ko1FiZ8z-DtCEMIHGOJeWA
> 作者：AI技术立文，2026-08

## 引言

当 AI 智能体进入更长的工作流和多会话场景，一个熟悉的模式会出现：约束在中途被丢弃，不该再出现的检索信息又冒出来，上一步的上下文渗进当前步骤。这类故障很难定位——问题通常出在两个常被一起搭建、被混为一谈、或干脆被跳过的环节：**上下文工程和记忆工程**。两者相关但独立，失败方式不同，需要不同的系统才能做对。

## 上下文与记忆工程总览

- **上下文工程**：覆盖单次推理调用的设计——纳入什么、压缩什么、放在哪里、丢弃什么。作用域内的东西都是临时的，调用结束窗口清空
- **记忆工程**：关注单次模型交互之后还能留下什么——写入、存储、检索、更新、治理信息的系统和策略，使未来交互能够复用

| 维度 | 上下文工程 | 记忆工程 |
|------|-----------|---------|
| 作用范围 | 一次推理调用 | 跨调用、跨会话、跨智能体 |
| 数据所在 | 模型的活动窗口内 | 外部存储：向量库、K/V、关系库 |
| 核心问题 | 纳入什么、怎么排列 | 持久化什么、检索什么、信任什么 |
| 何时失败 | 窗口装满、放置错误、噪声压过信号 | 检索落空、过时、被污染、无写入策略 |
| 工程面 | 提示结构、压缩、token 预算 | 存储模型、检索策略、写入与更新策略 |
| 数据寿命 | 一次 LLM 调用的时长 | 取决于记忆类型 |

## 上下文工程：装配最优上下文窗口

Anthropic 对有效上下文工程的拆解：系统提示、任务描述、对话历史、工具输出、检索到的文档、子智能体摘要。上下文工程就是决定每个组件贡献什么、以什么形式、放在哪个位置的那组决策。

### 3.1 选择性纳入

不是所有可得信息都该进入上下文。哪些原文纳入、哪些压缩成关键事实、哪些直接丢弃，是设计选择不是默认值。

### 3.2 结构性放置

模型对长上下文的首尾关注更强，中间内容权重明显更低（"中间丢失"效应）。硬约束和任务关键指令放窗口顶部；与当前任务最相关的检索信息放靠后位置；当前用户查询紧跟在检索信息之后——把相关上下文和即时目标放到尽可能靠近生成点的地方。

### 3.3 到达即压缩

工具输出应在调用返回时就压缩，而不是等窗口装满。3000 token 的原始 API 响应里智能体只需要 150 token，就该在进入下一步上下文前被摘成要点。等窗口满了再慌忙截断，是在被动管理一个本可以在源头消除的问题。

### 3.4 对话历史管理

对话历史比任何其他上下文组件增长都快。压缩策略（滚动窗口、分层摘要、结构化状态抽取）应在固定间隔施加，而不是等窗口溢出才动手。

## 记忆工程：设计持久化 AI 记忆系统

覆盖四个独立关切：写什么、存在哪、怎么取、怎么保持准确。

### 4.1 写入策略设计

写入策略是记忆工程里最被忽视的一环。一个清晰的写入策略要说明：什么事件触发写入 / 哪些信息有资格存储 / 以什么格式存储（原文、结构化记录、抽取的事实、摘要）/ 置信度或校验要求 / 哪些智能体允许写入特定命名空间 / 更新更正冲突如何处理 / 留存规则、过期策略、TTL。没有显式写入策略的系统往往默认存太多、对所有条目一视同仁地信任、无限期保留——时间一长记忆系统不停增长却越来越没用。

### 4.2 存储层选型

| 记忆类型 | 存什么 | 存储后端 | 检索方式 |
|---------|--------|---------|---------|
| 工作记忆 | 当前任务状态、中间结果 | 内存或短时 K/V（Redis） | 直接按 key 查 |
| 情景记忆 | 过往交互、任务运行、决策 | 向量库（Pinecone、Weaviate、Chroma） | 语义相似度搜索 |
| 语义记忆 | 持久事实、用户偏好、领域知识 | 向量库 + K/V 混合 | 语义搜索或精确 key |
| 程序记忆 | 学到的工作流、成功动作模式 | 结构化存储或提示注入 | 模式匹配、直接检索 |

OpenAI Agents SDK 的上下文个性化示例区分：基于检索的记忆 vs 基于状态的记忆——结构化状态抽取（写入带类型、经校验的事实）对需要跨会话可靠应用的事实更稳定。

### 4.3 检索策略

设计良好的检索层：先查工作记忆（快、便宜、精确 key 查）→ 找不到退到情景或语义记忆做语义搜索 → 返回前按时效和信任级别做元数据过滤 → 只注入当前步骤需要的部分。

### 4.4 记忆维护

没有维护策略的存储会随时间退化。实际有用的维护动作：对易变事实做置信度衰减、对语义相近条目去重、对工作记忆和时效数据按 TTL 过期、把旧情景记录周期性压缩成会话级摘要。MemoryEntry schema 示例（content/memory_type/importance/confidence/trust_level/created_at/expires_at/provenance）+ should_write_to_long_term 判定（importance≥0.6 且 confidence≥0.7 且 trust_level≥0.5）。

## 检索边界：连接记忆工程与上下文工程

记忆工程关注持久化（什么该存/更新/保留/遗忘），上下文工程关注使用（什么该进入活动上下文窗口/怎么组织）。**检索是这两门学科交汇的边界**：记忆系统产出候选信息，上下文装配接着决定要不要进提示、进多少、放哪个位置。

## 失败模式之一：没有上下文预算的检索

最常见失败：把检索和上下文装配当成独立的两件事。记忆搜索返回相关条目，上下文装配器全部塞进提示——随着记忆越加越多，窗口被检索内容渐渐填满，留给指令/工具输出/推理痕迹/任务信息的空间越来越少。症状有迷惑性：检索质量看起来很高、相关记忆确实被找到、系统性能仍在退化——记忆系统没做错什么，失败原因是上下文装配缺少预算机制。

更好做法：**检索感知的上下文装配**——上下文层在检索开始前先分配好 token 预算，检索层只返回落在预算内价值最高的记忆（retrieve_for_step 代码示例：max_tokens 参数 + 按 relevance_score 排序 + 预算内截断）。检索必须在上下文约束内运作，不能假设下游有无限空间。

## 失败模式之二：检索信息放置不当

光有检索质量不够。即使高度相关的记忆，放在上下文窗口里位置不对也会失效。常见问题：把检索纯粹当成搜索问题，忽略放置——检索到的记忆被追加到它到达的位置，不考虑在当前推理步骤里的角色。长上下文里影响更大：注意力在提示内并非均匀分布，放在深处的信息受关注程度远低于首尾。

隐蔽失败链：正确的信息被检索到 → 信息被插入上下文 → 模型表现得像是没看到。**检索成功了，放置失败了。** 上下文装配要同时优化两点：选择（什么进入窗口）和放置（它在窗口里的位置）——需要影响当前步骤的检索信息应放在靠近活动推理区域的位置。

## 小结

上下文工程和记忆工程是同一个系统的两层，控制模型知道什么、何时知道、这些知识怎么被用。上下文工程在推理时运作塑造活动信息窗口；记忆工程跨时间运作塑造什么信息留存、以后怎么被检索。
