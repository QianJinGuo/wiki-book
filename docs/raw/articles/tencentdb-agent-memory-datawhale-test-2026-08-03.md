# 腾讯把 Agent 记忆系统开源了，TencentDB Agent Memory 实测！

> 作者：李秀奇，Datawhale 成员

## 背景：Agent 缺乏跨会话持久状态

不带长期记忆的 AI 编程工具：说过的偏好（PPT 用 HTML 写）下次开新会话照样丢；纠正过的毛病照犯。本质：对话一结束上下文就被销毁，模型没有跨会话持久状态。

腾讯云数据库开源 TencentDB Agent Memory，官方仓库文档称能把碎片对话自动沉淀成可检索的长期记忆。7 月加强 Memory Hub 团队记忆能力，把 Skill、Wiki、CodeGraph、Chat Memory 四类资产汇入同一 AI 协作团队池。GitHub 仓库已 1.1w Star。开源地址：https://github.com/Tencent/TencentDB-Agent-Memory

## 一、从个人记忆到团队记忆

### 个人记忆的四个维度

记忆从产生到被用上要经过**写入、提炼、检索、更新**四步，链路上前后依赖，前一步输出是后一步输入。哪一步掉链子，结果是这一轮拿不到该有的记忆——而且掉链子的方式往往不是报错，是安静地返回空结果。

写入、提炼、检索都走公开接口，整条链可见：写进去什么、提炼成什么、召回了什么、各环节耗时多少。

### Team Memory / Memory Hub

7 月发布的 Team Memory 版本把关注点拉到团队层面：多个 Agent、多个成员共用一套记忆时，知识迁移、权限划分、资产归属是另一组系统性问题。

Memory Hub 把四类资产汇入同一个池子：Skill（验证过的操作流程）、Wiki（团队文档）、CodeGraph（代码仓库知识）、Chat Memory（历史交互）。四类资产经审核和共享后挂给新 Agent，新 Agent 接着团队已有进度往下做。

**团队记忆不是个人记忆的放大版**：个人记忆错了自己纠正，团队记忆错了会被所有人继承；个人记忆没有权限边界，团队记忆里存着谁能看、谁能改、谁能删。

## 二、四层实测

### 第一层：时效性

写入分两层：
- **落盘**：话说完原文当场原样存进本地流水账，毫秒级完成，保证不丢
- **提炼**：后台调一次模型，通读对话，分出场景，抽出重点，做成结构化卡片，保证能查

实测：写入"我习惯早上 6 点起床跑步，晚上 11 点前睡觉"，查询词"跑步"，第 5 秒查不到，第 10 秒卡片出现。后台日志显示原始对话落盘后几乎立刻触发提炼任务，模型整理耗时约 6 秒。卡片几乎原样保留两条作息。

两层都达标：原文不会因提炼没跑完被删；从一句话到可检索的结构化记忆全程 10 秒。批量场景要注意空窗期（写完不能立刻查）。

### 第二层：提炼质量

设计两组对照（主题不同，避免去重机制拦截）：A 组一次性说完三条项目规范，B 组分三轮说三条文档格式规范，都手动触发提炼。

- A 组：1 张规则类卡片，三条约束全写在内（包管理器用 pnpm 不用 npm、代码注释用中文、提交记录以中文动词开头）
- B 组：2 张规则类卡片。第一张合并第 2、3 轮（避免第一人称、章节标题用陈述句）；第二张单独保留第 1 轮（统一用 Markdown 不用 Word）。两张共享同一场景名

结论：一次说完倾向合成一张卡；分多轮按提炼批次拆成多张，但落在同一场景、检索时一起召回。两种说法的信息完整度没有差别，三条约束一条都没丢。

### 第三层：检索命中

存"用户完全不能吃辣，对辣味食物有严格禁忌"，用八种不同说法查询：带"辣"字的说法都能查到，"川菜""忌口""spicy food"一条都召不回。

**发现：TencentDB Agent Memory 的语义召回默认是关着的**。打开语义召回后系统同时跑第二条路，把问题和卡片各自转成"语义指纹"（文字含义变成数字坐标），查询时按语义距离判断关联。

### 第四层：更新演化

选"数据库选型"话题避开已有包管理器规范（同主题会被去重拦掉）。四轮对话：第一轮"项目数据库必须使用 PostgreSQL"，中间两轮无关内容，第四轮"改用 MySQL"。

查库结果：**旧卡片和新卡片都还在**。旧卡片内容编号原样保留，没被删除改写；新卡片明确记录"决定将数据库从 PostgreSQL 切换到 MySQL"，时间顺序和变更动因都保留。

写新卡片前系统做一次**冲突仲裁**：先在现有记忆里找几张相似老卡片，再交给模型判断该新增、跳过、覆盖还是合并。这次语义召回没开，找候选只能靠关键词，新旧记录除"数据库"三字几乎无重叠，没找到足够相似候选 → 新内容直接存成新变更记录。后续 Agent 同时看到两张卡，从时间线和内容判断哪条是现行偏好。

## 三、核心机制设计（源码拆解）

拆解源码发现设计共七块：底座是四层分层，往上是写入、检索、注入三条主干，再加上冲突仲裁、短期记忆、故障降级三处兜底。

### 记忆金字塔：L0 → L3 四层分层

为什么不直接存列表？想要证据完整就得把原话一字不改存下来；想省 Token 就得压缩成精简摘要。同一份数据没法既是原文又是摘要。解法是拆四层，官方叫**记忆金字塔**：

- **L0 流水账**：每次对话结束，用户和助手原话写进本地文件+同步数据库，一字不改，不做任何提炼
- **L1 记忆卡片**：会议纪要。后台通读对话，先按情境分段，再抽结构化事实。每张卡片只记一件事，类型只有偏好、事件、规则三种，带优先级
- **L2 场景档案**：同一情境下的卡片打包成一份文件，按情境组织不按日期。文件头记创建时间、更新时间、摘要、热度值（每检索命中一次 +1）
- **L3 人格摘要**：从所有场景档案提炼的稳定画像，描述"这个用户是谁"。四层里唯一不需要检索的——前三层查到了才用得上，只有它每次新会话无条件注入，所以必须足够短、足够稳定

四层各管一段：L0 留证据，L1 保精度，L2 保情境，L3 保效率。底层存数据库全量可检索，高层写 Markdown 人能直接读改。四层可串起来从人格摘要追到原始对话，平时给高密度摘要、纠错时给完整证据链。

### 写入与提炼：分离式处理

写一条记忆只需要一个动作（用户输入+助手回复交给系统，原始对话毫秒级落盘），这一步只是录音不做理解。记忆卡片不顺手一起做，因为提炼绕不开模型："我不吃香菜"是长期偏好、"今天中午吃了火锅"是一次性事件，文本上没区别，只有理解内容才能分开，规则和关键词统计做不了。模型调用有成本有延迟，放主流程会干等，只能后台异步跑。

提炼默认两个触发条件：每满 5 轮对话，或停止输入 10 分钟，也可手动立即触发。新会话默认开预热，前几轮阈值从 1 开始递增（1 轮、2 轮、4 轮），之后稳定到 5 轮，所以刚开始聊第一轮就会触发提炼。

每张卡片的类型和优先级由模型根据内容判断，没有写死的规则——好处灵活，代价不可预测。

### 检索与注入：平衡精度和成本

三种方式：

1. **字面匹配**：底层全文索引+关键词稀有度打分，中文查询先分词再"或"匹配，命中稀有词的排前面。快、省钱、死板。卡片总量少时稀有度分数会失真，源码留补救路径：遇到这种情况放弃阈值过滤直接信任索引排序（实测"你能吃吗"意外命中就是补救路径起效）
2. **语义指纹**：问题和卡片各自转成数字坐标，按坐标远近判断是不是一回事，字面零重叠也能命中。需额外配模型服务，默认没开，打开后换说法、跨语言都能召回
3. **混合检索**：前两条路同时跑，排名叠加器合成一张榜单。规则：卡片在自己那份排名里越靠前加分越多，两边都出现分数累加。**叠加器只看名次不看原始分数**（字面匹配和语义相似度是两套计分方式，0.8 分不是一回事，直接比大小没意义）

**易踩坑**：策略默认值是混合检索，但语义能力默认值关闭——两个凑一起检索实际降级成纯关键词。零配置装完跑的是字面匹配。

**注入**：每轮对话开始前，系统把当前这句话和记忆库做匹配，召回最相关几张卡片，5 秒超时保护，超时跳过注入。召回内容放两处：
- 用户消息前面：本轮动态召回的记忆卡片，每轮都变
- 系统提示末尾：人格摘要、场景导航、工具指南，几轮才变一次

分开放是因为大模型服务商缓存系统提示这段稳定前缀，命中缓存不重复计费；把每轮都变的卡片塞进系统提示会立刻失效缓存，Token 和延迟一起上升。注入有预算控制：单条记忆长度上限+本轮注入总字符上限。系统在提示词里约束 Agent 每轮主动检索合计不超过 3 次（软约束，靠模型自觉）。

### 冲突仲裁：解决记忆更新问题

"必须用 PostgreSQL"和"改用 MySQL"字面上矛盾，但矛盾至少有三种可能：改主意了（覆盖旧的）、两个不同项目的事（两条并存）、自己前后不一致（留两条让人类判断）。三种在文本上长得一模一样，只有理解上下文才能分开，所以写一条记忆要多调一次模型。

两个阶段：
1. **候选召回**（不调模型）：新卡片转成语义指纹，在已有卡片里找距离最近几张；语义不可用降级关键词召回；两条路都不可用跳过这步
2. **模型判断**：新卡片+候选老卡片打包，一次问模型该新增、跳过、更新还是合并

**关键**：第二阶段的判断质量完全取决于第一阶段召回到了什么。模型只能在给它看的候选里做判断，没召回到的老卡片在它眼里等于不存在。

### 任务地图：长任务上下文卸载

单次任务太长（改跨十几个文件的 bug，几十轮上下文撑爆）：把详细过程转存外部文件，上下文只留一张任务地图（节点和箭头呈现状态流转，节点标编号和下一步动作，核对细节按编号回详细记录）。思路和长期记忆一样：平时给折叠视图，需要时展开细看。

官方 WideSearch 长任务基准：Token 消耗从 2.21 亿降到 8500 万，通过率从 33% 提升到 50%。

### 故障降级：记忆系统坏了也不影响对话

原则：**故障容忍优先于功能完整**。

- 检索侧：语义和关键词都可用跑混合；只有一条可用降级成那一条；两条都不可用返回空结果
- 写入侧：去重判断超时全存为新卡片；语义指纹写入失败不影响已落盘原始对话；召回超时跳过本轮注入

最坏情况是这一轮没有记忆可用，但对话还能继续。

## 四、上手

默认本地 SQLite 存储，安装完就能用。换成自己的大模型做提炼和画像生成只需填三项：模型访问凭证、服务地址、模型名称。接入三种路径：装成 Agent 平台插件、通过统一网关调用、自研项目直接引用。

**配置决策**：要不要开语义召回。只需记住格式规范、工具偏好这类说法固定的东西就不用开；要理解自然语言表达的偏好就需要开。

## 核心观察

以前向量化、相似度检索、结果重排序全是应用层任务，现在变成安装时的一个选项。**Agent 需要的记忆能力，正在从应用层下沉到数据库层。数据库给人存了几十年数据，现在要开始给 AI 存记忆了。**
