# 大模型之外，向量存储如何支撑 Agent 的检索链路

> 作者：木洛，千问AI平台（公众号，阿里官方）
> 从 Agent 实际需求出发谈向量存储：三种主流索引实现取舍、混合检索、分布式架构设计、Serverless 维度，以及阿里云 Tablestore SearchIndex 与 OSS Vectors 两种 Serverless 向量存储用法。

## 向量存储在 Agent 中承担什么角色

向量存储并非所有 Agent 的必选组件。当数据量很小、内容能完整放入上下文，或查询总能通过确定主键完成时，文件和普通数据库已够用。向量存储处理另一类问题：数据规模持续增长，查询者不知道准确位置和关键词，只能根据内容含义寻找结果。

在需要处理外部知识和跨任务记忆的 Agent 架构里，向量存储承担两个角色：**检索**和**记忆**。

**检索**：Agent 要为当前任务补充外部数据，因为模型参数不含企业全部私有数据，也跟不上持续变化的业务信息。数据量小还好，多起来后难点变成找出真正相关的部分。用户问题和原始资料常用不同表达（如"升级后看不到以前的审批单" vs 文档"版本迁移后历史流程的可见范围发生变化"）。Embedding 模型把问题和文档转成向量后，语义接近的内容在向量空间距离更近。图片、音视频、代码也可通过模型生成向量，一次解析后语义能被不同任务反复检索。

**记忆**：长期经验需要在后续任务中被重新找到和使用。历史对话、执行结果、用户反馈未来都可能继续发挥作用。文件也能存规则和摘要，但历史记录持续增长后就扛不住——Agent 通常不知道目标记录的文件名和产生时间，新旧任务表述未必一致。把历史对话和执行结果生成向量后，Agent 可根据当前任务找回语义相关的记忆（如运维 Agent 用当前故障现象检索过去症状相似的处理记录）。向量存储在这里就是记忆的搜索引擎。

两个场景说到底是一回事：Agent 要从持续增长的数据中找出与当前任务语义相关的内容。

## 向量存储的基本实现

向量存储不只是存向量。一个完整系统要同时管理向量、文本和元数据，写入和查询都围绕这三类数据展开。一条可检索记录通常包括向量、原文/摘要，以及租户、来源、时间、权限等元数据。Embedding 表达语义，Agent 最终用的仍是原文/摘要；检索时根据租户、权限等属性判断结果能否用。这些内容可与向量放同一系统，也可通过唯一标识关联外部数据。

数据结构直接影响查询能力。如"在当前租户最近三个月发布的文档中，查找与审批权限有关的说明"既含语义，也含明确租户和时间条件，系统需把向量检索、全文检索和元数据过滤放进同一条查询链路。

三项技术直接影响能力边界：**向量索引**（避免扫描全部向量找相似结果，影响召回率/延迟/成本/规模）、**混合检索**（组合语义、关键词、业务条件，决定能否同时满足相关性和业务约束）、**分布式架构**（突破单机容量吞吐限制，决定单个数据空间能扩多大）。

### 向量索引：从全量计算到近似搜索

向量检索先确定距离/相似度度量（欧氏距离、余弦相似度、内积）。数据量少时可全量计算返回最相似 K 条，但数据量上来后全量计算线性增长，实际系统用 **ANN（近似最近邻）** 索引，只搜更可能含近邻的部分数据，代价是可能漏掉真实近邻。评价索引看召回率（近似 TopK 与精确 TopK 重合度）、查询性能、资源成本、数据规模。主流没有一种索引能同时最好，核心区别在搜索路径和主要资源消耗。三类路线：

**HNSW（内存图索引）**：把向量组织成多层邻接图。上层节点少、连接跨度大，快速接近目标区域；底层节点多、连接密，完成局部搜索。查询从上层入口开始沿邻居逐层下降，最后在底层扩展候选。用内存换低延迟高召回率，节点除向量还维护多层邻接关系，图结构和查询向量常驻内存，内存随向量数和维度增长。适合查询频繁、延迟要求高、能提供足够内存的场景。

**DiskANN（磁盘图索引）**：同样沿邻接图搜索，但针对 SSD 优化。内存保留量化后的向量、入口点和热点信息，完整向量及主要图数据放 SSD。查询先用内存近似信息筛选候选，再并行读 SSD 邻居，最后用完整向量算精确距离。用 SSD 承载主要索引、较少内存维持在线查询，承载更大规模，但查询性能受 SSD 随机访问、缓存命中率、单次读取量影响。适合规模大、仍要求稳定在线查询的场景。

**IVF（聚类分区索引）**：先训练聚类中心，把每个向量分配到最近分区。查询先找与查询向量最接近的几个聚类中心，只在对应分区内算距离（搜索分区数称 nprobe）。用分区缩小搜索范围、扫描量调节召回率和成本，索引元数据小、分区内数据适合批量读，易利用大容量低成本存储。增 nprobe 召回率更高但扫描量和延迟增加。适合数据规模大、成本敏感场景。

| 索引路线 | 数据组织 | 查询路径 | 主要资源 | 适合场景 |
|---|---|---|---|---|
| 内存图（HNSW） | 分层邻接图 | 稀疏上层进入，底层扩展候选 | 内存 | 低延迟高召回，索引能入内存 |
| 磁盘图（DiskANN） | SSD 优化邻接图 | 图遍历+缓存+SSD 读取 | 内存+SSD | 大规模、高召回、稳定在线查询 |
| 聚类分区（IVF） | 聚类中心+数据分区 | 定位相近分区后扫描 | 存储+计算 | 超大规模、成本敏感、可调扫描量 |

没有统一最优索引。实际选型要用业务数据，在相同召回率目标下比较延迟、吞吐、成本。

### 混合检索：把语义和业务条件放进一条查询链路

关键在候选如何产生、过滤在哪一步执行、结果怎样排序。一条真实查询通常同时含向量（语义）、关键词（产品名/错误码等准确术语）、过滤条件（租户/权限/时间）。接口上同时支持这些条件 ≠ 以正确方式共同参与查询。

**过滤时机直接影响结果**：先召回 20 条向量结果再按租户/权限过滤，大部分可能被排除、返回数量不足；满足条件但没进最初 TopK 的内容也不会被找回。让过滤条件参与候选生成，系统就能在满足业务条件的数据中找近邻，但这要求向量索引本身能高效处理过滤。

全文和向量检索分数含义不同，不能直接相加。常见做法：先归一化各路分数，或用 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 根据结果在各路召回中的排名完成融合。RRF 不依赖不同引擎的原始分数尺度，多系统召回中易落地。

混合检索可在单一查询引擎内完成，也可由多系统分别召回后应用层合并。前者链路更短、数据/权限/过滤规则易一致；后者可独立选组件，但要处理数据同步、调用延迟、结果融合。

### 分布式查询：分片执行和全局 TopK

分布式能力决定单个逻辑数据空间的容量吞吐上限。单机装不下时把数据和索引拆到多分片，各分片并行查询返回局部 TopK，协调节点合并成全局 TopK。分片增加后，一次查询成本取决于访问多少分片：若所有分片都可能含近邻，请求广播到整个索引；若按租户/业务属性准确路由，可查询前缩小范围，减少计算/网络开销和协调节点合并压力。扩容带来分片迁移和索引重建，需保持查询稳定。

## 向量存储选型：不再只看检索和规模

选型分两层。第一层是检索能力和数据规模（三项技术怎么匹配业务），第二层是资源如何创建、交付和计费——过去主要关注前者，但 Agent 应用让后者越来越重要。

三个因素互相影响，不是选完一项再选下一项：数据规模增长后全内存 HNSW 成本可能过高；过滤条件复杂时候选生成方式直接影响召回结果；多系统召回增加数据同步和查询延迟。选型要从完整数据和查询负载出发，不能只看单项性能。

**Serverless 成为新的选择维度**。Agent 平台可能按用户/任务动态创建大量数据空间，负载差异很大（有的长期空闲、有的持续活跃、有的短暂突发）。固定实例能为持续高负载提供稳定资源，但很难经济地承载这种分散且变化频繁的负载。Agent 需要的不是更大的实例，而是能跟着负载走的交付方式。Serverless 让用户只管理逻辑数据空间，系统按负载自动扩缩容、按实际使用量计费。Agent 平台可通过 API 创建和使用存储，低频空间不长期占用实例，突发查询不依赖人工调容量。阿里云在表格存储和对象存储也提供类似能力：**Tablestore SearchIndex**（面向大规模在线查询和混合检索）、**OSS Vectors**（以 Vector Bucket 组织向量及元数据）。

## 阿里云怎么做 Serverless 向量存储

阿里云在表格存储和对象存储中提供 Serverless 向量能力，面向不同查询场景：
- **Tablestore SearchIndex**：把向量检索放入多元索引，向量、全文、业务字段可在一次查询中组合，适合需要混合检索的在线查询
- **OSS Vectors**：通过 Vector Bucket 和 Vector Index 管理向量及元数据，与普通 OSS Bucket 原始内容关联，适合海量、长尾向量数据

两种服务都通过 API 管理逻辑资源，用户不需部署维护向量检索集群。

### 产品与资源模型

Serverless 向量存储把资源管理边界放在逻辑数据空间，而非服务器和分片。Tablestore 中，向量能力依附于数据表和 SearchIndex：数据表保存一行完整数据，SearchIndex 为向量、全文和标量字段建索引。OSS Vectors 中，Vector Bucket 是顶层资源，一个 Bucket 可含多个 Vector Index，每个 Index 保存向量记录及元数据；原始文档/图片/视频放普通 OSS Bucket，通过 object_key 等字段与向量记录关联。

Agent 平台需保存业务空间与云资源映射（某租户用哪张表、哪个 SearchIndex/Vector Index）。多小规模租户可共享索引并通过 tenant_id 过滤；隔离要求高或规模大的业务用独立索引。底层索引构建、分片、扩缩容、故障恢复由服务完成，应用只处理逻辑资源及生命周期。

### 创建和管理资源

**Tablestore SearchIndex** 资源层次：实例、数据表、多元索引。创建向量字段需指定维度和距离度量。伪代码：
```python
tablestore_client.create_table(
    TableMeta("knowledge", [("id", "STRING")]),
    TableOptions(),
    ReservedThroughput(CapacityUnit(0, 0)),
)
index_meta = SearchIndexMeta([
    FieldSchema("vector", FieldType.VECTOR, vector_options=VectorOptions(
        VectorDataType.VD_FLOAT_32, VectorMetricType.VM_COSINE, 1024)),
    FieldSchema("text", FieldType.TEXT, index=True, store=True),
    FieldSchema("tenant_id", FieldType.KEYWORD, index=True, store=True),
    FieldSchema("document_id", FieldType.KEYWORD, index=True, store=True),
    FieldSchema("embedding_version", FieldType.KEYWORD, index=True, store=True),
])
tablestore_client.create_search_index("knowledge", "knowledge-search", index_meta)
```
**OSS Vectors** 资源层次更直接：先建 Vector Bucket，再建 Vector Index，向量维度和距离度量在创建 Index 时确定。向量维度和距离度量必须与 Embedding 模型保持一致；模型变化导致维度/向量空间变化时，通常需建新索引并重新生成向量，再切换查询版本。

### 准备向量数据

写入前先对文档/图片/视频解析和切分，再经 Embedding 模型生成向量。记录除向量还保存文本、租户、原始内容标识、模型版本（后续过滤、版本切换、原始内容回查依赖这些字段）：
```python
text = parse_and_split(source)
vector = embedding_model.encode(text)
record = {"id": "chunk-001", "vector": vector, "text": text,
          "tenant_id": "tenant-a", "document_id": "document-001",
          "embedding_version": "model-v1"}
```
tenant_id 限制查询范围，document_id 定位原始内容，embedding_version 区分不同模型生成的向量。

### Tablestore SearchIndex 写入与查询

向量、文本、业务属性作为同一行写入数据表，多元索引为已配置字段建索引。纯向量检索时指定向量字段、查询向量、TopK，服务通过磁盘图索引产生候选并按相似度返回。混合查询把条件放入同一次查询：先限定租户和模型版本，再匹配文本关键词，并在符合条件的数据中执行向量检索。filter 参与向量候选生成可先缩小范围再近邻搜索；若把条件放向量 TopK 之后执行，大量候选被过滤时最终结果可能不足。

### OSS Vectors 写入与查询

原始文档/图片/视频存普通 OSS Bucket，向量和元数据写 Vector Index，向量记录通过 object_key 关联原始对象，查询结果不需保存完整内容也能在召回后读原文/媒体。查询用同一模型生成查询向量并按租户、模型版本过滤，return_metadata 返回原始对象位置等业务信息；应用根据 object_key 读取原始内容再把相关片段交给 Agent。

### 实际踩坑

- 写入和查询必须用相同 Embedding 模型、向量维度、距离度量，否则向量空间语义关系对不上
- 换模型用版本字段隔离新旧向量，等索引重建完成后再切换查询版本
- 多租户每次查询都带租户条件，少一次可能返回跨租户结果
- 向量记录保留原始数据标识，不然检索到内容却不知来自哪份文档/图片/视频
- 召回率和资源消耗受 TopK、过滤条件和数据分布共同影响，文档写的和实际跑的有差距，必须用真实数据验证。尤其 OSS Vectors 的标量过滤在结果阶段执行，若过滤筛掉大部分结果，TopK 设再大最终返回数量也可能很少

## 写在最后

向量存储解决的核心问题是语义检索——从持续增长的数据中找出与当前任务相关的内容。要让检索结果真正可用，需同时处理好几件事：向量要和文本、元数据一起组织；查询链路要正确组合语义、关键词、业务条件；索引要在召回率、延迟、成本间取舍。这些选择互相影响，不存在统一最优方案，只能从具体工作负载出发。

向量存储要打通的最后一公里，不是算法本身再快多少，而是让散落各处的数据真正被 Agent 用得上。选型标准也在变：过去主要看检索能力和数据规模，Agent 应用让资源交付方式也成了绕不开的维度。当大量数据空间由应用动态创建、负载模式不可预测时，固定实例不再是默认答案。这个趋势再往前走一步，索引算法和容量管理会逐步被云服务吸收，开发者的注意力回到数据本身：怎么组织、怎么关联、怎么让 Agent 真正用得上。最终拼的不是谁选了更好的索引，而是谁的数据组织得更清楚。
