一笔供应商付款卡在了财务。准入面板却一片绿色：材料收齐，合规、信息安全和合同审批全部通过。临到付款，财务才发现品牌、签约主体和收款主体没对上。运行记录里节点一个没少。系统却把品牌名和法定主体合成了同一个实体，后面的 Agent 又把这条待核验关系带进合同和付款报告。

Agent Loop 证明任务走完了，Graph Engineering 还要回答多个 Agent 交接的事实能不能信。事实怎么建立、发布，错了又怎么收回，是另一张图要管的事。

## 两张图，管的是两件事

**执行图**：节点是一项项工作，边表示依赖、分支和状态变化。最简单的 Agent Loop 就是模型调用工具、读取结果，再决定是否继续的一张有向循环图。

**知识图谱/事实图**：节点是实体（品牌、公司、账户、合同），边表示事实关系（"品牌 A 的法定主体是公司 B"）。关心这些关系由什么证据支持，又在哪段时间内有效。

执行图管工作怎么走，知识图谱管事实怎么连。两条边都叫 edge，工程含义相差很远。"合规通过后进入合同审批"是一条控制关系；"品牌 A 的法定主体是公司 B"是一条事实关系。

## "共享记忆"里装了三种东西

| 类型 | 记录什么 | 由谁管理 |
|------|---------|---------|
| 运行状态 | 一次任务走到哪了 (run_id, node_id, attempt) | 编排器和运行状态库 |
| 事实状态 | 跨任务可复用的事实 (实体、关系、来源、有效时间) | 事实服务 |
| 环境与证据状态 | 当时依据什么得出结论 (commit, 沙箱快照, 审批记录) | 运行环境和审计系统 |

checkpoint 适合恢复一次运行。拿它当长期知识，中间结论过期后还会被继续使用。知识图谱适合保存跨任务事实，拿它代替运行状态，又回答不了工具是否执行成功。

## 从主张到事实的流水线

Agent 从材料里读到的只能先算一条**候选主张**（claim），经过实体消解、规则校验或人工确认后，变成带版本和有效时间的**规范事实**。

Claim 设计示例：
- claim_id, tenant_id, schema_version
- subject_mention, predicate, object_mention (保留原始名称)
- source_uri, source_span (原文片段引用)
- observed_at, valid_from (观察时间≠事实生效时间)
- status: "candidate"
- producer_run_id

从主张到事实的链：证据 → 候选主张 → 实体消解与校验 → 规范事实 → 按版本查询

## 最小 Graph Engineering 架构

- 编排器和运行状态库：管理 workflow_runs, node_attempts, checkpoint
- 事实服务：管理候选主张、消解校验和规范事实
- 检索网关：查询时把来源、版本和有效时间一并带回
- 四个接口：submit_claim(), query_facts(), publish_fact(), retract_fact()

起步建议用 PostgreSQL（claims/entities/relations/evidence 几张表），等需要不定长路径遍历再评估图数据库。

## 四件事必须盯住

1. 时间和版本：已发布事实不能静默覆盖
2. 幂等：同一来源被任务重放时，幂等键挡住重复主张
3. 权限：遍历时就校验租户、关系类型和字段权限
4. 撤回：事实失效后发出 fact.retracted 事件

## 何时增加知识图谱（4 个信号）

1. 同一实体在不同文档里有多个名称
2. 回答经常需要跨两跳以上关系
3. 关系要长期积累并保留来源和有效时间
4. 多个 Agent 重复生产、校验和消费同一批事实

## 试跑方案

1. 执行图只覆盖一个工作流（如供应商准入）
2. 事实层支持候选主张、规范实体、来源和状态
3. 从脱敏历史记录选 20-50 个真实问题作为评测集
4. 每次回答带回引用的事实版本与原文片段
5. 人为制造中断、重复写入、实体误合并和事实撤回观察行为
