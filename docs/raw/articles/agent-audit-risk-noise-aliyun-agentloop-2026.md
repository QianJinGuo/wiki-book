# Agent 审计：从海量噪音中捞出真风险

## 摘要

阿里云 AgentLoop（Agent 观测与优化平台）审计视角分享：Coding Agent 的能力越强，工作空间就越不只是编辑器，而是代码仓库、模型上下文、工具调用、外部授权和企业内部数据共同组成的**一条执行链路**。Agent 审计的目标不是风吹草动就告警，而是让真正进入高危队列的风险更准——单点命中要能回到上下文里被解释，风险事件要能说明越过了哪条边界、影响了哪些对象、证据在哪里、下一步怎么处置。

## 审计核心链路

**行为事实统一采集 → 规则局部命中（低保真信号）→ 上下文语义判定（高保真风险事件）→ 落到可定位治理的对象**

1. **完整事实底座**：LoongSuite Pilot 把不同 Coding Agent 和 Agent 应用里的会话、轮次、模型请求、模型回复、工具调用、工具结果统一采集——不是一组孤立日志，而是一条**能回放的行为链**。先看全，再判断准。
2. **低保真信号**：模型输入出现疑似 AK、模型回复出现疑似 AK、工具参数出现疑似敏感片段——局部事实上的命中，值得记录但不应直接变高危（否则安全同学看到一堆"可能有问题"的红点）。
3. **高保真事件**：上下文语义判定——同一凭证出现在模型输出和外部上传目标中，风险性质就变了：不再是"疑似 AK 泄漏"，而是具体凭证在 Agent 链路上的实际扩散。
4. **原则**：低保真信号可以多、事实尽量全，但推到高危位置的事件必须能解释为什么值得优先处理。

## 审计产品设计要点

- **运营优先级**：概览页先回答"今天该看什么"——"影响面最大风险"（如数据泄漏：密钥/阿里云凭证已影响 6 个应用）与"恶化最快风险"并列首屏
- **边界判断**：同样是阿里云凭证，位置不同风险边界不同——"敏感数据提交到模型 38 次" vs "模型回复泄露敏感数据 43 次"：前者查上下文拼接/输入侧，后者查输出过滤/日志落盘/凭证轮换
- **凭证聚合下钻**：同一 AK 反复泄漏（→ 轮换 + 追来源） vs 多个 AK 分散泄漏（→ 上下文拼接/输出过滤存在系统性问题）——先按"风险类型+应用"聚类，再聚合具体凭证值
- **一键定位证据**：风险详情页显示应用、严重性、发现 ID、证据摘要、命中字段、关联事件；右侧会话视图直接跳到风险事件并**高亮模型输出中的 AK**
- **实体调查（AK 反查影响面）**：从对象出发而非从会话出发——Secret/PII/应用/主机/容器/用户/来源 IP/Tool 变成可调用的实体；某个 LTA... 凭证关联 loongsuite-pilot-qoder 应用、qoder 工具等；同一 AK 关联多应用/主机/用户/工具 → 扩大排查范围查凭证来源

## 安全背景

- openai/codex#2847：.env、.pem、.aws/、.ssh/ 等敏感路径应如何被更确定地排除
- BeyondTrust：Codex branch name command injection 漏洞可导致 GitHub Token 沦陷
- 原则：**准确不等于没有边界**——降低误报不代表没有漏报，规则不可能一次写完；允许底层保留足够多低保真信号，同时让高危队列里的事件更能被相信、被复核、被处置

## 要点提炼

- Agent 审计 = 先解决"事实底座"（完整可回放行为链），再谈判断准
- 两级信号设计：低保真（局部命中，多而全）+ 高保真（上下文语义判定，可解释可复核）
- 处置导向：风险要落到"可治理对象"（凭证/应用/用户/主机），提供调查入口而非告警列表
