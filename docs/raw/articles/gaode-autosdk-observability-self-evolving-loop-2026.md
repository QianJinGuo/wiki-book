# 高德汽车工程 AI Native 演进实录｜AutoSDK AI Coding 可观测与自进化闭环的构建

> 高德汽车业务中心 AutoSDK AI Coding 系列「进化篇」：前三篇回答了链路贯通（架构篇）、AI 理解业务（知识篇）、守护质量（质量篇），本文补齐横向机制——以可观测驱动、持续自进化的 Loop Engineering。阶段成效：缺陷漏出下降约 73%，代码采纳率 84%，API 规范遵守率 80%。

## 为什么"单次跑好"远远不够
企业级交付对链路的要求不止"单次跑好"，还要"越跑越好"：上一次质检打回的问题，下一次任务能否自动避开；历史总结出的经验能否固化为下一次的默认约束；流程低效的环节能否被度量、被定位、被优化。人类研发组织有记忆，踩过的坑会变成团队免疫力；AI 系统默认没有记忆，没有机制沉淀教训，同一个坑就会反复掉。防线守的是这一次，进化补的是下一次。构建自进化闭环是 AI Coding 进入企业级生产后必须补上的一环。

## 可观测先行：进化需要证据，不是直觉
AutoSDK 的多阶段流水线并非单 Agent 顺序处理，而是多 Agent 与多工具的动态协作，执行过程是复杂状态机。输出偏离预期时，没有清晰的链路追踪，执行过程不可见，问题排查只能靠猜。凭感觉调 prompt、拍脑袋加规则，没有数据的进化是玄学。可观测是进化的地基。

现实约束：AI Coding 运行在 IDE，无法直接接入第三方可观测 SDK；企业级数据安全要求观测基础设施自建自控；AutoSDK 不止观测单次会话内调用链，还包括跨会话、跨 Agent 的"工程过程"（编排断点、上下文准确性）。现成方案搬不动，观测必须原生长在链路里。落地分两步：先采集，再组织。

### 采集：三源融合，互为补充
- **Hook 埋点**：在关键生命周期节点触发（任务开始、启动子 Agent、Tool 调用前后、LLM 调用前后、任务结束、异常发生），捕获关键事件与字段。Hook 提供实时事件。
- **本地会话转录文件**：记录执行过程完整上下文（用户输入、Agent 思考过程、计划变更、Tool 入参与返回、LLM Prompt、最终输出），解析后成为结构化执行数据。转录文件提供完整决策过程。
- **本地数据库**：通过 IDE 内置 SQLite 数据库，获取任务元数据与跨 Agent 关联关系，让分属不同会话的执行重新归拢到同一任务。本地数据库提供任务级关联。

三源融合，完整执行过程才能被还原。

### 组织：从观测目标到三支柱实现
观测覆盖三个层面：任务层（这次任务成没成，看结果）、能力层（Agent 与模型行为是否在劣化，看趋势）、机制层（质检机制拦没拦住，看过程）。结果告诉你"发生了什么"，趋势告诉你"正在往哪里去"，过程告诉你"为什么发生"。

沿用 Metrics、Trace、Logs 三支柱框架，但在 AI Coding 场景扩展语义：
- **Metrics 层（可度量，看效果和趋势）**：请求量/错误率/延迟这类传统指标只回答"快不快、错没错"，回答不了"值不值"——Token 消耗在哪里、哪一步绕弯路。Metrics 语义扩展为效率、质量、效果各自有答案，闭环中每次改进才有前后对比依据。
- **Trace 层（可见，看清过程）**：传统 Trace 记录服务间调用（谁调用谁），但 Agent 编排问题几乎不发生在单次调用里——最终产出偏差的根因可能在好几个阶段之前（探索产出不完整传导进设计，设计再传导进编码）。Trace 必须从调用链扩展为因果链：每个阶段的决策与交接都是执行树上的节点，产出出现偏差时沿树回溯到根。
- **Logs 层（可归因，用证据说话）**：归因要落到具体——哪个 Agent 在哪个阶段调用哪个工具失败、当时的上下文是什么。Logs 从文本扩展为结构化、有语义的行为记录，能按阶段/Agent/工具检索，与 Trace、Metrics 互为印证。

排查动作变成固定节奏：Metrics 先暴露异常 → Trace 再定位链路 → Logs 最后拿出证据。

链路黑盒变透明后第一批暴露的问题，往往不是模型能力问题，而是流程编排问题：①上下文膨胀——调研阶段消耗大量上下文和 Token，关键约束没稳定传递到设计阶段；②阶段交接不完整——上游产物没有明确接口兼容性或跨仓依赖，下游编码基于不完整输入继续执行；③角色边界越权——主 Agent 越过子 Agent 直接执行具体工作项，专职 Agent 的设计/编码/验证职责被绕开。三类问题共同点：不是简单的"模型答错"，而是链路中的流程、上下文或角色边界没有被正确组织。

## 自进化闭环：让流程长出记忆
可观测让问题被看见，但看见不等于进化。AutoSDK 基于 Loop Engineering 建立面向系统改进的自进化闭环——观测、归因、干预、验证四环节闭合。可观测是闭环输入源：Metrics 提供异常信号，Trace 提供因果链路，Logs 提供归因证据，让每轮改进建立在结构化执行事实上。

验证是闭环的关键，也是最容易被省略的一环。质量门禁有明确过/不过、代码能编译用例能跑，天然就是裁判；而"进化"没有天然裁判——改了一条规则，怎么知道是变好了还是把显性问题换成隐性问题？不受验证的进化，和没有测试的代码一样危险。验证设计三个维度：跟谁比（优化前 N 天 vs 优化后 N 天）；看什么（该类问题发生率、一次通过率、阶段耗时、Skill 召回率）；怎么看（不仅看目标指标是否下降，还要看是否引入新问题类型或误报）。进化的目标是收敛问题，不是堆砌控制——一条新规则拦住目标问题却制造一批新误报，在数据上会原形毕露。自进化闭环核心一句话：让每一次改进都经过识别、回灌和验证。

### 案例：一次质检打回如何变成默认约束
AutoSDK 的质检 Agent 持续检查意图理解、领域设计、开发实现和验证结果，对不符合要求的产出打回。一次真实闭环：观测（Metrics 层发现质检通过率未达预期，识别进化目标）→ 归因（AI 在离散打回中识别重复模式，聚类定位根因：问题集中在"设计→编码"阶段，设计文档缺少接口兼容性检查项）→ 干预（系统生成优化建议，人工评审合理性落地，拒绝则记录理由避免重复建议）→ 验证（观察期内对比打回率和一次通过率，确认问题减少且未引入新异常，数据稳定改善后闭环闭合）。

阶段效果：效率优化（调研 Agent 支持多实例并行，调研阶段平均耗时降低约 50%，整体流程从 1.5h 缩至 1h 以内）；上下文治理（主 Agent 平均上下文占用从 70% 降至 50%）；角色边界收敛（新增硬约束明确主 Agent 与设计/编码/验证子 Agent 职责边界）；质检数据稳定沉淀（四大质检门禁通过率提升 50%，数据进入闭环成为后续规则/Skill/流程优化输入）。

## 性能优化：从人工试错到数据验证的闭环
当效果评价本身可量化（常驻内存、启动耗时、CPU 占用，数字本身就是裁判），闭环有条件再往前一步：从"系统出建议、人来拍板"走向"系统自主迭代、人做最终决策"。性能优化被选为检验 Loop Engineering 上限的试验场。传统模式一个优化候选从选点到验证需半天，大多数候选无效——问题不在工程师判断力，而在验证代价太高，能试的候选数量受限。

基于 Loop Engineering 构建性能优化闭环：输入一个 APK 和一个优化目标（如"native 常驻内存降至 X MB 以下"），输出经过实测验证的优化结论。整条流水线分为前置阶段（执行一次）和循环体（每个候选重复），是链条最长的一条闭环——向内覆盖 AI Coding 全链路，向外纳入自动性能测试、数据采集、编译出包与集成验证。

关键机制：
- **AI 与确定性脚本的分工**：编译、采集、符号化、聚类由确定性脚本完成（可重复可追溯）；判断可行性、探索代码结构、设计优化方案、实施改码由 AI 子会话完成（需理解推理）。关键决策点"这个候选到底能不能优化"由 AI 产出判断字段后，Python 代码做硬逻辑拍板，不依赖 AI 自我评估。改码与验证由两个互相看不到对方过程的独立 agent 分别完成，避免自我确认偏差。
- **代码管理**：每个候选改码前对源码所有子仓打快照。验证通过则 commit 保留改动进入下一轮，验证无效或回归则回滚到快照状态。代码始终干净、改动可追溯，每轮 delta 可归因到单一优化点。
- **安全兜底**：设备掉线、连续多轮无效果、达到轮次上限，任一条件触发自动停止，不会无限空转。任何步骤中断后重跑，已完成步骤自动跳过。
- **自进化**：每轮结果反哺系统——深判不通过的原因回灌为浅判规则（下次同类方向直接跳过）；验证有效的候选沉淀为优化模式知识（后续浅判推荐更精准）；验证阶段发现的用例盲区反馈回测试场景（减少漏验）。系统越跑越准。

阶段效果：某版本 native 内存场景一轮运行中，浅判淘汰三分之二无效方向，进入循环体的 11 个候选里 2 个经实测验证有效——这些方向在人工模式下大多不会被尝试。系统交付的不是"AI 认为可以优化"，而是"改了、跑了、实测数据说话"的验证结论。边界明确：不自动合入生产代码，不替代工程师的架构设计决策；角色是穷举和验证，生产级实现由工程师基于验证结论重新设计。

## 结语
可观测和自进化闭环改变两件事：问题定位不再依赖人工回翻对话，可沿 Metrics、Trace、Logs 回到具体执行节点；改进不再依赖临时复盘，分散在质检打回、人工评审中的问题转化为规则、Skill 和流程上的具体改进。自进化不是一次性大改造，而是围绕真实执行数据持续推进的小步迭代。系列四篇主线：架构篇（链路能否贯通，多 Agent 全链路流水线）、知识篇（能否做对，体系化业务知识）、质量篇（能否稳定交付，Harness 三道防线）、进化篇（能否持续改进，可观测+自进化闭环）。前三篇建设纵向能力，进化篇补上横向机制——防线守住底线，闭环抬高上限。进化不替代工程师判断，最终决策始终在人手里。
