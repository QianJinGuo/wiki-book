前段时间我干了件挺无聊的事：把同一个开发任务，让 AI 连着干了 20 遍。

不是闲的。我一直有个疑问——大家都在说自进化 Agent「越用越强」，可到底强在哪、能不能量化？是模型偷偷变聪明了，还是它真的把「做法」记住了？

光看文档没用，我决定自己拿 Hermes Agent 跑一次实验，把过程和数字全记下来。

结论先摆这儿：跑到第 10 次左右，同样一个活，它从第一次的 12 步、26 分钟，稳定压到了 5 步、11 分钟，一次通过率从五成拉到九成。而模型一次都没换过。

这篇就把这 20 轮的完整过程、踩的坑、以及最后的数据，原原本本讲一遍。

## 先说清楚：我到底在测什么

要测「越用越快」，最怕的就是变量太多——今天心情好任务简单，明天任务难，那降下来的步骤到底算谁的功劳？

所以我把实验设计得很死板：任务固定，只看它进不进化。

我选的活是前端最烦、又最常见的那种：给一个中后台项目加一个标准 CRUD 页面。列表 + 搜索栏 + 分页 + 新增/编辑弹窗，接口对接、表单校验、loading 和报错处理都要有。

这种活的特点是——结构高度雷同，但每次又不完全一样（字段不同、接口不同）。正好适合观察：AI 能不能把「不变的那部分做法」沉淀下来。

然后我只盯 4 个指标：

- 步骤数：完成任务它一共动了多少步（调工具、写文件、改文件算一步）
- 耗时：从下需求到我验收通过，实际墙上时钟时间
- Token 消耗：单轮总消耗
- 一次通过率：第一版交出来我不用打回、直接能用的比例

模型全程用同一个（我用的 Claude 家的接口挂 main_model），温度、系统提示词都不动。工作目录单开一个 ~/hermes-crud-lab/，专门看它往磁盘写的 MEMORY.md、SKILL.md。

## 第 1 次：从零摸索，惨不忍睹

第一轮我给的需求很简单一句话：在 admin 项目里加一个「优惠券管理」页面，列表带搜索和分页，支持新增和编辑。

Hermes 接到之后的表现，说实话跟一个第一天来的实习生差不多。它先满项目里翻，找现有的页面参考，读了路由配置，读了 request 封装，又读了一个已有的列表页想抄结构……光「搞清楚这个项目怎么写页面」就花了一半时间。

这一轮我数了下，它一共走了 12 步，耗时约 26 分钟，中间还问了我两个问题（分页组件用项目里哪个、表单校验用什么库）。交出来的第一版，弹窗里的表单校验漏了必填，我打回改了一次。

一次通过？没有。

但重点在后面。任务结束时，Hermes 的 Review Agent 在后台默默做了一次复盘，往 SKILL.md 里写了一条东西。我打开一看，大概长这样：

```markdown
## Skill: admin 项目新增 CRUD 页面

### 适用场景
在 admin 中后台项目里新增一个"列表+搜索+分页+新增/编辑"页面

### 前置约定（从本项目实测得出）
- 页面放在 src/pages/{module}/index.tsx
- 列表用 ProTable，分页参数是 current/pageSize
- 请求统一走 src/utils/request.ts 的 get/post
- 表单校验用 antd 的 Form rules，必填项必须显式加 required

### 标准步骤
1. 在 routes 里注册路由
2. 复制 ProTable 列表骨架，替换 columns
3. 接搜索表单，参数拼到 request
4. 写新增/编辑 Modal，复用同一个 Form
5. 补 rules，尤其必填项

### 已知坑
- 编辑回填时要 form.setFieldsValue，别忘了 Modal 打开时机
```

看到这条我就知道，这实验有戏了。它把第一次踩的那个「必填校验漏了」的坑，直接写进了「已知坑」。

## 第 2 到 4 次：开始有「谱」了

第二轮我换了个模块——「运营位管理」，需求措辞照旧。

这次明显不一样。Hermes 一开始没有到处乱翻，而是先读了自己的 SKILL.md，找到那条 CRUD 的 Skill，然后基本照着「标准步骤」走。翻项目的时间几乎省掉了。

第 2 次 9 步，第 3 次 7 步，第 4 次也是 7 步。耗时肉眼可见地往下掉。

不过这几轮它还没「完全信任」自己的 Skill——每一步做完还会回头确认一下项目里是不是真这么写。这个谨慎我觉得是对的，毕竟 Skill 才刚沉淀，样本太少。

## 第 5 次：第一次真正「照着做」

到第 5 轮，转折点来了。

这一次 Hermes 几乎是「照单抓药」：读 Skill → 按 5 个标准步骤直接生成文件 → 只在最后校验了一遍。6 步，耗时压到 13 分钟左右，而且第一版就通过了，我没打回。

那一刻的感觉挺微妙的：它不是变聪明了，是它不用再重新思考「这个项目该怎么写页面」这件事了。这个认知第一次被显式地保存下来、又被稳定地取用。

## 第 8 次：踩了个坑，但它自己补上了

本来以为会一路平下去，结果第 8 轮出了岔子。

那次的模块接口返回结构变了——分页字段不是 current/pageSize，而是后端新换的 pageNum/pageSize。Hermes 照着老 Skill 做，结果分页翻页翻不动。它自己跑了一遍发现列表不对，回头排查，多花了两步定位到分页参数。

这一轮步骤反弹到了 7 步（曲线上那个小凸起就是它）。

但真正让我觉得这套东西「活」的，是任务结束后 Review Agent 的动作——它没有新建一条 Skill，而是给原来那条 CRUD Skill 打了个补丁：

```markdown
### 已知坑（更新）
- 分页参数注意区分：老接口 current/pageSize，
  新接口可能是 pageNum/pageSize，动手前先看接口返回的字段名
```

这就是我最想验证的一点：它不光会「学」，还会「改」。一次失败没有让它下次继续踩，而是变成了 Skill 里的一行防呆提示。

## 第 10 次以后：进入稳态

从第 10 次开始，曲线基本压平了，稳定在 5 步上下。

流程固定成这样：读 Skill → 确认接口字段（这是第 8 次那个坑换来的习惯）→ 生成页面 → 自检 → 交付。中后几轮我故意换了不同复杂度的模块，步骤也没怎么波动，说明它抓到的是「做法」，不是「背答案」。

一次通过率也上来了——后 10 轮里有 9 轮第一版直接可用。

## 20 轮跑完，数字长这样

把整个过程摊开，第 1 次和稳定后（第 10 次起的平均）对比：

- 步骤数：12 → 5，降了约 58%
- 耗时：约 26 分钟 → 约 11 分钟，降了约 58%
- Token 消耗：稳定后比第一次降了约 40%（省的主要是「满项目翻找、反复读上下文」那部分）
- 一次通过率：50% → 90%

我特别想强调 Token 这一项。很多人以为自学习会让上下文越堆越大、越跑越贵，正好相反——因为它不用每次重新「勘探」项目，前面那一大坨探索性的读取全省了。省下来的不是模型钱，是每一次从零摸索的时间和 Token。

## 几个踩坑，给想自己试的人

第一，别指望第一次就快。前 4 轮它其实比你自己手写还慢。自进化的价值在「同类任务的第 N 次」，任务如果永远不重样，这套东西体现不出价值。

第二，Skill 会脏，得管。我这 20 轮里有一次它沉淀了一条过于具体的 Skill（把某个模块的字段名都写死了），差点污染后面的任务。好在 Review 那层有个「泛化检查」，把它收敛成了通用做法。真上生产，Skill 的质量门禁不能省。

第三，接口这种「会变的外部约定」最容易翻车。第 8 次那个坑就是典型。解决办法不是让它记死，而是让 Skill 记住「动手前先确认」这个动作本身。

## 聊聊我的判断

跑完这 20 轮，我对「自进化 Agent」祛魅了不少，也更信了几分。

祛魅在于：它没有什么玄学，本质就是把「一次任务里学到的做法」结构化地存下来，下次优先复用，出错了就打补丁。Memory 记事实、Skill 记做法、Review 负责判断什么值得存——就这三件事。

更信的地方在于：这条曲线是真的会往下走的。只要你的工作里有「结构雷同、细节不同」的重复任务——中后台页面、接口联调、周报整理、issue 分类——它就能把你每次重新摸索的成本一点点吃掉。

说白了，普通 AI 是每次都请一个新实习生，干完就走；自进化 Agent 是同一个实习生，你带一次它记一次，第十次已经比你还熟门路。

对我们做工程的人来说，这里最值钱的一句话是：别再纠结模型够不够强了，先想想你有没有给它一个「把经验留下来」的地方。
