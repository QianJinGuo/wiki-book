# Graph Engineering 框架对比：LangGraph、AutoGen、Google ADK

> 作者：小智，模智空间（公众号）
> Graph Engineering（图工程）走红后，澄清它与 LangGraph 的关系，并对三大主流实现框架（LangGraph / AutoGen / Google ADK）做横向对比与选型建议。

## 先搞懂核心：什么是图工程

图工程是设计思想，LangGraph 只是实现它的工具之一——如同"造房子"是需求，"钢筋混凝土"只是实现需求的一种材料。除 LangGraph 外，微软 AutoGen、Google ADK 同样是图工程的实现工具。

图工程解决什么问题：可以把复杂 AI 任务类比为一个公司项目。若仅靠一个"超级 AI"完成所有环节，相当于让一个人同时负责市场、研发、财务与客服，结果往往是每项都涉及却无一精通。图工程的核心思想是"专人专事"：把庞大任务拆解为多个职责明确的小型节点，每个节点是一个具备特定技能的 Agent 或明确的工作步骤。

三个基本概念：
- **节点（Nodes）**：如"研究员"节点负责搜集资料、"写作者"节点负责撰写文案、"审核员"节点负责把关质量
- **边（Edges）**：定义工作流路径，任务如何从一个节点流向另一个节点，可以是顺序执行、条件分支（合格就发布，不合格返回修改）、并行处理（同时让两个编辑校对）
- **共享状态（Shared State）**：所有节点共享同一份工作状态，含任务进度、中间产物与最终结果，确保信息在节点间无缝传递

一个单独的 Loop 其实就是一个最小的图：一个节点加一条指回自身的边。当任务需要协调多个专业 Agent 协同工作、流程复杂、存在分支与循环时，图工程是合适选择；若任务本身简单、重复，一个 Loop 便已足够，强行引入图工程反而徒增复杂性。

## 三大图工程框架对比

### 1. LangGraph

出自 LangChain 团队，官方定位是低层级编排框架和运行时，用于构建、管理和部署长时运行、有状态的 Agent。**low-level 是 LangGraph 的关键词**：不隐藏图的结构，状态、节点、边（包括运行时分流的条件边）均由开发者显式定义，适合对流程有极致控制欲、想亲手搭建每个流程细节的开发者。

核心优势：
- **检查点与持久化**：最具代表性能力。工作流每一步状态自动保存，若程序在第 5 步意外崩溃可从断点无缝恢复，无需从头开始，对运行数小时乃至数天的长任务至关重要
- **人机协同**：可在工作流关键节点设置暂停，由人工介入审核或修改状态后继续运行，为需要人工审批的敏感业务提供便利

以 Python 为主（另有 JS/TS 版本）。虽然由 LangChain 团队开发，但明确不依赖 LangChain，可单独使用。

### 2. 微软 AutoGen 的 GraphFlow

AutoGen 从另一角度切入：多智能体对话。GraphFlow 在官方文档中描述为"遵循有向图（DiGraph）来控制 Agent 之间执行流的团队"，支持顺序、并行、条件、循环等行为，适合已习惯以多 Agent 对话方式解决问题的开发者。

核心优势：
- **基于对话的图**：把"图"的概念融入 Agent 对话。可指定"写作 Agent"说完必须由"审核 Agent"接话，审核通过后流程结束，否则循环回去修改，让对话式 AI 变得可控、可预测
- **图模式齐全**：顺序、并行、条件分支、循环，所有经典图模式都支持

AutoGen 属于 Python 生态。注意 GraphFlow 目前仍是实验性功能，API 未来可能变动；微软正将其整合进更宏大的微软 Agent 框架中，需关注其未来发展方向。

### 3. Google ADK

Agent Development Kit 定位在生产环境中构建稳定、可扩展的 AI 应用，核心理念是"构建生产级 Agent，而非原型"，适合需要在 Google Cloud 部署、需要多语言支持、或需要与其他系统及供应商 Agent 协作的企业级项目。

核心优势：
- **多语言支持**：与 LangGraph/AutoGen 主要聚焦 Python 不同，ADK 提供 Python、TypeScript/JS、Go、Java、Kotlin 等多种语言 SDK，对大型技术团队友好
- **内置 A2A 协议**：A2A（Agent2Agent）是开放的跨平台 Agent 通信标准，如同 AI 界的 HTTP 协议，让谷歌 Agent 可把任务委托给用微软工具、在亚马逊云上运行的 Agent，无需关心对方内部实现。2025 年 6 月 Google 把 A2A 捐给 Linux Foundation，如今由含 AWS、Cisco、Google、IBM Research、Microsoft、Salesforce、SAP、ServiceNow 的技术指导委员会治理

若项目追求企业级稳定性、多语言支持，并需构建跨越不同平台与供应商的开放 AI 协作网络，Google ADK + A2A 是合适选择。

## 你真的需要框架吗？

从本质上说，一张"图"就是一个保存状态的字典、一组读写该字典的函数（节点）、以及一个决定下一个执行对象的 if-else 路由器（边）。若工作流仅有三五个步骤，用纯代码手写反而比引入重量级框架更清晰、更轻量。

框架的价值不在于提供"图"本身，而是围绕"图"的一系列基础设施：
- **状态管理与检查点**：节点 7 出错了，不用重新跑前 6 个
- **可恢复性与持久化**：长任务扛得过重启，能接着上次的位置继续
- **可观测性**：能清晰看到每个节点的输入、输出和决策过程，方便调试
- **跨供应商委托**：通过 A2A 这样的标准协议将任务无缝交给外部 Agent

这才是"自建还是引入"的真正分界。合理决策路径：
1. 先问自己：这个任务真的需要一个图吗？还是一个循环就够了？
2. 从简开始：对小规模任务，先用纯代码手写一个图来跑通流程
3. 按需引入：当手写代码在状态持久化、调试监控、跨系统协作等方面开始让人感到阵痛时，再根据首要痛点选择最适合的框架

## 选型速查清单

安装任何框架之前，对照以下六条：
1. **这到底是不是一张图？** 单一任务 + 单一明确验证器 → 留在 Loop；出现多专业分工、并行分支、或分步工具 → 才考虑图
2. **能不能先手写？** 只有几个节点、每条边都看得懂 → 先用纯代码写，上线后再评估
3. **需不需要持久性？** 丢一次长任务很痛 → 需要检查点 → LangGraph
4. **是不是在编排会话式 Agent？** Agent 互相交谈、想要有向图式发言控制 → AutoGen GraphFlow
5. **要不要规模化、多语言、跨厂商交接？** 生产级目标、非 Python 技术栈、或 Agent 要跨系统委派 → Google ADK + A2A
6. **是不是先选了产品、再反推设计？** 如果先定了框架再反向硬套方案，那就推倒重来
