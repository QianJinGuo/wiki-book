# 高德 Push 机制智能化演进｜从静态阈值到 Agent 感知投放

> 高德技术（信息业务中心）第一方实践：把消息触达系统发送门控的"收/放"交给 LLM Agent——由大模型承担态势理解与方向性决策，由确定性代码承担数值计算与安全约束。记录从概念验证到线上稳定运行的三代架构演进（v1→v2→v3）及工程方法论。

## 一、该触达是否值得执行？
消息触达系统决策层需在每次下发前完成准入判断：该触达是否值得执行。本质是资源约束下的价值最大化问题——曝光是有限资源，透支损害通道长期触达能力；系统需在配额约束下把曝光分配给期望价值最高的触达。难点在于序列性与动态性：每次"收/放"都改变后续资源状态，当前最优决策依赖对线上状态的实时感知与长期收益权衡；环境持续变化，离线定型的策略难以长期有效。这层调控真正需要的是**在线感知与自适应决策能力**。

## 二、AI 时代，触达决策层能做什么？
端外通知决策通常拆成 Who（发给谁）/When（什么时候发）/What（发哪条），但之上还有一个更底层的决策——**Whether（要不要发）**，即发送门控。它与广告系统 Pacing & Budget Control、推荐系统 Exposure Allocation 是同一类问题——有限资源下的价值最大化。

工业界主流解法是"离线建模 + 在线规则执行"（离线训 CTR 模型、算门控曲线，线上固定反馈控制逻辑执行）。这套范式足够稳定但有一个根本假设——**环境是平稳的**。现实中流量分布/消息质量/用户活跃节奏都随节假日和天气波动，任何因素变化都可能让离线参数失效。传统应对是"人盯+人调"，本质把环境感知和自适应留给人类。

能不能把感知、分析、决策、执行串成一个闭环，让 Agent 直接接管发送门控——不是辅助人调参数，而是成为调控主体，实时感知线上变化、判断收还是放、自主执行调整、从结果迭代学习？这正是 Agent 最擅长的事。

## 三、大模型能给决策提供什么能力？
决策是序列决策，LLM 是 next-token 概率生成。学界已有理论回答：**Decision Transformer**（Chen et al., NeurIPS 2021）证明把 (状态, 动作, 回报) 三元组编码为 token 序列、用自回归建模条件概率 P(action | desired_return, state_history) 时，模型可直接输出策略——不需要估值函数和 Bellman 收敛；序列决策最优解和条件概率生成数学上相通。广告自动出价 AIGB（Guo et al., KDD 2024）把这一思想落到"预算约束下选择最优出价序列"做成条件轨迹生成，已大规模商用。

但当前阶段并不直接走自回归轨迹生成：轨迹生成需要大量高质量 [state, action, reward] 离线数据预训练，发送门控状态空间/奖励信号还在早期。当前定位是演进第一步：让 Agent 具备环境感知和简单调控能力（看实时状态、基于规则和简单推理做收/放、从执行结果拿反馈）——跨过"从完全静态的离线门控到具备在线自适应"，是整条演进路线的地基。

## 四、三代系统演进
### v1｜单 Agent 会话
设计：持久会话 + 定时任务发消息，让 Agent"聊天式"看数据、做判断、改门控。
**做对了什么**：验证大模型确实能理解流量调控语义——给实验组/对照组发送量、点击量、点击率，能正确判断"实验组好于对照可以放开"或"增量点击率跌破效益底线应收紧"，这是预训练知识里已有的约束优化直觉。
**为什么失败**：本质是"人工交互界面"的自动化版本，几乎无工程可靠性——无状态管理（上下文依赖会话记忆，进程重启全部丢失）、无安全边界（Agent 可输出任何数值，超安全工作区间照单执行）、无容错机制（并发写入混乱、网络超时无重试）、不可审计（决策散落聊天记录无法回溯）。

### v2｜多 Agent 协作
设计：拆多个专职角色（主 Agent 综合判断 + 子 Agent 研究助手），引入共享状态板（当前门控/实验日志/累积指标），把踩坑写成决策规范注入提示词。
**做对了什么**：状态持久化、职责分离（取数/执行/分析独立，主 Agent 专注推理）、实验框架（实验组/对照组评估体系）、自进化机制（日终独立角色收盘总结，策略评估器自动计算胜率）。跑了约两周，期间多个业务日成功识别可放开窗口。
**为什么失败**（两周后策略震荡被停用）——五个系统级问题：
1. **多 Agent 错误放大效应**：取数角色偶尔返回不完整数据（监控超时），主 Agent 不加质疑基于残缺数据得出"增量点击率暴跌"误判，执行角色忠实写入线上——链路无任何环节纠错。Google DeepMind 结论一致：缺乏中心化机制的独立多 Agent 架构可能把错误放大一个数量级以上。
2. **会话死锁**：依赖持久会话，模型接口超时会话锁不释放，系统连续多轮停摆只能人工重启。
3. **幻觉驱动的"自我说服"**：主 Agent 把样本噪声"发现"成稳定规律；面对规则很少硬闯，而是用冗长推理链"论证"今天为何应当例外——用推理去"修正"规则。
4. **通信成本挤占推理空间**：固定上下文预算下 Agent 间指令/回传/同步消耗大量窗口；Google 实验证实频繁 Agent 间沟通显著降低系统整体效果。
5. **单 Agent 够用后堆 Agent 更差**：单 Agent 成功率超中等水位后继续加 Agent 收益边际递减甚至为负。本场景核心"收/放"判断单 Agent 够用——真正瓶颈不是推理不够强，而是推理结果没有被约束。

### v3｜单 Agent 与约束工程（Harness Engineering）
设计哲学：**Agent 做指挥官（选策略），代码做计算器（算数值）**。从多 Agent"分而治之"回到单 Agent"聚而用之"，用约束工程重画模型与代码边界。
架构：每轮决策是固定五阶段流水线（Observe→Think→Guard→Apply→Log），只有推理阶段用大模型。调度器是常驻普通进程，不依赖任何 Agent 框架，每到决策时刻发起一次全新无状态的模型请求——不复用会话、不累积上下文，从根本消灭会话死锁。

**离散策略空间（从连续值到 6 选 1）**：Agent 不再输出具体门控数值，而是从 6 个预定义动作里选：HOLD（维持）、TIGHTEN_SMALL/LARGE（小/大收紧）、LOOSEN_SMALL/LARGE（小/大放开）、EMERGENCY_RECOVER（紧急恢复重置默认安全值）。为什么离散化：动作空间降维——v2 直接输出连续门控值动作空间近乎无限，任何不合理点都可能被幻觉生成；离散后只 6 个动作，数值由代码按固定步长算并钳位回安全工作区间，约束检查从"无穷点"变"有限动作"（类比棋类程序：盘面很大但合法落子有限）。

**约束模块（9 项硬检查）**：v3 与 v2 最根本区别。约束是一组普通代码实现的检查，Agent 任何输出必须通过全部 9 项才能执行。每项检查对应 v2 时期一个真实案例——约束不是凭空设计的安全机制，而是从失败里长出来的免疫系统。引入渐进信任：试运行第一周只允许小步、第二周放开到大步、正式运行维持大步上限（类比金融"新交易员限额"）。

**状态管理（文件是记忆，不是会话）**：彻底抛弃"会话即记忆"。状态落在几类文件：状态快照（每轮覆盖写）、决策日志（按日归档只追加）、参数配置（Agent 只读人工修改）、共享状态板（状态中心+人机通信双方可写）、日终蒸馏报告（收束时生成次日启动读取）。核心原则：进度持久化在文件系统而非上下文窗口——进程重启/接口超时/网络断连后下一轮读文件即可完整恢复。

**交易日制度（开盘、交易、收盘）**：开盘读昨日蒸馏报告+隔夜指令初始化今日门控；日间按固定时刻多轮（每轮 Observe→Think→Guard→Apply→Log）；收盘恢复默认门控、调用蒸馏 Agent 生成报告。为什么固定时刻：门控从决策到生效有分钟级延迟，决策时刻漂移就无法精确知道"现在看到的数据对应哪次门控的效果"（v2 在这吃大亏：刚调完就看数、看到旧门控效果、误以为调整没用又调回去形成震荡）。v3 延迟保护从代码层面卡住：上轮刚调过本轮强制 HOLD，至少等一个完整观察窗口再评估。

**蒸馏闭环（从经验到知识的沉淀）**：每日收盘一个独立蒸馏 Agent 触发（不是主 Agent 自己做蒸馏——职责要分开），输入当天全部决策日志，输出蒸馏报告。蒸馏出的知识通过检索注入次日推理模块——不是把整个知识库塞进提示词，而是根据当前状态取相关条目（渐进式披露 Progressive Disclosure）。知识库从空开始逐步积累多日数据支撑的已验证规则+少量待验证假设。已验证规则例：白天把门控放得过低会把当日配额提前耗尽；晚间可用配额不足增量点击率表观恶化——往往说明配额已被充分利用而非策略失效。

### 三代演化的本质认知
- v1 假设"模型什么都能做"→ 结论：能做判断但无工程可靠性
- v2 假设"多个模型协作更好"→ 结论：错误被放大、通信挤占推理空间
- v3 结论：模型擅长理解复杂局势做方向性判断，不擅长遵守规则和精确计算。让它做擅长的，其他交给代码。
- **公式：系统可靠性 = 模型的推理能力 × 代码的约束能力**。v2 试图加更多 Agent/更长提示词抬升可靠性，发现模型端上界是注意力极限（概率性）；v3 转而抬升代码端（约束、离散化、无状态调度），代码上界是实现是否正确（确定性）。

## 五、核心工程洞察
1. **约束工程 > 提示工程**：线上决策系统提示工程可靠性上界是模型注意力极限（概率性），约束工程可靠性上界是代码正确性（确定性）。Agent 价值不在于"遵守规则"（代码做得比它好一万倍），而在于理解复杂局势、权衡多维信号、做有温度的方向性判断。
2. **文件是记忆，会话是幻觉**：Agent 工程核心矛盾——状态应活在文件里而非会话里。会话会断/溢出/死锁；文件持久/可审计/可恢复。v3 每轮无状态：调度器读快照恢复上下文、调用模型拿决策、再写回文件。进程可随时杀死/重启不丢状态。
3. **渐进式能力披露**：不要一次性把所有知识塞进提示词。Agent Skills 理念是渐进式披露——把领域知识封装成独立技能文件，主 Agent 运行中缺什么读什么（先目录概览定位、缺知识再加载下一块）。从多 Agent"分而治之"到 Agent Skills"聚而用之"：知识注入拆到各子 Agent→文件系统按需加载；上下文割裂/有损传输→全局一致；高维护成本（多节点协调）→低（单 Agent+技能文件）；复用性往往重新构建→跨任务即插即用。
4. **信任要像贷款一样渐进释放**：渐进信任是必需的工程纪律而非可选功能。任何新上线 Agent 系统初始权限应被严格限制，靠持续稳定运行"赚取"更大操作空间。这和 RL 探索/利用权衡本质相同：初期保守探索、积累信心后逐步放开。

## 六、未来展望
当前解决"从完全静态到具备在线自适应"那一跃。这套在线调控除产生业务价值外，也在为未来生成式决策积累最关键的资产——高质量、结构化、带收益信号的决策轨迹。每一步都是下一步的数据基础和问题定义。
