# AI专栏 | 让Agent学会「不贰过」：从一次纠偏，到采纳率翻倍的工程实践

导读：Agent 答错后，人补一句正确答案并不难。真正困难的是：下一次遇到相似问题时，它能不能自己用上这次纠正；业务发生变化后，过去有效的做法能不能被重新检查；又怎样证明这次修改真的让 Agent 变得更好，而不是碰巧答对，或者修好这一类却让别的问题变差。

携程为此建立了一条从生产反馈出发的改进链路：系统保留 Agent 回答问题时的完整过程，找出错误从哪一步开始，把专家判断整理成候选知识，在隔离环境中重跑历史问题，经维护者审核后写回。修改后的 Agent 继续处理真实问题，新记录再回到同一条链路中。

这套机制已用于多个业务 Agent。在与携程酒店技术支持团队的共建中，两类明确接入该流程的 Agent，一线采纳率分别从约 20% 提升到 40% 以上、从约 40% 提升到 60% 左右。「采纳率」指一线人员认为 Agent 回答可以直接采用的比例。

## 一、为什么「库存不足」仍不是完整答案

一位用户很早创建了一笔需要企业审批的酒店订单。订单创建时尚有房间，但系统不会立即向商户确认订单并锁定房间，而要等审批通过后才真正执行。等审批完成，房间已经被其他订单订走了。排障 Agent 查到执行时没有库存，于是回答「库存不足」——描述了失败发生时的状态，却没有回答用户真正关心的问题：为什么很早创建的订单，最后仍然没有订到房？

问题出在时间线上。Agent 看到了执行失败时的最终状态，却漏掉了创建与执行之间的审批过程。订单创建时间和房间真正被锁定的时间不同；等待期间发生的状态变化，才把「很早提交」和「最后失败」连成完整的因果链。

这类问题并不只存在于酒店业务。申请提交后等待审核、任务创建后等待调度、支付发起后等待清算，都存在「已经提交」和「真正生效」之间的间隔。如果 Agent 只看最后一刻的状态，就容易把结果当成原因。

传统做法通常有两种：业务人员直接改对当前答案，或者补一条「遇到某类订单就检查审批」的规则。前一种只关闭了这次问题；后一种依赖具体名称和触发词。真正值得留下的不是这次答案，而是一条可迁移的业务知识：请求提交不等于操作真正生效；存在中间流程时，解释最终失败前要先检查等待期间发生了什么。

## 二、怎样让一次纠正影响下一次回答

要让这条知识影响下一次问题，系统不能只保存问题和最终答案，还要保留 Agent 当时怎样得到答案：调用了哪些工具、传入什么参数、拿到哪些结果，又依据这些信息作出什么判断。

改进系统随后检查这条执行过程，找出错误从哪里开始：是缺少必要信息，已经拿到字段却理解错了，还是信息足够但没有完成推理。专家提供的判断会先被整理成候选知识，去掉订单号、活动名和一次性返回值，保留适用条件和判断原则。

候选知识不会直接进入生产。系统先把它写入测试版本，在历史问题上重新运行，确认它确实被 Agent 使用、结果变化能够解释，而且没有让原本能正确处理的问题变差。通过验证并经维护者审核后，它才会写入 Agent 下一次运行时加载的工具说明、业务规则或提示词。

本文把这条持续链路称为**受人工治理的 Agent 自进化**。业务 Agent 仍然负责回答用户问题；另一套改进系统读取它留下的执行记录，分析错误、提出修改并回放历史案例。维护者决定哪些修改能够进入生产，新版 Agent 则继续运行并产生下一轮反馈。

一次变化要构成这样的自进化，需要同时满足四个条件：反馈来自 Agent 自己的真实运行；系统能根据反馈修改 Agent 后续仍会使用的内容；修改经过验证和人工选择；修改后的 Agent 继续产生新反馈。少了任何一环，都更接近一次普通优化，而不是持续循环。

## 三、系统怎样判断 Agent 错在哪里

生产记录和标准评测集不同，通常没有一份稳定、干净的标准答案。系统不能只把问题文本和最终答案攒起来做分类，需要读取从问题输入、工具调用、中间结果到最终回答的完整过程。常见错误大致有三类：

- **信息已经足够，但推理没有走完**：前面的订单案例——Agent 已查到执行时没有库存，却没把审批和时间差加入因果链。
- **字段已经拿到，但不知道它在业务上意味着什么**：例如某项优惠无法使用，真正判断依据可能是请求来源，字段早已在工具返回中，Agent 却不知道它与使用资格有关。此时不需要增加数据源，只需把字段含义写清楚。
- **现有工具确实拿不到必要信息**：系统先确认已有工具能否补足证据；仍缺失时再提出增加什么查询，并在只能读取、不能修改生产数据的隔离环境中验证。未经维护者审核，新查询能力不进入生产。若根因属于业务系统缺陷，或信息根本不存在，系统停止尝试，把已排除方向和最接近线索交给人。

人工反馈也要按可信程度分别使用。专家有时给出明确结论，有时只提供排查方向。分析阶段只得到「检查审批流程」这样的方向，并先从执行记录中寻找依据；完成分析后，另一道评估再检查分析结果是否与专家判断一致、记录证据能否支撑。这一阶段产物不是「这条订单应该回答什么」，而是换一个订单、换一种表达仍然成立的候选知识。

## 四、一项修改为什么值得被保留

自动提出修改并不等于已经学会。判断一项修改能否保留，需同时回答三个彼此独立的问题（并列条件，非依次步骤）：

- **生效性：修改真的被 Agent 使用了吗？** 知识写入测试版本不代表进入执行。系统需从执行记录确认新版内容已加载并真正影响工具调用或判断。
- **可归因性：答案变化来自修改，还是外部数据变化？** 历史问题发生后，库存、订单和审批状态仍会变化。回放时若重新查询今天数据，修改前后面对的就不是同一组事实。因此历史记录中已出现过的同名同参数调用，回放时优先返回当时保存的结果，让修改前后的 Agent 面对同一份基础事实。完全冻结回放则关闭所有新增查询，让两者完全基于当时保存的数据重新回答。
- **安全性：修好当前问题，有没有伤害其他问题？** 验证不能只盯当前错误，还要重跑一批原本能正确处理的历史问题。

证据是否充分、执行路径是否改变、最终结论是否改善，由不同角色分别判断，而不是让同一个模型先下结论再为自己的判断寻找理由。在内部评估中，由单一模型同时分析和裁判时，无效修改被误判为有效的比例曾在三成左右；拆分职责并增加「修改必须实际生效」条件后，这一比例下降到个位数百分比。

自动检查完成后，候选修改只有三种出口：证据充分则提交维护者采纳；信息不足则返回继续分析；无效或伤害其他问题则拒绝。系统负责提出候选并整理证据，维护者负责决定哪些变化值得长期保留。

## 五、怎样让一条经验帮助更多同类问题

一条执行记录足以发现新的业务知识，对低频、长尾问题尤其重要。当同一种错误反复出现时，系统进一步对照同类问题的成功和失败过程，寻找可复用的共同做法。它不会简单汇总各问题的最终答案——答案相同不代表推理正确，问题文本相似也不代表错误原因相同。

假设积累十条「很早提交却最终失败」的问题：回答正确的记录通常检查提交时间、审批完成时间和房间状态变化；回答错误的往往只检查最后库存。两组记录一对照，就能发现失败最常发生在没检查中间流程这一步。「存在延迟生效流程时要检查等待期间的状态变化」由此成为候选通用做法。系统还会过滤活动名、渠道名、订单号等只属于个案的信息，避免把特殊处理误写成共享规则。

通过审核的内容进入**可信经验库**，并保存它来自哪些生产记录、经过什么验证、适用于什么条件、属于哪个版本。未经验证的结论不会入库，已入库的经验也非无需检查的标准答案，每次仍要结合当前证据使用。目前经验库主要由改进系统使用：下一条错误记录进入分析时，系统先查找过去有没有类似经验以减少重复排查。尚未完全打通的是业务 Agent 的前置使用——当用户刚提出新问题时，业务 Agent 还不能稳定地在回答前自动找到并采用已有经验。系统已能加快「错误发生后的改进」，但还不能保证在错误再次发生前就阻止它。

## 六、人和基础设施各自负责什么

「自进化」容易让人联想到系统不再需要人，生产环境的实际情况恰好相反：机器适合承担可重复、可批量验证的工作，人保留对业务真因和生产发布的责任。

业务专家最有价值的输入，通常不是重新写一整份规则文档，而是指出真正原因的一句话（如「创建时有房，不代表审批完成时仍有房」）。系统据此查找相关执行记录、提出候选修改、批量回放并整理证据。人的位置从逐条搜索和手工改写，转向提供准确判断和排查方向、审核证据、治理生产变化。

权限要随任务阶段分开：分析系统只读取历史记录副本，不需要修改生产；需要重新调用工具时进入只能查询、不能写入生产数据的隔离环境；只有修改通过验证和人工审核后，专门发布流程才取得写入权限，并记录修改人、版本和回滚点。这样即使分析系统提出错误建议，也不能绕过审核直接改变生产 Agent。

并非所有 Agent 都能直接接入，至少要满足三件事：**看得见**（除最终答案外，还能看到调用了哪些工具、传入什么参数、拿到什么结果、怎样判断）；**改得动**（工具说明、业务规则和提示词能单独更新、比较版本和回滚）；**有人负责**（明确由谁审核、谁批准发布、出问题谁回滚）。

## 七、怎样判断这套方法是否产生价值

接入了多少 Agent、生成多少候选、采纳多少修改，只能说明系统在运行。真正需要回答的是：一线是否愿意采用新版 Agent 的回答，处理问题是否更快，最终用户是否感受到改善。

酒店技术支持团队每月处理上万条问题，大量场景低频、信息不完整。两类 Agent 接入前后变化最直接：负责排查房价、库存和售卖状态的 Agent，采纳率从约 20% 提升到 40% 以上（每周覆盖一百余条）；负责促销问题的 Agent，采纳率从约 40% 提升到 60% 左右（每周覆盖两百余条）。扩展到整个协作体系，总采纳率由 25.9% 提升到 51.7%。2026 年 6 月 AI 有效覆盖率达 48.08%（系统自动转移且无回流 / 系统自动解决 / Agent 诊断结论被一线采纳三类问题合计占比）。对于 Agent 确实提供有效帮助的问题，相比纯人工处理，解决时长中位数缩短约 40%；及时解决率同比提升约 4.9 个百分点。

这些整体结果不能全部归因于自进化系统，同期还有工具与业务知识整理、已有 Agent 复用、问题自动分流和部分场景自动处理。更准确结论：自进化补上了「从真实错误中持续发现 Agent 不会的地方，并形成经过验证的修改」这一环；最终业务结果来自工具、Agent、平台和一线团队共同形成的协作链路。

系统内部还要单独判断每次修改的净收益：多少原本答错的问题在修改后真正答对，又有多少原本答对的问题被新知识带坏。前者增加而后者接近零，才说明值得保留。还有两项能力需继续完善：历史问题集需覆盖更多类别，避免验证只围绕当前问题；业务事实会变化，需更完整地识别哪些经验已过时并重新验证。

## 结语

Agent 自进化不是让系统在没有约束的情况下随意修改自己，而是一套具体工程过程：从真实运行中取得完整反馈，找出错误从哪一步开始，把专家判断整理成候选知识，通过历史回放和人工审核决定是否保留，再让新版 Agent 回到生产继续接受新反馈。

一次经过验证的业务判断，有机会改变 Agent 之后处理一类问题的方式。被持续放大的不是某一句答案，而是人对真实业务的理解。在这个体系中，人工要做的不再是逐条看工单的体力活，而是对 AI 的结果做高质量决策。
