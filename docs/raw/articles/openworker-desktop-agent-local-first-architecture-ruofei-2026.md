# 吴恩达开源版WorkBuddy：拆解OpenWorker的桌面Agent架构

> 架构师（JiaGouX）/ 若飞 | 微信公众平台
> 正文整理：OpenWorker（Andrew Ng 开源桌面 Agent）源码级架构拆解

## 为什么用 WorkBuddy 类比

第一次看到 OpenWorker，很自然地想到腾讯 WorkBuddy。从公开介绍看，两者都在尝试把 AI 从"回答问题"往前推一步：接到一句话后，继续查资料、调用工具、完成任务，最后交出一份可以检查的成品。所以，标题借用了"吴恩达开源版 WorkBuddy"这个说法，方便快速交代产品形态。需要先说明：两者没有官方从属关系，也没有公开的代码继承关系。这个类比只用于理解方向，不用于判断谁高谁低。

2026 年，在《从 Prompt 到 Graph：五层 Agent 工程，真正解决的是什么》里梳理过 Prompt、Context、Harness、Loop 和 Graph 的职责。OpenWorker 给了一个更具体的源码样本：当 Agent 进入桌面，模型、工具、权限、后台任务和交付物到底怎样接在一起。本文不再重复前面的五层框架。更想沿着一次任务的执行过程，看看 OpenWorker 当前版本怎样组织桌面端、本地 Agent 服务、模型、文件、连接器、权限审批、后台任务和交付物。主要拆一条链路：一句需求，怎样经过运行时控制，变成可打开、可追溯的交付物。

## 全景：官方三层图，源码里是四组职责

OpenWorker 官方 README 把主体结构画成了三层：桌面应用 → 本地 Agent 服务 → 文件 / 工具 / 模型。这个三层图很好地交代了部署关系。顺着源码往下看，把运行职责再细分成四组：

- 交互层：React 与 Tauri 组成桌面 Surface，承载会话、进度、交付物、审批卡片和设置；
- Agent 运行层：Python 服务组织任务循环、模型调用、Skills、工具编排与工作区；
- 控制层：风险分类、权限决策、Inbox 和 Audit Store 共同约束动作；
- 资源与执行层：文件、终端、连接器、MCP 和模型提供方构成真实工作环境。

四层是便于分析的归纳，并非 OpenWorker 的官方命名。

把一次任务放进去，可以看到六条相互配合的运行线：
- 任务线：目标如何拆成步骤，进度怎样持续更新；
- 模型线：不同模型如何接入，又如何与工具层解耦；
- 工具线：文件、搜索、命令和外部系统怎样被统一调用；
- 权限线：哪些动作可以直接做，哪些需要等人批准；
- 状态线：前台会话、后台任务、待审批事项和审计记录怎样衔接；
- 交付线：结果如何落成文件、消息或日历变更，而不是停在一段回复里。

顺着仓库读，关键模块对应起来：
- coworker/agents/cowork.py 定义 Cowork Agent 的目标、能力与交付约定；
- coworker/agent.py 组装模型、工具、Skills、工作区和执行器；
- coworker/engine.py 负责一轮对话里的模型调用、工具授权、执行与结果回填；
- coworker/risk.py 和 coworker/permissions.py 负责风险分类与权限决策；
- coworker/inbox.py 和 coworker/audit.py 保存人工待办与审计事件；
- coworker/skills/base.py、coworker/tools/shell.py 分别实现技能加载和本机命令执行。

## 一次任务，怎样穿过整套架构

官网演示里有一个客户续约场景：帮我准备 Northwind 的续约电话会。如果任务在对话层结束，给出一份准备清单已经很有帮助。OpenWorker 希望继续往后走：读取 CRM 和邮件资料，归纳客户使用情况与风险，生成简报；如果用户要求发送，再把报告发到指定频道。把这件事放进源码，大致会经过下面几个阶段。

### 第一步：桌面端把目标交给本地服务

桌面应用建立会话和工作区上下文，再把用户需求交给本地 Agent 服务。模型密钥、连接器令牌和会话状态默认保存在本机的应用存储中。这里有一个重要分工：桌面端是 Surface，也就是人看见和操作的界面；Python 服务才是运行时。即使以后再增加 Slack、命令行或其他入口，底层仍可以复用同一个任务引擎。

### 第二步：Agent 先建立可见进度

Cowork Agent 默认拥有四组核心能力：`COWORK_CAPABILITIES = ["files", "search", "shell", "todo"]`。只要任务需要调用工具，系统指令就要求先使用 todo_write 建立步骤，并且始终只保留一个 in_progress 状态。桌面端的 Progress 面板会直接读取这份状态。没有 todo，运行过程很容易退回成一段长时间没有反馈的等待。todo_write 不是一套完整的工作流引擎，但它先解决了桌面 Agent 常见的反馈问题：人至少知道它正在查什么、卡在哪里、下一步准备做什么。

### 第三步：模型提议动作，工具层负责执行

模型不会直接操作电脑。它生成工具调用，Agent Engine 再把调用交给文件、搜索、终端或连接器。OpenWorker 自带二十多种连接器，也支持 MCP。于是，读取本地 PDF、搜索代码、查询 GitHub Issue、查看日历、草拟 Slack 消息，都可以进入同一个调用链。

当模型一次提出多个工具调用时，Engine 会先逐个完成授权判断。只有通过的调用才会进入执行队列，再按风险决定并发还是串行。源码里还有一个很实用的执行策略：低风险读取可以并行，有副作用的写入和命令保持顺序执行。这会牺牲一点表面速度，却能减少多个写操作互相覆盖，也让执行记录更容易还原。对真实工作来说，可解释的顺序通常比"所有工具一起跑"更可靠。

### 第四步：每个动作先经过风险分类

OpenWorker 把工具动作分成四类：

| 风险类型 | 典型动作 | 运行时关注点 |
|---|---|---|
| READ | 读文件、搜索、查询 | 没有副作用，可直接执行 |
| WRITE_LOCAL | 写文件、修改内容 | 写入模式与允许目录 |
| EXEC | 运行命令 | 命令内容、允许规则与审批 |
| EXTERNAL | 发消息、改日历、更新外部系统 | 对外副作用与明确授权 |

Permission Engine 会结合当前工作模式、可写目录、命令允许列表和工具元数据做决定。Discuss 和 Plan 模式会拒绝有后果的动作；默认的 Interactive 模式允许读取，写入、命令和外部操作通常需要确认；Custom 模式可以按配置放行指定工具；Auto 模式会直接放行有副作用的动作，但本地写入仍受目录范围约束。

命令检查还会处理 `;`、`&&`、管道、重定向和命令替换等 shell 操作符。只做字符串前缀匹配，很可能允许了前半条安全命令，却漏掉后面拼接的危险动作。

risk.py、permissions.py、inbox.py 和 audit.py 合在一起，构成了这套桌面 Agent 的控制平面：动作先分类，再决策、等待人工处理，最后留下记录。模型可以提出动作，控制层决定这个动作此刻能不能发生。

### 第五步：前台审批与后台 Inbox 共用一套机制

人在电脑前时，审批卡片直接出现在当前会话里。后台任务遇到同样的动作，不会默认替用户点击同意。系统把请求停在 Inbox，等人批准、拒绝或补充信息，任务再继续执行。这一点让"定时生成周报"和"定时发送周报"成为两件不同的事。前者可以在本机形成草稿，后者会改变外部系统状态，需要单独授权。

Inbox 也不只是一个通知列表。它是跨会话的人类注意力队列，保存待处理事项，并让暂停的任务在收到结果后继续。在《想让 Agent 在你睡觉时继续干活？先给它排好夜班》里，把稳定输入、交接状态、证据、权限和停止条件列为无人值守任务的基本条件。OpenWorker 的 Inbox 正好给出了一种运行时实现：任务可以先做无须人工介入的部分，遇到授权或信息缺口时暂停，把接力棒交回给人。

### 第六步：结果进入 Artifacts 和审计记录

Cowork Agent 的指令要求把文档、分析、计划、数据集或小脚本写成文件，并用 artifact: 链接交付。桌面端的 Artifacts 面板因此可以独立展示、打开和刷新产物。与此同时，Audit Store 会记录工具、执行阶段、状态、审批结果、参数摘要和资源引用。敏感字段只保留摘要或脱敏信息。

所以，一次"任务完成"至少有三份状态：
- Progress 说明任务走到了哪里；
- Artifacts 说明交付物在哪里；
- Audit 说明执行过哪些动作、谁批准了什么。

聊天记录仍然重要，但它不再承担全部事实。这和《Claude Code 与 Codex 六大组件拆解：Coding Agent 怎么把任务做稳》里提到的任务状态、动作日志、证据三类记录是相通的。两边命名不同，处理的是同一个工程问题：人不能只看到"完成"两个字，还要知道走到哪、做过什么、成品在哪。

## 模型可以换，运行时合同不能跟着换

OpenWorker 可以接 OpenAI、Anthropic、Gemini、GLM、DeepSeek、Kimi、Qwen、MiniMax 等模型，也能通过 Ollama 在本地运行模型。这并不意味着所有模型效果相同。工具调用稳定性、长上下文处理、指令遵循和成本都会影响完成质量。官方也只对部分组合做了验证，其他模型字符串可以自行添加，风险由使用者承担。

它的 Agent Engine 构建在 aisuite 之上，用统一接口适配不同模型提供方，并复用工具、Toolkit 和 MCP 能力。架构上更关键的是，模型没有直接绑定文件系统和外部服务。它看到的是工具定义，输出的是下一步调用建议。至于这个动作能否执行、在哪里执行、是否需要审批、怎样记录，由运行时决定。

模型更换之后，下面几份合同仍然保留：
- 工具参数与返回值；
- 风险分类和权限策略；
- 工作区和可写目录；
- 进度状态；
- 审批与 Inbox；
- 交付物链接和审计记录。

模型可以替换，工具、权限、进度、交付物和审计这些运行时合同仍要保持稳定。

## Skills 负责方法，权限仍由运行时掌握

OpenWorker 使用 SKILL.md 组织技能。一个 Skill 通常包含 YAML 元数据、Markdown 指令和可选资源。会话开始时，系统只把技能名称和描述放进上下文。Agent 真正需要时，再通过 load_skill 加载完整内容。这种渐进式加载能避免把所有工作说明一次性塞给模型。

以"生成架构评审报告"为例，Skill 可以约定：
- 先读取 ADR、接口文档和故障记录；
- 对照目标、约束、备选方案和回滚路径；
- 输出风险清单与待确认问题；
- 生成固定格式的评审文档。

Skill 解决的是任务方法。它不会自动扩大工具权限。即使技能说明里写着"把报告发到 Slack"，发送动作仍要经过连接器配置、风险分类和审批。方法层与执行层分开，才能复用专业流程，又不让一份 Markdown 说明绕过安全控制。

## 一个需要单独说明的边界：执行器还在本机

OpenWorker 的命令工具建立在 Executor 抽象之上，当前接入的是 LocalExecutor。它会维持一个持久 shell，所以 cd、环境变量和虚拟环境可以跨命令保留。对研发、数据处理和文档生成很方便。代价也很明确：命令运行在本机环境。源码为未来的 ContainerExecutor 和 VMExecutor 留了接口，但当前版本不能直接按"已有系统沙箱"理解。

审批代表用户同意执行某个动作，不会自动证明命令安全，也不会替系统提供隔离、幂等、补偿和业务正确性。

OpenWorker 中 local-first、审批与执行器的不同边界：数据放在哪里、谁授权动作、动作在哪执行，是三个需要分别回答的问题。local-first 也要按同样的方式理解。Agent 循环、会话、密钥和连接器令牌默认保存在本机；如果使用 Ollama，模型也可以完全在本地运行。选择云模型时，必要上下文仍会发给模型提供方；调用 Slack、邮箱、CRM 等集成时，数据也会进入对应服务。可选账号的一键连接还需要云端代理 OAuth 握手。本地优先描述的是运行时和状态的默认归属，并不等于所有数据永远不离开设备。

## "开源版WorkBuddy"，相似的是目标，架构路线不同

腾讯官方把 WorkBuddy 定位为面向办公场景的桌面 Agent，同样强调从一句指令到可验证交付物。其背后是 Tencent Agent Runtime，包含执行引擎、安全沙箱、工具网关、记忆与可观测等能力。从公开材料看，OpenWorker 采用了不同的实现路线：

| 观察角度 | 腾讯 WorkBuddy | OpenWorker |
|---|---|---|
| 产品形态 | 腾讯云产品与企业生态 | MIT 许可的开源桌面应用 |
| 模型与账号 | 平台提供的模型与服务体系 | 用户自带模型、密钥，也可接 Ollama |
| 工具接入 | 腾讯生态与平台能力 | 本地文件、终端、连接器与 MCP |
| 运行基础 | 官方强调 Agent Runtime 与安全沙箱 | 本地 Python 服务，当前 shell 使用 LocalExecutor |
| 公开材料的观察重点 | 企业级工作台与托管运行 | 桌面 Agent 的模块、协议和源码实现 |

两者共同回答"AI 怎样把任务做完"，基础设施选择却不一样。更倾向于把 OpenWorker 看作一套开源、模型提供方可替换、本地优先的桌面 Agent 参考实现。

## 四类任务，正好能检验四组架构能力

按当前的文件、搜索、终端、连接器、Skills 和审批机制，更倾向于从下面四类低风险场景试起。

工作：把周一晨会资料变成一份简报。让 OpenWorker 读取指定目录里的会议纪要、数据表和上周报告，生成一份 HTML 或 Markdown 简报。这个场景检验文件读取、任务进度、交付物和引用是否完整。先不开放邮件发送，成品由人检查后再分享。

生活：把零散行程整理成计划。给它一份本地旅行笔记、预算表和可用日期，让它生成行程与费用清单。如果还要修改日历，审批机制就会进入执行链。这个场景能直观看到"生成文件"和"改变外部日历"为什么属于不同风险。

架构：把 ADR、接口文档和事故记录放在一起分析。要求它整理当前方案、约束、历史故障、备选设计和回滚路径，输出架构评审草稿。这里重点检验 Skill 能否稳定复用评审方法，模型能否在限定资料范围内工作，最终文档能否回到原始来源。

研发：生成发布前诊断报告。让它读取仓库状态、Issue、测试输出和变更说明，必要时运行只读或已批准的检查命令，生成发布风险清单。这个场景会同时经过文件、搜索、终端、权限和审计，是理解 OpenWorker 架构最完整的一条路径。

## 第一次试用，任务说明可以这样写

架构能力再多，也需要一个边界清楚的输入。第一次不妨选一个干净目录和一件可人工核对的小任务：

目标：根据本目录的会议纪要和项目数据，生成本周项目简报。
输入：只使用 ./meeting-notes 和 ./metrics。
允许访问：可以读取上述目录，可以写入 ./output。
不要做：不要发送邮件，不要修改日历，不要读取其他目录。
交付物：./output/项目周报.html
完成条件：包含进展、风险、下周计划和来源清单，文件可以直接打开。
遇到以下情况先问我：资料互相矛盾、需要运行命令、需要访问外部系统。

这个模板对应的就是 OpenWorker 的几份运行时合同：目标、输入、权限范围、交付物、完成条件和人工介入点。先让一条窄链路跑通，再逐个增加连接器、后台任务和 Auto 权限，问题会更容易定位。

## 写在最后

OpenWorker 目前仍处在 open beta。它的价值不只是一套可以下载使用的桌面应用，也不只是在支持列表里放进了多少模型和连接器。更看重的是，它把桌面 Agent 的关键部件放进了一个可读、可运行的仓库：模型提出下一步，Engine 组织循环，工具连接真实环境，Permission Engine 判断风险，Inbox 等待人的决定，Audit Store 记录过程，Artifacts 保存最终成品。

这套架构还没有解决所有问题。本机执行器缺少强隔离，审批不能代替结果核对，模型与连接器仍可能把数据发送到外部服务。边界写在代码里，反而方便团队知道下一步该补什么。如果要研究"AI 同事"怎样从一句需求走到真实交付，会把 OpenWorker 当作一个可供对照的源码样本。

最后回到四个很朴素的问题：进度是否可见，动作是否受控，过程是否可查，成品是否能打开。
