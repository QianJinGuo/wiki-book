# 用好 Qoder Credits：优化的不是花费多少，而是单位 Credits 的产出

很多人认真用起 Coding Agent 之后，都会有一阵"账单焦虑"：一个看起来不算大的任务，Credits 就唰唰往下掉，掉得比想象快，也说不太清到底花在了哪儿。

  


想省，得先弄明白这笔账是怎么算的。Coding Agent 是一套执行系统：接到"帮我修这个 bug"，它会自己读代码、跑测试、改文件、看报错、再修复，一个任务背后往往是几十次"模型 → 工具 → 再模型"的往返。真正在烧 Credits 的是这条执行链。而且完成度越高，链就越长——模型的长任务自主性和自我验证一直在增强，单个任务的调用次数只会越来越多。这是正常的，不必逆着它优化。

  


所以值得优化的，不是"怎么少花 Credits"，而是"每一份 Credits 能换回多少被验证的交付"。写成一个式子会更清楚：

  


  


  


这个比值有两个方向可以使劲。**抬分子** ——靠好设计、好验证、AI 友好的仓库和合理的模型分工，让更多调用真正落成"能被接受、能过验证"的交付；**压分母** ——砍掉无效探索、重复搬运的上下文、返工，以及那些一次就烧一大笔的极端请求。这篇文章后面所有做法，拆开看都落在这两件事上。

  


只有一个前提要先说清楚：压分母不能把分子也压下去。所有省 Credits 的动作，都建立在"任务照样做成、做对"的基础上；要是为了省让任务做不完、做不对、逼着人反复返工，那不是省，是把单位 Credits 产出做低了，只是账单一时好看。顺序不能反——先保证做对，再谈省。

  


**先分清楚：哪些 Credits 花得值，哪些是白白浪费**

要让这个比值往上走，得先能分辨：一个任务里那几十次调用，哪些在真推进，哪些在原地打转。

  


一类是在真正干活：读关键代码、跑针对性测试、拿着失败证据去修复——这些是必要成本，该给它预留预算。另一类是在空转：反复澄清目标、读错目录、重复扫描整个仓库、没证据就瞎改、改完又返工——这些才是要砍的。Qoder Quest 把好的用法概括成一句话——"定义目标，检查结果"，你定义得越清楚，空转就越少。

  


  


前面那个"单位 Credits 产出"是结果指标；执行过程里还可以盯一个更细的——**有效路径占比** （产生新证据或推进交付的调用 / 全部调用），它直接告诉你这一轮有多少调用在真干活。举个例子：一个用高级模型、20 次有效调用就完成并验证的任务，单位 Credits 产出很可能高于一个便宜模型被人纠正 40 次的任务——哪怕后者单次更便宜、总 Credits 看着也没多多少。

  


真正需要压缩的是回头路，不是必要的工作步骤。这句话是这篇文章所有做法的出发点。

  


**钱到底花在哪：每轮都要重新发送完整的历史上下文**

要省钱，得先知道钱花在哪。每发一轮请求，System Prompt、项目文档、Skill / Tool 定义、历史会话、被读进来的代码文件，这些完整的历史上下文都要重新发送给模型、重新计费一次——它们通常占了一轮请求的绝大部分，是账单真正的大头。

  


这里有个容易搞反的点：重复本身省不掉。Agent 一步步往下做，前面的内容每一轮都得再带给模型，这是它的工作方式。真正能拧的，是这些上下文里"没用的那部分"。比如让它检索一段代码，往往只有两三成跟当前任务相关，剩下的都是噪声——可噪声一旦进了上下文，就会跟着每一轮被重新处理、重新收费。所以那些省钱动作——**不相关就新开会话、少装工具、只给必要上下文、用 @ 精确指路** ——与其说是在"减少重复"，不如说是在把无效内容挡在门外，别让它一遍遍地重复计费。

  


这也解释了为什么"从多满的上下文继续问"直接决定了这一单的价格。同样问一句话，**从一个塞了 600K 的上下文里继续问，比从 50K 起点问要贵得多** ——历史对话、项目规则和已读代码都会进入这一轮的输入计费。你的起点越满，缓存未命中时的成本越高。

  


而真正吓人的账单，往往不是日常那句提问，而是少数极端请求一次就烧掉一大笔。几个典型的踩雷动作：习惯性把上下文窗口开到 600K / 1M 还长期怼满；一个长 batch（测试或构建）跑太久，超过了缓存窗口；隔很久才追问、或同一任务里频繁切模型导致缓存被清空；把大文件、大日志、node_modules、构建产物一股脑塞进上下文。这些动作叠加起来，一次请求可能达到日常小上下文、缓存命中场景的几十倍。

  


  


图中按 GPT-5.6 Sol 的公开 API 价格计算：标准输入 $5 / M Token、缓存读取 $0.5 / M、缓存写入 $6.25 / M、输出 $30 / M；四种场景统一假设输出 1K Token，因此输出费固定为 $0.03。缓存未命中按写入新缓存计算。50K 输入时，未命中约为命中的 6.2 倍；600K 输入时，这个差距扩大到约 11.5 倍。价格来源为 OpenAI GPT-5.6 官方说明，这里只用于建立数量级直觉，与 Coding Agent 实际计费和所用模型无关。

  


所以省钱要同时做两件事：**压掉日常的重复上下文，堵住极端的异常请求。  **下面几节就是围绕这两件事展开的具体做法。

**上下文与缓存：一根很长的杠杆**

管好上下文和缓存，是省 Credits 里回报很高的一根杠杆——它未必是唯一决定成败的因素，但你在这里省下的、或浪费掉的，几乎都会按轮直接反映到账单上。

  


**一个 Session 只干一件事。**  话题一切换就新开会话——修 Bug、写文档、查线上问题各开各的，别让它们的历史互相污染。会话记录不是资产：一段塞满无关历史的长对话，会让模型在后续每一轮继续处理这些内容，输入成本也随之越滚越大。上下文的整理和压缩交给 Agent 自己处理就好，你唯一要做的是——任务不相关了，就新开一个对话。

  


**只给必要上下文，别习惯性怼满。**  用 @完整路径 直接指到文件或函数，能省掉一整条"让 Agent 自己搜索"的链路；大文件只读相关区段，大日志先过滤再喂。长上下文是模型的能力上限，不是你的默认工作集——别一上来就开到最大再往里塞。

  


**一次把话说清。**  目标、范围、约束、验收标准一次给全，避免"你问一句、我答一句"的聊天式拆碎。每多一个来回，历史对话、项目规则和已读代码都会再次参与本轮处理与输入计费。心里已经有方案的话，直接给伪代码，让 AI "填空"比让它"开放作文"又省又准。

  


真正偏门、但省下来很可观的一条经验，是顺着缓存的生命周期安排执行节奏。Prompt Cache 缓存的是稳定前缀的处理结果，命中之后重复上下文不必再从头计费，输入成本和延迟都会明显下降。但缓存不是永久的——本文用于价格计算的 GPT-5.6 支持至少 30 分钟缓存寿命，不同模型和服务的具体规则可能不同。

  


这里还得澄清一个常被误解的点：缓存命中不是"全有或全无"，而是分平台和用户两层。平台侧兜住的是基本盘—— Qoder 会把基础缓存命中率保障在 90% 以上，稳定前缀那部分你基本不用操心。真正握在你手里的是用户侧那部分：同样一段上下文，是接着命中、还是被推回未命中重新计费，取决于你怎么操作它。用户侧能做的，主要就下面两条：

  


  * **别在同一任务里频繁切模型。  **多数实现下切换模型会清空缓存，让输入重新按未命中计费、白白多花 Credits。确实需要换模型时，先把核心结论总结进新会话再切。

  * **让请求趁热，别让缓存凉在半路。**  缓存有寿命，相邻两轮隔太久就会过期：一个测试或构建的 batch 跑太久，等它结束再发下一轮，前缀缓存可能已经失效；人离开一会儿、过十分钟才想起来追问，也是同一回事。更省的做法是主动让执行链连着——优先跑针对性测试，把长回归、全量构建后台化或拆成小步，真正的长跑交给 /schedule 夜间执行；同时在 Agent 运行过程中就把下一步敲好回车让它排队（queued messages），或用支持运行中插话的客户端实时把内容插进当前执行。

  


顺着这个思路，还有个更省心的选择：**用 Quest 的目标驱动（goal）模式。** 你把目标定清楚交给它，就算 Agent 中途停下、目标还没达成，Quest 也会自动驱动它接着往下做，而不是停在原地等你重新发一句话。执行链不断，上下文就一直连着，缓存自然更容易持续命中——省掉了"人回过神来才继续、缓存早凉了"的那部分浪费。

  


  


**让 AI 少返工：好设计、好验证，**

**再加一个 AI 友好的仓库**

上下文管的是"怎么少搬运"，这一节管的是"怎么少走回头路"——每发生一次返工，此前的对话、规则、代码和错误信息都会再次进入模型的处理链。少返工主要靠两件事：动手前把设计想清楚，代码写完把验证做扎实；这两件做熟了，再往上走一层——把仓库本身改造成"AI 友好"的。

  


最烧钱的输入是一句话需求。"帮我优化这个模块"没有目标、没有范围、没有完成定义，Agent 只能先猜、你再不断微调，每次补充都可能让已经写好的代码返工。所以动手前花几分钟，把"要做什么、不做什么、怎么算完成"写下来——不用写成正式文档，几行就够。这几行还是你能给 Agent 的最便宜的上下文：后续模型、夜间任务、新开的窗口都能照着接力，省得每次从头解释一遍。

  


再说测试。别把它当成 Credits 黑洞——恰恰相反，有可运行的测试，AI 才知道自己"做对没、修好没"，能在同一轮里自我收敛；没有测试，它只能凭感觉交付，然后你反复描述"哪里还不对"、它带着完整上下文一次次返工，这种"人肉调参"比一开始就用测试自证要贵得多。

  


真正浪费的不是测试本身，而是错误的测试半径——无差别跑全量测试。合理的做法是从最小范围逐步扩大：

  


从改动半径和风险选层级：小改动不必先跑全集，核心链路也不能只靠 lint。结束条件是三件套——代码改完、最小充分验证通过、给出 Task Report（改了什么、取舍和风险）。"模型说完成了"不算完成。

  


上面这两件——设计和验证——都是"每个任务都得重做一遍"的动作。要是每次都靠人临场叮嘱，迟早会有漏网的地方。更省的做法，是把这些约束沉淀进仓库本身，让它变成一套一直生效的护栏。这套思路这两年有了个名字：**Harness Engineering** ——与其指望模型每次都足够聪明，不如把仓库设计成"普通模型也能稳定写对"的环境。

  


它的前提有点反直觉：Agent 自主性越高，运行环境越要被约束——不是把规则写松，而是把工程纪律前移到仓库结构里。一个 AI 友好的仓库通常在三处下功夫。一是把仓库当成唯一可信的知识源：架构、规范、目录约定放进结构化的 docs/，AGENTS.md 和 Rules 只当索引和硬性约束，而不是塞满一切的大杂烩——因为对 Agent 来说，没写进仓库的知识（口头结论、群里的共识）约等于不存在。二是把架构边界做成可验证的：分层清晰、依赖方向固定、跨域调用走显式接口，再用自定义 lint 和结构化测试把这些边界钉死——越界的代码在写出来的当下就被挡回，而不是拖到 review 或上线才暴露。三是让测试和质量门禁常驻：AI 每写一步都有裁判，问题在本轮就收敛，而不是攒到最后一次性返工。

  


这套机制的核心原则可以浓缩成一句：**对局部实现给自由，对系统边界给高压约束。**  它的回报是复利的——单个任务里的设计和验证，只让"这一个任务"少返工；而一个 AI 友好的仓库，会让之后"每一个任务"都少搜索、少猜测、少回归。落到单位 Credits 产出的账上：前者是一次性收益，后者是把所有后续任务的基线一起抬高。花点时间把仓库改造成护栏，是这篇文章里唯一一个"投入一次、长期复利"的动作。

  


  


**模型分工：把贵的算力用在决策上**

不是所有任务都值得用最贵的模型，也不是永远用一个便宜模型就最省。经济的做法是让不同智能密度的任务，匹配不同档位的模型。

  


  


这套策略可以浓缩成一句话：**高级模型做决策，高性价比模型做吞吐，测试工具做裁判。**  高级模型负责读需求、识别风险、输出设计和任务列表；高性价比模型按确定好的任务批量实现、补测试、整理文档；交付前再由高级模型审一次，形成 Plan → Execute → Review 的接力。

  


判断省不省，要看总成本，不看单次倍率。记录完成率、总 Credits、人工介入次数，去比"完成一个同类任务"的平均成本，而不是盯着某一次调用的单价。有几个信号出现时反而不该降档：根因还没确认、多模块有隐式约束、回滚成本很高、已经反复失败或需要人连续纠正——这些时候用便宜模型硬试，往往更贵。

  


值得单独说的是国产旗舰的性价比。以下仅选取几款公开 API 作为价格样本，用来说明输出侧价差的数量级。图中模型与 Coding Agent 实际使用、路由或推荐的模型无关，也不构成选型建议。价格为 2026-07 采集的每百万 Token API 官方按量价，USD 口径，后续可能变化。

  


  


差主要落在输出侧——而输出恰恰是成本大头。以输出价看，GPT-5.6 Sol 的 $30 大约是 GLM-5.2 的近 8 倍、千问的 6 倍。海外旗舰近半年价格基本冻结在 $5/$25–30，国内旗舰虽然在为更强能力小幅上探，但输出价仍只有海外的约 1/8 到 3/5。结论很直接：批量吞吐类任务（补测试、批量迁移、格式统一），在设计和验收已经明确之后，尤其值得交给国产高性价比模型。

  


**时间调度：把可异步的活儿交给夜里**

省 Credits 还有个简单的办法：把活儿挪到夜里。Qoder 支持在 Quest 输入框用 /schedule 定时执行，比如：

  


  * 

    
    
    /schedule At 10 PM tonight, fill in tests for the code I changed today

  


这么做有两重省法。一是那些定义清楚、不用你频繁确认的活（补单测、批量迁移、更新文档、跑长回归），本来就适合异步，人不用守着；二是夜间部分模型的费率有很低的折扣，同样的活，成本更低（具体规则以当期活动页为准）。

  


要点只有一个：夜里没人盯着，所以 prompt 得把范围、验证命令、停止条件和交付物写清楚，别把有歧义、会动生产数据、失败不可逆的活扔进去。跑顺了就是一个自然的节奏——白天定方案、拆任务，夜里让它执行，早上验收 diff 和测试结果。

**结语**

绕了一圈，落点还是开头那个比值——**验证过的产出 / 花掉的 Credits。** 在今天这个时间点，把它做高没有单一的银弹，靠的是把手上已经有的三样东西叠起来用。

  


第一样是**现有的模型能力** 。模型档位已经拉得很开，就别再一个模型用到底：强模型做决策、性价比模型做吞吐、测试当裁判，而国产旗舰在批量吞吐类任务上性价比尤其明显。把贵的算力用在真正需要判断的地方，比一味求强或一味图便宜都划算。

  


第二样是**现有的 Agent 架构** 。执行链才是烧 Credits 的大头，所以真正的杠杆都在上下文、缓存和时间上：一个 session 只干一件事、只喂必要的上下文、追问趁着缓存还热，再把定义清楚的长活用 /schedule 挪到夜里（还能吃上夜间折扣）。这些都是顺着 Agent 的运行机制去拧的螺丝。

  


第三样是**现有的工程实践** 。动手前把设计写清楚，动手后把验证做扎实，再把这些约束沉淀进仓库、做成一套 AI 友好的护栏（Harness Engineering）。前两样让"这一个任务"少返工，这一样让"以后每个任务"都少返工，回报是复利的。
