# 代码越来越快，架构工作变在哪里？从吴恩达 AI 工程技能图谱说起

> 架构师（若飞）。从吴恩达 2026-08 更新的 AI Engineering Skills Map（软件工程基础五方向）出发，论述 AI 时代架构工作的本质转变：代码生成越快，架构中的身份/状态/边界/失败语义决定越密集。包含原创「决策链」归纳 + 知识库同步链路三案例（身份模型/数据架构/确定性约束）+「架构=约束系统」结论。

## 一、身份案例：Karpathy MenuGen 失误的架构解读

Karpathy 做 MenuGen 时让 Agent 接入 Stripe 购买记录和 Google 登录，用邮箱关联购买者和登录用户；一旦付款邮箱和 Google 账号邮箱不同，权益就对不上。表面是字段选错，本质是**身份模型没设计清楚**：邮箱是可能变化/不一致的属性，不能天然承担稳定身份的职责。更早要确定的是：系统用什么稳定标识连接登录主体、支付主体、业务权益，映射由谁维护，异常怎么处理。

Agent 能很快写出能跑的关联逻辑，却不会自动定义业务世界里"同一个人"是什么意思。**代码生成越来越快，架构工作没有变轻**；实现吞吐上去后，身份、状态、边界、失败语义这些决定反而更密集涌进系统。

## 二、吴恩达 AI Engineering Skills Map 的软件工程基础

2026-08 吴恩达连续更新 AI 工程技能图谱：8/14 给四项一级能力（构建部署 AI 应用、软件工程基础、使用 Coding Agent、决定构建什么）；8/21 展开构建部署；8/28 讲软件工程基础。软件工程分五方向：**全栈开发、数据、系统架构、安全与可靠性、规模化与生产运行**。

重点不是重新整理传统 SE 知识，而是：**即便 Agent 能写出全部代码，人仍要理解这些基础**，才能引导技术取舍、发现取舍做坏后的延迟/可用性/一致性/可靠性/维护性/复杂度/成本问题。五方向放进同一系统看，是同一个系统问题经过的不同边界：
- 全栈开发 → 能力以什么运行形态交付，前端/后端/API/部署如何衔接
- 数据 → 系统承认哪些事实，状态放哪，如何保持一致/可追溯/可治理
- 系统架构 → 边界怎么切，依赖往哪流，变化和故障如何隔离
- 安全与可靠性 → 哪些事绝不能发生，异常时如何降级恢复
- 规模化与生产运行 → 用真实流量/成本/故障检验前面假设

## 三、决策链（若飞原创归纳，吴恩达原图无此名）

回到身份案例，五类能力连起来：不稳定字段被当身份后，问题沿**数据模型 → 服务边界 → 权限校验 → 恢复流程**一路扩散。图的意义不在画多少方框，而在于**把错误怎样跨过系统边界表现出来**。Google 登录和 Stripe 支付各自正常、数据库未必损坏，缺的是稳定连接登录/支付/业务权益的身份映射——由谁维护、失败后谁对账、账号合并如何处理，都是实现前要说的架构决定。过早拆分服务同理：单库状态一致性可能转成跨服务幂等、补偿、对账问题。

## 四、架构基本功：先看取舍再看技术

很多团队谈架构从"单体还是微服务/关系库还是向量库/同步还是异步"开始，但这是答案的一部分。更靠前的工作是**把业务语义和质量目标说清楚**。

质量目标举例：高可用不是口号，要落到谁在什么条件发起什么请求、允许多久恢复、能丢多少数据；低延迟要说明平均值/P95/P99、是搜索还是写入链路。**约束一旦具体，技术争论自然收敛；语义和质量目标含糊，技术栈只是把不确定性藏进代码。Agent 写得越快，被藏起来的决定越多。**

呼应此前《Agent 时代，架构师应该学什么》：重点放在状态、权限、Eval、Harness——把人的判断变成系统可执行、可检查、可追溯的边界。

## 五、案例：知识库同步链路三类架构取舍

假设一条企业知识库同步链路（云盘+内部文档库同步 → 解析切分向量化索引 → 带权限问答），不是真实事故，只是把几类取舍放进同一场景。

### 业务不变量要先进入数据模型
最危险错误不是"没搜到"而是"看到不该看的内容"。租户隔离/资源身份/权限撤销/源文档删除都是业务不变量。文档键需含租户+稳定资源标识，唯一性由数据库约束兜底；同步合同要带来源版本/删除标记/变更游标；重试依赖幂等键。只让 Agent 按需求生成同步代码，容易先做出新增/更新却漏删除/移动/重命名/权限撤销/重复事件——缺的是**完整状态语义**。

### 事实、运行状态、派生数据要分开
原始文档仍由上游负责，进向量库后向量库不能变新事实源；同步游标/任务状态/失败记录属运行账本；切片/Embedding/搜索索引是可重建派生数据。层次混淆则恢复困难（索引坏不知能否重建/同步断不知从哪续/上游撤权本地仍留旧权限）。梳理 Ontology 时同类问题拆成证据层/事实层/语义控制面/动作层——搜到什么、什么现在有效、谁有权看到，须由不同责任边界回答。

权限校验有真实取舍：查询时回源校验接近最新但增延迟依赖上游；ACL 写进索引更快但担传播延迟。高风险内容实时校验，低风险高频用短时缓存+版本化 ACL。

### 边界跟着变化压力演进
内部试点阶段，边界清楚的单体+任务表+后台 Worker 往往够用；解析耗尽资源/不同源需独立扩缩/失败隔离成真实需求时再引入队列+独立 Worker。**推动拆分的是变化频率/资源模型/故障边界/团队所有权，不是预设的"AI 系统标准形态"**。索引升级用架构手段降风险：新版本离线构建、校验后切换别名、问题保留旧索引回退；向量库可以后选，先确认真实体面变化能否观察/比较/回滚。

### Eval 之外还要有确定性约束
AI 应用当然要 Eval（检索相关性/引用准确/答案有用）。但租户隔离/资源唯一性/权限拒绝/幂等这些规则**不能只交给概率评分，更适合写成数据库约束/策略规则/属性测试/发布门禁**。生产环境要看同步延迟/失败重试/陈旧索引/权限撤销传播时间/跨租户访问异常。文档是外部输入不能默认可信；把抓取权限/外部网络访问/索引写入/生产发布分开，缩小单次错误影响范围。Eval 不应是上线前跑一次的分数，而是和确定性测试/运行指标/告警/回滚证据一起，回答这次变更能否交付。

## 六、架构决定要穿过整条交付链

架构价值不在一张漂亮图，而在**让关键决定在需求/实现/发布/运行中持续生效**。

- 实现前：把业务不变量/质量属性场景/数据语义/外部约束说明白；ADR 不只记"选了什么"，还写背景/备选/取舍理由/何时重新审视。
- 实现中：决定下沉到接口契约/Schema/类型/权限策略/测试/架构适应度检查；**写在提示词的约束帮 Agent 理解上下文，真正阻止错误进系统的仍是能自动执行的边界和 Gate**。呼应 AI-First 判断：AI 出错不能只让人修那一行，上下文漏了什么/接口为何允许错误输入/测试为何没覆盖/反馈为何没回规则，这些是系统下一轮该补的。
- 发布前：关注点从"代码是否完成"转向"证据是否足够"（关键场景验证/影响范围控制/灰度观察/失败回滚）。Simon Willison：和 Coding Agent 协作的关键是能把握给指令、能把握验证改动，逐行审查只是验证手段之一。
- 上线后：真实流量暴露容量假设/故障暴露边界/成本改取舍；事故模式回到测试/规则/运行手册/下一轮设计。拆 Anthropic AI-Native SDLC 时最深的印象：每一步都要有权威记录（当前决定/谁批准/什么证据允许继续/出问题退回哪）。架构决定只有落到记录和 Gate 里，才不在 Agent 高速执行中失真。

吴恩达三层 Loop 的"慢反馈"：Agent 把写代码/跑测试/修 Bug 压到分钟级，用户行为/事故模式/业务方向不会自动加速。内层越快，架构师越要把慢信号接回规格和验收。Addy Osmani 称"外层循环"：Agent 可内层调查/实现/自检，工程师仍对约束/证据/结论/最终结果负责。

## 七、结论：代码快了以后，架构更像一套控制系统

AI 能力周围始终是完整的软件系统——模型再新/提示词再好，仍要面对身份/数据/事务/并发/安全/部署/监控/技术债。Karpathy 区分 Vibe Coding 和 Agentic Engineering 即在划此边界：前者探索/一次性，后者获得杠杆且不牺牲正确性/安全性/可维护性/工程品位。

架构师当下更值得投入的是把**业务语义/事实来源/系统边界/质量目标/运行证据组织成能执行/能反馈/能演进的约束**。**架构工作更关心的是：系统快速变化时，哪些约束仍然必须成立，又怎样证明它们确实成立。**
