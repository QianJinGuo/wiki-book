# 用过一次就能学会！哈工大开源自进化GUI Agent，跨App连续干活

原创 让你更懂AI的 2026-08-18 22:06 北京

AI 助手终于会“长记性”了

只用一句自然语言指令，让个人 AI 助手依次从邮件提取会议地址、转发联系人、打开地图规划路线，它能否像人一样在多个应用之间顺畅协作？

简单地给 OpenClaw 通用智能体“外挂”一个 GUI Agent，往往仍会遇到问题：跨应用信息容易丢失、操作依赖不断变化的图形界面、执行轨迹用完即弃。

许多现有 GUI 智能体每次面对任务都像第一次使用设备：走过的弯路不会成为经验，成功的操作也无法沉淀为下一次可复用的能力。

近期，哈工大张民教授立知大模型团队开源 KnowAct-GUIClaw，面向个人助手提出 “Know Deeply，Act Perfectly” 范式——知道得越深，行动得越准。

〓 KnowAct-GUIClaw 在长程 GUI 任务评测基准 MobileWorld 上达到 SOTA 表现

框架以具备长期上下文、记忆和工具能力的主智能体负责任务编排，以可插拔的 GUI 智能体负责实时界面操作，在二者之间引入结构化信息传递、可归因经验记忆和自进化技能库，支持跨应用、跨平台完成长程任务，并从执行轨迹中积累经验与用户偏好，从而越用越好。

从“外挂 GUI Agent” 到 Host–GUI 协同

KnowAct-GUIClaw 并不把所有任务都交给一个单体 GUI Agent，它将长期任务管理与底层界面操作解耦：Host Agent 保留对话、工作区记忆、用户画像、外部工具和全局任务进度，负责判断“做什么”。

GUIClaw 感知屏幕、规范化动作、连接不同设备后端、校验技能并记录轨迹，负责决定“如何在界面上完成”。

这一区分让效率成为系统设计的一部分：只有需要读取实时页面、操作登录态应用或进行设备端验证时，Host 才调用 GUI 智能体。

如果已有上下文、记忆或外部工具足以完成某个信息型子任务，Host 会直接处理，减少不必要的 GUI 交互和视觉 Token 开销。

在此基础上，KnowAct-GUIClaw 将一次任务组织为 Know、Route、Act、Reflect 四个阶段，并让经验记忆与执行技能在任务结束后重新回到下一轮决策中。

〓 KnowAct-GUIClaw 架构图

Know + Route：先理解上下文，再把跨应用任务拆清楚

在真正操作界面前，Know 阶段会主动汇集当前对话、用户画像、历史任务、候选应用、相关经验和可用技能。

检索到的 UI 操控经验和技能是辅助信息，不会取代用户当前指令和实时屏幕证据；当用户指令较为模糊时，系统可以从记忆中提出明确、可覆盖的默认假设。

随后，Route 阶段把请求划分为单应用任务或有序的跨应用工作流。对于跨应用任务，每个子任务都显式声明目标应用、所需输入和应返回的输出。

系统不再依靠一段不断增长的自由文本摘要传递关键信息，而是使用临时 Blackboard（黑板）保存带类型的中间结果：上游应用观察到什么，下游应用就消费什么。

如果必需输入或声明输出缺失，工作流会停止，而不是让后续步骤猜测或编造。

这让“从邮件读取时间并设置闹钟”“从两个购物应用读取价格后比较”“从购物车读取订单信息并发送短信”等任务，都能把跨应用数据流变成可检查、可恢复的结构化契约。

〓 Blackboard 保存任务上下文信息

Act：统一 GUI 操作、可复用技能与快捷路径

进入 Act 阶段后，GUIClaw 在统一的混合动作空间中执行任务，既可以点击、滑动、输入、返回和等待，也可以调用已经沉淀的技能、经过验证的 Deep Link / Intent 快捷路径，或在需要用户输入和授权时主动请求干预。

其中，技能不是对旧轨迹的机械重放。每个技能都包含适用应用与平台、参数、可靠性统计、操作步骤和状态契约；调用前先检索与当前子任务相关的候选技能，执行中再逐步检查当前页面是否满足预期状态。

如果页面不匹配，系统可以进行有限恢复、跳过可选障碍步骤，或退回普通 UI 操作。

Deep Link 和 Intent 同样遵循“先发现、后验证”的原则。应用清单只能证明某个入口可能存在，不能证明它在真实设备上可用，更不能证明它会落到正确页面。

KnowAct-GUIClaw 会实际启动候选入口，结合前台应用、UI 树、截图和参数保留情况进行页面级验证，只有通过验证的入口才会进入技能库成为快捷路径。

在跨应用比价案例中，系统从用户画像获得目标商品型号，分别调用京东与淘宝完成查询。

经过验证的京东搜索快捷路径可以一步直达商品结果页，而淘宝分支需要五次常规 GUI 操作；两个应用中观察到的价格通过 Blackboard 回传，再由 Host 给出比较结果。

〓 跨应用比价案例

Reflect：让每次成功和失败都成为下一次的起点

任务结束后，Reflect 阶段不会简单保存一份冗长日志，而是从轨迹中提炼两类彼此独立、用途不同的长期资产：

  * 经验记忆保存可检索的文字策略，包括成功做法、失败原因、应用选择、界面布局、快捷路径可靠性和恢复建议，用来影响下一次的路由与执行判断。

  * 执行技能保存参数化、可运行、带状态验证的操作过程，用来压缩重复导航和高频交互。




系统会过滤空轨迹、过短轨迹、异常终止等缺乏有效信号的执行记录。对于可复用的成功过程，它从任务、平台、应用、动作参数、截图和目标控件等证据中抽取新技能。

对于已经调用但执行失败的技能，它优先根据失败步骤、页面证据和错误反馈对原技能进行定向修复，而不是无条件生成一个无关的新流程。

这种“记住为什么、学会怎么做”的双层机制，让文本经验与可执行技能各司其职。

以 Mastodon 邀请链接任务为例，没有经验记忆时，GUIClaw 会在移动端设置中反复尝试；检索到历史失败经验后，系统能在低层操作开始前修正任务上下文，转向网页管理后台，再由实时页面证据指导后续操作。

〓 从失败轨迹吸取经验, 修正后续任务

开源模型在 MobileWorld 长程任务上展现 SOTA 性能

〓 KnowAct-GUIClaw 在 MobileWorld GUI-Only 基准上展现 SOTA 性能

在面向长程、跨应用 GUI 任务的 MobileWorld 基准上，搭载开源模型 Kimi-K2.6 的 KnowAct-GUIClaw 取得 64.1% 的成功率，展现出具有竞争力的 SOTA 性能。

更值得关注的是，这一提升并非单纯依赖更强的基础模型。加入 Host 与经验记忆后，Kimi-K2.6 的表现由 55.6% 提升至 61.5%；进一步启用自进化技能后达到 64.1%，累计提升 8.5 个百分点。

这表明，持续积累的经验与可复用技能能够切实转化为更可靠的 GUI 执行能力。

框架沉淀的经验和技能还具备跨模型迁移潜力：将 Kimi-K2.6 轨迹中提炼的能力迁移至 Qwen3.5-35B-A3B 后，其成功率提升 16.2 个百分点。

与此同时，技能复用可减少重复操作，并节省约 6% 的 Token 消耗，让任务执行更准确、更高效。

从移动端到桌面端，KnowAct-GUIClaw 已在 Android、iOS、HarmonyOS 和 Windows 等环境中完成验证，展示了面向多设备个人助手的跨平台适应能力。

不只是“会点屏幕”：工具与 UI 操控协同

KnowAct-GUIClaw 的目标不是让 GUI 智能体包办一切，而是让 Host、外部工具与 UI 操作围绕同一任务状态协作。

在一个会议地点查询案例中，Email 任务只返回了酒店名称，无法满足后续短信和地图任务对完整地址的输入要求。

Host 检测到输出契约未满足后，先通过网页搜索补全街道地址，再把这一结构化结果分别交给 Messages 和 Maps 任务，最终完成地址发送与步行路线查询。

在另一个联系人缺失案例中，按姓名发送消息的 UI 任务失败后，Host 保留失败进度，从简历中恢复电话号码，再重新规划 Messages 子任务。失败不再意味着整条长程工作流推倒重来，而是成为可以继续编排的检查点。

总结与展望

KnowAct-GUIClaw 从两个方向扩展了 OpenClaw 风格个人助手的能力边界：

一方面，以可插拔 GUIClaw 补足无标准 API、登录态应用和动态界面中的跨平台操作能力；

另一方面，以可归因经验记忆和技能库建立从执行、反思到再次执行的自进化闭环。

从“完成一次任务”走向“积累长期能力”，个人助手需要的不只是更强的单步视觉定位，还需要理解用户与上下文、组织跨应用信息、选择 GUI 与非 GUI 路径，并把真实执行经验沉淀为以后可调用的知识和技能。

这正是 “Know Deeply，Act Perfectly” 所希望表达的核心：知行合一，知道得越深，才能行动得越准；每一次行动，又会反过来丰富下一次的认知。

未来，团队将继续探索通用外部工具与 GUIClaw 的原生联合规划与行动方式，让系统在同一个决策周期内权衡知识检索、工具调用和 GUI 操作，进一步减少 Host 与 GUI 子智能体之间的通信与串行切换开销。
