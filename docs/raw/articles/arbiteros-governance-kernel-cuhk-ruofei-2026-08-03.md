# Agent 能干活之后，谁来管执行权？港中文开源了治理内核

> 作者：若飞（架构师 JiaGouX）

## 问题：模型能力越强，执行权越需要治理

Agent 能读代码、改文件、发邮件、调用 API 之后，很多问题就变了。留在聊天框里的错误通常还能重新生成；已经发出的邮件、改过的生产配置、写进数据库的数据，却未必能轻松撤回。模型能力越强、能串起的工具越多，系统真正需要回答的就越具体：谁给了这一步执行权，动作发生前谁能拦住，出了问题又从哪里查起？

香港中文大学 CURE Lab 开源的 **ArbiterOS**，把治理点放在模型输出和工具执行之间。它在模型输出和工具执行之间增加一层运行时治理，将工具调用整理成结构化指令，记录数据来源和步骤依赖，再由策略决定放行、阻断或请求确认。从架构上看，ArbiterOS 补的是 Agent 控制循环里长期缺失的一层：模型负责规划，确定性的治理层决定动作能否进入执行面。

## 边界：ArbiterOS 是什么、不是什么

ArbiterOS 并非新的 Agent 框架，也不是装上就能覆盖所有风险的操作系统。当前实现建立在 LiteLLM 代理之上，要求 Agent 能把模型请求路由到 OpenAI 兼容端点，本地默认地址是 http://127.0.0.1:4000/v1。README 目前列出的集成包括 OpenClaw、Nanobot 和 Hermes Agent。

能否管住一条调用链，取决于请求有没有经过代理、工具格式能否被解析，以及部署时究竟启用了哪些策略。直接运行的脚本、MCP Server 或宿主进程如果绕过这条链，治理层也就看不到它们。

## 风险藏在控制循环里

看一个普通任务：读取测试日志，整理摘要，再发到内部知识库。Agent 可能先访问网页查错误信息，再读取本地配置，最后发起一次 HTTP 请求。每一步单独看都挺正常，连起来却可能形成另一条路径：不可信网页影响了后续规划，本地配置带入了敏感数据，最后一个语法完全合法的 POST 把这些内容送出系统。

只检查最后一次 API 调用，看到的只是目标地址和请求参数；只检查提示词，又看不到真实文件权限、网络出口和之前发生过的工具调用。问题出在 Agent 的控制循环：传统应用里业务代码负责提出请求，权限系统、事务、网关和基础设施分别把守执行边界；很多 Agent 系统却把规划、判断和下一步动作都交给同一个概率模型。模型既决定"做什么"，又决定"现在就做"，外面再补几条 Prompt、确认弹窗和日志。

高风险动作缺少一个独立、确定、位于执行前的控制点。单独一层防护总显得不够的原因：

- Prompt 能说明项目约定，却很难成为强制权限边界
- 安全模型可以给出风险信号，却未必掌握完整的数据来源和系统状态
- Sandbox 能限制进程读写和联网范围，却不理解一段客户数据接下来要发给谁
- 人工确认适合处理关键决定，频繁弹窗又容易造成授权疲劳

这些机制都要保留，只是它们各自负责不同的故障面。ArbiterOS 的价值，在于尝试给它们补上一份共同的运行时上下文。

## 规划权与执行权分开

沿着一次真实调用往下走，责任落在这几层：

1. **Agent 与模型负责规划**：理解任务、拆步骤、选择工具，也允许在阻断后重新规划
2. **ArbiterOS 负责运行时判断**：把模型返回的工具调用转成 Instruction，追踪来源与依赖，运行策略并记录 Trace
3. **工具网关负责执行**：文件、数据库、浏览器和外部 API 的真实调用都从这里发生
4. **Sandbox、IAM 和网络出口负责刚性限制**：哪个进程能读什么、哪个身份能写什么、请求能去哪里
5. **业务系统负责最终一致性**：审批、幂等、监控、补偿和回滚仍属于具体业务，治理内核无法替代

这样一拆，规划权和执行权就不再混在一起。ArbiterOS 站在模型输出和工具执行之间，后面仍有刚性权限与业务恢复。模型可以提出"修改限流配置"，治理层先检查目标环境、参数来源和风险标签；IAM 再判断当前身份有没有权限；发布系统核对版本和变更单；动作发生后，监控与回滚流程继续负责结果。

**限制**：当前 ArbiterOS 运行在 LiteLLM 请求链路中，"控制点"首先建立在模型调用和工具格式可被接管这一前提上。要把它做成生产里的治理控制面，还要解决旁路调用、策略版本、身份绑定、高可用和故障降级。否则代理一旦不可用，系统默认放行还是默认阻断，本身就会变成新的架构风险。一种相对稳妥的做法：高风险链路默认失败关闭，低风险只读任务允许有限降级，把降级本身写进审计记录。

## 数据流比工具名更重要

ArbiterOS Kernel 位于 LiteLLM 请求链路中。请求到达后，它维护 Trace、处理元数据和消息格式；模型返回工具调用或结构化输出后，由 InstructionBuilder 解析成统一的 Instruction，交给策略模块检查。

官方 Kernel 文档里，一条 Instruction 可以记录：

- 工具名、调用参数和可选结果
- runtime_step、parent_id、source_message_id 等步骤关系
- 保密性、可信度、风险和可逆性等安全属性
- reference_tool_id 指向的上游工具调用

字段很细，落到架构上只回答一个基础问题：**策略除了知道"Agent 正在发请求"，还要知道请求里的数据从哪里来**。例如网页内容被标记为低可信度，本地密钥文件带有高保密性。后续摘要一旦引用了这两份结果，相应标签会沿指令依赖继续传播。等数据准备进入网络外发、数据库写入、文件删除这类高风险终点时，策略看到的是整条数据链，而非孤立的工具名。

同样是合法的 POST，处理方式可能完全不同：

- 发送普通测试摘要到内部白名单地址，可以放行
- 请求体引用了凭据文件，即使目标地址合法，也需要阻断
- 内容来自不可信网页，又准备进入发布或转账工具，可以先请求确认或重新规划

工具白名单回答"这个工具能不能用"，数据流还要回答"这次调用带着什么数据、从哪一步来的、要流向哪里"。Instruction 也不能被误解成可信事实——它是可追踪的中间表示，让系统看清并检查模型提出的动作；模型结论是否正确、工具解析是否完整、策略是否覆盖真实风险，仍需各自验证。

## 控制点必须在执行前

"不要读取生产配置"写在 System Prompt 里，可以减少模型主动选择这条路径；同样的边界落到文件权限和 Sandbox，进程才真的读不到。网络白名单写进策略，可以提前识别目标；真正限制连接范围，还要靠出口代理或防火墙执行。ArbiterOS 管的是中间这层判断：把路径、参数、数据来源和动作后果放到一起，在工具执行前给出放行、阻断或确认结果，并把原因写进 Trace。

先看入口：所有高风险工具调用都要经过同一个治理入口。Agent 主循环走代理，旁边的 Python 脚本却能直连数据库；浏览器工具受策略约束，MCP Server 又在宿主机上拿着完整权限——这种情况下治理覆盖率只存在于报表里。

入口收住以后，还要防着治理层变成新的超级权限中心。它需要最小权限、策略版本管理、变更审计、超时和熔断，也要避免在 Trace 里再次泄露密钥、客户数据和完整请求体。可观测性并不等于把所有内容原样记下来，日志同样需要脱敏、分级保留和访问控制。

完整调用路径：任务输入 → Agent 规划 → ArbiterOS 判断 → 工具网关执行 → Sandbox/IAM/网络约束 → 业务验证与恢复。少了前面的治理判断，动作可能来不及拦；少了后面的刚性权限和业务恢复，策略通过也不代表系统安全。

## 回滚跟着故障域走

治理讨论很容易停在"允许还是阻断"。到了工程现场，还要继续问：动作已经发生以后，哪个系统负责恢复？不同副作用属于不同故障域，回滚方式差别很大：

- 代码修改停在独立 Worktree，恢复通常是丢弃 Diff 或回退提交
- 依赖安装已经改了锁文件和本地缓存，需要额外核对制品
- 生产配置更新涉及版本、流量和实例状态，要靠发布平台回滚
- 数据库迁移可能只能执行补偿脚本
- 邮件、支付和外部通知已经离开本系统，往往没有真正的"撤销"

"策略允许"和"业务安全"之间还隔着一段恢复链路。例如 Agent 生成数据库迁移方案，ArbiterOS 可以检查目标库、SQL 类型、数据来源和风险标签，IAM 可以限制账号权限；可一旦迁移开始，版本校验、幂等、灰度、监控和补偿仍要由数据平台负责。治理内核能告诉团队哪一步被批准、哪条策略命中，却不能凭空恢复已经损坏的数据。

同样的道理适用于研发、办公和日常工具：

- 改代码：调查和生成候选 Diff 可以自动进行，push、合并、部署与迁移另设闸门
- 改架构配置：先生成变更单和流量方案，生产写入继续经过 IAM、审批、灰度与回滚
- 发邮件和处理工单：读取、归纳、生成草稿可以放宽，对外发送、关闭工单、修改 CRM 关键字段慢一步
- 整理文件和日历：普通文件按规则移动，证件和财务目录单独限制；删除先去回收站，向他人发邀请时再确认

场景不同，架构原则相同：**执行权要跟副作用绑定，恢复能力要跟故障域绑定**。

## 先写一张小策略表

落地时没必要先设计一部庞大的"Agent 宪法"。选一条任务链，把最容易造成副作用的动作写清楚，更容易暴露架构里的真实缺口。这张表可以先用在测试环境，它不是 ArbiterOS 的官方默认策略：

| 场景 | 默认处理 | 执行前再看什么 | 出问题从哪里退 |
| --- | --- | --- | --- |
| 读取普通测试日志 | 允许 | 路径、工具、Trace ID | 无状态读取，重新执行 |
| 读取密钥或生产配置 | 阻断 | 调用链、数据用途、策略版本 | 不进入后续步骤 |
| 写入测试目录 | 允许 | Diff、文件范围、测试命令 | Worktree 或提交回退 |
| 删除文件或数据 | 请求确认 | 目标、影响范围、可逆性 | 回收站、备份或补偿 |
| 访问外部网络 | 白名单 | 域名、请求参数、数据来源 | 阻断请求，轮换泄露凭据 |
| 发送邮件、关闭工单 | 草稿优先 | 收件人、原始输入、最终状态 | 撤回有限，准备人工补救 |
| 生产写入或部署 | 阻断或升级审批 | 变更单、版本、操作者 | 灰度回切或业务回滚 |

麻烦在于每一行都要对应到真实工具、真实账号和真实日志："读取密钥"由哪一层识别？软链接和脚本封装会不会绕过？网络白名单限制的是域名、IP 还是最终连接？审批通过后参数被替换了是否需要重新确认？Trace 里记录的是摘要、哈希还是完整载荷？这些问题一旦回答不清，策略文件写得再漂亮也很难成为可靠边界。

## Trace 要回答三个问题

只留下"命令失败"或"请求超时"，几乎无法复盘 Agent 为什么走到了危险步骤。ArbiterOS 会把模型响应、工具调用、策略结果和指令关系写入 Trace，其中 log/{trace_id}.json 保存按轨迹组织的指令记录。从文档给出的设计看，它要回答三件事：**输入从哪里来，哪条规则生效，确认是否真的发生**。

这类记录对策略迭代很重要：某条规则频繁命中，可能是边界画得太宽，也可能是任务本身需要拆分；误拦截集中在某类工具，说明解析器或策略缺少上下文。阻断原因能回到 Agent，低风险步骤还有机会继续，使用者也不必为了赶进度直接关闭整套护栏。

但 Trace 只能证明治理层看到了什么。它看不到的旁路、没有解析出的工具参数、业务系统内部发生的二次调用，都不能靠一条完整日志自动补齐。真实接入时最容易漏的正是这里。

## 评测数字有边界

论文在 AgentDojo 和 Agent-SafetyBench 的攻击轨迹上做确定性重放，人工复核后得到 **1,914 个危险案例**。对 OpenClaw，原生策略拦截率为 **6.17%（118/1,914）**，集成 Arbiter-K 后为 **92.95%（1,779/1,914）**。

这组数字回答的是：在论文设定的样本和重放协议下，危险步骤被拦住了多少。实验采用围绕危险步骤的 prior+current 重放，目的是减少重新规划带来的差异，并非重新运行完整的端到端任务。它不能直接等同于"生产 Agent 的安全率"——真实系统里的规划漂移、插件覆盖、旁路调用、业务状态和网络环境都还在。

安全收益也带来了可用性代价：在 OpenClaw 的 312 个良性样本上，良性通过率从 **92.95%（290/312）降到 88.78%（277/312）**。论文说明，额外误拦截主要集中在跨会话委派、日历或界面副作用、外部通信等边界动作。README 同时把"可复现的基准打包和更清晰的指标定义"列入近期工作。

就目前材料而言，把 ArbiterOS 看作一套值得验证的治理架构和原型实现更合适。距离团队自己的生产控制面，还有工具覆盖、误拦截、性能、稳定性和业务恢复等不少问题要回答。

## 从一条可回滚小链开始

第一次试跑不必接管所有 Agent。选一条边界清楚、容易验证、失败后能够恢复的测试任务：读取测试环境日志并生成摘要，可以写入内部草稿区，但不能访问凭据，也不能向外网发送数据。可以这样跑：

1. 把任务放进 Sandbox 或隔离环境，不提供生产凭据
2. 让模型请求经过 ArbiterOS，确认工具调用能被解析，Trace 能串起前后步骤
3. 先配置敏感路径、网络白名单、删除确认和远端写入确认四类规则
4. 分别跑正常任务和故意构造的越权任务，观察阻断点、误拦截和日志可读性
5. 保留人工审批与业务回滚，分别验证"策略允许"和"动作完成后可恢复"

试跑结束后，下面几项数据比一句"拦住了"更有价值：

- **工具覆盖率**：文件、网络、数据库和脚本调用有多少真正经过治理链
- **阻断准确性**：越权任务在哪一步停下，原因能否说明白
- **良性通过率**：正常任务是否被频繁打断
- **轨迹完整性**：Trace 能否还原输入、引用关系、策略版本和确认记录
- **恢复时间**：误操作或误拦截后，多久能回到明确的版本、草稿或业务回滚点

工具覆盖率往往比拦截率更早暴露问题。只统计经过 ArbiterOS 的请求，却漏掉直接脚本、MCP Server 和宿主进程，得到的高拦截率并不能代表整个系统。

Agent 还会获得更多工具，也会进入更多真实流程。模型可以负责理解和规划，执行权最好落在模型之外：意图先变成可检查的指令，数据来源、策略结果和副作用留在同一条轨迹里，最后一步再交给权限系统、业务系统和人共同决定。运行时治理的价值，就落在这条执行链上。
