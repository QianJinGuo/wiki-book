# ICML 2026 | 免训练跑赢14B模型，Sonar-TS补上时序问答规模空白

原创 让你更懂AI的 2026-07-30 12:47 北京

一句话搜遍百万点时序

## 

过去，大模型能读懂一小段曲线，却塞不下一整座时序数据库。Sonar-TS 无需训练，只用一句话，就能从百万点历史中找出所有目标形态。

近年来，随着大模型与时序基础模型的快速发展，让人用自然语言向时间序列提问（时序问答）已经取得长足进步。

但有一类听起来很朴素的问题，至今几乎无人能解：在一个数据库规模的时间序列里，用一句话找出“某种形态”出现的所有片段，比如“过去一年里，先快速上升、随后进入平台期的日子有哪些”。

本文深入解析 Griffith 大学金明课题组的 ICML 2026 工作 Sonar-TS。

该工作把这一被长期忽视的空白正式定义为新问题 NLQ4TSDB，配套提出第一个基准 NLQTSBench，并以“先搜索、再验证”的神经符号框架给出第一个可行解，重点探讨其将“形态”转化为可检索符号、以及用可执行程序做精确验证的两步设计。

本文依次讲清三件事：为什么这是个真问题、如何度量它，以及 Sonar-TS 如何在数据库规模上既读懂形态、又不失精度。

引言：一个被忽视的新问题

几乎所有时序问答工作都默认被问的是一段短序列，可真实时序是数据库规模的：一个传感器一年就是数百万点，一座工厂上万条通道。

一个数据库规模的形态查询，比如“过去一年里，先快速上升、随后进入平台期的日子有哪些”，要求系统同时满足三件事：形态理解（MP，懂“快速上升”“平台”这类形状）、数据库规模（MS，在百万点多通道上跑得动）、语言落地（NLG，把口语意图对齐到具体信号）。

而现有三类方法，每一类都恰好缺一格：

〓 图2. 相关工作能力对比：MP 形态、MS 规模、NLG 语言，三者无法兼得

Text-to-SQL 有规模、有语言，却读不懂形态；时序问答模型懂形态、懂语言，却喂不进数据库规模；经典的时序相似性搜索懂形态、有规模，却接不住自然语言。

三格俱全的那个位置，此前一直是空的。把它补上，就是 NLQ4TSDB：输入一句自然语言加一个数据库规模的时序库，输出满足形态语义的区间或事件。这不是某个方法的工程细节，而是一个没人系统研究过的新问题。

NLQTSBench：度量这个新问题

要研究一个新问题，第一步是能衡量它。NLQTSBench 是第一个面向 NLQ4TSDB 的基准，最大特征是规模：单题平均搜索空间约 1.2 万个点，而以往时序问答基准通常只有几百点。

任务从基础数值检索，递进到形态识别、周期检测、子序列匹配、复合趋势、上下文异常、因果异常，直至洞察综合，共 9 类子任务、1153 项查询。

〓 图3. NLQTSBench 任务概览：四个难度层级、九类子任务

它的标注怎么保证可靠？参数化模板生成查询，把严格符合语言描述的形态按设定信噪比注入真实背景数据，再对全部样本人工目检，让“语言描述”与“形态真值”一一对应、可审。

〓 图4. 基准数据构建流水线：参数化模板、信号注入、人工目检

Sonar-TS：先搜索，再验证

Sonar-TS 的整体框架分为三部分：离线索引、在线先搜后验、后处理，全程免训练。下面结合框架图（图 5）逐步来看。

离线阶段：系统把原始序列在年、月、日多个尺度上切窗，为每个窗口预存统计原语（slope、std 等）与 SAX 形态符号，建成可被 SQL 检索的特征表。

“形态”由此变成数据库里可索引的对象，例如“急涨又急跌”对应符号正则 [ab]+.*[de]+.*[ab]+。

在线阶段是一个“先搜索、再验证”的闭环：LLM 先把问题规划成子步骤，生成 SQL 在符号索引上粗搜候选窗口（便宜、可扩展、宁可多召回不漏）。

再生成 Python，用 DTW、PELT、Theil-Sen 等成熟算子在原始信号上逐一精确验证（准确、可解释）；执行失败则把错误回灌、闭环自纠错。

〓 图5. Sonar-TS 框架：离线构建多尺度特征表与 SAX 模式索引；在线由 LLM 规划任务、生成 SQL 检索与 Python 验证并执行；最后汇总为答案。

粗搜负责在规模上不漏，精验负责在原始数据上不错。验证通过的区间最终被整理成自然语言答案与可视化结果。

实验结果：领先，但远未解决

在长历史（数据库规模）设定下，Sonar-TS 总分 0.6144，约为最强 Text-to-SQL 基线 MAC-SQL（0.16）的 3.8 倍。

在短上下文（Lite）设定下，免训练的 Sonar-TS 取得 0.30，领先 ChatTS-14B（0.18）等时序模型。消融显示，符号粗搜与代码精验缺一不可。

但更值得注意的是另一面：即便是表现最好的 Sonar-TS，在最吃形态理解的任务上得分依然偏低。

这张榜单真正的信息不是“谁赢了”，而是“所有方法都还差得远”。对一个刚被提出的新方向来说，这恰恰是它该有的样子。

方法学贡献与讨论

5.1 它为什么重要：从应用看价值

**现** 实里大量高价值的需求，本质都是“形态查询”，却长期没有趁手的工具：金融风控要找特定形态的异动，运维监控要找“先冲高、再回落”的故障前兆，工业与能源要识别设备的异常波形，医疗要在生理信号里定位特定形态。

它们的共同点都是“数据库规模 + 形态意图”。

Sonar-TS 第一次把这件事做成了可问的查询：用一句自然语言，就能在数据库规模的历史里把符合形态的片段逐一定位出来。它全程免训练，只依赖 SQL 与 Python 这类已有基础设施，接入现有时序数据库与监控栈的成本很低。

落到贡献上，是三个“第一”：第一个被正式定义的新问题 NLQ4TSDB、第一个数据库规模且标注可审计的基准 NLQTSBench、以及第一个把可检索符号与可执行验证缝合起来的免训练框架 Sonar-TS。

5.2 与相关工作的对比

对比 Text-to-SQL：它能在规模上检索，但 SQL 只表达数值、不表达形态；Sonar-TS 用 SAX 把形态变成可检索的符号，补上了形态这一格。

对比时序问答模型（如 Time-LLM、ChatTS）：它们能理解形态，却受上下文长度限制，喂不进数据库规模；Sonar-TS 用检索代替“读全部数据”，绕开了上下文瓶颈。

对比经典时序相似性搜索：它能在规模上匹配形态，但只接受示例序列、接不住自然语言；Sonar-TS 把自然语言意图翻译成符号正则加可执行验证。

5.3 局限性与未来方向

粗搜可能漏：当 SAX 近似过粗时，候选召回可能为空，论文为此设计了回退到原始数据的机制。

形态硬任务仍弱：形状识别、复合趋势等最吃形态理解的任务得分偏低，组合语义推理远未解决。

领域适配：符号粒度与验证算子在分布外领域，可能需要重新校准。

在线成本：验证阶段依赖大模型现场生成代码，复杂查询的延迟与成本仍有优化空间。

结论

Sonar-TS 从根本原理出发，用“可检索符号加可执行验证”这一组合，回应了时序问答在“规模”与“形态”上长期无法兼得的矛盾。

比起一套最终方案，它更像是为时序社区立了一个新问题、一把尺子和一个可行的起点：把数据库规模时序的问答，从“做不到”推到了“可度量、可比较”。
