# Agent 做了这么多轮重构，企业到底该留下什么？（EventHouse 架构深化）

> 阿里云云原生（沈林），整理自第 10 届 AI + 研发数字峰会（AiDD）北京站 TOP10 最佳演讲《Agent 开发范式演进：简化多源实时上下文构建》。核心：模型/框架/Runtime 仍会变化，企业该留下的不是通用智能，而是**业务上下文**。详述 EventHouse 架构深化——消息底座 + 统一元数据层 + 语义层 + Benchmark + 语义变更 PR 治理 + 两个场景。

## 一、正交生长：留下业务上下文，不重复建通用智能

Agent 建设拆两条增长轴：
- **横向：通用智能**（Memory/Planner/Managed Runtime/Agent 协作）——模型公司和平台持续投入，企业跟进复用即可，避免重复造公共能力；今天业务自实现的能力，明天可能成平台默认配置，不适合作为长期资产。
- **纵向：业务深度**（业务事实/对象关系/统一业务语义/流程规则/行业知识与经验）——不会因模型升级自动出现，模型公司替不了。模型可帮助整理/推断/生成候选，但业务口径、数据关系、流程边界需业务侧沉淀。

判断投入是否值得长期做：**下一次模型升级后，这项投入是被替代还是被放大？**

业务上下文必须来自**持续运行的数据**：不是一次整理的静态文档，而是每天持续产生。业务事实三特点：①来自实际运行而非事后整理；②一个答案需多系统参与（客户/订单/库存/履约/客服/售后）；③状态始终变化（导出表格只代表导出时刻）。要建设一条持续数据供给"管道"：持续接入/多源汇流/增量更新/跨系统组合，随业务状态更新。**一次导入≠持续上下文。**

## 二、消息服务：企业实时数据集成的天然底座

类比 Linux 管道（进程输出接另一进程输入，互不认知），消息服务把单机模型扩展到分布式：管道一端是业务应用/数据库/SaaS/日志/IoT，另一端是业务系统/数据平台/分析/Agen。三个原因天然适合数据集成：

1. **追加写入、传输快、上下游解耦**：Append-only Log，写入路径短近硬件上限，适合高吞吐；生产者只写、消费者按位点速度读，互不等待。
2. **接入方式灵活，连接异构系统**：上游 Put 主动写 / Pull 采集；下游 Pull 读 / Push 投递。连接数据库/SaaS/日志/IoT/应用/API。
3. **数据可缓存、订阅、回放**：保留一段时间吸收流量峰值、缓冲速度差异；一次接入多路订阅；失败从历史位点回放（重试/补数/追赶）。

以 RocketMQ/Kafka/EventBridge 为代表的连接器生态：上游接 ERP/CRM/交易/数据库/文件/对象存储/微服务/API/日志/IoT；下游接数据湖/实时数仓/ETL/BI/风控/推荐/AI/监控。消息流动中完成过滤清洗/格式转换/关联补全/路由分流。消息服务正从传输组件升级为企业实时数据集成基础设施。

**当前链路较"间接"**：业务/文档/设备/外部数据 → 消息服务（供给中枢）→ 不同数据服务（关系库/搜索库/向量库/分析库）→ 经 MCP Server 标准化提供给各 Agent（Qoder/ChatGPT/Claude/自研）。

## 三、可访问 ≠ 可用：Agent 用好数据还差什么

数据可访问≠对 Agent 可用。加工/过滤/转换/同步/分散存储后，Schema/语义/血缘/实时性出现断点。Agent 需要知道：值代表什么、从哪来、经过什么变换、何时更新、是否可信、是否允许用。否则出现：数据分散找不到、口径不一致看不懂、来源不可追溯不敢用、实时离线难对齐用不准。

**三个判断**：
1. **源头数据语义持续传递演进**：源系统→消息接入→加工转换→同步存储→MCP。每环节交付的不只数据，还有数据定义/版本/变换过程/可信解释；每次交接确认三件事（含义一致/Schema 兼容/变化可追溯）；源头字段变化后语义映射存储访问契约沿链路演进。
2. **数据存储可分散，但语义和检索提前统一**：存储分散是客观状态（流/交易/湖仓/搜索/向量/外部），但理解不能分散。平台在 Agent 调用前持续构建统一认知：Catalog 找得到/Schema 语义看得懂/Entity+Lineage 跨源关联/Freshness+Quality+Policy 判可信。**把"调用时临时理解"变"调用前持续沉淀认知"**（Agent 响应时间与上下文窗口有限，不可能每次都遍历系统临时猜）。
3. **整条集成链路不断收拢**：多段拼接代价增高——上下文易断、统一管理难（Catalog 分散多套解释）、复制对齐越来越多、责任边界破碎。收拢重点不是强制搬数据，而是**一个服务对数据从进入、被理解到被使用全过程负责**。

## 四、EventHouse：一站式 Agent 实时数据服务

### 4.1 架构：消息底座 + 统一元数据层
以消息集成为数据底座，统一元数据层贯穿**加工、存储、查询、Agentic 检索**四大模块。底层消息集成：上游 Put/Pull，下游 Pull/Push；接入 Kafka/RocketMQ/MQTT/RabbitMQ/EventBridge。数据进入后让 Catalog/Schema/Semantic/Lineage 在统一元数据层持续沉淀，后续环节不必从零解释。四模块：加工（EventHouse 或流向其他）、存储（内置或开放湖格式留客户侧）、查询（EventHouse 或 Trino 联查外部）、Agentic 检索（API/CLI/MCP/IM）。**一站式≠封闭替换**（外接/开放存储/联查/元数据独立开放）。

### 4.2 语义层：让业务口径变成可执行定义
语义层不是字段说明书，而是可辅助匹配/关联/执行的定义，分**五类**：①对象语义（表列描述/业务名称/同义词）②范围语义（当前场景选哪些源、隐藏歧义字段）③关系语义（Join 条件/左右表/关系基数）④计算语义（Measure/Filter/可执行 Field SQL）⑤值语义（格式辅助/实体匹配）。
例："北京地区本季度已支付订单净收入"→"北京"匹配 region_code='BJ'、"已支付"→payment_status='PAID'、净收入→SUM(order_amount-discount_amount)。名称负责匹配、SQL 负责精确执行、关系和代表值补齐上下文。

### 4.3 平衡语义建设与使用成本
EventHouse **不用 Semantic Web Ontology / Knowledge Graph Schema**——维护成本高，无 FDE 跑不起来（Palantir Ontology 极度依赖现场工程师，是 Palantir 选客户而非客户选 Palantir）。选择平衡方案：简化语义建设（结构化定义 + 支持 wiki 弱语义，类似 Skill 灵活）；把语义理解对齐放使用环节，信 LLM 能力+上下文窗口增长 + LLM 侧缓存降成本。使用环节：先注入场景相关可信语义（只选相关一组表，一般≤15 张，不把整个库给模型），ReAct 闭环在真实执行反馈中修正——**Reason（按口径元数据推理）→ Act（生成 SQL 真实执行）→ Observe（读返回 rows/errorReason）→ Reflect（修正进入下一轮）**。语义层让第一步走对，ReAct 让走偏后有依据纠正。

### 4.4 语义初始化：先继承事实，再让 AI 提候选
四步：①继承上游 Schema/表列描述/字段类型/数据访问范围（确定性信息原样继承，不重新猜）②采样代表值（格式分布补 Format Assistance 与 Entity Matching）③发现确定关系（优先用 Schema 已有 PK/FK/关系基数，存有证据 Join）④AI 推荐候选语义（可复用 SQL Expression/无元数据声明但值得核验的补充 Join）。最终 Semantic Draft v0 待专家认证。**AI 作用是缩短从空白到可评审草案的距离，不跳过业务判断。**

### 4.5 语义认证：模型提供证据，专家承担责任
明确四类不能交给模型的业务责任：①定义责任（指标怎么算/统计口径）②关系责任（哪些表 Join/基数/是否重复计数）③边界责任（实体映射/语义适用范围）④发布责任（Owner/版本 Draft 或 Certified/出问题谁决定回滚）。机器提供来源元数据/代表值/PKFK/候选 SQL/历史查询模式，专家接受/修改/拒绝并明确适用范围与生命周期。认证后语义资产=描述+决策+责任人+版本状态+Benchmark 回归。

### 4.6 Benchmark：衡量业务答案，不只 SQL 字符串
SQL 能执行≠业务答案正确。平台自身 Benchmark + 客户专属 Benchmark。客户侧用例**三层**：
- **探索层**（扩大问题覆盖面）：验证问题是否真实可问、Agent 能否生成可执行 SQL，不一定有标准答案；AI 批量生成候选问题+SQL 人工抽样确认。
- **正确性层**（验证业务结果，主体）：Gold SQL+预期结果+业务规则；验证执行结果正确（过滤/聚合/Join/排序/口径），非同义写法差异。
- **生产可靠性层**（验证上线风险）：换说法能不能理解、歧义主动澄清、查不到如实返回、SQL 满足权限性能安全。不需最多但覆盖高频高风险。
层级越高≠价值越高；正确性层通常是主体。

### 4.7 把语义变更当受控 Pull Request
语义不是一次写死的 Prompt。每次变更内容与原因/涉及表指标问题/必须回归用例与同义问法/预期收益与潜在风险。发布门槛：核心 KPI 零回归、总体准确率不下降、延迟错误率成本达标、Owner 批准；不满足继续改或回滚。流程 **Draft→Review→Benchmark→Merge/Rollback**。把语义当代码治理，获得版本/差异/审批/回归/回滚能力。

### 4.8 从真实问答出发，持续升级闭环
最有价值 Benchmark 来自真实用户问题。记录完整 Trace：原始问题/生成的 SQL/工具调用/查询结果/最终回答。结合用户反馈+LLM Judge，领域专家确认错误归因（业务定义错/字段表选错/Join过滤聚合错/同义覆盖/多轮上下文断）。归因后两类产出：语义修复（补定义/修 Join/增可信资产与示例 SQL/新语义版本）+ Benchmark 样本（真实失败样本入测试集，多种问法/边界/正确 SQL）。离线回归→人工确认→灰度→收集线上反馈。**失败会话能变成下一轮可复用、可验证的资产。**

## 五、两个场景

**场景一：退单客户投诉溯源与流失预警**。问题"退单前 90 天内谁投诉过、投诉什么"跨时间/系统/数据类型：实时退单消息 + MySQL 在线库（客户/订单/售后工单）+ 搜索系统（对话/投诉/通话摘要）。EventHouse 围绕 customer_id+时间窗口关联成客户时间轴（12 天前首次投诉→8 天前催促→4 天前工单升级→今天退单）；多源混合检索免人工拼接。统一元数据定义"投诉"口径（含平台工单+电话），带 Catalog/Schema/血缘/新鲜度/权限入查询。输出退单名单+投诉主题+投诉到退单路径+需挽留高风险客户。业务从"谁退单了"事后统计→"为什么退单/如何提前预警"。

**场景二：制造数据一次接入，开放流出与复用**。生产质量负责人问"某产线电芯温度异常、之前出过问题，下次实时告警+同步质量库+长期归档+维修 Agent 使用"。数据来自 IoT/PLC 消息、MES/ERP、维修质量系统。EventHouse 保留一条完整一站式主链路，四环节按需开放：加工可外接流处理、存储用 Iceberg/Parquet 留企业对象存储、查询 Trino 联查 PG/MySQL、统一元数据 API/CLI/MCP/IM 开放给 Copilot/ChatGPT/Claude/Gemini/Dify/自研。不需一次性替换，加工外接/存储开放/查询联查/语义复用。

## 结语

模型/框架/Runtime 仍会变化，Agent 该留下什么：①通用智能持续跟进，但真正值得沉淀的是业务上下文（模型越强价值越大）；②消息服务已是成熟实时数据管道，下一步让 Schema/语义/血缘/实时性随数据一起到达；③链路收拢必须开放（一站式服务全链路负责+保留对外加工/开放存储/联合查询/多 Agent 接入）。Agent 长期竞争力 = 看见真实业务 + 理解企业口径 + 信任数据 + 基于信息行动。
