# 拆解智能体循环的四大模式，从人工协同到无人自治

> 模智空间（小智）。基于 Claude Code 原生能力拆解工程落地的四种循环范式。循环工程核心观点：真正的工作单元不是提示词，而是循环本身；循环选型本质是架构取舍——愿意下放多少控制权给循环，下放后靠什么机制让它停下来。

## 区分循环的核心标准

所有智能体循环都在重复三件事：触发一轮执行 → 智能体处理任务 → 执行终止（或开启下一轮）。四种循环的差异，在于将哪些环节交给系统自动处理：

- **轮次驱动（Turn-based）**：把单轮内部的工具调用审批交给系统
- **目标驱动（Goal-based）**：把判断任务是否结束的终止条件交给系统
- **时间驱动（Time-based）**：把触发机制交给设定时间
- **主动触发（Proactive）**：由定时任务或外部事件唤醒智能体，无需保持会话连接

从左到右，每一类都比前一类移交更多循环控制权。一旦选型出错，要么本该自动跑的任务还得人工盯着，要么放出一套缺少约束、极易失控的智能体。

## 类型一：轮次驱动循环

权限下放程度最低的模式。每一轮任务仍需人手动输入指令启动，但本轮内每一次工具调用不再需要人工逐个确认——对应 Claude Code 的 **Auto 自动模式**：同一轮会话中智能体直接读写文件、修改代码、运行命令，不会每操作一步就弹窗等待确认；但它不会自己开启新一轮任务（智能体会自行判断任务做完就停下）。

明显短板：停止判断完全依赖大模型自己的主观判断，是可靠性最差的校验方式。适合人机协同调试（人全程在场可及时纠正），但人一旦离开就很容易陷入**死亡循环**——没有外部机制强制它停下。结论：轮次驱动适合调试，绝对不能直接丢给无人值守运行。

## 类型二：目标驱动循环

整个体系中最关键的一级，循环第一次可以完全脱离人工自主收尾——自动开启一轮又一轮迭代，由一套**外部校验逻辑**确认任务达成后才真正停止。Claude Code 的 `/goal` 指令是典型实现：开发者预先设定完成条件，每一轮执行结束后调用一个轻量高速模型校验条件是否达成（默认 Haiku，输出「完成/未完成」+ 简短理由指导下一轮）；未满足直接开启下一轮，不把控制权交还人类；条件达成自动结束。底层实现是会话级 Stop 钩子，由独立于业务执行的另一个模型负责判断何时终止。

目标驱动效果完全取决于完成条件质量。一份高质量的完成条件需包含三要素：

1. **可量化的最终状态**：测试用例执行结果、程序编译退出码、文件数量、空的任务队列等客观指标
2. **明确校验方式**：写明智能体该如何证明任务完成（如 `npm test` 返回退出码 0、git 工作区无变更）
3. **关键约束**：过程中禁止发生的改动（如「禁止修改其他测试文件」）

**易踩坑细节**：校验模型只能读取对话记录里已输出的内容，不会自己去执行命令、读取本地文件。想校验「全部测试通过」能生效，前提是智能体主动跑测试并把结果输出到对话上下文。同时一定要加保护限制，如「最多跑 20 轮就强制停止」，防止任务永远达不到目标无休止消耗算力——这正是 Karpathy 生成-验证思路从开环升级到闭环的关键：校验逻辑足够靠谱，才能放心不用盯着运行。

## 类型三：时间驱动循环

目标驱动由智能体自身执行结果推进；时间驱动面向外部现实场景：等待项目构建结束、拉取 PR 的 CI 检测结果、监控任务队列堆积——不需要一轮结束立刻跑下一轮，而是等到设定时间再启动一次检查。Claude Code 的 `/loop` 是对应的基础能力：

- `-loop 5m check whether the deploy finished`：每 5 分钟检查一次部署完成情况
- 不填时间间隔：每轮由智能体动态选择等待时长（构建还在跑就短间隔轮询，系统空闲就拉长等待）
- 裸指令 `/loop`：执行内置维护任务，可自定义 loop.md 作为循环脚本

明确局限：`/loop` 只作用于当前会话，只有会话保持打开、处于空闲状态才会触发；支持恢复会话但最多维持 7 天。做轮询任务是优势（开销小、复用当前会话权限和工具），但时间驱动依旧依赖人——终端会话不能关掉。想摆脱这个限制，就要进一步下放触发权限。

## 类型四：主动触发循环

依靠定时调度或外部事件启动，不需要维持会话，本地机器也不必一直开机——行业常说的主动型智能体：不再是需要人手动操作的工具，而是可以自主干活的协作角色。Claude Code 提供三种主动触发实现：

- **Routines 云例行任务**：跑在 Anthropic 托管服务器上，不用会话、本地电脑可关机，完全自主运行。每次启动都是全新环境、访问不了本地文件，最短调度间隔 1 小时——适合「不管电脑开没开都要稳定执行」的任务
- **桌面端定时任务**：本机运行，最短间隔 1 分钟，可读取本地代码仓库与密钥——适合需要操作本地项目、使用本机凭证的自动化
- **事件通道**：跳出定时轮询思路，CI 流水线报错时事件直接推送给智能体立刻启动处理——主动不等于只能定时跑，也可以是事件驱动

官方文档典型用法：夜间自动化测试、早上批量处理问题；无人值守智能体到点自动唤醒，从待办列表取高优先级任务，通过质量检查后自动提交 PR，最后输出报告。前提是前面三级循环都已打磨稳定。

## 失败模式：死亡循环

越往上走，系统接管的流程越多，一旦出错人能介入的机会越少。把触发和停止权限全部交给系统、却没有靠谱校验机制，得到的不是高效自动化而是死亡循环：反复重试错误方案、深夜持续消耗资源、输出一堆看似有理但完全无效的内容。

市面上不少工具号称能解决 AI 编码助手的死亡循环，但根源不在工具本身，而是一条适用于全部模式的设计准则：**循环的终止条件必须是智能体需要达标才能停下的客观标准，不能交给模型自行判断**——需要可衡量的目标、硬性的最大轮次限制、一套独立于模型主观判断的检查逻辑。这套校验逻辑恰恰是目标驱动模式的核心，所以必须先做扎实目标驱动，再去做自动触发。跳过校验直接上主动模式，只会白白消耗成本产出垃圾结果。

## 搭建自动化流程：递进升级

四种循环不是平行备选，而是递进关系，稳妥的开发方式是逐级升级、每一步验证没问题再下放更多权限：

1. **轮次驱动开始，人工监督**：开启 Auto 模式运行任务，观察出错场景，摸清边界
2. **搭建校验逻辑，升级目标驱动**：把模糊指令「优化登录流程」改写为可校验条件「登录测试用例全部通过，原有用例无报错」，循环实现自动闭环，观察校验机制能否捕捉原本要人才能发现的故障
3. **外部状态依赖时钟，切换时间驱动**：校验逻辑足够可信且任务由外部状态驱动（部署、PR），切换到 `/loop` 时间驱动
4. **完全移交触发能力**：整套流程验证稳定后升级为 Routine 云任务或桌面定时任务，实现无人值守

每向上晋升一级，都要求校验器先通过考验——**智能体能拥有多大自主性，取决于能做到多强的校验能力**，这是开环、闭环思想落到工程上的实操方案。

**边界**：四种循环都属于单一触发源的独立循环。业务需要多套任务并行执行、互相流转时，单纯升级循环模式解决不了，要用另一套方案——图工程（Graph Engineering），依靠节点、连线、共享状态编排复杂流程；图里的每一个节点依旧可以套用四种循环选型。

## 常见问题

- **目标驱动 vs 时间驱动**：目标驱动上一轮结束立刻启动下一轮，靠校验结果判断要不要停，适合有明确终点的任务；时间驱动等到指定时间间隔才启动、由时钟控制，需要人工停止。有可验证完成状态选目标驱动；需持续轮询外部变化（部署、PR）选时间驱动
- **如何防止死亡循环**：给循环设置硬性校验终止条件——用可量化指标（测试通过、编译成功、队列为空）代替模糊描述 + 最大轮次上限（如最多 20 轮强制退出），终止逻辑不能依赖模型主观判断
- **夜间无人自动运行选哪种**：主动触发循环（云例行任务或桌面定时任务，不用保持会话，云任务甚至不需要电脑开机），重要前提是该任务已用目标驱动模式跑通、校验逻辑稳定可靠
