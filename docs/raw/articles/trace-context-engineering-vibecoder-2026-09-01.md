生产 Agent 给出错误答案时，最后一句话往往只是症状。真正的故障源可能是一段过时的 Skill、缺失的知识库条目、写错的工具 schema，也可能是 system prompt 少了一条约束。arXiv 论文 TRACE 研究的就是这个问题：能不能利用历史执行轨迹，把用户纠正转成可审查的上下文缺陷单，并定位应该新增哪份内容、更新哪份文件。

## TRACE 解决的是上下文运维

TRACE 的全名是 TRajectory Attribution for Automated Context Engineering。它不训练模型权重，处理对象是 system prompt、tool prompt、知识库、知识图谱和 Skill 文件。这个边界很重要。用户说"答案不对"，并不能直接推出"Prompt 写坏了"。一次 Agent 执行同时读了哪些文件、选了哪个工具、拿到了什么结果、如何引用这些来源，才构成真正可排查的证据链。论文把流程拆成 Detector、Root Cause、Recommender 三个 Agent，最后保留 Human Review。批准以后才把建议应用回上下文层。

Detector 从纠正、重述、负面表达、放弃会话和工具执行错误里识别 DSAT，也就是用户不满意。Root Cause 负责定位故障最早从哪个执行节点进入。Recommender 会打开当前上下文文件，核对权威来源，再给出 CREATE、UPDATE、DELETE 或 NO_ACTION 建议。

论文的量化结果没有覆盖自动写回，也没有测补丁部署后的任务成功率。它评测到的是诊断和建议阶段。

## 归因算法是一轮逆序阅读

论文先从用户纠正和 Agent 回答中抽出 delta：用户期望 X，系统实际给出 Y。这个差值扮演文字版 loss signal。随后，Root Cause 把完整轨迹按逆时间顺序整理：最终回答、工具输出、推理与来源引用、输入和上下文。所有节点一起放进一次 LLM 调用，目标是找到 delta 第一次出现的最早节点。更晚的错误节点可能只是在传播上游问题。

论文还把轨迹画成上下文图，节点代表 query、prompt、tool、KB、skill 和 response，边表示上下文如何流入后续决策。

这里要读准实现：上下文图主要用于建模和解释，主算法并不遍历这张图，也没有做结构化反事实推断。实际过程是一轮 LLM 对逆序证据包的整体比较。论文把它称为 delta-guided holistic attribution。这个设计对级联故障很合适。旧 SOP 会让后面的 SQL 结果、检索和回答都显得可疑。逐节点判断"哪里含有错误"容易抓到多个症状；全局比较更有机会找到第一次引错的位置。代价也清楚。系统要保留结构化轨迹，论文尤其依赖推理中对 KB 或 SOP 的来源引用。现实平台未必允许保存完整思维链。轨迹只有工具调用和可审计决策摘要时，72.7% 的归因结果还能保留多少，论文没有测。

## CREATE 与 UPDATE 必须打开文件

从一句"你给的信息错了"，无法判断知识库里完全没有这条信息，还是已经有一条过时版本。两种情况在对话里都表现为用户纠正，修复动作却不同。Recommender 因此把 Root Cause 的输出当成候选假设。它检查内容是否存在、是否能被检索、内容是否正确、多个来源是否一致。缺失时 CREATE，陈旧时 UPDATE，检索失败时更新路由，权威来源不明确时标成 AMBIGUOUS 交给人处理。

这部分有一组很有决策价值的消融。在 KB gap/stale 子集上，主动读取文件后的操作准确率为 83%，不探索、直接接受上游结论时为 33%。50 个百分点的差距说明，存在性判断不能靠措辞分类。

## 72.7%、96%、82% 分别代表什么

论文构造了 75 条轨迹，其中 60 条带 DSAT 和已知根因，15 条是正常对照。六类故障覆盖过时 Skill、陈旧 KB、缺失 KB、工具提示错误、system prompt 缺口和检索失败。所有定量结果来自这套合成数据。

72.7% 是 Root Cause 的根因节点 Acc@1。85% 是正确节点进入归因前三。96% 是 Recommender 在全部 60 条 DSAT 上选择 CRUD 操作的总体准确率。82% 要求操作类型和目标文件路径同时命中。

82% 没有执行修改，也没有重新跑任务。它表示作者标签中的操作和路径被命中，不能翻译成"线上自动修好 82% 的 Agent 故障"。公开材料还有几处需要谨慎。主文把 end-to-end 定义成 operation 与 path 同时正确；附录的累计准确率公式却要求 DSAT、node、CRUD 同时正确，并且没有 path。两套定义不兼容。若强制 node 正确，端到端结果不可能高于 72.7%。复杂度也出现三套划分：主文是 2–8、9–11、15–16 节点；复现附录写成 2–3、4–5、6+；消融又把 14–15 节点叫作 complex。72.7% 和 96% 也无法由 n=60 的整数正确数按常规四舍五入直接得到。论文没有给逐条预测、混淆矩阵、模型版本、temperature、运行次数或 bootstrap 配置。

holistic 40% 对 iterative 20% 的消融只有 10 条长轨迹，大致就是 4 条对 2 条。它能支持继续验证整体归因，支撑不了稳定两倍提升或普遍 16 倍成本优势。调用次数少也不等于 token、延迟和费用同比例下降。

## 这套思路怎么落到生产

我会先把 TRACE 放在只读诊断层。输入是经过脱敏的轨迹和固定版本的上下文仓库，输出是一张缺陷单：用户纠正、候选根因、责任文件、权威依据、建议操作和影响范围。下一步生成可审查 diff，并自动构造失败用例。候选修改先跑历史回放和独立保留集，由文件 Owner 审核后进入小流量灰度。监控异常时回滚到上一版上下文。

第一批实验可以只聚焦 KB GAP 与 STALE。这是论文机制最清楚、消融信息量最高的部分。真实盲审结果如果没有复现明显差距，就应停下来修正数据分布和探索策略，没必要继续穷举更多合成故障类型。

## 总结

TRACE 最值得借鉴的设计，是把根因定位和文件验证拆成两个阶段。轨迹负责缩小范围，当前文件与权威来源负责决定怎么改。它把失败会话推进到了工程可处理的上下文缺陷单。论文公开证据仍停在合成诊断 benchmark。arXiv v1 源包里没有 75 条轨迹和文中提到的验证脚本，生产验证也没有可审计指标。现阶段适合做只读影子试验，保留人工审核、回放、灰度和回滚。自动写回要等真实数据把这条证据链跑通。
