# Claude Opus 5 系统提示词疑似泄露：Agent 规则到底该如何定？



架构师（JiaGouX）我们都是架构师！  
架构未来，你来不来？

  


* * *

做 Agent 做久了，团队很容易养成一个习惯：每出一次问题，就往系统提示词里补一句。

误删文件，补一条确认；测试没跑，补一条验证；工具调用错了，再塞几个示例。刚开始每条都很合理。半年后，Prompt 越写越长，团队却很难说清哪些规则仍然有效，哪些早该交给工具、代码和权限系统。

今天，我找了三份公开流传的 Claude Opus 5 样本。它们分别有 135,669、202,762 和 224,359 字节，行数、哈希和结构都对不上。现有证据无法还原各自的提取链路，也不足以确认哪一份是官方逐字原文。恰恰是这些差异，把另一个问题摊开了：大家口中的“系统提示词”，可能早已混入工具 Schema、记忆规则、Skill 注册表和运行环境。

**比起盘点 Claude 写了多少条规则，我更关心一个做 Agent 绕不开的问题：一条规则，到底该放进 Prompt，还是交给工具、记忆、权限和评测？**

我现在更倾向于把它看成一个规则归属问题：**离事实越近、失败代价越高，越不能只靠 Prompt。**

* * *

##  太长不看版

  * • 公开流传的 Opus 5 文件至少有三份不同样本，“13.5 万字符完整泄露”不宜当成已证实事实。这里的体量均按字节数统计。
  * • 三份样本的收录边界不同：有的像结构化阅读版，有的接近运行时上下文快照，还有一份混入了更多 API 与 Artifact 开发说明。
  * • 同一时间，Anthropic 公开表示，Claude Code 面向 Opus 5、Fable 5 等新模型删掉了超过 80% 的系统提示词，在其编码评测上没有可测量的损失。
  * • 一项第三方客户端实验测得，手写策略正文减少约 81%；Opus 5 又增加了模型专属说明，工具描述仍有 37,167 个字符。“80%”不是总上下文的缩减比例。
  * • 需要模型结合现场判断的规则可以留在 Prompt；越接近事实、越不能出错的约束，越要落到工具、代码、权限和审批，最后用评测与日志验证。

* * *

## 三份样本是真是假？目前还不能下结论

Anthropic 官方的 `System Prompts` 页面列出了 2026 年 7 月 24 日的 Claude Opus 5 条目。官方也明确写着，这个页面记录的是 `claude.ai` 网页端和移动端使用的核心系统提示词，相关更新不适用于 Claude API。

官方没有确认几个 GitHub 仓库的提取方法，也没有为其中任何一份文件的完整性背书。因此，“官方确实发布过 Opus 5 系统提示词”和“网上这三份文件是官方逐字原文”，是两件不同的事。

三份公开样本的差异很具体：

  * • `Eversmile12/leaked-llm-prompts`：135,669 字节，1,510 行；
  * • `elder-plinius/CL4R1T4S`：202,762 字节，2,049 行；
  * • `asgeirtj/system_prompts_leaks`：224,359 字节，3,677 行。

能确认的基本到这里。再往下，仓库作者对提取方式和完整性的描述，只能算发布者自述；服务端有没有继续拼接内容、采集账号开了哪些能力、哪一份覆盖最广，目前都没有独立证据。

真假暂时说不清，但文件本身仍有分析价值：我们看到的究竟是不是一段单独的行为 Prompt？工具 Schema、Skills、网络白名单和文件系统配置都出现在其中，收录范围已经超出核心行为 Prompt，更接近不同产品环境在某个时刻组装出的上下文快照。

**更稳妥的称呼是“第三方公开样本”。** 文件大小不代表真实性或完整性，能继续讨论的，是其中确实出现了哪些结构，以及这些结构在 Agent 系统里分别承担什么工作。

## 十几万字节的公开样本，怎么读才有用

十几万字节的公开样本，如果逐行从头读到尾，很容易读着读着只记住几句醒目的规则。碰到这类文件，我习惯先确认样本，再看结构差异，最后才回到具体措辞。

### 先确认自己读的是哪一份

先记录 URL、提交时间、产品端、版本、文件大小和哈希。最小的一组命令就够了：
    
    
    wc -l -w -c prompt.md  
    shasum -a 256 prompt.md  
    rg -n '^(#|##|###|<[^/!][^>]*>)' prompt.md

前两条用来确认我们谈的是不是同一份文件，最后一条先抽出 Markdown 标题和 XML 标签。采集方法、账号能力和服务端链路如果无从核实，就直接记成未知。以后再出现一个所谓“完整版”，也不至于把不同样本混在一起比较。

### 先看结构，别急着摘句子

可以先把内容粗分为稳定行为、产品能力、用户与会话状态、工具 Schema、Skills 与参考文件、网络和文件系统限制。示例代码、迁移说明和开发文档再单独归到一起。

这一步能避免一个常见误判：看到一份文件有 20 万字节，就以为厂商写了 20 万字节的行为指令。实际上，其中很大一部分可能是接口定义、当前状态和按产品能力注入的说明。

### 好句子先别急着抄

一句话读起来很有道理，还不等于放进自己的 Agent 也有用。我通常会继续追问：

  * • 它在解决什么失败？
  * • 只对哪类任务有效？
  * • 什么条件下触发？
  * • 希望模型采取什么动作？
  * • 怎样证明它真的有用？

比如 `did the user say this?`，它针对的失败很具体：模型把自己的推断存成用户事实。把它变成自己的设计时，还要补上来源、时间、证据类型和修改入口，再用“用户明确陈述、上下文暗示、模型自行推断”三组任务测试。到这里，原文中的一句提醒才变成可实现、可验证的规则。

### 再找这条规则该由谁负责

最后再问，这条规则应该靠 Prompt 提醒，还是由工具接口、Skill、记忆、权限或代码强制执行。行为原则可以留在 Prompt；参数和错误语义写进工具；低频专业流程按需加载；长期事实进入带来源的记忆；付款、删除和生产写入则交给权限与审批。

读这类 Prompt，能带回自己项目的，是它暴露出来的失败模式，以及处理这些失败的分工思路。产品、模型、工具和风险都不同，原句照搬到另一套 Agent 里，未必还能解决同一个问题。

## 三份样本，收录的不是同一个东西

如果只看文件大小，很容易把三份样本排成“普通版、完整版、超完整版”。逐段看下来，它们分别呈现出不同的整理和采集边界。

  
  


图 1：文件更长，首先代表收录范围更宽，不代表更真或更完整

### 135,669 字节：一份结构化阅读版

`Eversmile12/leaked-llm-prompts` 这份样本做过明显的 Markdown 标题化。它从 `claude_behavior`、`memory_filesystem` 展开，后面依次列出工具 Schema、Computer Use、搜索、引用和环境说明。阅读很方便，但这种整齐本身也说明它不是未经处理的原始输入形态。

里面有一句很短的规则：

> “A prompt implying a file is present doesn't mean one is”

提示里暗示“文件已经上传”，不代表文件真的存在，Claude 要自行核验。

这条规则提醒模型，不要把用户措辞直接当成环境事实。不过，提醒只能促使它去核验，不能替它给出结果。文件是否存在，仍要看 `view`、目录列表或文件系统的返回值。

**Prompt 可以要求模型先查证，证据只能来自工具和环境。**

同一份样本的记忆规则里还有一句：

> “The test for every line: did the user say this?”

每一条准备写入记忆的信息，都先问一句：这是用户说的吗？如果只是模型推断出来的，就不该当作用户事实长期保存。

这条规则先管来源，再谈记忆容量。放到自己的系统里，记忆写入至少要带上来源、时间和对应证据；用户明确陈述、模型观察和模型推断也不宜混在同一个事实层。否则，一句写在 Prompt 里的提醒，很难挡住错误记忆在多轮任务里越滚越真。

### 202,762 字节：接近运行时上下文快照

`elder-plinius/CL4R1T4S` 保留了更多 XML 标签。除了行为、记忆、搜索和版权规则，尾部还能看到 Functions、引用说明、Skills 注册表、网络白名单、文件系统配置以及 Thinking Behavior。

文件系统配置里直接写着：

> “The following directories are mounted read-only”

后面列出了上传目录、会话记录和 Skills 目录，并提醒 Claude 不要尝试修改。

边界最终由 `mounted read-only` 守住。“不要修改”帮助模型理解该怎么做；即使模型判断失误，文件系统仍会拒绝写入。网络白名单也是同样的设计：Prompt 可以解释限制和失败原因，能访问哪些域名仍由出口代理决定。

这份样本呈现出“行为规则 + 当前可用能力 + 运行环境”的组合。把它全部叫作 Prompt，会掩盖一个重要区别：有些文字在影响模型判断，有些配置已经在系统层强制执行。

### 224,359 字节：收录范围更宽的组合上下文

`asgeirtj/system_prompts_leaks` 前半段能看到相似的行为、记忆和产品能力规则，后半段却继续出现 Storage API 的 JavaScript 示例、React Artifact 约束、Claude API 请求、MCP 结果解析、上下文窗口管理和错误处理。

例如，它在 API 相关说明里写道：

> “Claude has no memory between completions. Always include all relevant state in each request.”

结合上下文看，这是写给 API 调用方的状态管理要求：模型两次生成之间不会替应用保存业务状态，调用方需要把本轮所需状态重新组装进请求。它和 Claude 在网页产品里的记忆功能并不冲突，因为前者谈的是模型调用，后者依赖产品侧的存储和运行时注入。

这些内容已经超出核心行为规则。这份 3,677 行的样本可能把行为 Prompt、工具与环境注入、Artifact 开发指南以及其他开发上下文收在了一起，不能仅凭篇幅就称它为“更完整的官方 Prompt”。

把三份文件叠在一起，大致能看见一条装配顺序。底部是相对稳定的产品身份、安全和行为原则；往上是搜索、引用、记忆、Artifact、连接器等产品能力；再往上是用户偏好、历史记忆、当前文件和任务状态；工具 Schema、Skills、网络、文件系统与运行时限制，则跟着具体环境进入请求。这是根据样本做的工程归纳，并不是 Anthropic 公布的官方架构。

一次请求到底装进多少内容，取决于产品端、账号能力、功能开关、可用工具和采集方式。文件更长，首先说明收录范围更宽；在没有提取链路的情况下，它不能证明规则更权威，也不能证明模型更强。

## 一条规则放在哪里，我会先问三件事

三份样本读到最后，我更想顺着每条规则追下去：它为什么出现，又该由哪一层负责。单独摘一句漂亮 Prompt，反而容易漏掉它背后的工具和运行环境。

我现在通常先问三件事。

第一，这条规则是否需要模型结合现场判断。像“先理解现有代码，再做最小修改”，具体怎样才算小，要看仓库结构、调用链和团队习惯，适合留给 Prompt。Todo 状态只能取 `pending | in_progress | completed`，则是确定的接口约束，写进 Schema 比反复提醒模型更稳。

第二，规则失效后的损失能不能恢复。注释多写了一段，通常可以在 Code Review 里改回来；误删生产数据、把邮件发给错误的人、同一笔订单扣款两次，代价完全不同。后几种情况需要代码不变量、最小权限和人工审批，Prompt 只能提前提醒。

第三，哪一层离事实最近，又能留下验证证据。文件是否存在，文件系统最清楚；订单有没有重复记账，数据库约束和账本最清楚；一条规则删掉后成功率是否下降，则要看固定任务、日志和回归评测。

**需要现场判断的交给模型，必须成立的落到能强制执行的那一层，是否有效再交给评测和日志。**

## 删掉 80%，删的是什么

带着这三个问题，再看 Anthropic 技术团队成员 Thariq Shihipar 在官方博客披露的调整，就容易理解一些：面向 Claude Opus 5、Fable 5 等新模型，Claude Code 删掉了超过 80% 的系统提示词，在他们的编码评测上没有可测量的损失。

这句话不能脱离它的前提：产品是 Claude Code，模型是 Opus 5、Fable 5 等新一代模型，验证手段是 Anthropic 自己的编码评测。离开这些前提，80% 就失去了原来的分母。我更想追的是，哪些内容被删了，原来由它们承担的责任后来去了哪里。

早期 Claude Code 曾用很硬的规则限制代码注释：默认不写注释，不写多段 docstring 和多行注释块，也不要自行创建计划或分析文档。旧模型判断力有限，这类规则能压住一些常见问题，代价是遇到复杂代码或有特殊规范的仓库时，规则很容易和用户要求打架。

新版只保留了一句更依赖现场的信息：写出来的代码要像周围的代码，匹配现有的注释密度、命名和惯用写法。

工具也采用了类似思路。Todo 工具不需要在系统提示词里反复讲状态如何流转，只要把 `status` 定义为 `pending | in_progress | completed`，再明确同一时间保留一个 `in_progress`，接口本身就在表达行为边界。

代码审查、验证这类重要但非每次都需要的说明，被迁到按需加载的 Skills。部分工具通过延迟加载，在实际用到时再搜索完整定义。`CLAUDE.md` 则尽量保持轻量，把篇幅留给仓库里看不出来的坑，而不是复述目录和代码已经表达的信息。

Anthropic 还把这套检查放进了 Claude Code 的 `/doctor` 命令，用来发现过重的 Skills 和 `CLAUDE.md`。

从官方给出的例子看，删掉的主要是重复说明和新模型已经能结合环境判断的内容。有些约束随之消失，有些换了位置，进入工具接口、Skills 和参考文件；还有一些本来就由运行时负责。

从结构上看，这次变化也不只是把旧 Prompt 截短。旧路径里的 `Doing tasks`、`Executing actions with care`、`Text output` 等六段策略正文，被收成一段约 1,702 字符的 `Harness`。里面主要交代终端如何呈现 Markdown、工具调用被拒绝意味着什么，以及当前执行环境有哪些约束。自然语言仍然存在，只是从逐项规定模型行为，转向解释运行环境和交互语义。

另一份针对 Claude Code 客户端的公开实验，把这层差别量化了。实验者将 CLI 指向本地 HTTP 服务，记录客户端实际发出的请求，再按模型统计其中的系统内容和工具描述。它不是 Anthropic 的官方测量，相关数字也只代表这套实验条件下的客户端可见部分。

这组结果也说明了“80%”的分母。只统计手写的策略正文，旧路径是 12,443 个字符，新路径是 2,308 个字符，减少约 81%，和官方说法基本一致。这轮精简在 Opus 4.8 所走的路径上已经发生，不能理解成 Opus 5 相比 Opus 4.8 又缩短了 80%。客户端实际发出的系统内容里，Opus 4.8 是 4,467 个字符，Opus 5 反而回到 7,694 个字符，差值主要来自 `Delivering work` 和 `Corrections` 两段 Opus 5 专属说明。

实验还发现，在当时的 CLI 版本里，走新策略还是旧策略，取决于客户端对 `model id` 和 provider 的分流。未被识别的模型名，如果配合 Bedrock、Vertex 或自定义 `base URL`，可能回到 15,225 字符的旧路径；Opus 5 新增的两段说明则挂在模型 capability 上。这些实现以后可能变化，但有一点对排查很实用：审一份 Prompt 文件还不够，客户端最终选中哪套规则，也受路由条件、功能开关和版本影响。

工具描述仍然更大。在同一实验里，它从 53,328 个字符降到 37,167 个字符。即使系统策略正文大幅精简，工具接口依旧占着很大一块上下文。

这组数据适合解释 Claude Code 客户端如何组装请求，不能直接当成模型最终收到的全部上下文。它来自第三方实验，只对应当时的 CLI 版本、模型路由和统计方法；服务端还可能继续追加内容。**这里的 80% 指一组历史策略正文，不等于总上下文也缩小 80%。** 新模型仍会针对新的失败模式增加专门规则。

### 自己复核时，静态文件还不够

如果要判断自己使用的 Claude Code 到底装进了什么，只比较仓库里的 Prompt 文件还不够。静态文件能说明代码里有哪些候选内容，运行时究竟选了哪条路径，还要结合一次受控请求来看。

我一般把复核过程控制在四步：

  1. 1\. 固定 CLI 版本、`model id`、provider、`base URL` 和功能开关，避免一次比较里同时变化多个条件。
  2. 2\. 在隔离环境里把请求指向本地记录服务。保存请求体前先剔除 `Authorization`、Cookie 和其他凭据，记录完成后返回固定错误，不让请求继续访问外部模型服务。
  3. 3\. 每次只改变一个条件，分别统计 system 内容、工具描述和其他消息；文件大小、字符数与 token 数也分开记录。
  4. 4\. 把结论明确标成“客户端可见部分”。服务端可能追加的安全规则、产品状态和路由信息，客户端抓包无法证明其存在或不存在。

这样得到的不是一份“完整 Prompt”，而是一条可复现的客户端装配记录。以后 CLI 升级、切换 provider 或更换模型时，也能知道差异来自正文、工具，还是路由条件。

前面的公开样本统计的是多种内容组装后的体量，Anthropic 所说的 80% 特指 Claude Code 系统提示词的精简。两边的统计对象不同。上下文可以继续丰富，同时减少每次都要常驻的自然语言规则。规则是否继续存在，要看工具、Skills、运行时和评测有没有承担起它原来的责任。

* * *

## 拿一次支付回调故障来对照

前面的判断，放进一次常见的研发故障里，才看得出是否站得住。

假设线上出现一个问题：支付平台重复发送回调，同一笔订单被记账两次。研发 Agent 能读仓库、改代码、跑测试并创建 PR。我们希望它修掉重复记账，又不希望它碰生产数据库、顺手重构整个支付模块，或者在验证不足时自动合并。

到了这一步，Prompt、工具、Skills、记忆、权限和评测各自该负责什么，就具体了。

  
研发 Agent 修复支付重复回调时的验证、审批与幂等执行流程

图 4：Agent 负责提出和验证修复，重复记账仍由代码不变量与数据库约束拦住

### Prompt：告诉它做事时优先考虑什么

Prompt 适合表达通用目标和行为倾向，例如：先理解现有实现，再做最小范围修改；遵循仓库风格；遇到需求歧义先暴露假设；交付时说明改动、验证结果和剩余风险。

这些话给模型留下了结合现场判断的空间。Agent 读到支付模块大量使用事务脚本，就不该因为自己偏爱领域模型而重写整条链路；仓库只在复杂并发处写注释，也没有必要给每个判断都补一段解释。

前面那句“提示里暗示有文件，不代表文件真的存在”也属于这一层。它要求模型保持核验意识，却没有替模型证明任何事实。

同样，**“不要重复记账”不能只写在 Prompt 里。** 模型理解了目标，并不等于系统已经保证幂等。

最后采用数据库唯一约束、条件写入，还是在事务里登记已处理事件，要看现有架构。无论选哪种，重复回调只能产生一笔账都应该成为代码能够强制执行、测试能够反复验证的业务不变量。

### 工具：把能力和错误说清楚

Agent 能做什么，取决于它拿到的接口。

这个任务里，`read_file`、`search_code`、`edit_file`、`run_test` 和 `create_pr` 应该有清楚的参数、返回结构和错误语义。文件存在性由 `read_file` 或目录查询返回，不靠模型猜。`run_test` 如果失败，也需要区分测试断言失败、依赖缺失、命令超时和权限拒绝。只返回一个 `failed`，模型很容易把环境问题误判成代码问题，然后反复修改实现。

任务状态也一样。与其在 Prompt 里写几段“先计划、再执行、完成后更新”，不如让工具只接受 `pending`、`in_progress`、`completed` 三种状态，并拒绝不合法的迁移。

### Skills 和项目规则：只在需要时加载专业做法

支付回调有一组低频但关键的验证知识：同一事件重复投递、两个线程并发处理、事务回滚后重试、账本唯一键冲突、通知与记账的先后关系。如果每次改前端都让这些内容常驻上下文，既浪费注意力，也容易和别的模块规则互相干扰。

这组验证知识可以放进支付模块的 Skill 或项目规则。Agent 进入这一模块时再加载，并按照仓库真实实现执行，例如：

  * • 使用同一个 `event_id` 连续回放两次，账本只能新增一条；
  * • 并发执行两次回调，最终余额和订单状态必须一致；
  * • 模拟记账后通知失败，重试不能再次入账；
  * • 修改数据库约束时，同时检查迁移、回滚脚本和旧数据兼容性。

这些验收经验只在处理支付模块时加载就够了。能写进测试、固定夹具和现有实现的部分，也比一段泛泛的文字说明更可靠。

### 记忆：让过去有条件地影响下一次任务

如果 Agent 在排查中确认了一个长期事实，比如“支付回调先写事件表，再由 outbox 异步记账”，这类项目知识可以带着来源、提交版本和时间进入记忆。下次处理同一模块时，它能少走一点弯路。

一次失败推测则不该自动变成长期事实。某次测试环境网络抖动，不能被记成“支付服务经常超时”；模型猜测用户喜欢某种实现，也不能替团队写进项目约定。

样本里的“did the user say this?”问的就是来源。换到生活助手里，用户明确说过“订高铁票优先靠窗”，可以作为偏好保存；某次临时选了过道座，未必意味着长期偏好改变。谁说的、从哪里来的、何时更新、怎样修正和删除，都应该跟着记忆一起保存。

《[Agent Memory 架构解析：过去的信息，凭什么影响未来？](<https://mp.weixin.qq.com/s?__biz=MzAwNjQwNzU2NQ==&mid=2650409319&idx=1&sn=0301eb71a592e20188e071a238fcd9c8&scene=21#wechat_redirect>)》讨论的也是这层问题。向量库解决了存取，记忆系统还得回答：过去的哪条信息，有资格进入下一次决策。

### 权限和审批：把不能做的事真的拦住

这个任务里，风险最大的一种错位，是把“未经确认不要操作生产环境”写进 Prompt 后，就以为边界已经存在。

如果 Agent 使用的凭证本来就能写生产库，这句话仍然只是提醒。能落地的边界来自系统本身：开发环境拿不到生产凭证，数据库工具默认只读，PR 合并和发布需要独立审批，危险命令在执行层被拒绝，拒绝原因进入审计日志。

CL4R1T4S 样本里的只读挂载就是一个很具体的例子。模型收到“不修改”的文字约束，文件系统同时收紧写权限。即便前一层偶尔判断错了，后一层仍能把损失挡住。

付款、报销、邮件外发、删除数据、合并 PR 也一样。模型可以判断何时应该申请权限，最后能否执行，仍由权限系统和审批链决定。

《[OpenClaw 安全，不是多写几句确认就够了：架构师视角下的三层防线与落地实践](<https://mp.weixin.qq.com/s?__biz=MzAwNjQwNzU2NQ==&mid=2650408683&idx=1&sn=afd67e40b84846b7e0006c08cb97cb04&scene=21#wechat_redirect>)》里那三层防线，放到这里仍然成立：聊天里的约束负责提醒，工具权限限制可达范围，沙箱和审批守住不可逆动作。

### 评测和日志：让修改有证据可查

Agent 创建 PR 后，一条完整轨迹至少包括：使用的模型与 Harness 版本、加载过的规则、工具调用、代码 Diff、测试结果、权限拒绝和最终停止原因。

只有一个“测试通过”还不够。针对重复记账，可以固定几组回归场景：重复事件、并发回调、回滚重试、乱序到达、缺失字段和生产写入拦截。失败时还要分清是实现错误、工具错误、环境错误还是权限错误。

这样，下次删掉一条 Prompt、调整一个工具参数，或者升级模型时，团队才知道成功率、成本和延迟发生了什么变化。出了问题，也能把模型与整套 Harness 一起回到上一版。

《[Cursor 复盘 Harness：模型决定能力上限，Harness 决定生产下限](<https://mp.weixin.qq.com/s?__biz=MzAwNjQwNzU2NQ==&mid=2650409236&idx=1&sn=71ae43ca6ec5b3cb1f82c258b1542271&scene=21#wechat_redirect>)》里讨论过同一个问题：发布和评测要覆盖模型、Prompt、工具、规则和运行时的组合，单独记录一个 `model id` 远远不够。

## 一套已经变长的 Prompt，可以从哪里动手

如果要清理团队现有的 Prompt，我不会因为 Anthropic 删掉了 80%，就照这个比例大砍。很多旧规则当初确实解决过问题，只是模型、工具和代码库都变了，它们该留在哪一层，值得重新过一遍。

可以先挑一个高频任务，比如修复接口缺陷、处理告警或生成发布 PR，只清点这条任务链上的系统 Prompt、项目规则、Skills、工具描述、Hooks、记忆和审批策略。每条规则旁边记六项：来源、使用频率、失效代价、当前归属、验证方式和回滚入口。来源可能是用户要求、仓库事实、团队约定，也可能只是一次故障后的临时补丁；验证则要落到具体测试、日志或权限拦截上。

这些信息摆在一起，规则的去处通常就清楚了：

  1. 1\. 每次任务都要用、又必须结合现场判断的原则，留在 Prompt。
  2. 2\. 参数、状态、返回值和错误语义，收回工具 Schema 与接口实现。
  3. 3\. 只在特定模块或任务出现的专业做法，迁到按需加载的 Skill 或项目规则。
  4. 4\. 需要跨会话保留的事实与偏好，进入带来源、时间和更新机制的记忆。
  5. 5\. 涉及付款、删除、外发、合并和发布的边界，落到最小权限与审批。
  6. 6\. 每次调整都绑定回归任务和日志，记录模型与 Harness 版本，保留回滚入口。

如果一条规则暂时说不清该放哪，也不用急着删。先看它在真实轨迹里有没有被使用、解决了哪类错误。很多 Prompt 越写越长，只是因为每次出问题都来不及深究，先补一句让系统继续跑，后来也没人再回头判断这句话应该进入接口、测试还是权限系统。

这套做法并不玄乎。落到日常研发，就是给规则找准位置，记下每次改动，用任务和日志验证效果，出了问题还能退回上一版。

* * *

## Prompt 只是控制面的一部分

读完这三份 Opus 5 公开样本，我最后留下来的，是一个很朴素的问题：每条规则究竟该由谁负责。Claude Code 精简系统提示词也给了一个侧面印证：模型能自己判断的内容，可以少写一些；工具接口、Skills、参考文件和运行时，各自承担离自己更近的责任。

至于该删多少，没有一个可以照抄的比例。现在再遇到一条新规则，我会先看它失效时会发生什么。回答差一点，可以先交给模型判断，再用评测观察；可能改错代码、泄露数据或重复扣款，就要继续下沉到接口、代码、权限和审批。

**Prompt 可以提醒模型怎样做对，系统还要兜住它偶尔做错的那一次。**
