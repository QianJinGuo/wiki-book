# 本体论（Ontology）：Agent 事实系统的语义控制面

> 架构师（JiaGouX）/ 若飞

供应商准入时，模型从材料里抽出一条关系：品牌甲 --收款主体--> 乙公司。同一批材料里，上一版合同的签约主体又是丙公司。抽取链路没有报错，图里也确实多了两条边。可付款 Agent 真要回答"现在该付给谁"，问题才刚刚开始：收款主体和签约主体是不是同一种关系？哪一条现在有效？证据是什么？如果材料缺了一页，系统应该判定"没有收款主体"，还是"目前不知道"？

这些问题，向量检索回答不了，图数据库也不会替我们回答。

本体论（Ontology），取知识工程里的含义：把一个领域里的对象、关系、约束和可推导边界写清楚。如果放进架构图，摆在事实层和动作层之间，称作"语义控制面"。它负责约束不同 Agent、不同系统对同一条事实的解释。

从架构分工看，大模型提出候选，事实层保存主张，本体约束含义；能否执行由权限和策略系统决定。大模型把候选关系生成得更快，本体论要守住的，是这些关系进入系统后的共同含义。

## 一条边不够

RDF 用 subject、predicate、object 三元组表达一条陈述。但放到真实业务里，一条边至少还藏着五个问题：两端是不是同一个稳定对象；谓词的业务含义是什么；关系从什么时候生效/失效；来自哪份材料、是否经过复核；哪些查询和动作有权消费它。

W3C 在 RDF 1.2 候选推荐快照中专门提醒：RDF 的抽象数据模型本身是无时间的，图是信息的静态快照。时间、版本和来源要由我们显式建模。

生产里的事实要带上状态、有效期和来源，存成一条可追溯的主张（claim）：claim_id, subject_id, predicate, object_id, valid_from, valid_to, source_ref, status, schema_version。

status 的生命周期：candidate → validated → published → retracted。candidate 表示模型提出了一条主张，可以进入核对流程但不能直接成为付款依据。经过实体消歧、关系校验和人工复核后才变成 published。来源有误时进入 retracted，不能悄悄覆盖旧记录。

## 四层架构

"知识库"这个词太宽了。文档、向量索引、关系表、知识图谱和本体经常被装进同一个盒子。如果放进一次架构评审，先分成四层：

| 层 | 负责什么 | 供应商案例里保存什么 |
|---|---------|-------------------|
| 证据层 | 保存原文和上下文 | 合同、准入表、附件、审批记录 |
| 事实层 | 保存候选与已发布主张 | 谁是收款主体、何时有效、来源在哪 |
| 语义控制面 | 定义类型、关系、约束与推理边界 | has_payee 两端类型、必需证据、多值规则 |
| 动作层 | 处理权限、策略、审批与副作用 | 能否付款、是否转人工、如何审计和撤回 |

RAG 主要服务证据层。知识图谱或关系表服务事实层。本体处在语义控制面。动作层还要独立存在——即使图里有一条已发布的收款关系，付款仍要检查额度、账户状态、审批、幂等和操作权限。

这个分层也适用于研发系统。CMDB 里 Service A calls Service B、Team X owns Service A、Service A deployed_on Cluster P 都是关系；如果全都压成 related_to，图会很热闹，故障路由、变更影响分析和责任定位仍然做不准。

## 本体管什么

本体落到工程里，管四件事：

**对象**：稳定 ID 比名称重要。公司改名、产品有简称时，展示名可以变，身份不能跟着漂移。实体合并要保守——无法确认时，保留两个待解析实体，比"为了图更干净"强行合并更安全。

**关系**：关系字典写清两端类型、业务含义、时间要求、证据要求和多值规则。has_payee、signed_by、owns_bank_account 看起来都在描述"企业之间有关联"，却服务不同判断。谓词越含糊，后面的查询和动作越容易越权。

**约束**：负责回答"这条主张能不能进入已发布事实"。已发布收款关系必须有来源和有效时间；同一时间存在多个收款主体时返回冲突或待复核；证据已撤回后关系不能继续进入当前有效结果。使用 RDF 时可用 SHACL 根据 shapes graph 校验 data graph。工具可以后选，约束要先说清。

**推理**：事实、规则和推论最好分开保存。is_a、part_of、owns、calls 是否允许继承、传递或反向，都要有明确规则和测试。图上的路径很容易找到，路径是否构成业务结论，要慢一点。

## 推理不等于校验

OWL 2 采用开放世界假设。一条事实没有出现在知识库里，通常只能说明"还不知道"，不能直接推出它是假的。OWL 擅长根据本体公理做语义推理，却不负责强制某个字段必须出现在每条数据里。

三者解决的问题不同：
- OWL 回答"根据现有事实和公理，还能推出什么"
- SHACL 或领域校验器回答"这批数据是否满足发布条件"
- 策略与权限系统回答"满足条件后，谁能执行什么动作"

把推理器当校验器，或者把数据校验当授权系统，都会在边界处留下洞。缺失事实先视为未知，动作流程再决定暂停、补证还是拒绝。

## 大模型放在哪

大模型先负责提出实体、关系和主张的候选。Microsoft GraphRAG 的标准索引用模型抽取实体、关系和可选主张；OntoGPT 使用 SPIRES 方法按 LinkML schema 抽取结构化信息。

大模型可以参与：识别候选实体与关系、归一建议、按 schema 输出结构化主张、整理冲突来源差异、从业务专家修改中归纳校验样例。但抽取结果符合 JSON 不代表主张真实；关系名字看起来专业也不代表业务已接受。

我更信任的链路：原文/日志/表单 → 模型生成候选 → 实体消歧、类型检查、时间与来源校验 → 冲突检查和人工复核 → 发布事实 → 查询层组织回答 → 策略/权限/审批决定是否执行。

模型可以读、可以提议、也可以解释冲突。生产事实的发布权、全局语义的修改权和高风险动作的执行权，应该分别授权。

## 从一条链开工

不建议一开始就做"企业级统一本体"。先选一条输入、输出和责任人都明确的流程，只做四样东西：

1. **实体清单**：第一轮收敛到 5-10 个核心类型，每个分配稳定 ID，保留别名、来源、匹配方法和人工合并记录
2. **关系字典**：10-30 个高频谓词，每个写清 domain、range、含义、反向关系、基数、时态和证据要求
3. **主张账本**：候选/已发布/已撤回分开，查询接口支持 as_of
4. **发布测试**：故意准备同名主体不错误合并、端点错误拦截、新旧主体按时间查询不同、来源撤回后旧事实不返回等样本

五个接口：submit_claim / validate_claim / publish_fact / query_facts / retract_fact。候选、校验、发布、查询、撤回五个动作分开，后面才容易加权限、幂等、审计和回放。

## 什么时候上图

当下面几种压力同时出现时，图数据库越来越有吸引力：同一实体散落在大量来源中需持续对齐；业务问题经常跨两跳以上查询；关系长期累积还要按来源/时间/版本追踪；多个 Agent 共同消费和更新同一批事实。

如果需求仍是从几份文档里找段落，RAG 更直接；如果大部分查询是一跳、结构固定，关系数据库也很好用。

稳定 ID、关系字典、事实生命周期和动作边界不会消失。存储可以替换，语义债务很难靠换库还清。

六个朴素的问题：对象有没有稳定 ID？关系有没有精确定义？事实何时有效？证据在哪里？谁有权发布和撤回？哪类动作可以消费它？这些问题如果还答不清，暂缓技术选型，先把一条事实链跑顺。
