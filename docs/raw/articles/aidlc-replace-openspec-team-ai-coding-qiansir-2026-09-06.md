# 从 OpenSpec 到 AIDLC，我是如何提升团队 AI 代码质量的

> 账号：Data Leads Future | 作者：骞先生 | 团队 AI 编码流程重构：AIDLC 替换 OpenSpec 的实践复盘（源码：github.com/qtalen/aidlc-skills）

## Introduction

到今年八月份，团队用 AI 写代码写了大半年。最大的感受是团队开发效率上去了，但代码质量却总是一言难尽，经常开发只需要半天，但查 BUG 却要查上好几天。作者花了一个多月的时间对团队的 AI 编码流程进行重构，使用 AIDLC 来替换 OpenSpec，使用更细化的软件开发流程管理和增强的团队协作能力，代码质量终于提升了一大截。

AI Coding 发展到现在这个阶段也有一年多的时间，关注点逐渐从哪个模型更好、能提升多少效率，转移到怎样才能保证 AI 生成的代码质量上——社交媒体上越来越多地讨论「我究竟要如何确保 AI Coding 的代码质量」「到底谁应该为 AI 生成的代码负责」。

如果是在半年前，作者会认为这个问题的最佳解法一定是 SDD（Spec Driven Development）。基于 SpecKit、OpenSpec 这类规则框架，先采用问答式对话的方式逐步把需求和实施规范讨论清楚，然后将规范文件作为提示词输入给大模型，让大模型严格按照规范文件进行编码。作者甚至写了好几篇 OpenSpec 使用技巧。直到将方法推广到开发团队后才发现：做小型项目时 SDD 比较好用；但当项目很大、需要长达几年、横跨多个团队的协作时，OpenSpec 就行不通了。

## OpenSpec 究竟出了什么问题

以 OpenSpec 为代表的 SDD 框架在企业级团队中行不通的问题：

### 使用过于复杂

GitHub 上 OpenSpec 的使用文档里各阶段命令（explore 何时用、propose 何时用）很难分清。作者在团队推广时撰写了整整一篇说明文档详细介绍每个命令的使用场景并要求按定义工作流使用，结果还是出现岔子——explore 应该在 propose 前面还是后面？为什么不能直接使用 plan 智能体？命令和使用场景过于复杂的最终结果是团队里每个人的用法都不一样，甚至存在一开始用 OpenSpec 应付一下、后续只使用 vibe coding 的情况——额外的学习成本并不能为开发者带来相应的收益。

### 没有记录原始意图

OpenSpec 写的规范文件里，并没有保存用户提出的原始意图或原始需求，也没有保留用户在 plan 阶段与 AI 进行的对话。导致复核团队另一名成员的 spec 文件时一头雾水：这个用户故事为什么要这么写？这个方法设计出来到底是要解决什么问题？时间长了，或许开发者自己都不清楚某个功能当初为什么会那么设计。缺失了原始意图，项目会随着迭代一步步偏离原始目标。

### 很难把握需求的粒度

OpenSpec 的 explore 模式（或其他 SDD 框架的 brainstorm 模式）很强，于是容易陷入「许愿式」编程的陷阱——希望自己只说一句话，OpenSpec 就会通过对话帮忙做需求拆解，逐步搭建起完整产品。但当前大模型非常善于走捷径：对项目描述笼统目标后指望自动拆成细粒度需求和迭代，大概率行不通，最终只得到一个只具备主要功能的 demo，其他细节完全没有实现，是无法在生产系统上线的半成品。

有经验的开发者都知道 SDD 开发时最好把产品功能拆细，让 OpenSpec 一轮轮迭代（第一轮搭建骨架和技术栈，第二轮做登录认证系统…）。但需求拆分的粒度很难把控：拆粗了项目变成 demo，拆细了开发效率上不去，甚至很多必要功能在开发之初开发者自己都还没想到，很容易遗漏细节。

### 文档一致性问题

团队成员一开始用 OpenSpec 建立规范文档后开始编码，并在编码过程中随时调整实现。但没有显式调用 OpenSpec 命令时，后续调整过程没有回写到任何文档里。另一种情况：生成规则制品过程中发现 tasks.md 有问题并修改，只要不提出要求，AI 也不会主动去改 design.md。项目随迭代变大后，这种不一致性散落得到处都是，最终规范文件完全失去参考价值，收获一堆屎山代码。

### 不知道什么时候该开始流程

团队成员选择 Vibe Coding 的理由之一：由于命令对应的开发阶段比较复杂，根本不知道该什么时候开始流程。举例：刚用 apply 写完代码后发现 bug，是要求 AI 直接改，还是先走 propose 制品流程？修复 bug 过程中冒出好点子想临时调整现有功能、或干脆删掉代码换种方式写，是先走 OpenSpec 流程还是直接改？

### 团队协作问题

所有类似 OpenSpec 这一类的开源框架都在默认一个假设：在 AI 的帮助下每个人都是超级开发者，一个人就能从头到尾搞定所有问题。但现代商业的复杂度已经不可能支持一个人什么都自己搞定。写完需求分析文档和用户故事时，要不要拿去跟产品团队对一下指标计算口径？做完架构设计和编码计划后，要不要与其他开发者或架构师对一下设计思路？然而 OpenSpec 框架忽略这类问题——从 propose 编写规范制品到完成编码，整个工作流只在自己的环境搞定，只要不主动，别人就不会查看文档。OpenSpec 也很难接入质量门禁或审核机制进行管控。

## 我的解决方案是什么

一开始的想法也是自己造个新轮子，让 AI 在指导下写一个新的工作流程。但很快意识到这个方案不可行：一个没经过大量开发团队验证过的新开发流程，只会变成又一个 AI 玩具，不具备企业级开发环境里使用的可靠性保证。

于是想起半年前亚马逊 AWS 部门 AI coding 流程的新闻：**亚马逊要求初中级工程师开发的任何代码都必须交由团队里的其他角色审批**——亚马逊遇到的问题似乎一样：AI 开发流程的不可靠引发了生产环境灾难。作者想当时这个应对措施只是临时方案，半年过去了一定有更系统性或工程化的解决方案。查找后找到了：aidlc-workflows。

注意：虽然亚马逊已推出 aidlc-workflows 2.0 版本，但本文仍基于 1.0 版本撰写并进行了定制化改造。1.0 版本足够轻量、易扩展、更方便使用。

## 什么是 AIDLC

AIDLC 全称 AI Driven Development Life Cycle，是与传统 SDLC（Software Development Life Cycle）相对应的软件开发过程。传统 SDLC 把企业级软件开发流程拆成六到七个主要阶段：规划、需求分析、设计、开发、测试、部署、维护。AIDLC 在这 7 个阶段的基础上，增加了两个新能力：**动态工作流**和**动态团队协作能力**。

AIDLC 不只继承了 SDLC 的 7 个阶段，还把这 7 个阶段归纳进 3 个大阶段：

- **Inception 阶段**：负责工作区检测、条件子阶段、工作流规划，解决是什么（What）和为什么（Why）的问题。
- **Construction 阶段**：负责设计、实施、构建与测试等子阶段，解决如何做（How to）的问题。
- （第三个大阶段即 Operations，负责部署与运维相关子阶段。）

AI-DLC 的全部子阶段中，绿色标记的是始终会执行的必要阶段，黄色标记的是只有满足特定条件才会被执行的阶段。决定哪些会被执行的，就是 AIDLC 称之为的动态工作流规划能力。

### 什么是动态工作流规划？

提出新开发需求时，与传统 SDD 框架「先对话、再写文档、最后实施」的方式不同，AIDLC 会根据当前的项目环境以及用户在对话过程中的选择进入不同的条件分支，在分支里加载不同的子工作流——复杂项目加载的子工作流阶段多一些，小项目加载的子工作流比较简单。

举例：

- AIDLC 首次加载时先检测当前项目环境是全新项目（Green Field）还是现有项目（Brown Field）。如果是现有环境，加载 reverse-engineering 工作流分析已有代码的职责；全新环境则不加载。
- 提出新需求时，AIDLC 判断该需求会不会对产品的最终用户产生影响。如果有影响，加载 user-stories 工作流进行用户故事分析；如果只是非功能需求或纯前端页面开发任务，则跳过 user-stories 直接进入下一子阶段。

AIDLC 还维护一份 aidlc-state.md 文件，除了记录工作流当前所处阶段外，另一个作用是：如果希望进行许愿式开发，AIDLC 会对一句话需求进行拆解，拆出当前最需要被执行的子需求来启动工作流，其他子需求则记录进 aidlc-state.md 等待下一轮工作流后再启动——解决需求粒度问题。

核心工作流就像一个常驻的管家一直待在对话里。当说的话或项目状态触发某个条件时，它才从柜子里抽出对应的子工作流文档让子流程开始干活。不用自己记什么时候该用什么命令，管家会代替判断。

### 什么是动态团队协作能力？

AIDLC 的动态团队协作包含两个部分：**需求分析记录**和**审批门禁**。

与传统的问答式对话大部分把对话记录保存在上下文里不同，AIDLC 会在流程进行过程中随时根据子工作流的指引发起对话并向开发者提问，所有问题和开发者的选择都会被记录在 {current-phase}-questions.md 文件里。同时，在每个子阶段结束后如果希望对当前阶段产物做调整或提出新看法，这些调整和 AI 的回复也会被整理后记录在 audit.md 文件中——解决原始意图没有记录的问题。

每个子阶段结束后，AIDLC 都会忠实记录输入、LLM 的响应以及 LLM 对当前阶段的工作总结，然后工作流暂停等待人工审核。个人开发者只要确认所有文档没问题后回复「继续」；开发团队则需要另一名角色帮忙审核文档，通过 git 提交代码到同事那里审核。同事的审核记录和标记都会被记录在 audit.md 文件里再提交回来。AIDLC 只有拿到当前阶段审核通过的标记才会进入下一个阶段。audit.md 只允许被增量更新、不支持修改，所以永远可以拿到所有的变更和审核记录。

AIDLC 支持使用 extensions 目录对工作流进行扩展，可以设置哪几个关键阶段需要什么角色审核、每轮审核记录审核人信息方便核查。相对于 OpenSpec，AIDLC 更强调团队协作能力。

## AIDLC 在团队中的实践

根据团队开发的实际需要做的本地化改造，已全部重写为 Skill 形式，放在对应位置并让编码智能体加载后自动生效。

### 将 AIDLC 改造成 Skill

AIDLC 核心是两个文件夹：aws-aidlc-rules（核心工作流定义）和 aws-aidlc-rule-details（按需加载的子工作流文件）。默认支持亚马逊自己的编码智能体 Kiro，对其他常见编码智能体的官网设置步骤非常复杂。

AIDLC 本质上就是十几个 Markdown 文件，可以改造成一个技能：在 .agents/skills 目录下创建 aidlc-workflows 文件夹，把 aws-aidlc-rules/core-workflow.md 复制过去更名为 SKILL.md，按 Agent Skills 规范把 aws-aidlc-rule-details 目录下所有文件复制到 aidlc-workflows/references 目录，最后让编码智能体把所有文件里的对应路径调整正确即可。

### 扩展 AIDLC 工作流程

除了 references 目录下针对 Inception、Construction 和 Operations 等大阶段定制的子工作流外，还支持通过 extensions 目录扩展可选的可动态加载的定制化流程（例如测试、安全和弹性部署）。扩展工作流一般分为两个文件：工作流核心文件 {workflow-name}.md，以及后缀名添加了 opt-in.md 的前导文件 {workflow-name}.opt-in.md。

{workflow-name}.opt-in.md 文件包含一个需要用户澄清的问题，该问题的答案决定了扩展工作流 {workflow-name}.md 将应用于哪些阶段。opt-in 文件会在需求分析阶段被加载，根据用户回答决定后续扩展工作流是否被加载。如果定制的扩展工作流只有 {workflow-name}.md 而没有 opt-in 文件，则该工作流一定会被加载。这种机制确保多个扩展的动态加载能力，允许维护无限个扩展而不至于上下文爆炸。

### 文档一致性

该扩展要求 AIDLC 在每次代码变更的时候，必须同步修改相关的所有工作流文档，确保文档与代码一致性，不会出现 SDD 那种修改代码后与规范文档不一致的情况。

### 审批和执行分开

默认的 AIDLC 流程，审批通过某个阶段后流程会自动开始往下执行。个人开发者没问题，但需要审批另一位同事的文档时就出问题了：作为产品经理，总不能在需求文档审批通过后让 AI 直接在你自己电脑上生成代码。所以将审批门禁通过的语义拆分成两个：**通过**和**继续**。审批通过某阶段文档后工作流并不会直接进行下一步，此时应提交代码到负责下一阶段的同事那里；同事看到文档审核通过后说「继续」，工作流才会继续执行。这种拆分将审批和操作分开，确保软件开发流程的不同阶段由不同角色负责，最大限度发挥团队里每个同事的专长。

### 审计署名

默认流程里 AIDLC 会在 audit.md 记录用户与 AI 的每一轮对话，方便审计 AI 的需求来源和每个阶段的审批历史。但默认 audit.md 里没有记录是谁提的需求或变更、谁审批了这些文件——团队协作时难以通过 audit.md 历史找到具体需要沟通的那个人。作者通过扩展对 audit.md 改造，增加 User 和 Email 两个 key，并用 git config user.name 和 git config user.email 分别填充，这样就能知道每条历史记录分别对应谁了——解决「谁应该为 AI 生成的代码负责」的问题。

### 使用 question 工具

原版 AIDLC 是 Kiro 的工作流模块，不太兼容其他 AI IDE，向用户提问的问题记在 {phase-name}-questions.md 文件里，并要求用户到文件里回答并记录问题。作者主要使用 OpenCode，所以做了一个扩展，要求 AIDLC 在生成问题后直接使用 OpenCode 的 question 工具向用户提问，并把用户回答写回文档，不需要离开 OpenCode 到另一个 IDE 里编辑文件。

### 测试，以及其他最佳实践

testing、security 和 resiliency 三个扩展子目录存放了该企业在软件测试、安全性、持续集成与部署方面的最佳实践。举例：以前 AI 写单元测试还会修改源码或测试好让覆盖率达标（AI 自己出题自己改答案，骗过指标）。但 AIDLC 要求引入基于属性的测试（Property Based Testing，PBT）——PBT 不检查单个固定输入，而是随机生成一大批输入条件，让代码很难提前「背题」，AI 不知道下一轮是什么输入，也就没办法针对性地修改代码。

## Conclusion

AIDLC 这套工作流程基本没有学习成本，上手就能使用。作为互联网大厂推出的最佳实践，重点打造了动态工作流和动态团队协作方面的能力，方便根据团队开发流程需要进行定制，也方便厘清团队成员在各个开发阶段所承担的责任——生产环境遇到问题时方便定位根因和责任方并进行修复。

需要注意的是，这套流程非常强调软件生命周期管理的开发模式，对话中需要澄清的问题也专业了许多，可能需要学习更多的软件工程专业知识才能完美驾驭。
