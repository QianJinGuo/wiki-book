# 3天7个步骤，基于 AgentLoop 的游戏 Agent 效果优化实践

> 原始来源：https://mp.weixin.qq.com/s/VOB7IHobrWnmmyS5FDoHGA
> 作者：夏明（涯海），阿里云云原生账号，2026-08

## 全文速读

Cloud Native UGC 游戏平台把 Coding Agent 接进创作链路后的效果优化实战指南。核心问题：Demo 很惊艳、线上很难受——Agent 的「自述」不可信，只有「轨迹」可信；绝大多数团队卡在"没有可取证的轨迹、没有能对齐业务的评估标准、没有能回归验证的数据集"。本文给出已跑通的路径：观测取证 → 分层评估 → 根因定位 → 优化回写 → 数据集回归 → 常态化监控，实战 3 天完成首轮闭环，抓出 5 个以上生产环境代码生成 Bug 与 API 文档缺陷。

## 第 0 步：先想清楚「评什么」

UGC 游戏 Agent 质量是多维度问题，混在一起评只能得到解释不了也优化不了的总分。建议分三层：

- **通用层**（先上，当天出结果）：工具调用成功率、工具选择合理性——摸清 Agent 执行健康度，问题在工具层/Skill 层，与玩法无关，修起来最快。实战第一天用内置「工具调用成功率」评估器在测试+生产双环境抓到工具调用失败问题，通过专家二次复核
- **事实层**（紧跟，收益最大）：API 事实性评估器，第二天上线即在生产环境挖出 5+ 代码生成 Bug 与 API 文档缺陷
- **玩法层**（价值大但风险大，最后做）：判断做出来的东西是不是用户想要的那个。UGC 玩法是玩家想出来的，评估标准写死会变成创意天花板

## 第 1 步：观测接入——目标是「能取证」

UGC 游戏 Agent 架构：游戏客户端 - Go 网关 - Agent 运行时（如 Claude Code）- 外部依赖。两种接入方式：

- **LoongSuite Pilot Hook**（推荐首日接入）：一条命令完成安装配置，无需改 Agent 代码；`--service-name-prefix` 一开始就把环境/角色编进前缀（ai-coding-agent-dev/prod），决定后面评估任务过滤条件好不好写
- **语言探针接入**（需要业务埋点时）：Node.js 为例 `npm install @loongsuite/cms_node_sdk` + `node -r @loongsuite/cms_node_sdk/register app.js`；Span 加业务属性（关卡 ID/玩法类型/会话来源）、跨进程标签透传必须走探针

验收标准：AI Agent 可观测 → 链路追踪，一条 Trace 应有基础指标（Agents 数/总 Token/缓存命中率/LLM 调用次数/工具调用次数/TTFT）+ 推理轨迹页签（System/User/Assistant/Tool 完整消息流，每个 [tool_call] 能看到 args 与工具返回值）。真实样例：复刻灾难模拟器会话，耗时 2 分 1 秒，总 Token 1,367,194（输入 99.5%），缓存命中率 82%——输入 Token 占比本身就是成本优化输入。

## 第 2 步：评估器设计——通用层打底，事实层攻坚

判断口诀：**能一眼看出对错的用 LLM Judge，需要「动手查手册」才能定论的用 Agent Judge**（评分 Prompt + 挂载 Skills/MCP，评委按流程取证再判分）。UGC API 事实层必须用 Agent Judge。

### 2.1 通用层：内置评估器零成本起步

先上「工具调用成功率 + 工具选择合理性」两个。真实输出示例：45 次工具调用 3 次失败（读不存在的参考文档/参数格式错误/命令行直接注入 Lua 失败），成功率 42/45 得分 0.9。理由不只给分数，还归纳三类失败模式——文档索引缺失、参数序列化规范缺失、工具选择不当，全部可转成 Skill 防错护栏。

### 2.2 事实层：API 事实性评估器（投入产出比最高）

UGC 脚本 API 几百个模块，Agent 幻觉集中在 API 调用：参数顺序记错、把服务模块函数当实例方法调、编造不存在的方法名。设计要点是把「唯一事实依据」钉死：评估器 Prompt 明确唯一 API 查询 Skill 是 ugc-api-reference-skill，必须完整读 SKILL.md 按查阅纪律只读对应 reference 文件，**禁止用模型记忆/函数名相似性/其他引擎经验/常识推断/Agent 自己的说法替代 Skill 证据**。

配置三件事：①参考变量 input/output/agent_trajectory 必填；②能力挂载 ugc-api-reference-skill（Agent Judge 与 LLM Judge 的分水岭——评委打分时真的去读 Skill 手册）；③比率型计分 score = 正确项/(正确项+错误项)，「无法核验」项不计入分母。

实战产出：灾难模拟器复刻请求评估得分 0.4，16 项检查：正确 5、错误 9、无法核验 2。**「无法核验」项（self:xxx/DoXXX 框架方法，bindings 提及但 API reference 无独立定义）恰恰是 API 文档体系的缺口——评估器同时在评测 Agent 和体检 API 文档**。

### 2.3 评估器六段式组装规范

顺序固定：①角色定义 → ②（可选）前置提取步骤（缺基准时从轨迹现场抽）→ ③评估维度（逐条审查点+权重）→ ④评分标准（计分公式/精度/边界情况）→ ⑤评估内容（只放参与打分的占位符+中文标签）→ ⑥输出要求+示例（只输出合法 JSON：score 浮点 + explanation 字符串）。

硬约束：占位符必须来自平台字段白名单；结果与过程分离（判断结果达成用 {{output}}，流程约束遵守用 {{agent_trajectory}}）；explanation 必须可复核（写计算过程：检查几项/各子分/扣分原因/加权公式）；权重要能分摊（某维度不适用时按比例分摊给生效维度）。AgentLoop 内置模板库 18 个模板，冷启动先套模板再改。

## 第 3 步：跑评估任务——采样策略比评估器更影响成本

四个参数直接决定成本与有效性。提效技巧：按分数区间筛选（0~1，0.1 精度）日常只看 0.8 以下档（Bad Case 主战场）；traceId 秒级跳调用链分析页（从分数到证据的关键动作）；分组视图聚合同一样本所有评估器结果；版本对比靠 experimentId 过滤。

## 第 4 步：三级取证链（低分到根因）

拿到低分不直接改 Prompt，固定走三级：①读评估理由定位问题类型（参数顺序/方法不存在/调用形态错/缺参数）→ ②回轨迹看现场（点 traceId 切推理轨迹，按关键词定位 [tool_call]，区分「Agent 判断错了」vs「Agent 拿到的信息本来就是错的」）→ ③回官方 API 文档核对（常有意外的收获——文档本身的问题）。实战中 9 个错误项绝大多数根因在 Skill 与文档，**改 Prompt 是治标**。

## 第 5 步：优化回写——评估结论变成 Skill 防错护栏

把低分样本根因反向写成 API Skill 的最小防错规则。实战第一个试点模块「运行时发放道具/枪械」——0 分样本「开局给我生成一把枪放到背包」，Agent 用了世界掉落物 API，玩家背包不会出现枪。回写护栏设计四特征：

1. **前置槽位校验**：三槽（玩家 UIN/道具 ID/落点类型）任一为空不得写调用——把「信息不全就不许写」变硬规则，源头掐掉猜测
2. **路由表**：把语义请求（「发到背包」vs「放到地上」）映射到确定 reference 文件，杜绝凭记忆选 API
3. **回读验证**：保留返回 ID 并二次读取确认，把「声称成功」变「可验证成功」
4. **诚实声明**：无法验证时写明「仅完成配置，未验证」，打掉虚报

回写纪律：只改 Skill 护栏部分不改自动生成的 references；每次回写跑 Skill 库校验 0 errors/0 warnings；API 事实与对应 reference 逐项核对。推进节奏按「低分密度」排序模块，每个模块走：低分样本 → 可验证根因 → 最小防错规则 → 下一次评估回归。

## 第 6 步：BadCase 数据集与实验回归——证明「确实变好了」

- **数据集**：自定义 Schema/CRUD/SQL 查询/批量上传/标注管理；至少含 input/output/score_value/explanation/语义标注字段。强烈建议 tag 语义标注——不加标注回归时把所有样本送进所有评估器产生大量无效评估（用 API 事实性评估器评纯咨询问答纯属烧钱），按语义标注路由到不同数据集是控成本关键。第一版不用大，首批 3 条（0/0.4/0.5 分）照样跑通闭环——**价值在代表性不在规模**
- **SDK 离线实验**：`pip install agentloop-sdk`，AgentLoopBenchmark/GeneralEvaluator 并行评估，n_workers=4（样本多改 RayEvaluator）
- **关键动作：透传 experiment_id**——通过 Context 透传到 Agent 轨迹，评估阶段提取记录，才能按实验过滤/仪表盘聚合/对比分析（设 Baseline 逐条比对）

实操建议：实验前每道题新建独立 session，避免多条样本共用会话导致上下文污染。

## 第 7 步：仪表盘与告警——从项目制走向常态化

仪表盘至少三块：①线上效果盘（各评估器分数趋势/低分样本数/按模块分数分布）②变更验证盘（按 experiment_id 聚合，Skill 回写/Prompt 变更前后对比）③成本盘（Token 消耗/缓存命中率，避免成本黑洞）。告警至少：工具调用成功率跌破阈值、API 事实性评估周均分下滑、单会话 Token 异常上涨。

## 业务效果（实战数据）

- **质量**：API 事实性评估器在生产环境发现 5+ 代码生成 Bug 或 API 文档问题，多个错误跨脚本重复出现（同类错误批量存在，人工抽检几乎不可能全发现）；单条样本 16 项 API 检查查出 9 项错误，每项定位到函数签名与证据文件，可直接转研发工单；「生存 100 天」请求中识别出 Agent 全程没搭建可站立场景但 output 只字未提（「声称完成、轨迹无证据」，人工验收极易漏过）；工具调用成功率评估在双环境抓失败并归纳三类失败模式全转 Skill 护栏
- **效率**：从「人工试玩找问题」变「自动打分+证据定位」，单条样本评估 3 分钟出结论带完整推理链；3 天完成从零到闭环
- **机制**：建立「低分样本 → 可验证根因 → 最小防错规则 → 下一次评估回归」标准动作，优化不再依赖个人经验；把「Agent 老出错」的锅拆成 Agent 问题和文档问题分别认领

## 玩法层评估展望

UGC 玩法是玩家想出来的，不是平台列出来的——**最直觉的「主流玩法清单+固定 Rubric」方向是错的**：清单写死后玩家发明的新玩法被系统性判低分，Agent 为迎合评分收敛到标准形态，评估器成了创意天花板。设计原则改为：评估器不预设任何玩法，需求清单每次从用户输入动态抽取，只判断「用户要的有没有正确做出来」。玩法无关维度：需求覆盖度、可运行与可进入、被请求功能的实现正确性、反馈可见性、表达达成度。

设计纪律：只对用户显式要求的内容计分（没提的不扣分、主动创新不扣分）；一切结论以轨迹证据为准（output 声称但轨迹无证据一律按未完成）；不评审美不评好玩程度（「这个关卡不好玩」不是可优化信号，「用户要的传送门没做」才是）；玩法专属判据只能作可选插件细化「某项要求怎样算做对」，绝不能新增强制项或因为没有匹配 Rubric 就降分拒评。等通用层/事实层被认可、BadCase 数据集积累到规模后启动，需先有人工标注样本校准评委。

## 实战避坑清单（9 条）

1. 别用 output 判分——Agent 自述倾向乐观，一切以轨迹证据为准（写进每个评估器的铁则）
2. 别给用户没要求的功能扣分——否则分数系统性偏低、创意被压制
3. 别在评估器里硬编码工具名——按语义匹配，平台工具名会变
4. 别跳过语义标注——不做数据集路由会把不相关样本送进 Agent Judge 产生无效评估
5. 别忘了透传 experiment_id——不透传没法做优化前后对比，实验白跑
6. 别在实验里复用 session——每道题新建 session 避免上下文污染
7. 别只改 Prompt——根因多在 Skill 与 API 文档，改 Prompt 治标且规则互相打架
8. 长会话要单独验采集——20 分钟以上会话轨迹容易缺失
9. fork 起子进程要处理上下文透传——否则轨迹断裂评估器取不到证据
