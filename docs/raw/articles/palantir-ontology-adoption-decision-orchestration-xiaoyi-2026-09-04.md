# 读懂 Palantir Ontology（番外篇）：上了本体，CRM 和 ERP 要不要重做？

> 来源：AI打工人小伊，Palantir Ontology 系列番外篇。结论：多数企业第一步不是重做 CRM 和 ERP，而是在它们之上补上跨系统的决策与行动闭环。核心概念：decision orchestration（决策编排）、writeback vs side-effect、四步落地路线、四责任模型。基于 Palantir 官方文档深度解读。

## 结论先行：不用重做 CRM 和 ERP

做企业 Ontology 方案时常遇到的问题：上了 Ontology，CRM 和 ERP 是不是要重做一遍？业务团队怕流程被打断，IT 团队怕双系统并行，管理层怕数字化投资被推倒。// 前 16 篇已讲完对象、关系、Function、Action、权限、应用、Agent 和最小决策闭环；番外回答"现有系统该怎么办"。多数企业的第一步，不是在 CRM/ERP 之上重做一遍，而是在它们之上补上跨系统的决策与行动闭环。

一家制造企业同时拥有 CRM（客户等级/商机/沟通）、ERP（订单/交期/采购/财务交易）、WMS（各仓库存/锁定量/出入库）、TMS（运输任务/节点/ETA），每套系统都能完成自己的工作。但当一张重要订单可能延误时，履约经理要回答的是跨四套系统的问题（哪些订单必须今天介入？调库存/催运输/重新承诺？），而非"ERP 里这个字段是什么"。问题不在某套系统缺一个界面，而在于这次决策没有自己的业务上下文、确定性逻辑和可执行动作。

Palantir 架构并不假设只有一套整齐系统，明确列出分散的 ERP、自研记录系统、CRM、工业数据库、实时传感器和文档库等来源；Ontology 把这些来源组织成连贯的对象、属性和关系，再用逻辑、Action 和安全约束支撑决策——不是给原始数据换一套业务名称的"薄语义层"。但也不等于每次建设 Ontology 都要启动核心系统替换，Palantir 同时强调与现有/未来企业软件的深度互操作。第一阶段职责分工：CRM/ERP 继续承担客户记录、交易处理和专业流程；Ontology 给跨系统业务对象、关系、决策逻辑、行动入口提供共同语境；Action 把通过权限与业务校验的决定写回应记录的系统。

## 跨系统不等于把所有数据复制一遍

听到"统一业务对象"，很多团队就规划大工程（把 CRM/ERP 所有表、字段、历史数据都同步）。这容易把 Ontology 做成又一个数据搬运工程。// 有价值的问法是：为完成某次决策，究竟需要哪些对象、哪些属性、新鲜度到什么程度。以延误订单为例，只需建立几个业务对象：Customer Order（承诺日期/待交数量/履约状态）、Customer（客户等级/服务约定）、Inventory Position（哪个仓有可调库存）、Shipment（当前位置/ETA）。这四个对象可来自四套系统，也可由多数据源补齐属性；关键不是物理存在哪，而是使用者看到订单/客户/库存/运输，而非四个系统的表名和字段编号。在这些对象之上，Function 可根据缺货量、交期缺口、客户等级和备选库存计算影响分并解释为何优先处理。

## 写回不仅仅是 PPT 上的一根箭头

履约经理决定"从华东仓向华南仓调拨 200 件库存"，不该只是把 Ontology 状态改成"已调拨"。真实业务可能还要：检查当前库存是否足够；判断操作人调拨权限；按金额/跨区域规则发起审批；在 ERP 创建正式调拨单；通知仓库并把外部单号带回决策上下文。

Palantir Action 中 Webhook 以 writeback 或 side effect 两种方式工作：
- **Writeback**：在 Ontology 对象修改之前请求外部系统；请求失败则 Action 停止、用户看到错误、Ontology 修改不会继续。适合"ERP 必须先创建调拨单"的场景。
- **Side effect**：在 Ontology 修改之后执行，适合发通知或尽力同步到多个外部系统；不保证多调用执行顺序，可能在用户看到成功消息后才完成。

容易忽略的边界：官方文档明确 writeback 能提供一定程度的事务性，但不是跨系统的完美分布式事务——外部请求可能已成功、随后 Ontology 修改仍可能失败。生产级写回至少要说清楚：请求是否幂等？哪个系统生成最终单号？超时后重试还是转人工？两边状态不一致谁来对账？否则界面上漂亮的 Action 只是把集成风险藏在按钮后面。

## 决策编排：让老系统继续做擅长的事

当 Foundry 之外的系统仍是事实来源时，Palantir 把与现有流程协作的方式称为 decision orchestration（决策编排）。它解决的不是"数据最后存哪儿"，而是"这次决定如何在多套系统之间可靠地发生"。以调拨为例：ERP 仍拥有正式调拨单，WMS 负责出入库，CRM 保留客户沟通记录；Ontology 把订单风险、客户影响、可用库存、运输状态组织一起，Function 给可解释判断，Action 完成校验、审批、写回、日志。每套系统责任清楚，无需为一次跨系统决策重建全部交易流程。

"不先替换"不等于"永远不替换"。若某老模块已无法支持所需流程、维护成本明显高于价值；或某条 Ontology 工作流运行稳定、业务边界和用户习惯得到证明，选择性替换可进入方案。区别在于：不是靠一张目标架构图决定，而是由真实使用证据决定。

## 一条更现实的四步落地路线

在有大量 CRM/ERP/自研系统时按四步走：
1. **只读观察**：选一个高频、跨系统、有明确负责人的决策，先接入必要数据、对齐订单号/客户ID/时间语义/数据新鲜度，不写回；先证明业务人员看到的是同一张订单（不会因主键/延迟/权限差异得到几个版本现实）。
2. **组织语义与判断**：按业务对象建立稳定语义，把重复出现在 Excel/SQL/会议/个人经验里的判断收敛成可测试的 Function；让业务人员真实班次使用，记录他们仍回老系统查的信息（那些缺口比会议室里的"完整模型"更值得优先处理）。
3. **打通一个受控 Action**：不要一次打通所有写回；选一个高频、可验证、可恢复的动作（如"提交库存调拨申请"而非"修改字段"），配参数/提交条件/权限/日志/超时/幂等/异常升级，连续运行后再扩大范围。
4. **用证据选择替换**：统计业务人员完成任务需切换几套系统、决策周期缩短多少、Action 失败和人工对账发生多少；哪个旧模块经常被绕过、哪个只剩薄薄一层交易记录、哪个互操作成本居高不下，再讨论是否替换。

顺序关键：先证明能协同，再决定要不要替换。

## 谁来对这条链负责

跨系统决策最易出现的空白：每套系统都有 owner，整条链却没有。CRM 团队管客户数据、ERP 管订单交易、数据团队管管道、应用团队管页面；延误订单判断错误或写回失败时大家可能都认为自己的模块没问题。第一条闭环至少要明确四种责任：源系统 owner（数据正确性/接口契约/最终交易记录）、业务流程 owner（何时介入/有哪些选项/什么算成功）、Ontology 产品团队（对象语义/Function/Action/应用一致性）、安全运维（权限/审计/监控/对账/异常升级）。重点不是组织图长什么样，而是出现状态不一致时有人对整条决策链负责。

## Agent 会让这个边界更重要

没有 Ontology，履约 Agent 需分别学会 CRM/ERP/WMS/TMS 的表结构、API、权限和失败方式，每换一个系统工具和 Prompt 都要改。有了 Ontology，Agent 面向稳定业务对象（Customer Order/Customer/Inventory Position/Shipment）调用同一 Function 解释风险，再在权限和 Action 提交条件允许时发起调拨。它不会自动消除外部系统接口复杂度，只是把复杂度从每个 Agent/应用收回，放到可测试、可审计的共享业务能力里。因此 Agent 不应拿着四套系统的超级账号越过 Action；它有能力调用什么、调用能否提交、写回失败如何处理，仍回到同一套权限/校验/日志/升级边界。

## 别用"接了多少张表"证明落地

企业项目最容易量化的是接入数据源数、建对象数、打通接口数——这些证明工作量，不证明某次决策变好了。延误订单闭环优先跟踪：处理异常需切换几套系统；从发现风险到有人接单的中位时长；调拨建议被接受/驳回/撤销比例；Action 写回失败率/重试次数/人工对账量；延误率/缺货损失/客户承诺达成率变化。如果业务人员仍要开四个页面、复制三次订单号、在群里请领导确认，建再多 Object type 也不能算闭环落地。

## 所以 CRM 和 ERP 要不要重做？

不要因为决定做 Ontology 就默认 CRM/ERP 必须重做。先保留它们的事实记录和专业交易能力，用 Ontology 建立跨系统对象/逻辑/Action，让一条真实决策先跑通。闭环运行后你会看得更清楚：哪些系统仍是不可替代的事实来源，哪些界面只因过去没有共同决策层才存在，哪些老模块维护成本高到值得替换。到那时再替换，是带着使用数据和已跑通的业务边界做决定，不是靠宏大目标架构图下赌注。// 真正需要先被重做的，往往不是 CRM 和 ERP，而是它们之间那条仍依赖人工搜索、复制粘贴和群聊确认的决策链。
