# Harness-of-Harness：编程智能体之上的自主开发编排层

> 来源：模智空间（小智）。上海人工智能实验室论文《Harness-of-Harness: Multi-Day Autonomous Software Development with Continual Improvement》解读。HoH 不改任何现有 harness 的内部实现，而是在它们之上再架一层编排与质量保障框架（规划→开发→测试闭环），让任意（harness+模型）组合都能小步增量 + 独立验收 + 证据留痕持续改进。

## 为什么 AI 自主开发很难

自主开发不是跑得更久，而是如何长期保持有效进展。从零造一个软件系统牵涉一串相互依赖的决策（高层需求翻译成计划、协调模块、设计集成组件、测试排错），开发轨迹很长，三个问题冒出来：遗忘（早先需求/设计决策/踩过的坑被丢到脑后，局部合理修改悄悄破坏别处功能）、停滞（失败尝试与次优决策累积 + 新测试证据推翻旧假设 → 反复"检查—修复—再检查"或无意义重复验证）、自欺欺人（功能缺陷不一定在测试暴露，AI 可能在残缺系统过早宣布完工）。全自主开发真正难点是让无监督系统在漫长时间里保持连贯有效进步。

## Harness-of-Harness：可持续改进的循环

现代编程智能体被 harness 围绕（决定模型看到什么信息、能调什么工具、执行结果如何反馈，如 Codex CLI/OpenCode/SWE-agent）。近年趋势是把 harness 本身当成优化对象：AutoHarness（环境反馈合成 harness）、Meta-Harness（搜索调 harness）、Self-Harness（迭代诊断修改自己）。**Harness-of-Harness（HoH）再上一层**：不改现有 harness 内部实现，在它们之上架一层编排与质量保障框架（像 OS 之上装项目管理和测试体系）。本质是软件工程原则"迭代式增量开发"的 AI 化：把孤立开发重新组织成 规划→开发→测试 闭环，每轮只做一件小而可验证的事，把成果连同证据带到下一轮。

**机制硬原则**：①修复与增长间找平衡（每轮真实进步）；②开发切成小的可验证增量（范围有限、问题易定位）；③开发中的测试与独立验收分开（自己说自己写对不算，另一角色独立验证）；④约束可验证产出而非工作流程（框架规定每角色交什么/不许越权，具体推理用工具交模型）；⑤鼓励复用不重造。上下文管理用**渐进式披露**：计划/报告/历史持久化到文件系统，先给模型精简分类索引，相关内容相关时才取详细内容——保持长期连续又不撑爆上下文。

## 三个角色

每一轮由同一固定的 harness+模型组合分别扮演三个角色各跑一次：
- **Project Planner（规划者/产品经理）**：每轮开始读需求文档、查当前项目状态、看上轮测试报告；产出开发文档（决定本轮做什么、保留哪些已验证功能不能弄坏、如何验证新功能）。（只读，不能改代码）
- **Developer（开发者/程序员）**：唯一能修改代码的角色；遵循 Shift-Left Testing 边写边测（每改动立即运行相关功能验证有效不破坏其他）。（唯一写者）
- **QA Tester（质检员/第三方）**：独立严格第三方，拿候选版本从黑盒（玩游戏/看界面）+白盒（查代码/日志）全面测试；产出结构化测试报告（区分 Verified 已验证 / Gap 有缺陷或证据不足），是下轮规划依据。（只读，不修候选版）

为什么三角色而非一个模型边写边自评：三种决策需要的信息/权限/立场完全不同——选目标需要项目全局视野，实现需要写权限和局部技术自主权，验收必须由未参与实现的第三方（否则"开发者说写完、代码存在但功能没跑"的自欺欺人）。**关键细节：QA 评估的是被冻结的只读快照**，所有观察绑定同一候选版本，避免评估中偷偷修 Bug 再自我表扬。

**每轮输出两个状态**：A（工件状态：当前软件样子——源码/配置/资源/项目元数据，保证开发增量延续非每轮从零重来）+ E（证据状态：通过评估获得的已验证知识——哪些行为证实/缺证据/失败未解决，保证规划有据可依）。A 和 E 一起跨轮次边界，缺一不可（只有 A 没 E → 下轮靠猜重建开发历史；只有 E 没 A → 没有可改的东西）。这是 HoH 长期进步关键。

长周期还保留**角色级和迭代级的版本化项目历史**（软件当前状态 + 变更说明）：大改动搞崩系统可回滚到之前已验证状态；相似失败再现可直接翻前一次诊断证据辅助定位。

## 实战测评

三组 harness+模型：高配 Codex CLI + GPT-5.5（高推理档）、中配 OpenCode + DeepSeek-V4-Pro、另一组 Pi Coding Agent + MiniMax-M3。三个基准：GameCraft-Bench（45 任务覆盖 15 游戏家族，动作/时机/策略/模拟/冒险五类，用 Godot 从零做完整可玩游戏）、FrontierSWE（仓库级软件工程，15 任务，从零实现或深度优化真实开源项目）、ProgramBench（只给编译好的可执行程序和文档，重建行为一致同款代码库）。

**结果**：三轮迭代后 HoH 在每组配置、每个基准都超过 Vanilla（原始用法），平均相对提升 52.25%，最高 82.86%。提升与原始水平无关——最强 Vanilla（Codex+GPT-5.5）拿 GameCraft-Bench 最高分；原本垫底的 OpenCode 组合提升同样巨大，甚至在动作类/模拟类游戏和 FrontierSWE 性能类任务反超 Codex Vanilla（对弱基座同样有效甚至更有效）。越跑越好而非越跑越崩：GameCraft-Bench 三组配置分数 HoH@1→HoH@3 单调上升；Codex 组合在 FrontierSWE 跑 10 轮，支配率从第 3 轮 39.33% 涨到第 10 轮 72.67%（第 9 轮达 76.00%），Vanilla 仅 27.33%。

**不是多跑几遍的功劳**：预算控制实验让 Vanilla 连续开发 3 遍（Vanilla Continuation），HoH 只用了 2 遍预算（5.67M tokens）就拿到 64.84 分，超过 Vanilla 连跑 3 遍（6.33M tokens）的 58.24——提升来自规划—测试结构本身，非单纯堆预算。**消融**：不更新开发计划（每轮用第一版）掉 8.13 分；不给规划者反馈测试证据掉 6.28 分；不保留上一轮工件（每轮从零重写）掉 7.85 分且 token 从 8.41M 涨到 11.12M——"计划随证据更新""证据驱动重规划""保留既有实现"三者缺一不可。

**Fusepoint 实战案例**：单机剧情向第一人称射击游戏（约 5 分钟单人拆弹任务、按序占领两个控制点、最终目标处三阶段拆弹、固定 18 名敌人按 3/5/10 分布前中后三遭遇区、成功拆弹与引爆两条结局分支）。开发环境 Godot 4.7 + Godot MCP（操作引擎/执行/调试）+ 素材生成工具 + UI/UX 技能 + 测试技能 + CC0/CC BY 可复用素材库，系统用 Codex CLI + GPT-5.6-Sol。人类只偶尔恢复网络或 API 连接。70 轮迭代的轨迹三阶段：初始搭建（第 1-27 轮：建核心交互路径，新增功能暴露大量缺陷，积压不降反升）、能力扩张（第 28-49 轮：加功能+诊断修复，局部改动牵动任务/战斗/界面/运行时）、趋于稳定（约 49 轮后：计划功能接近完成、修复成主线、活跃 issue 积压下降）。第 70 轮 81 个 issue 关闭 65 剩 16；17 个 issue 曾被重新打开（后来改动让已验证行为失效），回归被完整记录在案、下轮规划直接当明确修复任务。最终交付：连贯剧情、完整战斗与武器系统、敌人 AI、玩家引导（小地图）、HUD、菜单设置、过场动画、特效光照、音效，真人可玩；开发过程/轨迹/试玩公开在 GitHub。

## 小结与局限

最核心是把视角抬高一层：没有发明新模型、没强迫重写工具链，而是找到通用编排方式让任意（harness+模型）组合通过小步增量 + 独立验收 + 证据留痕持续改进。局限：实验集中在游戏与特定工程任务，70 轮只跑一个案例；token 成本不低（HoH@3 单任务动辄数百万到上千万）；人类只修网络只适用于网络环境相对可控场景。让 AI 开发复杂软件的关键不仅是模型多强，更在于如何管理组织其开发过程——通过"计划-执行-验证"迭代循环 + 项目历史与测试证据在不同环节流动，AI 也能展现持续稳定有效的长期工作能力。
