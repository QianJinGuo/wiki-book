## 背景

阿里国际商品中心（IC）承载海量商品的信息管理、权限管控、标签体系构建与上下游系统协同。商品中心每天面对运营小二、开发人员、产品团队的大量咨询问题——错误码分析、可见可售性、标签体系、离线数据、变更记录等，信息分散、逻辑复杂、人工排查成本高。

基于 App Builder 平台构建了 6 个 AI 答疑 Agent：trace 排查、错误码分析、标签使用分析、可见可售性分析、变更记录溯源诊断、IC 文档查询。

但各 Agent 多为按需独立开发，缺少标准化部署流程，数据埋点不统一，关键链路数据难以追溯。

## 三阶段框架演进

### 第一阶段：单 Agent 框架（场景识别 + 工具调用 + SOP 执行）

**四个核心模块**：
- **感知模块**：接收用户输入，基于场景知识库进行场景分类、关键信息抽取和意图识别
- **规划模块**：制定任务执行路径，选择调用工具并定义执行顺序
- **工具模块**：脚本执行（ToolBox 平台）+ MCP 协议接入（Aone 开放平台）
- **记忆模块**：短期记忆（会话状态）+ 长期记忆（RAG 知识库）

配套建设**三类知识库**：
- 场景知识库：场景类型、关键信息、问题示例、解决步骤
- 工具知识库：工具类型、描述、入参格式
- SOP 知识库：输出格式定义

**存在问题**：功能耦合严重、修改风险高、响应延迟长、关键信息被截断、维护成本高。

### 第二阶段：多 Agent 融合框架（场景识别 + 单一路由）

以**主控 Agent** 为核心、**专项 Agent** 为执行单元：
- 主控 Agent 查询场景知识库进行意图识别 → 场景补全机制（IC 文档查询 Agent 兜底）→ 单一路由决策 → 专项 Agent 执行

6 个专项 Agent + 1 个通用 Agent（IC 文档查询），覆盖 18 类知识库文档。

**解决问题**：功能解耦、响应高效、易于维护。

**仍然存在的问题**：仅支持单一场景路由（跨场景复合型问题无法处理）、Agent 间无通信、扩展灵活性受限。

### 第三阶段：多 Agent 协作框架（意图拆解 + 多场景路由）

正在构建的方向：
- **意图结构化拆解**：将用户问题分解为多个可独立诊断的意图
- **多场景协作路由**：动态调度多个专项 Agent 协同工作
- **关联分析结果聚合**：联合诊断生成一致性、可解释的最终答案

示例：商品不可售原因包括业务自定义 feature + 商品未上架/审核不通过 → 需要可售性分析 Agent + 变更记录 Agent 协作。

### 三阶段对比

| 维度 | 单Agent框架 | 多Agent融合 | 多Agent协作 |
|------|-----------|------------|-----------|
| 核心模式 | 场景识别+工具+SOP | 场景识别+单一路由 | 意图拆解+多场景路由 |
| 诊断能力 | 单一场景 | 单一场景 | 跨场景协作 |
| 响应延迟 | 高（上下文膨胀） | 中等（按需加载） | 中高（协作成本） |
| 功能耦合 | 高 | 低 | 极低 |
| 维护扩展 | 差 | 良 | 优 |
| 适用场景 | 简单标准化问答 | 明确单一问题 | 复合型根因分析 |

## 效果与展望

已集成至答疑小蜜、商品中心答疑群、Tickets 工单等高频场景。未来方向：多 Agent 协作框架、文档知识库完善、智能工作台（Atlas 平台）。
