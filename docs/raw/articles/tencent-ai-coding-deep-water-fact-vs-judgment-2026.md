# 两万字长文｜手把手带你趟过 AI Coding 深水区：编码让位，人退到哪里

> 来源：腾讯技术工程（黄迅，PUBGMobile 后台）| 2026-08-27 入库 | v=8 c=9 v×c=72 NEW Entity

背景：内部平台（对照组）纯 AI 交付——三个月、七个服务、三十多万行代码、人一行没写（16万行生产代码+11万行测试+8万多行前端），设计文档全由 AI 落笔。但真正的业务是另一边：百万行 Lua、自研框架、模型几乎没见过、历史债层层叠。

## 核心尺子：事实 vs 判断
"手上这件事，是事实，还是判断？是事实就交给机器，别让人去核对，也别听 AI 声明；是判断就留给人，别指望机制替他拍板。"——三个发现都指向这一句，贯穿全文五部分。

## 前言：人的工作量没减少，只是从落笔挪到拍板
- 每天读的东西从"读代码"变"读方案/读结论/读证据"，拍板从"这段怎么写"变"这条路走不走、这个失败算不算问题"。
- 仓库留 70+ 篇 AI 落笔设计文档，每篇取舍都是人定的；**海量 spec 文档最后被删掉，删完项目照跑**。动手前用来对齐的 spec 用完可扔，事后沉淀的设计说明得留着（给下一个改代码的人建立心智模型）。两头对不上说明：**核心从来不是 spec 载体，而是产出它过程中被迫想清楚的事——brainstorming**。
- AI 犯错是规模问题不是概率问题：错误绝对数量由累积量决定，不随单次准确率降低。模型越强产出越多越快，人这端上限不动，缺口更大——"模型越强 harness 就该越薄"是想当然。
- 有一类错 AI 特别容易犯：**失败不可见**。AI 交付功能的能力明显强于交付"让失败可见"这种纪律的能力（前者是需求，后者是价值观）。

## 第一部分：提示词的尽头是基础设施
提示词边际收益会耗尽。测试 agent 打磨数月后进瓶颈期，调提示词无果（用自研 tracesift 会话分析工具摊开所有会话才看清问题在框架层）。
- **例一 mock 还原**：提示词反复强调 setup/teardown 成对，AI 仍约一半概率漏 teardown。在框架层加"声明式 mock + 自动还原"（像自动 GC）→ 这类错误消失，把 AI 注意力还给主任务。
- **例二 trace 链路分析**：链路超时最难解（要读大量代码追调用链，AI 常耗时极长/上下文过载）。框架重构 trace：超时报错时自动返回准确原因+链路分析包（反向探测队列/限频登记表分类超时，每类跟下一步动作+代码执行路径贴出卡住行）。**报错通道本身就是提示词注入通道**——"最好的提示词，是恰到好处的反馈"。但注入不是越多越好（删过信噪比差的告警，会带错方向的反馈比没有更糟）。
- 共同点：解法不在 agent 层在框架层——提示词只能"叮嘱"，框架可以"取消这个错误的存在"。
- 注意点加不下去了：ut-tester 的 SKILL.md 400+ 行，7 月后几乎停加。注意点越多模型注意力越碎主任务越差——"harness 越厚，agent 越笨"在开发环节成立。**两种"厚"别混**：写提示词里越厚越笨，写进框架越厚越省心主任务越强。打补丁档尤其不要写（"严禁 mock ss"写后 8 天对 529 个存量单测发现与事实相反——有限规则覆盖无限问题）。
- 什么都该往下沉？判断标准：**判据是确定的事实才能做硬门禁；判据是代理指标最多做提醒**（"禁止读 protocols 目录"路径前缀硬拦截 vs"编辑 .lua 前先读编码规范"是代理指标降为警告）。信号要能从外部取到，不能靠 AI 自述（防假测试：AI 把被测函数内部逻辑抄出来重算再断言，断言全过覆盖率零，只有从外面看"被测函数行一次没执行"戳得穿）。门禁误报代价高（逼人和 AI 为过检查把代码写更差）。能不能往下沉一半不由自己说了算，取决于脚下那层给不给接口。

## 第二部分：编排的尽头是 runtime
workflow-engine（主 agent 状态机固定流程 spawn 子 agent）换来稳定但三问题：子 agent 从干净上下文反复探索同一代码、编排逻辑复杂不透明、主 agent 只维持秩序浪费直接对话能力。两条路并行：方案一（交互重环节收回归主 agent+resume 续接，低风险已落地）；方案二（Claude Code agent teams，网状常驻通信，风险大）。

**实验一：整个开发流程搬上 Team**（experiments/2026-05-29-team-driven-dev）——产物驱动状态（不 state.json，查磁盘产物恢复），七角色（planner/implementer/reviewer/test-planner/test-engineer/explorer/guardian），审查点对点直连。实跑踩坑四类：①模型根本不认识这套机制（全靠提示词现教，逐条补丁）；②中断活锁（主 agent 约一分钟催一次 planner，打断其在途工具调用，产出 580→278→1 token，主 agent 误判"Team resume 失效"重建团队接着催——三条铁律：不催正在工作的 agent 只认显式 DONE/BLOCKED（PROTOCOL-A）、planner 一次性 spawn 自包含、测试断言提前冻结）；③成员生命周期靠不住（一切以磁盘产物为准，失联就重建）；④机制本身反直觉（强杀工具要 taskId 但 spawn 拿 agentId 不互通，靠改 config.json 摘成员，任务窃取关闭后卡死无人接）。完整流程编排最终没推广（太脆），但熬出 agent-teams skill（上百次失败会话的运维知识库，纪律全是"不信声明，信事实"）。

**实验二：收窄到测试流程 /module-test**——主 agent 亲写 spec（"自带答案的交接物"），Team 只两个成员 test-engineer + reviewer 点对点直连互审，spec 验证点矩阵是审查权威基准早早冻结，测试红了且对应验证点按 bug 处理绝不软化断言。跑稳了。缺点：常驻 reviewer 被自己上轮意见带着走，彻底解决只能每轮 spawn 新 agent（权衡留下常驻）。

**三起黑盒事故**证明 agent loop 每环节必须可审计可干预：①Claude Code 遥测事件（检测中国用户并在提示词/工具调用投毒，动摇黑盒 CLI 信任）；②CLI 写长中文 UTF-8 损坏（37 份产出 36 份损坏 370 处 U+FFFD，CLI 按字节切断多字节字符，黑盒里改不了）；③压缩 bug 11 小时空转（只读探索 11h/6556 次调用/1.23 亿 token 一无所获：max_turns 没生效、压缩阈值卡 100K、压缩摘要误把"生成摘要"当用户请求、"当前进度/待办"只剩标题，203 轮压缩=203 次从头再来）。

**合流：自建 agent runtime**。claude/codebuddy 不开源只能靠提示词/hook 从外面伸手。选型：trpc-agent-go（重复造轮子）/ 薄封装（别团队在做）/ claude SDK（黑盒躲不掉三事故）/ codex（开源但"开源不等于主权"——多 agent 通信任务载荷加密只有 OpenAI 服务端解得开，假开源）/ **pi agent**（MIT 最小 agent harness，系统提示词<1000 token，扩展点能碰工具/命令/事件/TUI）/ **DeepSeek Harness**（v0.1 MIT 开发者预览，"一切皆插件"，Cordis 元框架只管装卸，能换 agent loop 自己）。选型的真问题不是"选哪个产品"而是**主权的边界划在哪**。审计底线：上下文注入/遥测要能按来源回看（append-only 会话日志）。决策：pi agent 先动（几个月接触+上下文治理压伤口），DSH 跟进（"可预期"要自己验不能听它说）。原则：元框架只管装卸，能力全部可替换插件，从最小 harness 起步撞墙换撞墙那块。

## 第三部分：分数不可信，问题在题集
**撞墙那次**（107 天 17 万行评测平台）：六阶段流水线+四层加权评分+Web 平台+六个容器+自动推企微+低分触发七类根因归因；题集 25 道真实需求、人写百分制评分表、LLM 逐项判。结果只有两次完整跑数 69.9(D)/51.9(F)，二十天后被当"清理冗余"删掉。四个问题：①判据不能执行（判分从跑单测→比对参考实现→checklist 打分，确定性判分占比 65%→40%，LLM 判分力升 60%，交给 Cohen's Kappa 0.10-0.21"几乎不存在一致性"的裁判）；②判分器自己有 bug（同一份日志格式错=0 分、修好=98 分，差 98 分）；③把流水线维持住是份全职工作（运维文档全是流水线自己的事故）；④卷子追不上考生（107 天搬三次家/判分换三套/被评对象自己也在动）。教训：**值钱的是想清楚，不是承载它的载体——文档如此，平台也如此**。对照：16 次跑数的小实验（知识库检索 A/B，8 道题）改掉了至今在用的策略（寻路 12 步→2 步）。差别不在工程量，在**判据能不能执行、结论能不能变成一次提交**。立了纪律：一行平台代码都不写——只有题集/配置/脚本/跑数记录。

**测试线 V1 卡死数字**：闸门漏斗（Meta TestGen-LLM 范式）+ 挖空回填。审计召回率 100%→40% 改两轮 skill 纹丝不动 → 扒开评分器：①量错东西（评分按文件逐个核对，挖掉条目写进同模块另一文件被判"没找到"——量的不是"能不能发现覆盖遗漏"是"和标准答案文件划分是否一致"）；②单次跑数追噪声（每模块只挖 5 条，±1 条随机波动和真实回归分不开）。**错误的评测信号比没有更危险——把迭代引向根本不存在的问题**。

**调研后 V2**：业界调研 50+ 论文/基准，用业界尺子量自己方案——四个核心方法里三个有顶会支撑的全站住，唯一自研的挖空回填塌掉（构造效度研究：模糊测试工具杀 100% 人工注入 bug 却没发现真实 bug，人造缺陷普遍比真实缺陷好发现）。**判据必须是执行结果，不能是合成清单**。V2 主指标落**变异击杀率**：AI 写的测试闯五道闸门（有产出→lint 干净→能跑→连跑三次稳定→杀死多少变异体）。为什么不用覆盖率：TestGenEval 实测 GPT-4o 测试覆盖率 35.2% 变异分数仅 18.8%（覆盖率能靠无断言测试刷出来，杀变异体必须有真断言）。变异体故意埋进业务代码的单点 bug（比较符翻转/and-or 互换/删兜底/注释状态写入），算子后四种取自代码评审 checklist（真实 bug 分类学）。

## 第四部分：人退到决策点
（AI 交付能力够用，正因产得多又快，兜底比以前更必要，不是更不必要。）机器提供事实的难点不在"人做判断"这一半，而在"机器给出的那个事实本身是不是真的"——**提供事实的机器自己也要被验证**。

## 第五部分：把判据变成流程 + 流与常
- 发现平台把"采集失败"显示成"没有数据"——同一判断在四个地方各犯一次。
- 结尾哲学：模型每季度变强，提示词/编排/评测数字都会随之作废——**它们是流**；但另一些东西模型再换代依然值钱：把问题想清楚的过程、从上百次失败会话提炼的运维纪律、对 runtime 主权的判断、框架层不占模型注意力的能力、验收的杠杆、评测题集、治理链上每条判据——**它们是常**。"做 AI 工程，就是在湍急的流里，找到并守住那些常的东西。"
