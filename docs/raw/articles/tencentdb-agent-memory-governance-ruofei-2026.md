# 拆解 TencentDB Agent Memory：Agent 记住之后，如何不被错误带偏？

> 作者：若飞（架构师 JiaGouX）

## 引子：记忆的三种对象

做一个会长期工作的 Agent，最容易低估的就是「记住」这两个字。真实研发里的麻烦通常不大，却很磨人：某个仓库用 pnpm，PPT 用 HTML，发布前要跑 smoke test。这些约束第一次已经说清楚，换个会话又得从头交代。Agent 会写代码，也会调用工具，只是上一次发生的事，还没有变成这一次可以依赖的工作依据。

生活里也有类似的区分：会议纪要、值班记录、个人习惯、团队规范都可以叫「记忆」，但它们的保存期限、读者和出错代价完全不同。把它们全扔进一个向量库，系统也许能搜到相关文字，却未必知道这句话现在是否有效、适用于哪个项目、谁可以修改。

年初整理《把 AI 记忆做成 Markdown：Clawdbot 的极简工程解法》时，先关心记忆要落到人能读、能改、能追溯的文件里。可真正接进工作流以后，很快会遇到下一层问题——存下来只是开始，系统还得知道什么时候读、读哪一条、错了怎么改。TencentDB Agent Memory 给了一个具体剖面：把这些问题放进运行时以后，写入、提炼、召回、冲突、共享和长任务留痕分别怎么做，哪些地方已经由产品提供，哪些边界仍要接入方自己守住。

它的价值不在存了多少历史，而在过去怎样进入下一次决策。后面用一个发布 Agent 把这些问题串起来：要记住项目约束，能从上一次失败的地方接着做，在记忆服务超时时照常完成回滚，也要知道某次偶然成功没有资格直接改写团队流程。

## 三条路径：写入、读取与治理

把 Memory 放进 Agent 的运行循环，拆成三条路径：**写入**负责把当轮结果变成可追溯的候选记忆；**读取**负责按当前任务缩小范围、排序并控制注入；**治理**负责处理冲突、核验证据，再决定它留在个人范围，还是进入团队资产。

三条路径不在同一条时间线上，速度不同。原始证据可以先落盘，提炼晚一点完成；读取最好设定延迟和上下文预算，拿不到时当前任务照常继续；治理最慢，因为它要处理来源、冲突、权限和晋升。

5 月整理《Agent Memory 架构解析：过去的信息，凭什么影响未来？》时，写入、管理和读取被拆成了三条线。往运行时里再走一步，会发现三条路径不仅职责不同，速度和失败方式也不同。很多记忆系统的问题，都出在把三条路径揉成一次模型调用。写入接口返回成功，不代表结构化记忆已经可查；召回一条相似记录，不代表它是当前有效值；一次任务做对了，也不代表经验已经可以改写团队默认流程。TencentDB Agent Memory 把分层存储、异步提炼、可降级召回和长任务留痕都放进了运行时。

## 四种对象：别共用一套写入和召回规则

日常讨论里「Agent 记忆」经常把几个不同对象混在一起。放到系统里，它们最好有自己的生命周期：

| 对象 | 保存什么 | 主要读者 | 出错代价 |
|------|---------|---------|---------|
| 对话证据 | 原话、工具输出、时间和来源 | 调试者、提炼器 | 现场丢失，后面无法追溯 |
| 任务状态 | 已完成步骤、当前节点、待办和失败点 | 当前 Agent、接续 Agent | 长任务重复劳动或走错下一步 |
| 长期记忆 | 用户偏好、项目约束、历史决策 | 后续会话和相关任务 | 旧事实持续影响新任务 |
| 过程资产 | Skill、Runbook、Wiki、代码关系 | 团队成员和多个 Agent | 一个错误被批量复用 |

Policy 也要单独放出来。权限、合规、预算和审批属于外部约束，Memory 可以记录「某条规则在哪里见过」，却不负责把一次临时处理改写成新的许可。Policy 可以引用 Memory，但不应该被 Memory 自动改写。个人偏好、跨会话事实、长任务日志和团队技能当然都可以被检索，却不该共用一套写入、召回和修改规则。用户说「今天先别跑测试」，团队规定「发布前必须跑 smoke test」，在文本上都像一句话，在系统里却不是同一种资产。

前些日子整理《Agent 记忆与可验证自我改进怎么设计》时，把「一次有效」和「可靠经验」之间的距离单独拎了出来。放在 Memory 里，它对应的是一条晋升路径：影响范围越大，验证和治理责任越重。一段历史从原始证据晋升为团队资产的边界：候选记忆可以被召回，但还不能直接当成规则。

## 公开方案对比：没有标准答案

公开方案对 Memory 的拆法并不一样。差异主要不在「有没有向量库」，而在什么信息常驻上下文，什么信息按需读取，线程状态与长期事实如何分开，变化又怎样留下时间线。

| 路线 | 核心拆法 | 留下的架构启发 |
|------|---------|--------------|
| Letta | 少量重要内容放进持久化的 Memory Block；文件和 archival memory 按需查询 | 重要信息可以常驻，海量资料应该下沉到外部存储 |
| LangGraph | 线程状态用 checkpointer 保存；跨线程复用交给带 namespace 的 Store | 会话恢复和长期共享要分开建模 |
| Mem0 | 写入和读取分开，结合语义、BM25、实体与时间信号；当前算法强调 ADD-only | 历史保留、候选召回和时间推理是三件事 |
| Zep | 用带时间的知识图谱表达实体、关系、事实和失效时间 | 发生变化的事实，要能说清何时生效、何时失效 |
| TencentDB | 长期记忆做 L0 到 L3 分层，短期任务保留状态图和原始证据，团队资产另有管理面 | 记忆可以沿「证据、场景、画像、过程资产」逐步提升 |

这里比较的是各家代表性的架构切法，不是产品排行榜。Letta 更关注上下文层级，LangGraph 提供状态与存储抽象，Mem0、Zep 和 TencentDB 覆盖的产品边界也不完全相同。这些路线各自在回答不同的问题，没有哪一套能脱离场景直接照抄。

做架构设计时，先问自己五个问题：1. 这条信息是否必须每轮都在上下文里？2. 它属于当前线程、某个用户、某个项目，还是整个团队？3. 它要按字面、语义、实体还是时间来召回？4. 事实变化时，旧记录保留到什么程度？5. 一次成功什么时候只是观察，什么时候可以变成默认动作？所以通常把产品放到后面看：它能替我们完成一部分默认实现，作用域、当前状态、权限和错误恢复仍然要由应用架构负责。

## L0 到 L3：渐进式披露

如果把所有历史对话切成向量，再在里面找相似文本，系统能回答「哪里可能相关」，却很难回答「这条记忆来自哪一次对话」。摘要覆盖原文以后，后面即使发现摘要有误，也没有证据可查。TencentDB Agent Memory 的长期记忆采用四层结构：

| 层级 | 官方名称 | 保存什么 | 主要用途 |
|------|---------|---------|---------|
| L0 | Conversation | 原始对话和上下文 | 查原话、时间和来源 |
| L1 | Atom | 从对话里提取的事实、偏好、约束和事件 | 召回可执行信息 |
| L2 | Scenario | 围绕项目或情境组织起来的记忆块 | 恢复工作背景 |
| L3 | Persona | 稳定的画像、长期模式和高层认知 | 帮助 Agent 进入状态 |

这四层不是四份互相独立的摘要。L3 负责定位，L2 负责恢复场景，L1 负责核对事实，L0 负责追溯原话。官方 README 把它描述成渐进式披露：平时先使用高层信息，需要具体事实时再向下检索。高层记忆适合导航，低层数据负责取证。分层也不等于每一层都可以直接改变当前规则。决定一条记忆是否仍然有效，还需要来源、适用范围、状态和有效期。

拿发布 Agent 来看，构建日志是原始证据，当前发布版本是任务状态，「这个项目使用 pnpm」可以成为长期约束，而「失败后把超时调大」最多只是候选经验。L1 是提炼结果，不自动等于最终配置；一次偶然成功，也不该直接晋升成 Skill。

## 写入分两步：原文落盘与异步提炼

记忆写入至少有两个时间点。第一步是把对话原样留下。此时系统还不需要判断它是长期偏好，还是今天发生的一件小事，所以可以很快完成。第二步才是调用模型做提炼，把对话变成结构化记忆。提炼需要理解语义，放进对话主链会增加等待，所以通常放到异步任务里。

一组本地测试记录写入了「早上 6 点起床跑步，晚上 11 点前睡觉」这条偏好。原始记录很快落盘，用「跑步」查询时，第 5 秒还没有结构化结果，大约第 10 秒才出现记忆卡片，日志记录的提炼耗时约 6 秒。10 秒只是这次测试里的表面数字，更关键的是把两个状态分开：原始对话已经保存，不会因为提炼还没完成而丢失；结构化记忆还没有准备好，所以立即查询可能得到空结果。

批量导入历史对话时，这个区别尤其重要。写入接口返回成功，只能说明原始数据已经保存，不能证明 L1、L2 已经完成，也不能证明下一轮一定能召回。按仓库当前的配置表，每 5 轮对话触发一次 L1 提取，空闲 600 秒也会触发；新会话还提供从 1、2、4 轮逐步升高的 warm-up。当前交互先保持响应，记忆质量交给异步任务处理，这个取舍很常见。接入时，把这段延迟单独记下来，不让它被「写入成功」四个字遮过去。比如团队要把过去半年的项目会话导入发布 Agent，导入任务至少要拆成三个状态：原文接收完成、结构化提炼完成、抽样召回通过。只看第一项，第二天新 Agent 仍可能查不到它应该知道的项目背景。

## 召回要能降级

TencentDB Agent Memory 提供三种召回路径：1. 关键词或 BM25，速度快、成本低，但依赖字面重叠；2. 向量召回，在 embedding 模型合适时更容易识别改写和跨语言表达，但需要额外服务；3. 混合召回，同时跑关键词和向量，再用 RRF 合并两个排名。配置里的默认策略是 hybrid，但这不等于安装以后自然拥有语义理解。没有配置 embedding 服务时，实际只能使用当下可用的路径，混合策略会退回关键词或其他可用召回。配置名叫混合召回，不等于语义链路已经配齐。

测试记录用「用户完全不能吃辣」这条记忆做了几种查询。带「辣」字的表达容易命中，「川菜」「忌口」和 spicy food 则没有召回；打开语义召回后，这些换说法才有机会被识别为同一语义。这个结果是一次测试观察，不能直接当成普遍性能结论，但它把关键词召回的边界展示得很清楚。

召回还要有预算。官方默认最多返回 5 条，超时阈值是 5 秒，超时后跳过本轮注入，不阻塞对话。不过单条记忆和单轮召回的字符上限默认都是 0，也就是不限制。到了线上，结果条数、字符预算、延迟和模型上下文成本要放在一起看，Top-K 只是其中一个参数。

Memory 服务短暂不可用时，Agent 可以少拿一部分背景，当前请求仍要继续。换成线上回滚，要求就很具体：记忆服务刚好超时，主流程仍要保留当前会话里的版本号、命令输出和人工审批状态。Agent 可以少拿历史经验，不能因为历史服务慢了，把当前任务的状态也一起丢掉。

## 冲突要有时间线

项目最初规定使用 PostgreSQL，后来改成 MySQL。系统不能只看到两条相似记录，就把后一条覆盖前一条。这里至少有三种可能：当前项目真的改变了技术选型；两句话属于两个不同项目；前后说法不一致，需要保留证据，交给人判断。

从测试观察看，TencentDB Agent Memory 的处理大致分两步：先从已有记忆里找相似候选，优先使用向量召回，向量不可用时再走关键词路径；再把新旧记忆交给模型，判断应该新增、跳过、更新还是合并。这里有一个风险：仲裁模型只能判断已经召回的候选；没被召回的旧记忆，在这次判断里就等于不存在。

测试记录中，PostgreSQL 和 MySQL 最后都留在了库里。旧卡片没有被改写，新卡片记录了切换决定和时间顺序。当时没有打开语义召回，两条记录只有「数据库」这个词相同；从这次结果看，候选召回没有把它们稳定地关联起来。至于是哪一步造成的，还需要结合对应版本的完整日志复核，不能只凭最终卡片反推。

保留旧记录和变更原因，比静默覆盖更容易审计；后续注入时仍然要明确哪一条是当前有效值。实际接入时，至少补齐 source、scope、status、valid_from、supersedes 和 evidence_ref。Mem0 当前官方文档把新算法描述成 ADD-only，强调新旧事实并存；Zep 用时间图表达事实何时生效、何时失效。实现形式不同，都在处理同一个麻烦：历史不能凭一次更新悄悄消失，当前状态也不能靠模型自己猜。只有「相似度最高的那条」，系统解决的还只是搜索。记忆治理还要能说明旧事实为什么失效、当前值从哪来，以及谁有权修改。

## 共享要有负责人

个人记忆解决「下一次不用重新解释」，团队记忆还要回答「谁可以使用、谁可以修改、哪个 Agent 应该加载」。Memory Hub 把团队资产分成几类：

| 资产 | 保存什么 | 进入运行时的方式 |
|------|---------|----------------|
| Chat Memory | 对话经验、偏好和决策 | 作为背景线索被召回 |
| Skill | 经过验证的操作流程 | 按任务加载，影响执行步骤 |
| Wiki | 文档、规范和知识关系 | 按页面和链接检索 |
| Code | 代码仓库及其检索知识 | 修改前查代码和影响范围 |

比如，某个项目约定「注释用中文、提交记录以中文动词开头、PPT 用 HTML 输出」，它可以先是个人或项目范围的长期记忆。等团队确认后，才适合进入 Wiki 或 Skill。某次修 CI 时把超时时间从 30 秒调到 90 秒，测试刚好变绿，这最多先算一个候选经验；没有复现、日志和回归验证，它不该自动变成团队默认流程。

腾讯云文档把 Memory Hub 描述为本地部署的 Panel 和 Knowledge Service，连接云端 Memory 实例提供存储与检索。OpenClaw 插件的默认形态则是本地 SQLite + sqlite-vec。这两条路径服务的对象不同，部署位置和权限边界也不同，不能笼统地说成「所有记忆都在本地」。团队资产至少要看得见 Owner、版本、状态、可见范围和 Agent 绑定关系。个人经验进入团队范围前，还要有撤回、替换和查来源的入口。共享是一项明确的治理动作，不能只把个人目录换成公共目录。

还有一个容易在演示阶段漏掉的安全边界。在 Hermes 接入里，Gateway 把 capture、search、recall 暴露为 HTTP 接口，API Key 鉴权是可选项，默认没有配置。只在本机使用时应保持 loopback；一旦监听到非本机地址，就要给服务端和客户端配好同一把密钥。若还允许浏览器跨域访问，再单独收紧 CORS 白名单。「本地能跑」和「可以放进内网」之间，还有这道门。

## 长任务要留现场

跨会话复用靠长期记忆；同一个会话越跑越长，则要另做上下文管理。一个 Agent 连续改十几个文件，期间会读日志、跑测试、查看网页、调用工具。把所有过程原样留在上下文里，Token 会快速膨胀；直接压成一段总结，又可能丢掉「哪一步失败、原始报错在哪里、下一步应该从什么状态继续」。

这类任务在研发现场很常见：一个跨模块的 bug 修复，Agent 已经跑过三组测试，改了两个文件，最后一次构建因为环境变量缺失失败。接续工作真正要拿到手的是当前节点、失败原因、已验证的路径，以及能回到原始日志的入口；「它很努力」这句摘要帮不上多少忙。

4 月写《再看 Hermes Skills：Agent 如何自我进化？》时，讨论过另一种留下来的东西：可复用、可验证、可修订的过程资产。这两件事要分开看：Skill 解决「下次怎样做」，任务状态解决「这次做到哪」，两者不能用同一段摘要代替。

TencentDB Agent Memory 还提供一条可选的短期上下文卸载路径：完整工具日志 → refs/*.md 保存原文执行步骤 → JSONL 保留结构化节点任务状态 → Mermaid 任务画布 → Agent 上下文只注入轻量任务地图。任务地图上的 node_id 负责把摘要和原文接起来。Agent 平时看状态流转，需要核对细节时，再沿节点回到完整日志。它留下的是「当前状态」和「继续查证的入口」，不是一段不可逆的总结。

这项能力当前默认关闭。用于 OpenClaw 时，官方要求版本不低于 0.3.4，还要注册 contextEngine slot 并执行补丁脚本。装好长期记忆插件以后，短期上下文卸载仍要单独启用。官方 README 公布的 WideSearch 对照数据是：成功率从 33% 提升到 50%，Token 消耗从 221.31M 降到 85.64M。这个数字属于 OpenClaw 加插件的特定测试设置，不能直接当成所有 Agent 都能得到的收益。这组数据至少给了一个清楚的提示：长任务的上下文治理，要同时保留状态图和原始证据。

放回发布 Agent 的运行链路，三类对象分别回答三个问题：长期记忆记录「过去发生过什么」，任务地图记录「现在走到哪里」，Skill 或 Runbook 说明「以后这类事按什么顺序做」。三者可以互相提供线索，不能互相冒充。

## 先跑四个测试

7 月那篇文章里一直想守住的边界：一次成功先留下证据，经过归因、回归和回滚，才有资格改变默认行为。放到 TencentDB Agent Memory 的接入上，这条线可以先落到下面四个测试里。如果准备把它接到真实工作流，先拿个人偏好和非敏感项目约束做四个测试，跑通后再考虑扩大范围：

| 测试 | 记录什么 | 观察重点 |
|------|---------|---------|
| 写入延迟 | 原文落盘、L1 可查、L2/L3 生成的时间 | 写入成功与可检索之间差多久 |
| 召回质量 | 原话、同义表达、跨语言表达和无关词 | 关键词、向量、混合召回各自的漏召回和误召回 |
| 更新安全 | 旧规则、新规则、来源和当前注入结果 | 能否区分历史值、当前值和被替代值 |
| 故障降级 | embedding 不可用、召回超时或服务重启 | 对话是否继续，日志是否写明跳过原因 |

测试数据最好故意放入一组会变化的约束，例如「数据库先用 PostgreSQL，后来切到 MySQL」，以及一组不应跨项目传播的规则。只有这样，作用域和时间线的问题才会露出来。还要顺手检查保留策略。当前 capture.l0l1RetentionDays 默认是 0，也就是 L0/L1 本地文件不自动清理。个人试用也许没什么感觉，长期运行以后，它会变成磁盘、隐私和合规问题。如果这四项里有一项说不清，先把范围留在个人工作流，补上观测、删除和纠错入口，再考虑把 Skill、Wiki 或 Code 纳入团队范围。涉及生产权限、客户隐私或合规规则时，Memory 更适合做参考和索引，最终约束仍应由 Policy、配置和审批系统负责。

## 最后五问

Agent 记住一句话并不难，难的是记住以后不把它变成新的隐患。一个可用的记忆系统，至少要回答五个问题：1. 这条记忆来自哪里？2. 它经过了几次提炼、验证和修改？3. 为什么在这一轮被召回？4. 和新信息冲突时，当前有效值是谁？谁有权修改？5. 服务不可用或记错时，系统怎样继续、怎样纠正？

文件型记忆解决了「能不能留下来」，治理问题继续追问「它凭什么影响下一次决策」，验证门槛又决定「它能不能进入 Skill」。TencentDB Agent Memory 还不是最终答案，但它把这些问题放进了可配置、可观测、可下钻的工程链路：高层记忆负责导航，低层数据负责证据，事实变化留下时间线；共享资产有边界，服务出问题也不拖住当前任务。

参数表会随着版本调整，更看重的是这套检查顺序：先确认生命周期和作用域，再核对证据与召回，最后才谈经验要不要晋升。
