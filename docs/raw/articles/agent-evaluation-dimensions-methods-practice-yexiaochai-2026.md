# 一文讲透Agent评测：维度、方法和落地实践

> 作者：叶小钗（公众号）
> 基于作者所在项目自建 Agent 评测平台的实操经验，系统讲 Agent 评测的维度、方法与落地流程。

## 为什么必须评测 Agent

现在开发一个 Agent 不难，难的是判断它到底做得好不好：任务是否完成？效果达到预期吗？模型升级、提示词调整或知识库更新以后，Agent 的表现真的变好了，还是看起来更聪明？如果只靠产品和测试自己想出的几个案例、凭感觉说"看起来可以了"，Agent 就很难稳定用于生产。

**Agent 评测**：用一组具有代表性的任务，在尽可能固定的环境中运行 Agent，并从结果、过程、效率和安全等维度判断它是否达到产品目标。一次完整评测需要回答：
- 结果是否正确（事实、结论、格式、交付物是否满足需求）
- 过程是否合理（有没有选对工具、参数是否正确、是否重复调用/空转/错误后无法修复）
- 运行是否可接受（延迟、Token 成本、执行是否稳定）
- 行为是否安全（有没有越权、泄露敏感信息或执行不该发生的外部动作）

传统问答主要关心答案对不对，Agent 评测还要关心它怎样把事情办成。

**必须评测的原因**：大模型输出有概率性，同一输入多跑几次可能不同；手动测一两次成功只能说明"大概率成功"，无法说明"稳定成功"。Agent 行为依赖环境（网页、知识库、接口会变，工具返回数据可能缺失），只看最终答案很难定位问题。升级一次 Agent 往往改动多个变量（模型/提示词/Skill/工具描述），缺固定数据集和基线报告就很难客观判断收益与代价。执行类 Agent 会真实操作业务数据（发消息、写文件、改数据），操作对象、参数、顺序、权限都必须正确。

## 与传统软件测试的区别

传统软件有明确输入、处理逻辑和预期输出，可用布尔断言。Agent 测试处理更多不确定性：

- **正确答案可能不唯一**：一份报告有多种合理结构，客服回复有多种合格表达，字符串精确匹配会误判
- **最终答案正确 ≠ 执行过程正确**：可能碰巧得到正确结果，但中间调用了错误工具、用了高风险参数、或做了十几次无意义重试
- **评测标准多维**：准确性、完整性、依据充分程度、格式、语气、延迟、成本、安全性需综合权衡，有些维度要一票否决
- **评测器本身也可能出错**：LLM 作为裁判时，评分提示词、模型版本、评分协议都影响结果，评测器也要版本管理、结构化输出校验和人工校准
- **需要统计意义的稳定性验证**：高价值用例不能只跑一次，要重复运行观察平均分、通过率和波动范围

传统测试在 Agent 评测中仍然必要——工具、权限、接口、脚本可用确定性方法验证，先保证基础能力稳定，上层 Agent 才有稳定运行条件。

## 什么时候开始评测

早期是 Agent 开发完成后再考虑测试；后来改为在 PRD 阶段就同步定义评测口径，每个核心功能点写成可观察、可执行的验收。例如 PRD 不能只写"能根据企业知识回答员工问题"，还要明确：必须引用哪些资料、无答案时不得编造、P95 响应时间上限、哪些敏感内容不得输出、检索失败怎么处理。

PRD 评审阶段产品/研发/测试完成：
- 定义任务边界（Agent 做什么、不做什么）
- 定义成功标准（正确性、完整性、格式、过程、延时、成本、安全阈值）
- 建立典型用例（主流程、边界条件、异常输入、高风险操作）
- 约定上线门禁（核心用例必须全部通过、整体通过率和成本上限）

同时定义首批测试集（不必多但要有代表性）：产品/业务提供真实场景，研发补充技术边界与失败路径，测试持续扩充、去重、维护回归集；线上新问题脱敏后加入。

## 按任务类型划分评测

按"要交付什么结果"分四类：

| 类型 | 典型场景 | 预期交付 |
|---|---|---|
| 查询类 | 查天气、查订单、检索网页、查询业务数据 | 一组来自指定数据源、满足查询条件的最新结果 |
| 知识问答类 | 企业制度问答、产品咨询、客服答疑 | 一份有资料依据、能处理未知问题的回答 |
| 内容生成类 | 调研报告、经营分析、会议纪要、方案生成 | 一份满足内容和格式要求的文档 |
| 执行类 | 发消息、写文件、创建日程、修改业务数据 | 目标系统中一次准确、合规且可确认的状态变化 |

一个 Agent 可横跨多种类型（先查询订单→生成回复→发送给客户）。设计用例按阶段拆开，同时保留端到端用例检查衔接。无论哪类，测试集都要覆盖正常流程、边界条件、失败场景（知识问答加资料缺失/冲突/超范围；执行任务加参数缺失/权限不足/接口超时/中途报错/失败后处理）。

## 评测维度

任务类型确定评测对象，评测维度描述对象做得好不好。不同类型可用同一组维度，只权重和门禁不同。

- **任务完成度**：是否真正实现用户目标，而非仅输出看似专业的文本。四类完成标志：查询类=用了正确数据源/查询条件、结果准确及时无遗漏；知识问答类=有指定资料支撑、覆盖要点、资料不足能说明无法回答部分；内容生成类=覆盖要求内容、事实论证可靠、结构格式符合交付；执行类=操作对象/参数/最终状态正确、无额外副作用。
- **答案质量**：准确性、相关性、完整性、事实依据、格式规范、表达清晰度。知识问答关注资料忠实度，报告类检查结构/论证/关键信息。
- **工具调用质量**：是否调用正确工具、规避禁止调用的工具、参数传递与上下文意图一致、返回结果正确解析用于后续推理、失败时合理重试或降级。
- **Skill 使用质量**：场景是否适合、skill 选择是否正确、是否遵循 Skill 规定步骤（不跳步/不私自简化）、是否正确调用配置脚本并遵守输出约束。
- **执行过程质量**：最终答案正确时过程缺陷仍带来成本与风险——无意义重复调用、无任务推进的空转轮次（循环推理/无效自我修正）、错误后能否有效恢复、是否绕行过长路径。
- **非功能质量**：延迟、Token 消耗、成本、稳定性、安全性、隐私保护。

## 评分与验证方法

实践中组合使用：
- **确定性评分**：精确匹配、包含、正则、JSON Schema、字段断言。靠规则+代码验证，快、成本低、结果稳定
- **轨迹评分**：评估 Agent 执行路径，检查必需/禁止工具是否参与、工具参数、重复调用、空转、错误恢复、步骤数量，适合工具型与执行型
- **LLM-as-a-Judge**：按明确 Rubric 评价准确性、完整性、逻辑等语义维度，适合开放式答案
- **人工评审**：用于高风险样本、主观体验、抽样质检；主要负责校准机器评分
- **重复运行与统计评测**：同一用例跑多次，算均值、方差、通过率，识别偶发成功与不稳定
- **对比评测**：新版本与固定基线得分比较，看哪些用例变低/变高、成本延迟变化
- **线上评测**：对真实请求脱敏抽样，结合用户反馈和安全监控发现问题，再把典型失败加入离线数据集

## 落地流程

**建立数据集**：按准确性、幻觉、性能、安全等目标管理，分开发集（日常调试）、回归集（验证已知问题没复现）、保留集（尽量少参与提示词调试，检查对未见任务的表现）。数据集要版本管理（修改中的用例可继续编辑，正式评测用已发布固定版本，几周后仍能确认当时跑的是哪批）。每条用例至少含问题、上下文、参考答案/期望结果、评分标准、标签、优先级；复杂任务可加多轮消息、结构化期望输出、断言、评分器绑定。

**评分器设计**：能写成确定性规则的优先交程序，开放式内容交 LLM，争议样本和高风险结果人工复核。四类评分器：执行过程评分（工具选择、执行路径、错误恢复）、模型评分（按 Rubric 判最终答案）、人工审核（高风险样本+争议）、执行过程指标统计（重试/空转/错误/工具调用次数）。每条用例可绑定不同评分器，评分器要保留版本（否则换评分提示词后分数失去可比性）。多评分器按权重算总分，安全/权限/关键业务结果设为强制门禁（任一项失败即不通过）。LLM 评分器返回结构化维度分+理由，总分服务端重算。规则评分（精确匹配/包含/正则/JSON Schema/延迟/成本）配置在具体用例里。

**执行环境设计**：运行评测记录完整快照（数据集版本、Agent 提示词版本、模型与参数、工具、Skills、MCP、知识库配置、评分器版本、评测协议），否则今天与上周的分数差可能来自未记录的配置变化。执行任务控制外部副作用：禁用/Mock/记录/回放/受控执行等工具模式。每条评测任务限制单用例超时、总 Token、总成本、总运行时间，预算耗尽及时停止。

**执行并记录完整 Run**：Agent 平时运行已记录完整过程，评测复用同一套 Agent Runtime 和可观察性数据，工具调用、模型输出、耗时、Token 与真实运行同一种记录方式，轨迹评分和 LLM 评分从 Run 取证据。高价值用例重复执行多次，报告除平均分/通过率还展示波动；新版本测试绑定以前结果做对比，看哪些用例进步/退化、成本延迟变化。

**分析失败**：未通过用例进问题中心，人工结合执行轨迹、失败类型、评分理由判断问题出在提示词/模型/知识库/工具/环境/评分器；记录严重程度、负责人、修复版本；修复后从原问题发起复测，复测失败重新进问题中心。

**持续回归**：开发失败、人工评分争议、线上典型问题都可脱敏后加入回归集。新增用例去重+评审，评分器靠人工样本持续校准。回归按计划定时运行或接入 CI。

## 结语

作者强调是"一路踩坑一路填"，每做一个功能拿真实例子跑，等第一批用例真跑通，冒出来的小问题比想的多得多。核心经验：Agent 评测要从"感觉还行"变成一套可反复运行、版本对比、发现问题、持续回归的机制。
