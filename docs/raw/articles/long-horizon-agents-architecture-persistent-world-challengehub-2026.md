# Long-Horizon Agents 架构全解：如何让智能体持续工作数小时甚至数天

> ChallengeHub 长时程智能体架构解读：从"完成任务"到"进入环境"的范式转变，长时程环境六组件（状态/时间/事件/动作/记忆/奖励）+ 状态架构演进 + 持久/分布式/部分可观测状态。

## 从"完成任务"到"进入环境"
Agent 现在最不缺的是演示。真正难的是让 Agent 连续工作十二小时、三天甚至更久，中间记住关键事实、等待外部反馈、处理突发事件、从失败中恢复，并为早先决定承担后果。

强化学习（Sutton 和 Barto）→ 深度学习（AlphaGo/AlphaGo Zero/OpenAI Five）→ 语言模型（DeepSeek GRPO、Thinking Machines Lab on-policy distillation）——这些方法都指向：Agent 不只是生成答案，还要在反复交互中推理、行动、获得反馈再继续改进。任务一旦从几分钟拉长到几小时几天，就必须面对持久状态、有效记忆、外部事件、带副作用的工具、故障恢复和延迟奖励。

常见基准（SWE-bench 等）给一段提示词、一组固定工具、一串可执行动作和一个最终答案，只在任务足够短、模型思考期间外部世界不变时好用。任务周期一拉长就不够：期间有新信息到达、工具改变系统状态、人类几小时后回复、早先决定影响后面选择。GitHub Actions 和 AWS Step Functions 就是例子——即使当前没有模型在输出 token，系统里的事件和状态依然在变化。

**核心区别：任务给 Agent 一个需要解决的问题，环境则给 Agent 一个可以持续行动的地方。** "模型此刻看到了什么"和"世界里真正发生了什么"不是一回事——上下文窗口只有 Agent 当前拿到的观察结果，环境里保存着完整世界状态（未查看文件、排队事件、不可见约束、行动后果）。评估不能只问"模型能不能答对"，还得问"能不能在一个持续变化的世界里长时间做出正确行动"。

## 长时程环境的核心架构：六个基础组件
长时程环境不是多接几个工具，而是能持续存在、不断变化并记录后果的系统。Agent 看到的是系统某时刻暴露的观察结果，通过接口采取动作；最终被评估的是一条可能横跨数小时甚至数天的完整轨迹。六个基础组件：

1. **状态（世界的事实底座）**：不是上下文窗口也不是聊天记录，包括文件/数据库/邮件/账户余额/待处理案件/任务进度/权限/已做决定。时刻 t 世界状态记作 S_t。必须拥有独立于模型进程的持久状态——即使模型退出/崩溃/被替换，状态仍能被检查、更新和恢复。
2. **时间（Agent 一块表，世界另一块表）**：Agent 时间记录推理步数/消息数/工具调用数；世界时间记录真实经过的小时/截止日期/等待周期/后台任务。两者不同步——Agent 四小时没调用但截止日期仍靠近。环境必须显式支持等待、定时动作、超时和时间推进；训练环境还需加速模拟（三小时压缩成三分钟）但事件顺序和因果不能乱。没有世界时间，所谓"长任务"只是更长的一段聊天记录。
3. **事件（世界不会等 Agent 思考完再变化）**：不一定由 Agent 触发的变化（邮件到达/客户回复/实验结束/其他员工改文件/API 失败/价格波动）。状态转移：S_{t+1}=f(S_t, A_t, E_t)，A_t 是动作、E_t 是外部事件流。有了事件环境才真正动态——Agent 思考、等待甚至离线时世界依然变化。
4. **动作（工具调用成功≠决策正确）**：动作是改变环境的接口，不同动作分量不同（读数据库记录 vs 批准理赔，搜代码 vs 合并 PR）。动作可能带来成本/延迟/权限/副作用/可逆性/后续影响。真正有意思的是动作会不会改变未来决策空间——一步做完后未来还剩哪些选择。
5. **记忆（环境保存世界，Agent 保存线索）**：记忆属于 Agent，状态属于环境，不能混。四类记忆：工作记忆（当前子任务）、情景记忆（过去事件）、语义记忆（稳定知识）、制品记忆（指向文件和产物）。困难在于决定什么值得保留、什么压缩、何时重新检索——把三天完整轨迹塞回上下文不叫记忆架构，只叫上下文越来越长。
6. **奖励（不仅看结果，还看怎么做到的）**：R(τ)=R_outcome+R_efficiency+R_constraints+R_process。长任务要评估成功如何实现而不只是停在哪个状态——保险 Agent 结论正确但索要不必要材料/违反政策/解释错误原因，轨迹仍不优秀。

## 状态架构：状态放在哪里，由谁负责
状态架构决定三件事：系统能否在故障后继续、能否与其他参与者协同、能否区分"过去看到的结果"和"当前世界的真实情况"。

**Agent 状态架构演进**：2022 ReAct（观察-推理-行动工具调用循环）→ 2023 WebArena（评估从最终答案走向真实网站/持久数据/多步交互）→ 2024 SWE-bench（真实代码库/Issue/测试/补丁/仓库状态）→ 2025 Temporal（持久化执行，工作流保存历史/跨故障运行/等待人工后继续）→ 2026 状态外部化（现代 Agent SDK，沙箱/快照/记忆/工具/重建机制统一到长时运行框架）。

- **提示词内状态**：全部状态放进提示词（系统指令+对话历史+最近工具输出每步重传）。开发快，但对有边界编码任务/短时研究够用。问题是上下文窗口承担太多责任，进程崩溃/历史截断/第二天回来关键状态就消失。适合作为工作记忆，不适合作为长期环境事实来源。
- **持久状态**：把 Agent 临时执行过程与必须长期保存的信息分离。计划/任务状态/文件/外部作业 ID/已做决策/检查点/权限写入持久存储。模型可以不运行，但 Agent 作为持续存在的工作实体没有消失——可被唤醒、加载状态、完成一段工作、写检查点、休眠、新事件到来后继续。Cloudflare Agents 是生产级参考；OpenAI Agents SDK 描述外部化状态/沙箱快照/长时任务重建。难的不是保存一切，而是判断哪些信息必须持久化（一笔待付款项/决策理由/外部任务标识符不能丢，完整对话记录没必要）。
- **分布式状态**：生产环境很少只有一个 world_state.json。保险 Agent 可能同时依赖理赔数据库/邮箱/文档存储/CRM/支付系统/外部 API，状态分散在不同系统、不同团队维护，各自不同延迟/权限/故障模式/一致性保证。带来经典分布式系统问题：陈旧读取、并发写入、重复事件、重试、部分失败、最终一致性。Temporal 有参考价值：把可持久化工作流历史与产生副作用的活动分离，API/工作进程消失工作流仍记得发生过什么、可安全重试——这是"从检查点继续"和"整项任务全部重来"的区别。
- **部分可观测状态**：不能把答案直接塞给 Agent，需持续观察环境更新对当前局面的判断。
