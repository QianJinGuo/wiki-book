# 一篇讲透 Agent 自进化飞轮怎么搭：评测→记忆→落地→控制

> 腾讯技术工程（yannisyang、ethanytzhou）基于对 Anthropic 递归自改进报告、斯坦福 CS329A 课程、EvoAgentX 等开源框架的深度研读，提炼出评测→记忆→落地→控制的四齿飞轮方法论——一个完整、可落地、经过验证的工程闭环。

## 开篇：一个被拆散的系统
评测、记忆、Self-Improve 三件事在大多数团队里被拆散着做：评测团队跑完打个分就结束（分数去了周报，没到改进链路）；记忆团队做向量检索存对话历史（召回噪声高，最后被默默关掉）；Self-Improve 团队探索 Skill 自动生成（质量参差不齐，没评测筛选、没版本管理）。每个团队都认真做自己那一块，但飞轮没转起来——因为这三件事不是三个独立功能点，而是同一个闭环的不同环节。评测是"眼睛"（感知问题）、记忆是"大脑"（积累经验）、Self-Improve 是"手脚"（把经验变改进）、人机协作是"方向盘和刹车"（确保方向不跑偏）。

三个核心立场：①自进化的瓶颈不是任何技术点，而是环节之间的衔接——评测信号必须能流进记忆和 Skill 更新，更新后必须能被评测验证，验证结果必须能反哺下一轮进化，断任何一环飞轮都转不起来；②评测的可信度 > 系统的复杂度——错误的正反馈会让 Agent 加速开往悬崖；③记忆系统的核心不是存储，而是治理能力——版本控制、主动遗忘、冲突解决、来源溯源这些"不性感"的治理能力才是决定记忆系统帮忙还是添乱的关键。

## 〇、先对齐概念：自进化改的到底是什么？
自进化按"改什么"分三层：①Artifacts 迭代——改输出产物（代码写几版越来越好，但任务结束 Agent 本身没变，不是进化，已成熟如 Self-Refine/Test-time Compute Scaling）；②Harness 自改进——改 Agent 配套系统（记忆/Skill 文件/Prompt/工具配置/工作流，持久化跨会话生效，改一次后续所有任务受益，当前最具性价比）；③Model 进化——改模型参数本身（Agent RL/自对弈微调写入权重，持久性最强但成本最高风险最大，仍在研究阶段如 MiniMax M2.7）。

Harness 层是主战场，四个字：即时、可控。改完 Skill/Prompt 立刻生效不用重训，改错一键回滚。实测：落地案例通过 Harness 层进化，迭代次数减少 70%、Token 消耗降低 80%+；Agent Memory 场景 Token 节省超 60%。三层非割裂——Harness 经验可变成训练数据改进 Model，更强 Model 产出更好 Artifacts。

## 一、信号——评测不是打分，是整个飞轮的信号源
### 1.1 评测在自进化中的角色被严重低估
评测至少有三重职责：方向指引（告诉系统"哪里有问题"决定进化方向）、质量门控（更新 Skill/Prompt 前验证"改了是否更好"防退化）、经验筛选（判断执行结果是"好经验"值得沉淀还是"坏经验"丢弃）。传统评测只承担质量门控；自进化评测打错分是"Agent 学到错误经验并持续污染后续所有任务"。评测质量直接决定记忆质量、Skill 更新方向、飞轮正转还是反转。评测的可信度 > 系统的复杂度——搭任何自动化之前先确保评测信号是准的。

### 1.2 评测体系的七大核心难题
评测面临精度×成本×覆盖面三难困境，七个难题按"最致命→最常见"：
1. **弱评估器**（最致命）：LLM 给 LLM 打分，评估器有系统性偏差——偏好长文本、偏好特定格式、偏好表面正确性。偏差是系统性的，Agent 会在多轮进化中"学会"把答案写长来骗过评估器。错误的正反馈比没有反馈更可怕。
2. **评什么维度**：Agent 输出是"推理过程+工具调用序列+中间结果+最终答案"的组合体，只看最终答案漏掉大量问题（虚假通过/工具冗余/推理链错误但记忆力强记住答案）。
3. **评什么粒度**：粗粒度（整个任务成功/失败）便宜但不知错在哪；细粒度（每个 step/tool call/决策节点）精确但成本指数级增长（实测几百到上千次 LLM 调用）。建议日常粗粒度快速筛选，失败 case 细粒度深度归因。
4. **开放式任务难量化**：写作/策略规划/方案设计无确定对错标准。人工审查不可扩展，纯 LLM Judge 有弱评估器偏差。这也是最成功自进化案例集中在编码和确定性任务的原因。方向性建议：偏好排序代替绝对打分、AI 初筛+人复核流水线（人只审有争议的 10-20%）。
5. **评测集漂移**：业务在变但评测集半年不更新，Agent 在旧集上"刷出高分"而线上体验下降。隐蔽性在于没人会在全绿时怀疑评测本身。
6. **预算公平性**：很多"自动进化"的提升只是多花计算预算（Best-of-N/多次重试取最好），关掉预算就打回原形。评估必须在预算对等条件下进行，否则是自欺欺人。
7. **评测成本**：一轮完整评测需几百次 LLM 调用，每次改动跑全量 Token 成本失控，限制迭代频率。解法是分层评测（每次改动轻量级回归核心 case，定期全量评测全集）。

### 1.3 建设要点：可信评测体系
评测手段分层组合（成本花刀刃上）：底层规则/自动化校验（代码能跑/测试通过/SQL 匹配/格式正确，零成本 100% 客观，是基石但被大量浪费）；中间层 LLM-as-Judge + 对照实验（关键原则：生成模型和评估模型必须分离避免自洽偏差、评估 temperature 设为 0、输出必须结构化用 Pydantic/JSON Schema、分维度独立评估）；顶层人工抽样 + 元评测集（定期随机抽样人工二次评审对比人 vs LLM Judge 打分，不一致超阈值校准评估器；维护"绝对正确/绝对错误"元评测集，评估器连极端 case 都判错则所有打分不可信、系统告警）。

评测集三分法严格职责分离：train 集（只用于诊断阶段，告诉系统"哪类问题失败率最高"，可暴露给 LLM 生成修复方案）、val 集（只用于筛选候选变体是否比基线好，绝不暴露给生成修复的 LLM 否则被记住）、test 集（只用于最终验证，独立捕捉"在 val 上过拟合但对新问题无效"）。三者互不泄漏。比例 train 50-60%/val 20-30%/test 15-20%，按问题类型分层抽样，val 集每 2-4 周更新 20-30%、test 集每 1-2 月更新、train 持续追加线上失败样本。

评测的终点不是打分，是诊断归因。按失败类型分组、分析失败模式、定位根因，然后按根因类型走不同链路：系统性问题（多个 case 同类错误）→ 触发 Skill/Prompt 更新 + 写入 Playbook；偶发个例 → 写入记忆作为"教训/反例"；能力缺失 → 触发工具/能力补充（Auto-Research）；回归问题 → 立即回滚 + 标记 blocked + 人工排查；全部通过 → 新版本合入 + 正例加入"金标集" + 灰度观测。归因粒度决定修复精度：粗归因（"这个 Skill 不好"）导致大面积重写，精细归因（"参数提取阶段正则漏了某格式"）才精准。血泪教训：某场景连续 3 轮失败率 80%+ 不下降，先查工具实现层（API 参数/服务端异常/数据没回来）而非配置层——配置层进化解决不了工具层 Bug，实践中出现过 20+ 轮无效迭代、根因在工具层的案例。

评估器本身也需要被"评测"（元问题）：四种互补机制识别 LLM Judge 系统性偏差。

### 1.4 Skill 评测的特殊性——证明 Skill"真的有用"比想象中难
Skill 是 Harness 层进化的核心产出物，但证明它"真的有用"而非"碰巧存在"很难（很多 Skill 只是和模型能力碰巧重叠）。Skill 评测至少需通过四层验证：
1. **对照实验**：有/无 Skill 两组对照，若无 Skill 时 Agent 也能做对则贡献为零（很多团队跳过，积累大量浪费上下文窗口的无用 Skill）。
2. **难度校准**：评测 case 太简单则有无 Skill 结果都对看不出差异，需设计有一定难度梯度的 case（无 Skill 时能做对一部分做错一部分）。
3. **轨迹追踪**：运行时追踪执行轨迹（tool calls/推理链），检查是否出现 Skill 定义的关键步骤——Skill 存在但 Agent 靠自身能力完成、Skill 只占位置没被使用是常见假象。
4. **路径验证**：结果对但路径对吗？Agent 绕过 Skill 关键校验步骤碰巧得到正确结果，下次会翻车。工程化建议：每个 Skill 上线前跑对照实验、评测 case 有难度梯度、引入轨迹评测、定期复评（Skill 可能因环境变化过时）。

## 二、积累——记忆系统的核心不是存储，而是治理
记忆做不好比没有记忆更差：多个团队加长期记忆后因检索噪声过高降级回无状态。记忆系统真正要解决的不是"存储"（最简单），而是治理——什么该存、什么该忘、怎么确保存的是对的、怎么精准召回、怎么不占太多上下文。把记忆系统当作"治理系统"而非"存储系统"来设计是最重要的认知转变（像 Git 的价值不在存代码而在版本控制/分支/冲突解决/审核）。

### 2.2 记忆的三环矛盾与十大难点
写入环（什么值得存）：①价值判断难（大量中间信息大部分是噪声，有价值经验藏在小细节）；②正负反馈不对称（成功时不知因何成功，归因难）；③记忆粒度选择（太粗无法复用，太细信息过载）；④隐性知识难捕获（最有价值的是"什么不能做"这类负空间知识）。
存储环（怎么不腐烂）：⑤记忆污染/上下文投毒（错误记忆写入后影响数百次后续任务，错误蔓延快于修复——最危险失败模式）；⑥时效性衰减（过期信息没清理，Agent 高置信错误输出）；⑦记忆冲突（不同来源互相矛盾，无解决机制随机引用）；⑧存储成本失控（无遗忘策略则线性增长、检索越慢噪声越高）。
读取环（怎么用不出问题）：⑨检索噪声（向量相似≠语义相关，注入错误"相关记忆"比不注入更糟）；⑩上下文预算分配（注入太多挤压工作空间，太少漏关键背景）。

### 2.3 建设要点一：写入——"策展而非全存"
Agent 不是录音机而是策展人。正信号触发写入（用户确认/评测通过/任务成功），无信号中间过程默认不存。失败也提取经验但标记"反例/陷阱"（明确的反例比模糊的正例更有价值）。三层晋升机制（来自 self-improving-agent Skill）：先用低门槛解决"忘记记录"，再通过门槛层层筛选把有价值内容升级，越往上质量越高噪声越少。非对称淘汰设计：好经验强化速度(+0.05)远慢于坏经验淘汰速度(-0.12)，淘汰是强化的 2.4 倍——一条错误记忆的伤害>一条正确记忆的收益。

### 2.4 建设要点二：存储——分层架构 + 生命周期管理
分层架构（Hermes Agent 56K+ Star 等验证）：默认用顶层（轻量高密度），需要时钻取下层（详细有证据）。更细化为四层（L0 原始对话→L1 原子事实→L2 场景块→L3 用户画像），核心"默认 L3，按需钻取 L1/L0"。生命周期管理：版本控制（每条记忆带版本号+来源标记）、演化能力（沿时间线更新/合并/分裂/衰减）、主动遗忘（TTL/使用频率衰减/负反馈标记淘汰）、冲突解决（后入优先+人工仲裁高冲突项+乐观锁防并发）。

### 2.5 建设要点三：读取——"渐进披露 + 严格预算"
"从粗到细、按需钻取"模型：Step1 默认只注入顶层（Persona+Skill 前言约 500-800 token 最小背景）；Step2 按需检索中层（任务到来语义检索相关 Facts/Scenario，三路并行语义向量+全文关键词+精确匹配融合排序取 Top-K）；Step3 需要时钻取底层（node_id 回溯原始对话，平时不加载）。严格预算：分层 Token 预算（Skill≤2000/Facts≤800/Profile≤500）、单条≤200 Token 强制精炼、最多注入 6 条、Pain-aware 动态调整（简单任务少给复杂任务多给）。反直觉发现（Anthropic Dreaming 2026.5）：记忆建模为文件系统让 Agent 用 Bash/grep 检索管理比专用 API 更有效（Agent 本就擅长操作文件）。符号化压缩方向：用 Mermaid 编码任务状态、完整日志卸载外部、Agent 在符号图上推理需要时 node_id 检索——实测 Token 节省超 60%。
