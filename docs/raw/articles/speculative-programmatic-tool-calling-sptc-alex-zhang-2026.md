# Speculative Programmatic Tool Calling (sPTC) — Alex L. Zhang

Speculative programmatic tool calling (sPTC) is a class of techniques for overlapping tool call computation with the code being generated by a harness. It is inspired by speculative execution in CPUs and speculative decoding in LLMs. The trick: speculate and pre-launch tool calls from partially generated REPL calls as the harness is still generating tokens, rather than waiting for it to finish the entire generation. It is most useful when the tool of interest is a sub-LLM or sub-agent call, such as in a Recursive Language Model (RLM). If the fully generated REPL actually ends up calling these tools, they immediately return with their cached outputs from the speculated call.

A key observation is that LLM tools (sub-agents, search APIs) are often high-latency and are usually the bottleneck in harnesses that rely on code execution as actions. Furthermore, the actual generation of the main context is often also a significant latency bottleneck that blocks intermediate calls from happening. There are two obvious areas of savings:

1. **Overlapping already-generated tool calls during token streaming.** Most harness designs wait for the entire model generation to complete before executing tools. This is likely a consequence of JSON-style tool-calling, where it was not a bottleneck. Because generation of the main context per turn is often slow, this represents a significant portion of time that can be cut, especially for models that "think" for a long time.
2. **Acting as a JIT compiler over REPL calls.** Even without streaming enabled, many REPL programs contain blocking tool calls that aren't actually blocking — e.g. two independent sub-agent calls that the code does not write as asynchronous can still be run in parallel. sPTC acts as a "really naive" JIT compiler to prevent such cases, and likely can be improved further across languages and REPL designs.

On locally running LLMs (one or a few chat instances at a time), the inference engine is often highly memory-bound from decoding just the main context, and speculation can help increase arithmetic intensity. For high-volume serving systems using frontier labs or model routers, batched requests are abstracted away to disjoint serving engines, so the gain is purely from overlapping computation with the main context, or overlapping execution time with a slow REPL call.

## Benchmark Numbers on RLMs

The implementation was benchmarked on OOLONG (trec-coarse, 132k) and OOLONG-Pairs (32k) from the original RLM paper, using a node of 8xH100 80B running a vLLM server, with Qwen3-30B-A3B-Instruct-0527 at both temperature=0.7 and temperature=0.0. Each experiment ran 5 times, across 4 concurrent and 8 concurrent runs over the same serving engine. The speed-ups for the RLM are generally on the order of **1-1.2x**.

## Design: Shadowed Execution

The high-level design is to have imported tool calls in the REPL have a hook that can be called earlier and replaced with a cached output when needed. The contract defines (1) what tools should be speculated (e.g. sub-LLM calls yes, sub-RLM calls too costly), and (2) a mechanism for speculating on tool calls whose inputs rely on variables computed previously in memory, rather than just literals.

The key mechanism is a "shadow REPL": a deepcopy fork of the primary code REPL that executes the partial REPL on the fly. Most external libraries and unsafe functions (like `open`) are marked as "unsafe", and any speculatable tools with input dependencies using those functions are not speculated. The speculator executor is deliberately NOT used as the real REPL executor, because the full REPL the model produces may contain error-prone code or incomplete tool calls — in these cases we do not want the speculator to modify REPL state, treating the entire REPL cell as a unit of computation.

```python
@spec.tool(speculatable=True, pure=True)
def tool(...) -> OutputType: ...

# Speculated version
def tool_spec(...):
    promise = launch(tool(...))
    register_speculation(promise)

# Hooked version run in real REPL
def tool_real(...):
    if exists(promise, ID(...)):
        return promise
    else:
        return tool(...)
```

```python
real_ns = {**locals, real_tools}
shadow_ns = replace_tools(real_ns)
# speculate while LLM is streaming
while not LLM.done:
    code += LLM.next_tokens()
    parse_and_peek(code, shadow_ns)   # queue without code execution
    parse_and_speculate(code, shadow_ns)  # re-run shadow REPL
# real tools now route to promised tools
exec(code, real_ns)
```

**What can be speculated:**
- **Case 1 — Literals:** String/integer literals can immediately be parsed and converted into a tool call without shadowed execution.
- **Case 2 — Input dependencies:** As long as all inputs are "safe" (pure functions, no side effects), they can be speculated. Tools relying on speculated dependencies wait for the dependencies, then execute even if the LLM is still streaming.
- **Case 3 — Peekable and non-peekable dependencies:** During streaming, the working namespace of the shadow REPL enables speculation even when dependencies are variables in memory.
- **Case 4 — Blocked speculation:** An allowlist of keywords/function calls defines what can be used to compute input dependencies; blocked tools are not speculated.

In PTC, a tool call is uniquely indexed by its inputs (and occurrence if non-deterministic). For identical tool calls (e.g. majority vote over several sub-agents), unique instances must be tracked so a single speculated call does not route to each copy, unless the call is known to be deterministic.

## Speculation Overhead

The extra runtime overhead is negligible because the speculator cheaply parses and checks whether it can speculate over the partially generated REPL. On memory, a deepcopy of the harness code REPL is created, generally cheap relative to the allocated memory of actual REPL variables. The worst case is when the serving engine for the tool is clogged with many concurrent speculated requests, controllable by how aggressive speculation is and how tools are queued.

## Related Ideas

- **Conveyor (Xu et al., 2024):** allows users to define partial execution opportunities such as a line of code, parsed during decoding.
- **Speculative Interaction Agents (Hooper et al., 2026):** formally defines the Conveyor system as "speculative tool calling", mainly reducing time-to-first-token (TTFT) by overlapping long thinking chains with an invoked tool call.
- **AsyncFC (Feng et al., 2026):** argues tool calls are often implemented blocking, defines a contract for future-based async wrappers; risk of not being 1:1 with the original harness trajectory.

sPTC argues that adding speculation to tools in a more complex program is significantly more useful than for standard tool calling because of the unknown runtime of the program itself. For standard tool calling, by the time the LLM has finished generating enough tokens to fully specify the tool call, there likely are not many more tokens left to generate. Code execution makes the actual tool call patterns significantly more complicated, leaving more room for overlap.

## Ending Note

Speculative programmatic tool calling is a natural trick arising from programmatic tool calling itself having more potential for overlap than traditional tool calling. Beyond overlapping with streamed token generations of the root LLM, the real long-run value comes from more clever JIT compilation tricks to overlap tool calls in the PTC setting with the actual REPL execution itself. The current implementation is most useful for locally running models and agent harnesses; it is currently mainly {Python, bash, Bun} x {Coding harness, RLM, game agent}.
