# 一文搞懂个人AI记忆系统构建全流程

> 来源：腾讯云开发者（原创作者 左德军）| 2026-08-27 入库 | v=7 c=7 v×c=49 Raw only

## 缘起

任何公司/组织想用好 AI，前提是完成基建治理（数据清洗、知识库构建、流程对接），否则再强模型也只是"聪明的陌生人"。个人层面：给 codebuddy 讲的个人信息/原则/协作关系，还要给 workbuddy、龙虾、claude code 重复讲；新增/更新要重复，且信息频繁变。更痛的是——积累的上下文和判断经验**绑在特定工具上，换工具就丢**。诉求：无论用哪个 AI，它都能快速知道"我是谁/我在做什么/我怎么判断/我希望怎么协作"，且自动更新同步，信息属于用户并归用户管、不绑定单一工具。

## 怎么构建

### 2.1 五层记忆（每层回答一个问题）
- `identity` — 我是谁
- `principles` — 我的原则/我如何判断
- `preferences` — 我希望 AI 怎样和我协作
- `context` — 我正在经历/做什么
- `knowledge` — 我有哪些可复用的经验和能力

### 2.2 二级子目录
每个一级目录下再划分二级子目录。分法遵循一个原则：**同一层内部按「信息的来源或用途」拆成三类**，不强行凑数也不放任发散。

### 2.3 目录有且只有两级、禁止无限嵌套（硬约束）
- 二级目录下只放文件，禁止三级目录；内容多用文件名前缀区分（`report-xxx.md`、`coding-xxx.md`）。
- 理由：路径每深一层，AI（和自己）定位一条记忆要做的选择就翻倍，三层四层嵌套会让「这条到底在哪」本身成为成本。两级封顶，任何一条记忆最多两次选择即可定位。
- "嵌套会把分类变成迷宫"：子目录无限建，同类信息会因约束不明确越积越乱；扁平+文件名前缀，分类信息写在文件名里一眼可扫。
- 想再建一层目录时，往往是在用新增目录逃避「这条记忆到底属于哪类」的判断——约束死目录深度倒逼归类想清楚。

### 2.4 冲突解决
- 稳定性考量：`identity/`、`principles/` 是**稳定层**（极少变）；`preferences/`、`context/`、`knowledge/` 是**动态层**（持续更新）。分清「长期不变的我」vs「当前阶段的我」，避免把易变 context 误当长期身份。
- 示例：「诚信是底线」（价值判断）→ principles/；「系统风险梳理工作法」（操作步骤）→ knowledge/skills/；「2026-02-04 xx系统设计评审纪要」（有日期事件）→ knowledge/experiences/；「系统设计评审模板」（无时间绑定方法）→ knowledge/skills/；《金字塔原理》读书笔记（外部输入）→ knowledge/learnings/；内化后自己的表达框架 → knowledge/skills/。
- **升级路径**：经验里反复出现的规律 → 提炼成技能；学习内容内化后 → 形成自己的技能。记忆不是静态归档，会"升级"（目前升级主要靠人工判断）。

## 记忆权重管理
- 五层记忆按重要性分五个等级（L1-L5）。
- **权重等级不作为独立字段写入文件，而是和目录绑定**——内容所在目录决定其权重。
- **冲突裁决**：高等级优先于低等级，但始终保留用户最终决策权——AI 可提示「某条 L1 原则与当前决策冲突」，但决策由用户做，不是 AI 替做。

## 记忆文件的元数据（7 字段 YAML frontmatter）
参考 Google Cloud 的 OKF（Open Knowledge Format）规范，只取自己需要的 7 个字段（相当于每条记忆的身份证）：
- `type` — Identity/Principle/Preference/Context/Skill/Experience/Learning，与目录一一对应
- `title` — 一句话标题，进 INDEX 总索引
- `description` — 一句话说明「是什么 + 何时调用」，AI 扫到即可判断要不要读
- `status` — active/archived，过期标记不参与调用
- `privacy` — internal（个人信息/团队信息）/ public（通用方法论）
- `tags` — 跨目录主题标签（如 [写作, 汇报, 认知]），弥补目录单一维度不足
- `timestamp` — YYYY-MM-DD 沉淀日期（非创建日期）

## 实际案例：组织协作关系维护
维护一份「团队组织协作关系」说明整套结构落地。定位：**不是通讯录、不是项目材料，而是一份「AI 协作索引」**，帮 AI 判断「涉及谁/哪个团队负责/谁能拍板/谁要对齐/哪些还不确定」。放在 `context/relationships/`（组织关系是会变的现状，不是长期身份、不是判断原则）。

内容三类：①高置信组织事实（谁负责什么/谁向谁汇报/团队边界）；②可使用的协作约束（谁是负责人还是对接人/谁能拍板）；③明确标注的待补齐项（不确定信息单独列「待补齐清单」）。

案例效果：AI 基于协作关系文档主动提醒「此方案涉及标签系统和投放策略——张三团队李四提运营需求，你承接能力建设，要不要先发草稿给李四对齐？交易应用侧对接人是王五，也建议提前同步」。AI 挖掘的协作人员清单比用户自己想到还全。无此信息时 AI 像执行员工，有此信息 AI 像贴身秘书。价值不在「存了谁是谁」，而在 AI 在正确时机把正确的人从记忆里「捞」出来。

## 记忆索引机制（两层）
- **总索引 `memories/INDEX.md`**：整个记忆库的地图，收录所有记忆文件 `title` + `description` 一行一条。AI 扫一遍 INDEX 就知道「有啥、哪些相关」，再决定读哪些正文，不全量阅读。每写一条新记忆或修改已有记忆，INDEX 由维护 skill 自动同步。
- **子索引（每目录 README.md）**：每个一/二级目录下都有 README，告诉 AI 此目录装什么/不装什么/常见文件。新 AI 首次接入按 README 快速了解结构。

## 记忆的使用和维护
使用分两层：**公共基线**（关键协作原则/沟通偏好/行为准则，定期同步到各 AI 工具全局配置，不用每次手动调用）+ **按需加载**（特定任务/会话才用，任务相关时调取）。开发两个跨平台 skill（只要工具支持 skill 就能用）：

### 7.1 记忆使用：personal-memory-recall
只做一件事：根据当前任务类型把相关记忆加载进来，需显式调用。流程：读 `memories/README.md` 的「调用判据」表 → 按任务信号匹配要加载的目录 → 扫 INDEX.md 的 description 筛出具体文件 → 按 L1→L5 权重顺序加载。不同任务优先调用哪层由 skill 自动路由。实际案例（设计文档评审）：加载后应用「设计文档要补齐边界/链路/依赖风险/异常处理/为什么这么做」，补背景、补协作、补决策（每个关键方案写"选项/选择/依据/代价"）。

### 7.2 记忆维护：personal-memory-curator
curator 管写。从日常对话提取值得沉淀内容，按 README 路由到正确位置，经用户确认后写入并提交。维护流程：读路由权威（README）→ 从对话提取候选记忆 → 用户确认 → 提炼每条属性（本质/时间/来源/稳定性/形式）→ 按 README 路由表定位目录 → 输出决策报告（含排除理由）→ 用户批准 → 写入文件+同步 INDEX → 每条独立 git 提交。

原则：README 唯一路由（每次运行前完整读，不靠记忆跳过）；先提取、再确认、后写入；排除理由必写；一次归档一个 commit，多条信息分别提交（可追溯可回退）。实际案例：从写作纠正中提取「拒绝正确的废话」和「命名要清晰直接、少用抽象黑话」两条偏好，明确其余项目产出归 worklog 不提取。

## 总结
运行闭环：接入任意 AI/工具 → 读个人记忆入口 → 理解身份/目标/原则/偏好/上下文 → 按任务选择相关记忆 → 参与推理/表达/行动 → 产生新经验写回或更新。

好处：①换 AI 工具摩擦几乎为零（recall 自动加载身份/偏好/上下文，接得住连续任务）；②复利效应（经验/原则集中在同一记忆库，每次调用叠加）；③AI 从「执行工具」变「协作伙伴」（基于身份/原则主动做判断，如提醒「这个人还没对齐」）。

下一步优化：①记忆升级仍依赖人工（计划自动识别"经验被反复调用 N 次建议提炼为技能"）；②记忆冲突与过期缺自动检测（两条原则打架/某 context 三个月没更新，目前被动靠人发现）。**刻意不做全自动**：每条记忆写入前都要用户确认——不是做不到，而是希望记忆库维护「更好版本的我」而非「现在版本的我」，全自动沉淀会把临时的、不够好的判断也加进去，久了反而困住自己。
