小米技术团队关于 Harness Engineering 从个人实践到团队标准的三次跨越。

## 三次跨越

### 第一次：把流程写进 Prompt

初期用 /flow 命令将开发拆分为需求分析、方案设计、编码、测试、评审等标准化环节，用结构化 Prompt 模板约束 AI。根本局限：Prompt 是"软"约束，AI 可能绕过规则，上下文压缩后可能"忘记"约束，且无法核验 AI 的实际操作。

### 第二次：把约束下沉到 Hook

在 Claude Code 的 PreToolUse / PostToolUse 生命周期挂载检查脚本：工具执行前检查阶段和准入条件，执行后记录关键事件。首次具备了可执行的流程强制力。但系统是"单体"的——Hooks、命令、门禁脚本、知识库分散在各项目本地目录，靠 rsync/git pull 分发。

### 第三次：把约束沉淀为可复用能力（插件化）

整套管控逻辑封装为 Claude Code 插件，通过内部 Marketplace 统一分发。三重故障闭锁机制：
- Bash 状态守卫：检查可能修改受保护状态的命令
- 源码守卫：方案未完成校验前阻止修改业务代码
- 状态文件防篡改：仅允许通过专用接口更新

门禁引擎（workflow-gate.sh，约 2600 行）统一验证器完成 5 路检查：技能事件、CLI 事件、工件、度量和项目状态。

## 双通道证据

任何关键步骤同时留存两份独立证据：
- 工程工件：AI 在文档中记录技能、完成时间等
- 工具执行记录：Hook 自动写入事件记录，不依赖 AI

验证时同时检查两个来源。工件有证据但工具事件不存在=AI 声称完成但未执行；工具事件存在但工件缺失=工程产物不完整。

## 质量门禁三层拦截

1. PreToolUse 源码守卫：方案阶段阻止修改业务代码（exit 2 = 阻断工具调用）
2. PreToolUse Commit 守卫：前置步骤未完成无法提交
3. Bash 状态守卫：审查命令，仅放行白名单只读操作

## 实测数据（2026-04-24 至 06-05）

- 3 个业务项目，6 名开发者
- 23 个正式需求完成流程归档（21/23 未跳过必经步骤，合规率 91.3%）
- Flow 首尾耗时中位数约 23.4 分钟，均值约 38 分钟
- 同类需求可节省约 40%-50% 开发时间（团队经验口径）
- 110 份知识类 Markdown（首次审计发现 15 项高风险错误，修复后补充 64 项遗漏）
- Brainstorm 阶段经模板约束后从 25 分钟降至 12 分钟

## 案例：GP Inline Install

完整 /flow 案例：减少 3 轮评审修改，减少 2 个功能缺陷。关键决策：brainstorm 阶段"安装时机"初稿选"应用启动时"，模板强制要求 2 个备选方案后改选"用户首次触发广告场景时"——避免后续 2 个功能缺陷。propose 阶段一次 AI 跳过 CLI 直接生成 proposal 被门禁检测并阻断。

## 诚实边界

- Bus Factor = 1：整个约束引擎是一人维护的 2600 行 Bash
- 平台锁定风险：深度依赖 Claude Code Hook API
- 标准流程偏重低风险小改动，需轻量路径
- 因果链尚未完全建立（合规率到业务结果的归因仍在积累）
- 最小可行版本：50 行脚本→一个状态文件+一个拦截器
