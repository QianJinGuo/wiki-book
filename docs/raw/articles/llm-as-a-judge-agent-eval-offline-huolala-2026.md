# 重塑 Agent 度量衡：基于 LLM-as-a-Judge 的离线评估体系与实践

## 1. 背景：Agent 评估的困境与需求
当前的 AI 外呼已经从传统一问一答的 FAQ 模式演进为 AI Agent 模式，复杂的业务场景要求 Agent 必须同时具有两种能力：FAQ（知识解答），精准理解并生成回应用户疑问的话术；SOP（流程执行），严格遵循预设的业务策略推进对话，针对用户具体需求进行自主规划（planning）并在合适时机传递正确的参数调用合适的工具，通过执行工具（action）切实解决用户诉求。

随着 AI 外呼对话复杂度提升，Agent 系统不可避免需要进行不断的技术迭代（持续优化 prompt、扩充 RAG 知识库、或替换底层基座模型等）。在这一过程需要构建一套可量化的度量标准：防范功能退化（Regression），确保每一次局部的策略调优或知识库更新没有导致系统其他核心能力下降（避免"修好 20 个 Badcase，却搞坏了 80 个 Goodcase"的盲目迭代）；量化迭代收益（Optimization），在更换基座模型或部署方式时，通过明确的数据指标证明新版本确实优于老版本，为架构选型提供客观决策支撑。

传统大模型评测侧重于静态检验单次输出的"正确性、流畅度与合规性"。而 Agent 作为具备调用外部工具与自主决策能力的系统，评测对象也应作出改变：不仅评估"最终结果"（回复话术是否符合策略设定、能否达成业务目标），还要校验"中间过程"（能否在正确时机触发正确工具、传递给 API 的参数是否正确）。在 AI 外呼的复杂交互场景下，Agent 面对的是泛化且不可预测的多轮对话，传统测试方案已无法满足迭代需求。正则匹配规则无法覆盖所有相同语意的回复（"5米2及以上的车型是一口价"和"货拉拉的大货车都是一口价"语意一致但规则匹配判定不一致）；人工评测极度耗时（约 800/人天），且长对话时人工判定标准容易被个人主观影响。

破局点：引入 LLM-as-a-Judge，构建一套客观、高一致性的自动化 Agent 评估引擎。

## 2. 行业调研：LLM-as-a-judge
Agent = LLM + Harness。LLM 是纯粹的文本输入/输出，自身不能直接操作外部世界，职责是基于上下文进行语义理解、意图识别，并生成回复内容或输出调用工具的指令；Harness 负责将 LLM 包装成具有自主行动能力的 Agent，包含系统 Prompt 模块、RAG 知识库检索模块、以及与外部环境交互的工具调用执行器。

评估手段对比（按评估场景与评估对象）：
- 无参考打分（Reference-free / Point-wise）：提供详细评分维度或检查单（Rubric），不提供参考答案，让 judge 模型直接对单次输出打分（如 1-5 分）或做二分类判断（如 Yes/No）。
- 有参考对齐（Reference-based）：提供"黄金参考答案（Golden Answer/Ground Truth）"，强制 judge 模型比对当前输出与参考答案的核心事实和语义一致性。Google 在 Gemini 迭代时在 GPQA、MATH、MMLU、MTOB、Natural2Code 等公开 benchmark 上验证模型能力。
- 双盲对抗（Pairwise / GSB）：judge 模型同时接收版本 A 和版本 B 的输出，盲测对比，直接输出胜者（Win/Tie/Loss）。Google 称为 Auto SxS（side by side）。
- 动态轨迹评估（Agent-as-a-Judge / Trajectory Eval）：在离线仿真环境中运行 Agent 进行多轮交互，judge 模型最终对整条对话轨迹（Trajectory）和业务结果打分。Anthropic 构建沙盒环境（Sandbox environment）并使用大模型审查系统（LLM-based Auditing System）对中间 API 调用链进行逐行审查。

## 3. 方案设计：场景定制化
Google 和 Anthropic 的通用评估手段无法直接应用在大车外呼场景：大车 AI 外呼是针对特定业务场景的，公开 benchmark 无法衡量 Agent 在指定业务场景下的表现；业界方案仅定义了通用评估手段，缺乏多种方案如何协作的评估细节。

在日常迭代中：基础模型（LLM）的优化不仅会影响 SOP（遵循 prompt 推进流程、调用工具），也会影响 FAQ（即使完全相同的 prompt 和参考话术，也可能给出完全不同的答案）。在基础模型不变、仅仅是 Harness（非 LLM）优化时，基础模型的理解能力保持稳定，因此只需要验证 SOP。

### 3.1 基础模型（LLM）优化场景的评测
#### Reference-based + GSB 混合方案
为什么不能单独用 Reference-based？它只能判断线上模型和候选模型是否"正确"，但无法在两个"正确"的回复中判断"更优"话术。候选模型 100% 正确并不代表其具备与线上模型相当（或更优）的话术回复能力。为什么不能单独用 GSB？GSB 虽然能判断话术的"优劣"，但无法决策回复是否"正确"。即使候选模型与线上模型胜率相同，也无法得知候选模型是否以牺牲业务事实的"准确性"换来表面上"更优"的回复。

方案是把 Reference-based 和 GSB 结合，在"正确"的前提下选择"更优"回答：
- 第一关：Reference-based（回归拦截）：确认候选模型在 goodcase 中未发生退化，确保能力有保障。评估指标为迭代前后的语义一致率，打分逻辑是设计明确评分标准，统计输出发生退化的占比。
- 第二关：GSB（细节寻优）：在验证"正确性"后，针对话术细节等主观维度进行对比，最终决策出更优模型。评估指标为 Win rate（新模型 vs baseline），采用 GSB（Good/Same/Bad）体系统计 Win Rate。

### 3.2 Harness（非 LLM）优化场景的评测实践
不同于基础模型优化时需要"优中选优"，Harness 的迭代通常是为了修复明确的业务缺陷（Badcase），此时不再适合使用 GSB 方案：追求"确定性达标"而非"主观偏好"，核心关注工具调用与 SOP 遵循等客观事实判定，而非话术体感；聚焦"功能纠错"而非"能力演进"，优化目标明确为纠正错误逻辑，只需确认迭代后没有失去已有的遵循能力。

目前仅尝试了针对 Agent 最终结果的评估：Reference-based 方案。但在复杂工具调用场景，只看最终回复往往会掩盖中间过程的逻辑偏差。由于目前缺失离线仿真环境且不支持获取中间过程，团队计划未来在离线仿真环境中引入 judge 模型对中间过程评估，更白盒化地审查 Agent 的意图分析是否准确、API 传参是否合规，验证 planning-action 循环是否符合策略要求。

## 4. 实践：评估手段实现和效果
实际使用中发现一个关键问题：即使有了完整的 Prompt 框架、选择了能力强的 judge 模型，评估结果仍可能不可靠——LLM-as-a-judge 存在系统性偏见。

### 4.1 系统性偏见消除
judge 模型的打分经常与人类预期不一致。做 GSB 时交换两个输出的位置，judge 模型总是倾向于选择位置靠前的输出。经排查与查阅文献，确认 judge 模型本身存在严重的系统性偏见（Systematic Bias），来源：《Judging the Judges: A Systematic Study of Position Bias in LLM-as-a-Judge》。因此采用"judge 模型选型"和"工程消除偏见"两个方法消除系统性偏见。

Step 1：judge 模型选型。核心原则：judge 模型的能力必须远大于被测模型，因为"评估"的难度远高于"生成"。在大车外呼场景下测试的是 Qwen3 235B，选择了 DeepSeek V3.2 作为 judge 模型。选择能力更强的模型作为 judge 不仅因为"评估"任务本身难度，用 DeepSeek 评估 Qwen 也是为了消除"自我偏好"，这也是消除系统性偏见的策略。

Step 2：系统性偏见消除。将评测逻辑拆解为：是否按业务流程推进对话 → 是否真实准确回应用户 → 语气、用词是否完美，正是为了消除系统性偏见中的"风格偏见"。

### 4.2 大车-提估转场景效果
为验证 LLM-as-a-judge 方案可靠性，在整个迭代周期与最终验收阶段始终将人工标注结果作为基准（Ground Truth）。在促估转场景测试了底层大模型整体切换、推理引擎切换、回归测试三个使用场景，均获得极高收益：极高的一致性——推理引擎切换时模型与人工评估一致率达 97%，回归测试达 98%，验证了大模型评估标注的可信度；极致的效率释放——传统评测占用大量人力，Reference-based 方案过去人工离线评估速度极限约 100 case/小时，交由大模型引擎后 100 个 case 压缩至 5 分钟以内；GSB 方案受限于底层 DeepSeek 接口并发配额限制，大模型跑完 100 个 case 物理耗时拉长到 5 小时（人工需 1 小时），但核心质变在于可以利用晚上闲时使用机器，全程 0 人工干预。

## 5. 未来规划
目前离线评测主要聚焦于 Agent 最终回复。下一步将向更深处探索：引入轨迹与日志评估（Trajectory + Trace），实现对中间过程的精准度量；自动化评测 Planning-Action 循环，建立仿真测试环境自动评估每个"思考-行动"步骤的合理性；构建"评测-归因-修复"闭环，将评估结果与问题根因分析直接关联，通过分析中间输出和工具调用日志精准定位问题源头（意图理解偏差、API 传参错误、还是基模幻觉），最终让评测系统不仅能"发现错误"，还能输出定向的策略/Prompt 优化建议。
