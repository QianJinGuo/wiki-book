# FDE：产品经理管不了的我要管，管得了的我也要管

> 来源：叶小钗。一段数字员工公司 FDE 负责人与产品负责人的争论，逐步收敛出两句话：确定性下沉、不确定性上浮；业务长产品、产品长底座。AI 产品不是一开始就能被完整设计出来的，它更像是在真实业务里一边交付一边生长，而 FDE 恰好站在业务探索和产品收敛之间。

## 争论：B 端 Agent 产品应该做成什么形式

作者在数字员工公司咨询中旁听了一场 FDE 负责人和产品负责人的争论：AI 时代 B 端 Agent 产品该做成什么形式，以及如何设计才能兼顾可处理问题难度、结果确定性和灵活性。

业务复杂度低时可以保证确定性足够高；业务复杂度过高时，用工作流缺少灵活性且难以维护，但 Agent 驱动又很难保证结果确定性。

一开始聊技术：业务理解该承载在什么载体上、Workflow 在哪里承载、数字员工怎么定义。慢慢聊到产品边界：产品负责人认为产品必须有边界，什么能做、什么不能做必须定义清楚，否则客户每来一个需求就得重新开发，最后做出来的是越来越复杂的项目平台而非产品。FDE 负责人观点相反：现在大量 AI 项目本就在产品边界之外，客户不会因为产品只能做到这里就只提这些问题，甚至说出"产品实在做不到，我可以不用你的产品来交付"。

一路又聊到交付方法论、平台架构设计、Agent 商业模式和团队投入。背后始终是同一个问题：一个复杂、模糊、不确定的客户问题，怎样能变成可以规模化交付的产品能力。

## 压缩不确定性

回到最传统软件逻辑。业务复杂度低、规则可说清、输入输出明确、异常可枚举时，最好用程序实现。程序最大价值是确定性——同样的输入尽量给出同样结果，出问题可定位到节点，改规则可明确解释影响面。

软件产品本质上一直在做一件事：把无限复杂的现实世界切出一个有限边界，再把边界内问题的解法封装，让边界内部尽可能稳定。去年 Coze、Dify 流行时 AI 项目主流路径是：现实业务 → 业务规则 → 显性化 SOP → 程序承载的 Workflow → 标准产品 → 商业化、规模化复制。产品经理做需求抽象、功能设计、流程标准化，都是在交付前尽量减小不确定性。

如果 100 个客户要重复做 100 次调研、设计、开发，那只是项目；100 个客户有 80 个能用同一套东西，才逐渐成为产品。

## 扩展问题难度

现实业务可从确定性高到不确定性高划一条线：规则 → 程序 → Workflow → LLM 节点 → Agent → 业务专家。越向左越适合软件方式，越向右越依赖理解、判断和探索。

规则判断、固定格式数据处理、状态流转适合软件；经营分析、复杂销售跟进有多种可能，不一定能提前写成固定流程。这些事靠人做，不一定是因为没流程，可能理完流程才发现判断分支多到难以穷举和维护。业务专家内化了判断逻辑，总比别人更好更快定位问题根因和方案。LLM 节点和 Agent 在这里衔接固定流程与业务专家中间的部分，把过去必须由人承担的一部分系统化承接。

## 有限自由度

这里容易产生误区：既然 Agent 能处理不确定问题，是不是复杂业务就不用再理清了，配好工具、上下文和权限直接让 Agent 自由发挥？这恰恰是很多 AI 产品设计里最大的误解。

Agent 的价值不是替代业务梳理，而是承接梳理之后仍然无法完全穷举的部分。更合理的架构是：**确定性下沉，不确定性上浮**。能写成规则的不要交给大模型，能固化成 Workflow 的不要让 Agent 每次重新规划，真正无法穷举、必须结合上下文动态判断的部分才交给 Agent。

系统内部分工：规则/程序处理高确定性逻辑；Workflow 承接已理解清楚的流程；Skill/LLM Node 承接局部判断、语义理解与能力调用；Agent 负责目标驱动下的动态规划、跨流程组合和剩余不确定性处理。所以 Workflow 和 Agent 是分层协作模式，且不静止——随着业务理解加深，原本交给 Agent 的一部分判断会继续向下沉淀成 Skill、Workflow 甚至规则。

## 创造性任务能不能进生产

生产应用需要有明确的验收标准，如果最后结果对不对都不知道，怎么敢让它进入生产。但生产本来就存在不可穷举任务，可穷举任务在 AI 时代之前就被处理了大部分，AI 项目要面对的大多是不可穷举任务。方案设计、研究分析、路径规划本身包含探索，很多 AI 任务只能做到风险可控。

传统软件：生产可用 = 结果基本可预测。Agent 系统：生产可用 = 确定部分足够稳定 + 不确定部分有边界 + 高风险可以发现和接管 + 结果可评估。

AI 生产任务分三层：
- **确定性任务**：规则/程序/Workflow，目标稳定执行一类任务。
- **约束型任务**：加 LLM Node 节点判断，有明确边界和评价机制，可随时发现和接管，目标在约束内提高质效。
- **探索型任务**：只有可控目标，由 Agent 动态规划、多步探索，目标提高原来人的能力上限。

三种任务无法用同一种产品设计方法，硬塞进一套平台必然越来越复杂——这也是很多通用数字员工平台最后不好用的原因之一。

## FDE 与不确定性

前面解决已经理解的业务内部如何分配确定性与不确定性。如果连业务本身都还没被结构化，产品该怎么办。

产品负责人面对的是已经知道怎么稳定解决的问题；FDE 负责人面对的是客户确实有问题，但我们还不知道怎样能被稳定解决。比如客户说要做经营分析 AI 智能化，这不算需求只算想法。继续往下可能发现没有统一数据口径、没有经营分析 SOP、不同管理者关注的问题各异，企业想要的甚至不是报告而是发现异常后的追问、归因和行动建议。

FDE 先把模糊问题逐步拆清楚：客户目标 → 业务建模 → 现状梳理 → 问题诊断 → 优化方案 → 核心 AI 能力 → MVP。他负责去现场，帮助客户把产品暂时无法理解的问题变成可被理解、验证、交付的结构。它属于产品体系前面的**不确定性处理层**——这也是为什么 FDE 负责人敢说不用产品交付：他首先负责的是客户目标能不能达成。

## 边交付边吃业务边完善

传统产品理想状态是先研究清楚用户场景需求、定义产品边界，再规模化卖。但 AI 场景还没成熟，很多业务以前根本没被软件承载过。销售为何这么判断、财务为何追这个指标，多以人的经验为主，坐在办公室设计不出来。问用户什么是对的，他大概率答不上来；但先做一版可运行的 MVP，谁都能说上两嘴哪里不对。

B 端 AI 产品需要不同的生长方式：先基于自己理解最深的业务做出第一个成立的数字员工，放进真实客户里发现产品边界，FDE 进入解决边界外问题，再把反复出现的共性认知重新吃回产品，产品在这一轮轮里慢慢长。但也不是没有边界——先有边界，再不断用真实业务重新验证和扩大边界。产品之外允许探索，但探索出来的东西要回流产品；如果一开始没想清楚这个逻辑，或 FDE 交付的目的不是回流，那就还是定制开发。

## 业务长产品、产品长底座

Agent 底座位置也很简单：不用先设计万能 Agent 平台再往里面装业务，应该越来越多数字员工和 FDE 项目出现相同工程问题后，再把公共能力沉到底座（权限、安全、企业系统集成、运行环境、状态管理、监控）。完整路径只有一条，一句话：**业务长产品，产品长底座**。

## 总结

产品负责人关心哪些问题已经可以被稳定解决；FDE 关心那些产品暂时解决不了的问题怎么办。压成两句话：确定性下沉，不确定性上浮（回答一个 Agent 应用内部怎么设计：能规则化的往下沉，不能穷举的留给 Agent）；业务长产品，产品长底座（回答一家 AI 公司的产品体系怎么长：先做数字员工，再通过 FDE 进入真实业务，把共性能力持续吃回产品，最后沉淀公共底座）。
