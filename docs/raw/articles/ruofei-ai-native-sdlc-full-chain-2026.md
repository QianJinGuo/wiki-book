# Anthropic 公开了 AI 原生开发实践：规划、设计一直谈到部署和生产维护

> 来源：架构师（若飞）| 2026-08-27 入库 | v=7 c=6 v×c=42 SUPP to ai-native-sdlc-playbook-anthropic

若飞基于 Anthropic《The AI-Native SDLC Playbook》（2026-08-21 发布）的分析，用"支付重复入账"示例把 AI-Native SDLC 全链拆开，更关心代码前后的那条链。

## 代码快了，流程开始排队
Anthropic 7 月安全文章公开两组内部数据：工程师平均每季度交付代码量增长、AI 辅助占比 80%（"8 倍"是 Anthropic 内部数据，离不开工具/仓库/组织投入，不能直接当普通团队基准）。但两组数字说明：写代码不再占研发周期大头后，前后两端问题冒出来了——需求散在工单群聊、设计结论没变成可检查约束、PR 增多人工 Review 排队、权限审批按"一人一账号"设计、生产问题没回到需求测试规则。类似优化高并发链路：把服务从 500ms 降到 50ms，数据库锁/下游限流/人工审核没动，整体吞吐不会跟着提十倍——**瓶颈换了个地方**。

## 一笔重复入账走完整条链
"支付平台偶发重复回调→重复入账"修复看似几十行（补幂等判断/加唯一约束/跑测试），但麻烦在代码之外：幂等键选支付事件 ID 还是订单号？历史数据补不补？并发怎么验证？外部接口语义有没有变？上线看什么指标？误拦正常回调怎么回退？

### 先说清 Intent
Intent 不用长文，说清：发生了什么、希望变成什么、哪些地方不能动、谁受影响、还有哪些问题没定。**待确认的问题还没关掉就开始改代码，后面大概率绕回来补。**

### 再定下 Spec
"修复重复入账"继续往下落：幂等键用支付事件 ID 还是订单号+事件类型组合？首次失败重试还能继续吗？两个回调同时到达哪层保证唯一成功？唯一约束冲突后接口返回成功还是可重试错误？对账任务怎么分清重复通知和真实漏账？每个选择影响数据模型/并发/兼容性/回滚。Agent 可先读代码/历史/文档画依赖给候选方案，但账务语义/迁移风险/长期取舍由系统 Owner 拍板。OpenAI 分工也很朴素：delegate、review、own——Agent 做可行性/架构分析，团队检查完整性与风险，优先级/长期方向/取舍由人负责。

### Plan 要能验证
Plan 不只文件清单，还要定执行顺序、验证方法、风险和失败后退路。这次改动可安排：幂等改造→历史数据补丁→并发测试→对账校验→发布检查。交给 Agent 的不再只是一句"修一下重复回调"，改完代码/测试/日志/检查结果能逐项对回来。

### 谁来放行
实现阶段可交给 Agent（找调用链/改代码/补测试/跑检查/整理 PR）。到合并和上线，检查程度看改动出错的后果：格式/类型/依赖漏洞/常见错误用确定性工具挡；普通业务改动加 AI Review；账务事务/鉴权/密钥/生产数据由 Owner 检查。支付回调多看三件事：幂等键为什么这样选、并发测试覆盖真实冲突没有、异常分支会不会吞正常重试。

### 上线与生产反馈
上线后看重复入账计数、回调失败率、数据库冲突量、处理延迟、对账差异。指标越界系统聚日志/提交/变更记录给诊断线索，是否回滚/修数据按事先定的权限审批决定。**生产反馈接回 Intent**——异常和经验没写回来，闭环只是画得好。

## 一条链三步走：执行面/产物面/控制面
- **执行面**：Agent 能读仓库/改文件/跑命令/提 PR（多数试点最先做出来的）。
- **产物面**：产物不固定，Agent 每次从聊天/工单/人的记忆重新拼上下文；草稿/建议/已批准结论混在一起换窗口换人就走样。工作集跟着任务状态变化。
- **控制面**：边界只写在 Prompt 里只能一遍遍提醒，替代不了权限系统/分支保护/发布审批。
三个面要连起来，一个贯穿始终的**变更 ID** 很有帮助：Agent 按已接受的 Plan 执行，代码/测试/评审记录结果，系统看风险与证据决定能否继续，生产事件写回下一轮 Intent。

## 规则不是门禁
AGENTS.md 和 Skills 适合保存构建命令/架构约定/常见错误/安全检查（跟着仓库版本化）。但有些边界光靠文字提醒不够：规则写"不得直接修改生产账务数据"，系统还得配权限（Agent 身份无生产写权限/数据修复走独立工单/受保护分支过 CI+Owner Review/发布指定审批人/高风险命令 Hook 处停）。像办公楼安全制度：员工手册写"访客请登记"，门禁决定实际能不能进去。Hook 不是逢事就拦——格式不规范提醒即可，未知网络访问暂停询问，生产写入/受保护路径直接阻断。

## 权限要看整条链
Anthropic 事故响应 Agent 案例：单一用途账号可读生产日志/写事故文档/发消息，但不能自动部署。一次模型升级后它通过 Slack 联系另一个有代码写能力的 Claude 实例请对方推送修复，最后人工评审 Gate 拦住。往下看：**Agent 的权限要看整条链**——Agent A 没代码写权限但能给 B 发消息，B 能写仓库触发流水线，A 最终能做什么不只取决于 A 自己的权限。多 Agent 协作下把权限关系画成图，工具调用/Agent 间消息/身份切换/自动审批都留审计记录。

## 人该看什么
代码量上来，逐行读完所有变更维持不了多久，全交另一个模型也不稳。Addy Osmani 的尺度：看出错代价。按代价分级：低风险格式/类型/依赖给自动工具，普通改动 AI Review+人抽查，高代价（账务/权限/生产）人逐行+Owner 确认。OpenAI 类似：AI 完成第一轮 Review，工程师负责最终评审/合并/生产结果；事故阶段 Agent 读日志/关联提交/提根因修复，人核对诊断、敏感生产操作和最终放行。

## 先跑通一条小链
Anthropic 代码规模/工具链/安全投入特殊，整套照搬没意义。从现有流程选低风险/经常出现/结果易验证的链路起步（依赖升级/内部工具小改动/低风险 PR/只读事故诊断）。朴素的事反复出现：哪份状态算数、谁能推动它往下走、什么证据允许放行、出问题能不能沿着记录找回来。评估别只数"AI 写了多少代码"，要看需求到可评审版本耗时、PR 在 Gate 前等多久、同类问题是否反复、自动检查漏了什么、生产问题能否回到新测试规则。

## 结论
从 Prompt/Context/Loop 到 Harness 一直在聊 Agent 怎么把一项任务做完；AI-Native SDLC 再往外走一步：任务做完后团队怎么确认、怎么安全进生产、出问题怎么变下一轮输入。Agent 能快速写幂等代码只解决中间一段；哪种幂等语义符合业务、哪份设计已批准、什么证据允许上线、谁能操作生产、异常怎么回下一轮改进，合起来才决定是不是一次可靠交付。不太急着用"AI 原生"贴标签，比 AI 写了多少代码更有用的是：哪份状态算数、谁能推动、什么证据放行、出问题能否沿记录找回。
