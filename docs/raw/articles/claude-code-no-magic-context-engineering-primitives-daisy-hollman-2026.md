编译｜宇琪 策划 | Tina。Daisy Hollman，曾在 C++ 标准委员会深耕近十年、当过两年主席的资深工程师，如今在 Anthropic 的 Claude Code 团队主导插件与 Agent 团队的设计。近日她在 NDC Copenhagen 演讲，介绍 Claude Code 插件的设计与其构成的上下文工程原语，以及 Anthropic 内部如何运作多 Agent 工作流。基于该演讲视频，InfoQ 对内容进行了整理。

## 核心观点

- 如果 Claude 不能做所有你能做的事，它就无法和你一起做你的工作。
- 给 Claude 或者给你的模型，访问你完成工作所需信息的权限，会帮助它更好地做你的工作，或者和你一起做你的工作。
- 我们并不是真的要取代自己，我们是想要成倍地放大自己。
- 定制化就是知识，定制化是在弥合模型天生所知与你们团队所知之间的差距。
- 钩子是唯一真正能扩展的插件抽象，不匹配就不注入，只在触发时才往上下文里放东西。
- 2026 年的核心转变是，从"把信息输入模型"转向"把信息从模型输出给用户"，人的注意力才是系统中最小的盒子。

## 从聊天机器人到 Agent

最初大语言模型是聊天机器人：人类说一句，模型回应一句。2024 年出现工具调用，让模型可以请求计算机去做某件事——执行操作、拿输出、基于结果做决策。工具越来越多，模型可以基于第一次工具调用结果做第二次、第三次调用，到某个节点跨过边界，开始叫它们 Agent。编码 Agent / Agentic 编程 Harness（Claude Code、Codex、Cursor）本质就是 Agent，工具是普通程序员用的：文件编辑、CI 工具、跑代码、编译。

工具调用原始得令人震惊：模型写 JSON，写了某种 JSON 之后就有事情发生，结果喂回上下文窗口紧跟其后的位置。Agentic Harness 里所有东西都围绕这个想法构建：基于输出采取行动、生成新的工具调用、继续循环，这就是 Agent 的本质。

编辑工具是真正让编码 Agent 跑起来的主力工具。Claude Code 编辑工具字面 schema 就是查找替换：旧字符串、文件名、旧字符串和新字符串，没有光标、没有选区、没有引号转义，旧字符串必须逐字节匹配；旧字符串出现多次时要提前声明预期多个匹配，否则失败。模型在这方面的表现好得惊人（生成嵌套引用的 JSON 一个 token 都没错）。上次看到字符串替换错误或编辑工具错误大概在 2025 年 2 月或 4 月——模型已远远超越那个阶段。

METR 图表（"Agent 的摩尔定律"）：模型能以 50% 成功率完成的任务时间跨度大约每四个月翻一番，该趋势今年年初开始停滞（METR 认定过了 Opus 4.6 之后"什么算作 16 小时任务"的误差范围太大，图表几乎不再有用）。但过去三年它一直是相当稳定的趋势，值得考虑至少再持续一两年。Mozilla 基金会 4 月用最新模型修复的安全漏洞数量比过去 15 个月修复的总和还多。

## 为什么要定制化

如果正朝着 AGI 前进，为什么还需要告诉它任何事？第一，它需要能访问它完成工作所需访问的东西；第二，它需要了解你公司里任何员工都能获得的全部机构知识；第三，它必须有工具去获取这些。

开箱即用时 Claude 只能看到一个代码仓库和一个 shell，默认甚至不允许走出启动它的文件夹。这对零到一项目还行（这也是人们在快速原型上看到更多成功的原因之一），但受限上下文对 Agent 的负面影响更大，很少足以在真正大规模范围内做高质量的软件工程。

大多数专业软件工程并不存在于源代码里：决策在团队聊天工具、CI、仪表盘、内部文档、设计文档里做出。建议：试着离开终端做一整天的工作，如果你不能完成全部工作，Claude 也无法和你一起完成。如果你收到 Slack 消息而无法通过告诉 Claude 该替你说什么来回复，Claude 就无法替你回复。

知识（Knowledge）不只在训练数据里。有些东西根本没法训练进模型：不同公司的做法各不相同，如代码库的 Conventions、机构记忆、团队两个季度前尝试过但从未见天日的事情、上周刚发生变化的事情（训练截止日期）、内部 API、内部词汇、术语定义。定制化就是知识，是弥合模型天生所知与团队所知之间的差距。

定制化几乎全部发生在文本层面（上下文学习）：模型权重在发布那一刻冻结，尤其是最近微调接口和 API 逐渐收缩，外面的微调越来越少。这其实很酷，因为程序员最擅长的就是控制文本，不需要知道 LLM 权重的任何数学原理，只需要知道如何操控文本。

Claude 现在工具调用的方式差不多相当于 Unix 的 ED 编辑器（VI 最底层的功能集合）。从 ED / 原始 VI 到 VS Code 之间的巨大鸿沟就是机会所在，而这一切都发生在文本空间里。例如：Agent 的红色波浪线应该长什么样？模型拿的是纯文本，得不到富文本反馈，也无法在输入过程中实时获得反馈，必须自己动手补上这个机制。Claude Code 提供的机制叫 post tool use hook——当 Claude 执行工具调用时，作为工具响应块的一部分附加信息。关键：这段信息你的代码库本来就知道怎么生成（你以前就是靠它鼠标悬停看红色波浪线的），是在错误发生的那一刻给出轻推，而不是等模型回头编译时才意识到。可以放：类型检查、linting、标记 CLAUDE.md 里想让它做但它没做的事。让 Agent 在你代码库里表现更好的最快方式不一定是更聪明的模型，而是更紧密的反馈循环——尽早告诉它犯了错，而且这些脚本大部分你早就有了。

工具分两种：一种是在弥补智能的不足，另一种是随智能一起扩展（对人类或模型都适用）。初级工程师需要工具阻止他们编辑某些文件、运行某些命令；成长为高级工程师后需要一套新工具。但能给出轻推或提醒的工具可以跨越级别——高级工程师偶尔也会犯这些错，但他们也知道什么时候不是错误。构建第二种工具给 Agent，不只想着现在什么能帮到模型，还要想着两代之后、当它变得更强时什么能帮到它。

## 上下文窗口是一个盒子

上下文窗口是模型为预测下一个 token 所能看到的那一组 token，是有限的、固定大小的东西，是你做定制化的空间。过去一年模型能力爆炸式增长，但上下文窗口大小没变：第一批 100 万 token 上下文窗口出现在 2024 年底，2025 年 2 月最前沿模型是 100 万 token，现在大约还是 100 万。扩展速度远远赶不上模型能力的增长。随着任务越来越复杂，往这个窗口里放什么必须越来越聪明。

"上下文工程师"这个头衔与"软件工程师"其实是同一件事：随着 Agent 在写软件、做真正的软件工程方面越来越强，教它们怎么做这件事将会成为软件工程的主要学科。过去要资深到一定程度，全职工作才是确保更初级工程师做好工作；现在只是换成了 Agent，而且你得在每个级别上都能做到。

上下文窗口必须容纳：系统 Prompt、工具定义、CLAUDE.md、Skills、读过的任何文件、任何工具结果。在前面堆得越多，留给后面实际任务的空间越少，每一项定制都在和工作空间竞争，整个代码库根本放不进去。类比：在 Arduino 上跑 npm。npm 有菱形依赖冲突时直接导入两个不同版本就能解决，但定制上下文做不到——你必须智能判断哪个是更相关的信息放进去，把不相关的排除掉。

定制化原则：不为你不用到的东西付费，零开销原则，否则很快把 token 用光。

KV 缓存约束：现代 LLM 的 next token 预测，如果 token 和上一次完全一样，计算成本便宜非常多。计算领域早就遇到过类似问题（相关信息、不太相关信息、非常有限的存储空间），通常做法是 LRU 缓存（CPU 缓存和 Web 缓存都是）。但 LLM 有个硬约束：要预测下一个 token，前面所有 token 都必须保持一致——导致这次的预测成本比那次贵 10 倍，每次工具调用都这么做 token 消耗会极其庞大。Cursor 早期在 Cursor Rules 上就吃过这个亏：最初根据当前任务把最相关规则换进来、驱逐不相关旧规则，本质是 LRU 缓存，结果成本高得离谱。这个问题比单纯做 LRU 缓存复杂得多、微妙得多：预测机制的缓存能力让某些操作非常便宜，另一些则极其昂贵。

## 选择可扩展的插件抽象

场景：5,000 个不同的仓库，每个都想提供三四个 Skill 解释如何在自己的那部分代码上工作；每个仓库都提供自己的 MCP 服务器呢？

**MCP 服务器**：MCP 协议本质上是为系统 Prompt 增加更多工具调用 schema。基于 JSON 的协议，客户端角度非常轻量，传输无关，对消费者有很多不错的属性，但对软件工程师不一定友好。什么时候是正确工具？需要为任何客户端设计集成、需要能和聊天机器人配合、服务端拥有认证权（可移植性优势），代价是得让整套东西在任何环境下工作。如果你已经有一个 CLI，创建一个解释如何使用该 CLI 的 Skill 可能比 MCP 服务器好得多。扩展性：Monorepo 里一千个 MCP 服务器全部加载进上下文，每个工具都有名称、描述和 schema 放进系统 Prompt——20 个 MCP 服务器 × 15 个工具，上下文窗口大部分被工具描述占满。所以它没法在没有帮助的情况下扩展。

**工具搜索**：先加载所有工具的名称，然后给 Claude 一个搜索工具的工具（套娃）。仍然不能完全扩展（一百万个工具照样用光上下文），但比"名称加描述加 schema"好一些。没有太多免费午餐：工具名越有描述性（名称里包含一部分描述），Claude 越可能记得去搜索；名字很随意（如"query"）就很少在正确时机搜它。用 Claude Code 应认真考虑接入多少 MCP 服务器，因为会稀释它找到所需工具的能力。

**Skill**：其实就是文件夹 + 一个 markdown 文件，是一种惰性系统 Prompt：有一堆指令 + 摘要，模型用摘要决定何时展开系统 Prompt 的这一部分（软件工程的老套路：先有一个小的东西，需要时变成大的东西）。skill.md front matter 字段如 description，告诉模型要不要展开完整 Prompt。扩展性：整个正文是按使用付费的，不用就不花钱；但描述是始终加载的，永远在系统 Prompt 里。十万个 Skill 的十万个描述照样用光上下文窗口。所以仍无法完全扩展到谷歌/Facebook 那种大型企业代码库规模。Skill 目前也还没有层级结构的能力。

**Skill 搜索**：我们正在做。比工具搜索难一些：工具搜索只需要模型知道自己做不到什么，Skill 搜索要求模型知道自己不知道什么——意识到自己做不到某件事，比意识到自己不知道某件事容易得多。

**子 Agent**：和 Skill 挺像——给一段简短描述放进系统 Prompt。区别：Skill 让 Claude 把描述直接展开到自己的上下文窗口；子 Agent 把描述展开到独立上下文窗口，单独跑子任务，只返回摘要。从这个意义上扩展性更好。但大型 Monorepo 里成百上千、甚至上万个子 Agent，会开始把上下文窗口很大一部分浪费在这些描述字符串上。理解两者区别的关键点：**Skill 是上下文内的，子 Agent 是上下文外的**。

**钩子（Hooks）**：最受喜爱的抽象，因为它是真的能扩展的。理想抽象应该是：除非你以某种方式判定它相关，否则完全不往上下文窗口里塞任何东西。钩子是：当特定事件发生（一次工具调用、用户提交 Prompt、模型停止工作、上下文压缩），运行一个特定脚本，对脚本输入/输出有一套协议，根据交付输出方式决定是否往上下文窗口放内容。扩展性对比：Rust 项目 + 10 个 JavaScript Skill → 仍要为那 10 条短 Prompt 付费（尽管与工作无关，还得记得手动关掉）；反过来 10 个 lint JavaScript 的 Skill 在 Rust 代码库上工作 → 不会为它们付费，会为运行脚本付费，但脚本立刻发现没在写 JavaScript 就退出——除了 CPU 资源外，不为任何用不到的东西付费，而 CPU 资源比上下文空间宽裕得多。钩子在上下文窗口之外运行，可以写成脚本，也可以把 Agent 塞进去（要谨慎，会非常快烧掉大量 token）。模式：调用脚本 → 立刻判断是否相关 → 不相关快速退出 → 相关则做处理，看有没有相关东西告诉模型。这是红色波浪线所在的地方。

**CLAUDE.md 为什么不是插件抽象**：它在"不为没用到的功能付费"上是最糟糕的——如果提供允许插件在每个上下文最开头无条件注入大量文本的抽象，就会被限制在同时只能激活五到十个插件。实现端成本太低（写插件时第一件事就是创建 CLAUDE.md 解释插件是什么），使用端成本却太高。仍可以这样做（会话开始钩子注入），但至少那样会让你清楚意识到正在消耗大量成本。

**记忆（Memory）**：在插件边界上划出不同线。记忆是模型策展的，全是文本文件——告诉模型写一个文本文件，之后某个特定时间点读它。因为是模型策展的，不认为它是上下文工程的基元。超大规模软件工程的未来，将不得不在"上下文工程"和"记忆"之间做出非常明确的区分，这两样东西需要非常独立地运作。

## 多 Agent 工作流

要扩展规模、提速的唯一方式就是同时做多件事。能舒服地同时管理 20 个 Claude，完成的工作量差不多是管理 5 个时的 4 倍。2026 年的大量工作，就是找出合适抽象，给开发者提供快速切换上下文所需的认知空间。

**Git worktrees** 是起步最简单的方式：每个会话放不同 worktree，各 Claude 不会互相踩脚。/color 功能：给窗口标注颜色，切换时大脑看到颜色触发记忆（有研究表明非色盲人类回忆与颜色相关事物比文字更快）。演讲者实际设置：运行着长期存活的 Agent，16 个常驻 worktree 不够用，现在一直排到了 Z（26 个），每一个独立，且有一个 Agent 知道自己的职责就是长期维护那个 worktree。有持续身份标识的 Agent 很有帮助：固定名字 + 固定记忆，在自己的 worktree 分支里管理自己的临时文件。长期存活的 worktree 名字对应 Agent 名字，都跟踪上游 main 分支，知道要负责管理对上游 main 的跟踪，不会互相踩脚。

**Agent 团队**：给模型提供与其他 Agent 对话的途径。Send message 工具是最基础的原始能力——让 Claude 能够从一个会话向另一个会话发送消息。可以有一个团队领导把任务委派给团队成员，也可以让一堆 Agent 互为平级（其中一个发现什么就分享给其他 Agent）。以某种方式登录并给予权限后，任何一台机器上的任何会话都可以与任何其他机器上的任何会话对话。这是"把 Claude 能访问的东西扩展到你所拥有的一切"的例子：如果另一个 Agent 是你能看到的东西之一，那你就应该让它也能访问那个 Agent。

**/loop**：大约两个月前发布的功能，本质上是一个 cron 命令、给模型用的定时工具——让模型安排一条消息每隔 10 分钟自动出现一次，还能在某个时间点自行关闭（"我已经每 10 分钟看一次这个看了 3 天了，现在关掉"）。相比人类亲自检查 CI、复制粘贴、再重启任务，这点 token 消耗微不足道。问题经常在于模型在完成任务之前就"睡着"了，/loop 真的能解决——给了 Claude 工具确保自己不会在任务完成前停下来。模型越来越擅长理解：如果结果会在 3 小时后才产生，就应该设置机制让自己在 3 小时后被唤醒。

**自动模式**：实现多 Claude 协作的关键，也是能同时跑 20 到 30 个 Agent 的方式——不需要整天坐在那里按回车键。比 YOLO 模式更好：一套复杂的安全保障机制，经过多轮模型和分类器筛查，在阻止或放行之前检查某个操作是否危险；检查所有 Prompt 看是否真的指示去做某件事，没有明确指示做看起来危险的事就会阻止。正是这个机制让 /loop、Agent 团队和过夜运行真正变得可行。代价：有点贵，根据模型不同成本增加 10% 到 40%。

**Claude Agents（Fleet View）**：把信息从模型传递给用户的产品。负责这个功能的团队成员用它在一周内合并了大概一千个 PR。显著扩展注意力的方式：把所有正在运行的东西显示在一个地方。轻量级分类器模型给出模型需要什么、刚刚完成了什么的简短描述，10 个不同的 Claude Code 会话全部显示在一个视图里，可以直接跳进任意一个会话，不用再开 20 个标签页。

**远程控制**：在云服务器上运行持久化 Agent，在手机和 Claude Code 桌面版上与它们交互（演讲者一边从酒店走过来一边通过手机与 Agent 交互完成部分演讲写作）。

## 2025 → 2026 的转变

2025 年是把信息输入模型以获得更好的结果（Agent 编程还处于萌芽期，一直在补偿模型犯下的错误）。2026 年转向把信息从模型传递给用户：用户给模型的信息质量会随着模型变强而变得越来越不重要，不再是瓶颈；更多的问题在于你能多快地切换上下文、多快地扩展工作流，以获取关于模型正在做什么的信息。

最后重申三件事：1、给模型访问权限。2、思考那个盒子——思考你往盒子里放了什么，以及这会如何影响你从盒子里得到什么。3、选择那些能够扩展到大规模、真实世界软件工程的抽象。
