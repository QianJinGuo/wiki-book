# 给 Agent 做「CT」：大规模 Agent 的可观测与质量保障体系

作者：钱世俊，火山引擎应用观测技术负责人。本文整理自其在 QCon 全球软件开发大会 2026 北京站的分享。

## 1 背景与挑战：Agent 的「黑盒」困境

现代 Agent 能自主任务规划、调用第三方工具、利用记忆与知识库沉淀上下文。当系统正常时表现令人满意，但线上难免出现响应变慢、反馈报错、与输入无关的自言自语。传统排查手段难以定位成因，因为无法洞悉 Agent 内部每一步决策。

类比医学 CT：为 Agent 构建「CT 系统」，让研发者看清内部一步步判断与决策轨迹，回答三个核心问题：**可见性**（用户输入到最终输出全过程中 Agent 发生了什么）、**可解释性**（变慢/报错/成本飙升的具体原因）、**可行动性**（从观测数据提炼优化 Agent 的可执行方案并闭环）。

Agent 观测困难归为三个维度：
- **本质差异**：传统应用由确定性代码驱动，因果关系清晰；Agent 自行规划、调工具、沉淀记忆，复杂性指数级增长。
- **决策难分析**：传统日志几乎无法还原 Agent 的思考机制、规划逻辑与执行链路。
- **成本管控**：Agent 内部编排不确定性，逻辑偏差可能在极短时间触发巨量大模型调用，Token 消耗指数级激增。

把 Agent 系统自上而下分四层：**业务应用层**（财务 Agent、投资分析 Agent 等）→ **Agent 框架层**（思考编排与工具调度）→ **大模型推理服务层**→ **云基础设施层**（GPU/网络/容器）。四层观测数据和对象分散在不同系统、关注点各异，导致三个断层：
- **链路断**：不同层次采集方式各异，链路常断裂，业务上下文跨层透传易丢失。
- **语义断**：不同供应商存在链路孤岛，内部链路标准语义不对齐。
- **因果断**：最底层硬件核心指标与上层推理逻辑脱节（如把一次推理异常与底层 GPU 瞬时波动关联极难）。

## 2 破局之道：构建统一观测基座

核心目标：融合多维度观测数据（不只 Metrics/Traces/Logs 三驾马车，还要涵盖 Prompt、模型返回、Token 消耗等 AI 场景特有数据）。协同五大支柱能力：

**①统一观测门户**：将云监控、托管 Prometheus、应用观测、云拨测、日志分析等产品汇聚到统一门户，构建聚合与场景化分析能力（含 AI 观测）。

**②统一集成中心（OneAgent）**：拥抱 OpenTelemetry 标准生态，构建零代码埋点方案与轻量观测配置，打造统一采集器 OneAgent（自研 SDK / OTel SDK / Prometheus / 日志统一采集、加工、预聚合）。自研原因：重载场景需把采集器性能极限推向更高水位。性能优化：发送并发度自适应调整（据 RTT 调并发、本地队列缓存防雪崩）；预排序增强（PB map 字段改为 sortable slice，编码器无需内部排序，效率 +30% 以上，高频方法达一个数量级）；预分配大块内存、栈内存减少逃逸、对象池引用计数、优化日志。在 200K QPS 下 OneAgent 数据吞吐量比 OTel Collector 高一倍左右；线上重载节点压测负载降低 50% 以上，部分极端场景性能提升近三倍。

**③统一数据加工**：清洗过滤（Prompt/Input 敏感信息脱敏，黑白名单过滤探针心跳/压测/调试数据）；数据富化（补集群/地域/租户标签，错误码到业务语义动态映射）；降维转换（日志和链路提取关键字段生成 Metrics）；高基数高密度预聚合；动态分流与冷热存储（热数据高频告警，海量明细进冷存储）。

**④统一看板**：跨类型数据联动（Metrics 异常时同界面唤起日志和 Tracing）；同一视图混绘指标/Trace/日志/拓扑图；兼容 Grafana 模型支持存量 Dashboard 导入导出；预置 AI/Agent 最佳实践看板一键克隆。

**⑤统一告警**：智能告警降噪（规则收敛、去重、依赖抑制，告警风暴收敛为一条核心告警）；统一告警配置管理（一处配置全产品生效）；告警规则开箱即用（TTFT/TPOT 突增、Token 成本暴涨、工具调用大规模失败等预置）。

统一观测底座支撑 Agent 时代三个目标：链路白盒化可见性、根因可解释性（慢在哪/错在哪/成本消耗在哪）、从观测数据回流到评测优化最终线上验证的业务闭环。

## 3 深水区探索：AI 与 AgentKit 深度观测

**AI 通用观测能力**：打通模型推理层到基础设施层完整调用闭环。①制定 AI 语义规范（在 OTel 基础上拓展大模型专属语义字段）；②对不同框架和模型供应商做统一数据规划纳入管控；③把上层 Prompt/Response 分析与底层 GPU 利用率/网络吞吐关联，实现全栈穿透。三项核心能力：精细时延拆解（捕捉 TTFT/TPOT 抖动，判断模型思考变慢还是吐字变慢）；Token 消耗监控（按业务/用户/模型聚合分析，揪出成本大头）；多轮会话分析管理（脱敏后保存上下文/Prompt/Response，用于排障、评估、安全审计）。

**AgentKit 深度集成**：AgentKit 是火山引擎 Agent 研发平台（内置记忆、知识库、监控、评测等基础设施）。提供全局运行时洞察看板（核心环境指标：Token 消耗/调用成功率/调用次数/延迟 + 下钻到模型用量/工具调用量耗时）；白盒化调用链分析（两层：会话诊断分析汇总多轮会话 Trace → 调用链分析展示规划耗时/工具执行状态/大模型交互状态/多模态，通过对比 Span 耗时状态定界问题出在模型生成慢/外部 API 慢/数据处理瓶颈）；记忆和知识库监控（Memory 加载耗时、RAG 检索索引性能、Embedding 耗时、Trace 深度埋点透出召回结果/相关性得分/Chunk 内容）。

## 4 工程化闭环：从可观测到可迭代

四点闭环：**观测数据 → 回流形成评测集 → 评测系统系统化评估 → 持续迭代优化**。

- **定位高价值 Trace**：调用失败的异常场景、高频使用的典型链路场景回流到评测系统，形成覆盖主流场景的高价值评测集。
- **两类评测**：离线评测（每个 Agent 版本上线前新旧版本对比回归测试）；在线评测（线上持续监控误答率上升、Token 消耗异常波动等质量退化信号）。
- **优化动作沉淀**：提示词调整、检索策略优化、模型路由策略切换。
- **两类数据回流**：离线回流（周期性清洗提取高价值 Trace 转评测集）；在线回流（点赞/点踩反馈、核心异常典型链路实时回流，支撑分钟级问题呈现与动态告警拦截）。回流中提供自动化标注能力，将离散观测点对齐为结构化评测数据集。
- **评测系统五要点**：回流数据快速评测动态生成基准题库；评测集灵活管理（版本控制、切片抽样保证样本科学性与场景覆盖）；多维度评测指标体系（准确/相关性 + Agent 专有深度指标：Token 效率、API 调用合理性、规划轨迹分析、拒答率）；自动化与人工协同（大规模自动化评测依赖 LLM 作为评估器但结果会偏离预期，提供白盒化人工复核页面，高价值高风险场景引入人工标注对齐）；评测结果反哺模型与提示词优化、工具接口调整。
- **两个实践发现**：多实验对比分析（并行提示词/换模型/RAG/加工具等多条思路，宏观对比不同实验提升效果、微观分析每个评测数据在不同实验中的表现）；人工标注打分校正自动化 LLM 评估器。

## 5 落地为王：OpenClaw 观测实践

OpenClaw 内部含大量配置文件、众多插件、版本迭代，任何操作都可能导致配置异常无法启动或反馈异常。接入统一观测前，需拉上 OpenClaw 开发/运维/模型/基础设施多个团队分别定位；接入后平均修复时间（MTTR）整体降低 80% 以上。

核心思路：以服务等级指标（SLI）度量先行，数字驱动建设全链路可观测性。OpenClaw 一个请求涉及多步推理、多次工具调用、内部大量状态更新，因此构建多层可归因、面向任务的六层 SLI 体系：**Channel 接入层**（连接成功率、端到端成功率和耗时——北极星指标，用户体感最明显）→ **Message 与 Session 层**（Session 初始化成功率、Session 卡顿恢复成功率）→ **调度层**（出入队列与延迟）→ **执行层**→ **大模型工具层**→ **缓存命中层**，以及定时任务的创建成功率和执行成功率。

数据采集不满足于通用日志，深入 OpenClaw 运行时，通过 Hook 机制在会话开始、模型推理、工具调用、任务分配等关键时间点采集信号，构建自研基于 OpenClaw 的插件保证数据采集完整性和实时性。对比官方 OpenClaw 观测插件和基础日志采集方案，自研插件（多轮……）。
