# 第 13 章 衰减、主权与工程师的下一站

!!! abstract "学习目标"
    - 正视 Harness 衰减：证据、机制与"Build to Delete"设计原则；
    - 掌握"何时不该 Harness"的四问清单与组件保质期检查；
    - 理解主权线：五件不随模型进步消失的工作；
    - 形成自己的判断：Agent 时代工程师的价值坐标。

## 13.1 衰减：每个 Harness 组件都有保质期

本书一路论证 Harness 的必要性，最后一章必须把对立面讲透。**Harness 不是静态配置，模型升级后会出现"旧规则阻碍新能力"**——库内称之为 Harness 衰减（`entities/harness-engineering`）：

- Opus 4.5 → 4.6 一代更新，上一代必要的 Sprint 分解机制反而拖慢速度，去掉后**节省 38% 成本**；
- Anthropic 为 Sonnet 4.5 的"上下文焦虑"设计的重置机制，换更强模型后模型自行消除了该行为，机制不再必要；后来更是删除了 Claude Code 80% 以上的系统提示词；
- Manus 6 个月重构 5 次 Harness，方向是**简化**；LangChain 一年调整 3 次；Vercel 砍掉 80% 的工具，性能反而更好。

**Build to Delete**由此成为设计原则（若飞提出，`entities/harness-engineering` 第 4 来源）：不是先建好 Harness 再优化，而是**先建一个能删的 Harness**——每个组件从设计之初就该可被移除，且移除后系统仍能工作。定期强制删掉一个组件看是否还工作，是衰减检测的直接手段。Harness 工程的真正护城河不是积累了多复杂的规则，而是**删规则的判断力**。

组件保质期检查（每次模型升级执行一次，`queries/harness-minimum-checklist`）：

| 组件 | 它编码的假设 | 检查方法 |
|------|-------------|---------|
| Context Reset | 模型有长上下文焦虑 | 关掉跑一轮 vs 开着跑一轮 |
| Sprint 契约 | 模型无法自己拆任务 | 移除后看生成器是否迷失 |
| 激进压缩 | 模型被冗余上下文干扰 | 降低压缩强度，看质量是否反而提升 |
| 工具格式化 | 模型不会用原始格式 | 原始 vs 格式化对照 |

方法：**每次只移除一个组件**，观察对最终结果的影响。配套的模型迁移检查表（工具 schema 兼容、引用格式、prompt 结构、历史对话 OOD、缓存清空、tokenizer 变化）见附录 B。

## 13.2 何时不该 Harness：四问

`concepts/when-not-to-harness-engineering` 把反方立场整理成四条边界条件（第 2 章已引两条，这里给全）：

1. **模型代际更新会主动侵蚀 Harness 价值**——为当前短板建的工件是负债，模型一升级就变成纯摩擦；没有删除机制就不该开始建设；
2. **干预在强模型上可能为负**——Gene-GEP 实验（-9.4）；判断顺序：确定性 API → 单次调用 → 薄循环 → 重 Harness，Harness 是最后一档，不是第一档；
3. **任务不值得时成本永不回本**——一次性脚本、原型探索，上工程约束直接消灭快速探索的价值；
4. **安全边界不在 Harness 里**——沙箱可被逃逸（NomShub 链），"上了 Harness"不是安全结论。

落地为上 Harness 前的四问（附录 B 收录）：

> ① 这个短板**当前模型**还有吗？② 有没有更便宜的确定性替代？③ 任务复用频次撑得起维护成本吗？④ 删除条件现在就写了吗？

## 13.3 裁决的完整形态

第 2 章给出的"分层时序"在这里补上时间维度。库内登记的三个可判定预测（`comparisons/model-capability-vs-harness-engineering`）之外的行业共识是（`entities/harness-engineering` 三阶段演进）：

- **短期（1–2 年）**：工具描述精雕细琢不再重要，Context 管理变声明式配置——工程师从实现细节转向系统设计；
- **中期（3–5 年）**：模型开始自动构建部分 Harness（Anthropic 删提示词已是先声）——工程师从"构建 Harness"变为"**审核和约束自动生成的 Harness**"；
- **长期**：不可消亡的内核固化为"Agent 宪法"——工程变成**治理工程**。

趋势线的一句话版本（`entities/harness-engineering` 第 3 来源）：**更好的模型 = 更简单的 Harness = 更便宜的运行 = 更快的产出**——这是当前最乐观也最可信的 Harness 经济学判断。模型进步不消灭这个工种，它一次次抬高这个工种的工作台。

## 13.4 主权线：五件不消失的事

模型能力提升会接管越来越多的"怎么做"（how）——工具调用、格式适配、基础规划、基础自验证、通用技能封装。但有一类工作不在此列（`entities/harness-engineering`）：

1. **意志注入**：Agent 服务于谁的目标？目标函数由人定义；
2. **权限授予**：权限是被赋予的，不是学会的——GPT-10 也不会自己给自己发写入权限；
3. **环境供给**：Agent 的能力上限由工具集决定，不给浏览器就不能上网；
4. **边界划定**："元 Harness"——约束进化本身的规则。Agent 能自我改进，但"改进到什么程度该停"由人划定，像宪法修改需要更高层级共识；
5. **治理与审计**：评估框架从"衡量能力"演变为"约束行为"。

**主权不可自生**——权力来源永远在权力行使者之外。三个类比：员工不能自己定 KPI；自动驾驶需要人类预设伦理框架；法官的合法性来源在立法机关之外。

对应到工程师个体的能力迁移（Karpathy 的判断，`drafts/karpathy-2026-vibe-to-agentic-engineering`）：亲手代码量（bits）与价值贡献脱钩，价值向**问题定义、语义建模、边界设计、验证体系**迁移。"可以外包思考，不能外包理解"——理解 tensor 关系、定义什么是用户身份、设计权限模型、建立验证体系，这些能力的重要性不降反升，因为 Agent 在这些领域的错误成本最高。

## 13.5 未解问题：诚实的边界

一本讲"可靠"的书，结尾要诚实列出还没解决的问题（`topics/agent-harness-deep-dive-qa`）：

| 问题 | 现状 |
|------|------|
| **行为验证** | 结构质量基本可解；行为正确性未解——AI 生成 PR 被拒率 67.3% vs 15.6% |
| **置信度校准** | Agent 无法表达"我不确定"，对正确与幻觉输出表现同等自信 |
| **编辑格式** | 应用代码变更无标准可靠方式；一个格式变量能让 15 个模型提升 5–14 分 |
| **棕地适用性** | 成功案例多为绿地项目；10 年历史代码库是更难的题 |
| **感知差距** | METR：实际慢 19%，自感知快 20% |

这些未解问题恰恰标注了未来十年工程价值的高地：谁能把"行为正确性"变成可验证命题，谁就接下了下一棒。

## 13.6 结束的话：设计验证者，而非提示词

把全书收回一句话：

> **Agent = Model + Harness；Loop ⊃ Harness ⊃ Context ⊃ Prompt。模型负责可能性，你负责可靠性。**

三层原语各留一句话给你：

- **Harness**：别教模型怎么做，给它一个做错了也翻不了车的环境——每条规矩都是结过痂的伤疤，每个组件都要可删。
- **Loop**：提示给 Agent 的是指令，循环给的是工作；先造验证器，再造循环，永远给循环装熔断器。
- **Graph**：控制流长在确定性代码里，模型负责产生动作，图负责决定什么时候做什么；拆分按上下文边界，协作先定协议。

Samuel McDonnell 那句话，是全书最好的收束（`entities/loop-engineering-feedback-control-system`）：

> "Agent 时代的管理，不是招到能干的工人——工人既能干又便宜。它是设计他们在其中运行的约束。别再设计提示词，去设计验证者。"

而你此刻正在做的事情——把工程经验沉淀为可执行的知识资产、给每一次失败建一条规则、为每个系统写下它的边界——就是 Harness 工程本身。这本书的下一版，应当由你所在团队的事故报告来续写。

## 13.7 练习

**动手**

1. 给你的 Harness 做一次"删除演练"：按保质期表逐项检查，实际移除一个组件跑一轮基准，记录质量变化。删不掉的组件，写出它为什么删不掉——那正是你的系统真正的耦合点。
2. 为你的团队起草一页"Agent 宪法"草案：意志（服务谁）、权限（默认拒绝清单）、边界（L5/L6 清单）、治理（评估与升级路径）。四栏各不超过五条。

**思辨**

1. 13.5 的五个未解问题中，哪一个最可能被下一代模型自然解决？哪一个会**更严重**？（提示：模型越强、产出越多，行为验证与审查带宽越紧张。）
2. "主权不可自生"对你的职业规划意味着什么？五年后，你的价值锚定在"会怎么做"上，还是"决定该不该做"上？
