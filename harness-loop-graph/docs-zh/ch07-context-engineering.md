# 第 7 章 上下文工程：供给链设计

!!! abstract "学习目标"
    - 建立"上下文是供给链"的心智模型：五层信息各按什么策略进出窗口；
    - 掌握渐进式披露——按需加载是控制 Context Rot 的第一杠杆；
    - 会写一份合格的 AGENTS.md（以及不写什么样的 AGENTS.md）；
    - 理解压缩（compaction）与重置（reset）的适用边界，以及模型升级时的上下文责任迁移。

## 7.1 从"塞满窗口"到"供给链"

第 2 章确立了两个事实：上下文窗口不是数据库；填充率超过约 40% 后质量衰退。由此推出上下文工程的第一原理：**Context 不是越多越好，Context 是一条供给链——什么信息、在什么时机、以什么形态、由谁决定进入窗口。**

实践中的工作集模型（`concepts/context-management-agent-systems`，经 `topics/agent-memory-systems` 收口）：总上下文 → 筛选 → 工作集 → Agent 决策。筛选环节的四个敌人：窗口限制、成本、干扰（无关上下文干扰正确决策）、衰减（早期上下文被"遗忘"）。

**分层是应对之道。** 把信息按生命周期与稳定性分为五层（`concepts/harness-engineering-framework`）：

| 层 | 内容 | 策略 |
|----|------|------|
| 常驻层 | 身份定义、核心约束、项目级约定 | 短小精悍，每次在场；太重则第一轮就腐化 |
| 按需加载层 | Skills、领域知识文档 | 默认只注入名称与描述，任务需要时才读全文 |
| 运行时注入层 | 当前任务目标、用户反馈、工具结果 | 任务结束即释放 |
| 记忆层 | 跨会话经验、被否决的方案、已确认结论 | 检索制：用时调入，用完回到存储 |
| 系统层 | 编译器/类型检查/lint 输出 | 由确定性系统产生，是验证的外部基准 |

若飞 2026 年的框架把同一种思想表达为三层装配：**常驻层 → 按需层 → 强制层**（权限、校验、审计在执行层生效，不靠提示词自觉）（`entities/harness-engineering` 第 8 来源）。

## 7.2 渐进式披露：按需加载是第一杠杆

**渐进式披露（progressive disclosure）**是上下文工程里投入产出比最高的实践：默认只注入能力的名称与一句话描述，模型判断需要时才读取完整内容。OpenClaw 的实践是只让子智能体看到技能目录而非全文；OpenAI 对 AGENTS.md 的建议是约 100 行的"目录页"，详细文档放仓库里按需引用（`topics/agent-harness-deep-dive-qa`）。

量化案例（`queries/harness-minimum-checklist`）：Cloudflare 把 2,500 个 API 端点压缩成 2 个工具暴露给模型，token 从 150K 降到 2K（-98.7%）——不是砍能力，是把"目录"和"详情"分开供给。

**为什么不能全量注入？** 一份生产实录给了反例：把知识图谱的 143 条关系全量注入后，误报率（FPR）翻倍；正确做法是 Markov Blanket 式选择——只注入与当前决策因果相关的部分（`topics/agent-harness-deep-dive-qa`）。全量注入不是慷慨，是稀释。

## 7.3 AGENTS.md：怎么写，以及怎么会被写坏

AGENTS.md/CLAUDE.md 是常驻层的主要载体。GitHub 对 2,500+ 仓库的分析与 OpenAI 自己 88 个 AGENTS.md 的实践给出了一份"怎么写"的共识（`topics/agent-harness-deep-dive-qa`）：

- **当目录表，不当百科全书**：约 100 行，指向深层文档；
- **命令优先于描述，代码示例优于文字**；
- **覆盖六个领域**：命令、测试、项目结构、风格、git 约定、边界（不许做什么）；
- **作为免疫系统维护**：每次 Agent 犯错，加一条规则防再犯（呼应第 6 章的错误喂养规则库）。

**怎么会被写坏？** 两个真实教训：

- **巨型文件自伤**：一份 16,000 字符的 AGENTS.md 被截断 11%，恰好截掉了安全规则补充条款——真实生产事故（`topics/agent-harness-deep-dive-qa` 反模式）。
- **文档 ≠ 控制**：ETH Zurich 的 138 任务实测——人写的说明文档只提升约 4% 成功率，AI 自动生成的文档反而降 3% 并多烧 20% 成本。HumanLayer 的对应实践是 **CLAUDE.md 控制在 60 行以内，少写废话，多上硬拦截**：CLAUDE.md 写一万遍"不许 rm -rf"都不如一个 hook——说明是"请求别做"，hook 是"让它根本做不到"（`entities/harness-engineering` 第 5 来源）。

把两者合起来是一张编码智能体组件的功能表（同源）：

| 组件 | 作用 | 偏向 |
|------|------|------|
| CLAUDE.md / AGENTS.md | 汇总项目规则 | Context |
| Skills | 注入特定任务方法 | Context |
| MCP Servers | 接入外部工具与数据 | Context |
| Commands | 固化可重复工作流 | Harness |
| Hooks | 关键事件后自动检查 | Harness |
| Permissions | 限定自动执行动作 | Harness |

## 7.4 压缩与重置：窗口满了怎么办

长任务必然遇到窗口耗尽。两种策略（`concepts/harness-engineering-framework`）：

- **压缩（compaction）**：同一会话内把历史变短——保留决策相关信息的摘要重写；
- **重置（reset）**：直接换干净上下文的新 Agent，交班时交接清楚（把状态写进文件，新会话从文件恢复）。

Anthropic 的发现值得记住：对某些模型（如 Claude Sonnet 4.5 一代），**Reset 才能真正"清空包袱"**——旧上下文里的焦虑与叙事会污染新决策；换到能力更强的模型后，该模型自行消除了这种行为，重置机制不再必要。这再次印证第 2 章的裁决：机制要跟模型的当前边界匹配。

配套的纪律是**启动序列**：会话开始先 `pwd`、读 Git 日志与进度文件、确认当前最高优先级任务，然后才开始工作（`topics/agent-harness-deep-dive-qa`）。状态从文件恢复，不从"记忆"恢复——这是第 9 章的主题，但它本质上是上下文工程的供给侧动作。

## 7.5 模型升级：上下文责任的重新审计

2026 年，Anthropic 披露为更强的新一代模型删除了 Claude Code 80% 以上的系统提示词。若飞据此提出一套"上下文工程新规"（`entities/harness-engineering` 第 8 来源），核心命题是：**模型能力变化后，旧上下文里的每一项责任都要重新确认由谁承担。**六处典型迁移：系统提示词硬规则 → 模型自行判断；示例 → 接口设计；常驻注入 → 按需加载；重复信息 → 唯一事实源；文字约定 → 可执行规格。

落地为五条新规（同源）：

1. 同一产品的上下文配置因模型而异——**模型与上下文配置是同一个发布单元**；
2. 一条信息只承担一个责任；
3. 按需加载必须有触发条件；
4. 接口问题回接口解决，不往上下文里打补丁；
5. 精简之后留证据（对照评测，不是拍脑袋删）。

评测方法：20–50 个真实任务，按模型轴 × 任务轴交叉评测，一次只改一个变量；监控四个信号——任务做对了吗、过程是否变差、旧失败是否回潮、高风险边界是否被碰。

## 7.6 反模式

- **巨型常驻层**。16,000 字符的 AGENTS.md 不是护城河，是截断事故的候补。常驻层越短，按需层越富。
- **把规则写进文档就以为有了约束**。文档的边际效用近乎零（ETH 4%），安全与边界必须落到 hooks/权限（第 8 章）。
- **压缩代替治理**。反复压缩腐化的历史，是在回收噪音。该重置就重置，该外部化就外部化。
- **模型升级只换模型 ID**。上下文配置不同步审计，等于穿旧鞋走新路——上次截断事故式的失效会换个地方重演。

## 7.7 本章小结

- 上下文是供给链：五层（常驻/按需/运行时/记忆/系统）各有进出策略；工作集思想是"总上下文→筛选→工作集→决策"。
- 渐进式披露是第一杠杆：目录与详情分开供给（Cloudflare 150K→2K）。
- AGENTS.md 当目录表（约 100 行）+ 免疫系统维护；但文档≠控制——硬边界靠 hooks/权限。
- 压缩 vs 重置按模型边界选择；启动序列从文件恢复状态。
- 模型升级 = 上下文配置的重新审计：责任逐项确认归属，交叉评测留证据。

## 7.8 练习

**动手**

1. 审计你的项目上下文：打印一次真实请求的完整 prompt，按五层分拣每一部分。统计常驻层占比——超过窗口 10% 就该瘦身。
2. 把你的 AGENTS.md 压到 100 行以内：命令与测试入口留下，描述性文字改成指向仓库文档的链接。对比前后任务成功率。

**思辨**

1. "文档的边际效用近乎零"与"AGENTS.md 是免疫系统"矛盾吗？（提示：前者说的是"用文档控制行为"，后者说的是"用文档沉淀教训"。控制靠机制，沉淀靠文档。）
2. 你的团队里，"模型升级审计"应该由谁负责、以什么节奏执行？写一份一页的检查流程（对照 7.5 的五条新规与四信号）。
