# 第 8 章 工具、权限与护栏：让 Agent 做得到，更让做不到

!!! abstract "学习目标"
    - 掌握工具系统设计的三条纪律：少而准、schema 即合同、反馈即修复指令；
    - 会算工具表征的 token 账（CLI vs MCP vs 代码执行）；
    - 建立权限与护栏的分层模型：软控制（文档）与硬控制（hooks/沙箱/权限）各管什么；
    - 把审批强度对齐任务等级（L1–L6），并理解 fail-closed 原则。

## 8.1 工具系统：约束即提升

Harness 五层里最反直觉的发现集中在工具层（`topics/agent-harness-deep-dive-qa`）：

- **Vercel 砍掉 80% 工具后效果更好**——更少步骤、更少 token、更高成功率。约束 Agent 的解决空间，反而提升表现；
- **Stripe Toolshed 有近 500 个工具，但确定性编排器每次只给模型筛出约 15 个相关工具**——避免"token 瘫痪"（模型在选工具上浪费大量精力）；
- **TerminalBench 的证据**：工具越少，模型越容易选对。上手默认先砍掉 80% 的工具，按需添加（`queries/harness-minimum-checklist`）。

工程含义：工具集合不是能力清单，是**注意力预算**。每个工具的 schema 都要占用窗口、参与竞争模型的选择注意力。

工具形态的 token 账（`queries/harness-minimum-checklist`）：

| 形态 | Token 成本 | 适用 |
|------|-----------|------|
| CLI | 最低（基准 1x） | 有标准命令行的能力（git、curl、npm） |
| 代码执行 | 中等 | 万能后备（必须配沙箱） |
| MCP Server | 最高（约 32x） | 需要标准化接入的复杂 API |

结论：CLI + Skills 是 token 效率的甜蜜点；MCP 留给真正需要协议化接入的外部系统。**给工具写 schema 时记住：schema 是合同**——名称、参数、返回格式一旦发布，模型与提示词都会依赖它，改合同要按接口变更管理。

**Linter 错误消息 = 修复指令**（OpenAI/Stripe 实践）：约束机制不仅要标记违规，还要告诉 Agent 怎么修。一条"依赖方向违规：UI 层不得 import Service 层"远胜一个红叉。OpenAI 把分层依赖（Types→Config→Repo→Service→Runtime→UI）做成 CI 级 Linter——**架构规则机械化，不留给人肉提醒**；Linter 本身也是 Agent 写的。

**Blueprint 模式**（Stripe）：确定性节点"夹住"概率性 LLM 工作——Agent 最多尝试 2 轮 CI，要么成功要么放弃转人工。概率性环节放中间，确定性校验放两端，这个结构适用于几乎所有 Agent 工作流。

## 8.2 权限与护栏：hook > 文档

第 7 章埋的伏笔在这里展开。控制手段分两档（`entities/harness-engineering`、`queries/harness-minimum-checklist`）：

| 软控制（文档） | 硬控制（机制） |
|--------------|--------------|
| "要跑测试" | completion 前强制检查测试结果 |
| "不要越权" | 工具权限/沙箱拦住高风险动作 |
| "别忘了进度" | progress 文件写到磁盘 |
| "别破坏架构" | lint / CI 把边界机械化 |

**安全必须是机制保证，不是口头承诺。** 在 Prompt 里写"请不要做危险的事"是第 6 章七反模式之外最常见的自欺。

一个值得研究的安全设计：Anthropic 的自动模式分类器**只看 Agent 要执行的动作，不看 Agent 嘴上说了什么**——故意为之，防止花言巧语忽悠安全门。这是对提示注入（prompt injection）的结构性防御：外部内容可能操纵模型的"话"，但权限判定锚定在动作本身。

**fail-closed 原则**：生产实录中的本体拦截层用声明式规则在每次工具调用前评估安全性，规则引擎异常时默认拒绝而非放行。护栏的默认方向必须是"拒绝"，因为护栏失效的场景恰恰是没人盯着的场景。

## 8.3 沙箱：隔离的边界要按逃逸面评估

沙箱是 L2 的最后防线，但要按"逃逸面"而非"有无"来评估：库内记录的 NomShub 沙箱逃逸链表明，执行层隔离可被"Shell 内建命令 + 隧道外联"组合攻破（`concepts/when-not-to-harness-engineering`）。**"我们上了沙箱"不是安全结论**——隔离语义（文件系统、网络、进程、凭据四个维度各隔离到什么程度）才是。

配套的第 6 章分级表在此重申：高风险场景（自动化运维、金融、医疗）必须部署完整护栏链并加人工审核节点，任何 destructive 操作都要有可逆路径与审计日志（`entities/harness-engineering`）。

## 8.4 审批强度对齐任务等级

把第 2 章的 L1–L6 翻译成权限设计（本书综合）：

| 任务等级 | 权限设计 |
|---------|---------|
| L1/L2（可静态校验/可测试） | 全自动，验证器把关 |
| L3（验证不完备） | 自动执行 + 抽查门禁 |
| L4（验证成本高） | 计划审批制：先审计划再执行 |
| L5（资金/身份） | 动作级人工确认（删库、扣费、发客户邮件） |
| L6（法律/伦理） | 人主导，Agent 只做准备工作 |

关键设计不是"哪些要审批"，而是**审批的粒度与时机**：事前审批计划（便宜、批量）+ 事后审计动作（完整、可回溯）的组合，比每个动作都打断人高效得多——这正是"等待很贵，纠正很便宜"在权限层的应用。

## 8.5 错误→约束：护栏的生长方式

第 6 章的运营哲学在护栏层的具体形态：**每次真实的安全事件或执行事故，都应转化为一条机制约束，而不只是一条文档提醒。** Ghostty 的"每条规则都是结过痂的伤疤"在护栏层的版本是：每条 hook 都对应一次真实的翻车。

一个护栏的生长周期：

```
事故发生 → 复盘定性（人为/模型/环境） → 选择控制档位
  （文档提醒 / lint 规则 / hook 拦截 / 权限收紧 / 人工门禁）
→ 上线 → 定期评审：这档约束是否已可降档？（对照第 13 章衰减检查）
```

## 8.6 反模式

- **工具堆砌**。50+ 工具是七反模式之一；工具数量应服从注意力预算，不服从"我们有能力做"。
- **权限一刀切**。要么全放开（裸奔）要么全审批（没人干活）。正确做法是按 L1–L6 分级，把人力集中在 L4 以上。
- **把沙箱当安全结论**。按逃逸面评估，四个维度（文件/网络/进程/凭据）分别写清隔离程度。
- **护栏永不降档**。只加不减的护栏会变成第 13 章说的"过拟合负债"；每条约束都该有重估日期。

## 8.7 本章小结

- 工具三纪律：少而准（Vercel -80%、Stripe 500→15）、schema 即合同、错误消息即修复指令。
- Token 账：CLI 1x、代码执行中等、MCP 约 32x；CLI+Skills 是甜蜜点。
- 软控制管沉淀，硬控制管安全；hook > 文档；fail-closed；权限判定锚定动作而非话语。
- 审批强度对齐 L1–L6；事前审计划 + 事后审计动作。
- 护栏按"伤疤"生长，也要按日期降档评审。

## 8.8 练习

**动手**

1. 盘点你的智能体项目的工具清单：砍到 15 个以内需要砍掉哪些？砍完跑一轮基准任务，对比工具选择错误率与 token 消耗。
2. 为你最担心的一个危险操作（如删表、强制推送）实现一条硬拦截：优先级依次是权限系统 > hook > CI 检查 > 文档提醒——能上多硬的档位就上多硬。

**思辨**

1. Anthropic 的"分类器只看动作不看话语"牺牲了什么？（提示：上下文相关的合法动作会被误拦。）在你的业务里，这个取舍应该怎么调？
2. 你的团队过去三个月发生过的 Agent 事故里，有几条转化成了机制约束、几条只停留在"下次注意"？这个比例说明团队的护栏文化处在什么阶段。
