# 第 12 章 评估与可观测：从 vibes 到证据

!!! abstract "学习目标"
    - 理解评估错配：为什么"能跑通"不是生产指标，以及审查开销为何必须计入 ROI；
    - 掌握 Pass@k / Pass^k 的区别与"确定性评分器优先"原则；
    - 建立生产级指标体系：五类指标 + 三个 Harness 核心指标；
    - 会用"POC → 生产"检查清单做上线前的最后一道审计。

## 12.1 评估错配：看不见的审查开销

Harness 报告的数据揭示了一个反直觉事实（`queries/why-agent-poc-fails-production`）：**81%** 的工程领导者表示，编码节省的时间中相当一部分被用于审查 AI 的产出；开发者每天有**近三分之一**时间花在审查 AI 输出的"隐形工作"上。另一组数据更扎心：LinearB 统计 AI 生成 PR 的被拒率 67.3%，人工 PR 仅 15.6%。

**归因**：传统生产力指标（产出量、周期时间）只反映代码交付，完全看不见审查开销。AI 代码率从 25% 提到 90% 的团队，审查成本同步膨胀——**行业过去十年依赖的度量框架，并非为这种新型工作单元而构建**。

度量改革三件事：把"工程师审查 AI 结果的时间"作为一级指标追踪；把审查开销计入 AI 的真实 ROI；区分自动化层级——哪些环节可完全信任 AI、哪些必须人审。

## 12.2 POC 与生产之间隔着什么

第 1 章说"POC 惊艳、上线翻车"，现在给出完整的失败图谱（`queries/why-agent-poc-fails-production` 六大失败类别）：

1. **Harness 体系缺失**：POC 靠人全程盯着，生产无人值守——"一切不可被机器验证的约束，在 Agent 执行中都是无效约束"；
2. **评估体系错配**：POC 只看"功能是否跑通"，不看质量与维护成本；
3. **上下文腐化**：POC 单会话干净环境；生产多会话长周期，填充率超 40% 后衰退；
4. **工具链脆弱性**：POC 只测核心交互；生产的 RPC 超时、降级、事务边界全部失控——隐性知识（"某配置有 85 处引用"）从未被记录；
5. **团队能力断层**：POC 靠技术强者个人技巧；生产需要团队级 Harness 维护能力；
6. **知识未外部化**：POC 场景简单；生产的隐性业务约束 Agent 全都不知道。

本质：**POC 验证的是原始能力上限，生产要求的是可靠运行下限。**两者之间横亘着系统性鸿沟，跨越它的方法是第 6–11 章的全部内容；本章关心的是"怎么知道你已经跨过去了"。

## 12.3 评估指标的语法：Pass@k 与 Pass^k

`topics/multi-agent-systems` 收口的一对指标，值得写进每个团队的评估规范：

- **Pass@k**：k 次尝试中至少一次正确 → 评估**探索能力上限**（"它能不能做到"）；
- **Pass^k**：k 次尝试全部正确 → 评估**上线回归能力**（"它每次都做到吗"）。

POC 汇报几乎总是引用 Pass@k，生产决策几乎总是应该看 Pass^k。两者的落差就是第 12.2 节那道鸿沟的数值形式。

**评分器优先级**：确定性评分器（测试、编译、断言）> 模型评分器 > 人工评分器。第 4 章的验证器三形态在这里变成评估基础设施的选型原则。一个可参考的量化样板：AutoResearch 的五维加权评分——功能正确性 35%、测试充分性 25%、代码质量 20%、安全性 10%、性能 10%，总分 ≥ 9.0 达标。

## 12.4 Shadow 验证：比单元测试更狠的置信度

一份运行两个月的生产实录（`topics/agent-harness-deep-dive-qa`）给出了一个有力的做法：**Shadow 验证**——新旧系统并行运行，22,792 次影子调用比对，99.49% 一致性。实录的原话值得记录：这比 961 个单元测试更能发现真实边界。

影子运行的适用场景：替换既有决策逻辑（Agent 接管人工流程/旧规则引擎）前的并行期。它把"评估"从抽样检验变成全量对照，代价是双倍运行成本——所以它是**过渡手段**，不是永久架构。

## 12.5 生产指标体系

五类指标（`topics/agent-harness-deep-dive-qa`），注意最后一类的特殊地位——**Agent 也要能看到这些指标**：

| 类别 | 指标示例 |
|------|---------|
| 吞吐量 | 首次 PR 时间、合并时间、每日完成任务数 |
| 质量 | CI 通过率、缺陷逃逸率、回滚频率 |
| 人类注意力 | 每 PR 审查分钟数、升级次数 |
| Harness 健康 | 文档新鲜度违规、架构边界违规、测试 flake 率 |
| 安全 | 被阻止的出站请求、权限拒绝、secret 扫描命中 |

Harness 层面另有三个核心指标（`entities/harness-engineering`）：

1. **任务成功率**：目标 > 85%；
2. **错误重犯率**：滚动 7 日窗口，应趋向 0——它是"错误喂养规则库"是否在运转的直接读数；
3. **系统熵增速度**：Trace 状态大小变化趋势——超阈值触发人工复核，防止副作用无限累积。

**Trace 驱动迭代**（LangChain 实践）：从 LangSmith 取 traces，并行错误分析 Agent 做归因，类似 ML 里的 boosting——下一轮改进专注上一轮的失败案例。评估不是上线前的一次性考试，是接入第 6 章运营闭环的常设器官。

若飞的四信号为日常监控提供了最小集合（`entities/harness-engineering` 第 8 来源）：任务做对了吗？过程是否变差？旧失败是否回潮？高风险边界是否被碰？

## 12.6 POC → 生产检查清单

`queries/why-agent-poc-fails-production` 的十项清单（节选合并为八项，完整版见附录 B）：

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 1 | 质量门禁可程序化验证 | "CI 通过"被拆成可判定的布尔表达式，而非自然语言 |
| 2 | 执行与评判角色分离 | 评审者发现了执行者遗漏的问题（分离有效性的直接证据） |
| 3 | 上下文分层加载落地 | 常驻/触发/按需分层实现，填充率不超约 40% |
| 4 | 知识显性化启动 | 隐性约束（字段类型、超时降级、高频变更区）已写入规范 |
| 5 | 度量框架已更新 | 追踪代码交付率与审查开销 |
| 6 | 外部依赖调用规范已记录 | RPC/缓存/配置中心的超时、重试、降级写入 Skills |
| 7 | 变更审计链已建立 | 每个需求有完整变更目录（summary/tasks/review） |
| 8 | 团队角色已调整 | 有专人负责 Harness 维护 |

## 12.7 反模式

- **用 Pass@k 汇报生产决策**：探索上限不是可靠下限。
- **只测快乐路径**：评估集里没有失败案例的 Agent 评估是在给自己发奖状；boosting 式迭代的前提是失败案例进评估集。
- **指标只给领导看**：Agent 看不到的指标无法进入它的自我修正；指标要回流到上下文（第 7 章运行时注入层）。
- **影子运行当永久架构**：双倍成本，用完即拆——记得写删除条件（第 13 章）。

## 12.8 本章小结

- 评估错配的真相：审查开销是隐形税，必须入账；AI PR 被拒率 67.3% 说明质量门禁在生成侧之外。
- Pass@k 管探索，Pass^k 管上线；确定性评分器优先；五维加权是可参考的样板。
- Shadow 验证提供生产级置信度（22,792 次对照），是过渡手段。
- 五类指标 + 三核心指标（成功率 >85%、错误重犯→0、熵增速度）+ 四信号；Trace 驱动 boosting 式迭代。
- 上线前过十项清单——POC 验证上限，清单验证下限。

## 12.9 练习

**动手**

1. 为你的智能体任务各建一个 Pass@k 与 Pass^k 测量：同一任务跑 5 次。两个数字的差值就是你的系统方差——缩小方差的杠杆依次是：更好的验证器、更稳定的状态恢复、更少的工具。
2. 给你的 Trace 加"错误重犯率"统计：同一类错误 7 日内第二次出现即计数。这个指标连续两周不降，说明"错误→规则"管道断了。

**思辨**

1. "Agent 也要能看到指标"——哪些指标应该注入 Agent 的上下文？注入会不会又犯"上下文喂太多"的错？（提示：运行时注入层 + 触发条件。）
2. 你的团队对 AI 产出的审查时间有度量吗？如果没有，第一天该埋哪个点？
