# 第 2 章 模型的边界：为什么工程不可省略

!!! abstract "学习目标"
    - 掌握模型的四类系统性缺陷及其工程含义：上下文腐化、位置遗忘、自评偏乐观、能力错觉；
    - 会用 L1–L6 任务分级判断"哪些事能交给 Agent"；
    - 正视反方证据：模型进步确实在侵蚀部分 Harness 工件——并掌握"分层时序"裁决框架。

工程不能省略，但要省略得有依据。本章从正反两面把"模型能做到什么"盘清楚：先看模型的系统性缺陷（这是 Harness 的需求来源），再看模型进步带来的侵蚀（这是 Harness 工程的边界条件）。两面的证据都来自一线实践与公开研究，而非立场。

## 2.1 缺陷一：上下文腐化（Context Rot）

**事实**：生产实录显示，当上下文窗口填充率超过约 40% 后，Agent 决策质量快速衰退——这就是所谓的 One-shot Syndrome（`queries/why-agent-poc-fails-production`，引 Anthropic 对长程 Agent 四种失败模式的分析）。无关内容占据上下文多数篇幅时，无论模型多强，决策质量都会系统性下降：关键信息被稀释了。这不是能力问题，是信噪比问题（`concepts/harness-engineering-framework` 称之为 Context Rot）。

更早的经典证据是 Liu et al. 2023 年的 *Lost in the Middle*：把关键信息放在长上下文的开头或结尾，模型表现最好；放在中间，成绩显著下滑。窗口越大，"把正确的东西放进窗口"就越不等于"模型会用正确的东西"。

**工程含义**：上下文不是数据库，是昂贵的舞台——只有当前决策需要的角色才该上台。这直接引出第 7 章的上下文分层与按需加载。生产实录的对应实践是：控制常驻层总量，进度持久化到文件系统而非上下文（第 9 章）。

## 2.2 缺陷二：无状态与遗忘

**事实**：LLM 是无状态的，每个新会话从零开始。"上下文窗口之外的一切都会遗忘"（`entities/harness-engineering` 三大缺陷之一）。

**工程含义**：记忆必须放在磁盘上，不在上下文里。模型忘记，仓库不忘记——Git 历史、进度文件、结构化清单才是跨会话状态的合法载体（第 9 章展开）。第 4 章会看到这条缺陷的另一面：Agent 重读自己的代码"看起来 OK"就停（首次合理方案偏见），因为会话内的自我确认不构成验证。

## 2.3 缺陷三：自评系统性偏乐观

**事实**：Anthropic 的研究结论是 "Agents are incapable of accurately evaluating their own work"——Agent 无法准确评估自身产出。库内多份笔记（`entities/harness-engineering`、`concepts/harness-engineering-framework`）记录了同一判断：模型自评存在系统性正面偏差，倾向于认为自己做得比实际更好——为自己的输出辩护、放大成功面、淡化失败面。这是 LLM 的固有倾向，不是个别模型的毛病。

**工程含义**：生成与评估必须分离（Generator-Evaluator），这是第 4 章的核心。软件工程的老话在此完全适用：写代码的人不该测试自己的代码。

## 2.4 缺陷四：能力错觉——用户一侧的偏差

模型的缺陷会传染给使用者。两条值得记住的证据：

- **METR 2025 年的随机对照实验**：经验丰富的开源开发者使用 AI 工具后，实际完成速度慢了约 19%，但自我感知快了约 20%——感知与现实的差距约 39 个百分点（`topics/agent-harness-deep-dive-qa` 引 METR）。
- **"编程肌肉萎缩"**：Anthropic 的随机对照实验显示，学新编程库时，AI 辅助组比纯手写组的理解度低约 17%，最依赖 AI 者最低（`drafts/karpathy-2026-vibe-to-agentic-engineering`）。把理解、调试这些核心任务卸载给 AI，等于放弃通过摩擦建设认知的机会。

**归因**：Karpathy 用 animals vs ghosts 区分人类智能与 LLM——动物的智能来自与环境的持续互动和后果驱动，"幽灵"则由人类文档、统计模式和奖励函数塑造。这个比喻的工程价值在于校准协作预期：把 Agent 当"有动机的同事"会导向错误的管理手段——你不能催它、激励它、骂醒它，这些对幽灵完全无效。有效的手段是第 6–9 章的内容：设计它的环境、约束与验证。

## 2.5 L1–L6：哪些事能交给 Agent

Karpathy 提出的任务分级（`drafts/karpathy-2026-vibe-to-agentic-engineering`），按**可验证性**排序：

| 等级 | 任务特征 | 自主程度 |
|------|---------|---------|
| L1 | 输出可静态校验（格式、常量、纯函数） | 可完全自主 |
| L2 | 可编译、可测试（有明确测试套件） | 可完全自主 |
| L3 | 可验证但验证不完备（依赖部分人工抽查） | 较高程度自主 + 抽查 |
| L4 | 验证成本高（跨系统集成、性能、安全） | 需要审批门禁 |
| L5 | 涉及资金、身份（支付、鉴权、数据删除） | 人主导，Agent 辅助 |
| L6 | 法律与伦理责任（对外承诺、合规决策） | 人主导并担责 |

这张表的判断标准不是"AI 看起来能不能搞定"，而是**错误能不能被快速、廉价地发现**。测试套件完善的代码是 L2；"改了支付逻辑但回归测试不覆盖汇率边界"实际上是 L5。第 8 章的权限设计、第 12 章的评估设计，都建立在这张表上。

## 2.6 反方证据：模型进步在侵蚀 Harness

如果只讲缺陷，本书就成了 Harness 工程的广告。库内 2026 年 9 月的对抗分析（`comparisons/model-capability-vs-harness-engineering`、`concepts/when-not-to-harness-engineering`）记录了反方最强的几条证据：

- **代际侵蚀**：Opus 4.5→4.6 一代更新，去掉上一代必要的 Sprint 分解机制后节省 38% 成本——上一代模型的脚手架，下一代成了摩擦（`entities/harness-engineering` 记录的 Harness 衰减）。
- **强模型上的负收益**：Gene-GEP 实验中，更强的模型加上更长的 Skill 干预，成绩反而从 60.1 降到 50.7（-9.4）。
- **确定性替代更便宜**：任务合适时，结构化 API 比 Computer-Use 式的智能体方案便宜约 45 倍——问题合适时，应该绕过整个 Agent 栈。
- **工件半衰期**：库内以"claim half-life"度量论断的保质期，模型代际间隔约 59 天——为当前模型短板建立的防御，可能两个月后就过时。

**正方的最强证据同样硬**：MirrorCode 长程基准显示，14 小时的智能体运行可以完成人类 2–17 周的工作量——但那是"模型能力 × 执行脚手架"的复合产出，没有脚手架，当前模型在长程任务上的独立完成率急剧下降。

## 2.7 裁决：分层时序

两边证据拼起来的不是二选一，是**分层时序**（`comparisons/model-capability-vs-harness-engineering` 的结论，本书采纳并给出可检验形式）：

> **模型能力决定 Harness 的必要总量（逐代收缩）；Harness 工程决定当前代际的可用地板（逐代抬高）。**

两个错误姿态：用上一代的 Harness 约束这一代的模型（过拟合——Gene-GEP 案例）；用下一代的模型预期取消这一代的 Harness（裸奔——长程任务崩溃案例）。库内据此登记了三个可判定的预测，读者可以自己跟踪验证：

| 检验 | 支持"Harness 长期承重" | 支持"模型快速接管" |
|------|----------------------|-------------------|
| 长程任务上裸模型与 Harness-Agent 的差距 | 持续 ≥2 代模型不收敛 | 一代内收敛 ≥50% |
| Harness 工件平均存活期 | 随模型升级变长 | 变短 |
| 同任务 Harness 开销占比 | 占比下降但绝对收益上升 | 绝对收益同步下降 |

**实践含义**：上 Harness 前先过"四问"（详见第 13 章与附录 B）——这个短板当前模型还有吗？有没有更便宜的确定性替代？任务复用频次撑得起维护成本吗？删除条件写了吗？

!!! note "事实 / 归因 / 实践"
    40% 填充率、METR 19%/20%、Anthropic 17%、Gene-GEP -9.4、38% 成本、45 倍成本差为**事实**（各库内笔记标注了原始出处，转引时请以原始研究为准）；Context Rot 与"肌肉萎缩"的解释机制为**归因**；L1–L6 为**实践框架**（Karpathy 提出的判断工具，非自然定律）。

## 2.8 反模式

- **用昨天的缺陷论证今天的架构。** 引用"模型有幻觉"来为三层冗余校验辩护之前，先在当前模型上复现这个幻觉——缺陷清单也有半衰期。
- **用明天的模型规划今天的落地。** "等下一代模型就省事了"不是工程决策。生产系统的可靠性地板只能建在已发布的模型上。
- **把 L5/L6 任务包装成 L2。** "支付逻辑有测试覆盖"不等于支付逻辑可完全自主——测试覆盖的是你想到的边界，L5 的定义恰恰是错误后果超出验证范围。

## 2.9 本章小结

- 模型有四类系统性问题：上下文腐化（约 40% 填充率后衰退）、无状态遗忘、自评偏乐观、以及传染给用户的能力错觉。这些问题定义了 Harness 各层的需求。
- L1–L6 按**可验证性**（而非"看起来难不难"）划分任务自主级别，是权限与评估设计的地基。
- 模型进步确实在侵蚀 Harness 工件（38% 成本、-9.4 负收益、45 倍成本差），正确结论是分层时序：必要总量逐代收缩，当前地板逐代抬高。
- 工程姿态：上系统前过四问，给每个工件写下删除条件。

## 2.10 练习

**动手**

1. 给你当前项目的一个 Agent 任务打 L1–L6 标签，然后对照你给它配的权限与验证强度——多数团队会发现自己把 L4 当 L2 在跑。
2. 复现实验：取一段 8K token 的文档，把关键约束分别放在开头、中间、结尾，问同一个问题三次，记录回答质量。这是"Lost in the Middle"在你自己的模型上的版本。

**思辨**

1. 2.7 节的三个预测，你押哪一列？写下你的理由和检查日期（比如两个模型代际之后），到期对照——这是本书希望读者养成的"预测台账"习惯。
2. METR 的"感知快 20%、实际慢 19%"对你的团队意味着什么度量改革？（第 12 章会给出答案：把审查开销计入 ROI。）
