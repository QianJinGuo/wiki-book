# 第 11 章 多智能体编排：拓扑、协议与隔离

!!! abstract "学习目标"
    - 掌握单智能体 → 多智能体的迁移判据，以及"按上下文边界拆分、不按角色拆分"；
    - 熟悉两种基本拓扑（Orchestrator-Worker 与 DAG）的取舍；
    - 学习一线生产案例的五个机制：约束金字塔、CP 检查点、Spec 文件驱动、状态机、生成-评估分离；
    - 记住多智能体的第一性风险：幻觉级联放大与协议缺失。

## 11.1 迁移判据：默认单智能体

库内的对照结论非常直接（`comparisons/single-agent-vs-multi-agent`）：**约 80% 的场景单智能体就够**。多智能体的复杂度税包括：上下文开销从 1× 变 N+1×、编排复杂度陡增、幻觉可级联放大、调试从单一 trace 变分布式追踪。

迁移判据（同源）：任务能被单一 prompt 描述、推理链不超过约 20 步、不需要并行 → **单智能体**。需要多种专业能力 + 并行 + 隔离试错 → 才考虑多智能体。反模式：为了"看起来高级"过早多智能体化。

**拆分维度是本章最重要的一个判断**（`queries/harness-minimum-checklist`）：按"这份上下文只有这部分需要知道"的**上下文边界**拆，不按"前端 agent/后端 agent"的角色拆。拆分的收益恰恰来自上下文隔离——每个子智能体只装载自己需要的上下文，这是对第 7 章供给链原则的多智能体推广。

阿里云数据研发团队的实践补了一条元原则（`entities/harness-engineering` 第 7 来源）：**协议先于协作，隔离先于并行**——没有协议和隔离的多智能体并行只会放大幻觉和问题（`topics/multi-agent-systems`）。

## 11.2 两种基本拓扑

`comparisons/orchestrator-worker-vs-dag-agent` 的对照表：

| 维度 | Orchestrator-Worker | DAG-based |
|------|---------------------|-----------|
| 调度 | 集中式：编排者统一派活 | 图拓扑：节点独立消费上游输出 |
| 状态 | 编排者是唯一 state holder | 每个节点分布式状态 |
| 故障 | 编排者单点故障 | 单节点故障可重试分支 |
| 适用规模 | 3–10 个子智能体 | 10–100+ 节点 |
| 调试 | 低（调度集中在一处） | 高（必须分布式追踪） |
| 代表 | OpenClaw、AutoGen 类 | LangGraph、CrewAI 类 |

判断：OW 适合中等规模，调试与容错都简单；DAG 适合大型工作流，能扩展但运维门槛高。**多数项目从 OW 起步，规模到了再迁 DAG**——这与第 10 章的"循环→图"路径一脉相承。

更细的协作模式谱系（`topics/multi-agent-systems`）：Orchestrator（集中分发汇总）、Manager（层级监督）、Supervisor（单一专家决策）、Hive（去中心化并行）、Swarm（自组织动态协作）。两个特殊形态值得认识：**Blackboard**（共享黑板 + 控制器运行时决定激活谁——任务复杂度随时间增长、角色边界不清时用）与 **Ensemble**（同一任务多副本并行，投票融合——用冗余换可靠性）。

## 11.3 生产案例：阿里云数据研发的六个机制

`entities/harness-engineering` 第 7 来源记录的完整落地，是本章最值得精读的部分：

1. **编排者 + 四专家**：协调者 Agent 不写代码，只负责调度/把关/评审/汇报；四个子专家（需求拆解/方案生成/代码开发/测试验证）。每个 Agent 的能力定义"很薄反而稳"。
2. **三层行为约束金字塔**：超级红线（少而精，违规即事故）→ 错误记录（历史教训）→ 操作规则（流程模板）。约束分层的本质是**信号强度分级**——全部喊得震天响，Agent 对所有约束都麻木。
3. **CP 检查点**：每个阶段结束强制压缩为固定格式摘要（结论 + 关键信息 + 待关注事项），**不把整段对话历史传给下游**——下游无需回溯几十轮对话，上下文窗口干净。
4. **Spec 文件驱动**：Agent 之间不直接对话，通过结构化文件交换信息；编排者只传文件路径。五重好处：可追溯、可审计、可恢复、可解耦、可隔离。
5. **生成-评估强制分离**：子专家埋头干活，协调者拿 checklist 逐项验收——自己不能既当运动员又当裁判（第 4 章原则的编排层落地）。
6. **12 态状态机 + 三级故障恢复**：从需求接收到完成共 12 个状态枚举；故障分可重试/需回退/必须中止三档处理（第 3 章止血带的多智能体版）。

## 11.4 通信协议：摘要回传与 Inbox

子智能体之间的信息流有三条经过验证的纪律（`topics/multi-agent-systems`）：

- **摘要回传**：子智能体只回传摘要，探索细节留在自己的消息历史里。过度传递引发误解与上下文膨胀——**幻觉会互相放大**：一个 Agent 的错误信息传给另一个，错误被二次放大。这条风险的定量注脚来自 Anthropic：多智能体配置下非预期解法发生率从单智能体的 0.24% 升至 0.87%（`topics/agent-harness-deep-dive-qa`）——**Harness 不只是性能放大器，也是风险放大器**。
- **JSONL Inbox**：每个子智能体拥有独立的 JSONL 收件箱文件，主智能体写入任务、子智能体轮询处理。追加写入天然适合异步队列，避免并发写冲突。
- **任务图（Task Graph）**：子任务依赖关系用 DAG 管理并可持久化——跨会话恢复时重新加载图结构即可，不需要重新理解任务分解逻辑。

跨系统的标准化通信由协议层解决：MCP（Anthropic，2024 年底发布）解决模型与工具/数据的连接；A2A（Google 于 2025 年发布，后捐入 Linux 基金会）解决智能体之间的任务委托与状态协商。协议选型本身服从第 8 章的 token 账——MCP 的表征成本约为 CLI 的 32 倍，接入前先问是否值得。

## 11.5 反模式

- **多智能体无边界**：角色职责不清、没有协议约束——并行放大的不是生产力，是混乱。
- **过早多智能体化**：单智能体尚未稳定就上多智能体，把单智能体问题放大 N 倍。
- **信息过度传递**：回传全部细节而非摘要，上下文膨胀 + 幻觉级联。
- **缺少验证门禁**：多智能体并行产出直接合并，没有质量门禁——错误在合并点会师。
- **按角色拆分**：前端 agent/后端 agent 的拆法制造了不必要的协作界面；按上下文边界拆，很多"多智能体需求"会消失。

## 11.6 本章小结

- 迁移判据：单一 prompt 可描述 + <20 步 + 无并行 → 单智能体；80% 场景如此。
- 拆分按上下文边界，不按角色；元原则：协议先于协作，隔离先于并行。
- OW 与 DAG 按规模与调试能力选择；多数项目从 OW 起步。
- 生产六机制：薄专家、约束金字塔、CP 检查点、Spec 文件驱动、生成-评估分离、状态机 + 三级恢复。
- 通信三纪律：摘要回传、JSONL Inbox、任务图；幻觉级联是多智能体的第一性风险（0.24%→0.87%）。

## 11.7 练习

**动手**

1. 把你当前"想做多智能体"的任务用迁移判据过一遍：它真的需要并行/隔离/多专业吗？很多团队做完这道题会发现答案是"单智能体 + 更好的验证器"。
2. 实现 JSONL Inbox 协议的最小版：主进程写任务、两个 worker 进程各消费自己的 inbox 文件、摘要回传。用两个终端窗口观察整个信息流。

**思辨**

1. "约束金字塔"的洞见是信号强度分级——全部加粗等于没有加粗。检查你的系统提示词：有几条"超级红线"？它们真的最少、最精吗？
2. 0.87% 的非预期解法发生率意味着什么？如果 1000 个并行子任务里约 9 个会走偏，你的编排者该怎么设计才能把它们拦在合并点之前？
